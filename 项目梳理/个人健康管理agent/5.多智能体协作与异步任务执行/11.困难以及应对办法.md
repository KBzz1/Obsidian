# 困难以及应对办法

## 演化起点：旧版结构为何不够

这一节以仓库里仍然存在的旧版实现作为事实起点。旧版并不是「写错了」，而是一套在单领域任务下成立的先选领域、再在领域内做规划-执行（Plan-and-Execute）的分层；它隐含了一个后来不再成立的假设——一次用户任务只需要选择一个主要领域，进入领域后该领域自己就能完成剩余任务。下面的故障情形不是真实线上事故，而是根据这些真实机制反推出来的工程演化场景，用来解释为什么最终收敛到本笔记其余几节描述的决策。

旧版完整结构：

```text
Root Router / Supervisor
    ↓
Domain Team
    ↓
Planner
    ↓
Orchestrator
    ↓
Worker ReAct Agent
    ↓
Tool
```

这一分层在代码里能对应上几处事实：

- 顶层路由是一次性的。模型完成工具调用（Tool Calling）后，代码只读取 `tool_calls[0]`，据此生成唯一的 `next_node`。它只回答「这次请求先去哪个节点」，不回答「这个任务需要哪些领域参与、它们之间有什么依赖、第一个领域完成后下一步做什么」。这正是 Router（路由）与 Supervisor（会话主管）的区别：Router（路由）是一次分类和分发；Supervisor（会话主管）是持续持有主会话上下文的完整智能体，可以多次调用不同子智能体并依据前一个结果继续决定下一步。
- 领域内部的流程状态全部存在 `TeamState`：`plan`、`plan_history`、`current_step_index`、`manager_instruction`、`next_worker`、`worker_output`、`task_results`、`scratchpad`。Orchestrator（编排器）用它推进串行计划（`current_step_index` 加一），可并行步骤用 `asyncio.gather()` 并行执行、结果收集进 `task_results`。Worker 是用 `create_react_agent()` 创建的 ReAct（推理-行动循环）智能体，只拿到 `manager_instruction`，在自己的工具集合里跑循环，结果回写 `worker_output`、`task_results` 和 `scratchpad`；代码把它描述成「无状态工具人」，且不注入 `recalled_memories`。
- 后来加了 fast-path：当 Orchestrator（编排器）能直接确定工具时，跳过 Worker 的 ReAct（推理-行动循环），直接把该步标记完成。

单看每个环节都合理。问题在于这套设计叠加以后，不同层级的编排职责没有被清楚区分，出现了几个互相不独立的问题：

1. 跨领域任务没有会话级所有者。以「根据最近四周训练负荷调整饮食」为例，它需要先读取并分析训练状态、形成训练负荷结论、再交给饮食领域生成营养调整，是一个跨领域依赖序列。旧版最上层只有一个 Router，没有会话级任务所有者来负责「谁创建下一个领域任务、第一个领域的哪份结果能作为第二个领域的正式输入、两领域冲突后谁重新调度、整个任务什么时候算完成」（对应下文难点七）。
2. 领域内的 Orchestrator 作用域只到领域内部。它的 plan 是 `{worker, instruction}`，`next_worker` 只从本领域 Plan 中选 Worker，能回答「Workout Team 内下一步执行什么」，回答不了「Workout 完成后为什么启动 Diet、Diet 应消费 Workout 的哪一个结果」。这是「领域内的流程状态」与「领域之间的协作协议」两个不同层级的问题（对应下文难点五、难点六）。
3. 继续给 Router 加组合规则不能解决根因。为 `workout + diet` 这类固定组合写专门节点只在少数组合下可用；协作方式一增加，根图（Root Graph）就承担大量业务组合逻辑（能否并行、是否必须先完成、冲突后是否再次调用、谁最终合成、用户确认后从哪个 Agent 恢复）。即便让 Router 一次返回多个工具调用，也只能表达「A 和 B 都需要执行」，无法自然表达「A → Artifact → B」的依赖，也没有跨智能体结果的所有权和交付格式。不断加条件，最终会把这个单步分类器写成隐式 Supervisor（对应下文难点三）。
4. 领域内部抽象开始过重。很多 Worker 的差异只是 Prompt 和工具白名单，却都拥有完整的 ReAct（推理-行动循环）；fast-path 的出现说明系统为了让简单任务绕开通用 Planner → Worker 链路开始增加旁路，透视出 Plan-and-Execute 已不适合作为所有领域任务的默认执行模型（对应下文难点五）。

这几点指向同一个根因：不同层级的编排职责没有被清楚区分。顶层只有 Router、没有跨领域任务 Orchestrator；领域内部反而对大量简单操作默认采用较重的 Orchestrator-Worker。系统的智能编排能力放错了层级。

最终定位是：问题不在 Planner（规划器），而在 Orchestration Scope（编排作用域）。旧版实际上存在两个控制层——顶层 Router 负责选一个领域，Domain Orchestrator 负责领域内部步骤推进——中间缺了会话级的 Conversation Supervisor，需要它来决定是否自己回答、是否需要调用智能体、调哪些智能体、智能体之间是什么依赖、如何依据前一个结果继续、什么时候整个任务才算完成。重构目标因此不是换一个多智能体框架的 API，而是重新划分三个控制范围：

```text
Root StateGraph          → 运行时控制（任务状态推进与恢复）
Conversation Supervisor  → 会话级编排（任务所有权与委派）
Domain Agent             → 领域级执行（ReAct / 领域工作流）
```

下面各节（难点）讨论的取舍，就是在这一演化起点上收敛出的具体决策。

## 难点一：复杂任务是否天然要拆成多个 Agent

多智能体不是一开始就被当成默认执行方式。复杂任务并不天然要求多智能体（Multi-Agent），单智能体配合合适的提示词（Prompt）和工具很多时候已经能完成任务。如果默认拆分，每次请求都会多一层智能体调用成本，而且多个智能体之间的协调本身会带来新的复杂度和不确定性。

所以第五章不做「任务复杂就拆智能体」。默认由一个会话级主管（Supervisor）完成任务，只有当某项能力形成独立的数据所有权、工具集合、业务工作流或大规模专业上下文时，才提升为独立领域智能体（Domain Agent）（升级标准见 [[3.多智能体边界与升级标准]]）。

## 难点二：Agent 边界按什么划分

最容易犯的错是按话题划分：训练是一个话题、饮食是一个话题，就各建一个智能体。话题分类只能说明两个问题语义不同，不能说明它们需要两个独立执行单元——训练和饮食可能各只有几个 CRUD 工具，拆开只是为了分类好看。

真正决定是否值得拆的，是能力所有权和业务所有权：是否拥有一组别人不能随便改的正式业务状态、一组别人不应长期看到的领域工具、一套可沉淀的领域 SOP、一块需要的大上下文，以及独立执行的价值。按这五条，训练与饮食成了自然领域边界，习惯（Habit）只有创建、打卡、查状态等明确操作，还不具备独立业务状态和复杂决策，所以仍作为轻量能力（Capability）暴露给会话主管（Supervisor）（边界见 [[3.多智能体边界与升级标准#Workout 与 Diet 的边界]]、[[3.多智能体边界与升级标准#Habit 为什么不是独立 Agent]]）。

## 难点三：路由语义判断放在哪一层

早期设计里路由是独立的一层 Router（路由）组件，负责判断本轮请求交给哪个执行单元。但 Router（路由）与会话主管（Supervisor）会重复两次语义判断：Router（路由）先判断一次「属于哪个领域」，会话主管（Supervisor）再基于同样的输入做一次理解，两次判断的输入几乎一样。

既然会话主管（Supervisor）本身是持续存在的完整智能体，可以在每一步动态决定直接回答、调用共享能力还是委派领域智能体，领域选择就应该是会话主管（Supervisor）决策的一部分。所以第五章不再保留独立 Router（路由），路由判断并入会话主管（Supervisor）（见 [[4.Supervisor 架构与委派#不设独立 Router]]）。

## 难点四：如何控制委派带来的成本

一次会话主管（Supervisor）→ 领域智能体（Domain Agent）→ 会话主管（Supervisor）一定比会话主管（Supervisor）直接回答多一次模型调用。这个成本不能靠随意的预算上限硬压，也不能靠让所有智能体共用完整历史来省——后者会让每个智能体都面对无关上下文。

控制成本的核心是减少无意义委派：简单请求、常识问题、不依赖领域状态和能力的问题留在会话主管（Supervisor）层直接回答。只有真正需要领域独有的能力时才委派（见 [[4.Supervisor 架构与委派#直接回答与委派的边界]]）。

## 难点五：Domain Agent 内部是否需要固定层级

训练/饮食智能体（Workout/Diet Agent）内部如果默认加一层 Planner → Manager → Worker Agent → Tool 的固定层级，多数场景只是在重复描述已知的状态机：固定流程下 Planner 没有额外信息量，Manager 也只是转一道手。

领域智能体（Domain Agent）默认采用 ReAct（推理-行动循环）循环处理开放式领域任务：模型每轮决定调用哪个工具、拿到结果后继续，直到得到领域结果。已经稳定沉淀的 SOP 则作为领域工作流（Domain Workflow）整体调用，不再要求智能体每次重新规划。固定层级和覆盖所有请求的通用规划-执行（Plan-and-Execute）运行时（Runtime）都被去掉（见 [[5.Domain Agent 执行模型]]）。

## 难点六：Agent 之间传什么

如果智能体之间直接共享完整对话历史或以「A 给 B 发一段话」协作，接收方拿到的是与当前任务无关的其他智能体过程，上下文被污染，而且无法确认对方到底执行到了哪一步。

所以智能体之间交换的是结构化的任务、结果和产物：会话主管（Supervisor）给领域智能体（Domain Agent）一个领域任务（DomainTask，目标、约束、需要的用户事实、上游产物引用），领域智能体（Domain Agent）返回任务结果（AgentResult，终止状态、产物引用、缺失输入或冲突），真正要被其他智能体使用的结果做成版本化的类型化产物（typed Artifact）。跨领域的中间产物由产物存储（Artifact Store）保存，不会自动成为正式业务事实。通信协议见 [[6.通信协议与 Artifact]]。

## 难点七：跨领域冲突交给谁

跨领域协作允许智能体提出影响其他领域的约束，但不能越过业务所有权直接改对方的状态。饮食智能体（Diet Agent）可以读训练负荷作为营养调整依据，却不能直接改训练计划（Workout Plan）；训练智能体（Workout Agent）可以指出当前计划对能量摄入有要求，却不能直接改营养计划（Nutrition Plan）。

当饮食智能体（Diet Agent）无法满足训练负荷带来的营养要求时，它返回 `status = "conflict"`，由会话主管（Supervisor）判断是否创建新的训练修订任务，形成多跳但不越权。每个子任务（ChildTask）都有明确的 `required_output_type` 和终止状态，会话主管（Supervisor）对委派深度和任务数量设置配置化执行预算，避免智能体无限制互相讨论（见 [[8.跨领域协作与冲突#跨领域冲突处理]]）。

## 难点八：交互与后台任务的接回

子智能体（Subagent）默认不持有与用户的会话控制权。发现缺输入时不自己发消息，而是返回 `needs_input`，由会话主管（Supervisor）统一收集多个领域的请求后向用户发问，再按对应的子任务（ChildTask）恢复执行。

后台任务不能靠单纯把函数写成 `async def` 就算异步。真正异步是主智能体启动一个后台任务（job）后继续运行，当前会话不等待任务完成。后台任务建立持久化的异步任务（AsyncAgentTask）记录，完成后先持久化产物（Artifact）、再产生完成事件，父任务按确定性的任务（Task）状态恢复，而不是靠模型读聊天猜测进度（见 [[9.HIL 与异步任务]]）。

## 边界问答

**1. Q：** 复杂任务为什么不默认拆成多个智能体？
**A：** 多智能体会带来额外的调用成本与协调复杂度，而单智能体配合合适的提示词（Prompt）和工具很多时候已经能完成任务。默认由会话主管（Supervisor）完成、只在形成独立能力边界时才提升为领域智能体（Domain Agent），是不为复杂而拆。

**2. Q：** 为什么不给领域智能体（Domain Agent）内部保留 Planner → Manager → Worker 层级？
**A：** 固定层级多数场景只是在重复描述已知状态机，Planner 和 Manager 没有额外信息量。开放式任务用 ReAct（推理-行动循环）循环，稳定 SOP 用领域工作流（Domain Workflow）整体调用。

**3. Q：** 独立 Router（路由）为什么被去掉？
**A：** Router（路由）与会话主管（Supervisor）会重复两次语义判断。领域选择本身就是会话主管（Supervisor）决策的一部分，保留独立 Router（路由）只会多一层没有增量信息的判断。

**4. Q：** 为什么子智能体（Subagent）不直接和用户说话？

**A：** 让子智能体（Subagent）直接交互会把会话控制权分散到各个子智能体（Subagent）。它返回 `needs_input`，由会话主管（Supervisor）统一收集后再向用户发问，会话所有权（conversation ownership）始终在会话主管（Supervisor）。
