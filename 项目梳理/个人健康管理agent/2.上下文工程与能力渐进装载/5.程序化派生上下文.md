# 程序化派生上下文

## 把可确定的计算前置到程序

程序化派生上下文（Computed Summary）把模型每轮反复推导、但程序能确定性计算出来的逻辑前置到运行时：程序算好以后直接注入上下文，省掉模型遍历历史记录自行推断的开销，也消除了这部分推理留给幻觉的空间。

多步骤任务里典型的一例：系统在运行时层面直接计算并注入当前进度指标，替代模型在上下文中遍历历史自行推断：

```python
derived_context = {
    "total_steps": len(steps),                  # 步骤总数
    "completed_steps": count_completed(steps),  # 已完成步骤数
    "remaining_steps": count_pending(steps),    # 剩余步骤数
    "current_step": get_current_step(steps),    # 当前所在步骤
}
```

## 示例：当前工作状态由状态程序化派生

继续「修改训练计划」任务。运行时状态中保存执行阶段与候选产物：

```json
{
  "execution": {
    "phase": "plan_revision",
    "current_step": "evaluate_replacement",
    "completed_steps": [
      "load_plan",
      "identify_target_item",
      "search_replacement"
    ],
    "pending_steps": [
      "evaluate_replacement",
      "save_new_draft",
      "wait_for_confirmation"
    ]
  },
  "task_context": {
    "plan_id": "plan_88",
    "plan_version": 2,
    "target_item_id": "exercise_2",
    "temporary_constraints": {
      "shoulder_discomfort_today": true
    }
  },
  "artifacts": {
    "candidate_exercises": [
      {
        "exercise_id": "machine_chest_press",
        "name": "器械胸推"
      },
      {
        "exercise_id": "cable_chest_press",
        "name": "绳索夹胸"
      }
    ]
  }
}
```

上下文装配器通过固定代码生成「当前工作状态」视图：

```yaml
当前工作状态:
  目标: 完成 exercise_2 的替换
  阶段: plan_revision
  当前步骤: evaluate_replacement
  待处理:
    - 评估候选动作对训练量的影响
    - 保存新版本草稿
    - 等待用户确认

当前环境:
  plan_id: plan_88
  plan_version: 2
  target_item_id: exercise_2
  candidate_count: 2
  shoulder_discomfort_today: true

当前可用能力:
  - evaluate_training_load
  - update_plan_draft

当前禁用能力:
  - publish_plan：draft_not_confirmed
```

「当前工作状态」不是一段需要长期维护的自然语言，而是由运行时状态、业务数据和能力注册表实时派生的视图。程序还可以直接计算进度指标：

```yaml
执行进度:
  总步骤数: 6
  已完成: 3
  当前步骤: evaluate_replacement
  剩余步骤: 2

计划修改进度:
  总动作数: 3
  已确认动作: 2
  待修改动作: 1
  当前目标: exercise_2
```

能确定计算的内容交给程序，不要让模型从历史消息中重新推导。状态栏本身的区块结构见 [[4.AgentStatus 当前工作状态栏]]。

## 按需挂载，不做框架泛化

这类派生字段不是框架层的通用设计。只有性能评测暴露出模型对某个确定性状态存在重复推导瓶颈时，才按需挂载对应的派生视图。

数据源受严格约束：输入只依赖结构化状态、已验证的工具结果或正式任务产物；相同输入必须保证幂等输出；源数据发生变更时，派生视图必须触发重计算。

## 只读定位

派生上下文始终被定位为底层事实的只读视图，绝不作为新的数据事实源向后传递。上下文整理结束后，派生视图与工作状态栏一起由最新结构化数据重新生成（见 [[6.历史轨迹与上下文整理]]）。

## 边界问答

**1. Q：** 派生上下文的输入为什么受约束？
**A：** 约束有三条：输入只依赖结构化状态、已验证的工具结果或正式任务产物；相同输入保证幂等输出；源数据变更触发重计算。三条共同保证派生值始终可以从底层事实推导出来。

**2. Q：** 为什么不把派生字段做成框架级通用能力？
**A：** 派生视图按需挂载，触发条件是性能评测暴露模型对特定确定性状态的重复推导瓶颈；没有评测证据的状态不挂载。框架层的泛化设计不在这个方案内。
