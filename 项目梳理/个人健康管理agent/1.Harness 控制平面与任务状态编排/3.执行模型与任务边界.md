# 执行模型与任务边界

## 控制平面职责

控制平面负责管理一次请求或任务如何进入智能体运行时、如何推进，以及在人工中断或执行异常之后如何继续。它维护的是执行状态，而不是业务事实。

业务事实有自己独立的去处：已经确认的训练计划和历史训练记录仍然写入业务数据库；尚未确认的计划由草稿存储（Draft Store）保存；LangGraph 状态和检查点只记录当前执行到了哪里，以及恢复执行需要的运行状态（分层定义见 [[5.Task Runtime、Checkpoint 和业务状态#四层状态分层]]）。

## 执行单元与编排方式

执行单元指控制平面管理的一次执行：一个智能体调用或一个持久任务，被选择、启动、推进，必要时暂停和恢复。系统目前有两个领域智能体——训练智能体与饮食智能体——加一个持久存在的会话主管（见第五章 [[4.Supervisor 架构与委派]]）。

它们之间的差异不在能力，而在两个相互独立的维度：编排方式和生命周期。

### 能力层是共享的

训练智能体、饮食智能体和每日计划运行在同一层能力（工具与记忆）之上，任何一类执行单元都不独占某套工具。训练/饮食不是只能回答简单问题的普通处理器：它们同样能调用工具、读写记忆，完成查询、修改、生成等操作。每日计划能调用的训练计划工具，训练智能体同样能调用；反过来，这些工具也不会因为每日计划是固定流程就被排除在训练/饮食的能力之外。能力的可见范围由第二章的 [[8.能力渐进装载]] 按业务域与技能收敛，记忆归第三章；二者都不以「自由智能体还是固定工作流」为分界。

### 维度一：编排方式

- **自由编排（ReAct，推理-行动循环）**：训练智能体和饮食智能体收到 DomainTask 后，由模型自主决定调用哪些工具、读哪些记忆、按什么顺序完成。步骤不是预先写死的；简单请求直接走确定性路径，只有任务复杂到需要显式拆步骤时，才按需触发 Planner（见 [[9.Planner 按需规划]]）。
- **预编排（领域工作流）**：每日计划是一段提前编排好的固定工作流，步骤预先确定，由 Harness 按状态机推进，模型不负责决定「下一步做什么」。它是训练智能体的领域工作流，作为一项领域能力被调用（见第五章 [[5.Domain Agent 执行模型]]）。

### 维度二：生命周期

- **请求级作用域（request-scoped）**：生命周期绑定单次请求，通常在一个 HTTP 请求内完成，请求结束即结束。
- **任务级作用域（task-scoped）**：跨越多个请求。创建当天训练计划时，流程可能先补充参数，再检查已有计划，生成草稿后等待用户确认；用户之后还可能修改草稿、再次确认，最后才正式保存。整个过程跨越多个请求，因此不能和普通智能体调用共用同一种生命周期，需要独立的任务生命周期（见 [[4.Conversation 与 Task 生命周期]]）。

在目前的系统里，这两个维度在每日计划上恰好重合：每日计划既是预编排、也是任务级；训练/饮食的常规 ReAct 调用既是自由编排、也是请求级。把它们拆成两个维度，是为了避免把「没有工具、没有记忆」误当成请求级的含义，也避免把「固定流程」误当成「独立智能体」。

### 升级为持久任务的标准

持久任务指执行状态需要持久保存、能跨请求暂停和恢复的任务。不是每个智能体调用都需要任务检查点：训练/饮食的常规请求失败以后可以重新执行，所以仍然按请求级作用域处理。只有满足以下任一条件的流程，才升级成持久任务：

- 需要跨请求暂停、等待人工确认
- 需要服务重启以后恢复
- 中间执行成本已经高到不希望从头重跑

持久化机制本身见 [[5.Task Runtime、Checkpoint 和业务状态]]。第五章进一步区分同步执行与后台异步执行：后台任务同样是持久任务，但当前会话不等待它完成（见 [[9.HIL 与异步任务]]）。

## 路由：由 Supervisor 决策

路由是为每轮请求选择执行目标的过程：决定这一轮应该直接回答、调用共享能力，还是委派给哪个领域智能体。这个决策由会话主管完成，不再有独立的 Router 组件（理由见第五章 [[4.Supervisor 架构与委派#不设独立 Router]]）。

```text
                          用户请求
                             │
                             ▼
                          根状态图
                             │
                             ▼
                 会话主管（Supervisor）
                             │
              ┌──────────────┼──────────────────┐
              ▼              ▼                  ▼
         直接回答        共享能力             委派
                                              │
                                        ┌─────┴─────┐
                                        ▼           ▼
                                  训练智能体    饮食智能体
                                        │
                                        ▼
                                每日计划工作流
```

例如「罗马尼亚硬拉是什么动作」不涉及领域状态，会话主管直接回答。「我昨天深蹲做了多少」需要访问训练数据，会话主管委派给训练智能体。

当请求需要进入每日计划工作流时，会话主管不直接挂在每日计划的执行链上等待用户，而是把请求交给任务控制器（Task Controller），由它创建一个独立任务，再启动对应的每日计划图。任务入口的分流见 [[4.Conversation 与 Task 生命周期#任务入口分流]]。

## 业务归属与运行时

每日计划因此没有被定义成第三个业务领域，也没有被定义成第三个智能体。业务上它仍然属于训练，只是训练智能体的一项预编排工作流，在运行时中拥有单独的任务生命周期：

```text
业务归属

训练
├── 训练智能体（ReAct）
└── 每日计划（领域工作流）


运行时

训练智能体常规调用      请求级作用域
饮食智能体常规调用      请求级作用域
每日计划（含 HIL）      任务级作用域
后台 AsyncAgentTask      持久化 / 异步
```

这样拆分的原因主要是生命周期与编排方式不同，而不是能力不同，也不是为了增加一个新的智能体层级。任务生命周期的具体定义见 [[4.Conversation 与 Task 生命周期]]，后台任务的持久化见 [[9.HIL 与异步任务]]。

## 边界问答

**1. Q：** 训练/饮食和每日计划的能力有区别吗？

**A：** 没有。三者共用同一层工具与记忆，每日计划能调用的训练计划工具，训练智能体同样能调用，训练/饮食也不是只能回答简单问题的处理器。区别在编排方式（固定工作流 vs 自由编排）和生命周期（任务级 vs 请求级），不在能力。

**2. Q：** 为什么训练/饮食请求不升级成持久任务？

**A：** 这类请求通常在一个 HTTP 请求内完成，失败以后可以重新执行，所以按请求级作用域处理。只有需要跨请求暂停、人工确认、服务重启恢复，或者执行成本高到不希望从头重跑的流程，才升级成持久任务。

**3. Q：** 为什么路由不再由独立 Router 组件完成？

**A：** 独立 Router（无论确定性还是 LLM，大语言模型）都会与会话主管重复语义判断。领域选择是会话主管决策的一部分，由会话主管在每一步动态判断直接回答、调用共享能力还是委派领域智能体，理由见 [[4.Supervisor 架构与委派]]。

**4. Q：** 每日计划为什么不定义成第三个业务领域或第三个智能体？

**A：** 业务上它仍然属于训练，只是训练智能体的一项预编排工作流，在运行时拥有单独的任务生命周期。拆分的真正原因是生命周期与编排方式不同，而不是能力不同，也不是为了增加一个新的智能体层级。
