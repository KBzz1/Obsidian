# 第三章：长期记忆、知识 RAG 与证据装配

## 一、模块定位与职责边界

长期记忆模块负责管理跨 Thread、跨任务持续存在的用户信息，并在当前任务需要时从长期记忆、用户 Profile、业务数据库和领域知识库中检索相关证据。它解决的不是“如何把历史聊天重新放进 Prompt”，而是两个更底层的问题：哪些信息值得长期保存，以及当前任务真正需要哪些长期事实和外部知识。

系统中的 LangGraph Checkpointer 只负责 Thread 范围内的运行状态与对话恢复，例如当前 Graph 执行到哪个节点、任务中断后从哪里恢复。这类状态属于 Harness Control State，不等同于长期 Memory。长期记忆以 `user_id` 为主要作用域，即使用户开启新的 Conversation Thread，仍然能够读取已经形成的长期认知。

第三章也不负责最终 Prompt 拼装。Memory、Profile、Business DB 和 Domain Knowledge 经过检索与证据处理后统一输出 `EvidenceBundle`，由第二章的 Context Assembler 决定哪些 Evidence 进入当前 LLM Context、采用什么顺序以及占用多少 Token。因此两个模块之间的边界是：

```text
第三章：
长期信息如何保存
→ 当前任务需要检索什么
→ 哪些事实当前有效
→ 证据来自哪里
→ 输出 EvidenceBundle

第二章：
EvidenceBundle 中哪些内容进入本轮 Context
→ 如何裁剪
→ 如何组织
→ 如何与 Task Status、Conversation Context 一起装配
```

第五章中的 Conversation Supervisor 和 Domain Agent 也不会默认共享所有用户 Memory。Supervisor 或 Domain Agent 根据当前 `DomainTask` 判断是否需要长期用户信息或领域知识，再显式调用对应 Retrieval Capability。普通常识问题不触发 Memory Retrieval，需要领域个性化信息时才读取相关 Evidence，从而避免长期 Memory 重新演化成一份所有 Agent 每轮都加载的全局上下文。

整个长期信息体系的数据来源最终分为四类：

```text
User Profile
→ 当前高价值用户状态

User Memory
→ 跨会话保存的用户历史与长期认知

Business DB
→ 正式业务事实

Domain Knowledge
→ 健身 / 饮食领域公共知识
```

这些数据可以共同支持一次 Agent Task，但不会因为统一进入 Evidence Assembly 就混成同一种存储。

## 二、长期 Memory 的语义模型

当前长期 Memory 主要采用两类语义：Episodic Memory 和 Semantic Memory。

Procedural Memory 作为长期记忆理论中的一种类型保留概念边界，但当前健身 / 饮食业务不单独建设 Procedural Memory Store。Workout Agent 如何规划训练、Diet Agent 如何调用工具、某类任务按照什么 SOP 执行，这类行为主要由 Workflow、Skill、Prompt 和 Tool Runtime 管理。用户对回答组织方式的长期偏好，例如“先给结论再解释”，则属于用户 Semantic Memory 或 Profile 中的 `interaction_preference`，而不是单独学习一条 Agent Procedure。

因此当前系统的长期用户认知主要形成下面的关系：

```text
Episodic Memory
记录发生过什么
        ↓
Semantic Consolidation
        ↓
Semantic Memory
表达当前能够形成的长期认知
        ↓
Profile Projection
        ↓
User Profile
提供当前任务的快速读取视图
```

这三层并不是相同数据的不同副本，它们承担不同的数据语义和更新方式。

### Episodic Memory

Episodic Memory 保存用户长期经历中的具体事件。它描述的是“在某个时间和上下文中发生过什么”，因此必须保留时间和原始来源。

例如用户先后表达：

```text
3 月：
我最近习惯早上训练。

7 月：
换工作以后，我现在基本只能晚上训练。

8 月：
最近还是晚上训练比较稳定。
```

系统不会把这些内容维护成一个不断被 UPDATE 的 `training_preference` 记录，而是分别保存成多个 Episode。旧事件即使已经不代表当前状态，依然有历史价值。

Episodic Memory 采用 append-first 写入语义。新的用户状态不会修改过去已经发生的事件。只有 Memory Extraction 本身错误、用户要求删除数据或隐私治理要求删除时，Episode 才会进入 `invalid` 或 `deleted` 状态。

### Semantic Memory

Semantic Memory 是在一个或多个 Episode 基础上形成的用户长期认知。它描述的不是单次事件，而是系统根据已有证据当前可以支持的判断。

例如：

```text
E1：用户过去偏好晨练。
E2：工作时间发生变化。
E3：用户明确表示目前主要晚上训练。
E4：近期训练记录也主要发生在晚间。
```

可以形成：

```text
用户当前主要在晚间训练。
```

Semantic Memory 必须能够追溯自己的证据，因此会保存与相关 Episode 的 `derived_from` 关系。它不是简单把多个 Episode 合并成一句话后删除原数据，而是在历史层之上新增一层更适合长期读取的抽象表示。

Semantic Memory 同样不直接覆盖旧认知。当一个用户状态发生长期变化时，新 Semantic 作为新版本写入，旧 Semantic 保留为历史版本。例如：

```text
S1:
training.preference.time = morning
valid_to = 2026-07
status = historical

S2:
training.preference.time = evening
valid_from = 2026-07
status = current
```

这样系统既能快速判断当前状态，也不会失去用户状态变化的历史轨迹。

## 三、Memory Card 表示与持久化模型

Episodic Memory 和 Semantic Memory 统一使用 Advanced JSON Card 作为应用层的 canonical representation。

Advanced JSON Card 以普通 JSON Card 的：

```text
类别
→ 子类
→ Key / Value
```

为基础，再增加背景、主体身份、主体与用户的关系、时间、原始来源以及 Memory 之间的派生关系。这些信息的主要作用是消除长期记忆脱离原对话以后产生的歧义。

例如一句简单的：

```text
最近膝盖有点不舒服
```

如果只作为 Note 保存，未来无法确定它描述的是用户本人还是用户在讨论朋友，也无法确定这是当前状态还是过去的经历。Advanced JSON Card 会显式记录：

```json
{
  "memory_type": "episodic",
  "classification": {
    "category": "fitness",
    "subcategory": "physical_condition",
    "key": "knee_discomfort",
    "value": "reported"
  },
  "subject": {
    "entity_id": "user_123",
    "entity_type": "person",
    "relationship_to_user": "self"
  },
  "backstory": "用户在讨论近期深蹲训练后的恢复情况时提到右膝出现不适。",
  "temporal": {
    "event_start": "2026-08-20",
    "recorded_at": "2026-08-25T20:30:00+08:00",
    "precision": "approximate"
  },
  "provenance": {
    "source_type": "conversation",
    "source_refs": ["message_881"]
  }
}
```

其中 `event_start` 与 `recorded_at` 必须分离。用户今天说“去年一直晨练”，系统是在今天获得这条信息，但事件描述的是去年。只有区分事件时间与系统记录时间，后续 Semantic Consolidation 才能正确判断事实的时间关系。

Advanced JSON Card 中同时保存 `simple_note` 和 `enhanced_note` 两种文本表示，但它们不形成独立 Memory Store。

`simple_note` 是最短的人类可读描述，例如：

```text
用户当前主要在晚上训练。
```

它适合调试、UI 展示或非常紧凑的 Evidence 输出。

`enhanced_note` 会补充必要背景和语义，例如：

```text
用户当前主要选择晚间训练；这一变化发生在工作时间调整以后，并得到近期实际训练行为支持。
```

Enhanced Note 主要服务于向量 Embedding、语义检索和最终 LLM 阅读。相比只对 `value = evening` 做 Embedding，它携带主体和背景，检索歧义更小。

因此最终不是维护四套 Memory：

```text
Simple Notes Store
Enhanced Notes Store
JSON Card Store
Advanced JSON Card Store
```

而是：

```text
Advanced JSON Card
    ├── Structured Fields
    ├── Simple Note
    └── Enhanced Note
```

Profile 则使用更轻量的 Typed JSON Card，因为它表达的是当前状态，不需要复制完整背景和历史证据。

数据库层也不会把完整 Advanced JSON Card 无约束地塞进一个 JSONB。高频检索和状态判断字段作为普通 SQL Column 存储，例如：

```text
id
user_id
memory_type

category
subcategory
fact_key
state_key

subject_id
relationship_to_user

event_start
event_end
recorded_at
valid_from
valid_to

status
salience
safety_level
confidence

simple_note
enhanced_note

payload JSONB
embedding
schema_version
```

类型特有或未来可能演化的字段进入 `payload JSONB`。

Memory 之间的关系单独使用 `memory_relations` 保存，而不是全部藏在 JSON 中：

```text
memory_relations

from_memory_id
to_memory_id
relation_type
```

第一版只需要支持：

```text
derived_from
supersedes
```

因此系统保留证据关系，但不建设完整 Knowledge Graph。

## 四、Memory 写入与 Event Buffer

长期 Memory 不在每条用户消息结束后立即调用一次 LLM 抽取。普通 Conversation Event 先进入 `user_id` 范围的 durable Event Buffer，再以批次方式做 Memory Extraction。

主要流程为：

```text
Conversation Event
        ↓
Memory Event Buffer
        ↓
达到 Flush 条件
        ↓
Batch Memory Extraction
        ↓
Episodic Candidates
        ↓
Schema Validation
+ Attribution Validation
+ Idempotency Check
        ↓
Episodic Memory
```

Buffer 采用 Postgres 持久化，而不是放在 LangGraph State。原因是 Buffer 的生命周期是跨 Thread、面向用户长期 Memory 的，而 LangGraph State 属于某个 Thread 的控制和运行状态。

Buffer 中的事件仍然保留来源信息：

```text
event_id
user_id
thread_id
task_id
source_agent
source_message_id
content
created_at
status
```

默认 Flush 条件包括事件或 Token 达到一定阈值、用户进入 idle 状态以及当前 Task 正常结束。Memory Extraction 以批次为输入，可以看到一段完整局部上下文，从而减少把一次临时安排错误抽取成长期偏好的概率。

例如：

```text
用户：今天晚上训练吧。
```

单独看这一句话很容易错误形成：

```text
用户偏好晚间训练。
```

如果和完整 Task Context 一起处理，系统可以识别它只是今天的安排，不需要形成长期 Memory。

Memory Extraction 只负责生成 Episodic Candidate，不负责更新 Semantic、修改 Profile 或判断旧 Memory 是否应该被替换。它的职责尽量收窄为：

```text
这段用户事件中，有没有值得跨会话保存的长期经历？
```

长期保存的主要候选包括明确长期偏好、目标或状态变化、重要训练或饮食经历、长期约束，以及用户明确要求系统记住的信息。普通寒暄、临时任务选择、Agent 自己生成的内容、完整 Tool Result 以及已经存在于 Business DB 的业务记录不自动转换成 Memory。

ADD-only 也不等于允许同一个 extraction batch 重复写入相同事件。Worker 会通过 `source_event_id + extraction_batch_id + candidate_index` 形成幂等键，避免任务重试产生两条完全相同的 Episode。但系统不会使用 Embedding Similarity 判断“这条新 Memory 是否应该覆盖旧 Memory”。

## 五、关键事实 Hot Path

Memory Formation 默认采用后台 Batch，但安全相关信息、明确要求长期记住的信息，以及关键 Profile 状态变化允许走窄 Hot Path。

例如用户说：

```text
我对花生严重过敏。
```

不能等到若干分钟后的 Buffer Flush 和后台 Consolidation 才对 Agent 生效。

这类事件走：

```text
Critical User Statement
        ↓
Immediate Extraction
        ↓
Attribution / Schema Validation
        ↓
Episodic Memory
        ↓
Immediate Profile Projection
```

Semantic Consolidation 仍然可以后台完成。

因此 Hot Path 提供的是“立即持久化和立即进入当前状态”的保证，而不是同步执行整个 Memory Intelligence Pipeline。

Hot Path 不允许绕过 Attribution Validation。例如：

```text
我朋友对花生过敏。
```

不能因为命中了“过敏”关键词就直接写入当前用户的 Allergy Profile。

## 六、Semantic Consolidation

Episodic Memory 写入完成后，不立即扫描用户全部 Memory，也不做 Embedding Clustering。

每张 Card 的：

```text
category
subcategory
key
```

组合生成稳定的 `state_key`，例如：

```text
training.preference.training_time
diet.restriction.allergy
fitness.goal.primary
interaction.preference.response_style
```

`state_key` 表示一个可能随着时间演化的用户状态。

新 Episode 写入后，只把对应 `state_key` 标记为 dirty：

```text
new Episode
      ↓
state_key dirty
      ↓
Background Consolidator
```

后台 Consolidator 只读取：

```text
当前 Semantic
+
尚未处理的新 Episodes
+
少量必要历史 Episodes
+
必要时的 Business Evidence
```

而不是重新读取用户全部长期历史。

Consolidator 的输出被限制为四种明确状态：

```text
NO_CHANGE
NEW_SEMANTIC
SUPERSEDE
UNCERTAIN
```

`NO_CHANGE` 表示新 Episode 没有改变现有长期认知。

`NEW_SEMANTIC` 表示首次形成一个稳定认知。

`SUPERSEDE` 表示当前认知发生变化，需要新增一个 Semantic 版本，并把旧版本转为 historical。

`UNCERTAIN` 表示证据存在冲突或不足以形成稳定判断，系统不强迫产生新的 Current Semantic。

Consolidation 过程中不采用“最新 Memory 一定优先”或“Embedding 最相似就视为同一事实”的规则，而是区分不同证据类型。大致证据强度为：

```text
明确的当前用户陈述
        >
确定性的结构化业务事实
        >
一段时间内重复出现的行为模式
        >
模型从零散事件产生的弱推断
```

例如用户最近连续在晚上训练，但同时明确说：

```text
我其实更喜欢早上，只是最近加班只能晚上练。
```

系统不应该简单形成：

```text
preferred_training_time = evening
```

而可以区分：

```text
preferred_training_time = morning
current_practical_training_time = evening
```

这样长期 Memory 表达的是用户真实偏好和现实约束，而不是只根据最近行为覆盖以前认知。

## 七、User Profile

User Profile 表示当前 Agent 最经常需要读取的用户状态，是长期 Memory 的 current read model。

它只保存预定义、高价值且需要快速访问的字段，例如：

```text
当前 Fitness Goal
伤病和运动限制
过敏
Dietary Restriction
训练时间偏好
训练可用时间
器械条件
Interaction Preference
```

Profile 不复制全部 Semantic Memory。

Profile 字段有两类来源。

第一类是用户明确提供的 authoritative fact，例如过敏、明确伤病限制和某些固定约束。这些信息验证后可以直接从 Episodic Memory 投影进 Profile，尤其是安全事实，不需要等待 Semantic Consolidation。

第二类是 derived fact，例如长期训练时间偏好或交互方式偏好。这些字段通过：

```text
Episodes
    ↓
Semantic Memory
    ↓
Profile Projection
```

产生。

Profile Projection 尽量由确定性程序控制，例如：

```python
if semantic.state_key == "training.preference.training_time":
    profile.training_preference["time"] = semantic.value
```

而不是让 LLM 每次读取整个 Profile 后自由重写 JSON。

Profile 中重要字段保留自己的来源：

```json
{
  "value": "evening",
  "source_type": "semantic_projection",
  "source_memory_id": "sem_301",
  "updated_at": "2026-08-20"
}
```

这样后续 Agent 或开发者可以判断一个 Profile 值是用户明确告诉系统的，还是根据长期行为推导出来的。

最终三个数据层采用不同更新语义：

```text
Episodic
→ Append-first historical record

Semantic
→ Versioned derived knowledge

Profile
→ Mutable current state
```

这三种语义不再混在同一个 `UserMemory` 对象里。

## 八、Importance 与生命周期

Memory 不维护一个不断被后台任务修改的统一 `importance_score`。

不同类型的重要性信号被拆开处理：

```text
salience
→ low / normal / high

safety_level
→ normal / critical

temporal status
→ current / historical / future / unknown
```

安全信息不会因为长期没有访问而自动降低重要性。Recency、当前有效性以及历史状态更多作为 Retrieval 阶段的动态 ranking signal，而不是反过来修改 Memory 本身。

当前版本也不主动因为 Memory 较旧就删除 Episodic History。旧 Episode 可以降低普通检索优先级，但仍然保留用于时间追溯、冲突分析和 Semantic Evidence。

只有系统错误、用户删除请求或数据治理要求才触发显式 invalidation / deletion。

## 九、User Memory Retrieval

长期 Memory 不在每次请求开始时固定召回 Top-K。

Conversation Supervisor 或 Domain Agent 根据当前任务判断是否需要用户长期信息，例如：

```text
“深蹲主要训练哪些肌群？”
→ 不需要 User Memory

“根据我的情况帮我安排下周训练计划。”
→ 需要 Goal / Injury / Availability / Preference

“为什么我最近的训练安排和以前不一样？”
→ 需要当前 Semantic + 历史 Episodes
```

Memory Retrieval 使用当前已有的 Postgres + pgvector 体系继续演化，不额外引入独立搜索服务。

检索综合三类信号：

```text
Structured Filter
+
Semantic Vector Search
+
Lexical Search
```

Structured Filter 用于限定：

```text
user_id
memory_type
state_key
subject
current / historical
time range
safety level
```

Vector Search 主要针对 `enhanced_note`，用于发现自然语言语义相关的长期 Memory。

Lexical Search 补足用户名词、器械、动作名称以及 embedding 可能不稳定的精确关键词。

多路结果可以使用 RRF 一类简单 fusion 方式合并，再基于 temporal status、current semantic、safety priority 和任务相关性做轻量 rerank。

普通个性化任务优先读取：

```text
User Profile
      ↓
Current Semantic Memory
```

只有在需要解释来源、处理冲突、了解变化过程或 Semantic Evidence 不足时，才进一步下钻 Episodic Memory。

因此低层 Episode 不需要每次都进入 LLM Context。

## 十、Domain Knowledge Retrieval

领域知识与 User Memory 完全分开。

项目中的健身动作知识库属于 Domain Knowledge，它描述的是动作名称、肌群、动作模式、器械、适用场景、限制条件和注意事项等公共领域知识，不描述某个用户。

当前 Exercise Knowledge 已经具有较强的结构化属性，因此第一阶段优先使用 metadata-aware structured retrieval，而不是为了引入 RAG 强行把所有内容切成文本 Chunk 后做 Vector Top-K。

例如 Workout Agent 在选择动作时可以调用：

```text
search_exercise_knowledge(
    target_muscles,
    movement_pattern,
    equipment,
    must_tags,
    exclude_tags,
    user_constraints
)
```

先通过结构化条件缩小候选集合，再返回动作描述和必要知识。

当未来出现越来越多难以通过固定字段表达的自由文本知识，例如更复杂的动作解释、训练理论文章或康复注意事项，再给 AI enrichment 后的文本增加 Embedding Search，形成：

```text
Structured Filter
+
Vector Retrieval
```

的 Hybrid Knowledge Retrieval。

复杂多跳知识问题如果未来确实出现，可以让 Domain Agent 多次调用 Retrieval Capability，例如第一次搜索后发现证据不足，再修改 Query 重试。当前简单任务仍采用一次按需检索，不把所有知识请求包装成复杂 Agentic RAG。

## 十一、Business DB 与长期 Memory

正式业务事实始终由 Business DB / Domain Service 管理。

例如：

```text
Workout Session
Meal Log
Habit Check-in
Current Workout Plan
Current Nutrition Plan
Training History
```

这些数据不会为了统一 Memory 而复制一份到向量库。

如果 Agent 需要今天的训练计划，直接查询 Workout Service；如果需要当前饮食计划，直接查询 Nutrition Service。

Business DB 中的数据只有在形成长期个性化意义时，才可以转换成 Memory Evidence。例如连续多周的训练记录显示用户晚间完成训练更稳定，可以形成一个结构化 Domain Signal：

```text
最近四周的训练主要发生在晚间。
```

这个 Signal 可以作为 Episode 或 Semantic Consolidation 的 evidence，但仍保留对原始 Workout Session 的引用，而不是复制所有训练明细。

结构化 Domain Signal 不需要重新经过自然语言 LLM Extraction。如果业务程序已经明确知道事件含义，可以 deterministic mapping 成对应 Advanced JSON Card。

## 十二、Evidence Assembly

第三章最终不会直接返回一堆数据库对象给 Agent。

User Profile、User Memory、Business DB、Domain Knowledge 和上游 Agent Artifact 最终统一转成 `EvidenceBundle`。

逻辑结构例如：

```python
class EvidenceBundle:
    task_id: str

    profile: list[ProfileEvidence]
    memories: list[MemoryEvidence]
    business_facts: list[BusinessEvidence]
    knowledge: list[KnowledgeEvidence]
    artifacts: list[ArtifactEvidence]

    conflicts: list[EvidenceConflict]
```

单条 Evidence 至少携带：

```python
class Evidence:
    source_type: str
    source_id: str

    claim: str

    temporal_status: str | None
    confidence: str | None

    provenance: list[str]
```

例如：

```json
{
  "source_type": "semantic_memory",
  "source_id": "sem_301",
  "claim": "用户当前主要在晚间训练。",
  "temporal_status": "current",
  "confidence": "high",
  "provenance": [
    "episode_18",
    "episode_21"
  ]
}
```

Evidence Assembly 的职责是统一来源格式、保留出处、标记当前有效性并识别明显冲突，而不是决定所有 Evidence 都进入 Prompt。

第二章 Context Assembler 根据当前 Task、Agent Status、Token Budget 和任务阶段决定最终模型可见内容。

因此完整调用链是：

```text
Supervisor / Domain Agent
        ↓
判断当前任务需要什么信息
        ↓
Retrieval Coordinator
        │
        ├── User Profile
        ├── User Memory
        ├── Business Service
        ├── Domain Knowledge
        └── Upstream Artifact
        ↓
Evidence Assembly
        ↓
EvidenceBundle
        ↓
Chapter 2 Context Assembler
        ↓
LLM Context
```

## 十三、失败与恢复语义

长期 Memory 不是用户主请求的同步关键路径，因此高级 Memory 处理失败时不能阻塞普通 Agent 请求，也不能破坏已经保存的低层事实。

Buffer Worker 失败时，原始 Event 继续保持 `pending`，后续可以重试。

Memory Extraction 失败时，不生成 Episode，但原始 Buffer Event 不删除。

Episode 已经成功写入、Temporal Enrichment 失败时，Episode 仍然有效，只是部分时间字段暂时处于 unknown 或 pending。

Semantic Consolidation 失败时，不修改旧 Semantic 和 User Profile。低层 Episode 已经持久化，因此后续可以重新执行 Consolidation。

证据冲突无法稳定解析时，Consolidator 返回 `UNCERTAIN`，不强迫更新 Profile。

Vector Search 或 Embedding 暂时不可用时，可以退化为 Structured Filter 和 Lexical Search。

Domain Knowledge Retrieval 失败时，系统返回缺少知识证据，而不是让 Agent把无法确认的内容伪装成检索结果。

因此整个 Memory Pipeline 遵循：

```text
原始长期事实优先可靠保存
        ↓
高级抽象允许异步失败
        ↓
失败不能反向损坏历史
```

## 十四、最终模块边界

第三章最终负责：

```text
长期用户 Event 的持久化
Episodic Memory
Semantic Consolidation
User Profile Projection
Memory Retrieval
Domain Knowledge Retrieval
Business Evidence Retrieval
Evidence Assembly
```

不负责：

```text
Thread Checkpoint 与任务恢复
→ 第一章

Evidence 最终如何进入 Prompt
→ 第二章

Tool 权限、重试、幂等执行与 Guardrail
→ 第四章

Supervisor 与 Domain Agent 的协作协议
→ 第五章

高并发、全局队列、限流和 Trace
→ 第六章
```

最终系统因此形成一个明确的长期信息流：

```text
                写入侧

Conversation / Domain Signal
          ↓
Event Buffer / Hot Path
          ↓
Episodic Advanced JSON Card
          ↓
Temporal Enrichment
          ↓
Semantic Consolidation
          ↓
Versioned Semantic Card
          ↓
Profile Projection
          ↓
Current User Profile


                读取侧

Current DomainTask
          ↓
按需 Retrieval
          │
          ├── User Profile
          ├── Semantic / Episodic Memory
          ├── Business DB
          ├── Domain Knowledge
          └── Upstream Artifact
          ↓
Evidence Assembly
          ↓
EvidenceBundle
          ↓
Context Assembler
```

这套设计中的长期 Memory 不再等同于一个向量库，也不再通过“寻找最相似旧文本并覆盖”维持当前用户状态。历史、长期认知和当前读取状态被分别表示，同时通过来源、时间和派生关系保持可追溯性。向量检索只是 Retrieval 的一个组件，而不是 Memory 数据模型本身；Profile 也只是当前状态视图，不承担历史保存职责。这样可以在不引入复杂 Memory Graph、聚类系统或独立 Memory Agent 的情况下，形成一套适合当前健身 / 饮食 Agent 规模的长期状态与证据系统。
