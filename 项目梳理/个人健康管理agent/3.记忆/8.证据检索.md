# 证据检索

## 用户记忆检索：按需而不是固定 Top-K

长期 Memory 不在每次请求开始时固定召回 Top-K。Conversation Supervisor 或 Domain Agent 根据当前任务判断是否需要用户长期信息，例如：

```text
“深蹲主要训练哪些肌群？”
→ 不需要 User Memory

“根据我的情况帮我安排下周训练计划。”
→ 需要 Goal / Injury / Availability / Preference

“为什么我最近的训练安排和以前不一样？”
→ 需要当前 Semantic + 历史 Episodes
```

Memory Retrieval 使用当前已有的 Postgres + pgvector 体系继续演化，不额外引入独立搜索服务。

检索综合三类信号：

```text
Structured Filter
+
Semantic Vector Search
+
Lexical Search
```

Structured Filter 用于限定：

```text
user_id            # 归属用户
memory_type        # episodic / semantic
state_key          # 状态键
subject            # 主体
current / historical  # 是否当前有效
time range         # 时间范围
safety level       # 安全等级
```

Vector Search 主要针对 `enhanced_note`，用于发现自然语言语义相关的长期 Memory。Lexical Search 补足用户名词、器械、动作名称以及 embedding 可能不稳定的精确关键词。

多路结果可以使用 RRF（Reciprocal Rank Fusion，倒数排名融合）一类简单 fusion 方式合并，再基于 temporal status、current semantic、safety priority 和任务相关性做轻量 rerank。

普通个性化任务优先读取：

```text
User Profile
      ↓
Current Semantic Memory
```

只有在需要解释来源、处理冲突、了解变化过程或 Semantic Evidence 不足时，才进一步下钻 Episodic Memory。因此低层 Episode 不需要每次都进入 LLM Context。

## 相似不再等于同一事实

一个贯穿检索与写入的原则：Embedding 相似度只表示「可能相关」，不代表「同一事实」，更不代表「该覆盖」。

```text
旧版：similar → 可能 UPDATE

新版：similar → 可能相关 → 交给 temporal / semantic reasoning 判断
```

这个转变是第三章改造的根源，见 [[10.困难以及应对办法]]。

## 领域知识检索：结构化优先

领域知识与 User Memory 完全分开。项目中的健身动作知识库属于 Domain Knowledge，它描述的是动作名称、肌群、动作模式、器械、适用场景、限制条件和注意事项等公共领域知识，不描述某个用户。

当前 Exercise Knowledge 已经具有较强的结构化属性，因此第一阶段优先使用 metadata-aware structured retrieval，而不是为了引入 RAG 强行把所有内容切成文本 Chunk 后做 Vector Top-K。

例如 Workout Agent 在选择动作时可以调用：

```python
search_exercise_knowledge(
    target_muscles,     # 目标肌群，如 quads / hamstrings / glutes
    movement_pattern,   # 动作模式，如 squat / hinge / push
    equipment,          # 器械条件，如 barbell / dumbbell / bodyweight
    must_tags,          # 必须满足的标签
    exclude_tags,       # 排除的标签
    user_constraints,   # 用户约束，如伤病限制
)
```

先通过结构化条件缩小候选集合，再返回动作描述和必要知识。

当未来出现越来越多难以通过固定字段表达的自由文本知识，例如更复杂的动作解释、训练理论文章或康复注意事项，再给 AI enrichment 后的文本增加 Embedding Search，形成：

```text
Structured Filter
+
Vector Retrieval
```

的 Hybrid Knowledge Retrieval。

复杂多跳知识问题如果未来确实出现，可以让 Domain Agent 多次调用 Retrieval Capability，例如第一次搜索后发现证据不足，再修改 Query 重试。当前简单任务仍采用一次按需检索，不把所有知识请求包装成复杂 Agentic RAG。

## 业务事实归业务库

正式业务事实始终由 Business DB / Domain Service 管理。例如：

```text
Workout Session
Meal Log
Habit Check-in
Current Workout Plan
Current Nutrition Plan
Training History
```

这些数据不会为了统一 Memory 而复制一份到向量库。如果 Agent 需要今天的训练计划，直接查询 Workout Service；如果需要当前饮食计划，直接查询 Nutrition Service。

Business DB 中的数据只有在形成长期个性化意义时，才可以转换成 Memory Evidence。例如连续多周的训练记录显示用户晚间完成训练更稳定，可以形成一个结构化 Domain Signal：

```text
最近四周的训练主要发生在晚间。
```

这个 Signal 可以作为 Episode 或 Semantic Consolidation 的 evidence，但仍保留对原始 Workout Session 的引用，而不是复制所有训练明细。

结构化 Domain Signal 不需要重新经过自然语言 LLM Extraction。如果业务程序已经明确知道事件含义，可以 deterministic mapping 成对应 Advanced JSON Card（见 [[5.记忆卡片与持久化模型]]）。

## 边界问答

**1. Q：** 为什么不引入独立的向量搜索服务？

**A：** 当前使用 Postgres + pgvector 已经能满足检索需求，额外引入独立搜索服务会带来部署与同步成本。Memory Retrieval 在现有体系上继续演化，而不是新建一套。

**2. Q：** 为什么已经有 Vector Search 还要 Lexical Search？

**A：** 用户名词、器械、动作名称这类精确关键词，embedding 可能不稳定，Lexical Search 负责补足精确匹配，保证这类词不会因为向量语义偏差而漏掉。

**3. Q：** 为什么领域知识优先做结构化检索，而不是先切块做向量 Top-K？

**A：** 健身动作知识已有较强结构化属性（肌群、动作模式、器械、标签），先用结构化条件缩小候选集合更准确、成本更低。只有当自由文本知识变多、固定字段表达不了时，才叠加 Embedding Search 形成混合检索。

**4. Q：** 为什么业务数据不复制一份到向量库？

**A：** 业务事实由 Business DB / Domain Service 管理，需要最新值直接查询服务即可。复制一份会引入两份数据的一致性问题。只有业务数据在形成长期个性化意义时才转成 Memory Evidence，且保留对原始记录的引用。

**5. Q：** 为什么普通任务读取路径是 Profile → Semantic，而不是先查 Episodic？

**A：** 大多数个性化任务只需要当前高价值状态（Profile）和当前认知（Semantic）。只有需要解释来源、处理冲突或 Semantic 证据不足时才下钻 Episodic，所以低层 Episode 不必每次都进 LLM Context。
