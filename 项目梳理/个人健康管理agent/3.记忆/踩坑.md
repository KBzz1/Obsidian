## 二、工程演化与踩坑

早期版本的长期 Memory 采用一套比较直接的原子事实模型。Conversation 结束后由 LLM 从近期对话中抽取值得长期保存的事实，再为文本生成 Embedding 并写入 `UserMemory`。为了避免向量库不断积累语义重复的数据，新事实写入前会先搜索同类旧 Memory；当语义相似度达到较高阈值时，系统会把它视为已有事实的更新，直接修改旧记录。另一部分逻辑又采用 `superseded_by` 保存新 Memory，并把旧 Memory 标记为已经被新事实替代。读取时主要返回没有被 supersede 的 Memory。

这种方案在第一版里很自然。Memory 当时主要被理解成一组“关于用户目前知道的事实”，因此系统希望数据库尽可能保持干净：

```text
Conversation
    ↓
Atomic Fact Extraction
    ↓
Search Similar Memory
    ↓
┌────────────────────────┐
│ 相似度高 → UPDATE       │
│ 不相似   → ADD          │
│ 新事实出现 → supersede  │
└────────────────────────┘
    ↓
Current User Memories
```

对于“用户身高 175cm”或者“用户不吃牛肉”这类看起来接近静态属性的信息，这套方式通常可以工作。真正的问题出现在用户状态开始随着时间发生变化以后。

一个典型场景是训练时间偏好。用户早期可能明确表示：

```text
我一般喜欢早上训练。
```

几个月后因为换工作又说：

```text
现在上班时间变了，我基本只能晚上训练。
```

从 Embedding 的角度，两条 Memory 都高度围绕“用户 + 训练时间 + 偏好”，因此非常容易被认为是同一个事实。如果按照旧逻辑直接 UPDATE：

```text
preferred_training_time = morning
              ↓
UPDATE
              ↓
preferred_training_time = evening
```

数据库确实得到了一个更符合当前状态的值，但“用户过去喜欢晨练”这个事实已经消失。系统此后只能知道用户现在晚上训练，却无法再解释这个变化是何时发生、为什么发生。

使用 `superseded_by` 能保留旧记录，但如果 Retrieval 默认把 superseded Memory 过滤掉，问题只是从“历史被删除”变成了“历史还在数据库里，但 Agent 正常情况下看不到”。当任务只需要回答“用户现在喜欢什么时候训练”时问题并不明显；一旦用户提出：

```text
为什么你现在总把我的训练安排在晚上？
```

或者后续 Agent 需要判断：

```text
晚练到底是用户真正偏好，
还是工作变化造成的临时现实约束？
```

旧 Memory 模型就没有足够清晰的数据语义支持这种判断。

继续调整 similarity threshold 也无法解决这个问题。把阈值从 `0.92` 调高只能减少误合并，却不能回答“什么时候应该 UPDATE”这个根本问题。因为：

```text
我以前喜欢晨练
```

和：

```text
我现在改成晚练
```

语义相似度非常高，但两条信息并不是重复事实。它们描述的是**同一个用户状态在不同时间的两个有效阶段**。

同样，继续增加更多 `superseded_by` 判断也没有真正解决问题。旧设计仍然要求写入阶段回答一个很困难的问题：

> 新 Memory 到底是在纠正旧事实，还是描述一个新的历史状态？

而 Memory Extraction 所看到的通常只是当前一小段 Conversation。让 LLM 在这个阶段同时理解完整历史、时间关系、用户状态变化，再决定 ADD、UPDATE 或 DELETE，会让一个本来只应该负责“记录新信息”的组件承担过多职责。

最终定位到的问题并不是向量搜索效果不好，而是旧系统把三种不同含义的数据放在了同一个 `UserMemory` 抽象中：

```text
发生过什么
+
我们目前根据历史形成了什么认知
+
Agent 现在应该快速读取什么状态
```

于是同一次“用户状态变化”同时触发了三种互相冲突的需求：

```text
历史层：
旧事实必须保留

认知层：
当前判断应该变化

读取层：
Agent 最好直接得到最新值
```

单个 mutable Memory Record 不可能同时很好地满足这三个要求。

因此新版没有继续优化 `UPDATE / DELETE / supersede` 的判断 Prompt，而是重新定义了长期 Memory 的状态边界。

第一步是把 Episodic Memory 变成 append-first 的历史层。新的用户状态只产生新的 Episode，不再因为和旧 Episode 高度相似就覆盖过去：

```text
E1
2026-03
用户表示更喜欢晨间训练

E2
2026-07
工作安排变化后改为晚间训练
```

两条 Episode 都长期存在，并分别保存事件时间、主体、背景和原始来源。Embedding Similarity 只用于以后寻找相关 Evidence，不再拥有修改历史的权力。

第二步是在 Episode 上方增加 Semantic Memory。Semantic 不表示某一次用户陈述，而表示系统结合相关历史证据以后形成的长期认知。状态发生变化时，同样不是修改旧 Semantic 内容，而是新增版本：

```text
S1
preferred_training_time = morning
status = historical

        ↓ superseded by

S2
preferred_training_time = evening
status = current
```

`S1` 曾经是正确认知，因此仍然保留；`S2` 表达系统目前应该采用的新认知。Semantic 同时通过 `derived_from` 指向支持它的 Episode，避免长期抽象和原始证据断开。

第三步是把 User Profile 明确成当前状态读取层。Profile 本身允许正常 UPDATE，因为它的职责就是让 Supervisor 或 Domain Agent 快速得到当前高价值状态：

```text
profile.training_preference.time
morning
    ↓
evening
```

因此新版形成了三种不同的数据更新语义：

```text
Episodic
→ Append-first
→ 保存历史

Semantic
→ Versioned
→ 保存长期认知及其变化

Profile
→ Mutable
→ 保存当前读取状态
```

在这个结构下，同样一个用户状态变化不再要求 Memory Writer 做一次模糊的“应该 ADD 还是 UPDATE”判断。

```text
用户：
“换工作以后我现在基本晚上训练。”

        ↓

Episodic
新增一条时间化历史事件

        ↓

Semantic Consolidation
判断 current training time 是否发生变化

        ↓

如果证据足够：
新增新的 Semantic Version

        ↓

Profile Projection
更新当前 training preference
```

Memory Extraction 的职责因此被明显收窄：它只判断当前 Conversation 中有没有值得跨会话保存的新事件，并把事件忠实地写入历史层。关于这些事件是否已经构成稳定长期偏好、是否与以前认知冲突、哪个状态当前有效，则交给后续围绕同一 `state_key` 执行的 Semantic Consolidation。

这项改造也改变了向量相似度在系统中的位置。旧版中，Similarity 同时承担搜索和 Memory Mutation 决策：

```text
similar
→ 可能 UPDATE
```

新版中，Embedding 只负责帮助系统寻找可能相关的历史 Evidence：

```text
similar
→ 可能相关
→ 交给 temporal / semantic reasoning 判断
```

“相似”不再被解释成“同一个事实”。

改造后的代价是长期 Memory 不再像早期版本一样只有少量最新记录。Episode 数量会持续增长，Semantic 也会保留历史版本，因此系统需要额外维护 `state_key`、`derived_from`、有效时间和后台 Consolidation。Profile 也需要明确的 projection rule，而不能依赖一张 Memory 表直接返回结果。

当前项目接受这些额外复杂度，是因为它们直接换来了三个旧设计无法同时提供的性质：

```text
历史可以追溯
当前状态可以快速读取
高层认知可以解释自己的证据来源
```

同时系统没有进一步引入 Event Sourcing、Temporal Knowledge Graph 或复杂 Memory Graph。当前用户长期状态主要集中在有限的健身、饮食和交互偏好主题，使用 append-first Episodic、versioned Semantic 和 mutable Profile 已经能够解决真实的状态演化问题。只有未来 Memory 的实体关系和跨事实推理复杂度明显增加时，才有必要继续升级数据模型。

这次演化最终改变的并不是 Memory 使用了什么向量数据库，而是系统对长期记忆本身的理解：旧设计把 Memory 当成一组需要持续维护为“最新”的可变事实；新版则把“历史发生过什么”“当前能够形成什么认知”和“Agent 此刻需要快速读取什么状态”拆成了三个不同的数据层。长期状态变化因此不再通过修改过去来表达，而是通过新增历史、形成新的语义版本以及更新当前 Profile 来表达。
