# 记忆写入与生命周期

## Event Buffer：先落地再批量抽取

长期 Memory 不在每条用户消息结束后立即调用一次 LLM 抽取。普通 Conversation Event 先进入 `user_id` 范围的 durable Event Buffer（持久化事件缓冲），再以批次方式做 Memory Extraction。

主要流程：

```text
Conversation Event
        ↓
Memory Event Buffer
        ↓
达到 Flush 条件
        ↓
Batch Memory Extraction
        ↓
Episodic Candidates
        ↓
Schema Validation
+ Attribution Validation
+ Idempotency Check
        ↓
Episodic Memory
```

Buffer 采用 Postgres 持久化，而不是放在 LangGraph State。原因是 Buffer 的生命周期是跨 Thread、面向用户长期 Memory 的，而 LangGraph State 属于某个 Thread 的控制和运行状态（见 [[项目梳理/个人健康管理agent/1.Harness 控制平面与任务状态编排/5.Task Runtime、Checkpoint 和业务状态]]）。

Buffer 中的事件仍然保留来源信息：

```text
event_id            # 事件唯一标识
user_id             # 归属用户
thread_id           # 来源会话线程
task_id             # 所属任务（可为空）
source_agent        # 来源智能体，如 workout / diet / supervisor
source_message_id   # 来源消息
content             # 事件文本
created_at          # 事件产生时间
status              # pending / flushed / invalid
```

## 抽取的批次视野与职责

默认 Flush 条件包括事件或 Token 达到一定阈值、用户进入 idle 状态以及当前 Task 正常结束。Memory Extraction 以批次为输入，可以看到一段完整局部上下文，从而减少把一次临时安排错误抽取成长期偏好的概率。

例如：

```text
用户：今天晚上训练吧。
```

单独看这一句话很容易错误形成：

```text
用户偏好晚间训练。
```

如果和完整 Task Context 一起处理，系统可以识别它只是今天的安排，不需要形成长期 Memory。

Memory Extraction 只负责生成 Episodic Candidate，不负责更新 Semantic、修改 Profile 或判断旧 Memory 是否应该被替换。它的职责尽量收窄为：

```text
这段用户事件中，有没有值得跨会话保存的长期经历？
```

长期保存的主要候选包括明确长期偏好、目标或状态变化、重要训练或饮食经历、长期约束，以及用户明确要求系统记住的信息。普通寒暄、临时任务选择、Agent 自己生成的内容、完整 Tool Result 以及已经存在于 Business DB 的业务记录不自动转换成 Memory。语义是否成立、当前是否有效，交给后续围绕同一 `state_key` 的 [[7.语义巩固与用户画像#Semantic Consolidation]] 判断。

## 幂等：ADD-only 但禁止重复写入

ADD-only 也不等于允许同一个 extraction batch 重复写入相同事件。Worker 会通过 `source_event_id + extraction_batch_id + candidate_index` 形成幂等键，避免任务重试产生两条完全相同的 Episode。

但系统不会使用 Embedding Similarity 判断「这条新 Memory 是否应该覆盖旧 Memory」。相似度只用于寻找相关证据，不用于决定是否覆盖，这个原则见 [[8.证据检索#相似不再等于同一事实]]。

## 关键事实 Hot Path

Memory Formation 默认采用后台 Batch，但安全相关信息、明确要求长期记住的信息，以及关键 Profile 状态变化允许走窄 Hot Path（热路径）。

例如用户说：

```text
我对花生严重过敏。
```

不能等到若干分钟后的 Buffer Flush 和后台 Consolidation 才对 Agent 生效。

这类事件走：

```text
Critical User Statement
        ↓
Immediate Extraction
        ↓
Attribution / Schema Validation
        ↓
Episodic Memory
        ↓
Immediate Profile Projection
```

Semantic Consolidation 仍然可以后台完成。因此 Hot Path 提供的是「立即持久化和立即进入当前状态」的保证，而不是同步执行整个 Memory Intelligence Pipeline。

Hot Path 不允许绕过 Attribution Validation。例如「我朋友对花生过敏」不能因为命中了「过敏」关键词就直接写入当前用户的 Allergy Profile。Attribution Validation 要判断这条信息的主体是不是用户本人。

## 重要性信号与生命周期

Memory 不维护一个不断被后台任务修改的统一 `importance_score`。不同类型的重要性信号被拆开处理：

```text
salience
→ low / normal / high

safety_level
→ normal / critical

temporal status
→ current / historical / future / unknown
```

安全信息不会因为长期没有访问而自动降低重要性。Recency、当前有效性以及历史状态更多作为 Retrieval 阶段的动态 ranking signal，而不是反过来修改 Memory 本身。

当前版本也不主动因为 Memory 较旧就删除 Episodic History。旧 Episode 可以降低普通检索优先级，但仍然保留用于时间追溯、冲突分析和 Semantic Evidence。只有系统错误、用户删除请求或数据治理要求才触发显式 invalidation / deletion。

## 边界问答

**1. Q：** 为什么 Event Buffer 用 Postgres 而不用 LangGraph State？

**A：** Buffer 的生命周期是跨 Thread、面向用户长期 Memory 的；LangGraph State 属于某个 Thread 的控制和运行状态，生命周期与任务执行绑定。Buffer 放在 Postgres 才能跨会话、跨任务、跨重启持久保存。

**2. Q：** 为什么不每条消息都立即抽取，而要等批次？

**A：** 单条消息缺乏上下文，容易把临时安排（“今天晚上训练吧”）误抽成长期偏好。批次抽取能看到一段完整局部上下文，区分今天的一次安排和长期状态。

**3. Q：** 为什么安全事实要走 Hot Path，而普通记忆走后台批次？

**A：** 安全信息需要立即持久化并立即进入当前状态，不能等若干分钟后的 Buffer Flush 和后台 Consolidation 才生效。Hot Path 只保证「立即落库、立即投影到 Profile」，语义巩固仍可后台完成，不同步跑完整条 Memory Pipeline。

**4. Q：** Hot Path 为什么不允许跳过 Attribution Validation？

**A：** 命中了「过敏」关键词不代表信息属于用户本人。Attribution Validation 判断主体是否为当前用户，避免把「我朋友对花生过敏」错误写入用户的 Allergy Profile。

**5. Q：** 为什么不维护一个统一的重要性分数？

**A：** 不同类型的重要性信号（salience、safety_level、temporal status）含义和用途不同，混成一个会掩盖语义。安全信息不应因为长期没被访问就降低重要性；recency 和当前有效性只作为检索阶段的动态排序信号，不反过来改写记忆本身。
