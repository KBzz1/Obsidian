# 中文知识笔记 AI 写作模式参考（AI Agent 知识库专用）

## 目录

1. 内容层模式
2. 语言层模式
3. 结构与节奏模式
4. 知识库整理特有模式
5. 容易误判的正常写法
6. 应当保留的人类声线

把这些模式当作诊断线索，不要当成禁词表。只有当某种表达成簇出现、造成空泛、重复、跳跃或信息密度下降时才处理。用户给设计 Agent 定下的文风规则与知识库主人的偏好优先级高于本参考。

一个贯穿全文的区分：**概念解释 ≠ 口水话。** 讲机制、讲原因、讲边界的解释是笔记的核心价值，必须保留甚至补全；换词复述、总结意义、升华表态才是要删的口水话。不把前者误当后者删掉。

## 一、内容层模式

### 1. 万能时代背景

**线索**：“在当今 AI 快速发展的时代”“随着大模型技术的不断进步”。

**问题**：背景可套在任何主题上，不提供时间、事件或变化。

**原句**：随着大模型技术的不断发展，Agent 任务编排正面临越来越复杂的挑战。

**改写**：DailyPlan 的任务进入 WAITING_HUMAN 之后，需要从已有 Checkpoint 恢复执行。

只有原文给出具体背景时才能写后者；没有就删。

### 2. 空泛意义拔高

**线索**：“具有里程碑意义”“标志着全新篇章”“为 Agent 系统注入新动能”。

**问题**：把普通机制写成历史转折，没有证据。

**处理**：写机制实际做的事。“每个节点执行后状态落盘”而不是“Checkpoint 机制标志着状态管理迈入新纪元”。

### 3. 强行上价值

**线索**：“这不仅是一次升级，更是……”“其意义远不止于此”。

**处理**：删除价值判断，保留事实。

### 4. 模糊权威

**线索**：“业内普遍认为”“有研究表明”“专家指出”但没有出处。

**处理**：材料有来源就写明；没有就删除归因或保留为作者判断，不编造机构与报告。

### 5. 虚构因果与关联

**线索**：“这说明”“由此可见”“因此必然”连接的前后句缺乏证据。

**问题**：把相关性、时间顺序或猜测写成确定因果；会把材料里不存在的“依赖关系”写进笔记和链接。

**处理**：材料有依据才写因果；否则并列陈述，不推断。

### 6. 伪具体

**线索**：“多维度、全链路、系统性、深层次”没有对象和动作。

**改写原则**：写出真正的对象与动作；原文没有动作就保留抽象。

### 7. 挑战与展望模板

**线索**：结尾“尽管……但仍面临挑战”“展望未来”。

**处理**：保留材料里具体的困难或计划（“遗留问题 / 后续改进”按条目保留），删除通用过渡和乐观收束。

### 8. 假装全面

**线索**：“覆盖方方面面”“全方位、多层次”。

**处理**：列出真正覆盖的环节。反过来也成立：不要把两三个机制扩写成“完整的生产级系统”。

### 9. 重复解释同一事实

**线索**：一句陈述事实，下一句换词解释，第三句总结意义。

**原句**：task_thread_id 用于定位任务自己的 Checkpoint。也就是说，通过它可以找到状态存到哪里了，由此可见它是恢复机制的核心。

**改写**：task_thread_id 用于定位这个任务自己的 LangGraph Checkpoint。

**边界**：这说的是“换词复述 + 意义总结”。如果后一句是在讲机制（这个 id 由谁生成、为什么按它归档），那不是重复解释，要保留。

### 10. 概念抛掷不解释

**线索**：重要标识符、缩写、机制被一句话带过，读者仍然不知道它是什么。典型句式：“X 对应 Y”“X 用于 Z”，但不解释 X 本身。

**原句**：Conversation 对应 Root Graph 的 root_thread_id，用于维持多轮聊天的执行连续性。

**问题**：root_thread_id 到底标识什么、由谁生成、和 Conversation 什么关系，全篇没有讲清。读者（未来的自己）读到这里只能跳过去，概念链就断了。

**处理**：首次出现就地补一句机制解释。示例：

> Conversation 用一个 `root_thread_id` 标识自己。这个 id 在会话建立时生成，同一轮对话里的消息都挂在它下面；Graph 中断或恢复时，靠它找到这轮对话的完整执行记录，从而维持多轮聊天的连续性。

解释内容必须来自材料或代码；补不出的部分写进“待确认”，不编造。

### 11. 无来源的效果承诺

**线索**：“显著提升”“大幅降低”“彻底解决”。

**处理**：保留有测量口径的数据；没有数据就写机制本身，不替它承诺效果。

### 12. 术语包装（改名拔高）

**线索**：把简单机制改写成高级能力：asyncio.create_task → “生产级异步任务系统”；Redis 存状态 → “完整任务恢复”；普通日志 → “全链路可观测性”；业务过滤器 → “完整 Guardrail”。

**处理**：按材料里的真实实现层级称呼机制；设计但未实现的，保持“设计中 / 待实现”层级。

### 13. 事实层级拉平

**线索**：讨论中“共同设计的方案”被写成“已经实现”；“工程推导”被写成“资料明确支持”；为面试构造的旧设计被写成真实历史。

**处理**：整理时保留层级区分，必要时用 frontmatter 字段或 callout 标注（如 状态: 设计中）。事实层级是面试可信度的一部分，不能为了文本流畅而拉平。

## 二、语言层模式

### 14. 连接词流水线

**线索**：段落依次以“首先、其次、再次、此外、同时、最后、综上”开头。

**处理**：保留确有顺序的，其余直接写事实。知识笔记的段落本就是并列主题，路标多余。

### 15. 元话语暖场

**线索**：“让我们深入探讨”“下面将从三个方面介绍”“值得注意的是”“不难发现”。

**处理**：删除宣布句，直接进入内容。“值得注意”后确有重要限制时只保留限制本身。

### 16. 术语黑话堆叠

**线索**：“赋能、抓手、闭环、沉淀、打法、底层逻辑、组合拳”集中出现。

**问题**：动作、负责人和结果被抽象名词遮住。

**处理**：换成具体动作、对象和结果。

### 17. 空动词

**线索**：“进行、实现、推动、促进、打造、构建、助力”后接抽象名词。

**原句**：通过引入 Checkpoint 机制，实现状态持久化能力的有效构建。

**改写**：每个节点执行后把状态写入 Checkpoint。

原文没有具体动作时不得补写。

### 18. 形容词套餐

**线索**：“高效、便捷、智能、专业”“全面、深入、系统”成组出现。

**处理**：删除或换成能由事实支撑的一个词。

### 19. “不仅……更……”滥用

**问题**：机械制造递进和升华。

**处理**：删，改成直接陈述事实。

### 20. “无论……都……”假覆盖

**线索**：“无论任务处于何种状态，都能可靠恢复”。

**问题**：没有证据证明所有状态都适用。

**处理**：改成具体适用条件。

### 21. 假范围

**线索**：“从执行到恢复”“从设计到落地”，两端不在同一可测量尺度上。

**处理**：列出真正覆盖的对象。

### 22. 三段式强迫症

**线索**：所有观点恰好三点；“定义-意义-启示”套在每个概念上。

**处理**：按信息量决定条目数。概念笔记不等于“是什么-为什么-怎么做”。

### 23. 同义词轮换

**线索**：同一对象被轮流叫“平台、系统、工具、解决方案、模块、框架”。

**处理**：核心术语稳定重复，指代比变化重要。

### 24. 主体消失

**线索**：“得到提升”“被进一步优化”“持续推进中”没有主语。

**处理**：材料有主体就写主动句；没有不猜。

### 25. 过度缓和 / 过度确定

**线索一**：“可能在一定程度上或许会产生一些影响”。

**线索二**：把“计划、暂定、待验证”写成确定结论。

**处理**：按材料的证据强度写；限定词是事实的一部分。

### 26. 伪权威转折

**线索**：“真正的问题是”“归根结底”“本质上”“说到底”“核心是”“真正重要的是”。

**问题**：用姿态代替论证。用户角色提示词明确点名这类表达。

**处理**：直接写后面的判断，并检查判断有无依据。

### 27. “不是……而是……”连用

**线索**：一段内多次“这不是 X，而是 Y”。

**处理**：保留确有对比关系的一处，其余改成直接陈述。

### 28. 中英杂交

**线索**：中文句子夹带大量可用中文表达的英文词：“我们先 check 一下 state 是否 valid，然后 resume 这个 task”。

**问题**：读起来跳跃、费劲，也显得在硬凑技术感。

**处理**：正文以中文叙述为主。行业标准名（LangGraph、Checkpoint、LLM、RAG）可以保留，但首次出现给中文说明或全称；代码标识符（task_id、root_thread_id）只在引用代码时出现，正文引用时同步给出中文含义；能用中文表达的动作、状态、角色一律用中文。

### 29. 聊天机器人残留

**线索**：“当然可以”“以下是为你整理的内容”“希望这对你有帮助”。

**处理**：交付正文时全部删除。

## 三、结构与节奏模式

### 30. 标题过密 / 层级过深

**线索**：一两句话一个标题，正文像提纲；同一主题拆成过多层级小标题。

**处理**：合并相邻小节；只重复下一句的标题直接删。标题层级不超过实际信息量需要。

### 31. 碎片化条目

**线索**：每句都做成列表项或“**标签：**”条目，没有连续段落。

**问题**：知识库要求正式主体采用连续技术段落，而不是大量碎片化条目。

**处理**：确需扫描的信息保留列表（配置项、字段清单、阅读路径）；叙述性内容改成围绕一个工程问题的连续段落。

### 32. 排版装饰过多

**线索**：每个标题 emoji、每句粗体、连续感叹号。

**处理**：知识笔记默认不加 emoji 和感叹号；作者样本有习惯才保留。真正需要强调的约束（如“同一 Conversation 最多一个 Active Task”）用一处粗体。

### 33. 机械对称

**线索**：所有段落长度接近、都是“观点+解释+总结”。

**处理**：按内容决定篇幅，重要处展开，简单事实一句写完。

### 34. 连续短句制造戏剧感

**原句**：任务停了。状态丢了。恢复失败了。

**处理**：一个短句可以强调；连续短句显得刻意，改回自然叙述。

### 35. 跳跃式叙述

**线索**：每个概念只给一两句就换下一个；段落、小节之间话题频繁切换，一件事没讲完就切走；句子之间靠罗列连接，没有“为什么”的承接。

**问题**：这是知识库主人明确不满意的一点——读起来跳，概念链在脑子里连不起来。

**处理**：一个小节把一个概念讲完再进入下一个：是什么 → 在系统里如何工作 → 与相邻概念的关系（如有）→ 边界或异常。概念之间用机制和原因衔接，而不是平铺罗列。信息量小的概念合并进相邻小节，信息量大的允许写长。

### 36. 伪金句

**线索**：“状态是系统的记忆”“检查点是时间的锚点”。

**处理**：比喻没有可验证内容时，写清真正指向的行为。

### 37. 假坦率开头

**线索**：“说实话”“讲真”当固定钩子。

**处理**：笔记不需要钩子，直接写定义。

### 38. 结尾复读与升华

**线索**：结尾概括全文后再展望未来、上升到意义。

**处理**：停在最后一个具体事实、限制条件或待办上。

## 四、知识库整理特有模式

### 39. 材料顺序即结构

**线索**：把讨论的时间线、网页的段落顺序原样搬进笔记。

**问题**：零散材料的顺序是产生的顺序，不是知识的结构；流水账难检索、难复习。

**处理**：按主题重新组织（机制、状态流转、边界、示例、遗留问题），材料顺序只是线索。

### 40. 平均用力

**线索**：材料里每个细节都保留、权重相同，笔记变成记录而非知识。

**处理**：区分稳定的概念与规则、一次性上下文（当时的报错、临时结论、过程中的口误）。一次性上下文不写进概念笔记，或压缩成示例。

### 41. 自包含重复

**线索**：每篇笔记都把背景概念完整重讲一遍。

**问题**：同一知识多点维护，边界模糊，也是“知识碎片化”的主要来源。

**处理**：每个概念只有一处定义，其他笔记首次提到时给一句最小解释并链接，不完整重讲。整理成稿时先查“这个定义在库里是否已存在”。

### 42. 伪造概念关联

**线索**：材料没说的关系被写成链接或依赖：“A 是 B 的基础”“B 依赖 A”。

**处理**：只链接材料中确有依据的关系；不确定就并列陈述，不加链接。

### 43. 口语直搬

**线索**：“然后”“就是”“那个”“嗯”、来回改口、口头禅原样进笔记（语音转写材料尤其常见）。

**处理**：删填充词，保留最后一次修正后的结论；当事人原话有信息量时才保留为引文。

### 44. 章节越界

**线索**：把其他章节的机制在当前笔记里提前完整设计（上下文压缩、Memory、Guardrail、多 Agent 协议、生产治理各自有归属章节）。

**处理**：只写与当前章节直接相关的接口、依赖和边界；其余写进“不在本章展开”表并指向归属章节。

### 45. 无上下文术语

**线索**：术语直接使用，没有定义、没有链接、没有中文说明。

**问题**：读者是面试前复习的自己，也是仍在学习这个系统的自己；术语首次出现必须可追溯、可理解。

**处理**：首次出现给一句定义（是什么、为什么存在），或链接到概念笔记，或保留材料中的解释。英文术语同时给中文说明；缩写给全称。

### 46. 数字美化

**线索**：“性能提升 3 倍”“延迟降低一半”没有测量口径。

**处理**：保留原始数字和口径；没有口径不写倍数和百分比。

### 47. 拟真故事越界

**线索**：把“为面试构造的旧设计 / 失败场景”写成真实生产事故（“某次大促线上崩溃”）。

**处理**：构造的演化故事保持“构造”身份，现象、根因、改造必须与最终设计自洽，不虚构规模、性能数字、故障比例。

### 48. 代码块无注释

**线索**：数据类、SQL、配置片段裸奔，字段含义只写在远处的正文里。

**问题**：读者在代码块前停下来逐字段猜含义，复习和面试复述都要在正文与代码之间来回跳。

**处理**：定义型代码块每个字段、参数、条件加简短中文注释（是什么、用来干什么）。正文解释不替代注释；流程图、ASCII 状态图不是代码，不强加注释。

### 49. 边界问答位置随意

**线索**：选型理由、为什么不引入某组件、机制定位这类边界问题散落在正文各处，或只在正文一笔带过。

**处理**：边界问题用编号问答对补充，统一收束在笔记末尾的「边界问答」小节，按「**1. Q：** / **A：**」编号配对；不只选型问题，凡有材料支撑的“为什么这么设计 / 为什么不那么做”都值得收进来；答案只来自材料或代码，材料没有的理由不编造。

### 50. 标题术语未落地

**线索**：小节标题引入一个概念（如「两类执行单元」），正文第一句直接讲分类或细节，没有先说清这个概念本身指什么。

**问题**：第一次读到会愣一下，只能带着问题往下读，概念悬空到后面才慢慢拼出来。这是库主明确提过的“迷茫感”来源。

**处理**：小节第一句先给最小定义（这个术语在本系统里指什么），再进入机制。即使概念有唯一归属地，标题所在处也先落地一句再链接。示例：『## 两类执行单元』的首句先写“执行单元指控制平面管理的一次执行——一个普通 Agent 调用或一个持久任务”，再讲两类分别是什么。

## 五、容易误判的正常写法

以下特征单独出现时不要修改：

- 术语密集、正式的中性表达（LangGraph、Checkpoint、Guardrail 等正常使用）
- 对概念的中文机制解释（“它是什么、为什么这样设计”）——这是要保留甚至补全的内容，不是重复解释
- 术语首次出现时的中文说明、全称或一句定义
- 代码块、字段名里的英文标识符（task_id、root_thread_id 等）
- 行业标准英文名（LLM、RAG、HIL、OCC）
- 短陈述句和“一句话一段”的定义式写法（偶尔出现）
- 概念反复使用同一术语（不是同义词轮换失误）
- 一个常用连接词或一个排比句
- 标题、引文、产品名中的“高频 AI 词”
- 作者有意采用的省略、补充和自我修正
- 「概念归属」类 callout 与跨笔记链接
- 代码块里的字段级中文注释与末尾的 Q&A 边界问答小节（库主约定的补充习惯）

检查模式组合及上下文功能，不检查“禁词命中数”。

## 六、应当保留的人类声线

- 具体而不寻常的细节（真实标识符、真实超时值、真实取舍）
- 把一个概念从头讲透的耐心：机制、原因、边界都交代清楚，而不是抛词就走
- 作者真实的犹豫、矛盾和保留意见
- 句长不均、自然插入的补充说明
- 稳定的术语选择和个人组织习惯（表格、ASCII 图、callout、概念归属声明）
- 可以解释原因的个人判断与 trade-off 权衡
- 不完全工整但信息密度高的段落
- 材料中当事人原话里的关键表述
- 定义型代码块的字段级注释、末尾的 Q&A 边界问答等固定补充习惯
- 小节标题引入术语时，第一句先落地含义、再展开的节奏

去 AI 味的目标不是把所有笔记改成同一种“干净中文”，而是让笔记读起来像是这个知识库的主人写的，概念讲得懂、链条接得上，面试前复习时找得到、信得过、讲得清。
