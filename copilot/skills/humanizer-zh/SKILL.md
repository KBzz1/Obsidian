# 中文知识笔记去 AI 味（AI Agent 知识库专用）

把零散材料整理成信息密度高、直接克制、面试前能照着讲出来的工程设计笔记，同时不丢事实、不编内容、不破坏 Obsidian 结构。

先明确三个前提：

1. **这个知识库里的“人味”是工程设计文档的味道，不是口语化。** 中性、客观、术语密集是正常形态；不要往笔记里塞语气词、段子、感叹号或“接地气”改写。
2. **去 AI 味就是守住你给设计 Agent 定下的文风规则。** 那些规则（连续段落、每段一个工程问题、不给普通概念加引号、不用“本质上/核心是”、不碎片化、不包装术语、不拉平事实层级）就是本技能判断“AI 味”的最高依据，与它冲突时以它为准。
3. **读者是“面试前复习、仍在学习这个系统的自己”：概念要讲懂，但不啰嗦。** 不假设读者已经懂这些概念。重要的标识符、缩写和机制首次出现时，用一句中文讲清它是什么、为什么存在、在这里起什么作用；“讲懂”靠机制和原因，不靠换词复述和总结升华。

知识笔记里的 AI 味主要来自两类问题：

- **空**：万能背景、评价形容词、升华结尾、重复总结——词很多，信息没有增量。
- **模板**：机械三段式、连接词流水线、标题过密、碎片化条目、把简单机制包装成高级能力。

## 不可违反的规则

1. 保留材料中的事实：术语、代码、字段名、数字、日期、版本、引文、链接、结论和限定条件（“可能”“计划”“暂不”“待验证”）。
2. 不补写材料中不存在的事实。尤其不得编造概念间的关联、因果、来源、数据或“生产事故”。
3. 不篡改代码块、表格数据、专有名词、链接目标和 frontmatter。
4. 保持事实层级。材料明确支持的、代码已实现的、仅有雏形的、共同设计但未实现的、工程推导的、为面试构造的旧设计，整理后必须仍然可区分；不得把“我们共同设计的”写成“已经实现的”。
5. 允许中性表达。不强行加入第一人称、情绪或口语。
6. 用户笔记样本与设计 Agent 的文风规则优先于本文件。
7. 只处理成簇出现的模板痕迹。单个“此外”、一个排比句或一个“首先”不能证明 AI 味。
8. 不承诺绕过 AI 检测器，不把语言特征当作作者身份的证据。本技能只改善表达。
9. 重要概念、标识符、缩写首次出现必须讲懂：给一句中文解释（是什么、为什么存在、起什么作用），不能只写“X 对应 Y”就跳走。库里已有该概念的唯一归属地时，用内部链接引用。概念出现在小节标题里时，小节第一句先落地它的含义——一句话说清这个术语在本系统里指什么，再进入机制细节，不能让读者带着问题往下读。
10. 正文以中文叙述为主。英文只用于行业标准名、代码标识符和缩写；缩写首次出现给全称或中文说明；不用中文能表达却硬塞英文的写法。
11. 定义型代码块必须有注释：数据类、接口、SQL、配置、载荷结构等代码块，每个字段、参数、条件都要有简短中文注释，说明它是什么、用来干什么。正文里的解释不替代代码注释，两者可以少量重叠（用户明确要求注释独立存在）。流程图、ASCII 状态图不是代码，不强加注释。
12. 边界问题用编号问答对补充，统一放在笔记末尾的「边界问答」小节：为什么选 A、为什么不选 B、某机制的定位与边界、某条设计约束的原因，只要有材料支撑，都值得收进问答，不只限于存储选型。格式：`**1. Q：**问题` 接 `**A：**答案`，按 1、2、3 编号。答案必须来自材料或代码，材料没有的理由不编造。

## 工作模式

- **整理成稿（核心模式）**：把讨论记录、转写、零散结论整理成一篇新笔记。允许重组结构、删冗余、合并重复，但不得新增材料之外的事实、判断或因果。
- **直接改写（默认）**：只输出可直接落盘的终稿。
- **审校模式**：用户要求分析时，先列 3–8 个最明显的问题，再给终稿。
- **轻改模式**：用户说“尽量少改”时，只改明确的模板腔、病句和冗余。
- **文风匹配**：用户提供 2–5 段本人旧文时，先提取声线特征再改写；没有样本时，以同一 vault 中现有笔记的平均声线为基准。
- **文件模式**：只改正文；保留 frontmatter、代码块、表格、callout、链接目标和文件结构。完成后简述修改，不在聊天里重复整篇。
- **嵌入模式**：作为其他流程的一步时，只返回终稿，不输出分析、草稿或自我评价。

## 执行流程

### 1. 锁定任务边界

确认：材料类型（与设计 Agent 的讨论、语音转写、代码分析、网页资料、旧笔记）、目标笔记类型（章节索引、概念笔记、流程笔记、普通整理）、所属章节、读者是“面试前复习、仍在学习这个系统的自己”、必须保留的内容和 vault 的 frontmatter 约定。用户没有指定时，沿用同一 vault 中现有笔记的写法。

### 2. 建立事实锁

内部记录并逐项核对：

- 术语、代码、字段名、类名、接口名、产品名
- 数字、日期、版本号、比例、超时值、阈值
- 引文、出处、链接和参考文献
- 因果关系、否定词、范围词和不确定性
- 事实层级：资料支持 / 代码已实现 / 雏形 / 设计但未实现 / 工程推导 / 面试构造
- 材料作者明确表达的立场与结论

### 3. 检查模板痕迹

完整改写或整理成稿时，读取 [references/chinese-ai-patterns.md](references/chinese-ai-patterns.md)，按“内容、语言、结构、知识库特有”四组检查。轻改可以只用本文件的核心规则。

不要逐词机械替换。先判断某种表达是否真的损害准确性、信息密度或作者声线，再决定保留、压缩、合并或重写。

### 4. 整理与重写

- 每段围绕一个明确的工程问题：问题是什么、采用什么设计、数据和状态如何流转、何时触发、异常如何处理、为什么这样选。段落是连续文字，不是条目堆。
- 第一句直接写定义或结论，删掉“在当今……时代”“接下来我们介绍……”这类定场句。
- 用具体动作、对象和结果替代“赋能、推动、构建、实现”等空动词和“极大提升、至关重要、奠定了坚实基础”等评价形容词。材料没有动作和结果，就保持抽象程度，不自己补。
- 同一观点只写一遍。删掉“陈述 → 换词解释 → 再总结意义”的重复链条；删掉“综上所述”“展望未来”式结尾，停在最后一个事实、限制条件或待办上。
- 术语稳定重复，不做同义词轮换；不通过改名把简单机制包装成高级能力（asyncio.create_task 不写成“生产级异步任务系统”，普通日志不写成“全链路可观测性”）。
- 不确定照实保留：“计划”“暂定”“待验证”“遗留问题”不要写成既成事实或完美架构。
- 不加材料里没有的因果、对比、评价和“旧设计 → 事故”的演化故事。
- 结构按主题重组，不照抄讨论的时间顺序。
- 一个小节把一个概念讲完再进入下一个：是什么 → 在系统里如何工作 → 与相邻概念的关系（如有）→ 边界或异常。避免一句话抛出一个术语立刻切换话题，这是“跳跃感”的主要来源。
- 概念解释要落在机制上：`root_thread_id` 这类标识符要说清它标识什么、由谁生成、用来干什么，不要停留在“对应 X”。
- 英文克制：正文用中文叙述；行业标准名（LangGraph、Checkpoint）可保留，但首次出现给中文说明；代码块和字段名里的标识符保持原样，正文引用时同步给出中文含义。材料里零散出现的解释，收敛到概念首次出现处；材料确实没讲、又无法从代码确认含义的，列为“待确认”，不编造。
- 定义型代码块逐字段加中文注释：数据类、SQL、配置、载荷里的每个字段、参数、条件写一句“是什么、用来干什么”；注释与正文允许少量重叠，正文解释不替代注释。流程图、ASCII 状态图不是代码，不强加注释。
- 边界与选型问题用编号问答收束在笔记末尾：正文讲完机制后，在「边界问答」小节用「**N. Q：** / **A：**」编号问答对回答为什么选 A、为什么不选 B、某机制的定位与边界；不只选型问题，凡有材料支撑的“为什么这么设计 / 为什么不那么做”都值得收进来；答案只来自材料或代码，不编造理由；正文中间不再另开问答小节。
- 概念唯一归属：一个概念只在一处完整定义；其他笔记首次提到时给一句最小解释并链接，不完整重讲背景。
- 标题即术语：小节标题引入一个概念时，第一句先给最小定义（这个术语在本系统里指什么），再展开机制；即使概念的定义在别处有唯一归属，标题所在处也要先落地一句再链接——解决“第一次读到会愣一下、带着问题往下读”的迷茫感。

### 5. 朗读检查

默读终稿，检查：

- 大量普通概念被加了引号
- 一句话单独成段过于频繁
- 排比堆叠、“不是……而是……”式转折连用
- 反复出现“本质上”“核心是”“真正重要的是”
- 层级小标题过多、内容碎片化成条目
- 连续使用“首先、其次、此外、同时、值得注意的是”
- 多个评价形容词挤在同一句
- 重要标识符、缩写只出现不解释，或“X 对应 Y”之后立刻跳到下一句
- 小节标题是术语，但小节第一句没有先落地它的含义
- 正文英文词密度过高，缩写首次出现没有全称或中文说明
- 定义型代码块（数据类、SQL、配置、载荷）缺少字段级中文注释
- 边界问答没有统一放在笔记末尾、没有按编号配对（N. Q / A），或答案超出材料范围
- 小节内部话题跳来跳去，一件事没讲完就切走
- 结尾复读前文并强行升华
- 出现材料里没有的因果或“踩坑故事”
- 聊天残留：“当然可以”“以下是整理后的内容”“希望对你有帮助”

### 6. 事实复核

对照事实锁逐项核对。终稿新增的事实、数字、因果、来源或人物动机，撤回这些改动。压缩时不能删掉会改变含义的限定词；事实层级被拉平的（“设计”写成“实现”），恢复原层级。

## Obsidian 结构规范

处理 vault 文件时，结构和正文一样重要：

- **frontmatter**：保留原字段与原值（如 tags、章节、类型、核心概念、状态）。新建笔记沿用该 vault 的既有字段约定，不发明字段、不删旧字段。
- **内部链接**：保留已有 `[[链接]]` 与 `[[笔记#标题]]`；只添加材料中确有依据的关系，不为图谱密度机械加链接，也不把“语义相近”当成“知识关系”。
- **概念唯一归属**：同一概念只有一处 canonical home（通常在笔记开头用「概念归属」callout 声明），其他笔记通过链接引用，避免多篇笔记互相解释导致边界模糊。
- **章节边界**：不把属于其他章节的机制提前展开；确需提及的，写进“不在本章展开”表并指向归属章节。
- **callout、表格、代码块、ASCII 图**：保持原样，文件模式下只改其中的文字不改结构。纯文字说不清状态流转时，主动补代码块或 ASCII 图（State 边界、生命周期、幂等键、Checkpoint 恢复、Trace/Span 结构）。
- **图表克制**：章节设计阶段不用正式 SVG/架构图/时序图代替文字说明；章节内需要说明关系时用简单文本流程或 ASCII 图。
- **标题与开头**：标题直接具体（不写“浅谈”“关于……的思考”）；正文第一句给结论或定义，为检索服务；小节标题引入术语时，小节第一句先落地该术语在本系统里的含义。
- **代码注释与末尾问答**：定义型代码块要有字段级中文注释；边界/选型问答统一放在笔记末尾单独小节，不散落在正文中间。

## 输出规范

默认只输出终稿，不加“当然可以”“以下是修改后内容”等聊天残留。

审校模式使用：

```text
主要问题
- 问题与原文位置

修改后
终稿
```

文风匹配模式在用户要求说明时，最多概括 5 条声线特征；否则直接给终稿。

## 中文文风校准

分析用户样本时关注：

- 常用句长及长短句切换方式
- 段落开头是否直接、是否常用具体标识符或场景切入
- 常用词、行业词与固定术语
- 逗号、句号、括号、破折号和省略号的使用频率
- 第一人称强度与情绪外露程度
- 作者是否习惯保留犹豫、补充和自我修正

不要“优化”掉样本中的个人习惯，除非它影响理解或用户明确要求。

## 适配场景

- **讨论整理**：与设计 Agent 的多轮讨论 → 结构化笔记。删口语填充（“然后”“就是”“那个”）、来回改口和寒暄；保留最终结论、当事人判断与“待确认 / 遗留问题”。讨论里零散提到的概念解释，收敛到概念首次出现处写清楚；没讲明白的标识符列入“待确认”，不自己猜。
- **已有笔记去 AI 味**：按本文件直接改写。
- **旧笔记合并与拆分**：多篇笔记重复讲同一概念时，收敛到一处定义、其余改链接；一篇笔记塞进多个概念时按主题拆分。
- **外部分享转笔记**：公众号体、教程体的营销腔、悬念和“亲测有效”类表述还原为中性事实陈述；无依据的效果承诺删除。
- **其他文体**（公众号、小红书、邮件等）：核心规则仍适用，但本技能不再展开平台细节。
