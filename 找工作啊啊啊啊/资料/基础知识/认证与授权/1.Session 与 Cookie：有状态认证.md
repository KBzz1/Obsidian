# Session 与 Cookie：有状态认证

## 为什么需要它们

HTTP 无状态：每个请求独立，服务器不记得上一个请求来自谁。但购物车、登录态这类业务要求服务器认得「这是同一个用户」，跨请求的状态要有人记。分工是：Session 在服务端记状态，Cookie 在浏览器端带一张凭证条——服务器用 Set-Cookie 响应头把 sessionId 下发给浏览器，浏览器按域存好，之后对这个域的每个请求自动带上 Cookie 头，服务器拿 sessionId 查会话存储认人。

```text
登录：POST /login (账密) ──→ 校验通过
      ←── Set-Cookie: sessionid=abc123
后续：GET /api/...  Cookie: sessionid=abc123
      ──→ 查会话存储：abc123 → user_id=42 → 认出用户
登出：删会话存储里的 abc123 ＋ 让浏览器过期这条 Cookie
```

## Cookie 的关键属性

Set-Cookie 的属性决定这张凭证条的行为与安全性：Domain/Path 定生效范围；Expires/Max-Age 定寿命，不给就是会话 Cookie（关浏览器就没）；HttpOnly 禁止 JavaScript 读取，XSS 漏洞偷不走凭证；Secure 只在 HTTPS 上发送；SameSite 管跨站请求带不带——Strict 全不带，Lax（主流浏览器默认）只对跨站顶级导航的 GET 携带、其余不带，None 跨站也带但必须配 Secure。SameSite 与 CSRF 的关系：浏览器自动带 Cookie 正是 CSRF 攻击的前提，Lax 已经挡掉绝大多数跨站写请求。

## Session 的服务端存储

sessionId 对应的用户状态总得存，方案按演进顺序三种：

```text
单机内存      → 重启全员掉线，多实例各存各的互不认识
粘性会话      → 负载均衡把同一用户固定到同一实例；实例挂掉，它那批用户掉线
集中存储 Redis → 多实例共享一份会话，TTL 正好当会话过期 ← 生产默认
```

集中放 Redis 读写快、自带 TTL 正好当会话过期（见 [[3.Redis：内存数据结构与缓存角色]]）。代价是这套存储成了认证链路的单点——Redis 不可用等于全员掉线，要主从加哨兵保可用。这正是「有状态」的含义：服务端能随时吊销会话（删记录即登出），也要为这份状态付存储与可用性的成本。

## 适用面与对照

浏览器 Web 应用是 Session 的主场：Cookie 自动携带，HttpOnly、SameSite 的防护生态都是现成的。API 调用、移动端、微服务之间没有浏览器 Cookie 机制，凭证要走 Authorization 头——那是 token 的领地（[[2.JWT：无状态令牌的取舍]]）。LLM API 就没有会话概念：静态 API key 一次下发长期使用；MCP 的用户级授权走 OAuth（[[6.1 OAuth 2.1 授权框架]]）。

> [!example] 实践例子
> 如果健康管理项目加 Web 界面，登录态的自然选择就是 Session + HttpOnly Cookie：Worker 以进程模型部署（[[7.版本控制与并发]]），会话存储要集中放 Redis，而不是各实例各存一份内存。

## 边界问答

**1. Q：** CSRF 攻击为什么专打 Session + Cookie？
**A：** 浏览器对同域请求自动附带 Cookie，攻击者诱导已登录用户的浏览器向目标站发跨站请求时，凭证被顺带携带，服务器分不清请求是不是用户本意。SameSite=Lax 与 CSRF token 是标准对策；用 Authorization 头的 token 方案没有自动携带，天然免疫这个面。

**2. Q：** Session 怎么注销？JWT 难在哪？
**A：** Session 删服务端记录、立即生效，这是有状态换来的掌控力；JWT 无状态，签出去的令牌在过期前服务端没有依据拒绝它——吊销难题与对策见 [[2.JWT：无状态令牌的取舍]]。

**3. Q：** Cookie 过期与会话过期是什么关系？
**A：** 两层独立计时：Cookie 的 Max-Age 决定浏览器还带不带 sessionId，服务端会话记录有自己的 TTL 决定它还在不在，任何一层失效都算未登录。通常两边设成一致，避免「凭证条还在、记录已删」或反过来的错位。
