# JWT：无状态令牌的取舍

## 三段结构与性质

JWT（JSON Web Token，RFC 7519）是一个自带签名的字符串，三段 base64url 编码用点号连接：

```text
xxxxxx.yyyyyy.zzzzzz          三段 base64url 编码，点号连接

header     {"alg": "HS256", "typ": "JWT"}       用什么算法签的
payload    {"sub": "42", "exp": 1789000000}     claims：用户 id、过期时间戳等
signature  HMAC_SHA256(header + "." + payload, 密钥)   对前两段的签名
```

两条性质要分清。防篡改：payload 改一个字节，签名对不上、验证失败——签名是完整性保证。不加密：base64 是编码不是加密，任何人解开 payload 就能读——用户 id、过期时间可以放，密码、手机号不能放；要保密用 JWE（加密形态的 JWT）或干脆不放。

## 无状态验证

验证方只用密钥在本地验签、检查 exp，全程不查任何存储——令牌自己携带身份与有效期。横向扩容时多实例不需要共享会话存储，任何实例都能独立验证；跨服务同理，持有密钥（或公钥）的服务谁都能验。这与 [[1.Session 与 Cookie：有状态认证]] 的对照就是认证的两个流派：状态放在服务端（session），还是放在凭证本身（token）。

## 双令牌实践

无状态的代价是「签出去就收不回」，工程上用双令牌把风险窗口压小：access token 短寿命（15 分钟到 2 小时），泄露了损失窗口也小；refresh token 长寿命（天级），只干一件事——换新 access token，通常在服务端有记录、可吊销。登录响应发一对，之后的流转：

```text
登录成功    → 签发 {access: 15 分钟, refresh: 7 天}
access 过期 → 客户端拿 refresh 换新 access，用户无感
refresh 过期或被吊销 → 重新登录
泄露 access → 最多 15 分钟窗口；泄露 refresh → 服务端可吊销这条记录
```

## 算法与吊销

签名算法两条路线：HS256 对称，签发与验证共享同一密钥，单体服务自签自验够用；RS256 非对称，私钥签、公钥验，资源服务器持公钥验得动但签不了——多服务、第三方接入时防止「能验证就能伪造」，对称与非对称的分工同 [[4.HTTPS 与 TLS：加密握手与证书]]。

吊销难题的常见对策三条：短寿命 access 加可吊销的 refresh，把不可控窗口压到分钟级；黑名单——被吊销令牌的 jti（令牌唯一 id）进 Redis，验证时多查一次，本质是把状态请回来；用户级版本号——密码修改时版本加一，旧令牌全部失效。

> [!example] 实践例子
> 三家 LLM API 用的不是 JWT 而是更简单的静态 API key：无过期、服务端可吊销，验证靠查账户表——牺牲无状态换管理简单。MCP 的 OAuth 2.1 授权链签发的 access token 常以 JWT 为载体，也允许不透明 token 由资源服务器回查，见 [[6.1 OAuth 2.1 授权框架]]。

## 边界问答

**1. Q：** JWT 能替代 Session 吗？
**A：** 分场景。浏览器 Web 后台用 session + HttpOnly Cookie 更稳：吊销即时，CSRF 与 XSS 的防护生态现成。开放 API、移动端、微服务间调用是 JWT 的领地：没有浏览器 Cookie，无状态验证省掉集中存储。取舍始终是吊销能力对无状态扩展。

**2. Q：** JWT 存 localStorage 还是 Cookie？
**A：** localStorage 方便但 XSS 一偷一个准；HttpOnly Cookie 读不到、更安全，但要处理 CSRF（SameSite）且每次请求自动携带；内存保存加 Authorization 头的 XSS 面最小，但刷新页面就丢、要靠 refresh 重取。三者没有全胜选项，按威胁模型选。

**3. Q：** 给 JWT 叠 Redis 黑名单，那不就是 session 了吗？
**A：** 是吊销需求倒逼状态回归的混合体：验证主体仍是无状态验签，黑名单只存被吊销的少量 jti，不是全量会话，比 session 轻。但也说明一旦需要即时吊销，纯无状态就不成立——不如承认需要多少状态、按需选 session 或混合方案。
