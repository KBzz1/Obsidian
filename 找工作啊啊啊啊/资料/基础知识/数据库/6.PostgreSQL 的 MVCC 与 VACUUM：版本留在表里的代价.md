# PostgreSQL 的 MVCC 与 VACUUM：版本留在表里的代价

## 同一个思想，两种放版本的位置

MVCC 让读不阻塞写的思路各库共通：写不覆盖旧数据而是产生新版本，读的人按快照挑能看见的版本（概念与可见性判定见 [[2.事务与隔离级别：锁与 MVCC]]）。差别在旧版本放哪：InnoDB 把旧版本收进 undo log，版本链在回滚段里，表内只留最新版；PG 把所有版本就地留在表里——UPDATE 不原地改行，而是给旧行打删除标记、另插一行新版本，表随着修改越来越厚。这一个决定引出 PG 特有的三件事：VACUUM、表膨胀、事务 ID 回卷。

## xmin 与 xmax：版本号就写在行头上

PG 的行叫元组（tuple），每个元组头部带两个系统字段：xmin 是创建这个版本的事务 ID，xmax 是删除它的事务 ID，空值表示还没被删。UPDATE 一拆为二：旧行的 xmax 记下更新者，新行带着新 xmin 入表。判断某版本对某快照是否可见，拿 xmin/xmax 对应事务的提交状态与快照的活跃事务集比对，思路与 [[2.事务与隔离级别：锁与 MVCC]] 的 ReadView 一致：xmin 事务在快照时刻已提交才可见；xmax 事务已提交则这个版本已被删或被换掉。

隔离级别的口径与 InnoDB 不同处要带限定：PG 默认 READ COMMITTED，每条语句拿一个新快照，同事务两条语句可能读到不同结果；REPEATABLE READ 是事务内第一条查询时生成快照、用到事务结束——快照隔离，标准 RR 允许的幻读在这一级被快照天然挡住（InnoDB 同级靠 MVCC 加临键锁，路径不同，见 [[2.事务与隔离级别：锁与 MVCC]]）。

## 走查：改过两次的行

```text
UPDATE 两次后，表里的物理版本（calories 列为例）：
  v3 (520, xmin=105)                    ← 当前版本，105 号事务创建
  v2 (480, xmin=103, xmax=105)          ← 被 105 更新掉，等价已删
  v1 (450, xmin=100, xmax=103)          ← 被 103 更新掉，等价已删

另一事务 108 的语句快照：活跃事务 = {105, 110}
  v3：xmin=105 还活跃 → 未提交，不可见
  v2：xmin=103 已提交；xmax=105 未提交 → 删除对 108 尚未生效
  → 108 这条语句读到 480；105 提交后，108 的下一条语句（RC）改读 520
```

## dead tuple 与表膨胀

被更新或删除的旧版本，等所有可能还在读它的快照都结束后，对所有人不可见——死元组（dead tuple）。它占的空间不会自动释放：数据库无法断言哪个时刻起再无人需要它（长事务攥着的快照可以非常老），索引里也留着指向它的项。旧版本持续堆积，表和索引比有效数据大出数倍——表膨胀（bloat），扫描变慢。长事务是头号推手：autovacuum 不敢回收任何比现存最老快照更新的死元组，一个忘关的事务能把整库的清理卡住。

## VACUUM 与 autovacuum

VACUUM 是清理动作：扫表识别死元组，把它们占的页空间标记为表内可复用，并同步清理索引里指向死元组的项；空间不还给操作系统。autovacuum 是后台进程按阈值（死元组数量与修改量）自动触发的 VACUUM，不拿阻塞读写的锁——它是 PG 必须开着的基础设施，不是可选项。VACUUM FULL 是另一档：重写整张表把空间真正还给系统，代价是排他锁挡住一切读写，生产上只敢在维护窗口做，常规膨胀治理用 pg_repack 这类扩展在线重写。

## 事务 ID 回卷与冻结

事务 ID（xid）32 位，约 42 亿个，写多的库会耗尽。ID 比较按取模环绕：绕一圈后老 ID 会「跑到」新 ID 前面，可见性判定随之翻转——回卷（wraparound）。对策是冻结（freeze）：autovacuum 顺手把足够老、必然对所有人可见的元组的 xmin 改写成冻结标记（一个特殊事务 ID，含义是比一切都老），这些元组不再依赖原始 xid，ID 就能安全复用。这解释了一个反直觉现象：只 INSERT 从不 UPDATE/DELETE 的表，autovacuum 也会来——不是清死元组，是冻结老元组防回卷。

> [!example] 实践例子
> LangGraph 的 PostgresSaver 按 superstep 追加写检查点（每个 superstep 一行、链到父检查点，见 [[2.1 LangGraph 检查点与 Channel]]）：追加为主的表几乎不产生死元组，是 PG 侧负担最小的写入形态。应用层的并发序列（检查-执行防丢失更新）在 PG 默认隔离下同样要自己管，见 [[2.事务与隔离级别：锁与 MVCC]] 问答 3。

## 边界问答

**1. Q：** 一句话讲清 InnoDB 与 PG 的 MVCC 差别？
**A：** 旧版本放哪不同：InnoDB 收进 undo log、表内只留最新版；PG 全部就地留在表里。代价分居两头——InnoDB 回滚长事务要顺着版本链走很远（undo 膨胀），PG 靠 VACUUM 收尸，没有 autovacuum 的 PG 会持续膨胀。

**2. Q：** 只插不删的表为什么也有 autovacuum 光顾？
**A：** 冻结。32 位事务 ID 会回卷，autovacuum 要给老元组打冻结标记让 ID 可复用——与死元组无关的第二个职责。

**3. Q：** VACUUM 跑完表没变小，为什么？
**A：** 普通 VACUUM 只把死元组空间标记为表内可复用，文件大小不变；要真正收缩得 VACUUM FULL（重写整表、排他锁），生产慎用，常规在线治理靠 pg_repack。
