# MySQL 索引：B+ 树与查询优化

## 索引与数据结构的选型

索引是为加速查询额外维护的有序数据结构：查询少扫表，代价是占空间、拖慢写入（每次写数据要同步维护索引）。候选结构各有死穴：哈希表等值查询 O(1) 但完全无序，范围与排序做不了；二叉搜索树（红黑树一族）100 万行树高约 20 层，磁盘上按页读取、一层一次 IO，树太高就太慢——磁盘 IO 按毫秒计，树必须矮胖；B 树多路了，但每个节点都存数据行，单页装不下几个键，扇出上不去，范围查询还要中序回溯；B+ 树胜在两点——非叶子节点只存键不存数据（扇出极大），数据全在叶子且叶子串成有序双向链表（范围查询顺链走）。

## B+ 树的规模账

先说页：页是 MySQL 与磁盘交换数据的最小单位，InnoDB 一页 16KB——树上一个节点就是一页，读一个节点就是一次页读取，树高几层就几跳。非叶子页按「主键 8 字节 + 页指针 6 字节」算每项 14 字节，一页约 1170 个键；叶子页按一行 1KB 算约 16 行。三层树：1170 × 1170 × 16 ≈ 2200 万行——上千万行的表查一行最多 3 次页读取，其中根页常驻内存缓冲池，实际磁盘 IO 通常一两次。B+ 树矮胖的价值就一句：树高即 IO 次数。

## 聚簇索引与二级索引

InnoDB 的表本身就是一棵按主键组织的 B+ 树（聚簇索引）：叶子页存整行数据，表即索引。没有显式主键时，InnoDB 拿第一个 NOT NULL 的 UNIQUE 索引顶替，再没有就生成隐藏的自增 row_id。二级索引（辅助索引）是另外的 B+ 树：叶子存「索引列的值 + 主键值」，不存整行。于是查非索引列要走两步——先在二级索引拿到主键，再回聚簇索引取整行，第二步叫回表。用一张具体的表把两棵树摆出来：

```text
orders 表（主键 id，二级索引 idx_user_id）

聚簇索引（主键树）              二级索引 idx_user_id
叶子按 id 排，存整行             叶子按 user_id 排，只存 (user_id, id)
  id=1  张三  99 元               user_id=7 → id=1
  id=2  李四  50 元               user_id=7 → id=5
  id=5  王五  30 元               user_id=9 → id=2

SELECT *    WHERE user_id=7：① 二级索引拿到 id=1、id=5 → ② 拿 id 回主键树取整行（回表）
SELECT user_id WHERE user_id=7：第 ① 步直接出答案，② 免了（覆盖索引）
```

两个顺理成章的推论：

- 覆盖索引：SELECT 的列全部落在某个二级索引里（如索引 (user_id, created_at)，只查这两列），叶子页直接给全答案，免回表。EXPLAIN 的 Extra 出现 Using index 就是它。
- 自增主键：新行永远追加到最右叶子页，页满开新页，顺序写；随机主键（UUID）插进已有页的中间，页满触发页分裂——旧页拆两半、父页更新，写放大加碎片。且所有二级索引的叶子都存主键值，主键越长，全部索引跟着变肥。

## 联合索引与最左前缀

联合索引 (a, b, c) 的排序规则：先按 a 排，a 相同按 b，b 相同按 c——像字典先按首字母再按第二个字母。由此可推全部使用规则：WHERE a=? AND b=? 能用；只 WHERE b=? 用不上（b 在整体上无序）；a=? AND c=? 只用到 a 段。范围查询截断：a BETWEEN 1 AND 100 之后 b 的有序性失效（各 a 段内 b 有序，跨段不再有序），范围条件之后的列用不上索引加速。字符串列的前缀索引（只索引前 n 字符）与 ORDER BY 能否走索引，都是同一套排序规则的推论。落到具体索引上：

```sql
CREATE INDEX idx_order ON orders (user_id, status, created_at);
-- WHERE user_id=? AND status=?          → 最左两列连续命中，走索引
-- WHERE user_id=? ORDER BY created_at   → 等值后有序，连排序都免了
-- WHERE status=?                        → 跳过最左列，不走索引
-- WHERE user_id=? AND created_at>?      → 只用到 user_id 段（status 断开）
```

> [!example] 实践例子
> LangGraph 的 PostgresSaver 按 thread_id 存取检查点，checkpoints 表的主键是 (thread_id, checkpoint_ns, checkpoint_id) 联合键，按 thread_id 查全部历史正是最左前缀，见 [[2.2 Checkpointer 抽象与 thread_id]]。B+ 树一族不是 MySQL 专属——Postgres 的默认索引类型 B-tree 同属这一族。

## 边界问答

**1. Q：** 主键为什么推荐自增而不是 UUID？
**A：** 两笔账。写入：自增是纯追加，UUID 随机插页中间，页分裂带来写放大与碎片。空间：二级索引叶子存主键值，UUID 主键让每一棵二级索引同步变肥。

**2. Q：** 索引建了却不走，常见原因？
**A：** 对索引列套函数或隐式类型转换（字符串列传数字），破坏了有序性；列的选择性太低（如性别），优化器判断扫全表更快；统计信息过期导致估算失真。EXPLAIN 看执行路径是第一手段。

**3. Q：** 二级索引的叶子为什么存主键而不存行地址？
**A：** 行的物理位置会因页分裂变动，存地址意味着每次页分裂都要连带更新所有二级索引；主键永不变化，二级索引零维护。代价是回表一次，用一次额外查询换来索引体系的免维护。
