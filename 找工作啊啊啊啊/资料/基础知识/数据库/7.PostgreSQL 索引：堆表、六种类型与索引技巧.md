# PostgreSQL 索引：堆表、六种类型与索引技巧

## 堆表：索引都指向行，而不是行存在索引里

InnoDB 的表本身就是主键 B+ 树（聚簇索引，见 [[1.MySQL 索引：B+ 树与查询优化]]）；PG 的表是堆（heap）：行的物理存放与任何键无关，插入到哪算哪。因此 PG 没有聚簇索引这个层——所有索引（主键也在内）都是独立结构，叶子存「索引键 + ctid」；ctid 是行版本在堆内的物理地址（页号 + 页内偏移），任何索引命中后都按它一次跳到堆取整行。路径账两侧各有顺不顺：InnoDB 按主键查直达整行，按二级索引查要拿着主键回聚簇树再走一截；PG 按主键查多一跳索引到堆，按二级索引查反而直接到堆。不是谁绝对快，是各自把最短路径给了不同入口。

## 六种索引类型

B-tree 是默认：等值、范围、排序都能做，唯一约束靠它。其余五种各换赛道：

| 类型 | 结构与所长的查询 | 典型场景 |
|------|----------------|--------|
| B-tree | 有序平衡树：等值 / 范围 / 排序 | 默认选项，主键与常规列 |
| Hash | 哈希表：只支持等值 | 边缘——B-tree 同样胜任等值 |
| GIN | 倒排：元素映射到行集 | JSONB 包含、数组、全文检索 |
| GiST | 广义搜索树框架 | 地理形状、范围类型、近邻排序 |
| SP-GiST | 空间分区树 | 前缀类划分（radix / 四叉树一系） |
| BRIN | 块范围 min/max 摘要 | 超大表 + 物理顺序相关列 |

两个最常被追问的展开。GIN（Generalized Inverted Index，通用倒排索引）：把「值里的元素」当键、出现该元素的行集当 postings——一个 JSONB 文档含许多键值，一个键值出现在许多文档里，多对多映射正好倒排，JSONB 的包含查询、数组包含、全文检索都靠它（用法见 [[8.JSONB 与 pgvector：文档存储与向量扩展]]）。BRIN（Block Range Index）：不索引单行，只对每段连续页记该段的最小/最大值，索引体积小几个数量级；生效前提是物理顺序与列值相关——时间序列追加写的表按时间查范围正中靶心；数据一乱序，每段的 min/max 覆盖全域，过滤等于没滤。

## 部分索引与表达式索引

```sql
-- 部分索引：只收未完成订单，几万行小索引替代亿行大索引
CREATE INDEX idx_orders_pending ON orders (created_at)
    WHERE status = 'pending';                 -- 仅满足条件的行进入索引

-- 表达式索引：索引存 lower() 的结果，查询侧同样写 lower(email) 才命中
CREATE INDEX idx_users_email_lower ON users (lower(email));
```

适用面各一句：部分索引适合基数悬殊的状态列——全表上亿、未完成的几万行，待处理队列的查询只扛几万行的索引；表达式索引适合查询总套函数的列——按 lower(email)、按计算结果查，直接索引表达式本身。

> [!example] 实践例子
> PostgresSaver 首次使用要调 setup()，职责就是建表建索引（见 [[2.2 Checkpointer 抽象与 thread_id]]）；它按 thread_id 存取检查点，读路径主干是「按 thread_id 取最新一行」，靠 thread_id 上的索引撑。向量列的索引不在本篇类型里——那是 pgvector 扩展带来的 HNSW/IVFFlat，见 [[8.JSONB 与 pgvector：文档存储与向量扩展]]。

## 边界问答

**1. Q：** PG 没有聚簇索引，主键查询是不是天生吃亏？
**A：** 路径上多一跳：索引命中后还要按 ctid 跳堆取整行，InnoDB 主键树叶子即整行。换来的全局收益是所有索引平权：二级索引直接 ctid 到堆，比 InnoDB 的二级索引少一次中转；代价是堆无序——范围扫描没有聚簇性，主键也不决定表的物理布局。

**2. Q：** BRIN 索引这么小，为什么不全用它？
**A：** 它赌的是物理顺序与列值相关：追加型时间序列正中靶心，段级 min/max 一跳就跳掉无关块；数据一乱序，每段 min/max 都覆盖全域，等于没过滤，查询退回全扫。极小体量换粗粒度过滤，是 B-tree 逐行精确的另一个极端。
