# 事务与隔离级别：锁与 MVCC

## 事务与 ACID

事务是一组 SQL 作为整体生效或整体失败的执行单元：转账的扣款与入账要么都发生、要么都不发生。ACID 四性：原子性（Atomicity，失败回滚，靠 undo log 记下反向操作）、一致性（Consistency，前三性共同达成的结果——约束始终满足）、隔离性（Isolation，并发事务互不干扰的程度，本篇主线）、持久性（Durability，提交即不丢，靠 redo log 先落盘再返回成功）。

## 三种并发读异常

不加控制时，并发事务会互相看到对方写到一半的数据，按严重程度分三档：脏读——读到别人未提交的修改，对方回滚后，你基于一条从未存在过的数据做了决策；不可重复读——事务内两次读同一行，值变了，中间别人提交了 UPDATE，同一事务内事实前后矛盾；幻读——两次同样范围条件的查询行数变了，中间别人提交了满足条件的 INSERT，多出来的行破坏范围语义。

## 隔离级别

SQL 标准用四个隔离级别在「隔离程度与并发性能」之间权衡：读未提交（三异常都有）→ 读已提交 RC（防脏读）→ 可重复读 RR（再防不可重复读）→ 串行化（并发事务效果等同排队执行）。InnoDB 默认 RR，Postgres 与 Oracle 默认 RC——可重复读不是所有数据库的默认，表述时要带上「InnoDB 默认 RR」这个限定。

## MVCC

MVCC（Multi-Version Concurrency Control，多版本并发控制）让读不加锁。每行数据带两个隐藏列：最后修改它的事务 id，与指向旧版本的指针；undo log 把历次修改串成版本链，链上每个节点是行的一个历史版本。读的时候构造 ReadView——一个记录「此刻还活跃（未提交）事务」的快照，然后沿版本链从新到旧，找第一个作者事务在快照时刻已提交的版本（事务 id 与活跃列表比较判定：在活跃列表里就是未提交，不可见；比快照还新的事务也不可见），未提交的修改就这样被挡在视图外。

效果：普通 SELECT（快照读）不加锁、不阻塞写，读写互不挡——读的人看历史版本，写的人写新版本，两边看不见对方所以互不等待；换成纯锁方案，写锁会把所有读挡住，读多写少的业务并发立刻掉下去。写与写之间仍靠行锁串行（两阶段锁，事务中陆续加、提交时统一释放）。RC 与 RR 的差别只在 ReadView 的生成时机：RC 每条 SELECT 生成新 ReadView，能看到别人刚提交的修改——不可重复读正是这么发生的；RR 在事务第一次快照读时生成一次、整个事务复用，后续读都在同一快照上，两次读必然一致。

用一条改过两次的行走查可见性：

```text
版本链： (余额=100, trx_id=50) → undo (余额=120, trx_id=40) → undo (余额=150, trx_id=30)
ReadView（RR 事务第一次快照读时生成）：活跃事务 = {45, 50}

走查：trx_id=50 在活跃列表 → 未提交，不可见，沿链退到 40
      trx_id=40 不在活跃列表 → 已提交，可见
      本事务读到的余额 = 120；RR 下后续读全用同一 ReadView，结果不再变
```

## 幻读在 InnoDB 的实际边界

RR 级别下幻读大体被挡住，但分两种机制：快照读靠 ReadView 天然看不见新插入的行；当前读（SELECT ... FOR UPDATE、UPDATE、DELETE 这类读最新版本的语句）靠临键锁（next-key lock，记录锁加间隙锁）锁住范围，阻止别人往里插。漏洞在混用：同一事务先快照读、再当前读，当前读能看到别人已提交的新行，幻读的表现又回来了。串行化级别把所有读都升级为当前读并加锁，幻读彻底消失，代价是并发度崩回串行。

> [!example] 实践例子
> 健康管理项目的跨请求并发不在数据库层解决：Task 状态的版本控制与并发写防护是应用层的检查-执行序列问题，见 [[7.版本控制与并发]]。数据库的 MVCC 只保证单条语句读写的一致视图，跨请求的业务序列要应用层自己管——两层各管一段。

## 边界问答

**1. Q：** InnoDB 的 RR 就没有幻读了吗？
**A：** 快照读没有（ReadView 看不见新行），当前读靠临键锁挡住插入，但两种读模式混用时仍可见已提交新行。标准 SQL 的 RR 本来就允许幻读，InnoDB 是加强实现；说「InnoDB 用 MVCC 加临键锁在 RR 下基本解决幻读」比说「解决」准确。

**2. Q：** MVCC 下读写互不阻塞，写与写呢？
**A：** 写与写靠行锁串行：两个事务改同一行，后到的等前一个提交（或回滚）释放锁再改。MVCC 消除的是读写互堵，不是写冲突——读快照不占锁，写持行锁只挡别的写。

**3. Q：** 有了 MVCC，应用层为什么还要版本号或 SELECT FOR UPDATE？
**A：** 快照读不加锁，两个事务可以基于同一个旧值各自「检查-修改-提交」，后提交的把先提交的改动静默覆盖——丢失更新，数据库默认隔离不拦。要么 UPDATE ... SET x=?, version=version+1 WHERE id=? AND version=? 把检查原子化（乐观锁），要么 SELECT FOR UPDATE 把读升级成加锁的当前读，把业务序列锁死。这正是项目 [[7.版本控制与并发]] 在应用层做的事。
