# Redis：内存数据结构与缓存角色

## Redis 是什么，为什么单线程还快

Redis（Remote Dictionary Server）是内存 KV 数据库：value 不只是字节串，而是五大结构之一，命令按结构分派。命令执行是单线程的——免锁竞争、免上下文切换，加上数据在内存、网络层靠 epoll 事件驱动一条线程监听大量连接（见 [[1.IO 多路复用：从 select 到 epoll]]），单机十万 QPS 量级。6.0 起网络读写与协议解析可以多线程，命令执行仍单线程，原子性模型不变。

## 五大数据结构

- String：字符串、数字或二进制（单值上限 512MB）。缓存 JSON 序列化的对象、INCR 计数器、SET NX 抢分布式锁。
- Hash：field-value 映射。对象按字段读写，改一个字段不用整体序列化。
- List：双端列表。LPUSH 加 BRPOP 组成轻量队列，BRPOP 取不到时阻塞等待。
- Set：无序去重集合。SINTER 求共同关注，SRANDMEMBER 随机抽样。
- ZSet：member 带 score，按 score 有序。排行榜、按执行时间戳排序的延迟队列。底层是跳表——多层稀疏链表，查找 O(log N)，范围查询顺链表走——再加一个哈希表做 member 到 score 的定位。

跳表为什么快，看查 11 怎么走：

```text
L2:  1 ─────────────→ 9                    上层稀疏：大步跳，快速逼近
L1:  1 ────→ 5 ──────→ 9 ──────→ 17
L0:  1 → 3 → 5 → 7 → 9 → 11 → 17          底层全量：精细定位

从 L2 的 1 跳到 9 → 9 再往前就超了，下降 → L1 走到 9 → 下降 → L0 找到 11
```

每个节点掷骰子决定自己出现在几层，期望上越往上节点越稀，步数期望 O(log N)；定位之后范围查询顺着 L0 一路走就是答案。

典型命令的形状：

```text
SET session:42 "{...}" EX 3600     String：会话对象，1 小时过期
INCR api:quota:user42              String：计数器原子自增
HSET user:42 nickname 张三          Hash：单字段更新，不整体序列化
LPUSH queue:task "{job}"           List：生产者入队，消费者 BRPOP 阻塞取
ZADD rank:day 980 "user:42"        ZSet：记分，ZREVRANGE 取榜单
```

## 过期删除与内存淘汰

key 设置 TTL 后的删除靠两条腿：惰性删除（访问时检查，过期则删）加定期删除（周期性随机抽一批过期 key 删掉），平衡 CPU 与内存。内存用量到达 maxmemory 时按淘汰策略腾地方，共 8 种：noeviction（默认，拒绝写入报错）、allkeys-lru 与 volatile-lru（全量 key 或仅带 TTL 的 key 里淘汰最久未用）、对应的 lfu（淘汰访问频率最低）、两种 random、volatile-ttl（优先淘汰快过期的）。缓存场景常用 allkeys-lru。

## 持久化：RDB 与 AOF

RDB 是定时快照：fork 子进程把全量内存写成紧凑的二进制文件，恢复快，代价是宕机丢掉最后一次快照之后的数据。AOF 是追加命令日志：每条写命令追加进文件，刷盘策略 appendfsync everysec（每秒刷一次）是默认折中，最多丢一秒；日志随时间膨胀，靠重写（按当前内存状态生成等价的最小命令集）压缩。4.0 起支持混合持久化：重写后的 AOF 前半段是 RDB 格式，恢复速度与数据量兼得。

## 缓存角色

Redis 的常态角色是挡在数据库前面的读流量层：事实来源在 MySQL，Redis 丢得起、可以随时从库重建。读写模式叫 Cache-Aside（旁路缓存），是应用层的约定而非 Redis 功能——读路径先查缓存，miss 则查库并回填；写路径更新数据库后删缓存。这个模式的不一致窗口与三大故障模式（穿透、击穿、雪崩）见 [[4.缓存穿透、击穿与雪崩]]。

## 边界问答

**1. Q：** 单线程为什么怕大 key 与 KEYS 命令？
**A：** 所有命令排队执行，KEYS * 全库遍历、几 MB 的大 value 读写，都会把后面所有命令堵住。线上禁用 KEYS，用 SCAN 渐进式遍历；大 value 拆分成 Hash 的多个 field 或分片存储。

**2. Q：** Redis 能当主数据库吗？
**A：** 淘汰策略下随时可能丢数据，持久化也有丢失窗口。它的定位是加速层：事实来源放 MySQL，Redis 坏了可重建。真要当主存储，就得关掉淘汰策略并接受持久化窗口内的丢失风险。

**3. Q：** ZSet 为什么用跳表不用红黑树？
**A：** 范围查询顺着链表走更直接，实现与调试比带旋转的平衡树简单，每层节点密度可调、内存可控。官方给的理由主要就是实现简单与范围查询友好。
