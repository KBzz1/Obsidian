# JSONB 与 pgvector：文档存储与向量扩展

## json 与 jsonb：两种存 JSON 的类型

PG 存 JSON 有两个原生类型：json 把输入原样当文本存，保留键顺序、重复键与空白，但每次读都要重新解析，也建不了索引加速查询；jsonb 把文档解析成二进制结构存下，丢掉顺序与重复键（同键后者覆盖前者），写入多付一次解析，换来读得快、可索引。默认选 jsonb——要查询、要索引的 JSON 都归它；只有「原文格式本身是数据」的场景（审计留痕、逐字节归档）才用 json。它让 PG 兼具文档库的灵活：半结构化字段不拆表，与强类型关系列共存一行。

## 包含查询与 GIN 索引

jsonb 最常用的查询是包含语义：`@>` 问左文档是否包含右边的子结构（是否含有某个键值对或子对象），`?` 问是否存在某个键。GIN 索引（倒排索引，见 [[7.PostgreSQL 索引：堆表、六种类型与索引技巧]]）把这些查询变成索引查找：

```sql
-- 事件表：固定列与半结构化属性共存一张表
CREATE TABLE events (
    id       bigint PRIMARY KEY,          -- 主键（示意，未写生成子句）
    payload  jsonb  NOT NULL              -- 事件体：键不固定的 JSON 文档
);

-- 倒排索引：payload 里的键/值元素各映射到包含它的行集
CREATE INDEX idx_events_payload ON events USING gin (payload);

-- 包含查询：payload 含 type=meal_photo 的行，走 GIN 不走全表扫
SELECT * FROM events
WHERE payload @> '{"type": "meal_photo"}';
```

## pgvector：向量类型与 ANN 索引

PG 的核心只做关系引擎，更多能力以扩展（extension）形式装上去：CREATE EXTENSION 一条命令带入新类型、函数、运算符与索引方法，pgvector 就是这样一个扩展。它给 PG 加 vector 类型：定长浮点数组，建列时维度写死（vector(1536) 这类，与所用 embedding 模型对齐，模型概念见 [[1.Embedding 与相似度：从文本到语义向量]]）。距离运算符三种：`<->` 欧氏距离、`<=>` 余弦距离、`<#>` 负内积，用哪个取决于模型与归一化口径。不建索引时是精确检索：全表逐行算距离再排序，几十万行往上就慢；ANN 索引（近似最近邻，原理与召回率代价见 [[2.ANN 检索：HNSW 与召回率权衡]]）用 HNSW 或 IVFFlat 换延迟：

```sql
CREATE EXTENSION IF NOT EXISTS vector;      -- 装扩展：类型与运算符就位

-- 语义记忆表：原文与向量同表
CREATE TABLE memories (
    id         bigint PRIMARY KEY,          -- 主键（示意）
    content    text NOT NULL,               -- 原文
    embedding  vector(1536) NOT NULL        -- 语义向量，维度与模型对齐
);

-- 近似索引：HNSW 的余弦距离版，操作符类指定 <=> 为排序依据
CREATE INDEX ON memories USING hnsw (embedding vector_cosine_ops);

-- Top-5 语义召回：$1 为查询向量
SELECT id, content
FROM   memories
ORDER  BY embedding <=> $1                  -- ORDER BY 距离 + LIMIT 才走 ANN
LIMIT  5;
```

两个要点：距离运算符要与建索引选的操作符类一致（cosine_ops 配 <=>），不配套索引用不上；ANN 只在「ORDER BY 距离 + LIMIT k」的形态下参与，缺 LIMIT 就退化成全排序。建索引与查询参数（hnsw.ef_search 等）调的是召回率与延迟的权衡，概念同 [[2.ANN 检索：HNSW 与召回率权衡]]。

> [!example] 实践例子
> LangGraph 的 PostgresStore 用 PG 承载长期记忆，语义检索创建时给 index 配置才打开（Postgres 上的语义索引即 pgvector，见 [[3.2 长期记忆：Store 与 namespace]] 与 [[2.ANN 检索：HNSW 与召回率权衡]] 的实践例子）；健康管理项目的记忆卡片语义召回就踩在这层机制上。检查点走 PG 关系表、记忆检索走同一库的 pgvector——Agent 应用「一库两用」的典型形态。

## 边界问答

**1. Q：** json 与 jsonb 选哪个？
**A：** 默认 jsonb：读得快、可索引，付出的只是写入时多一次解析与格式信息（顺序、重复键、空白）的丢失。只有原文格式本身要保真的场景用 json。

**2. Q：** 有了 pgvector 还要专门的向量数据库吗？
**A：** 看规模与诉求。百万级向量、要与业务数据同库做事务一致查询的场景，pgvector 够用且省一套系统；到亿级向量、需要量化压缩、分片、独立扩缩的规模，Milvus、Qdrant 这类专用库的优势才拉开——落地形态对比见 [[2.ANN 检索：HNSW 与召回率权衡]]。
