# PostgreSQL 架构：进程模型、WAL 与后台进程

## 进程模型：一个连接一个进程

PostgreSQL 用进程不用线程。实例启动后 postmaster 进程监听端口，每接受一个连接就 fork 一个 backend 进程（服务进程），该连接的解析、优化、执行与会话状态全在这个进程里，连接断开进程退出。MySQL 是线程模型，每个连接一个线程，线程共享地址空间、创建和切换都轻，撑几千连接比 PG 容易；PG 选进程换来隔离与稳定——一个连接出错只死自己的进程，共享内存不会被崩溃的线程污染。代价是连接贵：max_connections 通常只敢给几百，高并发靠 PgBouncer 这类外置连接池承接。PgBouncer 的 transaction 模式在事务边界归还后端连接，几百条应用连接复用几十条真连接，利用率最高；代价是会话级状态不保——SET 的会话参数、LISTEN/NOTIFY 这类跨事务即失效的机制不可依赖。

## WAL：先写日志，再写数据页

WAL（Write-Ahead Logging，预写日志）是崩溃安全的机制：修改数据页前必须先把描述这次修改的日志记录写入 WAL；事务提交只要求 WAL 落盘，脏页本身可以慢慢刷。刷脏页最坏是满盘随机 IO，追加 WAL 是一次顺序写——「先写日志反而快」的原因就在这。checkpoint 周期性把积攒的脏页批量刷盘并在 WAL 里记下位置；崩溃重启后从最近 checkpoint 重放其后的 WAL，宕机前已提交的事务一条不丢，未提交的行版本因 xmin 事务未提交而对读者不可见（可见性判定见 [[6.PostgreSQL 的 MVCC 与 VACUUM：版本留在表里的代价]]）。WAL 也是流复制（物理主从）与 PITR（时间点恢复）的原材料。

实例里另有一组常驻后台进程各管一摊：checkpointer 执行周期性检查点、background writer 平时渐进刷脏页替检查点分摊压力、autovacuum launcher 派 worker 到各库回收死元组——它存在的理由见 [[6.PostgreSQL 的 MVCC 与 VACUUM：版本留在表里的代价]]，没有 VACUUM 的 PG 会持续膨胀。

> [!example] 实践例子
> LangGraph 官方把 PostgresSaver 列为生产环境的检查点实现（LangSmith 自己就用它），连接由 psycopg 的连接池托管，见 [[2.2 Checkpointer 抽象与 thread_id]]。Agent 应用选 PG 的理由在这组笔记的机制里都有落点：checkpoint 与业务表同库要事务与崩溃安全（WAL），语义检索要 [[8.JSONB 与 pgvector：文档存储与向量扩展]] 的扩展生态。

## 边界问答

**1. Q：** 为什么 MySQL 撑几千连接，PG 默认只敢给几百？
**A：** 进程模型：每个连接一个进程，内存独立核算、创建切换比线程重，max_connections 调大后内存与调度先扛不住。解法是 PgBouncer 的 transaction 模式——事务结束就归还后端连接，几百条应用连接复用几十条真连接；代价是会话级状态（SET 参数、LISTEN/NOTIFY）不可依赖。

**2. Q：** checkpoint 会不会卡住业务？
**A：** 会拖慢不会锁死：checkpoint 批量刷脏页时 IO 被抢占，前台写入变慢。PG 用 checkpoint_completion_target 把刷盘摊到整个检查点间隔来削峰，而不是一次打满——调优时这是控制 IO 尖峰的第一个旋钮。
