# PostgreSQL 架构：进程模型、WAL 与后台进程

## 进程模型：一个连接一个进程

PostgreSQL 用进程不用线程。实例启动后 postmaster 进程监听端口，每接受一个连接就 fork 一个 backend 进程（服务进程）：该连接的解析、优化、执行与会话状态全在这个进程里，连接断开进程退出。MySQL 是线程模型，每个连接一个线程，线程共享地址空间、创建和切换都轻，所以 MySQL 撑几千连接比 PG 容易。PG 选进程换来隔离与稳定：一个连接出错只死自己的进程，postmaster 察觉后让全体后端重启，共享内存不会被崩溃的线程污染。代价是连接贵——fork 与每进程独立内存都实打实，max_connections 通常只敢给几百，高并发要靠外置连接池承接，这是 PG 运维与 MySQL 明显不同的一处。

PgBouncer 是 PG 生态的标准连接池：应用开几百条连接指向它，它用少量真连接连库、转发 SQL。session 模式一条应用连接独占一条后端连接，只省连接建立；transaction 模式在事务边界归还连接，同一后端连接先后服务不同应用连接，利用率最高，代价是会话级状态不保——SET 的会话参数、LISTEN/NOTIFY、会话级顾问锁会跨事务丢失或错乱，用前要确认应用不依赖这些；statement 模式每条语句归还，做不了多语句事务，基本不用。

## 一条 SQL 的执行路径

backend 拿到 SQL 走四段：parser 做词法语法分析生成语法树；rewrite 按规则改写，视图展开发生在这一步；planner 是基于代价的优化器，用 ANALYZE 采集的统计信息（每列的行数分布、高频值）估算候选计划的 IO 与 CPU 开销，挑最便宜的；executor 执行计划树，火山模型逐节点要一行算一行。要记住的工程点是规划依赖统计：批量导入或表结构大变后统计过时，代价估算失真，计划可能突然变差——「昨天还快今天慢」的排查第一站是 EXPLAIN ANALYZE 对比执行计划。

## 内存：共享两块，私有按操作类别配额

实例级共享内存最常被问的是 shared_buffers：PG 自己的页缓冲池，官方建议的起点是机器内存的 25%。与 InnoDB 把大部分内存都划给缓冲池不同，PG 刻意只拿一层热数据，其余依赖操作系统页缓存兜底——读未命中的页从 OS 缓存走也是内存速度。WAL buffer 是日志缓冲，事务提交时保证刷进 WAL 文件（WAL 是什么见下节）。进程私有内存按操作类别给配额：work_mem 管单条查询内的排序与哈希，超了就落临时文件，大查询忽慢常卡在这；maintenance_work_mem 单独给 VACUUM、建索引这类维护操作。InnoDB 主要就是一个大 buffer pool，两种配额思路。

## WAL：先写日志，再写数据页

WAL（Write-Ahead Logging，预写日志）是崩溃安全的机制，规则两条：修改数据页前必须先把描述这次修改的日志记录写入 WAL；事务提交的持久性只要求 WAL 落盘，脏页本身可以慢慢刷。刷脏页最坏是满盘随机 IO，追加 WAL 是一次顺序写——「先写日志反而快」的原因就在这。崩溃重启后从最近一次 checkpoint 重放其后的 WAL：checkpoint 是周期性动作，把积攒的脏页批量刷盘、在 WAL 里记下检查点位置；重放把未落盘的修改补齐，宕机前已提交的事务一条不丢，未提交事务即使被物理重放，其行版本也因 xmin 事务未提交而对读者不可见（可见性判定见 [[6.PostgreSQL 的 MVCC 与 VACUUM：版本留在表里的代价]]）。WAL 也是复制与备份的原材料：流复制把 WAL 实时传给备库重放，形成物理主从；基础备份加 WAL 归档能做到 PITR（时间点恢复）——恢复到过去任意时刻。checkpoint 期间脏页集中刷盘可能拖慢前台写入，checkpoint_completion_target 参数把刷盘摊开到整个间隔，削平这个 IO 尖峰。

## 后台进程

checkpointer 执行周期性 checkpoint；background writer 平时渐进刷脏页，替 checkpoint 分摊压力；WAL writer 保证 WAL 缓冲及时落盘；autovacuum launcher 派 worker 到各库回收死元组、采集统计、冻结老元组——它存在的理由见 [[6.PostgreSQL 的 MVCC 与 VACUUM：版本留在表里的代价]]，没有 VACUUM 的 PG 会持续膨胀。这几个进程名在 pg_stat_activity 与日志里常见，排查时先认得出谁在干什么。

## 边界问答

**1. Q：** 为什么 MySQL 撑几千连接，PG 默认只敢给几百？
**A：** 进程模型：每个连接一个进程，内存独立核算、创建切换比线程重，max_connections 调大后内存与调度先扛不住。解法是 PgBouncer 的 transaction 模式——事务结束就归还后端连接，几百条应用连接复用几十条真连接；代价是会话级状态（SET 参数、LISTEN/NOTIFY、会话级顾问锁）不可依赖。

**2. Q：** shared_buffers 为什么不学 InnoDB 尽量调大？
**A：** PG 是双缓冲设计：shared_buffers 只做热数据第一层，之上有操作系统页缓存兜底，官方起步建议约 25% 内存。InnoDB 把缓冲池当主要缓存层，内存给得越多越好。两套思路都能跑好，调优口径不同：PG 调大的收益边际递减，因为 OS 缓存已经覆盖了大量读。

**3. Q：** checkpoint 会不会卡住业务？
**A：** 会拖慢不会锁死：checkpoint 批量刷脏页时 IO 被抢占，前台写入变慢。PG 用 checkpoint_completion_target 把刷盘摊到整个检查点间隔来削峰，而不是一次打满——调优时这是控制 IO 尖峰的第一个旋钮。
