# Embedding 与相似度：从文本到语义向量

## Embedding 是什么

Embedding 把一段文本映射成固定维度的稠密浮点向量（几百到几千维，如 768、1536、3072），由在大语料上训练出的编码模型产出（OpenAI text-embedding-3、开源 BGE 系列等）。它的价值在语义可计算：

```text
「糖尿病人能吃什么」
   │ 编码模型（BGE、text-embedding-3 这类）
   ▼
[0.021, -0.113, 0.087, …, -0.054]    ← 固定维度的浮点数组，入库
「高血糖饮食注意事项」→ [0.018, -0.102, 0.091, …, -0.049]   ← 与上一条很近
「Python 异步编程」   → [-0.44, 0.37, -0.12, …, 0.21]       ← 离得远
```

模型从语料中学到了语义的相邻关系：字面几乎不重叠的两句话，向量挨得很近。语义近即向量近，检索于是从「词是否重叠」（BM25 这类词频统计的稀疏检索）升级为「向量距离是否近」（稠密检索）。稀疏与稠密的差别在这里：稀疏向量长度等于词表大小，只有出现过的词那几位非零，其余全是 0；embedding 是稠密向量，固定几百维、每一位都是模型算出来的值，词没出现语义也在。两者不是替代关系：型号、错误码、专有名词这类必须字面精确的查询，词频匹配更可靠，生产管线常两路都跑、按排名融合结果，即混合检索（hybrid retrieval）。

## 三种度量与归一化后的等价

比较两条向量有多近，有三个常用度量：

```text
余弦相似度   cosθ = A·B / (|A||B|)     只看方向夹角，与模长无关
内积         A·B = Σ aᵢ·bᵢ             模长大的占便宜
欧氏距离     ‖A−B‖ = √(Σ (aᵢ−bᵢ)²)    空间直线距离，越小越近
```

工程惯例是入库前把向量归一化（除以自身模长，变成单位向量），归一化之后三者给出同一排序——余弦等于内积，欧氏距离的平方等于 2 减 2 倍余弦，与余弦单调反相关。所以「向量库该选哪种度量」在归一化前提下是个伪问题：主流向量库默认内积或余弦，效果等价。

## 性质与工程边界

三条必须记住的性质。向量是有损的语义指纹，从中还原不出原文。不同模型的向量不在同一个空间——两家的向量算距离没有意义，同一模型的不同版本也算不同空间。维度由模型定死，换模型等于全库重嵌入加重建索引。检索管线里的位置：查询文本同样 embed 成向量，与库内全部向量算距离取 top-k——「全部算一遍太慢」，这个加速问题就是 [[2.ANN 检索：HNSW 与召回率权衡]] 的主题。

> [!example] 实践例子
> 健康管理项目把用户记忆卡片嵌入成向量，新输入的事实按语义距离召回相关记忆、汇成证据包，见 [[5.记忆卡片与持久化模型]] 与 [[11.代码级逻辑：从用户事实到 EvidenceBundle]]。LangGraph 的长期记忆 Store 同样按语义相似度检索，见 [[3.2 长期记忆：Store 与 namespace]]。

## 边界问答

**1. Q：** 余弦、内积、欧氏到底怎么选？
**A：** 归一化后等价，选哪个都一样，工程惯例是归一化加内积或余弦。只有不归一化且模长携带业务信息的场景（比如想偏向长文本）度量选择才真正影响排序——多数文本检索不是这种场景。

**2. Q：** 距离近就一定语义相关吗？
**A：** 不是。相似不等于相关：「A 与 B 的区别」这条查询与 A、B 都近，否定表述与肯定表述也可能贴近。所以 RAG 管线在向量召回后还有重排（rerank）与阈值过滤——向量距离负责把百万候选缩到几百，相关性判断交给后面几道。

**3. Q：** 换 embedding 模型要注意什么？
**A：** 新旧模型的向量空间不同，不能混存混算——换模型意味着全量重嵌入与索引重建，要规划不可用窗口。选型时把维度（存储成本）、召回质量、单次嵌入成本一起看；库里记录每条向量用的模型版本，混着查出来的结果是错的。
