# 进程与线程：内核视角与上下文切换

## 进程：资源分配的单位

进程是运行中的程序实例，内核给每个进程两样东西。一是进程控制块（PCB，Process Control Block）：内核里描述这个进程的数据结构，记录 pid、当前状态、优先级、保存的寄存器现场、页表指针、打开文件表——内核对进程的管理全部围绕它，所谓切换进程就是从一个 PCB 记录的现场换到另一个。二是独立的虚拟地址空间：每个进程一套从 0 开始编址的内存，从低到高是代码段（机器指令）、数据段（全局变量）、堆（向上增长，动态分配）、共享库映射区、栈（从高向低生长，放函数调用帧）。两个进程的地址空间互不可见，一个进程写坏自己的内存不会波及别人——隔离是进程存在的理由，也是 [[3.进程间通信：从管道到共享内存]] 必须专门开辟通道的原因。

## 线程：CPU 调度的单位

线程是进程内的独立执行流，内核实际调度的单位是线程而不是进程。同一进程的多条线程共享代码段、堆、全局数据与打开文件表，各自独有一份栈和寄存器现场。轻就轻在这里：创建线程不复制地址空间，只是多一份栈和调度记录；切换同进程的线程不换页表；通信直接读写共享内存，不需要内核中转。代价是共享带来竞态——任何两行代码之间都可能被切走，共享数据处处要加锁（原语见 [[5.锁、信号量与死锁]]）；一条线程写坏共享内存，整个进程一起崩。进程与线程在并发模型里的取舍（多线程 vs 单线程事件循环）见 [[1.事件循环、协程与 await]]。

## 进程状态机

进程在三个主要状态间流转：运行（正占着 CPU）、就绪（可以跑，只是在排队等 CPU）、阻塞（在等某个事件——I/O 完成、拿到锁、内核服务返回，等到了也先回就绪）。

```text
              调度器选中                    时间片用完、被抢占
     就绪 ──────────────→ 运行 ──────────────────────→ 就绪
       ↑                    │
       │                    │ 等 I/O、等锁、等内核事件
       │                    ↓
       └──── 事件完成 ───── 阻塞
```

阻塞与就绪的区分是面试常考点：两者都不在 CPU 上，但阻塞在等事件、就绪只等 CPU——事件完成只是把进程从阻塞挪回就绪，能不能上 CPU 还要调度器说了算。

## 调度算法

调度器决定就绪队列里谁先上 CPU、跑多久。教科书算法一组：

```text
先来先服务（FCFS）  按到达顺序执行            实现简单；短任务排在长任务后吃亏
短作业优先（SJF）   估计最短的先执行          平均等待时间最优；时长不可知，长任务饿死
时间片轮转（RR）    每个就绪进程轮流跑一个时间片  公平、响应快；时间片太小切换开销占大头
优先级调度          优先级高的先执行          低优先级可能饿死，用老化（等待越久优先级越高）缓解
多级反馈队列        多个优先级队列，行为动态升降级  交互任务响应快，长任务逐级让位，Unix 系传统基础
```

Linux 服务器场景长期用完全公平调度器（CFS）按虚拟运行时间组织就绪任务，2023 年内核 6.6 起被 EEVDF 取代，思路仍是「按占用 CPU 的份额公平排序」。面试落点在这组算法的取舍，不必展开内核实现。

## 上下文切换

上下文切换是内核把 CPU 从一个执行流换到另一个：保存当前执行流的寄存器现场（程序计数器、通用寄存器、栈指针，存进 PCB），调度器选中下一个，恢复它的现场。跨进程的切换还要换页表基址，之前翻译缓存（TLB）大面积失效（机制见 [[4.虚拟内存：页表、缺页与页面置换]]）。成本分两笔：直接成本是寄存器保存恢复、页表切换与调度决策，微秒级；间接成本往往更大——新上来的执行流把上一个捂热的 CPU 缓存冲掉，之后一段时间的访存都在补 cache miss。三层对比：

```text
            切换内容                             大致成本
进程切换     寄存器现场 + 页表 + TLB 失效 + 缓存变冷  微秒级，叠加缓存惩罚
同进程线程    寄存器现场（地址空间不变）              比进程切换轻
协程切换     用户态保存少量寄存器与栈指针            亚微秒级，不进内核（见 [[1.事件循环、协程与 await]]）
```

## 协程在内核视角里的位置

内核不认识协程：一条线程在内核眼里就是一个调度单位，线程里跑了多少个协程、在哪些 await 处换来换去，内核一概不知。协程切换是用户态库代码在保存和恢复栈指针，没有系统调用、没有调度器介入——便宜的原因与不能利用多核的原因是同一个：一切发生在一条线程的用户态里，要吃满多核仍然要多进程或多线程。

> [!example] 实践例子
> 健康管理项目的部署形态是这两个概念的组合：多个 Worker 各自是独立进程（隔离、可水平扩容），进程内一条线程跑事件循环（并发靠协程在 await 处让位，不靠多线程），状态全在 PostgreSQL 所以进程无记忆、随起随停，见 [[7.版本控制与并发]] 的「Worker 进程模型」。数据库侧是同一组取舍：PostgreSQL 一连接一进程，用重量换隔离稳定；MySQL 一连接一线程，用轻量换连接容量，见 [[5.PostgreSQL 架构：进程模型、WAL 与后台进程]]。Python 侧多线程还有 GIL 挡着并行，见 [[3.GIL：多线程的边界与绕行]]。

## 边界问答

**1. Q：** 进程和线程的区别，一句话怎么说？
**A：** 进程是资源分配的单位（独立地址空间加打开文件表），线程是 CPU 调度的单位（独立栈与寄存器现场）；同进程的线程共享地址空间。再往下还有一层：协程是用户态的调度单位，内核不可见。

**2. Q：** 进程切换比线程切换贵在哪？
**A：** 贵在地址空间：换页表基址、TLB 大面积失效、CPU 缓存变冷。同进程的线程切换不换页表，只剩寄存器现场这笔账。

**3. Q：** 既然线程又轻又能直接共享内存，为什么服务器还常配多进程？
**A：** 要隔离：一条线程把共享内存写坏，整个进程一起崩；一个进程崩掉不影响别的进程。PostgreSQL 用进程模型换「一个连接出错只死自己」，见 [[5.PostgreSQL 架构：进程模型、WAL 与后台进程]]；Python 下还叠加 GIL——CPU 密集要并行只能多进程，见 [[3.GIL：多线程的边界与绕行]]。
