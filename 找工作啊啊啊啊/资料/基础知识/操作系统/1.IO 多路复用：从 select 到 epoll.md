# IO 多路复用：从 select 到 epoll

## 为什么需要多路复用

文件描述符（fd，file descriptor）是进程打开的每个 socket、文件、管道对应的非负整数编号，内核靠它索引这份打开的资源。一条线程 read 一个 socket，没有数据就阻塞睡在那——想同时伺候上万个连接就要上万条线程，MB 级栈与切换开销不可接受（线程成本见 [[1.事件循环、协程与 await]]）。IO 多路复用换一个思路：一条线程把一批 fd 的就绪监听交给内核，谁就绪通知谁，线程只处理有事的连接。真实负载也配合这条路：Web 服务器挂几万条长连接，任意时刻活跃读写的往往只有一小撮。

## select 与 poll

select 把要监听的 fd 集合（bitmap，上限 `FD_SETSIZE` = 1024）从用户态拷进内核，内核线性扫一遍有没有就绪的；没有就阻塞，有就改个标记返回，用户态再遍历找出就绪的 fd。poll 换成 pollfd 数组，没有 1024 的硬上限，但每次调用全量拷贝加 O(n) 扫描的模式没变——连接数一大，每次等待的固定成本就大。

## epoll

epoll 把「注册」与「等待」拆开：

```text
epoll_create() → 建一个 epoll 实例（内核里的监听站）
epoll_ctl()    → 注册 fd 与关注的事件（增删改），fd 挂进内核红黑树，注册一次常驻
epoll_wait()   → 取走就绪列表；没有就绪事件时在这里阻塞
```

fd 有事件时，内核通过回调把它挂进这个 epoll 实例的就绪链表。epoll_wait 只看链表、只返回就绪的 fd，成本从与监听总数相关变成与活跃数相关——这是 select/poll 每次全量拷贝加 O(n) 扫描做不到的。三代并排看：

```text
            select           poll             epoll
fd 上限      1024            无硬上限          无硬上限
集合传递     每次全量拷贝     每次全量拷贝      注册一次常驻
就绪发现     内核 O(n) 扫描   内核 O(n) 扫描    事件回调挂就绪链表
返回内容     改过标记的全集   改过标记的全集    仅就绪集合
```

直觉对比：1 万条连接、50 条活跃。select 每次等待都要拷 1 万个 fd 进内核、扫 1 万个，返回后用户态再遍历 1 万个找出就绪的 50 个；epoll 的 epoll_wait 直接返回那 50 个。连接越多、活跃越少，差距越大。

## LT 与 ET

epoll_wait 通知就绪有两种模式。LT（水平触发，Level Triggered，默认）：只要接收缓冲区里还有数据没读完，每次 epoll_wait 都继续报。ET（边缘触发，Edge Triggered）：只在缓冲区从空到有的那一刻报一次。同一场景看差别：

```text
客户端发来 2KB，应用只读了 1KB 就去处理了：
LT：之后每次 epoll_wait 继续报「可读」，直到剩的 1KB 被读完
ET：只报过那一次，剩的 1KB 不主动读完，永远没人再提醒你
```

所以 ET 必须配合非阻塞 fd：非阻塞的 read() 在没数据时不再睡等，而是立刻返回 EAGAIN（意思是「这会儿没数据了」），应用循环 read 到拿到 EAGAIN，才算确认读空。ET 省重复通知，代价是编程更苛刻；Python 的 asyncio 走 LT，nginx 用 ET。

## 与事件循环的关系

Linux 上 asyncio 的事件循环底层就是 epoll：[[1.事件循环、协程与 await]] 里调度员的等待名单对应 epoll_ctl 注册的 fd 集，结果到达移回就绪名单对应内核回调挂就绪链表，事件循环每轮调 epoll_wait 取就绪事件。整个进程只有 epoll_wait 这一处真正的阻塞——线程永远在「执行就绪代码」与「等待下一个事件」之间循环，这是单线程撑起大量并发的系统层答案。跨平台对应物：macOS 的 kqueue、Windows 的 IOCP，Python 的 selectors 模块把它们统一成一套接口。

> [!example] 实践例子
> 健康管理项目 Worker 的 asyncio 事件循环在 Linux 上就是 epoll_wait：几十个用户会话同时挂着等 LLM 响应，活跃事件只有零星几个，正是 epoll 的「大量连接、少量活跃」红利区，Worker 进程模型见 [[7.版本控制与并发]]。MCP 的 Streamable HTTP 服务端同时维持多条 SSE 长流，同一模型。

## 边界问答

**1. Q：** epoll 比 select 快，快在哪三点？
**A：** 注册信息常驻内核（epoll_ctl 一次），不用每次等待全量拷贝集合；就绪靠内核回调挂链表，不用每次全量扫描；epoll_wait 只返回就绪 fd，用户态不用遍历全部连接找谁就绪。

**2. Q：** 所有连接都活跃时 epoll 还有优势吗？
**A：** 优势缩小：就绪集趋近全量集时，返回与处理都是 O(活跃数)，select/poll 的 O(n) 扫描相比之下不再悬殊。epoll 的红利在「大量连接、少量活跃」——长连接服务的常态，不是通用加速器。

**3. Q：** 多路复用和真异步 IO（io_uring）是一回事吗？
**A：** 不是。epoll 只回答「谁可以读了」，read 本身仍要应用发起，数据从内核拷到用户态这步同步发生——这叫就绪模型。io_uring 是完成模型：应用提交读写请求，内核做完（含拷贝）再把完成事件放进队列通知应用。Linux 服务端生态目前 epoll 仍是主流，io_uring 在逐步铺开。
