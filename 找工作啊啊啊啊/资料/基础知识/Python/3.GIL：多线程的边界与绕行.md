# GIL：多线程的边界与绕行

## GIL 是什么

GIL（Global Interpreter Lock，全局解释器锁）是 CPython 解释器里的一把全局互斥锁：同一个进程内，任何时刻只有一条线程能执行 Python 字节码。字节码是把 .py 源码编译后的一步步中间指令，CPython 逐条执行它们来跑你的程序——锁住字节码的执行权，等于锁住了「跑 Python 代码」这件事本身。所以开四条线程做纯 Python 计算，实际是四条线程轮流执行，不是并行。它是 CPython 的实现细节，不是 Python 语言的规范——Jython、IronPython 等其他实现没有 GIL，只是日常说 Python 默认指 CPython。

存在的原因在 CPython 的内存管理方式。CPython 用引用计数管理对象生命周期：每个对象头部记着「正被几个地方引用」，计数归零就回收——`a = [1, 2]` 再 `b = a`，这个列表的计数是 2，del 掉一个名字计数减 1，减到 0 立即释放内存。两条线程同时改同一个计数就可能出错。给每个对象配一把锁（细粒度锁）实现复杂、单线程执行也凭空多开销，CPython 退而求其次：一把全局锁把所有字节码执行串起来，解释器内部状态就安全了。

## 对两类负载的不同影响

IO 密集与 CPU 密集的分界在 [[1.事件循环、协程与 await]] 讲过，GIL 对两者的作用完全不同：

- IO 密集：线程发起网络请求、读写文件这类阻塞调用时会睡在系统调用上等数据，睡之前解释器把 GIL 放开——等 I/O 的线程不占着锁，其他线程照常执行。所以 HTTP 服务开多线程，每个请求的大部分时间都在「睡觉让锁」，多线程仍然有效，GIL 不构成瓶颈。
- CPU 密集：线程在执行纯计算字节码，锁一直握在手里，八核八线程也是轮流执行，并行度是 1。不仅没有加速，还要额外付锁竞争与线程切换的成本，可能比单线程更慢。

解释器还有一个让位机制：每隔一段时间（`sys.getswitchinterval()`，默认 5 毫秒）强制当前线程释放 GIL，给其他线程机会，避免某条计算线程长期独占。

## 绕行路线

```text
CPU 密集 + 多核需求
├─ multiprocessing 多进程：每个进程独立解释器、独立 GIL，真正并行
│    代价：进程创建慢、进程间通信要序列化
├─ 下沉到 C 扩展：NumPy 这类库的大数组运算在 C 层执行并主动释放 GIL
├─ 拆独立服务：重计算交给独立进程/服务，主进程保持轻快
└─ free-threading 构建：无 GIL 的 CPython（见下），尚未成为默认
```

多进程是最直接的路线：进程是资源分配单位，各自有独立解释器与 GIL，四进程在四核上真并行；代价在进程间通信——传数据要序列化，共享状态要用 multiprocessing 提供的共享内存或队列。

free-threading（去 GIL）是 CPython 的进行中工作：PEP 703 推动的无 GIL 构建，Python 3.13 起作为实验性构建提供，3.14 转为官方支持但仍非默认。它把引用计数改造成无全局锁的方案，单线程性能仍有代价，大量 C 扩展需要适配；官方尚未宣布把它设为默认构建的时间表。在它成熟之前，多进程与 asyncio 仍是生产环境的默认答案。

## 与 asyncio 的位置关系

asyncio 是单线程模型，协程切换发生在 `await` 处，根本不制造线程级竞争，GIL 对它既不是助力也不是瓶颈。反过来，GIL 恰好解释了 asyncio 为什么流行：多线程在 CPU 密集上无用、在 IO 密集上有 MB 级栈与抢占式切换的成本，asyncio 用更低的成本拿到同样的 IO 并发。真正两边都救不了的是协程里跑重计算——事件循环被占住，谁也切不进来（见 [[1.事件循环、协程与 await]] 的边界问答），多线程也救不了（GIL），只剩多进程或独立服务一条路。

> [!example] 实践例子
> 健康管理项目的 Worker 是 IO 密集型：耗时几乎全在等 LLM 返回，单线程 asyncio 足够，Worker 进程模型见 [[7.版本控制与并发]]。反过来，哪天要引入本地模型算 embedding 这类 CPU 密集任务，放进 Worker 进程会卡住事件循环，多线程救不了（GIL），解法是拆独立进程或服务。

## 边界问答

**1. Q：** GIL 保护了什么，没保护什么？
**A：** 保护 CPython 解释器内部状态——引用计数、内存管理结构，保证字节码执行不出现解释器级竞态。不保护你的程序数据：`counter += 1` 是读-改-写多条字节码，中间可被切走，多线程下照样要自己加锁。个别操作（如 dict 单次存取）在 GIL 下碰巧原子，是实现细节，不能当契约依赖。

**2. Q：** IO 密集选多线程还是 asyncio？
**A：** 两者都有效（线程等 I/O 时释放 GIL），差别在成本。线程是 MB 级调用栈加操作系统抢占式切换，几千并发就是几千线程，且共享内存任何两行之间可能被切走、处处竞态。asyncio 协作式切换、切换点显式，代价是全链路异步库、一个阻塞调用卡住全场。几千上万并发连接选 asyncio；几十并发、手头是阻塞库，线程更省事。

**3. Q：** free-threading 之后这些取舍就消失了吗？
**A：** 还没。3.13/3.14 的无 GIL 构建仍非默认，单线程性能有代价，C 扩展生态在适配中，切换成默认没有时间表。在那之前，「CPU 密集用多进程、IO 密集用 asyncio、多线程只当顺手工具」仍然是默认答案。
