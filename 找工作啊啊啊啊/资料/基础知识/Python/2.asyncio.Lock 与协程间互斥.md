# asyncio.Lock 与协程间互斥

## await 之间可以插队

事件循环只在 `await` 处切换协程，所以两个 `await` 之间的代码不会被插队；但一段逻辑跨越了 `await`，中间就可能被其他协程插进来。典型的检查-执行序列：

```python
async def handle(user):
    active = await query_active(user)  # 挂起点：这之后可能切换到别的协程
    if active is None:
        await create(user)             # 与检查之间隔着 await，两步不原子
```

两个请求交错执行的可能顺序：

```text
请求 A：查 → 没有
                    ← A 在第二个 await 前被切走
请求 B：查 → 没有
请求 B：创建
请求 A：恢复 → 也创建    # A 的检查结果已过期，仍基于旧结果行动
```

这与多线程的数据竞态同构，差别只在切换点：线程任何两行代码之间都可能被切走，协程只在 `await` 处。

## asyncio.Lock 的用法

`asyncio.Lock` 是 asyncio 提供的锁对象，用 `async with` 包住需要互斥的整段序列：

```python
lock = asyncio.Lock()  # 一段关键区一把锁，模块或对象初始化时创建

async with lock:                    # 拿锁；拿不到就挂起当前协程排队
    active = await query_active(user)
    if active is None:
        await create(user)
                                    # 出了 async with 自动放锁
```

请求 A 持锁期间，请求 B 执行到 `async with lock` 被挂起等待，A 放锁后 B 才继续——这段检查加创建在同一进程内被排成先后执行。锁必须包住整个序列而不是只包创建那一步：竞态出在检查与执行之间，只锁后半段挡不住过期检查。

## 挂起协程，不阻塞线程

`threading.Lock` 是线程锁：拿不到锁时阻塞整个线程。放进协程代码等于冻住事件循环——这条线程上所有协程一起卡死，直到锁被释放。`asyncio.Lock` 拿不到锁只挂起当前协程，事件循环继续执行其他就绪任务。这是异步锁的含义，也是协程代码必须用 `asyncio.Lock`、不能拿 `threading.Lock` 凑合的原因。

## 进程内锁的边界

`asyncio.Lock` 是普通 Python 对象，活在创建它的进程内存里。部署多进程或多台机器时，各进程持有各自独立的锁对象，互相不可见：进程 1 的请求拿着进程 1 的锁，照样挡不住进程 2 的请求通过同样的检查。所以它只能消除单进程内的竞态；跨进程互斥要靠进程外的共享机制——数据库唯一约束、带版本号的条件 UPDATE，或分布式锁。锁放在哪一层，正确性就由哪一层保证。

> [!example] 实践例子
> 健康管理项目的并发控制组合正是这个分层：`asyncio.Lock` 只作单进程优化，降低同一 Worker 内请求互撞的概率；跨 Worker 的「一个会话最多一个活跃任务」由 PostgreSQL 部分唯一索引兜底，状态更新由版本号乐观并发控制。完整组合与推导见 [[7.版本控制与并发]]。

## 边界问答

**1. Q：** 单线程的协程为什么还需要锁？
**A：** 协程在 `await` 处会切换，跨越 `await` 的检查-执行序列可能被其他协程插队，检查结果过期后仍被使用。锁保护的是这种序列，不是并行执行。

**2. Q：** 用 `threading.Lock` 保护协程关键区行不行？
**A：** 不行。`threading.Lock` 拿不到锁会阻塞整个线程，事件循环随之冻结，同进程所有协程一起卡住；`asyncio.Lock` 拿不到锁只挂起当前协程，其他协程照常推进。

**3. Q：** `asyncio.Lock` 能防止两个服务进程同时创建同一条记录吗？
**A：** 不能，它是进程内存里的对象，跨进程互相不可见。跨进程互斥依赖数据库层：唯一约束让重复 INSERT 只有一个成功，或带版本号的条件 UPDATE 拒绝旧版本写入。项目里的落地见 [[7.版本控制与并发]]。
