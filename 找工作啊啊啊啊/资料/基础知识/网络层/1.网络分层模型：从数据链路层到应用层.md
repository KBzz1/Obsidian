# 网络分层模型：从数据链路层到应用层

## 为什么分层

把一台机器上的 JSON 变成另一台机器收到的 JSON，中间是一串彼此独立的子问题：数据怎么打包、怎么找到目标机器、怎么保证不丢不乱、怎么在物理介质上变成信号。协议栈的答案是把它们分给四层，每层只对上一层提供服务、只使用下一层的服务，层与层之间通过固定格式（各层的头部）交互。分层的回报是替换隔离：Wi-Fi 换成以太网、HTTP/1.1 换成 HTTP/2，相邻层不受影响；写 LLM 应用的代码一行都不用动。

## TCP/IP 四层

互联网实际运行的是四层模型，每层有明确的职责、代表协议与寻址标识：

| 层 | 职责 | 代表协议 | 寻址标识 |
|---|---|---|---|
| 应用层 | 应用间通信语义：请求响应、消息格式、鉴权 | HTTP、WebSocket、SSE、DNS、TLS | URL / 域名 |
| 传输层 | 进程到进程的字节送达：可靠性、端口 | TCP、UDP | 端口号 |
| 网络层 | 主机到主机：寻址与跨网络路由 | IP、ICMP | IP 地址 |
| 数据链路层 | 相邻节点间传输帧 | 以太网、Wi-Fi | MAC 地址 |

写 LLM 应用时三个层的标识天天见面：endpoint 里的域名是应用层的地址，`api.openai.com:443` 的 443 是传输层端口，「这台机器的 IP」是网络层地址。数据链路层以下由操作系统与网络设施处理，应用代码只在排障时感知它（网线、Wi-Fi、代理）。

两个位置细节。其一，TCP/IP 模型没有单列物理层（网线、光纤、无线电信号），讨论时并入数据链路层；OSI 参考模型把它单列为最底层。其二，TLS 在表里挂在应用层一列，但严格位置是夹在传输层与应用层之间的薄层——把应用层字节流加密后交给 TCP 发送。「Transport Layer Security」是命名习惯，不是「TCP 所在的那层」。

## OSI 七层与四层的映射

OSI 七层是 ISO 的参考模型（ISO 7498，1984），教材与故障排查常用它；TCP/IP 四层是互联网先跑起来之后总结的事实模型。映射关系：

| OSI 七层 | TCP/IP 四层 |
|---|---|
| 7 应用 / 6 表示 / 5 会话 | 应用层 |
| 4 传输 | 传输层 |
| 3 网络 | 网络层 |
| 2 数据链路 / 1 物理 | 数据链路层 |

面试两头都要能对上：说四层时知道 HTTP 在应用层、TCP 在传输层；说七层时知道 TLS 常被放进 6 表示层（加密与编码的职责），也有口径按实现归在传输层之上——先把它在做什么讲清，再给位置。

## 一次 HTTPS 请求自上而下穿过哪些层

以调用 `POST https://api.example.com/v1/chat/completions` 为例，发送侧每层做的事：

```text
应用层   生成 HTTP 报文：请求行 + 头部 + JSON 请求体
  ↓      请求行里是方法 POST、路径 /v1/chat/completions
TLS     整段报文加密成密文记录
  ↓      Authorization 头里的 key 到这里已是密文
传输层   密文切成 TCP 段，头里带源端口与目标端口（如 49152 → 443）
  ↓
网络层   段装进 IP 包，头里带源 IP 与目标 IP，逐跳路由
  ↓
数据链路层  IP 包装进帧，头里带相邻设备的 MAC 地址，变成电/光/无线信号
```

接收侧按相反顺序逐层剥头：网卡收帧、校验 MAC，剥出 IP 包、校验 IP，TCP 重组字节流，TLS 解密，HTTP 解析，应用拿到 JSON。每层只读写自己那层的头，这就是分层隔离在一次调用里的样子。发起前还有一步应用层服务：DNS 把 `api.example.com` 解析成 IP（DNS 是应用层协议，查询通常走 UDP）。中间设备各居其位：路由器看 IP 转发，交换机看 MAC 转发，反向代理与负载均衡读 HTTP 头工作在应用层。

## LLM API 知识落在哪层

LLM API 目录的笔记内容全部落在应用层：endpoint 路径、Bearer 鉴权头、JSON 请求体、SSE 流式事件（[[1.1 LLM API 的共同形态：endpoint、鉴权与请求骨架]]、[[1.3 流式响应：SSE 与增量事件]]）。往下三层不是无关的黑盒：流式响应「连接保持打开」说的是 TCP 连接的存续（[[2.TCP 连接：握手、可靠传输与长连接]]），key 的保密靠 TLS（[[4.HTTPS 与 TLS：加密握手与证书]]），超时与连接失败是下层故障向上冒泡的形态——应用层接收到的就是这些信号。

> [!example] 实践例子
> 健康管理项目模型网关对三家供应商的调用，整条设计都在应用层（[[11.代码级逻辑：一次 LLM 调用如何装配上下文]]）；网关感知到的超时、连接重置、5xx，是传输层以下故障在应用层的投影，保护与熔断策略见 [[7.外部依赖保护与服务级熔断]]。

## 边界问答

**1. Q：** 教材讲七层、工程文档讲四层，听哪个？
**A：** 两个模型描述同一个协议栈，粒度不同。四层是运行现状，七层把应用层再细出会话与表示、把物理从链路里拆出，适合讲原理与逐层排查。能把 HTTP、TCP、IP、以太网在两个模型里各归对位置，比争论用哪个模型重要。

**2. Q：** SSE 和 WebSocket 是不是独立的一层？
**A：** 不是。两者都在应用层：SSE 是 HTTP 响应的一种持续交付形态（[[5.SSE：HTTP 上的服务端单向推送]]），WebSocket 是从 HTTP 握手升级出的应用层帧协议（[[6.WebSocket：HTTP 升级出的全双工通道]]），底下都跑在 TCP 上。注意「传输」一词在 LLM API 与 MCP 语境里指「消息怎么投递」的协议设计（transport），不是分层意义上的传输层。

**3. Q：** 代理和网关在第几层？
**A：** 看它处理到哪层的头：反向代理、API 网关、负载均衡按 HTTP 头路由，是应用层设备；SOCKS 代理转发 TCP 字节流，工作在传输层；路由器看 IP，在网络层。「代理」这个词在多层都存在，判断依据是它读哪种头。
