# HTTP：请求响应、方法、头部与状态码

## 请求响应模型

HTTP（HyperText Transfer Protocol，超文本传输协议）只定义一种交互形态：客户端发请求，服务端回响应，一问一答，答完即止。请求由请求行（方法 + 路径 + 版本）、头部、可选的请求体组成；响应由状态行（版本 + 状态码）、头部、可选的响应体组成。服务端不会在没有请求时主动开口——「服务端主动推」由此成为需要额外机制解决的问题，SSE 与 WebSocket 都从这个短板出发（[[5.SSE：HTTP 上的服务端单向推送]]、[[6.WebSocket：HTTP 升级出的全双工通道]]）。语义的现行权威定义是 RFC 9110（2022，HTTP Semantics），HTTP/1.1 的报文格式是 RFC 9112。

## URL 与 endpoint

以 `https://api.openai.com:443/v1/chat/completions?stream=true` 为例，URL 的组成：

- scheme `https`：HTTP over TLS，默认端口 443；明文 `http` 默认 80
- host：域名（发起前由 DNS 解析成 IP）或直接写 IP
- port：可省略，省略即用 scheme 的默认端口
- path：资源路径，`/v1/chat/completions`
- query：`?` 起的可选参数，`&` 分隔，常用于开关项（如 `stream=true`）

API 文档说的 endpoint 指 scheme + host + path 的完整地址。LLM API 路径里的 `/v1` 是主版本号，路径级版本控制，见 [[1.1 LLM API 的共同形态：endpoint、鉴权与请求骨架]] 的边界问答。

## 方法

方法表达这次请求想干什么：GET 读资源（参数只能放 URL，没有请求体）、POST 提交数据（数据放请求体）、PUT 整体替换、DELETE 删除。幂等性是重要区分：GET、PUT、DELETE 重复执行结果不变，POST 不是——重复提交会重复生效。LLM API 清一色 POST：请求体是全量对话 JSON，语义是「提交输入、求一次生成」，且天然不幂等，同一输入再问一次是新的计费调用。

## 头部

请求头与响应头都是 `名: 值` 文本行，携带协议元数据。LLM API 常打交道的：

| 头 | 方向 | 作用 |
|---|---|---|
| `Content-Type` | 双向 | 声明体格式。API 请求响应用 `application/json`；SSE 响应用 `text/event-stream` |
| `Authorization` | 请求 | 鉴权。`Authorization: Bearer <key>` 是 Bearer 方案（RFC 6750）：持有令牌者即获授权 |
| `x-api-key` 等自定义头 | 请求 | 协议不限制自定义头，`x-` 前缀是历史惯例（RFC 6648 之后不再要求） |
| `Retry-After` | 响应 | 告知客户端多久后再试，429 限流时配合使用 |

头部是中间设施的第一手信息：网关、限流器、WAF 不解析请求体也能按头路由与计量——MCP 把请求方法镜像进 HTTP 头正是为了这个，见 [[3.2 传输：stdio 与 Streamable HTTP]]。

## 状态码

状态码是响应的第一行结论，按首位数字分五族：

| 族 | 语义 | LLM API 常见 |
|---|---|---|
| 1xx | 过程信息 | 101 Switching Protocols：协议切换，WebSocket 升级的专用出口 |
| 2xx | 成功 | 200 OK；202 Accepted：已受理（MCP 对通知的回法） |
| 3xx | 重定向 | 资源搬家，新地址在 `Location` 头 |
| 4xx | 客户端错误 | 400 请求格式或语义错；401 未认证（key 缺失或无效）；403 无权限；404 路径不存在；429 限流 |
| 5xx | 服务端错误 | 500 内部错误；502 网关从上游收到坏响应；503 暂不可用；529 过载（Anthropic 的非标准码） |

重试的分界线在这里：4xx 是调用方的错，原样重发没有意义，唯一例外是 429 要按 `Retry-After` 退避重试；5xx 与 429 才是重试与熔断的对象。LLM API 各家对 429、5xx 的细节自定义，多供应商路由要按家处理，见 [[2.4 OpenAI 兼容生态：事实标准的形成]]。

## 无状态

HTTP 协议不保存请求间的记忆：每个请求独立完整，服务端处理完即忘。状态要靠应用层补——传统 Web 用 cookie 让服务端找回 session，API 服务用 token 表达身份。LLM API 把无状态推到极致：服务端连对话历史都不存，全部上下文由客户端每次重发（[[1.2 多轮对话：无状态服务与客户端拼接]]）。换来的回报是服务端任意水平扩展：任何实例都能处理任何请求，不需要会话粘滞。

## 连接与版本演进

HTTP/1.0 一请求一条 TCP 连接；HTTP/1.1 默认 keep-alive 持久连接，同一条连接按顺序复用（连接本身的机制见 [[2.TCP 连接：握手、可靠传输与长连接]]）；HTTP/2（2015）改成二进制分帧，一条连接上多个请求并行交织（多路复用），不再互相排队；HTTP/3 把底座换成 QUIC（UDP 上重建可靠传输）。对 API 调用方这些演进基本无感：方法、头部、状态码的语义从 1.1 起稳定，版本由 SDK 与运行时处理。

## 边界问答

**1. Q：** 对话内容能不能放 URL 的 query 里？
**A：** 不能。query 有长度上限（浏览器与中间设施各有约束），且 URL 会进代理与服务器的访问日志，敏感内容跟着泄露。所以对话 JSON 放 POST 请求体、key 放请求头——体和头默认都不进访问日志。

**2. Q：** 401 和 403 怎么分？
**A：** 401 是「没有证明身份或证明无效」（key 缺失、失效），补对凭证能解决；403 是「身份明确但权限不足」，换一把权限不够的有效 key 结果一样。排障顺序：先解决 401，再看 403。

**3. Q：** 无状态和「不是长连接服务」是一回事吗？
**A：** 不是。无状态说的是请求之间没有记忆，是应用层语义；连接是 TCP 层的资源，keep-alive 让一条连接上跑多个无状态请求，两者不冲突。LLM API 说自己「不是长连接服务、没有会话」，指的是不维护对话状态，不代表底层 TCP 连接不能复用——SDK 连接池一直在复用。
