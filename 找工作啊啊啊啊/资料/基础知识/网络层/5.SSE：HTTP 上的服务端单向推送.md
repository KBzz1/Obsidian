# SSE：HTTP 上的服务端单向推送

## SSE 是什么

SSE（Server-Sent Events，服务端推送事件）是搭在普通 HTTP 上的一套事件流格式：服务端把响应的 `Content-Type` 设为 `text/event-stream`，不关连接，持续往响应体里写事件，客户端只收不发。它不是独立的传输协议——没有新端口、没有新握手，就是一次「不结束的 HTTP 响应」。标准归属在 WHATWG 的 HTML 标准里（连同浏览器 API EventSource 一起定义），不是独立 RFC。方向性是名字的核心：只有服务端到客户端一条道，客户端想说话得另发 HTTP 请求。

## 事件格式

响应体是一串事件，每个事件由若干字段行加一个空行构成：

```text
: ping                                ← 注释行：冒号开头，客户端忽略，常用作保活心跳
event: message                        ← 事件类型，客户端可按 type 分发；缺省为 message
id: 41                                ← 事件 id：客户端记住它，断线重连时带回
retry: 3000                           ← 建议的重连间隔，毫秒
data: {"choices":[{"delta":{"content":"今天"}}]}   ← 数据行，UTF-8 文本

                                      ← 空行：事件结束的边界，必须有
```

规则要点：`data:` 可以连续多行，客户端用换行符把它们拼成一个完整数据字段；注释行以冒号开头（整行只有冒号也行），协议设计它就是给心跳用的——服务端周期性发一条注释，连接就始终有流量，不会被中间设施当静默连接掐掉。LLM API 的流式帧正是这套格式里 `data:` 加空行的用法，见 [[1.3 流式响应：SSE 与增量事件]]。

## 自动重连

浏览器 EventSource 内置断线重连：连接断开后自动重连（默认间隔约 3 秒，服务端可用 `retry:` 覆盖），并把最后收到的事件 id 放进 `Last-Event-ID` 请求头带回，服务端可据此从断点续发。注意这只是协议提供的机制，用不用、怎么续由服务端决定——LLM API 的流断了没有续传，客户端整段重发；MCP 2026-07-28 版更直接移除了基于它的断线续传，断流的请求作废重发，见 [[3.2 传输：stdio 与 Streamable HTTP]]。

## 传输细节：没有 Content-Length 的响应

普通 HTTP 响应头带 `Content-Length`，客户端知道读多少字节收工。SSE 响应总长度未知（可能持续几十秒、理论上无限），HTTP/1.1 下用 chunked 传输编码逐块交付，靠连接关闭收尾。这带来两个工程点。其一，服务端必须及时 flush：写进用户态缓冲不算发出，要真正推到 socket 才算。其二，中间的反向代理可能攒缓冲，事件被攒住不转发，流式表现成「卡住」，所以要 `X-Accel-Buffering: no` 这类响应头明确禁止代理缓冲（nginx 的约定头，MCP 规范同样要求，见 [[3.2 传输：stdio 与 Streamable HTTP]]）。

## 在推流方案里的位置

HTTP 请求响应答完即止，服务端主动推有三条路线：轮询（客户端反复发请求问「有了吗」，浪费且延迟高）、SSE（一次请求，响应无限延伸，单向）、WebSocket（双向，握手升级成独立协议）。SSE 是复用 HTTP 基础设施最彻底的：普通连接、普通头部、过代理网关不用特殊配置，重连语义内置——LLM API 与 MCP 都选它不是偶然。三者完整对比见 [[6.WebSocket：HTTP 升级出的全双工通道]]。

## 边界问答

**1. Q：** 浏览器里 EventSource 能带 Authorization 头吗？
**A：** 不能。EventSource 的构造参数只有 URL 与 withCredentials（是否带 cookie），不支持自定义请求头。浏览器侧要用头鉴权，就得放弃 EventSource、用 fetch 手工解析流。服务端调用没有这个限制——SDK 就是普通 HTTP 客户端，LLM API 的主流用法在服务端，不受影响。

**2. Q：** SSE 和 chunked 传输编码是一回事吗？
**A：** 不是一层东西。chunked 是 HTTP/1.1 的传输编码，解决「响应总长度未知时怎么交付」，对上层透明；SSE 是应用层的事件格式约定，定义事件怎么用 `event`/`data`/`id` 字段表达。SSE 流在 HTTP/1.1 上通常由 chunked 承载；HTTP/2 没有 chunked 概念（自带二进制帧流），SSE 照样工作。

**3. Q：** SSE 连接一般被谁掐断？
**A：** 按来源分：反向代理与负载均衡的空闲超时（对策是注释行心跳）；服务端主动关闭（生成结束、负载控制）；网络切换或客户端退出。另外注意普通 HTTP 客户端的读超时——「长时间收不到新字节」会被当成超时掐掉长流，收 SSE 的客户端要调大或关闭读超时，EventSource 没有这个概念。断线后的动作回到应用层：重连加整段重发，或用 Last-Event-ID 续传。
