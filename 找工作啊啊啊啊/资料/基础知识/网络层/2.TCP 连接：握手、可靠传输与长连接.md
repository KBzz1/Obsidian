# TCP 连接：握手、可靠传输与长连接

## TCP 解决什么问题

IP 层的承诺很弱：尽力把每个包独立地送到目标主机，不管丢失、乱序、重复，也不区分主机上哪个进程该收。TCP（Transmission Control Protocol，传输控制协议，1981 年 RFC 793 定义、2022 年 RFC 9293 修订）在 IP 之上把它补齐成一个抽象：两端进程之间的可靠、有序、不丢不重的字节流。端口区分进程（一台机器上 443 给 HTTPS、5432 给 Postgres），序号与确认保证可靠。HTTP、WebSocket、SSE 全部选 TCP 做地基，用的就是「一端写字节进去，另一端按同样顺序读出来」这个保证。

## 连接的建立与关闭

连接是两端为这条字节流维护的状态（序号、缓冲、拥塞窗口），建立连接即双方协商初始状态，标准流程是三次握手：

```text
客户端                        服务端
  | ----- SYN, seq=x -----→  |   第 1 次：请求建连接，我的起始序号是 x
  | ←---- SYN+ACK, seq=y ---- |   第 2 次：同意，我的起始序号是 y，确认收到你的 x
  | ----- ACK, ack=y+1 ----→  |   第 3 次：确认收到你的 y，双向通路确认完毕
```

为什么是三次：通信双方都要确认「我发的对方收得到」和「对方发的我收得到」两个方向，三次是让双方都拿到双向确认的最小次数。两次握手下，服务端无法确认自己发的包客户端能收到，历史网络里迟到的旧 SYN 还会建出只有单方面认可的无效连接。

关闭走四次挥手：

```text
主动方                        被动方
  | ----- FIN --------------→ |   我发完了
  | ←---- ACK --------------- |   知道了；我可能还有数据没发完，先只回确认
  | ←---- FIN --------------- |   我也发完了
  | ----- ACK --------------→ |   确认，连接关闭
```

被关闭方的 ACK 与 FIN 分开，是因为它收到对方 FIN 时自己可能还有数据要发，先回确认，等发完再提自己的 FIN。主动方发完最后一个 ACK 后在 TIME_WAIT 状态停留一段时间才释放端口，防止这个 ACK 丢失时对方重传的 FIN 无人应答。

## 可靠传输怎么做到

四个机制，全部由协议自动完成，应用无感知。确认与重传：接收方每收到一段数据就回 ACK，确认号是期望收到的下一个字节序号；发送方超时未收到 ACK 就重传。序号排序去重：每个字节都有序号，接收方按序号重组流、丢弃重复段。流量控制：接收方在窗口字段里通告自己还剩多少缓冲，发送方不许超发。拥塞控制：发送方从慢启动开始探测网络容量，发现丢包或延迟升高就降速，避免把路径上的网络压垮。

## 长连接与连接复用

握手至少花一个往返（RTT）才能开始传正文，跨洲链路 RTT 上百毫秒。短连接（每次请求建一次连接、用完关闭）把这个成本付在每次调用上；长连接（一条连接上跑多次请求）只付一次。HTTP/1.1 起默认持久连接（keep-alive），SDK 的 HTTP 客户端维护连接池：对同一 host 建好的 TCP 连接用完不关，下一次请求直接复用。高频调用 LLM API 的应用省掉的就是每次握手加 TLS 协商的时间（TLS 的协商叠加在 TCP 握手之上，见 [[4.HTTPS 与 TLS：加密握手与证书]]）。

流式响应是长连接的另一种用法：一条连接被单次响应长期占用——SSE 流持续几十秒，期间这条 TCP 连接只服务这一次生成，见 [[5.SSE：HTTP 上的服务端单向推送]]。

## UDP：另一半

UDP（User Datagram Protocol，用户数据报协议）是传输层的另一个选择：无连接、不维护状态、发一个数据报即算完成，不保证送达、顺序与去重，换来的是头部开销小（固定 8 字节，TCP 头部 20 字节起步）与没有握手延迟。用在实时优先或应用层自建可靠性的场景：DNS 查询（一问一答，丢了重发比建连接快）、视频通话（迟到的帧不如丢掉）、游戏。QUIC（HTTP/3 的底座）是在 UDP 上重建可靠传输与加密的协议，动机之一是绕开 TCP 协议栈更新缓慢——它是「传输层可以换」的当代例子。

> [!example] 实践例子
> asyncio 事件循环等待的「I/O 到达」，底层就是这条 TCP 连接上对方的数据到达本机 socket，事件循环把 socket 可读变成协程唤醒，见 [[1.事件循环、协程与 await]]。LLM 流式响应的几十秒里连接保持打开，模型服务端把增量持续写入，客户端逐帧解析，见 [[1.3 流式响应：SSE 与增量事件]]。

## 边界问答

**1. Q：** TCP 可靠，为什么 LLM 流式还是会断？
**A：** TCP 保证的是「连接存续期间字节不丢不乱」，不保证连接存续。网络切换、代理空闲超时、服务端主动断开都会结束连接，之后的事 TCP 不再管。断流后怎么办是应用层问题：整段重发（LLM API 的常态），或用协议自带的重连续传（SSE 的 Last-Event-ID 机制，见 [[5.SSE：HTTP 上的服务端单向推送]]）。

**2. Q：** 长连接一直开着，谁先受不了？
**A：** 两端各维护连接状态与缓冲，中间的代理、负载均衡还要保持连接映射，静默连接对谁都是纯开销，所以普遍有空闲超时掐断（反向代理默认 60 秒量级）。对策是应用层心跳：SSE 发注释行、WebSocket 发 ping 帧，让连接看起来始终有流量。

**3. Q：** 握手有成本，有没有零握手的做法？
**A：** 有，方向都是压缩或消除往返：TCP Fast Open 允许 SYN 携带数据，TLS 1.3 的会话恢复把再次连接的协商压到 0-RTT，QUIC 把握手与加密合并设计并支持连接迁移（换网络不断连接）。常规业务代码不直接操作这些，通过连接池与运行时配置间接受益。
