# WebSocket：HTTP 升级出的全双工通道

## WebSocket 是什么

WebSocket（RFC 6455，2011）是双向全双工的应用层通信协议：两个方向随时互发消息，共用一条 TCP 连接。它借一次 HTTP 请求完成协议升级——握手是 HTTP，握手之后这条连接上跑的不再是 HTTP，而是 WebSocket 自己的帧格式。它解决的是 HTTP 请求响应模型的另一个短板：请求进行中客户端没法插话，空闲时服务端也没法主动开口。聊天、协作编辑、多人游戏这类双向实时场景需要的就是它。

## 升级握手

客户端发起一个带特殊头部的 HTTP GET，服务端回 101 同意换协议：

```http
GET /chat HTTP/1.1
Host: example.com
Upgrade: websocket                           ← 请求把协议换成 websocket
Connection: Upgrade                          ← 与 Upgrade 配套的标准写法
Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==  ← 客户端随机值，防中间设备缓存误用

HTTP/1.1 101 Switching Protocols
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Accept: s3pAAWJhjQ==           ← Key 拼固定 GUID 后取 SHA-1，证明服务端真懂协议
```

101 Switching Protocols 属于 1xx 状态码家族，含义是「按你的要求换协议」。`Sec-WebSocket-Accept` 由 Key 拼一个固定 GUID 字符串后取 SHA-1 得到——它不提供安全性（任何实现了协议的人都能算出来），作用是证明对端真的实现了 WebSocket：不认识这个协议的中间设备不会算这个值，也就不会把 101 当普通响应缓存下来复用。此后 HTTP 语义在这条连接上终止。

## 帧与保活

升级后的数据按帧收发，帧头里的 opcode 标明类型：1 文本、2 二进制、8 关闭、9 ping、10 pong。大消息可以拆成多个帧，用延续帧接起来。ping/pong 是协议级心跳：一端发 ping，对端必须回 pong，让连接在中间设施眼里保持活跃——与 SSE 用注释行保活是同一目的（[[5.SSE：HTTP 上的服务端单向推送]]）。连接是有状态的：两端都维护这条会话，协议本身不管断线重连，应用层自己补。加密形态是 `wss://`（WebSocket over TLS），对应明文的 `ws://`，生产环境一律 wss。

## 与 SSE/HTTP 的对比

| 维度 | HTTP 请求响应 | SSE | WebSocket |
|---|---|---|---|
| 方向 | 一问一答 | 服务端单向持续推 | 双向全双工 |
| 协议基础 | HTTP | 仍是 HTTP（text/event-stream 响应） | 握手借 HTTP，之后独立帧协议 |
| 客户端中途插话 | 等下一次请求 | 不行，需另发请求 | 行，同一条连接 |
| 断线重连 | 不适用 | EventSource 内置，Last-Event-ID 续传 | 应用层自己做 |
| 代理兼容性 | 最好 | 好，仍是普通 HTTP | 较差，Upgrade 与长连接穿透要额外处理 |
| 典型场景 | API 调用 | 流式生成、订阅通知 | 聊天、协作编辑、游戏 |

## 选型口径

判断顺序：只需要服务端单向推，用 SSE——更简单，HTTP 的连接、头部、代理设施全部照用（[[5.SSE：HTTP 上的服务端单向推送]]）；确实需要双向实时（客户端要在请求进行中说话、高频双向消息），才上 WebSocket，并接受自己管理重连、心跳与代理穿透。LLM API 是「一次请求 + 单向回流」，SSE 正好匹配；生成中途要打断，两家都提供独立的取消机制（另发请求或直接关流），不动传输层，见 [[1.3 流式响应：SSE 与增量事件]]。MCP 同样落在 HTTP/SSE 组合上，见 [[3.2 传输：stdio 与 Streamable HTTP]]。

## 边界问答

**1. Q：** 握手为什么借 HTTP，不直接开 TCP 连接定暗号？
**A：** 现实部署里客户端到服务端之间隔着代理、网关与浏览器安全模型，这些设施只认 HTTP。借 HTTP 头完成升级能自然穿过去；`Sec-WebSocket-Key`/`Accept` 的设计目标之一，就是让不认识 WebSocket 的中间设备把 101 识别为异常而不是缓存复用。

**2. Q：** WebSocket 上有请求响应语义吗？
**A：** 协议层没有。帧只是双向数据，发了不等回复；请求配对、消息格式（常见 JSON）由应用层自己约定。要保留请求响应边界又想要流式，HTTP/SSE 组合更直接——这也是 MCP 的选择。

**3. Q：** 既然 WebSocket 双向，能不能用它把 API 调用也搬进去，一条连接反复请求？
**A：** 能做但不划算。LLM 调用是低频请求加单向长回流，SSE 已覆盖；把多家供应商调用塞进自建 WebSocket 通道，鉴权、重试、限流反馈、连接管理都要自己重造，等于在 HTTP 已有的一层上再发明一层。传输选「够用的最简单方案」，是这篇与 [[5.SSE：HTTP 上的服务端单向推送]] 对比的落点。
