# 安全模型与信任边界

## 三条协议级原则

规范开篇给的三条原则，所有实现方必须处理：

1. **用户同意与控制**：用户必须明确同意并理解所有数据访问与操作；保留对共享什么数据、执行什么动作的控制权；实现方应提供清晰的审阅与授权 UI。
2. **数据隐私**：宿主把用户数据暴露给服务器前必须获得明确同意；未经同意不得把资源数据传给第三方；用户数据要有适当的访问控制。
3. **工具安全**：工具代表任意代码执行，必须以相应的谨慎对待；工具行为描述（如注解）除非来自可信服务器一律视为不可信；任何工具调用前宿主必须取得用户明确同意。

规范同时承认：MCP 在协议层强制不了这些原则，只能靠实现方落地——协议提供的是让实现「能做对」的结构，不是替实现做对。

## 信任边界地图

```text
┌─ 宿主进程 ────────────────────────────────────┐
│  完整对话历史、用户同意决策、模型访问            │  ← 只属于宿主
│  Host ── Client A ── Server A（本地/远程）      │
│       ── Client B ── Server B                  │  ← 服务器互相不可见，
└───────────────────────────────────────────────┘     跨服务器交互由宿主控制
```

边界规则：服务器只收到完成当前请求所需的最小上下文，拿不到完整对话；服务器之间互相隔离；自报的身份信息（clientInfo / serverInfo）不参与安全决策；未经用户同意，用户数据不出宿主。工具注解、服务器 instructions、资源内容、图标元数据这些「服务器说的话」全部按不可信输入处理。

## 各机制的安全要点

| 机制 | 要点 |
|---|---|
| requestState | 客户端回显的服务器状态按攻击者可控输入处理：影响授权/业务逻辑必须 HMAC 或 AEAD 完整性保护，编入主体、短 TTL、原请求标识防重放；一次性消费要服务器自己保证（见 [[3.3 MRTR：多轮往返请求]]） |
| 头部路由 | 处理 body 的服务器必须校验头体一致（HeaderMismatch `-32020`），防「中间设施按头路由、服务器按 body 执行」的双真相攻击（见 [[3.2 传输：stdio 与 Streamable HTTP]]） |
| HTTP 端点 | 校验 `Origin` 防 DNS rebinding（不合法回 403）；本地只绑 localhost；全连接认证（见 [[6.1 OAuth 2.1 授权框架]]） |
| tools | 服务器必须校验输入、实现访问控制、限流、净化输出；客户端调用前展示参数、对结果做校验、设超时、记录审计日志（见 [[4.1 Tools：tools-list 与 tools-call]]） |
| resources | 校验 URI、净化 file:// 路径防目录穿越、敏感资源访问控制、二进制正确编码（见 [[4.2 Resources：资源、模板与订阅]]） |
| elicitation | form 禁索凭据；URL 不预取、明示同意后打开、展示完整 URL、防钓鱼（服务器校验打开 URL 的用户与发起引出的是同一人）（见 [[5.1 Elicitation：form 模式与 URL 模式]]） |
| icons | 图标按不可信输入：URI 限 HTTPS 或 data:（拒绝 javascript: / file: 等）、同源校验、无凭据获取、限尺寸帧数防资源耗尽、按魔术字节验真实类型、防 SVG 内嵌脚本 |
| JSON Schema | `$ref` 默认不解析网络 URI（可选开启必须默认关闭 + 允许列表 + 拒绝内网地址 + 限时限长）；组合关键字设深度/数量/时间上限防校验器 DoS（见 [[3.1 JSON-RPC 消息、_meta 与无状态模型]]） |
| 授权 | 令牌受众绑定（resource 参数）、禁止 token passthrough、iss 校验防授权服务器混淆、凭据按签发方键控（见 [[6.1 OAuth 2.1 授权框架]]） |

## 提示注入：不在协议条款里的最大攻击面

工具描述、资源内容、服务器 instructions 都是自然语言，都会进入模型上下文——恶意服务器可以在这些文本里埋指令，让模型做出违背用户意图的动作（混入别的服务器的指令、诱导调用破坏性工具、把敏感数据写进看似无害的参数外传）。协议对它的防御是结构性的而非内容性的：最小上下文原则（服务器拿不到全对话与其他服务器的数据，注入的影响半径被边界限制）、人工确认环节（敏感操作前的用户审阅是最后一道闸）、注解与描述不可信（不基于自述放宽校验）。规范没有承诺检测或过滤注入文本的机制，这条边界由实现方与上层应用自己补。

> [!example] 实践例子
> 「对端自述的一切不可信，校验落在自己这一侧」是项目与 MCP 共用的安全立场：Supervisor 的输出要过根运行时校验才落状态、工具调用实例固化后幂等执行、护栏不因模型或工具的自述放行，见 [[5.护栏]]、[[4.Supervisor 架构与委派]]。提示注入的威胁模型同样适用于项目——证据与检索结果进入上下文前不加筛选，模型决策就可能被内容裹挟，见 [[9.证据装配与失败语义]]。

## 边界问答

**1. Q：** 协议为什么强制不了自己的安全原则？
**A：** 原则约束的是宿主应用的 UI 与运营行为（同意流、权限展示、审计），协议线上能做的只有拒绝畸形请求与提供可校验的结构（能力声明、令牌受众、头体一致性）。用户点了「同意」是否真是知情同意，协议看不见也管不着，这层责任明文留给实现方。

**2. Q：** 人在回路为什么是 SHOULD 而不是 MUST？
**A：** 规范的强制级别受场景制约：无人值守的服务器间集成、测试环境、企业内网自动化都可能合法地免确认。协议把「应当有人审」定为 SHOULD 并给出清单，把「何时可以豁免」留给实现方的威胁模型。

**3. Q：** 接入一个第三方 MCP 服务器，最需要盯的风险是什么？
**A：** 两类：其一是提示注入——服务器返回的描述与内容会进入模型上下文，可能驱动模型滥用已授权的能力；其一是数据外流——服务器能看到发给它的所有参数与资源内容。缓解靠最小授权（scope 最小化、工具按需启用）、敏感操作确认、以及参数进出审计。
