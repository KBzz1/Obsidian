# OAuth 2.1 授权框架

## 适用范围与角色映射

授权是可选实现：HTTP 传输应当遵循本框架；stdio 不走这套，从环境取凭据；自定义传输遵循各自的安全实践。角色映射是理解整套框架的起点——

| OAuth 角色 | MCP 对应 |
|---|---|
| 资源服务器（RS） | MCP 服务器（接受与校验访问令牌） |
| 客户端 | MCP 客户端（代表资源所有者发请求） |
| 授权服务器（AS） | 独立实体或与 MCP 服务器同体（规范不限定） |

底层标准：OAuth 2.1 草案、RFC 6750（Bearer 用法）、RFC 8414 与 OIDC Discovery（AS 元数据发现）、RFC 9728（受保护资源元数据）、RFC 8707（resource 指示）、RFC 9207（iss 签发方标识）、Client ID Metadata Documents 草案；RFC 7591 动态注册已废弃但保留兼容。

## 授权流

```text
MCP 客户端                       MCP 服务器（RS）              授权服务器（AS）
    │ 无令牌请求                      │                              │
    │──────────────────────────▶     │                              │
    │ ◀─ 401 + WWW-Authenticate      │                              │
    │    （resource_metadata URL、    │                              │
    │     scope 提示）                │                              │
    │ 取受保护资源元数据（RFC 9728）   │                              │
    │──────────────────────────▶     │                              │
    │ ◀─ AS 位置等元数据              │                              │
    │ 取 AS 元数据（RFC 8414 / OIDC，两种机制客户端都必须支持）        │
    │─────────────────────────────────────────────────────────▶    │
    │ ◀─ 端点与能力元数据             │                              │
    │ 客户端注册（CIMD 推荐 / 预注册 / DCR 兼容）                     │
    │─────────────────────────────────────────────────────────▶    │
    │ 浏览器授权请求：PKCE + resource 参数 + 期望 scope              │
    │─────────────────────────────────────────────────────────▶    │
    │ ◀─ 重定向回授权码 + iss（RFC 9207）                            │
    │ 校验 iss 与记录的签发方一致后换令牌                            │
    │─────────────────────────────────────────────────────────▶    │
    │ ◀─ 访问令牌（+ 刷新令牌）       │                              │
    │ Authorization: Bearer <token>（每个请求都要带）                │
    │──────────────────────────▶     │                              │
```

客户端注册三种机制按优先级：**Client ID Metadata Documents**（客户端把一个 HTTPS URL 当 client_id，AS 按需去这个 URL 拉取元数据文档与 redirect_uris，2025-11-25 引入、现为推荐路径）；预注册（线下拿到固定 client_id）；**动态客户端注册**（RFC 7591，运行时向 AS 的 /register 端点注册，已废弃、仅为不支持 CIMD 的 AS 保留）。2026-07-28 的强化：AS 应在授权响应带 RFC 9207 的 `iss` 参数，客户端必须在兑换授权码前校验它与记录的签发方一致（堵授权服务器混淆攻击）；客户端注册要声明合适的 `application_type`（避免桌面/CLI 应用的 localhost 重定向被拒）；凭据必须按签发方键控存储，换 AS 必须重新注册，不得跨 AS 复用。

## resource 参数与令牌绑定

RFC 8707 resource indicator 是强制项：授权请求与令牌请求都必须带 `resource` 参数，取 MCP 服务器的规范 URI（如 `https://mcp.example.com/mcp`；小写 scheme 与 host、不带 fragment）。效果是**令牌受众绑定**：令牌只对该资源有效，AS 不会签出能打任意服务器的通用令牌，恶意服务器也无法骗到打向别人的令牌。配套红线：客户端不得把非本服务器 AS 签发的令牌发过来；服务器只接受签给自己当受众的令牌，其他令牌既不接受也不中转（token passthrough 被禁止）。

## scope 策略与 step-up

最小权限从 401 就开始：服务器的 `WWW-Authenticate` 挑战应当带 `scope` 提示本次操作需要的范围（可以与元数据里的 `scopes_supported` 无严格包含关系，挑战的 scope 对当前操作是权威的）；客户端优先按挑战要 scope，没有挑战才退回 `scopes_supported` 全集。运行时已有令牌但权限不足，服务器回 403 加 `error="insufficient_scope"` 与所需 `scope`；客户端做 step-up：把已有 scope 与挑战 scope 求并集重新授权再重试，保留此前已授的权限。服务器应在一次挑战里给齐当前操作的全部 scope（挤牙膏式的逐个挑战会成倍增加授权往返），客户端要有重试上限。refresh token 不是资源侧要求（服务器不应把 `offline_access` 写进挑战或元数据），要不要发由 AS 决定。

## 与 URL 模式引出、企业扩展的边界

MCP 自身的授权（客户端 ↔ 服务器）与服务器对第三方的授权（URL 模式引出）是两套独立的流，凭据互不越界，见 [[5.1 Elicitation：form 模式与 URL 模式]]。授权还有独立的官方扩展：client credentials 流（机器对机器）、企业管理授权（EMA，由企业 IdP 统一管控），扩展列表在 ext-auth 仓库维护。

## 边界问答

**1. Q：** 为什么 MCP 服务器是资源服务器而不是授权服务器？
**A：** 职责分离：MCP 服务器只消费令牌（校验受众与权限），签令牌的 AS 可以独立部署或复用企业身份体系。RFC 9728 的发现机制让「哪个 AS 管这个服务器」成为可发现的元数据而非硬编码约定，服务器与 AS 的部署组合因此自由。

**2. Q：** stdio 为什么不走 OAuth？
**A：** stdio 是客户端自己启动的本地子进程，信任边界在进程启动那一刻就确定了；从环境变量读凭据（如 API key）足够且更简单。OAuth 解决的是远程端点「对面是谁」的问题，本地子进程没有这个问题。

**3. Q：** 动态客户端注册为什么被 CIMD 取代？
**A：** DCR 要求 AS 开放一个匿名可写的注册端点，是长期的滥用面（垃圾注册、伪装客户端）。CIMD 反转方向：客户端自持一个 HTTPS URL 作为 client_id，AS 要信息时去拉，注册端点就不需要了。规范保留 DCR 仅为兼容还不支持 CIMD 的 AS。
