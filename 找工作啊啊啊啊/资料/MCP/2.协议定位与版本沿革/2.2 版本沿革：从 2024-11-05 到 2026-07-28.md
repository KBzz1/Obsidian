# 版本沿革：从 2024-11-05 到 2026-07-28

MCP 的版本号是日期制。截至整理时（2026-09），最新版本是 2026-07-28，官方同时在线归档了 2024-11-05、2025-03-26、2025-06-18、2025-11-25 四个旧版规范。这条沿革线的主线只有一条：**从有状态走向无状态，从「服务器也能发起请求」走向「一切交互都是客户端请求的多轮往返」**。

## 2024-11-05：初版

Anthropic 发布 MCP 时的首个规范。基本盘：JSON-RPC 2.0 消息格式；`initialize` / `notifications/initialized` 握手建立有状态连接，握手时交换双方能力；三种服务器原语（Tools、Resources、Prompts）与两种客户端能力（Sampling、Roots）；两种传输——stdio 子进程，以及 HTTP+SSE 双端点传输（GET 打开一条 SSE 长流拿到消息端点，POST 发消息）。

## 2025-03-26：授权与 Streamable HTTP

引入四个主要变化：基于 OAuth 2.1 的完整授权框架；Streamable HTTP 传输取代 HTTP+SSE——单个 MCP 端点接受 POST，应答可以是 JSON 也可以是按请求的 SSE 流，连接由 `Mcp-Session-Id` 头标识（HTTP+SSE 自此进入废弃流程）；加入 JSON-RPC batching；工具注解（annotations）描述只读、破坏性等行为特征。此版的握手仍在：能力协商仍发生在 initialize 里。

## 2025-06-18：结构化输出与资源服务器定位

移除 batching（上一版刚加的）；工具结构化输出（`structuredContent` 与 `outputSchema`）；MCP 服务器被正式归类为 OAuth 资源服务器，按 RFC 9728 暴露受保护资源元数据供客户端发现授权服务器，并强制 RFC 8707 resource indicator 防止令牌被恶意服务器骗取；引入 Elicitation；工具结果支持 resource links；HTTP 请求需带 `MCP-Protocol-Version` 头。

## 2025-11-25：交互能力增强

授权服务器发现支持 OpenID Connect Discovery；工具、资源、提示支持 icons 元数据；`WWW-Authenticate` 增量 scope 同意（step-up）；URL 模式 elicitation（带外敏感交互）；sampling 请求支持 `tools` / `toolChoice`（采样中带工具循环）；客户端注册引入 Client ID Metadata Documents；实验性 tasks；JSON Schema 2020-12 成为默认方言；工具名给出正式指导。

## 2026-07-28：无状态重写（当前版本）

官方博客称之为一次大版本修订，动机是远程 MCP 上线约 18 个月积累的规模化与可靠性教训。九项主要变化：

1. **移除协议级会话**：Streamable HTTP 不再有 `Mcp-Session-Id`，列表端点不再随连接变化；跨调用状态改用显式句柄。
2. **协议无状态化**：`initialize` / `notifications/initialized` 握手删除，每个请求在 `_meta` 里携带协议版本与客户端能力；版本不符返回 `UnsupportedProtocolVersionError`。
3. **新增 `server/discover`**：服务器必须实现，用于前置发现版本、能力与身份。
4. **`subscriptions/listen` 取代 GET 流**：变更通知收拢到一条客户端按需开启的长流，带 `subscriptionId` 关联。
5. **移除 `ping`、`logging/setLevel`、`notifications/roots/list_changed`**：日志级别改为每请求 `_meta` 字段。
6. **Tasks 移出核心**，成为正式扩展 `io.modelcontextprotocol/tasks`，改为 `tasks/get` 轮询加 `tasks/update` 输入。
7. **MRTR（多轮往返请求）取代服务器发起的请求**：`roots/list`、`sampling/createMessage`、`elicitation/create` 不再作为独立的服务器请求发出，改为内嵌在 `InputRequiredResult` 里由客户端重试携带回答。
8. **所有结果必填 `resultType`**：`"complete"` 或 `"input_required"`，旧版缺省按 `"complete"` 处理。
9. **移除 SSE 流可恢复性**（`Last-Event-ID`）：断流的请求直接作废重发。

配套变化：头部路由（`Mcp-Method` / `Mcp-Name` 必需头）；列表结果可缓存（`ttlMs` / `cacheScope`）；错误码分区（`-32020` 到 `-32099` 留给规范定义）；授权强化（RFC 9207 `iss` 校验、凭据按签发方绑定、DCR 废弃改推 Client ID Metadata Documents）；工具列表建议确定性排序以提升客户端缓存与提示词缓存命中。

## 废弃政策与当前废弃项

2026-07-28 同时确立了特性生命周期政策：Active、Deprecated、Removed 三态，废弃窗口最短十二个月，废弃特性登记在规范的 deprecated 清单里。当前处于 Deprecated 的：

| 特性 | 迁移路径 |
|---|---|
| Roots | 目录或文件改走工具参数、resource URI 或服务器配置 |
| Sampling | 直接对接 LLM 供应商 API |
| Logging | stdio 场景写 stderr，其余用 OpenTelemetry |
| HTTP+SSE 传输（2024-11-05） | 迁到 Streamable HTTP |
| OAuth 动态客户端注册（RFC 7591） | 改用 Client ID Metadata Documents，兼容期仍可用 |
| sampling 的 `includeContext` 取值 `thisServer` / `allServers` | 省略该字段或用 `"none"` |

## 边界问答

**1. Q：** 2026-07-28 为什么敢做这么大的破坏性变更？
**A：** 官方给出的动机是无状态化是开发者要求最多的特性：有会话的服务器在负载均衡后面要么粘性路由、要么共享存储，无状态后任意实例可用普通轮询负载均衡接收任意请求。多轮往返请求与句柄模式解决了无状态之后「服务器怎么要输入、怎么关联多次调用」的两个连带问题，使整套设计自洽。

**2. Q：** Deprecated 和 Removed 有什么区别？
**A：** Deprecated 的特性仍在规范里、仍然工作，最短保留十二个月后才「有资格」被移除；新实现不应再采用。规范同时维护一份废弃特性登记表跟踪每个特性的状态。

**3. Q：** 2026-07-28 之后旧客户端还能连新服务器吗？
**A：** 看双方实现的时代。规范定义了 modern（2026-07-28 及以后，逐请求元数据）与 legacy（2025-11-25 及以前，initialize 握手）两个时代，双时代（dual-era）实现可以同时服务两类对端；纯 modern 服务器收到 legacy 的 initialize 会以 JSON-RPC 错误拒绝。检测与回退机制见 [[3.4 版本协商、server-discover 与扩展]]。
