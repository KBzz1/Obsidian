# MCP 是什么：定位与架构

## 解决什么问题

MCP（Model Context Protocol）是一个开放协议，为 LLM 应用与外部数据源、工具之间提供标准化的集成方式：AI IDE、聊天界面、自定义 AI 工作流都需要把外部上下文和工具接进模型，MCP 把这件事从「每个应用对接每个数据源」的 N×M 问题变成「双方各实现一次协议」。它对标的是 LSP（Language Server Protocol）在编程语言生态里的角色——LSP 让任意编辑器接入任意语言服务，MCP 让任意 AI 应用接入任意上下文与工具提供方。

## 三个角色

MCP 采用 client-host-server 架构，一个 Host 可以运行多个 Client 实例：

```text
┌─ 应用宿主进程 ──────────────┐
│  Host                       │
│   ├─ Client 1 ── Server 1（本地：文件、Git）
│   ├─ Client 2 ── Server 2（本地：数据库）
│   └─ Client 3 ── Server 3（远程：外部 API）
└─────────────────────────────┘
```

**Host（宿主）** 是 LLM 应用本身，担任容器与协调者：创建并管理多个 Client 实例；控制 Client 的连接权限与生命周期；执行安全策略与用户同意（consent）要求；处理用户授权决策；协调 AI/LLM 集成与采样；跨 Client 聚合上下文。

**Client（客户端）** 由 Host 创建，与且仅与一个 Server 保持一对一连接：在每个请求上附带协议版本与自身能力；双向路由协议消息；管理订阅与通知；维护 Server 之间的安全边界。2026-07-28 版里 Client 不再持有连接级会话状态，「一对一」指连接关系，不是共享状态。

**Server（服务器）** 提供专门的上下文与能力：通过 MCP 原语暴露 Resources、Tools、Prompts（见 4.服务器能力）；独立运行、职责聚焦；需要客户端输入时在应答里内嵌 InputRequiredResult（见 [[3.3 MRTR：多轮往返请求]]）；可以是本地进程也可以是远程服务。

## 四条设计原则

1. **Server 应当极易构建**：复杂的编排责任归 Host 应用；Server 只做聚焦的、定义良好的能力，接口简单。
2. **Server 应当高度可组合**：每个 Server 独立提供功能，多个 Server 可无缝组合，共享协议保证互操作。
3. **Server 不能读到完整对话，也不能窥视其他 Server**：Server 只收到必要的上下文信息；完整对话历史留在 Host；跨 Server 的交互由 Host 控制。这是信任边界的根基。
4. **能力可以渐进添加**：核心协议只提供最小必需功能，其余能力按需协商，双方可以独立演化并保持向后兼容。

## 无状态模型与能力协商

2026-07-28 版的 MCP 是无状态协议：处理一个请求所需的全部信息都在这个请求里，服务器不得从先前请求（即使同一连接上）推断上下文。版本、身份、能力改为逐请求声明：

- 客户端在每个请求的 `_meta.io.modelcontextprotocol/clientCapabilities` 里携带能力；
- 服务器在 `server/discover` 的应答里声明自己的能力，客户端可以在发任何其他请求前调用它做一次性发现，但不是必须（见 [[3.4 版本协商、server-discover 与扩展]]）。

服务器声明工具、资源订阅、提示模板等能力；客户端声明采样、elicitation 处理等能力。双方都必须尊重对方声明的能力——服务器依赖了客户端未声明的能力，会被 `-32021` 错误拒绝。

```text
Client                          Server
  │ server/discover（可选）        │
  │──────────────────────────▶   │
  │ ◀─ 支持的版本 + 能力 + 身份    │
  │                               │
  │ 请求（_meta: 版本、能力）       │
  │──────────────────────────▶   │
  │ ◀─ InputRequiredResult        │  ← 需要客户端输入时
  │ 请求（原参数 + inputResponses）│
  │──────────────────────────▶   │
  │ ◀─ 最终结果                   │
```

> [!example] 实践例子
> 健康管理项目没有接入 MCP，但 Host 的职责清单与项目里的 Harness + 上下文装配器是同一份关切：聚合上下文、维护执行单元之间的隔离、决定每个执行者能看到什么。对照差异：MCP 把隔离边界画在进程与组织之间（协议层），项目画在节点与阶段之间（装配层），见 [[3.上下文装配器与 ContextPolicy]]。

## 边界问答

**1. Q：** Host 和 Client 是什么关系，为什么要分成两个概念？
**A：** Client 是 Host 内部的连接器组件，一个 Client 只连一个 Server，Host 管理多个 Client。分开讲是因为职责不同：Host 承担编排、安全策略与上下文聚合这些应用级责任，Client 只承担协议消息的路由与安全边界。MCP 规范约束的是 Client 与 Server 之间的线上行为，Host 的内部实现不在协议范围内。

**2. Q：** 为什么 Server 不能读到完整对话？
**A：** 设计原则明文规定：Server 只收到完成任务所需的最小上下文，完整对话历史留在 Host。这是数据隐私与信任边界的要求——Server 可能属于第三方，把全对话交给它等于把用户的一切输入暴露给外部服务。Host 暴露用户数据给 Server 前必须获得用户明确同意。

**3. Q：** MCP 和 LSP 是什么关系？
**A：** 不是技术上的依赖，是定位上的类比。LSP 标准化了「开发工具 ↔ 语言服务」的集成，MCP 用同样的思路标准化「AI 应用 ↔ 上下文与工具提供方」的集成。规范原文明确说 MCP 的设计从 LSP 获得灵感。

**4. Q：** 无状态之后，需要跨请求保持的业务状态怎么办？
**A：** 协议层的答案是显式句柄（handle）：服务器在工具结果里返回一个显式标识符，由模型当作普通参数在后续调用里传回来。状态放在服务器自己的存储里，用标识符关联，不放在连接或会话里。具体模式见 [[4.1 Tools：tools-list 与 tools-call]] 的「有状态工具」一节。
