# 传输：stdio 与 Streamable HTTP

传输（transport）在 MCP 里是绑定（binding）的概念：它只决定消息怎么封装与投递、请求元数据怎么携带、取消怎么表达，不改变消息语义——消息模式（请求响应、MRTR、订阅通知）属于核心协议，在任何传输上都一样。当前两个标准传输：stdio 与 Streamable HTTP；自定义传输必须保留 JSON-RPC 格式、消息模式与每请求元数据模型，跑在可靠双向字节流上的自定义传输应当复用 stdio 的帧格式。

## stdio：子进程与换行分隔

客户端把 MCP 服务器作为子进程启动，用标准流传消息：服务器从 `stdin` 读 JSON-RPC 消息、向 `stdout` 写；每条消息一行、内部不得含换行；`stderr` 可以自由写 UTF-8 日志（信息级、调试级都行），客户端可以采集、转发或忽略，不应假定 stderr 输出就意味着出错。stdout 上除响应外还有两类通知：在途请求相关的进度与日志通知，以及订阅通知（必须用 `_meta` 里的 `subscriptionId` 关联到所属订阅）。取消在途请求靠发送 `notifications/cancelled` 通知——stdio 是单一共享双向通道，没有可关闭的按请求流。

关停协议：客户端先关闭子进程的标准输入，等它退出，超时再升级到强制终止（POSIX 从 SIGTERM 到 SIGKILL）。服务器侧应在 stdin 关闭或读到 EOF 时尽快退出。服务器进程意外退出时客户端应当重启它——协议无状态，在途请求直接作废重发即可，活动的订阅流需要重建。

stdio 没有头部层，请求元数据全部内联在 JSON-RPC 消息体的 `_meta` 里。

## Streamable HTTP：单端点 + 按请求 SSE 流

服务器作为独立进程运行，对外只暴露一个 MCP 端点（如 `https://example.com/mcp`），只接受 POST：

- 客户端每条 JSON-RPC 消息（请求或通知）都是一次独立 POST，`Accept` 头必须同时列出 `application/json` 与 `text/event-stream`；
- 通知被接受时服务器回 `202 Accepted` 无 body；
- 请求的应答要么是单个 JSON 对象，要么是一条作用于该请求的 SSE 流——流上先发与该请求相关的通知（进度、日志），最终响应收尾并结束流；
- 长效变更通知不再有独立 GET 端点（2026-07-28 移除），统一走 `subscriptions/listen` 请求：它的响应流保持打开，只投递客户端订阅的那几类通知，服务器应周期性发 SSE 注释行（以冒号开头的行）做保活，并建议带 `X-Accel-Buffering: no` 让反向代理不要缓冲事件；
- 取消 = 直接关闭该请求的 SSE 响应流，服务器必须视为取消并停止工作；`Last-Event-ID` 断线续传已移除，断流的请求作废、换新 id 重发。

安全基线：服务器必须校验 `Origin` 头防 DNS rebinding 攻击（不合法回 403）；本地运行时只应绑定 localhost；应当为连接实现认证（授权框架见 [[6.1 OAuth 2.1 授权框架]]）。

## 头部路由：Mcp-Method 与 Mcp-Name

Streamable HTTP 的每个 POST 必须携带把请求体关键字段镜像到 HTTP 头，让负载均衡、网关、限流器、WAF 不解析 body 就能路由、计量与授权：

| 头 | 来源 | 适用 |
|---|---|---|
| `MCP-Protocol-Version` | `_meta` 的协议版本 | 所有请求；与 body 不一致按 HeaderMismatch 拒绝 |
| `Mcp-Method` | JSON-RPC `method` | 所有请求 |
| `Mcp-Name` | `params.name` 或 `params.uri` | `tools/call`、`resources/read`、`prompts/get` |

```http
POST /mcp HTTP/1.1
Content-Type: application/json
MCP-Protocol-Version: 2026-07-28
Mcp-Method: tools/call
Mcp-Name: get_weather

{ "jsonrpc": "2.0", "id": 1, "method": "tools/call", "params": { ... } }
```

处理 body 的服务器必须校验头与 body 一致，不一致回 400 加 `-32020` HeaderMismatch——防止「网关按头路由、服务器按 body 执行」两个真相来源被利用。头值必须是可见 ASCII；含非 ASCII 或控制字符的值用 Base64 哨兵编码（`=?base64?…?=`），`Mcp-Name` 与参数头都适用，且恰好长得像哨兵模式的明文值也必须编码以避免歧义。

服务器还可以在工具参数 schema 里用 `x-mcp-header` 注解把特定参数镜像成 `Mcp-Param-{Name}` 头（如 `region` 参数 → `Mcp-Param-Region: us-west1`），让中间设施按参数值路由。约束较严：只能标原始类型参数（string、integer、boolean，不允许 number）、只能在 schema 根静态可达的属性上（链路只经过 `properties`，不得穿过数组、组合或 `$ref`）、值名必须合 HTTP 字段名语法且块内唯一。敏感参数（密码、令牌、PII）不应标记——头对网络中间设施可见。客户端必须支持该特性，遇到违规定义的工具要把该工具从 `tools/list` 结果里剔除并告警，而不是整体失败。

## 跨时代检测与旧传输回退

需要兼容新旧两个时代的客户端按传输用不同机制探测：stdio 上先发 `server/discover`，拿到 DiscoverResult 或现代错误即现代服务器，其他错误或超时回退 initialize 握手；HTTP 上直接发现代请求，收到 400 时检查 body——是可识别的现代 JSON-RPC 错误就按现代语义处理，否则回退 initialize。时代判定是服务器级属性，客户端应当缓存。

还要支持 2024-11-05 旧 HTTP+SSE 传输的客户端：POST 失败（400/404/405 且 body 不是现代错误）后改发 GET，若拿到返回 `endpoint` 事件的 SSE 流即旧传输服务器。

> 头部路由解决的问题是「让观测与治理设施不用理解载荷语义就能工作」，与项目把 Trace 身份（task、run、invocation）贯穿每层日志是同一关切，见 [[3.Task、Run 与 Trace 身份关联]]；Origin 校验与 localhost 绑定这类运行时防护则对照 [[3.生产运行时治理边界]]。

## 边界问答

**1. Q：** 为什么必须做头部路由，body 里不是已经有这些字段了吗？
**A：** 就是为了给不解析 body 的网络中间设施用的：网关按 `Mcp-Method` 分流、限流器按 `Mcp-Name` 计量、WAF 按参数头拦截，都不必解析 JSON。为此付出了头体一致性校验的成本（HeaderMismatch），换来路由层与执行层永远看到同一个真相。

**2. Q：** 为什么移除 GET 长流和 SSE 断线续传？
**A：** 无状态化的一部分：独立的 GET 通知流是连接级状态，`Last-Event-ID` 续传要求服务器缓存历史事件。移除后变更通知收进客户端主动发起的 `subscriptions/listen` 请求流（状态作用域在请求上），断流的请求作废重发，服务器不需要任何会话存储。

**3. Q：** stdio 上怎么区分现代与旧时代服务器？
**A：** 先发 `server/discover` 探测：返回 DiscoverResult 或 UnsupportedProtocolVersionError 是现代服务器（后者按 supported 列表换版本重试，不回退）；返回其他错误或超时则视为旧时代，回退 initialize 握手。不能把回退锚定在某个特定错误码上——旧服务器对未知请求的错误码是实现自定义的。
