# JSON-RPC 消息、_meta 与无状态模型

## 三种消息

MCP 的所有消息遵循 JSON-RPC 2.0，且只有三个方向：客户端发请求与通知，服务端发响应与通知。2026-07-28 版不存在服务器发起的 JSON-RPC 请求——服务器要输入时用结果多态（resultType）表达，见 [[3.3 MRTR：多轮往返请求]]。

请求（client → server，发起操作）：

```json
{
  "jsonrpc": "2.0",
  "id": 1,                    // 请求标识：字符串或整数，不得为 null，
                              // 也不得与尚无响应的在途请求撞号
  "method": "tools/call",     // 方法名
  "params": { }               // 可选参数
}
```

结果响应（server → client，操作成功）：

```json
{
  "jsonrpc": "2.0",
  "id": 1,                    // 必须与对应请求同 id
  "result": {
    "resultType": "complete", // 必填：结果的多态类型标识
    "...": "任意 JSON 对象结构"
  }
}
```

`resultType` 是 2026-07-28 新增的必填字段，两个核心取值：`"complete"` 表示请求完成、结果是最终内容；`"input_required"` 表示还需要输入，结果是一个 InputRequiredResult 对象。扩展可以增加新的取值；客户端不认识的取值一律视为非法；对旧版本服务器省略该字段的结果，客户端必须当作 `"complete"`。

错误响应（server → client，操作失败）：

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "error": {
    "code": -32602,           // 必须是整数
    "message": "Unknown tool: invalid_tool_name",
    "data": { }               // 可选附加信息
  }
}
```

通知（单向，不得有 id，接收方不得响应）：客户端到服务端方向，本版核心协议里实际只剩 stdio 取消用的 `notifications/cancelled`；服务端到客户端方向是进度、日志与订阅类通知。

## 错误码分区

MCP 使用 JSON-RPC 标准错误码（`-32700`、`-32600` 到 `-32603`）表达一般协议失败。JSON-RPC 保留给实现定义的 `-32000` 到 `-32099` 区间，2026-07-28 起做了正式分区：

```text
-32000 ~ -32019  遗留区：历史实现自行分配，新代码不得再分配，
                  除 -32002 外接收方不得假设任何含义
-32020 ~ -32099  规范保留区：只有 MCP 规范能定义，实现不得自造
```

规范当前定义的三个码：`-32020` HeaderMismatch（HTTP 头与请求体不一致）、`-32021` MissingRequiredClientCapability（请求依赖了客户端未声明的能力）、`-32022` UnsupportedProtocolVersion（版本不支持）。历史码 `-32002`（资源不存在，已被 `-32602` 取代）与 `-32042`（仅 2025-11-25 用过）保持保留不再复用。应用自定义错误建议落在 `-32768` 到 `-32000` 之外。

## _meta：每请求的协议元数据

`_meta` 是挂在请求参数或结果上的元数据通道，键名分「前缀 + 名称」两段：前缀是反 DNS 记法加斜杠（如 `io.modelcontextprotocol/`），第二标签为 `modelcontextprotocol` 或 `mcp` 的前缀保留给协议使用。规范保留键：

| 键 | 用途 |
|---|---|
| `io.modelcontextprotocol/protocolVersion` | 本请求的协议版本（每请求必填） |
| `io.modelcontextprotocol/clientCapabilities` | 客户端能力（每请求必填） |
| `io.modelcontextprotocol/clientInfo` | 客户端名称与版本（建议携带） |
| `io.modelcontextprotocol/serverInfo` | 服务器名称与版本（结果里建议携带） |
| `io.modelcontextprotocol/logLevel` | 本请求的最低日志级别 |
| `io.modelcontextprotocol/subscriptionId` | 订阅通知的关联标识 |
| `progressToken` | 进度通知的关联令牌 |
| `traceparent` / `tracestate` / `baggage` | OpenTelemetry 追踪上下文（W3C 格式） |

两条硬规则：缺必填 `_meta` 字段的请求是畸形请求，服务器必须以 `-32602`（HTTP 上 400）拒绝；服务器不得依赖客户端未声明的能力，处理需要未声明能力时必须返回 `-32021`。`clientInfo` 与 `serverInfo` 是自报家门，仅供展示、日志与调试，不得用于改变行为或安全决策。

```json
{
  "jsonrpc": "2.0",
  "id": 2,
  "method": "tools/call",
  "params": {
    "name": "get_weather",
    "arguments": { "location": "New York" },
    "_meta": {
      "io.modelcontextprotocol/protocolVersion": "2026-07-28",
      "io.modelcontextprotocol/clientInfo": { "name": "ExampleClient", "version": "1.0.0" },
      "io.modelcontextprotocol/clientCapabilities": { },
      "traceparent": "00-0af7651916cd43dd8448eb211c80319c-00f067aa0ba902b7-01"
    }
  }
}
```

## 无状态约束

协议声明自身是无状态的：处理请求所需的全部信息都在请求本身。落到实现约束上——服务器不得依赖同连接的先前请求建立上下文（能力、版本、身份都逐请求携带）；应当准备处理关联多个任务、线程或会话的请求；不应要求客户端复用同一连接或进程做相关操作；跨请求的状态必须由客户端每次携带的显式标识符引用。打开的 stdio 进程不是会话：客户端可以在同一传输上交错发送无关请求，服务器不得把连接或进程身份当作会话连续性的代理。`subscriptions/listen` 这类长请求仍是请求-响应形态，只是响应是一条保持打开的通知流，状态作用域在请求本身而不在底层连接。

## JSON Schema 使用规则

协议里大量结构用 JSON Schema 描述（工具的输入输出 schema、elicitation 的表单 schema）。默认方言是 JSON Schema 2020-12（无 `$schema` 字段时），实现必须支持 2020-12、可以额外支持并声明其他方言。两条安全规则：`$ref` 解析到网络 URI 时默认不得自动解引用（可选开启时必须默认关闭并强制允许列表、拒绝回环与内网地址、限时限长）；`anyOf` / `oneOf` / `$defs` 等组合关键字要做资源上限（深度、子 schema 数量、时间预算），防止恶意 schema 把校验器打成拒绝服务。

> [!example] 实践例子
> 「每个请求自描述、不靠连接状态」与项目里状态栏每轮重新生成、ContextManifest 只存摘要不存正本是同一个方向的约束：把元数据放进单次交互而不是放进隐式环境，见 [[4.AgentStatus 当前工作状态栏]]；`traceparent` 键则是 Trace 传播的标准做法，对照 [[3.Task、Run 与 Trace 身份关联]]。

## 边界问答

**1. Q：** 为什么能力声明放在每个请求里，而不是握手一次谈妥？
**A：** 2026-07-28 移除了 initialize 握手后，连接不再承载协商结果，能力只能逐请求声明。收益是任何请求可以打到任何服务器实例；代价是每请求多几十字节元数据。旧版的握手式协商仍是 legacy 时代的合法形态，双时代实现要同时支持两者。

**2. Q：** resultType 为什么必填？
**A：** MRTR 引入后，结果有了「完成」与「还要输入」两种语义，客户端需要统一字段区分怎么解析。对旧版服务器省略该字段的结果按 `"complete"` 处理，是刻意的向后兼容设计。

**3. Q：** clientInfo 能拿来做访问控制吗？
**A：** 不能。它是发送方自报的名称与版本，协议不校验，规范明文规定不得用于改变行为或做安全决策。身份与授权走 [[6.1 OAuth 2.1 授权框架]] 的凭据体系。
