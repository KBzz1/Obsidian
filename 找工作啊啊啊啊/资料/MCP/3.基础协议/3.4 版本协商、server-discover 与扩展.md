# 版本协商、server-discover 与扩展

## 无握手的版本协商

2026-07-28 版没有协商握手：每个请求在 `_meta` 里声明自己用的协议版本（HTTP 上同时镜像进 `MCP-Protocol-Version` 头），服务器逐请求接受或拒绝。服务器不支持请求的版本时，必须返回 `UnsupportedProtocolVersionError`（`-32022`）并列出自己支持的版本：

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "error": {
    "code": -32022,
    "message": "Unsupported protocol version",
    "data": {
      "supported": ["2026-07-28", "2025-11-25"],  // 服务器支持的版本列表
      "requested": "1900-01-01"                    // 客户端请求的版本
    }
  }
}
```

客户端应当从 `supported` 列表选一个双方都支持的版本重试；没有交集时报错给用户。协商的主动权这样落在「先试、错了再调」的循环里，而不是开场握手。

## server/discover

`server/discover` 是 2026-07-28 唯一新增的 RPC，服务器必须实现。请求不带额外参数，响应一次给出三样东西：

```json
{
  "jsonrpc": "2.0",
  "id": "discover-1",
  "result": {
    "resultType": "complete",
    "supportedVersions": ["2026-07-28"],       // 支持的协议版本
    "capabilities": {                          // 能力：tools / resources / prompts 等
      "tools": { },
      "resources": { }
    },
    "instructions": "提供天气与资源工具。",      // 给 LLM 的自然语言使用说明（可选）
    "_meta": {
      "io.modelcontextprotocol/serverInfo": { "name": "ExampleServer", "version": "1.0.0" }
    },
    "ttlMs": 3600000,                          // 结果可缓存时长（毫秒）
    "cacheScope": "public"                     // 缓存共享范围
  }
}
```

调用它是客户端的可选项：直接调用任何 RPC、靠版本错误兜底同样合规。两个典型用途——一次性拿全服务器的版本、能力与身份用于展示，省去分别探测 `tools/list`、`prompts/list`、`resources/list`；以及在 stdio 上作为旧时代服务器的探测探针。

## 两个时代与互操作矩阵

规范用三个术语描述互操作：**modern**（2026-07-28 及以后，逐请求元数据）、**legacy**（2025-11-25 及以前，initialize 握手）、**dual-era**（双时代实现）。交互结果矩阵：

| 客户端 | 服务器 | 结果 |
|---|---|---|
| modern | modern | 正常。discover 可选；版本不匹配靠错误重试收敛 |
| modern | legacy | 失败。旧服务器的拒绝行为实现自定义，可能是错误、沉默甚至按旧语义处理；stdio 上应先 discover 探测拿到确定性失败 |
| dual-era | modern | 正常，保持 modern |
| dual-era | legacy | 正常，回退 initialize 握手（HTTP 上可能再进一步回退 HTTP+SSE） |
| legacy | modern | 失败。旧客户端没有前向兼容机制；纯 modern 服务器应在拒绝 initialize 的错误里报出支持的版本，给旧客户端留一条诊断信息 |
| legacy | dual-era | 正常，按协商出的旧版规范服务 |
| legacy | legacy | 按旧版规范工作 |

dual-era 服务器按开场方式分流：带现代 `_meta` 的请求按无状态规范处理，initialize 请求则进入旧语义（作用域是 stdio 进程或 HTTP 会话）；两类客户端可以在同一端点或进程上并存。时代判定是服务器级属性，客户端应按进程（stdio）或源（HTTP）缓存判定结果。

## 扩展框架

核心协议之外的模块化能力走扩展（extensions）：显式选择加入，双方都要支持、在能力里协商。能力对象里的 `extensions` 字段是「扩展标识 → 每扩展设置对象」的映射，扩展标识遵守 `_meta` 键名规则（必须有前缀）：

```json
{
  "capabilities": {
    "tools": { },
    "extensions": {
      "io.modelcontextprotocol/tasks": { }     // Tasks 扩展：空对象=支持、无附加设置
    }
  }
}
```

一方支持扩展而另一方不支持时，支持方必须回退核心协议行为或以适当错误拒绝，扩展文档应当说明回退行为。官方扩展目前有：**Tasks**（`io.modelcontextprotocol/tasks`，异步长任务：`tasks/get` 轮询取结果、`tasks/update` 中途提交输入、服务器可不经请求方预先同意就返回任务句柄）、**MCP Apps**（`io.modelcontextprotocol/ui`，会话内嵌交互 UI）、**Enterprise Managed Authorization**（企业管理的授权）与 Skills over MCP（结构化技能指令的发现与消费）。Tasks 在 2025-11-25 曾以实验特性进过核心协议，2026-07-28 移出核心改入扩展体系。

> [!example] 实践例子
> 「声明什么才能用什么、未声明的能力不可依赖」与项目第二章的能力渐进装载同一思路：能力是逐阶段声明的边界而不是全局清单，见 [[8.能力渐进装载]]；扩展按需选择加入的粒度则对照项目「技能作为按需装载的 Skill / Prompt」。

## 边界问答

**1. Q：** server/discover 为什么服务器必须实现、客户端却可以不调用？
**A：** 必须实现保证了「任何客户端任何时候想发现都能发现」的可用性——尤其 stdio 探测把它当兼容性探针用。客户端不调用也合规，是因为逐请求版本声明让内联调用加错误重试已经覆盖了功能需求，discover 是优化不是前提。

**2. Q：** dual-era 服务器怎么区分对面是哪个时代？
**A：** 看开场：请求带现代 `_meta` 元数据就按无状态规范服务；发 initialize 就按旧语义服务。两类判断互不干扰，同一端点可以并存两类客户端。

**3. Q：** 扩展为什么不做成新的握手或新版本？
**A：** 无握手模型下没有协商仪式的位置，能力字段是唯一现成的协商通道。扩展挂在 capabilities 里逐请求声明，与核心能力走同一套「未声明不可依赖」规则，避免为可选用特性再造一套机制。
