# MRTR：多轮往返请求

## 解决什么问题

2026-07-28 之前，服务器可以向客户端发起 JSON-RPC 请求：`roots/list`（要文件系统根）、`sampling/createMessage`（要一次 LLM 补全）、`elicitation/create`（要用户输入）。这要求传输层维持一条服务器也能主动发请求的双向流——与无状态化正面冲突。MRTR 把方向反过来：**服务器不再发起请求，而是在对客户端请求的应答里声明「我还缺什么输入」，由客户端收集好后重试原请求把答案带上**。这样任何一次交互都不需要保持打开的双向流，也不需要服务器间共享存储或有状态负载均衡。

## 流程与核心类型

```text
Client                                Server
  │ ① 原始请求（id: 1）                  │
  │─────────────────────────────────▶  │
  │        服务器发现缺输入               │
  │ ◀── ② InputRequiredResult（id: 1）  │  resultType: "input_required"
  │        inputRequests + requestState │
  │        （原请求就此终结）             │
  │                                     │
  │  客户端向用户/模型收集输入            │
  │                                     │
  │ ③ 重试原请求（id: 2，必须换新 id）    │
  │    原参数 + inputResponses           │
  │    + requestState（原样回显）        │
  │─────────────────────────────────▶  │
  │ ◀── ④ 最终结果（id: 2）              │
```

`inputRequests` 是一个映射：键是服务器分配的字符串标识，值是三种请求对象之一——`elicitation/create`、`sampling/createMessage`、`roots/list`。一次可以要多个输入：

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "result": {
    "resultType": "input_required",
    "inputRequests": {
      "github_login": {                       // 键：服务器自分配的请求标识
        "method": "elicitation/create",       // 要用户填一个表单
        "params": {
          "mode": "form",
          "message": "请提供你的 GitHub 用户名",
          "requestedSchema": {
            "type": "object",
            "properties": { "name": { "type": "string" } },
            "required": ["name"]
          }
        }
      }
    },
    "requestState": "AEAD-protected blob"     // 不透明字符串，仅对服务器有意义
  }
}
```

客户端重试时带 `inputResponses`（键与 inputRequests 一一对应的回答）与 `requestState`：

```json
{
  "jsonrpc": "2.0",
  "id": 3,
  "method": "tools/call",
  "params": {
    "name": "get_weather",
    "arguments": { "location": "New York" },
    "inputResponses": {
      "github_login": {
        "action": "accept",                  // 三种动作之一：accept / decline / cancel
        "content": { "name": "octocat" }
      }
    },
    "requestState": "AEAD-protected blob"     // 必须原样回显，不得改动
  }
}
```

只有三个客户端请求允许返回 InputRequiredResult：`prompts/get`、`resources/read`、`tools/call`；其他请求一律不得。

## 服务器侧要求

1. 每个 InputRequiredResult 必须至少含 `inputRequests` 或 `requestState` 之一。
2. 不得向客户端塞它未声明能力支持的请求——客户端没声明 `elicitation` 能力，inputRequests 里就不能出现 `elicitation/create`。
3. 不得假设客户端会完成输入或重试原请求；同一请求多次返回 InputRequiredResult（反复追问）是合法的。
4. `requestState` 必须当作攻击者可控输入处理：它影响授权、资源访问或业务逻辑时，必须做完整性保护（HMAC 或 AEAD）并拒绝校验失败的状态；仅在篡改最坏后果只是请求失败时可以省略。
5. 防重放建议在受保护的 requestState 里编入并校验：认证主体（不同主体的状态要拒绝）、短有效期（TTL）、原请求标识（方法名加关键参数摘要，防止挪到别的请求上用）。这些措施压缩重放窗口，但不保证一次性——必须单次消费的场景（一次性兑换）要服务器自己落地一次性约束。

无状态目标下的推荐用法是把全部所需上下文编进 `requestState`（如 Base64 的 JSON 或加密 JWT），重试请求到达任意实例都能独立完成处理，不依赖服务器侧会话存储。

## 客户端侧要求

收到带 `inputRequests` 的结果，必须先构造所要求的输入再重试原请求（不含 `inputRequests`、只带 `requestState` 的结果可以立即重试）；`requestState` 必须原样回显，不得检视、解析、修改或对其内容做任何假设，服务器没给就不能自己造；重试的 JSON-RPC id 必须与首次不同（两次是独立请求）；`inputResponses` 与 `requestState` 只影响这一次对原请求的重试，不得用于客户端并行发送的其他请求。

## 错误处理

客户端漏答了部分输入且这些信息确实必需时，服务器应当返回一个新的 InputRequiredResult 再要一次，而不是直接报错；`inputResponses` 里服务器不认识的多余信息应当忽略。协议级错误（畸形 JSON、schema 不合法、内部错误）仍走 JSON-RPC 错误响应。用户拒绝或取消输入时客户端不必回传错误——原请求已经终结，服务器本来就不在等待。

> [!example] 实践例子
> 「停下来、把问题带出去、答案带回来、从头再来一遍」与 LangGraph 的 interrupt() / Command(resume) 同型：LangGraph 靠检查点持久化中断现场、恢复时重入节点，MCP 靠 requestState 把现场编码进字符串、由客户端回显。项目侧对应 [[6.HIL 与恢复]] 的恢复校验链（任务存在性、过期、版本、幂等防重放），与 requestState 的防重放三要素是同一份威胁模型。

## 边界问答

**1. Q：** 为什么改成客户端重试，而不是让服务器发起请求？
**A：** 服务器发起请求要求双向流通着，服务器实例必须与客户端保持绑定——负载均衡要粘性、多实例要共享会话存储。重试模式下处理第二次请求的实例不需要认识第一次请求，任何实例都能接，这是无状态化的直接收益。

**2. Q：** requestState 里应该放什么？
**A：** 服务器完成原请求所需的全部自身上下文：原请求参数摘要、用户身份、过期时间，格式自定（Base64 JSON、JWT、加密二进制都可）。红线有两条：客户端视角它必须不透明；影响授权或业务逻辑时必须做完整性保护并防重放校验。

**3. Q：** 用户拒绝回答，服务器怎么知道？
**A：** 客户端可以用 `action: "decline"` 或 `"cancel"` 的 inputResponses 重试，也可以干脆不再重试——服务器不得假设客户端一定会回来。设计上这是刻意的：原请求已终结，无状态服务器没有「等待中」的概念可被打断。
