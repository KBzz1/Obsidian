# 上下文怎么组织：工具、资源与提示进入模型的方式

## 三个入口，三种决定权

MCP 服务器提供的东西分三类，进上下文的方式各不相同。记住「谁决定」，就记住了整个组织方式：

**工具是模型决定的。** 应用把一个 Server 的工具清单挂上之后，每个工具的名称、描述、参数说明就进入模型上下文——形态上就是 function calling 那套工具定义。之后调不调、什么时候调、传什么参数，由模型在对话里自主判断。应用的工作是筛选：把哪些工具给模型，是上下文预算问题，也是权限问题。

**资源是应用决定的。** 资源是 URI 标识的只读数据：文件、数据库 schema、应用文档。哪个资源进上下文，模型说了不算，由宿主应用决定——可以让用户在界面上挑，也可以按规则自动附加。这是刻意的设计差异：资源面向「人与应用挑选后引入」，工具面向「模型自主调用」。

**提示是用户决定的。** 提示模板是服务器预置的参数化指令（典型形态是斜杠命令，比如在输入框敲 `/code_review` 触发一段代码审查提示）。用户显式选择了，展开后的消息才进入对话。服务器没有任何主动推送提示的通道。

## 成本视角：工具清单是常驻开销

工具定义不像对话消息那样轮换，它常驻在模型上下文里。挂的 Server 越多、工具越多，每一轮对话的前置开销就越大。

协议为此给了两个配合点：工具列表结果带有可缓存的新鲜度提示；服务器应当以确定性顺序返回工具（集合不变，顺序就不变）。排序稳定为什么重要——工具进入上下文后，前缀稳定，提示词缓存才命中得了，否则每轮都在为同一批工具付全价 token。

应用侧的对应动作是按需挂载：当前任务用不到的 Server、用不到的工具，就不要放进上下文。这也顺带收窄了攻击面——模型看不到的工具，就谈不上被诱导去调。

## 传引用还是传正文

资源进入上下文有两种粒度。一种是只给引用（一个 URI），模型或应用需要时再取正文；另一种是直接内嵌正文。多资源的场景先给引用、按需取正文，单轮上下文的体量才可控。

这和 agent 设计里「清单进上下文、正文留在存储」是同一个原则：上下文里放定位信息，正文按需加载。

## 反方向也要省：发给 Server 的最小上下文

上下文组织不只管「进模型的」，还管「出应用的」。Server 看不到对话历史，你发什么参数，它就知道什么——所以参数里塞多少上下文，既是成本问题，更是数据外流问题。默认给完成这次调用所需的最小信息，多余的对话内容、其他 Server 的结果，都不要顺手带过去。

另外，服务器可以在被发现时附带一段给模型的使用说明（instructions）。应用可以把它并进系统提示，但要按不可信内容对待——那是服务器的话，不是你的。

## 边界问答

**1. Q：** 工具描述为什么值得专门管理？
**A：** 它是模型决定调不调这个工具的主要依据，也是常驻 token 的大头；写得清楚，模型调用准确率才高。同时它是服务器提供的自然语言，属于不可信内容，可能被用来做提示注入——展示可以用，安全决策不能建立在上面。

**2. Q：** 资源和工具都是「给模型用的数据」吗？
**A：** 不是。资源是只读的数据上下文，面向人与应用挑选后引入；工具是有副作用的动作入口，由模型自主调用。一个体现了分工：客户端可以缓存、展示、让用户挑资源，而工具调用应当有人工确认环节。

**3. Q：** 想让上下文随外部数据自动更新，MCP 支持吗？
**A：** 支持到「通知你重取」这一步：应用开启订阅后，资源或工具列表变了，服务器在订阅流上发通知，应用收到后重新读取。更新动作仍在应用侧，服务器不推送正文。
