# 调用中途要输入：停下来问，答案带回重试

## 场景与解法

模型调了个工具，工具跑到一半发现缺东西：要用户确认（「即将删除这三个文件，继续吗」）、要补充信息（「你的 GitHub 用户名是」）、要走一趟外部授权。

MCP 的解法是把循环暂停，而不是让服务器干等。服务器立刻返回一个「需要输入」的结果——原请求就此结束，不留挂起的连接——并说明要什么。应用负责去拿输入：问用户、问模型，或者引导用户去外部页面。拿到之后，应用把原请求重新发一遍，答案随请求带上，服务器这次才有料继续。

整个交互像一场接力：服务器把问题递出来，应用带着问题去找用户，再把答案原路送回去从头再跑一次。

## 应用要记住的四件事

**重试是全新请求，不是续传。** 不是「接着上次的进度」，是从头再来——服务器不记得上一次。幸运的是工具调用本身就该设计成可重入的，从头再跑通常是安全的；实在不行，靠上一节的句柄把已完成的步骤接回来。

**服务器给的那段状态字符串，原样带回。** 需要输入的结果里带一段对客户端不透明的状态数据，它是服务器为自己准备的「现场」。重试时原封不动带上，不看不改不丢。丢了它，服务器就只能再问一遍。

**用户可能不回来。** 拒绝、取消、直接关掉页面，都是合法结局。原请求已经结束，服务器不在等待，也没有超时可踩。应用不要设计成「等服务器超时」，而是自己决定等多久、何时放弃。

**拒绝也是有效答案。** 用户明确拒绝时，应用可以带着「拒绝」重试一次，让服务器走替代路径；也可以不再重试，直接告诉模型这条工具路走不通。两种都符合协议。

## 问用户的两种形态

**表单（带内）：** 普通信息走应用内的表单，数据经过你的应用。表单被刻意限制成扁平的简单字段，方便应用渲染。红线：密码、API key 这类凭据不允许走表单收。

**外部链接（带外）：** 认证流、支付这类敏感交互，引导用户去浏览器里的服务器页面完成，数据不经过你的应用。要接受一个别扭但合理的语义：用户点了「同意打开链接」只代表同意开始，不代表完成——完成与否由服务器在你重试时判定。所以应用要给用户一个手动重试的入口。

## 和 LangGraph 的对照

这套机制与 LangGraph 的 interrupt() / Command(resume) 同型：都是「停下来、把现场存起来、答案到了从头重入」。差别在现场放哪——LangGraph 放检查点（持久化存储），MCP 放那段回显字符串（由客户端保管）。你的应用在两边扮演同一个角色：把问题带给用户、把答案带回来的中间人。

> [!example] 实践例子
> 项目第六章的 HIL 与恢复是同一形态的进程内版本：InputRequest 带稳定身份，恢复时先过校验链（任务存在、未过期、版本一致、幂等防重放）再执行，见 [[6.HIL 与恢复]]。MCP 那段状态字符串的防篡改、防重放要求，与这条校验链是同一份威胁模型。

## 边界问答

**1. Q：** 服务器为什么不挂着连接等，反正用户也就耽误一会儿？
**A：** 等待意味着服务器实例和这次请求绑死——负载均衡、自动扩容、实例重启都会被牵连。立即结束请求、让任何实例都能接下一次重试，是无状态设计的直接收益。

**2. Q：** 模型能替用户填这些输入吗？
**A：** 看输入的性质。补充上下文类的信息（比如从对话里已知的用户名）可以由应用交给模型或直接填；涉及授权、确认、凭据的输入必须由用户本人给出——这正是交互形态被协议化的原因。

**3. Q：** 重试之后服务器又问了新的问题，正常吗？
**A：** 正常，而且合法。一次重试可能只解开一部分依赖，服务器可以再次返回「需要输入」。应用把这当成同样的分支处理就行，不必特殊对待。
