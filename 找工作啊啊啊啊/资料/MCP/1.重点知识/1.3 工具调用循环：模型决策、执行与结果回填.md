# 工具调用循环：模型决策、执行与结果回填

## 循环长什么样

一个搭好 MCP 的 agent 应用，工具使用就是一个转圈的循环：

```text
工具定义进入模型上下文
        │
        ▼
   模型推理 ──不再调用工具──▶ 循环结束，输出最终回答
        │
      发起调用（工具名 + 参数）
        │
        ▼
   应用执行：把调用发给对应 Server
        │
        ▼
   结果回填对话（文本 / 图像 / 结构化数据）
        │
        └──────────────▶ 回到模型推理
```

要点在中间那一步：模型不直接碰 Server。它只是在回复里表达了「我要调这个工具、参数是这样」的意图，真正把调用发出去的是你的应用。这给了应用一个天然的插入点——在「模型想调」和「真正执行」之间，你可以展示参数、要求确认、记审计日志。协议明确要求实现方提供这样的人工介入：清晰的工具展示、调用时的明确指示、敏感操作的确认提示。

这个循环本身不是 MCP 发明的，它就是 function calling 的通用形态。MCP 标准化的是循环的下一段：应用怎么以统一方式连上任意工具提供方。

## 结果回填：给模型的和给应用的

工具结果是一条混合内容：给人读的文本、图像这类内容块，以及一份可选的结构化数据（声明过输出格式的工具，结果保证符合它声明的形状）。

文本回填给模型继续推理；结构化数据留给应用做后处理——存库、触发流程、跨服务编排，都不必去解析自然语言。

## 多步操作：句柄替协议记住状态

协议无状态，服务器不记得你上一步做了什么。连续操作（先建购物车，再往里加东西）靠显式句柄串起来：第一步的工具结果里返回一个句柄（比如购物车 ID），模型在后续调用里把它当普通参数带回去。

应用视角有两个注意点。第一，句柄的携带责任在模型——你的循环要把结果里的句柄留在对话里，模型下一次才会用上它。第二，句柄会过期：过期的调用会返回一条说明情况的执行错误（「购物车闲置 24 小时已过期」这类），模型看了能自己新建一个句柄恢复，不会卡死。句柄生命周期写在工具描述里，就是为了这一刻。

## 想中断怎么办

用户等不及了点停止，应用直接断掉这次调用的通信即可——协议规定服务器必须把「流被关闭」当作取消信号并停止工作。这比想象中简单：没有取消协商，断开就是取消。

## 边界问答

**1. Q：** 模型忘了把句柄带回来怎么办？
**A：** 协议里句柄只是普通字符串参数，忘了带等于参数没给全，服务器返回一条可读的执行错误，模型看到后自己补上重试。所以句柄的设计要求「可读、可恢复」，而不是「绝不出错」。

**2. Q：** MCP 工具调用和模型 API 的 function calling 是什么关系？
**A：** 循环形态一致：模型表达调用意图，应用执行，结果回填。分工不同：function calling 是模型侧 API 的能力，管模型怎么表达「我要调工具」；MCP 是应用与工具提供方之间的协议，管应用怎么连上工具方。一个 MCP 工具最终仍要以工具定义的形式进入模型上下文，走的是同一套循环。

**3. Q：** 长时间运行的工具，怎么知道进度？
**A：** 结果流上会附带进度与日志类的通知，属于这次调用的响应流；应用可以拿它做进度展示。中断仍然靠直接断流。
