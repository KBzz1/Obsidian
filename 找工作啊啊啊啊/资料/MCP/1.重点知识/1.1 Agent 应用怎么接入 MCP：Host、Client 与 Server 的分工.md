# Agent 应用怎么接入 MCP：Host、Client 与 Server 的分工

## 一句话对齐角色

你的 agent 应用就是 Host。它不是「MCP 客户端」——Client 是 Host 内部为每个 Server 建的连接器，一个 Server 配一个 Client，一对一。Server 是即插即用的能力包：一组工具、资源、提示模板，可以是本地进程（文件系统、Git、数据库），也可以是远程服务（外部 API）。

接入 MCP 之后，应用要承担的事情就三件：

1. 管理连接——创建和关闭 Client，决定连哪些 Server；
2. 把关权限——用户的同意、授权、敏感操作确认，都发生在应用这一侧；
3. 聚合上下文——把多个 Server 的能力收拢成一份模型可用的上下文，同时决定每个 Server 能看到什么。

这三件事没有一件可以外包给协议。MCP 管的只是 Client 与 Server 之间的线上行为，编排责任明文归 Host。

## 为什么值得接：N×M 变成各做一次

没有 MCP 时，每个应用要分别对接每个数据源和工具方，N 个应用 × M 个提供方就是 N×M 份集成代码。有了协议，双方各自实现一次 MCP，任意组合都能互通——这正是 LSP 当年在编辑器和语言服务之间做到的事。应用视角的收益：换一个工具提供方不用改应用，加一个能力不用说服提供方为你定制。

## 最重要的边界：Server 看不到完整对话

模型和用户聊了什么，Server 一概不知。它只收到这一次调用传过去的参数，加上应用主动放进请求里的那点元信息。

这意味着两件事。第一，「发给 Server 什么」是应用的裁剪决策：参数里带什么上下文，应用说了算，发出去的每一个字都会离开你的进程。第二，多个 Server 之间互相不可见——跨 Server 的编排只能由应用做，协议不会替你把 A 服务器的结果喂给 B 服务器。

数据隐私和信任边界都从这条线画出来：把用户数据交给 Server 之前，应用必须拿到用户的明确同意。

## 无状态对应用意味着什么

2026-07-28 版的 MCP 是无状态协议：服务器不记得「上一通电话」。每次调用都是独立请求，版本和能力这类信息每次随请求自己带上。

对应用的好处很实际：服务器集群随便负载均衡，任何一个实例都能接你的请求；断线了随时重连重发，不依赖某台机器记得你。对多步业务（先建购物车、再逐项加商品）来说，状态不能靠「服务器记得」，要靠显式句柄在参数里传来传去——模型负责带，细节见 [[1.3 工具调用循环：模型决策、执行与结果回填]]。

老资料里「initialize 握手建立会话」的说法已经过时：现在没有开场仪式，版本协商是「先发请求、报错了换版本重试」。旧版服务器怎么共存，需要时再看 [[3.4 版本协商、server-discover 与扩展]]。

> [!example] 实践例子
> 健康管理项目没接 MCP，但 Harness 加上下文装配器干的就是 Host 的活：聚合上下文、维护执行单元之间的隔离、决定每个执行者看到什么，见 [[3.上下文装配器与 ContextPolicy]]。差异在隔离边界画的位置：MCP 画在进程与组织之间，项目画在节点与阶段之间。

## 边界问答

**1. Q：** Host 和 Client 为什么要分成两个概念？
**A：** 职责不同。Client 只是个连接器，负责协议消息的收发和安全边界；编排、安全策略、上下文聚合这些应用级责任都在 Host。协议规范约束的是 Client 与 Server 之间的行为，Host 内部怎么实现它不管。

**2. Q：** Server 能主动给我推消息吗？
**A：** 2026-07-28 之后服务器不发起任何请求。它想向用户要输入，只能在应答里声明「缺什么」，由应用收集后重试，见 [[1.4 调用中途要输入：停下来问，答案带回重试]]；它想通知「数据变了」，靠应用主动开启的订阅流，见 [[3.2 传输：stdio 与 Streamable HTTP]]。

**3. Q：** 接入 MCP 是不是就是「多调一个 API」？
**A：** 不是。API 对接是应用直接消费一个服务的接口；接 MCP 是把一批外部能力以统一协议挂进应用，应用要持续做上下文聚合、权限把关和跨 Server 编排——这些恰是 agent 应用自己的架构课题。
