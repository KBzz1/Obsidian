# 错误处理：应用层怎么决策、怎么通信

## 先记决策树，不记错误码

应用每次发出一个工具调用，回来的结果只有四种走向。背这棵树就够了，具体错误码是开发者查文档的事：

1. **完成。** 结果回填对话，循环继续。这是主路径。

2. **要输入。** 不是错误，是交互分支。停下来收集输入，然后重试原调用，完整流程见 [[1.4 调用中途要输入：停下来问，答案带回重试]]。

3. **工具执行失败。** 业务层面的失败：参数校验不过、外部服务报错、日期不合法。关键在于这类失败是写给模型看的——错误信息回到对话里，模型读一遍，改参数重试就可能成功。应用要做的是把它交给模型，别自己吞掉。

4. **协议层失败。** 请求本身或环境出了问题：服务器不可达、版本不匹配、依赖了没声明的能力。模型改参数救不了这些，是应用开发者要处理的——修配置、换版本、降级、报错给人。

这棵树的分派价值在第 3 类和第 4 类的分别对待：执行失败走「模型自纠」通路，协议失败走「应用处理」通路。混着处理——比如把协议错误也丢回给模型——模型只会对着改不了的错误徒劳重试，白白烧轮次。

## 重试的三种含义

「重试」这个词在 MCP 里对应三件不同的事，应用别把它们搅在一起：

**为输入重试。** 同一个调用从头再来，带上刚收集的答案和服务器给的那段状态字符串。

**模型自纠的重试。** 模型发起一次参数不同的新调用。对协议来说这就是全新请求，没有任何关联，也不需要关联。

**断线后的重发。** 协议无状态，在途请求直接作废重发，不依赖「恢复某个会话」。本地子进程挂了，应用重启它就是；重开后订阅流要重新开启。

## 版本问题：先试，错了再调

版本不匹配不需要开场握手来预防。请求发过去，服务器如果只支持别的版本，会在错误里告诉你它支持哪些，应用挑一个交集重试一次就收敛；没有交集才报错给用户。这套「乐观尝试 + 一次修正」的协商方式，比维护版本兼容表省心。

## 安全立场：应用的三道闸

错误处理收尾的地方，把应用侧的安全动作放在一起记：

**对端自述不可信。** 工具说自己「只读」，只影响界面展示，不影响校验——确认与授权决策不能建立在服务器的自我描述上。

**敏感操作人工确认。** 模型决定调用和应用真正执行之间那道闸（见 [[1.3 工具调用循环：模型决策、执行与结果回填]]），是最后一道防线。

**参数进出留审计。** 服务器能看到发给它的所有参数，模型也可能被工具描述、资源内容里的恶意指令带偏。提示注入是协议条款之外最大的攻击面——协议的防御是结构性的（最小上下文限制影响半径），识破恶意内容这层责任在应用。

> [!example] 实践例子
> 「业务失败要可读、可让模型自纠；环境失败走治理」与项目第七章的 Tool Result 与错误协议同一分派，见 [[7.Tool Result 与错误协议]]；持续失败的应对（隔离、熔断、降级）在项目里落在运行时治理，见 [[7.外部依赖保护与服务级熔断]]、[[3.生产运行时治理边界]]。

## 边界问答

**1. Q：** 工具执行失败为什么不放在错误响应里，而放在正常结果里？
**A：** 受众不同。执行错误是给模型看的反馈（改什么参数可能成功），协议错误是给开发者看的（改参数没用）。放进正常结果，客户端才会把文本回填给模型，模型自纠的通路才通。这一条是 MCP 错误设计里最值得讲的一个点。

**2. Q：** 模型自纠会无限循环吗？
**A：** 协议不设上限，循环控制是应用的责任——这符合「编排责任归 Host」的总原则。应用给工具循环设终止条件（轮次上限、超时），到顶了就把情况报告给用户，别指望协议替你踩刹车。

**3. Q：** 怎么判断一次失败属于哪一层？
**A：** 问一个问题：「模型换个参数再试，有可能成功吗？」可能——参数校验、外部业务拒绝、格式问题，是执行失败，交给模型；不可能——连不上、版本不符、能力没声明，是协议层失败，交给应用自己。拿不准时看错误来自结果的执行失败标记，还是来自协议层的错误响应。
