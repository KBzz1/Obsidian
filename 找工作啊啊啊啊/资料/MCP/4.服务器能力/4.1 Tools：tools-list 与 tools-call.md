# Tools：tools-list 与 tools-call

Tools 是 MCP 三种服务器原语里「给模型执行的动作」：查询数据库、调 API、做计算。它的交互模型是模型控制（model-controlled）——由 LLM 根据上下文自主发现与调用；但规范同时要求实现方提供人工介入：应当有清晰展示哪些工具暴露给了模型的 UI、调用时的明确指示、敏感操作的确认提示。支持工具的服务器必须声明 `tools` 能力（含 `listChanged` 标志）。

## 工具定义

```json
{
  "name": "get_weather",                        // 唯一标识：1-128 字符，大小写敏感，
                                                // 只用字母数字与 _ - .，服务器内唯一
  "title": "Weather Information Provider",      // 可选的人类可读显示名
  "description": "Get current weather for a location",
  "inputSchema": {                              // 输入：JSON Schema 2020-12
    "type": "object",
    "properties": {
      "location": { "type": "string", "description": "City name or zip code" }
    },
    "required": ["location"]
  },
  "outputSchema": {                             // 可选输出 schema：结构化结果用它校验
    "type": "object",
    "properties": {
      "temperature": { "type": "number" },
      "conditions": { "type": "string" }
    },
    "required": ["temperature", "conditions"]
  },
  "annotations": {                              // 行为特征提示，视为不可信（见下）
    "readOnlyHint": true,
    "destructiveHint": false,
    "idempotentHint": true,
    "openWorldHint": true
  }
}
```

工具名的唯一性作用域是单个服务器；聚合多个服务器的客户端或代理会遇到撞名（两个服务器都有 `search`），应当自行消歧（如加服务器前缀），且不能依赖 `serverInfo` 的 name 做消歧——它不保证全局唯一。无参数工具的 inputSchema 推荐写 `{ "type": "object", "additionalProperties": false }`。

## tools/list：发现

客户端发 `tools/list` 拿当前可用工具，支持分页（`cursor` / `nextCursor`）与缓存（结果带 `ttlMs` 与 `cacheScope`）：

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "result": {
    "resultType": "complete",
    "tools": [ { "name": "get_weather", "...": "..." } ],
    "nextCursor": "next-page-cursor",           // 有下一页时才出现
    "ttlMs": 300000,                            // 新鲜度提示（毫秒），供客户端缓存
    "cacheScope": "public"                      // 共享中间设施可否缓存
  }
}
```

三条规则：工具集合可以随时间变化（配合 `notifications/tools/list_changed` 订阅通知），但不得随连接变化、也不得作为同连接上其他请求的副作用变化——集合可以随请求携带的授权变化，因为凭据是逐请求输入而非连接状态；服务器应当以确定性顺序返回（集合不变则顺序不变），让客户端可靠缓存、提升工具进入模型上下文后的提示词前缀缓存命中；声明了 `listChanged` 的服务器应当向开启了 `subscriptions/listen`（`toolsListChanged: true`）的客户端发变更通知。

## tools/call：调用与非结构化结果

```json
{
  "jsonrpc": "2.0",
  "id": 2,
  "method": "tools/call",
  "params": {
    "name": "get_weather",
    "arguments": { "location": "New York" }
  }
}
```

结果的 `content` 数组可以混装多种内容块：文本、图像（Base64 + MIME）、音频、resource_link（指向 Resources 的 URI 引用，不保证出现在 resources/list 里）、resource（嵌入的资源正文）。内容块都可以带 annotations（audience、priority、lastModified）。

**结构化输出**：结果可以同时在 `structuredContent` 字段里放任意 JSON 值（对象、数组、标量都行），声明了 `outputSchema` 时必须符合该 schema，客户端应当校验。向后兼容要求：有结构化输出的工具应当把序列化 JSON 同时放进一个文本内容块。注意 `structuredContent` 是服务器产生的结果数据，与 LLM 供应商的「结构化输出」（schema 约束的模型生成）无关。

调用中途需要输入时，服务器返回 `resultType: "input_required"`，客户端收集后带 `inputResponses` 与 `requestState` 重试（完整机制见 [[3.3 MRTR：多轮往返请求]]，重试的 id 必须换新）。

## 两类错误

1. **协议错误**：请求结构本身的问题——未知工具、畸形请求、服务器错误。走标准 JSON-RPC 错误响应，模型不太可能修复它们。
2. **工具执行错误**：模型可以据此自我修正再重试的反馈——API 失败、输入校验失败（日期格式错、数值越界）、业务逻辑错误。在结果里以 `isError: true` 报告：

```json
{
  "result": {
    "resultType": "complete",
    "content": [ { "type": "text", "text": "出发日期非法：必须在未来。今天是 2025-08-08。" } ],
    "isError": true
  }
}
```

客户端应当把工具执行错误交给模型以支持自我修正；协议错误可以交也可以不交。

## 有状态工具的句柄模式

协议无会话，服务器不能靠连接关联多次调用。需要跨调用状态（购物车、浏览器上下文、数据库事务）的服务器，做法是**创建型工具返回显式句柄（handle），后续工具把句柄当普通参数传回**：

```jsonc
// → tools/call
{ "name": "create_basket", "arguments": { } }

// ← result
{
  "content": [{ "type": "text", "text": "Created basket bsk_a1b2c3" }],
  "structuredContent": { "basket_id": "bsk_a1b2c3" }   // 句柄进了结构化结果
}

// → tools/call（模型负责把 basket_id 带回来）
{ "name": "add_item", "arguments": { "basket_id": "bsk_a1b2c3", "sku": "..." } }
```

线上视角句柄只是一段普通字符串：协议没有句柄概念，携带责任在模型。句柄设计的四条指导：授权上句柄只是名字不是凭证，认证服务器每次调用都要校验调用者对句柄的权限，无认证服务器的句柄要有足够熵（如 UUIDv4）与有限期；不透明性上避免编码内部结构招致猜测；生命周期要在创建工具的 description 里声明（「购物车闲置 24 小时过期」），让模型决策时可见；过期句柄的调用要返回说明情况的工具执行错误，让模型能靠新建句柄恢复。

> [!example] 实践例子
> 项目第四章自建 Tool Runtime，没有走 MCP，但两个对照点面试常被问：工具注解（readOnlyHint、idempotentHint）「视为不可信、只作展示提示」对应项目护栏不信任模型自述、校验落在运行时，见 [[5.护栏]]；协议错误与工具执行错误两分、「执行错误要能让模型自纠」对应项目的 Tool Result 与错误协议，见 [[7.Tool Result 与错误协议]]。句柄模式与项目把调用身份（invocation）固化在运行时侧、由系统而非模型负责关联，是同一问题的两种取舍。

## 边界问答

**1. Q：** 工具注解为什么必须视为不可信？
**A：** 注解是服务器对自己行为的自述，恶意服务器可以把破坏性工具标成 `readOnlyHint: true` 诱导客户端免确认执行。规范明确：除非来自可信服务器，注解一律不可信；确认与授权决策不能建立在注解上。

**2. Q：** 为什么列表结果要确定性排序？
**A：** 同一工具集合每次返回相同顺序，客户端才能放心缓存列表，工具进入模型上下文时前缀稳定、提示词缓存命中率高。这是 2026-07-28 为规模化部署加的 SHOULD 级要求。

**3. Q：** 两类错误为什么分开？
**A：** 受众不同。协议错误给客户端开发者看（未知工具、畸形请求，模型改参数也没用）；工具执行错误给模型看（日期格式、数值越界，模型调整参数重试就可能成功）。混在 JSON-RPC error 里，模型自纠的通路就断了。
