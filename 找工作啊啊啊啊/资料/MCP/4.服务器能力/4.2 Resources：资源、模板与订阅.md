# Resources：资源、模板与订阅

Resources 是 MCP 三种服务器原语里的「数据上下文」：文件、数据库 schema、应用专属信息——给用户或模型使用的只读数据，每项资源用 URI 唯一标识。它的交互模型是应用驱动（application-driven）：资源怎么进入上下文由宿主应用决定——树形/列表 UI 供用户显式选择、搜索过滤、或按启发式与模型选择自动包含，协议不规定。

支持资源的服务器声明 `resources` 能力，两个可选标志：`listChanged`（资源列表变更时发通知）、`subscribe`（支持按资源粒度的更新通知）。

## 资源定义与读取

```json
{
  "uri": "file:///project/src/main.rs",     // 唯一标识，RFC 3986 URI
  "name": "main.rs",                        // 名称
  "title": "Rust 主文件",                    // 可选显示名
  "description": "程序入口",
  "mimeType": "text/x-rust",                // 可选 MIME 类型
  "size": 1024,                             // 可选字节大小
  "annotations": {                          // 给客户端的使用提示
    "audience": ["user", "assistant"],      // 受众：user / assistant
    "priority": 0.8,                        // 0.0~1.0，越大越重要
    "lastModified": "2025-01-12T15:00:58Z"  // 最近修改时间
  }
}
```

`resources/read` 按 URI 取内容，一次可以返回多条内容（读目录资源时返回多个文件）；结果同样带 `ttlMs` / `cacheScope` 供缓存。内容两种形态：文本（`text` 字段）与二进制（`blob` 字段，Base64）。读取中途缺输入时同样可以返回 InputRequiredResult 走 MRTR。

标准 URI 方案的约定：`https://` 只在客户端能自己直接从 web 取该资源时使用（否则服务器应改用别的方案，即便内容实际来自网络）；`file://` 表示类文件系统资源但不必映射真实文件系统（目录可用 XDG MIME 类型如 `inode/directory`）；`git://` 用于版本控制集成；自定义方案需符合 RFC 3986。

## 资源模板

参数化资源用 RFC 6570 URI 模板暴露，`resources/templates/list` 列出：

```json
{
  "uriTemplate": "file:///{path}",          // 客户端填 path 得到具体资源 URI
  "name": "Project Files",
  "description": "访问项目目录下的文件",
  "mimeType": "application/octet-stream"
}
```

模板参数可以通过 completion 工具接口做参数自动补全。

## 变更订阅

2026-07-28 起订阅收拢到 `subscriptions/listen` 一条请求：客户端在请求里声明要哪些类的通知（`toolsListChanged`、`promptsListChanged`、`resourcesListChanged`、`resourceSubscriptions` 及具体资源 URI），服务器确认后在这条请求的响应流上投递变更通知，通知用 `_meta` 里的 `subscriptionId` 关联到所属订阅：

```json
{
  "jsonrpc": "2.0",
  "method": "notifications/resources/updated",
  "params": {
    "_meta": { "io.modelcontextprotocol/subscriptionId": 4 },  // 关联到哪条订阅
    "uri": "file:///project/src/main.rs"                        // 哪个资源变了
  }
}
```

客户端收到后重新 `resources/read` 拿新内容。请求作用域的进度与日志通知不进订阅流，只在自己所属请求的响应流上出现。

## 错误语义

资源不存在必须返回 `-32602`（Invalid Params）错误并附 URI——不允许用空 `contents` 数组表示不存在，空数组的语义是歧义的（存在但无内容，还是不存在？）。内部错误用 `-32603`。客户端为兼容旧版服务器应当仍然接受旧错误码 `-32002` 作为资源不存在。

> [!example] 实践例子
> 「传引用还是传正文」的取舍两边同构：resource_link 只给 URI 让客户端按需取，embedded resource 直接内嵌正文；项目的证据与产物同样以引用（evidence_id、artifact 引用）进入清单、正文留在归属存储，见 [[9.证据装配与失败语义]]。annotations 的 audience / priority 则与第二章装配器「每类执行者只看该看的信息」同一关切，见 [[3.上下文装配器与 ContextPolicy]]。

## 边界问答

**1. Q：** Resources 和 Tools 的边界在哪？
**A：** 资源是数据、工具是动作；资源是应用驱动（用户或应用决定引入哪个），工具是模型控制（模型自主决定调用）。一个体现：客户端可以缓存、展示、让用户挑选资源，而工具调用应当有人工确认环节。

**2. Q：** 为什么 `https://` 资源建议客户端直接取，不经服务器？
**A：** 客户端能自取的资源走服务器中转是多余的一跳，还让服务器有机会改写内容。方案命名因此承载了路由语义：服务器只是内容来源时，即便内部走网络，也应当用别的 URI 方案。

**3. Q：** 空 contents 数组为什么不能表示「资源不存在」？
**A：** 空数组合法用于「读取成功但没有内容」的场景，两种含义挤一个表示会逼客户端猜测。规范要求不存在必须走显式错误（`-32602` 附 URI），语义才无歧义。
