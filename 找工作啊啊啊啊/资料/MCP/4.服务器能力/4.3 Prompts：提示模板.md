# Prompts：提示模板

Prompts 是 MCP 三种服务器原语里的「参数化消息模板」：服务器把结构化的指令与工作流封装成可发现、可传参的提示，客户端取用后作为消息进入对话。典型形态是斜杠命令——用户在 UI 里输入 `/code_review` 触发服务器预置的代码审查提示。

它的交互模型是用户控制（user-controlled）：**由用户显式选择使用哪个提示**——这说的是谁决定何时用，不是说谁写内容；提示内容由服务器定义。这一条与 Tools（模型控制）、Resources（应用驱动）构成三种原语的定位差异。

## 模板定义与取用

```json
{
  "name": "code_review",                        // 唯一标识
  "title": "Request Code Review",               // 可选显示名
  "description": "分析代码质量并给出改进建议",
  "arguments": [                                // 可选的定制参数
    {
      "name": "code",                           // 参数名
      "description": "要审查的代码",              // 参数说明
      "required": true                          // 是否必填
    }
  ]
}
```

`prompts/list` 发现（支持分页与 `ttlMs` / `cacheScope` 缓存），`prompts/get` 带参数取展开后的消息：

```json
{
  "jsonrpc": "2.0",
  "id": 2,
  "method": "prompts/get",
  "params": {
    "name": "code_review",
    "arguments": { "code": "def hello():\n    print('world')" }
  }
}
```

响应是一组带角色的消息，角色只有 `user` 与 `assistant` 两种；内容块可以是文本、图像、音频、resource_link（引用资源不内嵌）或 resource（内嵌资源正文）：

```json
{
  "result": {
    "resultType": "complete",
    "description": "Code review prompt",
    "messages": [
      {
        "role": "user",
        "content": {
          "type": "text",
          "text": "请审查这段 Python 代码：\ndef hello():\n    print('world')"
        }
      }
    ]
  }
}
```

模板可以是动态的——服务器按参数即时生成内容，也可以嵌入服务器管理的资源（文档、代码样例）。`prompts/get` 同样允许返回 InputRequiredResult：解析提示还缺参数时，走 [[3.3 MRTR：多轮往返请求]] 要输入再重试。参数可以用 completion 接口做自动补全。错误约定：无效提示名、缺必填参数用 `-32602`，内部错误 `-32603`。

实现要求很薄：服务器应当先校验参数再处理；双方尊重能力协商（声明 `prompts` 能力与 `listChanged`，列表变更通过订阅流通知）。安全上必须校验提示的输入与输出，防注入与未授权的资源访问。

> [!example] 实践例子
> 「提示作为可发现、可参数化、按需装载的能力」与项目第二章的技能装载同一形态：规划器 Skill / Prompt 只在当前 stage 声明需要时才进上下文，见 [[8.能力渐进装载]]；差异在 MCP 的提示由用户显式触发，项目的技能由执行阶段配置驱动。

## 边界问答

**1. Q：** Prompts 和 Tools 的区别是什么？
**A：** 提示产出的是消息（进入对话上下文的指令），工具产出的是副作用与结果（对世界的操作）；提示由用户显式触发，工具由模型自主决定调用。一个提示可以引导模型去调用工具，但两者在协议里是独立原语。

**2. Q：** 模板参数为什么只有 name / description / required 三样，不像工具那样有完整 JSON Schema？
**A：** 提示参数面向用户填空（表单、命令补全），不是面向程序的严格校验边界；需要结构化约束的场合应当建模成工具的 inputSchema。参数补全走独立的 completion 工具接口，补全请求还可以带 `context` 字段携带已解析的变量。

**3. Q：** 提示可以主动进入对话吗？
**A：** 协议不强制交互模型，但定位是用户控制：设计意图是用户显式选择（如斜杠命令），而不是服务器在模型对话里自动注入。服务器没有任何「推送提示」的协议通道。
