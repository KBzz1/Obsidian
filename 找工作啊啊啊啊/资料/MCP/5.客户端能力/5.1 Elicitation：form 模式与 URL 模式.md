# Elicitation：form 模式与 URL 模式

Elicitation 让服务器在处理请求中途向用户要补充信息：缺参数、要确认、要授权。交互发生在客户端的 UI 里，客户端全程保持对用户交互与数据共享的控制。2026-07-28 起 elicitation 请求不再由服务器主动发出，而是内嵌在 `InputRequiredResult.inputRequests` 里（键名 `elicitation/create`），客户端收集回答后随原请求重试带回。

两种模式的分界是**数据要不要经过 MCP 客户端**：

- **form 模式**（带内）：结构化表单，数据对客户端可见；
- **URL 模式**（带外，2025-11-25 引入）：引导用户去外部 URL 完成敏感交互，除 URL 本身外数据不经过客户端。

客户端按模式声明能力，至少支持一种：

```json
{
  "_meta": {
    "io.modelcontextprotocol/clientCapabilities": {
      "elicitation": {
        "form": { },     // 支持 form 模式
        "url": { }       // 支持 URL 模式
      }
    }
  }
}
```

空对象 `elicitation: {}` 等价于只声明 form（向后兼容）。服务器不得发送客户端未声明支持的模式。

## form 模式

请求带 `message`（为什么要这项信息的说明）与 `requestedSchema`（期望回答的结构）：

```json
{
  "method": "elicitation/create",
  "params": {
    "mode": "form",
    "message": "请提供你的 GitHub 用户名",
    "requestedSchema": {
      "type": "object",
      "properties": {
        "name": { "type": "string" }
      },
      "required": ["name"]
    }
  }
}
```

requestedSchema 被刻意限制为**扁平对象 + 原始类型**，简化客户端表单生成：string（支持 `format`: email / uri / date / date-time）、number / integer（minimum / maximum）、boolean、enum（单选与多选，可带 title，支持 default 预填）。嵌套结构、对象数组等高级特性一概不支持。客户端据此生成表单、校验输入，提交前让用户检查修改。

## 三动作应答

客户端的回答统一用三动作模型，form 与 URL 都适用：

```json
{
  "action": "accept",              // accept：用户明确同意并提交
  "content": { "name": "octocat" } // form 模式下按 schema 提交的数据
}
```

`"decline"` 是用户明确拒绝（点「拒绝」「否」）；`"cancel"` 是未做选择就关闭（关对话框、按 Esc、浏览器加载失败）。三者语义不同：accept 携带内容、另两者通常省略；服务器应分别处理——accept 处理数据、decline 提供替代、cancel 稍后再问。

## URL 模式

请求带 `url` 与 `message`，用于认证流、支付这类**不得经过 MCP 客户端**的敏感交互：

```json
{
  "method": "elicitation/create",
  "params": {
    "mode": "url",
    "url": "https://mcp.example.com/ui/set_api_key",
    "message": "请打开链接设置你的 API key。"
  }
}
```

关键语义：客户端拿到 `action: "accept"` 只代表用户同意打开链接，**不代表带外交互完成**——交互发生在浏览器与服务器之间，客户端看不到过程与结果。完成与否由服务器判断：客户端重试原请求时，服务器从回显的 `requestState` 或自己的存储判断带外交互是否完成，完成了给最终结果，没完成再返回一个 InputRequiredResult。因此客户端应当提供手动重试与取消控件。

URL 模式的典型用途是**外部授权**：MCP 服务器作为 OAuth 客户端对接第三方服务。此时服务器同时扮演两个角色——对 MCP 客户端是 OAuth 资源服务器，对第三方是 OAuth 客户端。安全红线：第三方凭据不得经过 MCP 客户端；服务器不得拿客户端的令牌去调第三方（token passthrough，被明文禁止）；用户必须直接对服务器授权；令牌由服务器保管并绑定用户身份。这与 MCP 自身的授权（客户端 ↔ 服务器）是两套独立的流。

## 安全要求

form 模式禁止索取密码、API key、访问令牌、支付凭据这类敏感凭据——要走 URL 模式；姓名、邮箱这类一般联系信息不在此列。客户端必须清楚展示是哪个服务器在要信息、提供明确的拒绝与取消入口、发送前让用户审阅修改。URL 处理规则：不得自动预取 URL 或其元数据；未经用户明确同意不得打开；必须展示完整 URL 供检查、高亮域名防子域名仿冒、对含 Punycode 的可疑 URI 告警；必须用安全方式打开（如 iOS 的 SFSafariViewController，不得用可被客户端检视内容的内嵌 WebView）。

防钓鱼是服务器侧责任：攻击者可以把发给自己的引出 URL 转发给受害者点击。服务器必须校验**打开 URL 的用户与发起引出的用户是同一人**——常见做法是引出到自己的 connect 页面，用会话 cookie 对照 MCP 授权体系的 `sub` 声明确认身份，再把用户送去第三方授权端点。

> [!example] 实践例子
> 「停下来把问题带出去、答案带回来重启」对照 [[6.HIL 与恢复]]：项目的 InputRequest 有稳定身份与结构化回答恢复，MCP 的 elicitation 用 inputRequests 键 + requestState 承担同两个职责；URL 模式的「accept 只代表同意开始」与项目等待用户确认草稿的挂起语义（等待不是完成，确认才推进）同构。

## 边界问答

**1. Q：** form 和 URL 怎么选？
**A：** 数据敏感度定界：密码、API key、支付信息必须 URL 模式（数据不过客户端，不进 LLM 上下文与客户端日志）；一般信息用 form 模式，交互更轻。规范明文禁止 form 索取凭据类信息。

**2. Q：** URL 模式下 accept 为什么不代表完成？
**A：** 带外交互在浏览器与服务器之间进行，客户端既看不到过程也收不到结果，accept 只承诺「用户同意打开链接」。完成判定只能由服务器做——重试原请求时从 requestState 或自身状态判断，这也是为什么客户端要提供手动重试控件。

**3. Q：** requestedSchema 为什么只允许原始类型的扁平结构？
**A：** schema 的消费者是客户端的通用表单渲染器，不是程序逻辑：任意 JSON Schema 意味着任意 UI 复杂度，每个客户端都要实现全部渲染能力。限制到原始类型让「schema → 表单」的映射保持平凡，需要复杂输入结构的场合应该建模成工具调用。
