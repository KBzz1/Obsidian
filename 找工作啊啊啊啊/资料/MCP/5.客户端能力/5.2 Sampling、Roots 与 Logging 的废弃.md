# Sampling、Roots 与 Logging 的废弃

2026-07-28 版将 Roots、Sampling、Logging 三个特性标记为 Deprecated：仍然在规范里、仍然工作，最短保留十二个月，但新实现不应再采用，官方给出了各自的迁移路径。三个特性都依赖「服务器在协议里有超出应答的主动性」，与无状态化方向相悖，这是它们被一起废弃的共同背景。

## Sampling：服务器借客户端的模型

Sampling 让服务器在处理请求途中请求一次 LLM 补全——服务器不需要自己的 API key，模型访问、选择与许可都留在客户端手里。请求（现以内嵌 InputRequiredResult 形式）核心字段：

```json
{
  "method": "sampling/createMessage",
  "params": {
    "messages": [
      { "role": "user", "content": { "type": "text", "text": "What is the capital of France?" } }
    ],
    "systemPrompt": "You are a helpful assistant.",
    "modelPreferences": {                  // 模型偏好：提示 + 三项优先级
      "hints": [ { "name": "claude-3-sonnet" } ],
      "costPriority": 0.3,                // 越高越偏向便宜
      "intelligencePriority": 0.8,        // 越高越偏向能力强
      "speedPriority": 0.5                // 越高越偏向低延迟
    },
    "maxTokens": 100                      // 必填，客户端必须遵守
  }
}
```

模型偏好是一层刻意的抽象：服务器不能点名要某个模型（客户端未必有），hints 只作子串匹配的参考，三项优先级表达特征需求，最终选择权在客户端——没有 Claude 时可以把 sonnet 档的 hint 映射到能力相当的其他模型。结果带 `role` / `content` / `model` / `stopReason`（endTurn、stopSequence、maxTokens、toolUse 等）。2025-11-25 起采样请求还能带 `tools` 与 `toolChoice`（auto / required / none），支持采样内的多轮工具循环。安全上要求人在回路：客户端应当让用户审阅提示与生成结果。`includeContext` 的 `thisServer` / `allServers` 取值先被软废弃、本次正式废弃。

**废弃迁移**：直接对接 LLM 供应商 API。官方的判断是让服务器经客户端中转用模型的收益撑不起协议复杂度——需要智能的服务器自己配模型访问更直接。

## Roots：客户端向服务器暴露文件系统根

Roots 把客户端（宿主应用）认为相关的目录与文件告诉服务器——典型是 IDE 场景把工作区根给代码分析服务器，让它的操作聚焦在这些范围。请求（现内嵌）与回答：

```json
{
  "method": "roots/list"                  // 服务器：把你的根告诉我
}
```

```json
{
  "roots": [
    { "uri": "file:///home/user/projects/myproject", "name": "My Project" }
  ]
}
```

规范明确 roots 是**信息性指引而非访问控制**：协议不强制服务器待在 roots 之内，`uri` 当前必须是 `file://` 形态。通常由工作区选择器这类 UI 暴露，客户端应当先征得用户同意。

**废弃迁移**：目录与文件改走工具参数、resource URI 或服务器配置——即「需要什么就显式传什么」，不再维持一条专门的服务器反向查询通道。

## Logging：服务器日志流

Logging 让服务器按客户端设置的级别（`logging/setLevel`）持续发 `notifications/message` 日志通知。2026-07-28 删除了 setLevel 与相关通知：日志级别改为逐请求的 `_meta.io.modelcontextprotocol/logLevel` 字段——服务器只对带了这个字段的请求发日志通知；`ping` 方法也一并删除。

**废弃迁移**：stdio 场景直接写 stderr；其余场景用 OpenTelemetry（`_meta` 已保留 `traceparent` 等标准追踪键）。

## 三个共性与一个注脚

共性一：都依赖服务器在协议里的主动性——发起请求（sampling、roots）或主动推送（logging 的 setLevel 语义），无状态模型把这条通道收窄成了「应答内嵌 + 订阅流」。共性二：官方都给了「更简单的既有机制」做迁移路径，没有留悬空能力。共性三：废弃不等于立即移除，十二个月窗口内照常工作。

注脚：`notifications/elicitation/complete`（2025-11-25 引入的引出完成信号）也在本次移除——MRTR 下客户端靠重试原请求得知带外交互结果，完成信号与它的关联 id 失去了协议位置。

> [!example] 实践例子
> Sampling 的「模型访问留在客户端、用户审阅每次调用」对照项目的解法：模型调用全部由 Harness 装配与校验（Supervisor 只输出结构化动作、根运行时校验后才执行），见 [[4.Supervisor 架构与委派]] 与 [[5.护栏]]——两种设计关切的都是「谁有权触发模型与工具」，差别在 MCP 把控制点放在客户端人审，项目放在运行时校验。

## 边界问答

**1. Q：** 为什么废弃 Sampling？
**A：** 官方迁移建议是直接对接 LLM 供应商 API。经客户端中转的价值（服务器无 key、用户可控）在实践中撑不起成本：协议要抽象模型偏好、维护嵌套在工具调用里的采样循环，客户端要做全套人审 UI，而需要智能的服务器大多可以自建模型访问。

**2. Q：** Roots 为什么不是访问控制？
**A：** 规范原文定位就是信息性指引：协议无法强制一个持有任意代码执行能力的服务器待在给定目录里。真正的访问控制在操作系统与授权层（OAuth scope、文件系统权限）。这也是它能被「显式传参」取代的原因——既然只是提示，用普通参数传同样的信息不损失任何保证。

**3. Q：** 现在还该实现这三个特性吗？
**A：** 新实现不应采用（规范原文 SHOULD NOT）。要互操作已实现它们的对端时按废弃规范行事即可；十二个月最短窗口过后它们才「有资格」被移除，实际移除时间由后续版本决定。
