# Streaming modes 与子图流式

## stream_mode：一个参数决定看到什么

`graph.stream()`（同步）与 `astream()`（异步）不等执行结束拿最终 state，而是把执行过程一段段交给调用方。看到什么由 `stream_mode` 参数决定：它选择执行事件被包装成哪种粒度的载荷——每个 superstep 的全量状态、单个节点的增量写入、LLM 的 token 片段，或节点内手工发射的自定义数据。

输出格式分两代。v1（默认）：单模式时直接给该模式载荷，多模式时给 `(mode, chunk)` 元组，再开子图就是 `(namespace, mode, data)` 三元组，组合越多解包越乱。LangGraph 1.1 起传 `version="v2"` 统一成 StreamPart dict，无论几个模式、开不开子图，形状一致：

```python
{                             # StreamPart（langgraph.types 里各模式的 typed dict 联合）
    "type": "updates",        # 本段事件的模式：values/updates/messages/custom/checkpoints/tasks/debug
    "ns": (),                 # 命名空间元组：根图为空元组，子图事件在这里标来源
    "data": ...,              # 实际载荷，形状随 type 变化
}
```

消费端按 `chunk["type"]` 分发。下文示例输出以 v1 原始形态为主，各模式本来的载荷看得更清楚。

## 各取值逐个看

用官方示例图 refine_topic → generate_joke 对比前两个模式。

**updates** 只流每个节点实际写入的增量，带节点名，同一个 superstep 里多个节点的更新分开发：

```text
Node `refine_topic` updated: {'topic': 'ice cream and cats'}
Node `generate_joke` updated: {'joke': 'This is a joke about ice cream and cats'}
```

**values** 每步都流全量 state，最后一段就是最终结果：

```text
topic: ice cream, joke:
topic: ice cream and cats, joke:
topic: ice cream and cats, joke: This is a joke about ice cream and cats
```

**messages** 流 token 级输出（token 是模型输出的最小文本单元），每段是 `(message_chunk, metadata)` 二元组：前者是消息增量，后者标明来源。节点、工具、子图与 task 里的 LLM 调用都覆盖——代码里用 `.invoke()` 调模型，token 也照发。常见两种过滤：按 `metadata["langgraph_node"] == "节点名"` 只取某个节点，或给模型挂 tag 后按 `metadata["tags"]` 过滤。给模型加 `nostream` tag（`.with_config({"tags": ["nostream"]})`）可以让调用照常执行、token 却不进 messages 流，内部处理（如结构化输出）或避免与其他通道重复推送时用。

**custom** 流节点内手工发射的自定义载荷，配合 `get_stream_writer()`：

```python
def node(state: State):
    writer = get_stream_writer()                     # 节点或工具内拿到发射器
    writer({"progress": "Retrieved 0/100 records"})  # 载荷完全由业务自定义
    return {"answer": "some data"}
```

`@tool` 工具内同样能发，比如检索过程中逐条汇报进度；没有 LangChain 集成的模型 API 也这样接——节点里循环自家客户端的流式接口，每片 `writer({"custom_llm_chunk": chunk})`。异步且 Python < 3.11 时 `get_stream_writer()` 拿不到上下文变量，改成给节点/工具签名加 `writer: StreamWriter` 参数，并显式传 config。

**checkpoints** 流检查点事件，格式与 `get_state()` 一致，需要编译时挂 checkpointer 并以 `thread_id` 调用。**tasks** 流任务的开始/结束事件（含节点、结果、错误），同样依赖 checkpointer。**debug** 是两者的超集再加额外元数据，只要子集时用窄模式。

**events** 不在经典 stream_mode 的取值表里——文档把「事件」放在另一层 API，见下文。

## 多模式组合

`stream_mode` 传列表即可同时订阅多个模式：`stream_mode=["updates", "custom"]`。v1 下每段变成 `(mode, chunk)` 元组，按 mode 分发；v2 下仍是统一的 StreamPart dict，按 `chunk["type"]` 分发。典型搭配是 updates（节点级）+ custom（节点内进度）+ messages（token 级），三层粒度一次拿全。

## 子图流式：subgraphs=True

默认父图的流只到节点级：节点里嵌的子图（比如把 `create_agent` 的返回值当一个节点挂进图）内部发生什么，外面看不见。传 `subgraphs=True` 后子图的执行事件也展开流出，对所有模式生效——包括 messages，不开它，父图级 messages 收不到内层 agent 的 LLM token。来源靠命名空间区分：v2 看 `chunk["ns"]`，根图是空元组 `()`，子图是 `("node_2:<task_id>",)`；v1 是 `(namespace, data)` 元组：

```text
Root: {'node_1': {'foo': 'hi! foo'}}
Subgraph ('node_2:dfddc4ba-c3c5-6887-5012-a243b5b377c2',): {'subgraph_node_1': {'bar': 'bar'}}
Subgraph ('node_2:dfddc4ba-c3c5-6887-5012-a243b5b377c2',): {'subgraph_node_2': {'foo': 'hi! foobar'}}
Root: {'node_2': {'foo': 'hi! foobar'}}
```

## event streaming：再往上一层

LangGraph v1.2 起官方把 event streaming 列为多数应用代码的推荐流式模型：`graph.stream_events(input, version="v3")` 返回一个可被多个消费者并发读取的 run stream 对象——读 `stream.messages` 不会吃掉 `stream.values` 需要的事件。它在 stream mode 之上多做两件事：把 Pregel 引擎的原始执行事件归一化，再经 transformer 路由成一组类型化投影（projection）：

```python
stream = graph.stream_events({"messages": [...]}, version="v3")

for message in stream.messages:   # 投影：消息与 token 增量
    for token in message.text:
        print(token, end="")

final_state = stream.output       # 投影：等待最终输出
```

内置投影有 `stream.messages`（消息与 token）、`stream.values`（状态快照）、`stream.output`（最终输出）、`stream.subgraphs`（嵌套图执行）、`stream.interrupts` / `stream.interrupted`（人工介入的中断载荷与是否中断）、`stream.extensions`（自定义 transformer 的投影）。记住定位即可：event streaming 是 stream modes 的类型化包装，不是第 8 个取值。

> [!example] 实践例子
> 流式回答的是「执行过程怎么被实时看见」：updates/values 是节点级、messages 是 token 级、custom 是节点内自报进度，`subgraphs=True` 决定子图内部是否可见。健康管理项目的过程可见性走的是自建 Trace 链路——TraceSpan 只落在工程边界、持 `invocation_id` 等 Record 引用而不复制内容（见 [[3.Task、Run 与 Trace 身份关联]]）；质量定位用分层评估而非按流式事件消费（见 [[8.Agent 分层评估]]）。

## 边界问答

**1. Q：** updates 和 values 怎么选？
**A：** updates 只给每个节点实际写入的键和节点名，适合逐步展示「谁做了什么」；values 每步给全量 state，最后一段即最终结果，适合需要每步完整快照或只关心终态的场景。

**2. Q：** 把 create_agent 包成节点后，messages 模式收不到内层模型的 token，为什么？
**A：** 该节点内部是一张子图。不开 `subgraphs=True` 时父图流式只到节点级；开了之后所有模式（含 messages）都会展开子图事件，`ns`（v1 的 namespace）标明来自哪层。

**3. Q：** 没有 LangChain 集成的模型 API 怎么流 token？
**A：** 节点里循环自己的流式客户端，每片用 `writer()` 发 custom 事件，消费端用 `stream_mode="custom"` 接。反过来，某个 LangChain 模型不想流 token，给它加 `nostream` tag 或建模型时设 `streaming=False`。

**4. Q：** debug 模式和 checkpoints、tasks 什么关系？
**A：** debug 是 checkpoints 与 tasks 两个模式的内容合起来再加额外元数据，只需要其中一类时用窄模式。两个窄模式都要求编译时挂 checkpointer 并用 `thread_id` 调用。

**5. Q：** events 是 stream_mode 的一个取值吗？
**A：** 不是。经典 stream_mode 的取值是 values/updates/messages/custom/checkpoints/tasks/debug；「事件」对应 v1.2 的 event streaming（`stream_events(version="v3")`），在 stream mode 之上做归一化与类型化投影。
