# Functional API：@entrypoint 与 @task

## 定位：不建图，把能力装进普通代码

StateGraph 之外，LangGraph 提供第二种构建方式：Functional API。它要解决的问题不是「图不好」，而是「很多代码本来就不是图」——把持久化、记忆、人工介入（HIL）、流式这四样能力以最小改动装进已有代码：分支与控制流继续用 if、for、函数调用这些标准语言原语，不用把代码重组成显式流水线或 DAG，也没有强制的执行模型。

两个构件：@task 把一个函数变成可检查点化的工作单元（一次 API 调用、一个数据处理步骤），可异步执行、结果可持久化、可重试；@entrypoint 把一个函数标记为工作流起点，封装流程逻辑并管理执行——长任务、中断都由它承接。

两者与 StateGraph 共用同一套运行时基座：@entrypoint 的产物同样是一个 Pregel 实例，底层编译成一个单节点图，整个 entrypoint 函数在该节点里运行；checkpointer、Command(resume=值) 恢复、invoke / stream 调用方式全部与图一致。

## @task：可持久化的工作单元

```python
from langgraph.func import entrypoint, task
from langgraph.types import interrupt

@task
def write_essay(topic: str) -> str:
    # 被装饰函数：一个离散工作单元（LLM 调用 / API 请求 / 副作用）
    return f"essay about {topic}"

@entrypoint(checkpointer=checkpointer)
def workflow(topic: str) -> dict:
    essay = write_essay(topic).result()   # 调用立刻返回 future，.result() 同步等待结果
    is_approved = interrupt({"essay": essay})  # 中断等待人工审批，载荷原样透出给客户端
    return {"essay": essay, "is_approved": is_approved}
```

四条规则：task 只能在 entrypoint、另一个 task 或 StateGraph 节点内部调用，不能在应用主代码里直接调；调用 task 立即返回一个 future（结果的占位对象），同步用 .result()、异步用 await 取值；task 结果保存进检查点，恢复时已完成的结果直接读回、不重算——这是重放语义的基础；输出必须可 JSON 序列化（entrypoint 的输入输出同样要求），否则配了 checkpointer 就运行时报错。

官方列出该用 task 的场景：长操作结果要存检查点避免重算；人工介入流程里必须用 task 封装一切非确定性与副作用（随机数、API 调用），恢复才能对上；I/O 密集操作的并行执行；按 task 粒度做 LangSmith 观测；要封装重试逻辑的工作。

## @entrypoint：编排入口

entrypoint 函数必须接收单个位置参数作为工作流输入（多份数据打包成 dict 传入），装饰产物是可 invoke / stream 的 Pregel 实例；通常传 checkpointer 以启用持久化与人工介入。

它的短期记忆不用 State schema：给函数声明 previous 参数，拿到同一 thread 上一次调用保存的值（默认是上次返回值）；entrypoint.final(value=返回值, save=保存值) 可把「这次返回给调用方什么」与「这次存进检查点什么」解耦。还可注入 store（长期记忆）、writer（流式写自定义数据）、config，按名字与类型注解声明。

## 重放与确定性

Functional API 的恢复不是从停掉的那行代码继续：恢复回到检查点边界，entrypoint 从头重新执行，已完成 task（与 subgraph）的结果从检查点还原、不重算，重放到暂停处再往后走。由此三条工程约束：非确定性操作（随机数、当前时间）与副作用（写文件、发请求）必须装进 task，否则重放拿到的是新值而非原值；多个 interrupt 的恢复值按索引严格匹配中断顺序，恢复时顺序变了会错配；开始了但没跑完的 task 在恢复时可能重跑，副作用要按幂等设计。

## 与 StateGraph 的关系与选型

两套 API 同一运行时、可混用：同一应用里图节点调 entrypoint、entrypoint 里建图都合法。四点差异：

```text
控制流      Functional：普通 Python 措辞，代码量通常更少
            Graph：声明式，节点/边/状态显式
状态        Functional：状态在函数作用域内流转，不跨函数共享，无显式状态管理
            Graph：要声明 State，可能要写 reducer
检查点      Functional：task 结果存进 entrypoint 现有检查点，不是每个 task 一份新快照
            Graph：每个 superstep 边界生成一份新检查点
可视化      Functional：不支持——图是运行时动态生成的
            Graph：结构可渲染成图，利于调试、文档与团队沟通
```

官方选型口径：需要可视化、显式共享状态、多决策点分支、并行后汇合、团队协作——用 Graph API；要给现有过程式代码最小改造、标准控制流、函数作用域状态、快速原型、线性流程简单分支——用 Functional API。

> [!example] 实践例子
> 每日计划需要显式状态图：步骤固定、要在图上看清中断点与恢复位置、多节点共享草稿与计划状态，所以项目选 StateGraph 而不是 Functional API；Functional API 的适用面（线性逻辑、代码优先、少样板）正是这个选择的反面参照。执行单元与编排方式的分界见 [[3.执行模型与任务边界]]。

## 边界问答

**1. Q：** @entrypoint 底层还是图吗？
**A：** 是。@entrypoint 的产物是 Pregel 实例，与 StateGraph 共用同一运行时与 checkpointer；它实际编译成一个单节点图，整个函数在该节点内运行。持久化、人工介入、流式能力与图完全一致。

**2. Q：** 恢复时 entrypoint 会从断点那行代码继续吗？
**A：** 不会。恢复回到检查点边界，entrypoint 从头重放，已完成 task 的结果从检查点还原。这就是非确定性与副作用必须装进 task 的原因：装进去了，重放才能复现原结果。

**3. Q：** 不定义 State，Functional API 的短期记忆从哪来？
**A：** 来自 previous 参数：同一 thread 上一次调用保存的值，默认是上次返回值，可用 entrypoint.final 单独指定要保存的值。状态随函数参数传递，不跨函数共享。

**4. Q：** 什么时候不该选 Functional API？
**A：** 需要图可视化做调试与文档、多节点显式共享状态、复杂分支或并行后汇合时，选 Graph API；Functional API 适合线性流程、简单分支和对现有代码的最小改造。
