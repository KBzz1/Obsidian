# LangGraph 是什么

## 定位：低级别编排框架与运行时

官方定位：LangGraph 是一个低级别（low-level）编排框架与运行时（orchestration framework and runtime），用于构建、管理、部署长时间运行的有状态 agent。拆开看三个限定词：

- **编排**：管步骤怎么组织、状态怎么流动，不管构件本身——不抽象 Prompt、不预设架构，模型与工具的接入交给上层框架。
- **低级别**：不给开箱即用的 agent 循环，而是把节点、边、状态这些原语交给你；代码更多，换每一步的精确控制。官方分界很直白：只要现成高层抽象，就用 LangChain 的 agents（预建的 LLM 工具调用循环）。
- **长时间运行的有状态**：核心能力围绕执行现场——持久化、持久执行（durable execution，失败后从断点续跑）、人工介入（HIL）、流式输出，都是运行时自带而非外挂。

## 与 LangChain 的关系：依赖与分工

LangChain 公司把开源产品线分三层：运行时（Runtime）、框架（Framework）、Harness（成套脚手架）。

```text
Harness      Deep Agents：规划、子 agent、文件系统等成套能力，建在 LangGraph 上
Framework    LangChain：模型、工具、agent 循环的抽象与集成（create_agent）
Runtime      LangGraph：持久执行、流式、人工介入、持久化（同类：Temporal、Inngest）
```
关系的三个事实：LangChain 1.0 的 agent 抽象构建在 LangGraph 之上，依赖方向是 LangChain 依赖 LangGraph；用 LangGraph 不需要 LangChain，两者可独立安装（官方常用 LangChain 组件接模型和工具，是便利不是依赖）；用 LangChain 也不需要懂 LangGraph。分工一句话：LangChain 快速组装标准 agent，LangGraph 负责低级控制与生产运行。

## 图编排与链式编排

LangGraph 把 agent 工作流建模成图：节点（node）是编码逻辑的函数，边（edge）决定下一步执行谁，状态（state）是所有节点共享读写的数据结构。节点和边都只是函数，里面可以是一次 LLM 调用也可以是普通代码；执行借鉴 Google 的 Pregel 模型按 superstep 推进，接口命名借鉴 NetworkX（执行与状态机制见 [[2.1 LangGraph 检查点与 Channel]]，建图方法见 [[1.2 StateGraph 构建：Node、Edge 与条件边]]）。可以把它理解成一台显式状态机：共享状态加条件转移，哪一步做什么、什么时候循环，都在图上看得见。

链式编排指 LangChain 的 LCEL（LangChain Expression Language）链：用 `|` 把 Prompt、模型、输出解析等 Runnable 组件接成固定顺序的流水线，数据单向流过，一次调用走完，链本身自动获得同步/异步/批量/流式支持。它对应官方 Workflow 分类里的 prompt chaining 模式——每次 LLM 调用处理上一次调用的输出，适合能拆成小步、可逐步验证的明确任务。

LCEL 链一行就能立起来：

```python
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.output_parsers import StrOutputParser

prompt = ChatPromptTemplate.from_template("总结这周的训练负荷：{weekly_log}")
chain = prompt | model | StrOutputParser()   # | 把 Runnable 组件接成固定顺序的流水线

chain.invoke({"weekly_log": "周一跑步 5km、周三力量 40min"})
# 一次调用按 Prompt → 模型 → 解析走完，数据单向流，没有分支与回边
```

换成图，工具循环是一张带回边的最小图（工具执行节点的现成封装见 [[5.2 ToolNode 与工具循环]]）：

```python
from typing_extensions import Annotated, TypedDict
from langgraph.graph import StateGraph, START, END
from langgraph.graph.message import add_messages

class State(TypedDict):
    # add_messages：追加式 reducer，节点返回的消息合并进历史而不是整键覆盖（机制见 2.1）
    messages: Annotated[list, add_messages]

def agent(state: State):
    # 模型基于全部历史决定：直接回答，还是发起一次工具调用
    return {"messages": [model.invoke(state["messages"])]}

def tools(state: State):
    # 执行上一步发起的工具调用，结果作为消息写回同一份 messages
    ...

def route(state: State):
    # 条件边：最后一条消息还带着工具调用就转 tools，否则图结束
    if state["messages"][-1].tool_calls:
        return "tools"
    return END

builder = StateGraph(State)
builder.add_node(agent)
builder.add_node(tools)
builder.add_edge(START, "agent")             # 入口：用户输入先进 agent
builder.add_conditional_edges("agent", route)
builder.add_edge("tools", "agent")           # 回边：环在这里，链式编排没有的原生表达

graph = builder.compile()   # 编译后才能 invoke / stream
```

图编排多出来的能力落在三点：

1. **循环与条件路由**：链是固定顺序的单向序列；图可以成环——组合节点和边能创建「复杂的、带循环的工作流」。ReAct 这种「调用工具 → 观察 → 再决定」的反馈循环，链里没有原生表达。
2. **共享状态**：链上组件只看得到上一步的输出；图里所有节点读写同一个 state，分支汇合、跨步骤传中间数据是原生行为。
3. **每步持久化**：运行时在 superstep 边界存检查点，支撑中断恢复与人工介入；链没有这层设施。

官方还把应用形态分成 Workflow（预编排，代码路径提前确定）与 agent（动态，LLM 自己决定过程和工具用法）两类，LangGraph 两类都管，且允许确定性步骤与 agentic 步骤混排同一张图——需要可靠可预测的地方用确定性步骤，需要灵活的才交给模型。这是它反复强调的核心卖点。另一种不用显式图的构建方式见 [[1.5 Functional API：@entrypoint 与 @task]]。

## 单进程库与平台

LangGraph 首先是一个 pip 安装的 Python 库：装上就能在进程内建图、编译、调用，不强制任何云端服务。生产化时部署放在 LangSmith 平台：LangSmith Cloud 提供面向有状态长时 agent 的托管基础设施（持久状态、后台执行），另有混合部署、独立服务器、带控制平面的自托管等选项，部署后用 langgraph-sdk 或 REST API 访问。分工：编排运行时（执行、检查点、流式）在库里，规模化运行（托管、伸缩）在平台上。

## 适用场景

官方的选用理由：对 agent 编排要细粒度低级控制；要持久执行的长时有状态 agent；混合确定性步骤与 agentic 步骤的复杂工作流；要生产级部署设施。快速搭标准 agent、编排不复杂时，官方推荐先用 LangChain。

> [!example] 实践例子
> 健康管理项目把每日计划（DailyPlan）建成 LangGraph 状态图：参数准备、冲突检查、生成草稿、等人工确认都是预编排节点，训练/饮食智能体则是 ReAct 自由编排——正对应「确定性步骤与 agentic 步骤混排」的定位。会话/任务分层是框架之上的自建机制，不是图原语，见 [[3.执行模型与任务边界]] 与 [[8.一次完整的 DailyPlan]]。

## 边界问答

**1. Q：** 用 LangGraph 必须装 LangChain 吗？
**A：** 不必须。LangChain 是框架层（模型/工具/agent 循环的抽象与集成），LangGraph 是运行时层（持久执行、流式、人工介入、持久化），依赖方向是 LangChain 依赖 LangGraph。两者可独立使用，官方只是惯用 LangChain 组件接模型和工具。

**2. Q：** LCEL 链也能串多步调用，什么时候必须换成图？
**A：** 需要循环（工具调用-观察循环）、条件路由、多节点共享状态，或需要每步检查点支撑的中断恢复与人工介入时。链是固定顺序的单向流水线；固定序列在图里就是 START → n1 → n2 → END 的特例，图是链的编排超集。

**3. Q：** LangGraph 是一个服务吗，要不要配平台才能跑？
**A：** 都不是必须。它是进程内的 Python 库，装上即用；LangSmith Cloud / 混合 / 自托管等平台方案是生产部署的可选项，负责托管、伸缩与 Studio 可视化，编排与检查点能力本身在库里。

**4. Q：** Workflow 和 agent 在 LangGraph 里是两套机制吗？
**A：** 不是。两者是同一张图上的两种形态：Workflow 预先确定代码路径，agent 由 LLM 动态决定过程和工具；LangGraph 恰是允许两者混排，官方建议能确定的地方用确定性步骤、需要灵活的才交给模型。
