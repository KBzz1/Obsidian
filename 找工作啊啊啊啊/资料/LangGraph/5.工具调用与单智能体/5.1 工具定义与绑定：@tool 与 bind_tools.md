# 工具定义与绑定：@tool 与 bind_tools

## @tool：把函数变成工具

LangChain 的工具是一对东西：告诉模型「有什么能力、参数长什么样」的 schema，加真正执行的函数。`@tool` 把普通函数变成工具，schema 从签名自动生成：

```python
from langchain.tools import tool

@tool
def search_database(query: str, limit: int = 10) -> str:
    """Search the customer database for records matching the query."""
    ...
```

两条规则不可省：docstring 成为工具描述（`Args:` 段补充各参数用途）；类型注解生成输入 schema，必填。工具名建议 snake_case（部分提供商拒绝空格或特殊字符）；名字与描述可在装饰器参数覆盖（`@tool("web_search")` 改名，`description=...` 改描述）。

## args_schema：接管输入 schema

参数复杂（要字段级描述、枚举、默认值）时，用 Pydantic 模型接管 schema 生成；也可直接给原始 JSON Schema 字典，跳过 Pydantic：

```python
from pydantic import BaseModel, Field

class WeatherInput(BaseModel):
    location: str = Field(description="城市名")   # 字段描述进入 schema，模型据此填参
    units: str = "celsius"                        # 默认值：模型不填时按此执行

@tool(args_schema=WeatherInput)
def get_weather(location: str, units: str = "celsius") -> str:
    ...
```

签名里 `config` 与 `runtime` 被框架保留，不能用作自己的参数；`runtime`（类型 ToolRuntime）由 ToolNode 执行时注入、对模型侧 schema 隐藏，工具代码里能拿到 `runtime.state`、`runtime.context`、`runtime.tool_call_id` 等执行现场。

## 返回值：从字符串到 Command

工具返回什么，决定模型看到什么：

- 字符串：转成 ToolMessage 回给模型，最常见。
- 对象（字典）：序列化成结构化输出。
- 多模态内容块列表：`{"type": "text", ...}`、`{"type": "image", "url": ...}` 标准块。
- `Command(update={...})`：直接写图状态。约束：update 里必须含一条 `tool_call_id` 对应当前调用的 ToolMessage，漏掉时 ToolNode 抛 `ValueError`——每个工具调用都必须有配对的 ToolMessage，消息历史对提供商才合法；发给父图（`Command(graph=Command.PARENT)`）时不要求。

`return_direct=True` 短路智能体循环：不再回到模型，直接作为输出返回调用方；并行批次里每个工具都是 return_direct 才会退出，可与 Command 组合（先更新状态再退出）。ToolMessage 另有 `artifact` 字段：只把输出的一部分放进 `content` 给模型，完整输出整个放进 artifact 供调用方取用。

## bind_tools：把工具 schema 附给模型

`bind_tools` 把工具 schema 附给模型，之后模型可在调用中请求调用它们：

```python
model_with_tools = model.bind_tools([get_weather])
```

列表里可混三种东西：`@tool` 函数、Pydantic BaseModel（只用 schema）、字典（服务端工具，如 `{"type": "web_search"}`）。附加参数：`tool_choice="any"` 强制调任意一个工具，`tool_choice="工具名"` 强制调指定工具；`parallel_tool_calls=False` 关闭并行调用（OpenAI、Anthropic 支持）。已 bind_tools 的模型再套 with_structured_output 不受支持（见 [[5.3 Structured Outputs]]）。

## tool_calls：模型侧的调用提议

绑定工具后调模型，返回的 AIMessage 带 `tool_calls`——字典列表，每项三个关键字段加一个类型标记：

```python
response.tool_calls
# [{'name': 'get_weather',                     # 要调的工具名
#   'args': {'location': 'Boston'},            # 模型填好的参数
#   'id': 'call_Ga9m8FAArIyEjItHmztPYA22',     # 本次调用的 ID，回填配对用
#   'type': 'tool_call'}]
```

bind_tools 只让模型「提议」，不执行。单独用时循环要自己写：调模型 → 追加 AIMessage → 逐个 `tool.invoke(tool_call)` → 把带 `tool_call_id` 的 ToolMessage 追加回去 → 再调模型。`tool_call_id` 就是为并行调用准备的：一条 AIMessage 里多个调用，靠它对回各自的请求。

> [!example] 实践例子
> 框架侧工具是「schema + 函数」，模型只产出 tool_calls 提议。健康管理项目把模型可见的工具面按领域隔离、参数保持语义保真（[[3.工具能力设计与 Tool Surface]]），执行权收进自建 Tool Runtime——参数快照冻结、幂等键、护栏、执行记录（[[4.统一 Tool Runtime]]），工具描述按作用域渐进装载（[[8.能力渐进装载]]），是在框架循环原语之上加治理层。

## 边界问答

**1. Q：** docstring 和类型注解分别决定工具 schema 的什么？
**A：** docstring 成为工具描述；类型注解生成输入 schema，必填。字段级说明写在 docstring 的 `Args:` 段，或改用 args_schema 的 `Field(description=...)`。

**2. Q：** 为什么每个 tool_call 要带 id？
**A：** 一条 AIMessage 可同时提议多个工具调用，回填时每个 ToolMessage 靠 `tool_call_id` 对回各自的请求。

**3. Q：** 工具返回 Command 有什么额外义务？
**A：** 面向当前图的 `Command(update={...})` 必须在 update 里包含一条 `tool_call_id` 匹配当前调用的 ToolMessage，否则 ToolNode 抛 `ValueError`；面向父图的 Command 不受此约束。

**4. Q：** bind_tools 之后工具会被执行吗？
**A：** 不会。bind_tools 只把 schema 附给模型，模型返回的是 tool_calls 提议；执行要么自己写循环，要么交给 ToolNode（[[5.2 ToolNode 与工具循环]]）。
