# ToolNode 与工具循环

## ToolNode：批量执行 tool_calls 的预建节点

ToolNode 是 `langgraph.prebuilt` 的预建图节点，做一件事：读最后一条 AIMessage 的 tool_calls，逐个执行对应工具，把结果作为 ToolMessage 列表写回。构造签名：

```python
from langgraph.prebuilt import ToolNode

ToolNode(
    tools,                    # Sequence[BaseTool | Callable]：工具有序集合；普通函数自动转成工具并推断 schema
    name="tools",             # 节点名，默认 "tools"
    handle_tool_errors=...,   # 错误处理策略，见下文；默认捕获并转成 ToolMessage
    messages_key="messages",  # state 里消息列表的键名；输出 ToolMessage 也写回这个键
    wrap_tool_call=None,      # 包住每次工具调用的中间件
    awrap_tool_call=None,     # 异步版本的包装器
)
```

它接受三种输入：带 `messages` 键的图 state、消息列表（取最后一条 AIMessage）、或直接给 `{"name": ..., "args": ..., "id": ..., "type": "tool_call"}` 字典绕过消息解析。输出 `{"messages": [ToolMessage(...)]}`；工具返回 Command 时输出 Command，由框架传播。

## 经典接线：model ⇄ tools 的 ReAct 循环

官方对智能体的定义一句话：模型在循环里调用工具，直到任务完成。手搓的标准接线是两个节点加一条条件边：

```python
from langgraph.graph import StateGraph, MessagesState, START, END
from langgraph.prebuilt import ToolNode, tools_condition

model_with_tools = model.bind_tools(tools)       # 工具 schema 附给模型，见 5.1

def llm(state: MessagesState):                   # 模型节点：把全部消息喂给绑定工具的模型
    return {"messages": [model_with_tools.invoke(state["messages"])]}

graph = StateGraph(MessagesState)                # MessagesState：预建状态，仅一个带 add_messages 的 messages 键
graph.add_node("llm", llm)
graph.add_node("tools", ToolNode(tools))         # 工具节点：执行 tool_calls、回填 ToolMessage
graph.add_edge(START, "llm")
graph.add_conditional_edges(
    "llm",
    tools_condition,                             # 路由函数：最后一条 AIMessage 有 tool_calls → "tools"，否则 → END
    {"tools": "tools", "__end__": "__end__"},
)
graph.add_edge("tools", "llm")                   # 工具结果回填后回到模型，进入下一轮
```

`tools_condition` 是配套的预建路由函数：检查最后一条 AIMessage 是否带 tool_calls，有则返回 `"tools"`，没有则返回 `"__end__"` 结束图。整个循环即 ReAct 模式（模型交替「推理、行动、观察」）在 LangGraph 里的最小实现：模型提议 → ToolNode 执行回填 → 模型再决定下一步，直到不再产生 tool_calls。

## 并行工具调用

模型可在一条 AIMessage 里同时提议多个工具调用（默认开启；OpenAI、Anthropic 可用 `parallel_tool_calls=False` 关闭），ToolNode 批量执行同一条消息里的全部调用；预建智能体的 `version` 参数对应两种形态：v1 在单个工具节点里并行跑完，v2（默认）经 Send API 分发。

## 错误处理：handle_tool_errors

工具抛异常时，默认不炸图：错误转成 ToolMessage 回给模型，模型下一轮自己纠正参数或换路。`handle_tool_errors` 控制策略：

- `True`（默认）：捕获所有错误，返回带异常详情的默认错误模板。
- 字符串：捕获所有错误，返回这段自定义文案。
- 异常类或元组：只捕获匹配类型，返回默认错误消息。
- `Callable[..., str]`：异常交给这个函数，返回值作为错误消息。
- `False`：关闭处理，异常直接上抛打断图。

参数不合法是单独一类：经 ToolNode 调用时校验失败抛 `ToolInvocationError`（内部包 Pydantic 的 ValidationError），默认处理器同样转成描述性消息。要统一包装调用本身，用 `wrap_tool_call` / `awrap_tool_call` 挂中间件。

> [!example] 实践例子
> 框架的循环原语是「模型提议 → ToolNode 执行 → ToolMessage 回填」。健康管理项目刻意把 LLM 工具调用限定为提议，执行权收进自建 Tool Runtime——参数快照冻结、幂等键、护栏、执行记录（[[4.统一 Tool Runtime]]）；模型可见的工具集合按领域与执行深度收敛，见 [[3.工具能力设计与 Tool Surface]] 与 [[8.能力渐进装载]]。

## 边界问答

**1. Q：** ToolNode 和自己写一个执行节点差别在哪？
**A：** 批量执行、错误转 ToolMessage、ToolRuntime 注入、Command 传播都内置。官方定位：标准智能体用 create_agent（内部就是 ToolNode）；自定义路由、专门错误处理、非标准架构才自己组图（[[5.4 create_react_agent 与 prebuilt 组件]]）。

**2. Q：** 循环在哪一步停？
**A：** tools_condition 发现最后一条 AIMessage 没有 tool_calls 时路由到 `__end__`。停止条件是模型不再提议调用，不是外部步数。

**3. Q：** 工具抛异常，图会中断吗？
**A：** 默认不会：`handle_tool_errors=True` 把异常转成带详情的 ToolMessage；设 `False` 或类型不匹配时才上抛打断图。

**4. Q：** 工具需要读图状态怎么办？
**A：** 签名里声明 `runtime: ToolRuntime`，ToolNode 注入 state、context、store、tool_call_id 等现场，对模型侧 schema 隐藏（见 [[5.1 工具定义与绑定：@tool 与 bind_tools]]）。
