# create_react_agent 与 prebuilt 组件

## 现状：弃用与接替

create_react_agent 原属 `langgraph.prebuilt`，返回一张编译好的图（CompiledStateGraph）。LangGraph v1 起官方将其弃用，接替者是 `langchain.agents.create_agent`——等价的智能体工厂加灵活的 middleware 系统，仍跑在 LangGraph 上。迁移要点：`prompt=` 改名 `system_prompt=`；`AgentState` 及各变体（含 Pydantic 专版）统一为 `langchain.agents.AgentState`；`ValidationNode` 移除，create_agent 里工具自动校验输入。

```python
from langchain.agents import create_agent      # 现行写法

agent = create_agent(
    model="openai:gpt-5.5",                    # "提供商:模型" 字符串，或已初始化的模型实例
    tools=tools,                                # 任意可调用、LangChain 工具或工具字典
    system_prompt="...",                        # 对应 create_react_agent 的 prompt 参数
)
```

## 行为：它替你搭了哪张图

官方把智能体拆成 Model + Harness（harness：循环周围的一切——prompt、工具、塑造模型行为的 middleware）。create_agent 搭的就是 [[5.2 ToolNode 与工具循环]] 手搓的那条循环：agent 节点套上 prompt 调 LLM；AIMessage 带 tool_calls 时，tools 节点（内部就是 ToolNode）逐个执行、追加 ToolMessage；agent 节点再调 LLM，循环到不再出现 tool_calls，以 `{'messages': [...]}` 收尾。

循环带步数保护：`remaining_steps` 约等于 recursion_limit 减去已执行步数；低于 2 且还有工具调用未处理时，智能体返回一条固定的道歉消息，而不是抛递归错误。

## 参数

```python
create_agent(
    model,                    # 模型；create_react_agent 另接受 (state, runtime) -> 模型 的可调用
    tools,                    # 工具列表或 ToolNode；空列表 = 无工具调用的单 LLM 节点
    system_prompt=None,       # str / SystemMessage，前置到消息列表；也可给接收完整 state 的可调用
    middleware=[],            # 中间件：摘要、重试、PII、人工介入、子智能体、待办清单等，逐关注点组合
    state_schema=None,        # AgentState 子类加业务字段（如 user_id、call_count）；不支持 Pydantic state
    response_format=None,     # 结构化输出 schema，结果落在 structured_response 键，见 5.3
    checkpointer=None,        # 检查器，按 thread_id 持久化会话历史（如 InMemorySaver()）
    context_schema=None,      # 运行期上下文 schema，调用时 context=Context(user_id=...) 注入
    name=None,                # 图名，嵌为子图参与多智能体系统时用（如 name="research_assistant"）
)
```

create_react_agent 时期的一批参数由 middleware 承接或简化：`pre_model_hook` / `post_model_hook`（模型前后固定挂点，做裁剪、摘要、人工介入、护栏、校验）、`interrupt_before` / `interrupt_after`（在 `"agent"` 或 `"tools"` 节点前后停图）、`store`（跨 thread 持久化）。`response_format` 语义两代一致：循环结束后单独一次 LLM 调用按 schema 生成结果，落在最终 state 的 `structured_response` 键，要求模型支持 with_structured_output（[[5.3 Structured Outputs]]）。

## 什么时候手搓

官方对 ToolNode 的定位给出分界：标准智能体用 create_agent；需要细粒度控制——自定义路由、专门的错误处理、非标准智能体架构——用 ToolNode 自己组图。具体判断：治理要插在循环中间的任意位置（执行前冻结参数、执行后落记录），StateGraph 手搓随意摆节点，pre/post model hook 只覆盖模型前后两个固定位置；循环本身要改（并行形态、路由规则）也是手搓——预建智能体改不了内部结构。

middleware 是第三条路：各关注点一个 middleware，可组合，不动图结构改 harness 行为——改行为不改结构时的首选。

> [!example] 实践例子
> 预建智能体把「提议 → 执行 → 回填」整条循环连同 prompt、state 一起打包。健康管理项目要在自定义 state 与执行治理上收权，走的对照路径是手搓循环原语加自建 Tool Runtime——参数快照冻结、幂等键、护栏、执行记录（[[4.统一 Tool Runtime]]）；模型可见的工具面按领域与执行深度收敛，见 [[3.工具能力设计与 Tool Surface]] 与 [[8.能力渐进装载]]。

## 边界问答

**1. Q：** create_react_agent 和 create_agent 是什么关系？
**A：** 同一工厂的新旧两代。create_react_agent 在 `langgraph.prebuilt`，LangGraph v1 起弃用；create_agent 在 `langchain.agents`，等价能力加 middleware 系统，仍跑在 LangGraph 上，调用点 `prompt=` 改 `system_prompt=`。

**2. Q：** 预建智能体和手搓的选择标准？
**A：** 官方分界：标准智能体用 create_agent；自定义路由、专门错误处理、非标准架构用 ToolNode 组图（[[5.2 ToolNode 与工具循环]]）。只想改行为不改结构时，先看 middleware 够不够。

**3. Q：** response_format 的结构化输出什么时候生成？
**A：** 循环结束后单独一次 LLM 调用，结果落在最终 state 的 `structured_response` 键；要求模型支持 with_structured_output（[[5.3 Structured Outputs]]）。

**4. Q：** 步数耗尽会发生什么？
**A：** `remaining_steps` 低于 2 且仍有工具调用待处理时，返回固定的道歉消息而不是抛递归错误——调用方要自己识别这种未完成的终态。
