# Structured Outputs

## with_structured_output：让输出匹配 schema

结构化输出解决的问题：模型的自然语言回复要先解析才能进程序。`with_structured_output` 让模型按给定 schema 返回数据——校验过的 Pydantic 实例或字典，而不是一段要解析的文本：

```python
model_with_structure = model.with_structured_output(Movie)
model_with_structure.invoke(...)
# Pydantic schema 时返回 Movie 实例，不再是 AIMessage
```

## 三种 schema 写法

```python
from pydantic import BaseModel, Field
from typing_extensions import Annotated, TypedDict

class Movie(BaseModel):                     # 写法一：Pydantic，功能最全
    title: str = Field(description="The title of the movie")  # 字段描述进 schema
    cast: list[Actor]                       # 支持嵌套 schema（Actor 是另一个 BaseModel）

class MovieTD(TypedDict):                   # 写法二：TypedDict，轻量
    title: Annotated[str, ..., "电影标题"]   # 描述用 Annotated 给出
    cast: list[str]

json_schema = {...}                         # 写法三：原始 JSON Schema 字典，需配 method="json_schema"
```

Pydantic 返回经过校验的模型实例，支持校验、字段描述、嵌套，是首选；TypedDict 返回普通 dict，没有运行时校验；JSON Schema 字典直接给原生 schema。

## method 参数：三种实现方式

`method` 决定框架用什么机制约束输出：

- `json_schema`：用提供商专门的结构化输出能力，模型原生按 schema 生成。
- `function_calling`：强制模型发起一次符合 schema 的工具调用，从工具调用参数里取输出——适合没有原生结构化输出的模型。
- `json_mode`：更早的方式，只保证输出是合法 JSON，schema 本身要写进 prompt 让模型遵守。

## include_raw：拿到解析前的原始消息

```python
model_with_structure = model.with_structured_output(Movie, include_raw=True)
# 返回 {'raw': AIMessage, 'parsed': Movie, 'parsing_error': None}
```

`raw` 是解析前的 AIMessage（要 token 数等元数据时用），`parsed` 是解析结果，`parsing_error` 成功时为 None、失败时是异常对象。

## 校验与错误重试

校验发生在哪取决于 schema：Pydantic 自动校验，字段不匹配直接报 ValidationError；TypedDict 和 JSON Schema 没有运行时校验，需要自己验。模型这一层没有内置的「校验失败带错误重试」——重试机制在智能体层：create_agent 的 `response_format` 用 ToolStrategy 时 `handle_errors` 默认开启，校验失败把错误反馈写进 ToolMessage 让模型再试，也处理「模型一次返回了多份结构化响应」的情况；这个参数还能给自定义文案（str）、匹配的异常类型（单个或元组）、`Callable[[Exception], str]`，或 `False` 关闭重试。ToolStrategy 之外还有 ProviderStrategy，走提供商原生结构化输出（可选 `strict` 开严格模式）。这层机制的参数细节见 [[5.4 create_react_agent 与 prebuilt 组件]]。

一个限制：对已经 bind_tools 过的模型再用 with_structured_output 不受支持（bind_tools 见 [[5.1 工具定义与绑定：@tool 与 bind_tools]]）。

> [!example] 实践例子
> 框架在模型口（with_structured_output）与智能体口（response_format）各给一层结构化输出，靠 schema 约束模型的提议。健康管理项目把这种约束前置到工具面设计——工具参数即结构化契约（[[3.工具能力设计与 Tool Surface]]），运行时对参数再做快照冻结与校验，收进自建 Tool Runtime（[[4.统一 Tool Runtime]]）。

## 边界问答

**1. Q：** method 三个值怎么选？
**A：** 模型和提供商支持原生结构化输出就用 `json_schema`；没有原生能力用 `function_calling`，借工具调用的参数通道取结构化输出；`json_mode` 只保证 JSON 合法、schema 要自己进 prompt，是旧前缀。

**2. Q：** 解析失败时输出什么？
**A：** `include_raw=True` 时返回字典里的 `parsing_error` 带着异常对象，可以自查；不开 include_raw、用 Pydantic schema 时，校验错误直接抛出。自动带着错误反馈重试是智能体层 ToolStrategy 的行为，不是模型层的。

**3. Q：** with_structured_output 和 bind_tools 能同时用吗？
**A：** 官方文档明确不支持对已 bind_tools 的模型再套 with_structured_output；既要工具调用又要最终结构化结果时，用智能体层的 response_format（[[5.4 create_react_agent 与 prebuilt 组件]]）。

**4. Q：** 为什么不用输出解析器解析自然语言？
**A：** 解析自然语言是事后猜格式，结构化输出在生成时就把输出约束在 schema 上，出错面小得多；智能体层还有 handle_errors 兜底重试，解析失败不会直接炸掉调用方。
