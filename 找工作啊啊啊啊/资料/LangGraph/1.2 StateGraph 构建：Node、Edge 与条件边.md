# StateGraph 构建：Node、Edge 与条件边

## 三件套：State、Node、Edge

建一张图只需要三类东西：State 是共享数据结构，代表应用当前快照，通常用 TypedDict 定义，也支持 Pydantic 模型（递归校验）与 dataclass（可给默认值）；Node 是编码逻辑的函数，接收当前 state，做完计算或副作用后返回对 state 的更新；Edge 决定接下来执行哪个节点，可以是固定转移，也可以是按 state 分支的条件边。官方口诀：nodes do the work, edges tell what to do next——节点干活，边指路；两者都只是函数，里面可以是一次 LLM 调用，也可以是普通代码。

State schema 的每个键在运行时是一个 channel（带版本号与更新策略的通信槽位），节点返回的 dict 不是「修改状态」而是「向 channel 提交写入」；写入怎么合并、引擎怎么按 superstep 轮次调度，唯一归属见 [[2.1 LangGraph 检查点与 Channel]]。

## add_node：注册节点

```python
from langgraph.graph import StateGraph, START, END
from typing_extensions import TypedDict

class State(TypedDict):
    messages: list      # 图状态的键：所有节点共享读写，运行时即一个 channel
    plan_status: str    # 默认策略 LastValue：后写覆盖先写

def prepare(state: State):
    # 节点 = 普通 Python 函数，入参是当前 state
    # 返回「部分更新」：只写要改的键，不必返回整个 schema
    return {"plan_status": "preparing"}

builder = StateGraph(State)             # 建图第一步：传入 State schema
builder.add_node("prepare", prepare)    # 显式命名注册
builder.add_node(my_node)               # 不命名时默认用函数名作为节点名
```

add_node 背后把函数包成 RunnableLambda，自动获得批量、异步与原生追踪支持，同步异步函数都行。节点还可按需声明第二、三个参数：config（含 thread_id 与 tracing 标签）和 runtime（运行时上下文、store、stream_writer 等）。返回值两种形态：更新 dict（进入 channel 写入），或 Command 对象（状态更新与路由合并成一步，见下文）。

## add_edge 与 START / END

普通边 add_edge("a", "b") 表示 a 执行完无条件去 b。START 是虚拟节点，代表「用户输入进入图」的起点，add_edge(START, "a") 声明入口；END 是虚拟终止节点，add_edge("a", END) 表示 a 之后图停；没有更多可执行节点时图自然终止。一个节点可以有多条出边：所有目标节点在下一个 superstep 并行执行；多入口同理，从 START 连多条边就是多个并行入口。

## add_conditional_edges：条件边

条件边在节点执行完之后调用一个路由函数，由返回值决定去向：

```python
def route(state: State):
    # 路由函数同样接收当前 state，只决定去向、不更新状态
    if state["plan_status"] == "wait_human":
        return "confirm"     # 返回单个节点名：下一步去 confirm
    return END               # 也可以直接返回 END 终止

builder.add_conditional_edges("prepare", route)
# 第三个参数可选：路由返回值 → 节点名的映射表，
# 路由函数返回 True/False 或自定义枚举时用它翻译成真实节点名
builder.add_conditional_edges("check", route, {True: "node_b", False: "node_c"})
```

路由函数返回节点名、节点名列表（列表 = 下一轮多节点并行）或 END；返回值默认直接当节点名用，传映射 dict 可翻译。条件边也能从 START 挂（add_conditional_edges(START, fn)），实现按输入选起点的条件入口。路由函数还可以返回 Send("节点名", 状态) 对象的列表，为每个元素生成一份独立输入的并行执行——用于 map-reduce 这类边数运行时才知道的场景。

## Command：节点内路由

节点可以直接返回 Command(update={...}, goto="next")，把状态更新与控制流合并，goto 的效果等价于条件边。两条官方约束：返回 Command 的节点要写返回类型注解 Command[Literal["next"]]，供图渲染与校验识别可达节点；Command 加的是动态边，不会取消 add_edge 声明的静态边——同一节点混用两种路由会两条路都执行，只能二选一。Command 还有 resume 参数，用于中断后带值恢复，机制见 [[2.1 LangGraph 检查点与 Channel]]。

## compile 与调用

图建好后必须 compile() 才能用：编译做基本结构检查（如孤立节点），也是挂运行时参数的位置——checkpointer、断点都传给 compile。编译产物是一个 Pregel 实例（LangGraph 的执行运行时），用 invoke / stream 及异步变体驱动：

```python
graph = builder.compile(checkpointer=checkpointer)   # 不持久化时可省略参数

graph.invoke({"messages": [...]}, config)    # 同步跑完，返回最终 state dict
for update in graph.stream({"messages": [...]}, config):
    ...                                       # 逐步产出各节点的中间更新
```

invoke 的输入至少给一个 state 键；输出默认是最终 state，定义了 output schema 时按其过滤。配了 checkpointer 后，config 里的 thread_id 标识一条执行历史，是多轮对话与恢复的钥匙。stream 的多种模式属于流式板块，不在本篇展开。

> [!example] 实践例子
> 每日计划是一张预编排的 StateGraph：参数准备 → 冲突检查 → 生成草稿 → wait_for_human（interrupt）→ 提交，下一步去哪由边和路由函数决定，不靠模型现场发挥。端到端走查看 [[8.一次完整的 DailyPlan]]，预编排与自由编排的分界见 [[3.执行模型与任务边界]]。

## 边界问答

**1. Q：** 节点返回的 dict 是新的完整状态吗？
**A：** 不是，是部分更新。节点只返回要改的键，每个键按自己的 reducer 合并进现有状态，默认策略是覆盖该键，没写的键保留原值。要清空一个带合并策略的键，返回空值会被合并进去而不生效，得用 Overwrite 显式覆盖。

**2. Q：** 条件边和节点返回 Command，用哪个？
**A：** 只路由不更新状态用条件边；要同时更新状态并路由用 Command（update + goto 一步完成）。同一节点只用一种机制：静态边与 Command 混用会两条路都执行。

**3. Q：** 不 compile 直接调用会怎样？
**A：** 官方要求必须先 compile。编译既做结构检查（孤立节点等），也是传入 checkpointer、断点等运行时参数的位置；编译产物才是可 invoke / stream 的对象。

**4. Q：** 一张图能有多个入口吗？
**A：** 能。从 START 连多条边，目标节点在第一个 superstep 并行执行；也可以用 add_conditional_edges(START, fn) 做条件入口，按输入选择起点。
