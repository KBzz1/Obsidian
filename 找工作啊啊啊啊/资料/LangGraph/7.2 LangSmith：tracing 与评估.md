# LangSmith：tracing 与评估

## 开启 tracing：一个环境变量

LangSmith 是 LangChain 官方的观测与评估平台，核心数据是 trace——一次请求从输入到最终输出、中间每一步的完整记录。对 LangChain/LangGraph 代码，追踪不需要改代码，设两个环境变量就自动开启：

```bash
export LANGSMITH_TRACING=true        # 开关：LangChain/LangGraph 代码自动上报 trace
export LANGSMITH_API_KEY="<占位>"     # 平台 API Key（值不落知识库，此处保持占位）
```

可选变量：`LANGSMITH_PROJECT` 指定项目名，不设则进 default 项目；非 US 区域必须设 `LANGSMITH_ENDPOINT`（eu/apac/aws 各有端点，URL 结尾不能带斜杠，否则认证失败）。

非 LangChain 的自有代码要手工埋点：`@traceable` 装饰器把函数记为一个 run，`run_type` 指定类型（如 `"tool"`）；`wrap_openai` 这类 wrapper 包住 SDK 客户端后，每次调用自动成为嵌套 run。被装饰函数内部发生的模型调用、工具调用会自动挂到正确的父级上下文里。

## trace 与 run：一棵 runs 树

run 是单个工作单元——调一次 LLM、格式化一次 prompt、检索一次文档，相当于 OpenTelemetry 里的 span。trace 是一次操作的全部 run 的集合，靠唯一的 trace ID 绑在一起，组织形态是树：顶层是根 run，它内部发生的调用逐层嵌套成子 run。LangGraph 应用的图执行也在这个模型下呈现：每次图调用形成一条 trace，节点内发生的模型调用、工具调用作为嵌套 run 逐层可点（官方文档给了 agent/tools 两节点应用的公开示例 trace 可对照）。

两条规模边界：单条 trace 上限 25,000 个 run，超出部分被拒收；SaaS 版 trace 数据自摄取起保留 180 天。

## 在 trace 里看什么

UI 里 Threads / Traces / Runs 三个 tab 切换列表（Threads 与 Turns 视图只对带 `thread_id` metadata 的 run 生效），点开一条 trace 后有三个视图：

- **Messages**：把整条轨迹按回合渲染，每回合一块——模型回复、它触发的 tool calls、返回的工具结果；块上方元数据行给 token 用量、成本、模型名。子智能体（subagent）作为独立动作内联展开，扩展思维的思维链折叠显示。
- **Turns**：每回合的结构摘要，展示根 run 的输入输出，适合没有可渲染消息的集成或快速总览。
- **Details**：调试层，看单个 run 的输入、输出、metadata、时间、错误与子 run。`run_type="llm"` 的 run 会渲染 token 数与延迟；`run_type="tool"` 的工具消息自动展开；`run_type="retriever"` 把检索到的文档连同内容内联渲染。

Details 视图还能把一条 trace 加进 dataset 当评估样本，或加进标注队列转人工复查——这是观测通往评估的入口。成本方面，主要 provider 的 LLM token 用量与成本由平台自动记录。

## 评估：dataset + evaluator

跑一次评估要三样东西：dataset（测试输入，可带参考输出）、target（被测应用代码）、evaluator（打分函数）。工作流四步：建数据集、定义评估器、跑实验、分析结果。样本来源可以是手工构造、生产 trace 回捞或合成生成；把生产里失败的 trace 加进数据集，失败就变成可重复的测试。

```python
client = Client()
dataset = client.create_dataset(dataset_name="Sample dataset")   # 建数据集
client.create_examples(dataset_id=dataset.id, examples=[          # 写样本
    {"inputs": {"question": "..."},                               # 测试输入
     "outputs": {"answer": "..."}}])                              # 参考输出（可选）

def target(inputs: dict) -> dict:                                 # 被测应用：进 inputs 出 outputs
    ...

def correctness_evaluator(inputs, outputs, reference_outputs):    # 评估器：拿三个根键打分
    ...

results = client.evaluate(
    target,
    data="Sample dataset",              # 数据集名：逐条喂给 target
    evaluators=[correctness_evaluator], # 可以挂多个评估器
    experiment_prefix="first-eval",     # 实验名前缀
    max_concurrency=2,                  # 并发
)
```

评估器接收三个根键：`inputs`（进了 target 什么）、`outputs`（target 返回什么）、`reference_outputs`（数据集里的参考答案）。`evaluate()` 的产物是一次 experiment，UI 里按 Inputs / Reference Output / Outputs 列表逐样本对比。评估器分四类：human（人工）、code（代码规则）、LLM-as-judge（模型判分）、pairwise（两两对比）；确定性判断走代码规则，开放式输出走 judge。评估不限于离线：在线评估器可以挂在生产 trace 上自动跑，配合过滤与采样控制成本。

## LLM-as-judge

judge 评估器面向「没有唯一正确答案」的开放式输出。SDK 路线用 `openevals` 包的 `create_llm_as_judge`：

```python
evaluator = create_llm_as_judge(
    prompt=CORRECTNESS_PROMPT,        # 判分 prompt：带 inputs/outputs/reference_outputs 变量的 f-string
    model="openai:o3-mini",           # 当裁判的模型
    feedback_key="correctness",       # 分数挂载的 feedback key
)
```

UI 路线在 Evaluators 页从零建或套模板（按 Security、Safety、Quality 等分类），prompt 变量用下拉映射到输入/输出/参考输出的对应部分；打分标准（feedback key）分 Boolean、Categorical、Continuous 三种类型。人工对判分的纠正可以自动插回 prompt 当 few-shot 样本，让裁判对齐人类偏好。

## 与 LangGraph 衔接：查询与重放

观测数据可以被程序取回：`client.list_runs()` 按项目、run 类型、时间、错误、tag、feedback 等条件查 run，`client.read_run(id)` 读单条（含输入输出），配合 metadata 里的 `thread_id` 过滤能捞出一个会话的全部轨迹。

LangGraph 带检查点运行时，观测可以接回执行本身：LangSmith 文档明确「用了 checkpointing 的话，可以从 LangSmith 取回 trace 并在本地重放调试」。重放走 LangGraph 的时间旅行——`get_state_history` 找到历史检查点，`graph.invoke(None, 该检查点的 config)` 从该点继续。注意重放不是读缓存：检查点之前的节点不再执行（结果已存），之后的节点会真跑，LLM 调用、API 请求、中断都可能给出不同结果。

> [!example] 实践例子
> 健康管理项目不接 LangSmith：观测自建 Trace——TraceSpan 只落在工程边界、持 `invocation_id` / `retrieval_id` / `context_id` 等 Record 引用而不复制内容，不建第二套运行时数据库（见 [[3.Task、Run 与 Trace 身份关联]]）；评估用固定 EvalCase 夹具驱动上下文与 Evidence、Tool、Trajectory、Final Task 四层分层评估，judge 只评开放式结果、不看全轨迹（见 [[8.Agent 分层评估]]）。取舍边界在于：LangSmith 把采集、存储、查询与评估闭环整个收进产品；项目把同样的闭环留在自建边界内。

## 边界问答

**1. Q：** 接 LangSmith 要不要改代码？
**A：** LangChain/LangGraph 代码不用，`LANGSMITH_TRACING=true` 即自动追踪；只有非 LangChain 的自有代码才需要 `@traceable` 装饰器或 `wrap_openai` 这类 wrapper 手工埋点。

**2. Q：** trace 和 run 是什么关系？
**A：** run 是单个工作单元（相当于 OpenTelemetry 的 span），trace 是一次操作的全部 run 集合，靠唯一 trace ID 绑定，组织成树；根 run 收顶层输入输出，内部调用逐层嵌套。

**3. Q：** token 用量和成本从哪里看？
**A：** `run_type="llm"` 的 run 在 Details 视图渲染 token 数与延迟；Messages 视图每回合的元数据行带 token 用量与成本；主要 provider 的成本由平台自动记录，无需手工上报。

**4. Q：** 什么情况用 LLM-as-judge，什么情况用代码规则？
**A：** 文档把评估器分 human / code / LLM-as-judge / pairwise 四类：能确定性判定的走代码规则；开放式、无唯一正确答案的输出走 judge，其打分标准按 Boolean / Categorical / Continuous 三种 feedback 类型声明。

**5. Q：** 重放（replay）是把历史轨迹读出来看吗？
**A：** 查询（`list_runs` / `read_run`）只是读数据；LangGraph 的检查点重放是继续执行——检查点之前的节点不重跑（结果已保存），之后的节点会重新执行，LLM 调用与 API 请求都会真发并可能返回不同结果。

**6. Q：** 生产的失败案例怎么变成回归测试？
**A：** 在 Details 视图把失败 trace 加进 dataset 作为样本，再对数据集跑实验；LangSmith 的评估文档把「捕获失败 trace → 加进数据集 → 建针对性评估器 → 离线验证 → 重新部署」描述为标准反馈闭环。
