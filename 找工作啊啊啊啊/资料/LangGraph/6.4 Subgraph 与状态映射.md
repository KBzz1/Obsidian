# Subgraph 与状态映射

## subgraph：把编译好的图当节点用

subgraph（子图）就是被当作节点用在另一张图里的图：把编译好的子图交给父图的 add_node，父图把它当一个普通节点调用。官方列的用途：多智能体系统、跨图复用一组节点、团队分工——只要子图接口（输入输出 schema）稳定，父图与子图可以各自独立构建。

父子图怎么交换 state，取决于两边 state schema 的关系，官方给了两种方式。

## 方式一：共享 state 键，直接当节点

父图与子图的 schema 有公共键（多智能体系统里最常见的 messages）时，编译好的子图直接传给 add_node，不需要包装函数——子图自然地读共享键、写共享键。子图还可以有自己的私有键，父图看不见：

```python
class SubgraphState(TypedDict):
    foo: str   # 与父图共享的键
    bar: str   # 子图私有键，父图读不到

def subgraph_node_2(state: SubgraphState):
    return {"foo": state["foo"] + state["bar"]}   # 消费私有键，写回共享键

subgraph = subgraph_builder.compile()             # 用 SubgraphState 构建并编译

builder = StateGraph(ParentState)                 # 父图 state 只有 foo
builder.add_node("node_2", subgraph)              # 编译好的子图直接当节点用
```

Graph API 对共享键有一条要求：子图节点要向父子共享的键发送更新时，该键必须定义 reducer——并发更新同一键时靠它合并，机制即 [[2.1 LangGraph 检查点与 Channel]] 里的更新策略。

## 方式二：schema 不同，写转换函数

父子 schema 没有公共键——比如要让每个智能体持有私有消息历史——时，在节点函数里做映射：把父 state 变换成子图输入，调用子图，把输出变换回父 state：

```python
def call_subgraph(state: State):
    # 把父 state 变换成子图 state
    subgraph_output = subgraph.invoke({"bar": state["foo"]})
    # 把子图响应变换回父 state
    return {"foo": subgraph_output["bar"]}
```

这种包装可以套多层（父 → 子 → 孙）：每一层只看得到自己 schema 里的键，父够不到孙的键，孙也够不到父的。swarm 里给智能体配私有 state 键做隔离，用的就是这层底层写法（见 [[6.3 Swarm 与 handoff]]）。

## checkpointer 与命名空间

子图的持久化由它自己 compile 时的 checkpointer 参数决定，官方分三档：

```text
子图 checkpointer 三档
    None（默认，per-invocation）  # 每次调用全新；继承父图 checkpointer 以支持中断与持久执行，
                                  # 父图必须带 checkpointer 编译
    True（per-thread）            # 同一 thread 跨调用积累状态，子智能体记得之前几轮；
                                  # 不支持同一子图并行调用（checkpoint 冲突）
    False（stateless）            # 完全不落检查点，子图像普通函数
```

每个子图调用的检查点存在自己的命名空间（namespace）里：同一子图的多个并行调用互不串档，父子图也可以各自带独立的 checkpointer 与 thread_id。这个命名空间就是 [[2.1 LangGraph 检查点与 Channel]] 里 CheckpointTuple 的 config 中 checkpoint_ns 字段的来源——快照靠它区分归属哪层图。要稳定的命名空间隔离，官方建议把每个子智能体包进自己的 StateGraph 并给唯一节点名。

## 子图内部对外隐藏

两种方式下，子图内部 state 都不对父图暴露：共享键模式里父图只看得到公共键，转换函数模式里只看得到 wrapper 的返回值。要看子图 state 需显式声明：get_state(config, subgraphs=True)，且要求子图静态可发现——作为节点加入、或在节点函数内调用；藏在工具函数里调用的子智能体不满足条件。

## subgraph 当团队

多智能体的自然组合：一个子图封装一个智能体或一支团队，上层 supervisor 把每个团队当一个 worker 调度。官方 handoffs 指南给的判断标准：节点本身是带反思、检索等步骤的复杂图时，才值得做成子图。supervisor 库的多层层级就是这么搭的——下层 supervisor 整体 compile(name=...) 后作为上层 supervisor 的 worker（见 [[6.2 Supervisor 模式与委派]]）。

> [!example] 实践例子
> 健康管理项目的根状态图（Root StateGraph）负责编排与确定性控制节点，领域智能体（Domain Agent）各自是独立执行单元，形态接近「子图当 worker」；但父子数据不走共享 state 键，而是 DomainTask / AgentResult 结构化协议加 Runtime State / Agent Working State 分层，见 [[4.Supervisor 架构与委派]]、[[6.通信协议与 Artifact]]。

## 边界问答

**1. Q：** 什么时候直接 add_node，什么时候写转换函数？
**A：** 父子 state schema 有公共键，就把编译好的子图直接交给 add_node；没有公共键（或要给智能体私有历史）就写 wrapper 做双向映射。

**2. Q：** 子图的检查点存在哪？
**A：** 看子图 compile 时 checkpointer 的三档：None 每次调用全新但继承父图 checkpointer（父图必须带 checkpointer）；True 同 thread 跨调用记忆但不支持同子图并行；False 不落检查点。每份快照存在自己的命名空间里。

**3. Q：** 父图能不能看到子图内部状态？
**A：** 默认只看得到共享键或 wrapper 返回值；显式取用 get_state(config, subgraphs=True)，前提是子图静态可发现，藏在工具函数里的不行。

**4. Q：** 子图往共享键写更新要注意什么？
**A：** 该键必须定义 reducer——子图节点与父图节点并发写同一个共享键时，靠 reducer 合并，否则更新无法处理。
