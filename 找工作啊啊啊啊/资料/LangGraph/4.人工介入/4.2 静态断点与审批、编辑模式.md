# 静态断点与审批、编辑模式

## 静态断点：按节点名声明的停点

静态断点在图定义处声明，不改节点代码：compile 时传 interrupt_before 与 interrupt_after 两个列表，图运行到列表内节点执行之前（或之后）停下。前提与动态中断相同：必须有 checkpointer，断点现场才有处保存。

```python
graph = builder.compile(
    interrupt_before=["node_a"],          # 进入 node_a 之前停：适合审它将读写的状态
    interrupt_after=["node_b", "node_c"],  # node_b、node_c 执行完之后停：适合审它们刚产出的中间结果
    checkpointer=checkpointer,            # 断点现场随检查点持久化，启用断点的前提
)
config = {"configurable": {"thread_id": "some_thread"}}

graph.invoke(inputs, config=config)   # 第一次运行：跑到第一个断点停
graph.invoke(None, config=config)     # 续行：输入 None 表示不给新输入，从检查点继续，
                                      # 跑到下一个断点再停
```

断点也可以在调用时作为运行时参数传入，每次调用可以换：

```python
graph.invoke(
    inputs,
    interrupt_before=["node_a"],       # 仅本次调用生效的断点配置
    interrupt_after=["node_b", "node_c"],
    config=config,
)
graph.invoke(None, config=config)      # 续行方式不变
```

与动态中断的差别在声明位置：静态断点写在图定义或调用参数里，按节点粒度、无条件生效，不动节点函数；interrupt() 写在节点内部，位置任意、可按条件触发。官方对分工有明确表态——原文是 Static interrupts are not recommended for human-in-the-loop workflows. Use the interrupt function instead——静态断点定位调试与单步执行（LangSmith Studio 界面里也能设），生产环境的人工介入流程用 interrupt()。

## 审批（approve）：看状态再决定放不放行

审批模式的骨架是停下、读状态、决定续行或终止。配静态断点时用 get_state 取当前线程的最新快照，通过就用 None 续行；不续行，线程停在断点检查点上，不产生后续执行，等效终止。

```python
state = graph.get_state(config)   # 当前线程的最新状态快照
state.values                      # 各 channel 当前值——审批要审的内容
state.next                        # 待执行节点元组——图停在哪、下一步是谁

if 审批通过:
    graph.invoke(None, config=config)   # 放行：从断点检查点继续执行
```

配动态中断的审批是官方文档给的标准模式：节点内 interrupt() 发出问题与待审细节，恢复值直接驱动路由分支：

```python
from typing import Literal
from langgraph.types import interrupt, Command

def approval_node(state: State) -> Command[Literal["proceed", "cancel"]]:
    is_approved = interrupt({            # 中断载荷：问题 + 待审细节
        "question": "Do you want to proceed with this action?",
        "details": state["action_details"],
    })
    if is_approved:
        return Command(goto="proceed")   # resume 值 True：放行到 proceed 分支
    return Command(goto="cancel")        # resume 值 False：路由到 cancel 分支
```

## 编辑（edit）：改完状态再继续

编辑模式在审之外还要改：用 update_state 向指定检查点写入新值，再从写入后的检查点续行。update_state 不回滚历史——它从指定检查点分叉出一份新检查点，原历史原样保留；写入经目标节点的 writer（含 reducer）生效，并把该节点记为这次更新的产生者，之后从该节点的后继继续。完整语义（as_node、并行分支歧义、与重放的配合）归属 [[2.3 时间旅行：get_state、update_state 与重放]]，这里只记人工介入场景的基本形态：

```python
fork_config = graph.update_state(
    checkpoint_config,             # 从哪个检查点分叉（断点处快照的 config）
    values={"topic": "chickens"},  # 要改写的 channel 值
    as_node="generate_topic",      # 把这次写入记在哪个节点名下——
                                   # 并行分支有歧义或线程刚创建时需要显式指定
)
graph.invoke(None, fork_config)    # 从分叉出的检查点继续执行
```

动态中断体系内的编辑更轻：审阅前编辑（review and edit）让 resume 值本身就是改好的内容，节点恢复后写回 state：

```python
def review_node(state: State):
    edited_content = interrupt({                      # 中断载荷：审阅指令 + 当前生成内容
        "instruction": "Review and edit this content",
        "content": state["generated_text"],
    })
    return {"generated_text": edited_content}         # resume 值（编辑后的文本）写回 state

# 图外部：人工编辑后的文本作为 resume 值恢复
graph.stream_events(Command(resume="The edited and improved text"), config=config, version="v3")
```

工具调用场景同构：interrupt() 放进 @tool 函数里，工具真正执行前停下；恢复值是一个 dict，可以批准、取消，也可以改写工具参数后再执行。

## 审阅（review）：读中间产物再决定

审阅不改任何东西，只读。get_state_history 枚举同一线程的历史检查点（按时间倒序），用 state.next 定位「某个节点执行前」的那份快照，读快照里的 values 看中间产物，再决定续行、分叉还是不动作：

```python
history = graph.get_state_history(config)                       # 历史快照，倒序
before_joke = next(s for s in history if s.next == ("write_joke",))  # 按「下一步是谁」定位快照
replay_result = graph.invoke(None, before_joke.config)          # 从该快照续行/重放
```

重放有一条语义必须记住：从历史检查点 invoke(None, config) 不是缓存回放，检查点之后的节点真实重新执行——LLM 调用、外部请求、interrupt 都会再次触发并可能给出不同结果。官方原话是 interrupts are always re-triggered during time travel：重放到含 interrupt() 的节点会再次暂停，等一次新的 Command(resume=...)。

## 静态与动态怎么组合

按官方口径，组合选择收敛成三条。生产人工介入流程一律 interrupt()：停点语义在节点内部，载荷、恢复、Command(goto=...) 路由闭环完整。调试排查用静态断点：不改节点代码、按节点粒度停，配合 get_state 逐节点看状态，调用期参数适合临时加断点。改历史状态用 update_state：静态断点停下后改状态再 invoke(None) 续行，是编辑模式的完整形态；动态中断场景下多用于分叉——两个 interrupt() 先后问过两轮，想改后面那轮的答案又不想重问前面那轮，就在两份中断现场之间的检查点上分叉再继续。

一个组合时的边界：子图默认与父图共享继承的 checkpointer，整个子图只是父图的一次 superstep，只留一个父级检查点，时间旅行进不了子图内部节点之间；给子图单独配 checkpointer=True 后子图才有逐步检查点，能用 get_state(config, subgraphs=True) 取到子图快照、在子图内部做分叉。

> [!example] 实践例子
> 审批模式里框架只负责「停在哪、怎么继续」，批的是什么、怎么防重复执行是业务层的活——健康管理项目把审批对象固化为带冻结参数的工具调用实例，批准的是「替换为 D200 v3」这个已确定的动作而不是一段聊天文本，恢复前还要过版本与前置条件校验，见 [[6.HIL 与恢复]]、[[5.护栏]]。

## 边界问答

**1. Q：** 静态断点和动态中断怎么选？
**A：** 官方明确：静态断点不推荐用于人工介入流程，定位是调试与单步执行；生产人工介入用 interrupt()。要按节点粒度停、又不想改节点代码（比如排查一张陌生的图）时用静态断点。

**2. Q：** 静态断点续行为什么输入传 None？
**A：** None 表示不给新输入、从检查点继续跑到下一个断点。动态中断的对应输入是 Command(resume=...)——resume 值要进节点成为 interrupt() 的返回值；静态断点没有节点内断点，也就没有要递交的答案。

**3. Q：** update_state 改状态会抹掉原来的历史吗？
**A：** 不会。它从指定检查点分叉出一份新检查点，原历史原样保留；回退与分叉的完整语义见 [[2.3 时间旅行：get_state、update_state 与重放]]。

**4. Q：** 从断点前的检查点重放，interrupt 还会触发吗？
**A：** 会。重放不是读缓存，检查点之后的节点真实重新执行，LLM 调用、外部请求、interrupt 都会再次触发并可能给出不同结果；含 interrupt() 的节点会再次暂停等新的 Command(resume=...)。

**5. Q：** 时间旅行能进到 subgraph 内部吗？
**A：** 默认不能：子图与父图共享继承的 checkpointer 时，整个子图是父图的一次 superstep，只留一个父级检查点。给子图单独配 checkpointer=True 后，子图有自己的逐步检查点，才能进入其内部做检查与分叉。
