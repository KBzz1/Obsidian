# 短期记忆：thread 内 state 与消息管理

## 短期记忆是什么

短期记忆指局限在单个 thread 内的记忆。thread 是把一组交互归成一个会话的标识——像一封邮件往来的所有回复共用一个 thread_id，同一个 thread 下的多次调用看到同一份图状态。短期记忆的主要内容是这份状态里的消息历史：当前会话说到哪了、双方都说过什么。

消息历史由 checkpointer 按 thread 持久化，所以 thread 随时可以恢复接着聊。状态里除了消息也可以放别的东西——上传的文件、检索到的文档、生成过程中的中间产物，都在同一个 thread 的作用域内。快照如何保存与恢复是 [[2.1 LangGraph 检查点与 Channel]] 的内容；本笔记关心的是消息历史这一部分怎么管。

## messages 为什么只增不减

State schema 里的 `messages` 键用 `add_messages` 做 reducer：每个节点返回的消息追加合并进列表，而不是覆盖旧值（reducer 的机制见 [[2.1 LangGraph 检查点与 Channel]]）。追加是正确的设计——覆盖式会让后一个节点一写就冲掉前面的消息；但代价是列表单调增长，而消息是按令牌计费的。

增长带来两层压力。第一层是硬性的：历史超出模型的上下文窗口，调用直接报错，属于不可恢复的失败。第二层在窗口装得下时也存在：过长的陈旧历史会让模型分心（官方原文 distracted），响应变慢、成本变高。所以官方的建议是长会话应用应当主动移除或遗忘过期的信息，这就落到两种办法上。

## 办法一：裁剪（trim_messages）

裁剪解决「发给模型之前先截短」。`trim_messages` 来自 `langchain_core.messages`，在节点里对消息列表做一次过滤，保留令牌预算内的部分：

```python
from langchain_core.messages import trim_messages
from langchain_core.messages.utils import count_tokens_approximately

messages = trim_messages(
    state["messages"],           # 待裁剪的完整消息列表
    max_tokens=128,              # 裁剪结果的令牌数上限
    strategy="last",             # 保留最后 max_tokens 个令牌；"first" 则保留最前
    token_counter=count_tokens_approximately,  # 令牌计数器：换 len 即按消息条数计数；
                                               # approximate 近似计数快，适合每轮都要跑的场合
    start_on="human",            # 裁剪结果必须从 human 消息开始（多数 chat 模型的约定）
    end_on=("human", "tool"),    # 最后一条必须落在这些类型上：该类型最后一次出现之后的消息丢弃，
                                 # 保证不会停在工具调用与工具结果的中间
    include_system=True,         # 开头的 SystemMessage（系统指令）保留在裁剪结果里
    allow_partial=False,         # True 时允许把一条消息切开、只保留半条凑预算
)
```

这些参数大多在修「裁剪结果的合法性」。多数 chat 模型要求历史以 human 消息开头（或 system 消息后紧跟 human）；ToolMessage 只能出现在带工具调用的 AIMessage 之后。从中间一刀切断，可能切出一个模型不接受的历史。`start_on` / `end_on` / `include_system` 就是把截断边界修整成合法历史的开关。

裁剪是读时过滤：它只作用于本次要发给模型的那份列表，state 本身不动，下一轮仍然从完整历史重新裁。token 计数不必精确——官方明确 `count_tokens_approximately`（或字符串捷径 `"approximate"`）推荐用于每轮都跑的裁剪场景，精确计数不值得这份开销。

## 办法二：摘要压缩

裁剪丢掉的信息对模型永久不可见。摘要压缩换一条路：把旧消息压成一份滚动摘要存进 state，再从列表里删掉旧消息。官方例子的模式分四步：

```python
from langchain_core.messages import HumanMessage, RemoveMessage

class State(MessagesState):        # MessagesState 是预置 schema：只有一个带 add_messages
    summary: str                   # reducer 的 messages 键；这里追加一个 summary 键存当前摘要

def summarize_conversation(state: State):
    summary = state.get("summary", "")          # 已有摘要则扩展，没有则新建
    if summary:
        summary_message = (
            "Extend the summary by taking into account the new messages above:"
        )
    else:
        summary_message = "Create a summary of the conversation above:"
    messages = state["messages"] + [HumanMessage(content=summary_message)]
    response = model.invoke(messages)

    # 删除最近两条之前的全部消息：RemoveMessage(id=..) 是一条删除指令，
    # 经 add_messages reducer 从列表中移除同 id 的那条消息
    delete_messages = [RemoveMessage(id=m.id) for m in state["messages"][:-2]]
    return {"summary": response.content, "messages": delete_messages}
```

摘要节点在消息积累到一定数量后触发（条件路由，或直接挂在 call_model 之前的边上）。压缩之后 state 里是「一份 summary + 最近几条消息」，窗口压力解除，主干信息保留在摘要里。官方另一个例子用 langmem 库的 `SummarizationNode`（参数含 `token_counter`、`model`、`max_tokens_before_summary`、`max_summary_tokens`）把它做成现成组件，从 START 直接连到 summarize 再到 call_model。

## 编辑消息历史的时机与约束

两种办法在「动不动 state」上分道：裁剪每轮现做、state 不变；摘要压缩改 state——删旧消息、写 summary，都通过节点返回值提交。直接删除也是一种 state 编辑：`RemoveMessage(id=m.id)` 删指定消息，`RemoveMessage(id=REMOVE_ALL_MESSAGES)`（常量来自 `langgraph.graph.message`）清空整个列表。它们只在带 `add_messages` reducer 的键上生效——删除指令就是一条交给 reducer 解释的特殊消息，LastValue channel 只会覆盖，解释不了它。

改历史的合法边界要守住：历史改完必须仍符合 provider 的约定——开头是 user 消息、工具调用后面跟着工具结果，删错位置下一轮调用就报错。官方还把检查点管理算作第三类手段：`graph.get_state` / `graph.get_state_history` 查看快照，`checkpointer.delete_thread(thread_id)` 删掉整个 thread 的历史（快照链的结构见 [[2.1 LangGraph 检查点与 Channel]]）。

## 边界问答

**1. Q：** 裁剪和摘要压缩分别什么时候用？
**A：** 裁剪无状态、开销小，适合「只需要最近几轮」的场景，但被裁掉的内容本轮对模型不可见。摘要压缩保留对话主干，代价是摘要节点的一次额外模型调用和触发逻辑的维护。两者可以组合：先裁剪控制长度，重要会话再上摘要。

**2. Q：** 为什么 trim_messages 不把结果写回 state？
**A：** 它是发给模型前的读时过滤，state 保留完整历史，恢复、审计、重放仍基于全量消息。摘要压缩则相反，物理删除旧消息、只留摘要——两者对 state 的态度是设计差别，不是遗漏。

**3. Q：** RemoveMessage 为什么只在 `add_messages` reducer 的键上生效？
**A：** 删除的实现方式是向 messages channel 提交一条 `RemoveMessage(id=..)`，由 `add_messages` reducer 解释——碰到同 id 的消息就移除。这是官方文档明确要求的约束（键必须是带 add_messages 的，如 MessagesState）。

**4. Q：** 裁剪时为什么要用 `start_on` / `end_on` 管消息边界？
**A：** 多数 chat 模型要求历史从 human 消息（或 system 后跟 human）开始，ToolMessage 只能出现在带工具调用的 AIMessage 之后。截断可能切出非法历史，这两个参数把边界修整成模型接受的形式。
