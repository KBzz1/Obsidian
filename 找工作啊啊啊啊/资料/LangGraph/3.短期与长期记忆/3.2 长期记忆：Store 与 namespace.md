# 长期记忆：Store 与 namespace

## 跨 thread 的记忆放在哪

长期记忆指跨 thread 保存的用户级或应用级数据：在任何 thread、任何时刻都能取回。它与短期记忆的差别不在保存介质而在作用域——短期记忆挂在 thread_id 下（一个会话一份），长期记忆挂在自定义的 namespace 下（一个用户或一个应用一份）。官方文档举的例子：thread 1 里用户说「记住：我叫 Bob」，换到 thread 2 问「我叫什么」，模型照样答得出来，因为记忆写在了两个 thread 共享的地方。

承载长期记忆的组件是 store。装配时与 checkpointer 一起传入 compile：

```python
checkpointer = InMemorySaver()   # thread 内：按 thread_id 存图状态与消息历史
store = InMemoryStore()          # 跨 thread：按 namespace 存用户/应用级记忆

graph = builder.compile(
    checkpointer=checkpointer,   # 支撑短期记忆与会话恢复
    store=store,                 # 支撑跨会话共享的长期记忆
)
```

BaseStore 是持久化键值存储的抽象基类：数据可以跨 thread 共享，作用域由 namespace 划分；部分实现支持语义检索，需要创建时给 index 配置才打开，默认禁用。官方实现有 InMemoryStore（内存版，演示用）、`PostgresStore.from_conn_string(DB_URI)` 与异步版 AsyncPostgresStore、RedisStore 与 AsyncRedisStore；数据库版首次使用要调 `store.setup()` 建表。生产环境不用 InMemoryStore。

## namespace 与 Item

namespace 是一个字符串元组，语义是层级路径。官方的比喻：namespace 像文件夹，key 像文件名。`("memories", user_id)` 表示「这个用户的记忆集合」；概念文档里也出现 `(user_id, application_context)` 这种「先归属、再应用场景」的写法——元组只是一条层级路径，各层放什么由开发者定，前缀相同的 namespace 构成一个可检索的范围。

写入和检索的交付形态是 Item：

```text
Item                 # store 里一条记忆的结构
    namespace        # tuple[str, ...]：这条记忆所属的层级路径
    key              # str：namespace 内的唯一标识，写入时由调用方指定（如 uuid）
    value            # dict：记忆本体；其中的键可用于 filter 过滤
    created_at       # 创建时间
    updated_at       # 最近一次更新时间（同 key 重新 put 会刷新它）
```

## 接口

四个基本操作，各有异步版（`aput` / `aget` / `asearch` / `adelete`）：

```python
store.put(namespace, key, value)     # 写入或更新：namespace + key 定位，value 是 dict；
                                     # 同一个位置再 put 即更新，不产生新条目
store.get(namespace, key)            # 精确取一条，返回 Item 或 None
store.search(namespace_prefix,       # 按命名空间前缀搜索（位置参数，搜该前缀下所有条目）
             query="...",            # 语义查询文本：配了 index 才按向量相似度排序
             filter={"k": "v"},      # 对 value 的键做内容等值过滤
             limit=10, offset=0)     # 分页
store.delete(namespace, key)         # 删除一条
```

检索后从 Item 里取数据：`item.value["data"]`。写删改都精确到 namespace + key，search 是唯一的检索入口，query 与 filter 可同时使用。

## 节点里怎么拿到 store

第一种是参数注入。编译时传给 `compile(store=...)` 的 store 会以关键字参数注入节点签名，配合 `config: RunnableConfig` 拿用户标识：

```python
def call_model(
    state: MessagesState,
    config: RunnableConfig,      # 从 config["configurable"] 里拿 user_id、thread_id 等标识
    *,
    store: BaseStore,            # 注入的就是编译图时用的那个 store
):
    user_id = config["configurable"]["user_id"]
    namespace = ("memories", user_id)                # 该用户的记忆作用域
    memories = store.search(namespace,               # 检索相关记忆
                            query=str(state["messages"][-1].content))
    info = "\n".join([d.value["data"] for d in memories])
    system_msg = f"You are a helpful assistant talking to the user. User info: {info}"

    last_message = state["messages"][-1]
    if "remember" in last_message.content.lower():   # 简化的写入触发条件
        memory = "User name is Bob"
        store.put(namespace, str(uuid.uuid4()), {"data": memory})  # 写入长期记忆

    response = model.invoke([{"role": "system", "content": system_msg}] + state["messages"])
    return {"messages": response}
```

第二种是 Runtime 对象（v0.6.0 起官方推荐）。建图时声明 `context_schema`，节点签名收 `runtime: Runtime[Context]`，从 `runtime.context` 拿业务上下文、`runtime.store` 拿 store：

```python
@dataclass
class Context:
    user_id: str                            # 会话级业务上下文：本次调用归属哪个用户

graph = StateGraph(state_schema=State, context_schema=Context)  # 把上下文类型声明给图
...
def call_model(state: State, runtime: Runtime[Context]):
    user_id = runtime.context.user_id       # 调用时 context=Context(user_id="1") 传入
    memories = runtime.store.search(...)    # store 同样从 runtime 上取
```

两条路径取到的是同一个 store 实例；区别在用户标识从哪来——前者从 configurable 字典、后者从类型化的 context。

## 自带向量检索

store 支持语义检索，但要在创建时给 index 配置：

```python
from langchain.embeddings import init_embeddings

embeddings = init_embeddings("openai:text-embedding-3-small")
store = InMemoryStore(
    index={
        "embed": embeddings,   # Embedding 模型：把记忆文本转向量
        "dims": 1536,          # 向量维度，须与 embed 模型一致
        # "fields": ["text"],  # 可选：value 里哪些字段参与向量化，缺省整个 value
    }
)

store.put(("user_123", "memories"), "1", {"text": "I love pizza"})
store.put(("user_123", "memories"), "2", {"text": "I am a plumber"})

items = store.search(("user_123", "memories"), query="I'm hungry", limit=1)
# 按相似度取回 pizza 那条——query 与文本语义相近，不需要字面匹配
```

不配 index 时语义检索不可用，search 退化为前缀范围内的列举加 filter 过滤。

## 与 checkpointer 的分工

checkpointer 管 thread 内：按 thread_id 存图状态和消息历史，支撑 `get_state`、`get_state_history`、`delete_thread`——回答「这个会话执行到哪、状态是什么」。store 管 thread 间：按 namespace 存用户与应用事实——回答「这个用户长期是什么样、偏好什么」。一个跟会话走，一个跟用户走；thread 内的执行状态不因为 store 存在而共享，跨 thread 的用户事实也不依赖某个会话的快照。两者在 compile 时同时传入、互不替代（快照一侧的结构见 [[2.1 LangGraph 检查点与 Channel]]）。

> [!example] 实践例子
> 健康管理项目的长期记忆走自建的「事件抽取→语义巩固→画像投影」管线，框架 Store 在项目里只是存储原语层面的参照，不承担语义判断：[[4.长期记忆语义模型]]；写入侧与当前任务并行的设计见 [[6.记忆写入与生命周期]]。

## 边界问答

**1. Q：** store 能不能代替 checkpointer？
**A：** 不能。checkpointer 存的是图执行状态与消息历史、按 thread_id 归档，支撑会话恢复与时间旅行；store 存的是跨 thread 的用户级事实、按 namespace 归档。删掉 checkpointer，同一 thread 的第二轮调用就丢失第一轮的执行现场；这不是 store 的 namespace 能补的位置。

**2. Q：** namespace 为什么用元组，不用一个字符串 key？
**A：** 元组承载层级路径语义：search 的第一个参数就叫 namespace_prefix，前缀匹配天然支持「搜这个作用域下全部条目」。`("memories", user_id)` 这种类别加归属的组合可以整体当作作用域，key 只需在 namespace 内唯一，不同用户之间互不冲突。

**3. Q：** search 的 query 和 filter 有什么差别？
**A：** query 走向量相似度排序，需要创建 store 时配置 index（embed 与 dims）；filter 对 value 的键做内容等值过滤，不依赖向量。两者可同时给，先过滤再按相似度排。

**4. Q：** 语义检索什么时候不可用？
**A：** BaseStore 的说明写明：语义检索默认禁用，各实现要在创建时提供 index 配置才启用；没有配置时，与 index 相关的参数不产生效果，search 退化为前缀内列举加过滤。
