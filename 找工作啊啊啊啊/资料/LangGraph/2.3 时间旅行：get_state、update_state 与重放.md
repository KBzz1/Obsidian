# 时间旅行：get_state、update_state 与重放

## 时间旅行在做什么

时间旅行（time travel）是对检查点历史的利用。checkpointer 在每个 superstep 边界留一份快照、旧快照不删，同一个 `thread_id` 下它们靠 `parent_config` 连成一条链（见 [[2.1 LangGraph 检查点与 Channel]]）。这条链不只是中断恢复用的，还可以读、可以改、可以从中间任意一份快照重新启动执行。官方给出两种形态：重放（replay），不改状态，从某份历史快照重跑之后的节点，用于复查与调试；分叉（fork），先改状态再从历史快照分出新分支，探索另一条执行路径。

两者的共同机制是从历史快照恢复：目标快照之前的节点不重跑——结果已经在快照链里；之后的节点重新执行，LLM 调用、API 请求、interrupt（`interrupt()` 动态中断，机制见 2.1）都会重新触发，结果可能和上次不同。

## get_state：读线程的状态

`graph.get_state(config)` 返回线程当前的状态，类型是 StateSnapshot——图 API 侧的读取形态，checkpointer 接口侧交付的 CheckpointTuple 见 2.1。config 里只带 thread_id 读最新一份快照；再带 checkpoint_id 就读指定的历史快照：

```python
config = {"configurable": {"thread_id": "1"}}  # 只带 thread_id：读最新快照
graph.get_state(config)

config = {"configurable": {"thread_id": "1",
                           "checkpoint_id": "1ef663ba-..."}}  # 带 checkpoint_id：读指定历史快照
graph.get_state(config)
```

StateSnapshot 的字段：

```text
StateSnapshot（graph.get_state 的返回值）
    values         # 本快照时刻各 channel 的值
    next           # 接下来要执行的节点名元组；空元组表示图已跑完
    config         # 定位本快照：thread_id、checkpoint_ns、checkpoint_id
    metadata       # 执行元数据：source（input / loop / update，快照来源）、
                   #   writes（产生本快照的节点写入）、step（superstep 计数，输入快照为 -1）
    created_at     # 快照创建时间（ISO 8601）
    parent_config  # 上一份快照的定位，第一份为 None——快照链靠它回溯
    tasks          # 本步待执行的任务元组，每项含 id、name、error、interrupts
```

`next` 与 `metadata.step` 是遍历历史时最常用的两个定位线索：`next == ("node_b",)` 说明这份快照停在「下一步轮到 node_b」，`step == 2` 说明它是第 2 个 superstep 之后的快照。

## get_state_history：遍历快照链

`graph.get_state_history(config)` 返回该线程的全部快照，按时间倒序、最新在前。历史是普通列表语义，配合条件式过滤就能定位到想要的那一份：

```python
history = list(graph.get_state_history(config))  # 最新快照在下标 0

before_b = next(s for s in history if s.next == ("node_b",))  # 找「node_b 之前」的快照
step2 = next(s for s in history if s.metadata["step"] == 2)   # 按 superstep 序号找
edits = [s for s in history if s.metadata["source"] == "update"]  # 找 update_state 写的快照
stuck = next(s for s in history                              # 找停在中断上的快照
             if s.tasks and any(t.interrupts for t in s.tasks))
```

metadata.source 的三个文档取值各有含义：input 是图输入，loop 是 superstep 推进，update 专指 update_state 写入的快照——因此 `source == "update"` 过滤出来的就是历史里全部人工编辑点。从历史快照续跑时，引擎还会在续跑点写一份标记 source=fork 的新快照；这个取值出现在 LangGraph 源码（pregel/_loop.py 的 `_put_checkpoint({"source": "fork"})`），官方概念页的字段表只列了前三个。

## update_state：把人工编辑写成新快照

`graph.update_state(config, values)` 在指定快照上写入一组状态值，对应人工介入里「编辑状态」的场景。它不是原地修改：写入产生一份新的快照（metadata 标记 source=update），原快照与原执行历史原样保留——官方明确警告 update_state 不回滚线程，它是在指定点开分支。

写入的值按 channel 的更新策略合并（reducer 机制见 2.1）：声明了 reducer 的 channel 走累积，不是覆盖——往 `add_messages` 的 messages 里 update_state 一条新消息，效果是追加一条，不是换掉整个列表。

`as_node` 参数把这次更新视为某个节点写出的，它决定下一步从哪个节点的后继继续：

```python
fork_config = graph.update_state(
    before_b.config,               # 在哪份快照上写
    values={"topic": "chickens"},  # 写什么
    as_node="generate_topic",      # 视为哪个节点写的：执行从它的后继节点恢复
)
```

不指定时 LangGraph 从快照的版本历史推断，官方说从已有检查点 fork 时推断几乎总是对的。三种情况需要显式给：同一 step 有多个并行节点都写过状态，推断不出谁是最后一个（抛 InvalidUpdateError）；全新线程没有执行历史，常见于测试前铺设初始状态；以及故意跳过节点——把 as_node 设成靠后的节点，图就认为那个节点已经跑过。

## 重放与分叉

重放：找到目标快照后，把它的 config 直接传给 invoke，输入传 None：

```python
history = list(graph.get_state_history(config))
before_b = next(s for s in history if s.next == ("write_joke",))

graph.invoke(None, before_b.config)  # write_joke 重新执行，它之前的节点不重跑
```

语义是重新执行而不是读缓存回放：之后的节点连 LLM 调用、API 请求都会再次发生，可能产生不同结果；interrupt 也会重新触发、重新等人。目标若是最终快照（next 为空），无事可做，等价于 no-op。用途因此偏向复查与调试：确认某一步时图里到底是什么状态、某个节点现在再跑会得到什么。

分叉：先 update_state 改状态，再从分叉点续跑：

```python
fork_config = graph.update_state(before_b.config, values={"topic": "chickens"})
result = graph.invoke(None, fork_config)  # write_joke 用新 topic 重跑，原历史不变
```

组合效果是改一个 channel 值、让之后的执行走另一条路，用于探索替代轨迹、比较两次执行。含 interrupt 的图在时间旅行里 interrupt 总会重新触发：节点重跑，重新停在 `interrupt()` 等新的 `Command(resume=...)`；多步表单类的图还可以从两个中断之间 fork，改后面的答案而不重问前面的问题。

子图有一个粒度限制：子图默认继承父图 checkpointer（见 [[2.2 Checkpointer 抽象与 thread_id]]），整个子图算父图的一个 superstep，无法时间旅行到子图两个节点之间；给子图编译时加 `checkpointer=True` 它才有自己的快照历史，此时用 `get_state(config, subgraphs=True)` 取出子图自己的 config 再 fork。

> [!example] 实践例子
> 健康管理项目的恢复走「同 thread 最新快照 + `Command(resume)`」路径，不从历史快照 fork 或 replay：确认必须走结构化入口过版本校验，图回退到旧检查点也不被理解成业务数据库回滚，见 [[5.Task Runtime、Checkpoint 和业务状态]] 与 [[10.代码级逻辑：跨请求的任务暂停与恢复]]。

## 边界问答

**1. Q：** replay 是不是把旧输出从缓存里读出来放一遍？
**A：** 不是。官方警告写明：replay 重新执行节点，LLM 调用、API 请求、interrupt 都会再次触发，结果可能不同。它读回的只是「从哪份快照继续」，之后的执行是真的再跑一遍。

**2. Q：** update_state 会覆盖或删除原快照吗？
**A：** 都不会。它写一份新的快照（source=update），从指定点分支，原执行历史完整保留。官方明确说明它不回滚线程。

**3. Q：** update_state 写的值会盖掉 channel 旧值吗？
**A：** 按 channel 的更新策略走：声明了 reducer 的 channel 累积合并（如 add_messages 追加消息），没有 reducer 的才替换，机制与节点写入相同。

**4. Q：** 从历史快照恢复执行，之前的节点会重跑吗？
**A：** 不会。之前节点的结果已经在快照链里，恢复只执行目标快照之后的节点——这是 replay 与 fork 共同的语义基础。

**5. Q：** 什么时候必须显式指定 as_node？
**A：** 三种情况：并行分支同一步多个节点写过状态、推断不出时（InvalidUpdateError）；全新线程没有执行历史（测试铺状态）；以及故意跳过节点。从已有检查点 fork 时推断几乎总是对的，通常不用给。

**6. Q：** 时间旅行能不能撤销节点已经产生的外部副作用？
**A：** 不能指望它。时间旅行回退的是图状态与执行轨迹；重跑节点时 API 请求这类副作用会再次发生，而不是被撤销。框架机制里没有对已发生副作用的补偿，那是使用方要自己处理的边界。
