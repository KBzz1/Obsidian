# Checkpointer 抽象与 thread_id

## Checkpointer：编译时注入的持久化引擎

checkpointer（检查点保存器）是 LangGraph 持久化层的核心抽象：一个知道怎么把图状态快照存下来、取回去的对象。图代码本身不碰存储——编译时把一个 checkpointer 注入图，运行时引擎在每个 superstep（超步，图执行一轮的同步边界，调度细节见 [[2.1 LangGraph 检查点与 Channel]]）自动调它存快照。

装配发生在 compile：

```python
from langgraph.checkpoint.memory import InMemorySaver

checkpointer = InMemorySaver()                      # 选一个具体实现，这里是内存版
graph = builder.compile(checkpointer=checkpointer)  # 编译时注入，持久化由此开启
```

官方文档把 checkpointer 列为一系列功能的前提：人工介入（人随时能查看图状态、图在人操作后能继续）、记忆（同一 thread 的后续运行记得之前的交互）、时间旅行（重放或分叉历史执行）、容错（某轮 superstep 有节点失败，可从最后一个成功的位置重启），外加 pending writes（节点已提交、尚未随快照生效的写入，同一轮里部分节点成功时其结果不丢）。没有 checkpointer，图一跑完状态就没了，这些都无从谈起。

子图不需要单独装配：给父图配 checkpointer 会自动传播给子图；要让某个子图拥有独立的检查点历史（而不是整个子图只算父图的一个 superstep），编译子图时写 `checkpointer=True`。函数式 API 对应写法是 `@entrypoint(checkpointer=...)`。用 Agent Server 部署时不需要自己配，服务端把检查点全部托管。

## thread_id：一条可恢复的执行线

thread（线程）是 checkpointer 组织检查点的单位：同一个 `thread_id` 下的一串 run 累积起来的状态。调用带 checkpointer 的图必须传 thread_id，位置在 RunnableConfig 的 configurable 字典里：

```python
config: RunnableConfig = {
    "configurable": {     # configurable：RunnableConfig 里放运行时参数的字典
        "thread_id": "1"  # 本线程的标识，checkpointer 以它为主键存取检查点
    }
}
graph.invoke({"messages": [...]}, config)
```

checkpointer 用 thread_id 作为存取检查点的主键。同一个 thread_id 再次 invoke，引擎先取回该线程最新的检查点、从它的状态继续——这是会话记忆的来源：第二次调用即使不带旧消息，图也记得第一次说过什么。换一个 thread_id，那个线程下没有任何检查点，执行从输入完整开始，等于新开一条线程；thread 内的状态不会跨线程带过去，跨线程的记忆属于 Store（长期记忆），不在这套机制里。不传 thread_id 则状态无处存档：官方明确说没有它 checkpointer 既不能保存状态、也不能在中断后恢复执行。

两个工程细节：PostgresSaver 的 thread_id 列有长度上限，官方排障页要求控制在 255 字符以内，需要确定性 ID 时用 UUID；同一线程内多张子图的快照靠 checkpoint_ns（检查点命名空间）区分归属——根图为空字符串、子图为 `节点名:uuid`、嵌套子图用 `|` 连接。

## BaseCheckpointSaver：五个核心方法

所有内置实现都实现 BaseCheckpointSaver 接口，接口面由五个方法组成，异步执行走 `a` 前缀的对应版本：

```text
BaseCheckpointSaver 的五个核心方法
    put / aput               # 存一份检查点，连同 config 与 metadata
    put_writes / aput_writes # 存挂在某份检查点上的节点级写入（pending writes）
    get_tuple / aget_tuple   # 按 config 取一条 CheckpointTuple：不带 checkpoint_id 返回线程
                             # 最新一份，带则返回那一份——graph.get_state() 的底层
    list / alist             # 按 config 与过滤条件遍历检查点——graph.get_state_history() 的底层
    delete_thread / adelete_thread # 删除一个线程的全部检查点与写入
```

接口背后是两个存储抽象：检查点表（每个 superstep 一行，链到父检查点）和写入表（superstep 内每个节点的输出各一行）。PostgresSaver 把它们落成三张表（非原始类型的值拆去 blob 表），表结构见 [[2.1 LangGraph 检查点与 Channel]]；值的序列化由 serializer 决定，默认 JsonPlusSerializer，同样在 2.1。

`get_state` 与 `get_state_history` 两个图侧 API 就是靠 `get_tuple` 与 `list` 支撑的，对快照链的具体用法见 [[2.3 时间旅行：get_state、update_state 与重放]]。

## 内置实现选型

官方把各实现拆成独立的 pip 包，按环境选：

```text
实现                        pip 包与定位
    InMemorySaver           langgraph-checkpoint（随 langgraph 自带，无需额外安装）
                            快照全在 RAM，进程重启即丢——实验用
    SqliteSaver /           langgraph-checkpoint-sqlite（需单独安装）
    AsyncSqliteSaver        本地文件库——实验与本地工作流
    PostgresSaver /         langgraph-checkpoint-postgres（需单独安装）
    AsyncPostgresSaver      完整安装：pip install -U "psycopg[binary,pool]" \
                            langgraph langgraph-checkpoint-postgres
                            生产用，LangSmith 自身用的就是它
```

PostgresSaver 的典型构造与初始化：

```python
from langgraph.checkpoint.postgres import PostgresSaver

DB_URI = "postgresql://postgres:postgres@localhost:5432/postgres"  # 官方示例连接串（占位凭据）
with PostgresSaver.from_conn_string(DB_URI) as checkpointer:  # 连接串构造，上下文托管连接
    checkpointer.setup()   # 首次使用时调用：建表、建索引
    graph = builder.compile(checkpointer=checkpointer)
```

SqliteSaver 在官方示例里用现成连接构造：`SqliteSaver(sqlite3.connect("checkpoint.db"))`。除这三个官方包，社区还有 MongoDB、Redis、Azure CosmosDB、Oracle 等集成，接口同样基于 BaseCheckpointSaver。

## 快照什么时候写

checkpointer 装配后不需要手动触发：LangGraph 在每个 superstep 边界自动写一份快照。一条 START → A → B → END 的顺序图跑完恰好留 4 份：一份输入快照（metadata 的 source=input、step=-1），随后每个 superstep 边界各一份（source=loop、step 从 0 递增）。superstep 内每个节点跑完，它的输出还会作为节点级写入先落写入表——同一轮里别的节点失败时，成功节点的写入已经持久化，恢复时不必重跑。

持久化时机可以用 durability 参数调，三档从最快到最稳：`exit` 只在执行退出（正常结束、出错或人工介入中断）时写，性能最好但中途崩溃无法恢复；`async` 一边执行一边异步写；`sync` 在下一步开始前同步写完每一份。`setup()` 与写入无关，只负责首次建表建索引，建过之后官方示例直接把它注释掉。

> [!example] 实践例子
> 健康管理项目把框架的 thread_id 落成任务自己的执行线索：`task_thread_id` = 根线索前缀 + 任务类型 + task_id，恢复时按它定位检查点；在框架检查点之外自建 `agent_task_runtime` 控制索引，四层持久化分工见 [[5.Task Runtime、Checkpoint 和业务状态]] 与 [[10.代码级逻辑：跨请求的任务暂停与恢复]]。

## 边界问答

**1. Q：** InMemorySaver 用着方便，为什么不能上生产？
**A：** 官方排障页写明：InMemorySaver（与 MemorySaver）把检查点存在 RAM 里，进程重启全部丢失。生产换持久化实现——PostgresSaver，本地开发可用 SqliteSaver。

**2. Q：** thread_id 对应什么粒度：一次请求，还是一个会话？
**A：** 一条可恢复的执行线，粒度由使用方决定。框架只规定：thread 是同一 thread_id 下的一串 run 的累积状态，一次 invoke 只是线程里的一段。聊天场景通常一个会话一个 thread，任务场景可以一个任务一个。

**3. Q：** 同一张图、同一个 checkpointer，换一个 thread_id 调用会发生什么？
**A：** 新线程下没有检查点，执行从输入完整开始；原线程的状态原样留在自己的 thread_id 下，互不影响。官方也用同一用户换 thread_id 的示例说明 thread 内记忆不跨线程——跨线程的记忆要靠 Store。

**4. Q：** graph.get_state 和 checkpointer.get_tuple 是什么关系？
**A：** 上下两层。get_state 是图 API，面向使用者，返回 StateSnapshot，数据来自接口层的 get_tuple / list。平时用图 API；直接操作 checkpointer（如 delete_thread 清线程）时才碰接口层。

**5. Q：** setup() 什么时候调用？
**A：** 首次使用某个数据库后端的 checkpointer 时调用一次（Postgres、Redis 等建表建索引），之后不再需要。InMemorySaver 没有表可建，不涉及。
