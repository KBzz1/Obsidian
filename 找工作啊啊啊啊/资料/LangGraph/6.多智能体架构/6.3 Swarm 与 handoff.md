# Swarm 与 handoff

## swarm：没有中心节点的多智能体

swarm 官方定义：智能体按各自专长动态互相交接控制权的多智能体架构，没有中心协调者。整张 swarm 是一个共享 state 的图：每个智能体占一个节点，节点之间的边不是画死的，而是运行时由 handoff 工具的 Command 决定；系统跟踪最后一个活跃智能体（active agent），后续交互直接从它继续，不必每次回到中心。

```text
SwarmState（swarm 的共享 state schema）
    messages      # 所有智能体共享的一条消息列表：默认交接时全量带过去
    active_agent  # 当前活跃智能体名，路由器靠它决定下一轮谁接话
```

## handoff 的机制：Command(goto=目标, update=状态增量)

handoff（交接）把控制权从一个智能体转到另一个：每个智能体的工具列表里放着指向其他智能体的交接工具，LLM 决定调用哪个，工具返回 Command 完成跳转。预建库 langgraph-swarm 的 create_handoff_tool 生成名为 transfer_to_<agent_name> 的工具，内部实现：

```python
return Command(
    goto=agent_name,                             # 跳到目标智能体节点
    graph=Command.PARENT,                        # 跳转与写入作用于 swarm 父图，不是智能体内部
    update={
        "messages": messages + [tool_message],   # 共享消息列表追加一条交接成功的 ToolMessage
        "active_agent": agent_name,              # 活跃智能体标记切换为目标
    },
)
```

create_swarm 把智能体们组装成一张 StateGraph：default_active_agent 指定没有活跃智能体时路由回退到的默认入口，add_active_agent_router 读取 active_agent 决定每轮路由给谁。

```python
alice = create_agent(
    "openai:gpt-4o",
    tools=[
        add,                                                    # 自己的业务工具
        create_handoff_tool(agent_name="Bob",                   # 交接工具：目标 Bob
            description="Transfer to Bob"),                     # 给 LLM 看的用途说明
    ],
    system_prompt="You are Alice, an addition expert.",
    name="Alice",                                               # swarm 里的节点名
)
bob = create_agent("openai:gpt-4o",
    tools=[create_handoff_tool(agent_name="Alice")],            # Bob 也能交回 Alice
    system_prompt="You are Bob, you speak like a pirate.", name="Bob")

workflow = create_swarm([alice, bob], default_active_agent="Alice")
app = workflow.compile(checkpointer=InMemorySaver())            # 无 checkpointer 会忘掉活跃智能体
```

## 交接时传什么

默认传全量：交接工具把 swarm 到目前为止的完整消息历史交给下一个智能体，外加一条表示交接成功的 ToolMessage。这是共享单条 messages 列表的自然结果——接手方什么都看得到，代价是上下文膨胀，且无法对后来的智能体隐藏某一段的内部过程。

自定义交接可以只传显式内容。官方 handoffs 指南的推荐做法：只传触发交接的 AIMessage 与配对的 ToolMessage（交接对），不传完整子智能体历史；需要更多信息时，把工作摘要写进 ToolMessage，或让交接工具带 LLM 填写的参数（如给下一个智能体的任务描述）。自定义 Command 型交接工具有两个前提：调用方要有能处理 Command 的工具调用节点（如 ToolNode）；swarm 图和目标智能体的 state schema 都得包含 Command.update 写入的键。

要彻底隔离某个智能体的内部历史，官方 README 给的路子是给它配私有 state 键（如 alice_messages），wrapper 做父子 state 映射，再手工用 add_active_agent_router 组网——放弃默认的全量共享，隔离自己负责。

## 与 supervisor 的对比

路由位置不同：supervisor 一切经过中心，swarm 由当前活跃智能体自己决定交给谁。成本结构不同：supervisor 形态（subagents）结果要流回主智能体，单次任务多一次调用，但 worker 无状态、跨大领域任务因上下文隔离少处理 67% token；swarm 形态（handoffs）有状态，重复请求直接从活跃智能体继续，省 40-50% 调用。失控风险与上下文管理不同：swarm 默认全量共享消息，一个智能体的内部过程对后来者全部可见，要隔离就得自定义交接或私有 state 键，且没有 checkpointer 时整个 swarm 会忘掉谁在活跃、丢掉对话历史；supervisor 的上下文问题集中在中心一处，图式靠 output_mode 一个参数收口。

> [!example] 实践例子
> 健康管理项目没有采用 swarm 的点对点交接：控制权始终在会话主管（Conversation Supervisor）手里，领域智能体（Domain Agent）之间不互相 handoff，交接内容也是由领域任务（DomainTask）显式声明的结构化载荷，而非共享消息历史，见 [[4.Supervisor 架构与委派]]、[[6.通信协议与 Artifact]]。

## 边界问答

**1. Q：** swarm 里谁决定下一个智能体？
**A：** 当前活跃智能体自己。它的 LLM 选择调用哪个交接工具，工具返回 Command(goto, update) 改写 active_agent 并跳转；没有任何中心节点。

**2. Q：** 交接后原来的消息历史去哪了？
**A：** 默认全部跟过去——messages 是全体共享的单列表。要控制就自定义交接：只传交接对（AIMessage + ToolMessage），或把摘要写进 ToolMessage。

**3. Q：** 为什么 swarm 要配 checkpointer？
**A：** 活跃智能体记在 state 里。没有 checkpointer，多轮之间 state 不持久，系统会忘掉谁在活跃并丢失对话历史。

**4. Q：** 什么时候选 swarm 而不是 supervisor？
**A：** 按官方对比：对话型、多状态、有重复请求的流程适合 handoffs（swarm 式，有状态省调用）；需要并行执行、领域上下文大的任务适合 subagents（supervisor 式，隔离省 token）。
