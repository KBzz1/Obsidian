# 架构选型：supervisor、swarm 与层级式

## 单智能体什么时候够用

官方多智能体文档开篇先泼冷水：多智能体系统用多个专门化组件协作处理复杂工作流，但并非每个复杂任务都需要它——配上合适（有时是动态装载的）工具与 Prompt，单个智能体常常能达到相近效果。工具少、任务聚焦时首选单智能体。

值得拆分的动机，官方给三条：上下文管理（提供专门知识而不撑爆模型的上下文窗口）、分布式开发（不同团队独立维护各自能力）、并行化（为子任务派出专门 worker 并发执行）。一个更具体的触发信号：单智能体工具太多、开始频繁选错工具。设计的中心问题是上下文工程——决定每个智能体看到什么信息。

代价写在同一页：衡量指标是模型调用次数（决定延迟与 API 成本）和处理的 token 总量，调用越多延迟越高（串行时尤其明显）、按请求计费的成本越高。官方的对比数字：同一批任务上 subagents（supervisor 形态）比 handoffs（swarm 形态）多一次调用，因为结果要流回主智能体；handoffs、skills 这类有状态的模式在重复请求上省 40-50% 调用；跨多个大上下文领域的任务上，subagents 因上下文隔离少处理 67% 的 token。记一句话：多智能体买的是隔离与并行，付的是调用次数与状态管理复杂度。

## 三种基本架构

### supervisor：中心委派与汇总

supervisor 是中心化架构：一个由 LLM 驱动的中心节点统一决定下一个执行哪个 worker、给什么输入、结果怎么合并。所有路由都经过 supervisor——worker 之间不直接通信，也不直接面向用户，干完活把结果交回 supervisor，由它决定下一步或收尾。官方新文档把这个模式叫 subagents（主智能体把子智能体当工具调用，全部路由经过主智能体），supervisor 这个名字保留在预建库 langgraph-supervisor 里。supervisor 与 router 不是一回事：router 是一次性分类步骤，分完就结束；supervisor 是保持上下文的完整智能体，跨多轮动态决定每一步调用谁。

### swarm：点对点交接

swarm 去掉中心节点：智能体按各自专长直接交接（handoff）控制权。每个智能体持有一组指向其他智能体的交接工具，运行时由当前活跃智能体自己决定交给谁；系统记住最后一个活跃智能体，后续用户消息直接路由给它，不必每次回到中心。机制细节见 [[6.3 Swarm 与 handoff]]。

### hierarchical：多层 supervisor

hierarchical（层级式）是 supervisor 之上再叠 supervisor。langgraph-supervisor 库的自我定位就是「创建层级式多智能体系统」：supervisor 是根节点，worker 是叶子；多层级就是把一整层 supervisor 当作上一层 supervisor 的一个 worker——supervisor 的 supervisor。适合领域之下还有子领域、一支团队内部还有分工的大系统，组装手段是子图，见 [[6.4 Subgraph 与状态映射]]。

## workflow 与 agent 的边界

LangGraph 文档给的定义：workflow 有预先确定的代码路径，按既定顺序执行；agent 是动态的，自己定义过程与工具使用——agent 自主性更强，可以用可用工具集和行为准则约束它，但走哪条路由模型决定。选型口径：可预测、步骤已知的结构化任务用 workflow；问题与解法不可预测、需要连续反馈循环的场景用 agent。

两者不是二选一：官方多智能体模式清单里有「自定义 workflow」一项，用 LangGraph 把确定性逻辑与智能体行为混在一起——编排路径确定，其中某些节点本身是 agent。真正的问题不是「workflow 还是多智能体」，而是哪一段用确定性路径保证可控，哪一段交给 LLM 自主决策。

> [!example] 实践例子
> 健康管理项目在选型上落的是 supervisor 变体：不设独立路由、简单请求留在会话主管（Conversation Supervisor）层直接回答，见 [[4.Supervisor 架构与委派]]。智能体间不走聊天式交接，通信是 DomainTask / AgentResult / DomainArtifact 结构化协议；领域智能体（Domain Agent）既可以是 ReAct 也可以是预定义 workflow，对应本篇「确定性 workflow 与智能体节点混编」的说法，见 [[6.通信协议与 Artifact]]。

## 边界问答

**1. Q：** 为什么不一开始就上多智能体？
**A：** 官方明确说，配上合适工具与 Prompt 的单个智能体常常够用。多智能体的收益是隔离、并行与团队分工，代价是更多调用（延迟与成本）和更复杂的状态管理；触发信号是工具多到选错、领域上下文大到塞不进一个窗口。

**2. Q：** supervisor 和 router 有什么区别？
**A：** router 是一次性分类步骤，分完就结束；supervisor 是保持上下文的完整智能体，跨轮动态路由，全部路由都经过它。

**3. Q：** swarm 与 supervisor 的核心差别是什么？
**A：** 有没有中心节点。supervisor 所有通信经过中心、worker 不直接面向用户；swarm 智能体直接互相交接，靠共享 state 里的活跃智能体标记接续对话。成本侧：supervisor 每次委派多一次回流调用，swarm 默认全量共享消息、上下文控制要自己做。

**4. Q：** workflow 和多智能体冲突吗？
**A：** 不冲突。官方支持混编：workflow 提供确定性代码路径，某些节点是 agent；多智能体模式清单里的「自定义 workflow」就是干这个的。
