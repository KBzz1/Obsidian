# Supervisor 模式与委派

## supervisor 循环：一个 LLM 节点加一组 worker

官方 supervisor 库的表述：supervisor 智能体实现为一个带结构化输出的 LLM，选出下一个（或一批）要路由到的 worker，然后路由过去；被选中的 worker 执行任务，执行完再路由回 supervisor。所有通信流都经过 supervisor——worker 不互相调用、不直接面向用户（interrupt 可以中途暂停等人输入）；supervisor 决定调用谁、给什么输入、怎么合并结果，直到判断任务完成收尾。

## 路由怎么写：Command(goto=...)

LangGraph 的节点除了返回状态更新，还能返回 Command 对象：goto 字段声明下一个执行哪个节点，update 字段顺带提交状态写入。supervisor 节点把 LLM 的选择翻译成 Command——路由决策发生在运行时，而不是画死的静态边；worker 是父图里的独立智能体节点时，还要指明跳转的作用层级。官方 handoffs 指南的示例：

```python
return Command(
    goto="sales_agent",                             # 下一个节点：目标 worker
    update={
        "active_agent": "sales_agent",              # 状态增量：记录当前活跃智能体
        "messages": [ai_message, transfer_message], # 只传交接对（AIMessage + ToolMessage），不传完整历史
    },
    graph=Command.PARENT,                           # 跳转作用于父图，不是当前智能体内部
)
```

交接有一条硬规则：每次交接必须包含触发它的 AIMessage 与 tool_call_id 匹配的 ToolMessage，缺一条消息历史就是畸形的。

## 预建库 langgraph-supervisor：create_supervisor

循环可以手搭，官方也提供预建库 langgraph-supervisor，create_supervisor 一行拿到整张 supervisor 图：

```python
math_agent = create_react_agent(           # worker：一个 ReAct 智能体
    model="openai:gpt-4o",
    tools=[add],                           # 本 worker 自己的工具
    name="math_expert",                    # 节点名，supervisor 靠它指路；可放多个 worker
)
workflow = create_supervisor(              # 返回 StateGraph，编译后即可运行
    [math_agent],                          # 受管的 worker 列表
    model=ChatOpenAI(model="gpt-4o"),      # supervisor 用的 LLM
)
app = workflow.compile()
```

关键参数（以参考文档为准）：

```text
create_supervisor 关键参数
    agents               # 必填：worker 列表（CompiledStateGraph / 任意 Pregel 对象）
    model                # 必填：supervisor 的 LLM
    output_mode          # worker 输出怎么回流：'last_message'（默认，只留最后一条）或 'full_history'（完整历史）
    parallel_tool_calls  # 允许一次委派多个 worker 并行（仅 OpenAI / Anthropic）
    handoff_tool_prefix  # 交接工具名前缀，默认 transfer_to_<name>
    add_handoff_messages # 交接时补一对 (AIMessage, ToolMessage)，默认 True
```

一条重要的官方注记：该库 README 现在写明，多数用例推荐直接用「工具式」实现 supervisor 模式（worker 包装成普通工具挂到主智能体），而非引入这个库；库的价值在现成的 supervisor 图与参数（另有 prompt、tools、结构化响应、模型前后钩子等）。

## 工具式委派：worker 包装成 @tool

工具式（官方叫 subagents 模式）不另建 supervisor 图：主智能体本身就是 supervisor，每个 worker（一个完整智能体）包成一个工具，最后一条消息作为工具结果回到主智能体：

```python
@tool("research", description="Research a topic and return findings")
def call_research_agent(query: str):                # 包装层：把 worker 变成一个普通工具
    result = subagent.invoke({"messages": [...]})
    return result["messages"][-1].content           # 只把最后一条消息回给主智能体

main_agent = create_agent(model="...", tools=[call_research_agent])   # supervisor 持有 worker 工具
```

官方点名的常见失败：worker 忘了把结果放进最终消息——主智能体只看得到那条输出，漏了就等于白干。对策：在 worker 的 Prompt 里明确要求返回什么，或在包装代码里格式化返回值。

两种实现共享一个设计问题：supervisor 该看到 worker 的多少过程。工具式默认只回最后一条消息，worker 的工具调用与中间推理隔离在它自己的上下文窗口里——这就是 subagents 无状态的含义：每次调用都是干净的上下文，记忆全在主智能体手里。图式由 output_mode 决定：last_message 只要结论，full_history 全过程可见但 token 上涨。多个 worker 可在同一轮并行执行，结果分别回流汇总。

> [!example] 实践例子
> 健康管理项目的会话主管（Conversation Supervisor）+ 领域智能体（Domain Agent）是 supervisor 变体，但委派不走聊天式 handoff：会话主管每轮输出结构化的 SupervisorAction，worker 完成后回传 AgentResult 而非自然语言，领域间冲突经结构化冲突报告（ConflictReport）回到会话主管裁决，见 [[4.Supervisor 架构与委派]]、[[6.通信协议与 Artifact]]。

## 边界问答

**1. Q：** 为什么官方建议多数场景直接用工具式而不是 langgraph-supervisor 库？
**A：** 库的 README 明确写了这条建议：把 worker 包装成工具挂到主智能体更简单；库适合想要现成 supervisor 图与预建参数的场景。

**2. Q：** worker 之间可以直接协作、直接面向用户吗？
**A：** 都不能。所有路由都经过 supervisor / 主智能体；interrupt 可以在子任务中途暂停等用户输入，但那是暂停不是接管。

**3. Q：** output_mode 两个值怎么选？
**A：** last_message 只回 worker 最后一条消息，上下文省、多数任务够用；full_history 回完整历史，supervisor 需要看过程时才开，token 随之上涨。

**4. Q：** supervisor 的上下文会被 worker 的中间过程污染吗？
**A：** 默认不会：工具式只回最后一条消息，图式默认 last_message；worker 内部过程隔离在它自己的上下文窗口里。
