# 记忆类型与写入策略

## 三类记忆

框架文档按内容性质把长期记忆分三类，划分借自人类记忆的研究：

```text
类型            存什么         人的例子           Agent 的例子
语义记忆        事实           在学校学到的知识    关于用户的事实
情节记忆        经历           我做过的事         过去执行过的动作
程序性记忆      规则与指令     本能与动作技能      Agent 的 system prompt
```

语义记忆（Semantic Memory）是对事实和概念的保持，最典型的用途是记住用户相关信息做个性化。情节记忆（Episodic Memory）是对过往事件和动作的回忆——agent 过去怎么完成任务、走过哪些路径。程序性记忆（Procedural Memory）是执行任务的规则，在 agent 身上由模型权重、代码和 prompt 三者共同构成。

三类都落在 store 的 namespace 里（见 [[3.2 长期记忆：Store 与 namespace]]），差别在内容性质与管理方式。

## 语义记忆：事实的两种管法

官方给出两种管理方式。画像（profile）是一份持续更新的 JSON 文档：每次学到新事实，把旧画像连同新信息一起交给模型，让它生成新画像或一份 JSON patch。缺点在规模——文档大了之后模型调和旧内容容易出错，需要拆成多份或加严格解码约束。集合（collection）是许多小的、范围窄的文档，只追加不重写：对模型来说生成一条新对象比在旧画像里做合并容易，下游召回率更高；代价是更新和删除变麻烦（有的模型倾向多插、有的倾向多改），检索复杂度转移到调用方——store 的语义检索与 filter 过滤就是为这条路准备的。

## 情节记忆：拿经历当示例

情节记忆的典型用法不是把经历念给模型听，而是当 few-shot 示例。官方的说法是「有时展示比讲述更容易」：从过往执行记录里挑出与当前任务相近的成功案例，作为示例放进 prompt，模型照着做。存储载体不限于 store——官方同样接受 LangSmith Dataset 配自定义检索的方案；载体是次要的，用法是「检索相关经历 → 作为示例注入」。

## 程序性记忆：改自己的 prompt

agent 很少改自己的权重和代码，所以程序性记忆在实践里的落点是 prompt 自修改，官方称 Reflection（反思）或元提示。做法：把 agent 当前的指令和近期对话（或反馈）一起交给模型，让它改写出新指令，存回 store；下一轮 call_model 从 store 取出最新指令拼进提示模板再生成。官方示例的两个节点分工——`call_model` 里 `store.get` 取当前指令，`update_instructions` 里让模型基于对话改写指令后 `store.put` 回去。这样 agent 的行为规则随使用经验演化，不需要重新部署。

## 写入时机：热路径还是后台

记忆什么时候写，官方给了两个位置，各有明确代价。

热路径（Hot Path）指对话进行中同步写：当前轮里模型一边回话一边（通常通过一个保存记忆的工具调用）把值得记的内容写进 store。好处是实时生效、对用户透明——可以告诉用户「我记住了这条」。代价有三项：给模型增加工具与指令复杂度；写入动作拖慢当前轮响应；模型在对话和记忆两条任务间切换，多任务会降低记忆本身的质量。官方举的参照是 ChatGPT 的 save_memories 工具，对应 memory-agent 模板。

后台写指会话之外以异步任务处理：对话结束后或按调度触发，单独的任务读会话内容、提炼并写入记忆。好处是主应用不增加延迟、关注点分离——记忆任务可以专心做提炼，时机也灵活。代价也有两项：写入频率要自己决定，更新不频繁时其他 thread 在一段时间内拿不到新记忆（最终一致，不是强一致）；触发机制要设计——按时间重调度、cron 定时、手动触发，官方对应 memory-service 模板。

两种取舍的轴是一致的：写入越靠近对话，生效越快、透明度越高，但延迟与质量代价越大；越靠后台，主链路越干净，但一致性越弱。

## 记忆应该影响什么

写入只是前半段，官方对每类记忆的生效位置都有交代。语义记忆在检索后注入提示，用来让回复有据可依、产生个性化交互——常见形态是检索结果拼进 system 消息。情节记忆按当前输入检索，作为 few-shot 示例放进 prompt。程序性记忆的新 prompt 存回 store，call_model 每轮取出、格式化进提示模板后再生成——它影响的是所有后续轮次的行为。短期记忆则是 state 里的会话历史，每轮直接传给模型（管理方式见 [[3.1 短期记忆：thread 内 state 与消息管理]]）。

注入位置集中在 prompt 组装处：检索发生在节点内调用模型之前，注入落在 system 消息或提示模板的变量里。store 只负责存与检索，怎么用是图的编排决定的事。

> [!example] 实践例子
> 健康管理项目把记忆写入放在与当前任务并行的后台路径——当前输入不等记忆生效，只有安全等关键事实走窄热路径，与本篇两种写入时机的取舍同构：[[6.记忆写入与生命周期]]；三类记忆与项目「历史层/认知层/读取层」数据层的对应见 [[4.长期记忆语义模型]]。

## 边界问答

**1. Q：** 热路径内写和后台写怎么选？
**A：** 看延迟敏感度和一致性要求。热路径实时生效、对用户透明，但增加当前轮延迟和工具复杂度，多任务还会降低记忆质量；后台写主链路零延迟、任务专注，但其他 thread 要等下一次更新才有新记忆，还要自己设计触发（定时、cron、手动）。官方各给了模板：memory-agent（热路径）与 memory-service（后台）。

**2. Q：** 语义记忆选画像还是集合？
**A：** 画像是一份持续重写的文档，读取简单，但规模大了模型调和旧内容容易出错；集合持续追加小文档，生成容易、召回高，但更新删除麻烦、必须配检索。召回优先选集合，要求强结构、单文档消费时选画像。

**3. Q：** 情节记忆必须存进 store 吗？
**A：** 不必。官方认可 LangSmith Dataset 加自定义检索作为替代载体；store 是默认选项，不是唯一选项。

**4. Q：** 程序性记忆在框架里实际改的是什么？
**A：** 改的是 agent 的 system prompt——新指令写回 store，每轮 call_model 取出拼进提示模板。模型权重和执行代码不在 agent 运行时自修改的范围内。

**5. Q：** 记忆注入放在哪个环节？
**A：** 统一放在 prompt 组装处：节点内、调用模型之前完成检索，语义记忆拼 system 消息，情节记忆作为 few-shot 示例，程序性记忆替换提示模板里的指令变量。store 本身不参与注入。
