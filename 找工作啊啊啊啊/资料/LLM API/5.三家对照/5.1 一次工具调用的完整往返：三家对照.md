# 一次工具调用的完整往返：三家对照

## 场景

统一用一个场景：用户说「帮我记录今天跑了五公里」，模型决定调用 `record_run` 工具，应用执行后把结果回传，模型给出最终回复。各家都省略鉴权头与次要参数，只保留往返的骨架。

## 三个往返并排

**OpenAI Chat Completions**：工具嵌套定义；调用意图在 message.tool_calls，参数是 JSON 字符串；结果用独立 tool 角色：

```python
# ① 声明：function 字段包一层
tools = [{"type": "function", "function": {
    "name": "record_run", "description": "记录一次跑步",
    "parameters": {"type": "object",
                   "properties": {"distance_km": {"type": "number"}},
                   "required": ["distance_km"]}}}]

# ② 模型请求调用：finish_reason == "tool_calls"
msg = resp.choices[0].message          # msg.tool_calls[0].function.arguments
json.loads(msg.tool_calls[0].function.arguments)   # 参数是 JSON 字符串，先解析

# ③ 执行后回传：独立 tool 角色消息，tool_call_id 配对
messages.append({"role": "tool", "tool_call_id": "call_x1",
                 "content": "已记录，编号 run_88"})
```

**OpenAI Responses**：工具扁平定义；调用与结果是两种 Item，靠 call_id 关联；无 tool 角色：

```python
# ① 声明：扁平三字段，没有 function 包裹
tools = [{"type": "function", "name": "record_run", "description": "记录一次跑步",
          "parameters": {"type": "object",
                         "properties": {"distance_km": {"type": "number"}},
                         "required": ["distance_km"]}}]

# ② 模型请求调用：output 里的 function_call Item
out = resp.output[0]                   # out.type == "function_call"
out.name, out.arguments, out.call_id   # arguments 仍是 JSON 字符串

# ③ 执行后回传：function_call_output Item 放进下轮 input
input.append({"type": "function_call_output", "call_id": out.call_id,
              "output": "已记录，编号 run_88"})
```

**Anthropic Messages**：input_schema 扁平定义；调用意图是 content 里的 tool_use 块，input 是对象；结果块放进 user 消息：

```python
# ① 声明：字段名是 input_schema（不是 parameters）
tools = [{"name": "record_run", "description": "记录一次跑步",
          "input_schema": {"type": "object",
                           "properties": {"distance_km": {"type": "number"}},
                           "required": ["distance_km"]}}]

# ② 模型请求调用：stop_reason == "tool_use"，content 里是 tool_use 块
blk = resp.content[0]                  # blk.type == "tool_use"
blk.name, blk.input, blk.id            # input 已是对象，直接用

# ③ 执行后回传：tool_result 块放进 user 消息
messages.append({"role": "user", "content": [
    {"type": "tool_result", "tool_use_id": blk.id,
     "content": "已记录，编号 run_88", "is_error": False}]})
```

三家共享同一个抽象：声明工具 schema → 模型产出结构化调用意图（含唯一 id）→ 应用执行 → 结果带着 id 回传 → 模型给最终回复。差异全在字段名与装载位置，写供应商抽象层时这是能收敛的部分。

## 差异总表

| 维度 | Chat Completions | Responses | Anthropic Messages |
|---|---|---|---|
| 端点 | `/v1/chat/completions` | `/v1/responses` | `/v1/messages` |
| 系统指令位置 | messages 首条 system/developer 消息 | 顶层 `instructions` | 顶层 `system` 字段 |
| 输入结构 | `messages` 数组 | `input`（字符串或 Item 数组） | `messages`，content 为块数组 |
| 工具定义 | `function` 嵌套，schema 叫 `parameters` | 扁平，`parameters` | 扁平，schema 叫 `input_schema` |
| 调用意图载体 | `message.tool_calls[]` | `function_call` Item | `tool_use` 块 |
| 调用参数形态 | JSON 字符串（`arguments`） | JSON 字符串（`arguments`） | 对象（`input`） |
| 强制调用 | `tool_choice: "required"` | `tool_choice: "required"` | `tool_choice: {"type": "any"/"tool"}` |
| 结果回传 | `tool` 角色消息 + `tool_call_id` | `function_call_output` Item + `call_id` | `tool_result` 块（user 消息内）+ `tool_use_id` |
| 错误回传 | content 里写错误文本（无专用字段） | output 字符串写错误 | `is_error: true` 显式标志 |
| 服务端状态 | 无 | `store` 默认开 + `previous_response_id` | 无 |
| 推理上下文回传 | 不支持（GPT-5.4 起推理+工具受限） | reasoning Item / `encrypted_content` | thinking 块 + `signature` 校验 |
| 提示缓存 | 隐式，`cached_tokens` 计量 | 隐式（利用率官方称更高） | 显式 `cache_control` 断点，读写分开计量 |
| 结构化输出 | `response_format: json_schema` | `text.format` | `output_config.format` / 工具 strict |
| 采样参数 | temperature / top_p 可用 | temperature / top_p 可用 | 新模型已弃用（仅 1.0 / ≥0.99） |

## 跨供应商适配的心智模型

能收敛的收敛掉：工具 schema（name + description + JSON Schema）、调用意图（id + name + 参数）、结果回传（id + 内容 + 错误标志）在三家语义一致，抽象层里做成中立模型，渲染时做字段翻译。

收敛不了的能力差异要登记：strict 的支持度与默认值、并行工具调用行为、推理上下文回传、缓存机制（隐式 / 显式断点）、采样参数可用性。这些差异决定了「同一套 Agent 逻辑跑在不同供应商上」不是改 base_url 就完事——能力协商是网关的持久职责，不是一次性适配。

> [!example] 实践例子
> 项目的模型网关就是这个心智的落地：中立 ModelContext 进、供应商请求体出，装配器与节点不感知任何一家格式；「能力差异登记」对应项目的供应商配置与熔断分层，见 [[11.代码级逻辑：一次 LLM 调用如何装配上下文]]、[[7.外部依赖保护与服务级熔断]]。

## 边界问答

**1. Q：** 面试被问「OpenAI 和 Anthropic 的 API 有什么区别」，怎么组织回答？
**A：** 按三层讲：数据模型（messages+role vs content blocks；message 粘合 vs Item 化）、状态与缓存（全量重发+隐式缓存 vs 显式断点；Responses 的服务端存储）、工具往返细节（tool 角色 vs tool_result 块；字符串参数 vs 对象参数）。收在心智模型上：抽象同构、字段各异，所以跨供应商要抽象层加能力协商。

**2. Q：** 哪些差异最容易在迁移时踩坑？
**A：** 四个高频坑：Anthropic 的 max_tokens 必填（OpenAI 可省）；两家的参数形态（字符串要 json.loads、对象直接用）；Responses 的 reasoning Item 不能丢；Anthropic 回传 thinking 块必须带 signature 原样回传，改一个字符就 400。

**3. Q：** 三家并存还会持续吗，要不要赌一家？
**A：** 应用层不该赌任何一家：Chat Completions 是兼容生态的公共层，Responses 是 OpenAI 的演进方向，Anthropic 是独立设计且 Agent 特性（思考回传、显式缓存）完整。把供应商知识压在网关层、业务逻辑只依赖中立抽象，是三家并存现状下唯一稳妥的架构姿态。
