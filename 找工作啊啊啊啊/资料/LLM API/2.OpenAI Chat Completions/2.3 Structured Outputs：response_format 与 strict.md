# Structured Outputs：response_format 与 strict

## 从「提示词求 JSON」到「协议保证 JSON」

让模型输出可解析的 JSON 有三代做法。第一代靠提示词（「必须输出 JSON」加解析失败重试），不可靠；第二代是 `response_format: {"type": "json_object"}` 的 JSON 模式，保证输出是合法 JSON，但不约束内部结构——字段名、嵌套、类型全看模型发挥；第三代是 Structured Outputs：`response_format` 带 `json_schema` 且 `strict: true`，官方承诺输出从第一个 token 起百分之百匹配给定 schema，解析层不再需要容错分支。

```python
resp = client.chat.completions.create(
    model="gpt-5",
    messages=[...],
    response_format={
        "type": "json_schema",            # 走 schema 约束，而非宽松的 json_object
        "json_schema": {
            "name": "run_record",          # schema 名，仅标识用
            "strict": True,                # 严格模式：输出 100% 匹配 schema
            "schema": {
                "type": "object",
                "properties": {
                    "distance_km": {"type": "number"},
                    "feeling": {"type": "string"},
                },
                "required": ["distance_km", "feeling"],
                "additionalProperties": False,   # strict 模式必填的约束
            },
        },
    },
)
answer = json.loads(resp.choices[0].message.content)   # 直接解析，无需兜底
```

用 JSON 模式（`json_object`）时有两个附带要求：提示词里必须出现「JSON」一词（模型需要它对齐输出形态），且 messages 里必须有用户消息，否则请求被拒——这是迁移老代码时最常见的报错来源。

## strict 模式对 schema 的限制

strict 的保证是有代价的：schema 必须落在受支持的 JSON Schema 子集内。核心限制：

- 所有对象必须 `additionalProperties: false`，且每个出现的属性都列进 `required`——可选性不用「省略字段」表达，而用可空类型（`type: ["string", "null"]`）表达；
- 支持的类型与组合子有限（object、array、string、number、integer、boolean、null、enum、allOf、anyOf、oneOf 等），不支持 `minLength` 之类部分校验关键字；
- 数组元素、嵌套对象递归适用同样规则。

约束的意义：schema 被编译成模型生成时的约束解码流程（逐 token 限定合法候选），schema 本身必须是可静态完整确定的，动态校验类关键字没有对应实现。不满足子集的 schema 传 `strict: true` 会直接被 API 拒绝。

## 函数调用侧的 strict

同一套约束也用在工具参数上：函数定义里 `"strict": true`（Chat Completions 默认不开启），模型的 `arguments` 就受同样的生成时约束。工具参数是 Agent 链路里最值得开 strict 的位置——参数直接进执行层，类型错误的代价是运行时异常而不是展示瑕疵。

Responses API 把 strict 的默认行为收紧了：省略 `strict` 时先尝试严格模式，schema 不兼容才回退并在响应里标注 `strict: false`；要旧行为需显式传 `strict: false`，见 [[3.1 Items 模型：input、output 与 instructions]]。

## 边界问答

**1. Q：** strict: true 之后还需要解析容错吗？
**A：** 解析层面不需要（输出保证是匹配 schema 的合法 JSON），但业务校验仍然需要——schema 管不住语义：数值越界、日期不存在、枚举合法但业务上不合理。schema 约束格式，业务规则约束取值，两层不能互相替代。

**2. Q：** 为什么所有字段都必须 required，可选字段怎么办？
**A：** 约束解码需要一个确定的字段闭合集：不允许出现 schema 外字段（additionalProperties: false），字段是否出现也就不再有自由度。可选字段的表达方式是可空类型：`{"type": ["string", "null"]}`，字段永远出现，值可以是 null。

**3. Q：** json_object 模式现在还有用吗？
**A：** 有两个场景：schema 本身是动态生成的、无法预先满足 strict 子集；或只需要「是个 JSON」而不在乎结构。其余情况都应该上 json_schema——同样是拿结构化数据，一个有协议保证，一个靠运气与重试。
