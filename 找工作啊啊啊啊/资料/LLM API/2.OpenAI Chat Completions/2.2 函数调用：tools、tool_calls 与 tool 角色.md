# 函数调用：tools、tool_calls 与 tool 角色

## 工具是「声明给模型的函数签名」

函数调用（function calling，现通称 tool calling）让模型不生成最终文本，而是产出一个结构化的调用请求，由应用执行后把结果喂回去。第一步是在请求里声明工具：`tools` 数组，每项是一个函数签名，参数用 JSON Schema 描述：

```python
tools = [{
    "type": "function",              # 工具类型；OpenAI 格式用 function 包一层
    "function": {
        "name": "record_run",        # 函数名，模型在调用请求里引用它
        "description": "记录一次跑步", # 模型判断何时该用它的主要依据
        "parameters": {              # JSON Schema 描述参数结构
            "type": "object",
            "properties": {
                "distance_km": {"type": "number"},
                "duration_min": {"type": "number"},
            },
            "required": ["distance_km"],
        },
    },
}]
```

注意这个嵌套形态：`name` / `description` / `parameters` 包在 `function` 里，外层再挂 `type: "function"`。这是 Chat Completions 的格式特征，Responses API 把它拍平了，对比见 [[3.1 Items 模型：input、output 与 instructions]]。

`tool_choice` 控制调用策略：默认 `"auto"`（模型自行决定）；`"required"` 强制必须调工具（从声明的工具里选）；`"none"` 禁止调用；也可以指定 `{"type": "function", "function": {"name": "record_run"}}` 强制调用特定函数。`parallel_tool_calls`（布尔）控制是否允许一轮里并发请求多个调用，默认允许。

## 响应：模型不回答，而是请求调用

模型决定调工具时，响应里 `choices[0].message.tool_calls` 是一个调用请求数组，`finish_reason` 为 `"tool_calls"`：

```python
message.tool_calls = [{
    "id": "call_abc123",             # 本次调用请求的唯一标识，回传结果时引用
    "type": "function",
    "function": {
        "name": "record_run",        # 要调用的函数名
        "arguments": "{\"distance_km\": 5.0}"   # 参数，注意是 JSON 字符串
    },
}]
```

两个工程要点：`arguments` 是 JSON 编码的字符串，不是对象，执行前要 `json.loads`；解析要容错——即便不带 strict，模型也可能生成不合 schema 的参数（多余的键、类型偏差），执行层应当校验后拒绝或重试，而不是信任它。

## 回传：tool 角色消息

应用执行函数后，把结果作为 `tool` 角色消息拼回历史发起新一轮请求。完整循环：

```python
messages = [{"role": "user", "content": "帮我记录今天跑了五公里，用时28分钟"}]
while True:
    resp = create(model, messages, tools=tools)          # 请求模型
    msg = resp.choices[0].message
    messages.append(msg)                                  # 模型消息原样入历史
    if resp.choices[0].finish_reason != "tool_calls":     # 不再请求工具即收尾
        break
    for call in msg.tool_calls:                           # 逐个执行请求的调用
        result = execute(call.function.name,
                        json.loads(call.function.arguments))
        messages.append({                                 # 结果用 tool 角色回传
            "role": "tool",
            "tool_call_id": call.id,                      # 对应哪次调用请求
            "content": json.dumps(result),                # 结果序列化为字符串
        })
# 循环退出时 msg.content 是面向用户的最终回复
```

回传时的硬约束：每条 tool 消息的 `tool_call_id` 必须与 assistant 消息里某个 `call.id` 对应，漏配对直接 400；并行调用时所有结果都要回传，顺序与请求顺序一致。

## 循环的边界

这个「请求 → 调用 → 回传」循环跑在客户端，每一圈都是一次完整的 API 请求。模型可能连续多轮请求工具（先查再记），循环次数不封顶，工程上要设最大轮数防死循环。工具执行失败的处理约定：把错误信息作为 tool 消息内容回传（模型可以换参数重试或改道），而不是在客户端静默吞掉。

## 边界问答

**1. Q：** 模型是怎么「调用」工具的，它真的执行了函数吗？
**A：** 没有。模型只生成调用意图——函数名加参数的结构化输出；执行永远发生在应用侧。API 文档里「模型请求调用」的准确含义是：模型输出了一个符合工具调用格式的 JSON，解析与执行是你的代码的事。这个边界是工具安全设计的起点。

**2. Q：** arguments 为什么设计成字符串而不是直接给对象？
**A：** 模型输出本质是 token 序列，流式场景下参数 JSON 是逐片段推送的（见 [[1.3 流式响应：SSE 与增量事件]]），字符串形态与生成过程一致；对象形态要求整体解析后才能交付。代价是使用方多一步 json.loads 与容错。

**3. Q：** 多个工具调用并行请求时，执行顺序有要求吗？
**A：** 模型一轮 tool_calls 里给多个调用，说明它认为这些调用相互独立、可以并发。回传结果按请求顺序拼 tool 消息即可；如果你的工具之间实际有依赖（后一个的参数依赖前一个的结果），要么合并成一个工具，要么在系统指令里约束模型每轮只请求一个。

**4. Q：** 怎么让模型输出严格符合 schema 的参数？
**A：** 在函数定义里加 `strict: true` 走 Structured Outputs 约束，模型输出会被约束为第一个 token 起就匹配 schema，见 [[2.3 Structured Outputs：response_format 与 strict]]。不加 strict 时是尽力而为，需要执行层校验兜底。
