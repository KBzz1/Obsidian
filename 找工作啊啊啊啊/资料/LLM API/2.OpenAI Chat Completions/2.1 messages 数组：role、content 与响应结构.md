# messages 数组：role、content 与响应结构

## 请求：messages + 参数

Chat Completions 的输入是一个 `messages` 数组，每条消息由 `role`（谁说的）与 `content`（说了什么）构成，外层叠加生成参数：

```python
resp = client.chat.completions.create(
    model="gpt-5",                    # 模型标识，决定能力与计费
    messages=[                        # 按时间序排列的对话历史
        {"role": "system", "content": "你是健康助手"},       # 系统指令：设定行为规范
        {"role": "user",   "content": "我今天跑了五公里"},    # 用户输入
    ],
    temperature=0.7,                  # 采样随机性，0 更确定、1 更发散
    max_completion_tokens=1000,       # 输出 token 上限，撞顶时 finish_reason 为 length
    stop=["\n\n用户："],               # 停止序列，生成中命中即停
)
```

`content` 可以是字符串，也可以是多模态内容数组（`[{"type": "text", ...}, {"type": "image_url", ...}]`），图像以 URL 或 base64 传入。

角色体系按时间演进成了四层：`system` 给整段对话的行为指令；`developer` 是新模型引入的角色，语义是「给应用开发者的指令」，优先级高于 `system` 与用户消息（新模型推荐把原来放 system 的工具规则、格式约束迁到 developer）；`user` / `assistant` 是对话双方。工具结果用第五种 `tool` 角色，见 [[2.2 函数调用：tools、tool_calls 与 tool 角色]]。

常用生成参数：`temperature` 与 `top_p` 控制采样（两者通常只调一个）；`max_completion_tokens` 限定输出长度（旧参数 `max_tokens` 仍被兼容，新模型统一用前者）；`stop` 停止序列；`n` 一次生成几个候选（Responses API 已移除该参数，见 [[3.1 Items 模型：input、output 与 instructions]]）；`stream` 开流式；`response_format` 控制输出格式；`tools` / `tool_choice` 声明工具。

## 响应：choices 数组

```python
{
  "id": "chatcmpl-abc123",          # 本次完成的唯一标识，排障时报给官方用
  "object": "chat.completion",      # 对象类型，流式对应 chat.completion.chunk
  "model": "gpt-5-xxxx",           # 实际使用的具体模型版本
  "choices": [{
    "index": 0,                     # 第几个候选（n>1 时有多个）
    "message": {
      "role": "assistant",          # 固定为 assistant
      "content": "干得漂亮……",      # 文本回复；调用工具时可能为 null
      "tool_calls": [...]           # 工具调用请求，见 2.2
    },
    "finish_reason": "stop"         # 本候选的停止原因
  }],
  "usage": {
    "prompt_tokens": 52,            # 输入 token 数
    "completion_tokens": 18,        # 输出 token 数
    "total_tokens": 70              # 两者合计
  }
}
```

`choices` 是数组是给 `n` 参数留的位——`n=1` 时永远只有一个元素，取 `choices[0]` 即可。`finish_reason` 的枚举：`stop`（自然结束或命中停止序列）、`length`（输出上限）、`tool_calls`（模型请求调用工具）、`content_filter`（内容安全拦截）。Agent 循环的分叉点就是这个字段。

## 逐字段看一个多轮结构

第二轮请求时，客户端把第一轮的请求与响应都拼进历史，模型回复（含工具调用）以 assistant 消息原样回传：

```python
messages = [
    {"role": "system",    "content": "你是健康助手"},
    {"role": "user",      "content": "帮我记录今天跑了五公里"},
    {"role": "assistant", "tool_calls": [...]},          # 模型请求调用 record_run 工具
    {"role": "tool", "tool_call_id": "call_x1", "content": "已记录，编号 run_88"},
    # ↑ 工具执行结果：tool_call_id 对应上 assistant 里的那次调用
    # 下一轮模型基于工具结果生成最终回复
]
```

多轮拼接的通用机制（全量重发、角色约束、裁剪权）见 [[1.2 多轮对话：无状态服务与客户端拼接]]。

## 边界问答

**1. Q：** system 和 developer 什么关系，新代码该用哪个？
**A：** developer 是新模型引入的高优先级指令角色，语义分工是「应用层规则」（工具使用规范、输出格式）进 developer，「品牌人设类」指令留在 system。旧模型只有 system。写兼容多家模型的网关时，常见做法是按模型能力路由两个字段，或统一先发 system。

**2. Q：** assistant 消息里的 content 为 null 是出错了吗？
**A：** 不是。模型决定调用工具时，可以把全部输出预算花在 tool_calls 上，content 就是 null；这是 `finish_reason: "tool_calls"` 下的正常形态，拼接历史时这条 assistant 消息连同 tool_calls 原样回传即可。

**3. Q：** max_tokens 和 max_completion_tokens 用哪个？
**A：** 新参数是 max_completion_tokens，语义是完成 token（含推理模型内部的推理 token）；旧名 max_tokens 仍兼容但推荐模型已不接受。跨模型网关统一用新参数最省事。

**4. Q：** 这个 API 会被 Responses 取代吗，现在学它还有价值吗？
**A：** 官方口径：Chat Completions 仍受支持、未弃用，但 OpenAI 推荐所有新项目用 Responses，新模型能力（内置工具、完整推理支持）优先落在 Responses；GPT-5.4 起 Chat Completions 上带推理力度的工具调用已不可用（见 [[3.3 内置工具与推理模型]]）。学它的价值在生态：大量第三方服务兼容这套格式，见 [[2.4 OpenAI 兼容生态：事实标准的形成]]。
