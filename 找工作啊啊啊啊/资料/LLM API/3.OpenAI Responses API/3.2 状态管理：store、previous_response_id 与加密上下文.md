# 状态管理：store、previous_response_id 与加密上下文

## Responses 打破了「服务端无状态」的默认

Chat Completions 时代，多轮就是客户端全量重发。Responses 引入了服务端存储：响应默认被存储（`store` 默认开启，Chat Completions 只对新账户默认存储），拿到 `resp_` 前缀的响应 id 后，后续请求可以用 `previous_response_id` 引用它，服务端自动把链上的历史拼进本轮输入，客户端只发新增内容。

```python
r1 = client.responses.create(
    model="gpt-5",
    instructions="你是健康助手",             # 注意：链式引用不会延续 instructions
    input="帮我记录今天跑了五公里",
)
r2 = client.responses.create(
    model="gpt-5",
    instructions="你是健康助手",             # 每轮都要重发，丢了就丢指令
    previous_response_id=r1.id,             # 链式引用：服务端拼上 r1 的历史
    input="再记一下静息心率 58",             # 只发新增消息
)
```

## 链式引用的三个坑

**计费不减免**。官方迁移指南明确：链上先前响应的输入 token 仍按输入计费——服务端替你拼历史，不替你付历史。省的只是网络传输与应用侧的拼接代码，token 成本与全量重发相同（缓存折扣另算，Responses 的缓存利用率官方内部测试比 Chat Completions 高 40%–80%）。

**instructions 不延续**。`previous_response_id` 只携带对话数据，顶层 `instructions` 不在链上，每轮必须重发。这是官方列出的常见迁移错误。

**默认存储的合规含义**。store 开启意味着对话内容存在 OpenAI 侧。对零数据保留（Zero Data Retention，ZDR）要求的组织，OpenAI 会强制 `store: false`；一般应用也可以主动关闭，回到无状态形态。

## 无状态用法：encrypted_content

`store: false` 之后多轮怎么办？Responses 的答案是加密上下文：请求时设置 `include: ["reasoning.encrypted_content"]`，响应的 reasoning Item 里会带 `encrypted_content` 字段——服务端加密的推理内容，应用原样保存，下轮作为 input Item 传回，服务端在内存中解密使用、用后即弃。这样既不落盘明文，又保住了推理模型需要的推理上下文（丢弃 reasoning 会掉准确率，见 [[3.3 内置工具与推理模型]]）。

```python
# 第一轮：关闭存储，向响应索要加密的推理内容
r1 = client.responses.create(
    model="gpt-5",
    input="帮我分析这周的训练负荷",
    store=False,                             # 不在服务端留存任何东西
    include=["reasoning.encrypted_content"], # reasoning Item 附加密内容
)
saved = r1.output          # 应用侧保存全部 Item（含密文推理）

# 第二轮：保存的 Item 原样传回，服务端在内存中解密使用
r2 = client.responses.create(
    model="gpt-5",
    input=saved + [
        # 只追加本轮新增的用户消息
        {"role": "user", "content": "和上周比呢？"},
    ],
    store=False,
    include=["reasoning.encrypted_content"],
)
```

三种多轮方案各有适用面：

| 方案 | 状态在哪 | 适用 |
|---|---|---|
| `previous_response_id` 链 | OpenAI 服务端 | 快速原型；能接受数据存 OpenAI 侧 |
| 手动拼 Item（含 encrypted_content） | 应用侧 | 自管历史、ZDR、需要裁剪改写 |
| Conversations API | 服务端会话对象 | 长期会话产品形态，独立于单次响应 |

选择轴就一条：历史数据的控制权放谁手里。要裁剪、改写、审计历史（Agent 工程的常见需求）就必须应用侧自管；原型和纯对话产品用链式最省代码。

> [!example] 实践例子
> 项目在这条轴上选了应用侧：历史轨迹的选取、整理与裁剪是上下文装配器的显式职责，见 [[6.历史轨迹与上下文整理]]；把状态交给服务端会失去 ContextPolicy 对模型可见历史的控制权，取舍见 [[3.上下文装配器与 ContextPolicy]]。

## 边界问答

**1. Q：** store: false 之后还能用 previous_response_id 吗？
**A：** 不能，链式引用依赖服务端存储的响应对象；未存储的响应 id 无物可指。无状态多轮只能走手动拼 Item，推理模型场景记得带上 encrypted_content。

**2. Q：** 应用自管历史时，Chat Completions 和 Responses 的差别还剩什么？
**A：** 数据模型与能力面：Item 化的输入输出、内置工具、推理支持仍然只在 Responses 上完整（见 [[3.3 内置工具与推理模型]]）。状态管理只是两者差异的一小部分——把 store 关掉后，Responses 依然是对话数据结构更干净的那个。

**3. Q：** 服务端存储会不会让多轮计费变便宜？
**A：** 不会。链式引用下先前输入照常计费（官方明示）；变便宜靠的是缓存——Responses 的前缀缓存利用率官方测试高 40%–80%，缓存命中部分按折扣计费，与 store 无关。
