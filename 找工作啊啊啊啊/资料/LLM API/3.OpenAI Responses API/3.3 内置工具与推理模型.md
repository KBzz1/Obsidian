# 内置工具与推理模型

## 内置工具：OpenAI 替你执行的那一半

Chat Completions 的函数调用里，模型只出意图、执行全在客户端。Responses 在此之外提供内置工具（built-in tools）：声明即用，执行发生在 OpenAI 侧，过程与结果作为类型化 Item 出现在 output 里。

```python
resp = client.responses.create(
    model="gpt-5",
    input="查一下重庆这周适合跑步的早晨，并给建议",
    tools=[{"type": "web_search"}],      # 声明即用：没有 name/parameters，无客户端代码
)
# resp.output 里依次出现 web_search_call（执行记录）与 message（最终回答）
```

工具面（2026-09 的 API reference）：`web_search`（联网搜索）、`file_search`（对预先上传文件的向量检索）、`code_interpreter`（沙箱里跑代码）、`image_generation`（生成图片）、computer use（操作计算机界面）、`mcp` 连接器（把远程 MCP 服务器的工具接进本次响应）与 local shell 类工具。共同特征：调用、执行、结果装配由服务端完成，应用拿到的是成品。

## 代理循环：一次请求内的多轮工具

内置工具改变了请求的粒度。函数调用模式下，一轮工具循环 = 一次客户端往返（请求、执行、回传，见 [[2.2 函数调用：tools、tool_calls 与 tool 角色]]）；Responses 的内置工具把循环搬进服务端——一次 create 请求内，模型可以连续「搜索 → 读结果 → 再搜 → 综合作答」，客户端等一个终态响应即可。官方把它称为代理循环（agentic loop）：API 请求的单位从「一次生成」变成了「一段带工具的自主任务」。

内置工具与自定义函数可以混用：自定义函数仍走客户端执行的 function_call / function_call_output 往返，内置部分在服务端消化，两种 Item 出现在同一个 output 数组里。混用的声明与分工：

```python
resp = client.responses.create(
    model="gpt-5",
    input="查一下重庆明天的天气，再按我的偏好安排晨跑",
    tools=[
        # 内置工具：声明即用，OpenAI 侧执行
        {"type": "web_search"},
        # 自定义函数：扁平三字段，客户端执行
        {"type": "function", "name": "schedule_run",
         "description": "把晨跑安排写进训练计划",
         "parameters": {"type": "object",
                        "properties": {"time": {"type": "string"}},
                        "required": ["time"]}},
    ],
)
# output 里：web_search_call 是服务端执行完的记录；
# schedule_run 以 function_call Item 出现，
# 客户端执行后要把 function_call_output 传回再拿最终回复
```

还有异步函数调用（函数排队执行不阻塞响应）与函数输出 schema（`output_schema`，约束工具结果形态）等增强，属具体工程选型时再查的手册细节。

## 推理模型与 reasoning Item

推理模型（o 系列、GPT-5 及之后的世代）在回答前先做内部推理。Responses 对它的支持是原生的：output 数组里推理过程是独立的 `reasoning` Item（带 `summary` 摘要字段），计费上推理消耗的输出 token 单列在 `output_tokens_details.reasoning_tokens`。

生成侧的旋钮是 `reasoning` 参数：`effort` 控制推理力度（枚举从 `minimal` 到 `high`，高世代模型扩展到 `xhigh` / `max`，`none` 表示关闭），`summary` 控制摘要呈现（`auto` / `concise` / `detailed`）：

```python
resp = client.responses.create(
    model="gpt-5",
    input="...",
    reasoning={
        "effort": "medium",     # 推理力度：越高越慢越贵，换更深的多步推理
        "summary": "auto",      # reasoning Item 的摘要呈现方式
    },
)
```

工程上最要紧的一条约束：多轮传递上下文时必须保留 reasoning Item（或其 encrypted_content），丢弃会掉准确率——官方内部评测 SWE-bench 上 Responses 比 Chat Completions 高约 3%，主要差在推理上下文的完整传递上。

Chat Completions 侧对推理模型的支持是残缺的：GPT-5.4 起，Chat Completions 不支持在非 `none` 推理力度下做工具调用——推理 + 工具这个 Agent 主力组合只在 Responses 上完整可用。这也是官方「新项目用 Responses」结论的技术根据之一。

> [!example] 实践例子
> 项目的对应取舍相反：工具执行全部收敛在自建 Tool Runtime，模型侧只拿工具提案与结果，不把执行交给任何供应商侧沙箱——边界与理由见 [[4.统一 Tool Runtime]]、[[5.护栏]]；预算侧对「推理 token 单列计量」的同构设计见 [[4.任务预算与任务准入]]。

## 边界问答

**1. Q：** 内置工具和自定义函数工具，工程上怎么选？
**A：** 分工轴是「执行环境信任边界」。通用能力（搜索、代码沙箱）用内置，省集成与运维；触及业务数据与副作用的工具必须自定义——执行在应用侧，过自己的护栏、幂等与审计。混用时注意成本模型不同：内置工具按用量计费且过程细节有限，自定义工具的成本与可观测性完全自管。

**2. Q：** reasoning effort 调到多高合适？
**A：** 按任务分级：简单抽取与改写用 `minimal`/`low`，多步规划与复杂工具编排用 `medium` 以上，`xhigh`/`max` 留给难题与离线任务。effort 越高推理 token 越多、延迟与成本越高；没有「越高越好」，与项目的任务准入分层思路同构，见 [[4.任务预算与任务准入]]。

**3. Q：** 摘要（summary）是推理内容本身吗？
**A：** 不是。模型的内部推理原文不开放，summary 是面向开发者的摘要呈现；`encrypted_content` 是推理上下文的密文形态，供下轮解密使用，应用读不到明文。观测想要「模型在想什么」，能拿到的是摘要级别，不是逐 token 思维。
