# Items 模型：input、output 与 instructions

## Responses API 的定位

Responses API（`POST /v1/responses`，2025-03 推出）是 OpenAI 面向 Agent 场景重新设计的 API。官方口径：Chat Completions 仍受支持、未弃用，但推荐所有新项目用 Responses，新模型能力优先落在它上面；前一代面向 Agent 的 Assistants API 已于 2026-08-26 下线，其能力并入 Responses。它解决的问题在数据模型上最直观——Chat Completions 把对话、工具调用、推理过程都挤在 message 对象里，Responses 把它们拆成类型化的 Item。

## input：字符串或 Item 数组

最简形态 `input` 直接给字符串（单轮问答），完整形态是 Item 数组。与 Chat Completions 最大的结构差异是系统指令的位置：Responses 有顶层 `instructions` 字段，与 `input` 分离——指令是对话之外的行为规范，不该混在对话数据里。

```python
resp = client.responses.create(
    model="gpt-5",
    instructions="你是健康助手",       # 系统指令：独立字段，不占 input
    input=[                            # 对话数据：类型化 Item 数组
        {"role": "user", "content": "我今天跑了五公里"},
    ],
)
resp.output_text                       # SDK 便利属性：拼接全部文本输出
```

输入侧的 Item 主要是消息（role + content），也接受回传的 function_call_output（工具结果）。无状态多轮场景下，完整形态的 input 长这样——上轮 output 的调用 Item 与本轮的结果 Item 成对出现在同一数组里：

```python
resp = client.responses.create(
    model="gpt-5",
    instructions="你是健康助手",           # 指令每轮重发，不随链延续
    input=[
        # 消息 Item：与 Chat Completions 的消息同构
        {"role": "user", "content": "帮我记录今天跑了五公里"},
        # 上轮模型产生的调用 Item，原样传回
        {"type": "function_call", "call_id": "call_x1",
         "name": "record_run",
         "arguments": "{\"distance_km\": 5.0}"},
        # 应用执行后的结果 Item，call_id 与上面配对
        {"type": "function_call_output", "call_id": "call_x1",
         "output": "已记录，编号 run_88"},
    ],
)
# 本轮模型看到工具结果，直接生成面向用户的最终回复
```输出侧的 Item 类型更丰富，每种类型独立成对象：

```text
output: [
  {type: "reasoning", ...}             # 推理过程（含 summary 摘要）
  {type: "function_call", call_id, name, arguments}    # 工具调用请求
  {type: "message", content: [{type: "output_text", ...}]}  # 文本回复
  {type: "web_search_call", ...}       # 内置工具的执行记录
]
```

官方迁移指南对这两种设计的评价：Chat Completions 的 Message 把多种关注点粘在一个对象里（原文 glued together into one object），Responses 的 Item 彼此独立、各管一件事。对 Agent 工程的直接好处：推理痕迹、工具调用、文本回复在同一份数组里有明确顺序与边界，不再从 message 的字段组合里反推。

## 响应对象与状态

响应是一个有身份、有状态的对象：`id`（`resp_` 前缀）、`object: "response"`、`status`（`completed` / `failed` / `in_progress` / `cancelled` / `queued` / `incomplete`）。`incomplete` 配 `incomplete_details.reason`（如 `max_output_tokens`）说明为什么没生成完——Chat Completions 里这个信息在 finish_reason 里，Responses 把「响应生命周期状态」与「生成停止原因」拆开了。

usage 字段：`input_tokens` / `output_tokens`，附 `input_tokens_details.cached_tokens`（缓存命中的输入）与 `output_tokens_details.reasoning_tokens`（花在内部推理上的输出）——推理 token 单独计量是推理模型时代的计费基础。

两个删改值得记：`n` 参数被移除，多候选要发多次请求；SDK 提供 `output_text` 便利属性直接拿拼接后的全部文本，等价于遍历 output 里所有 output_text Item。

## 与 Chat Completions 逐项对照

| 维度 | Chat Completions | Responses |
|---|---|---|
| 端点 | `/v1/chat/completions` | `/v1/responses` |
| 输入 | `messages` 数组（含 system 消息） | `input`（字符串或 Item 数组）+ 顶层 `instructions` |
| 输出 | `choices[].message` | 类型化 `output` Item 数组 |
| 工具定义 | 嵌套：`{type, function: {name, ...}}` | 扁平：`{type: "function", name, parameters}` |
| 工具往返 | assistant.tool_calls + tool 角色消息 | function_call Item + function_call_output Item，靠 `call_id` 关联 |
| 结构化输出 | `response_format` | `text: {format: {type: "json_schema", ...}}` |
| strict 默认 | 默认不开启 | 省略时尝试严格模式，不兼容回退为 `strict: false` |
| 服务端状态 | 无，全量重发 | `store` 默认开启，支持 `previous_response_id` |
| 内置工具 | 无 | web_search、file_search、code_interpreter 等 |
| 流式 | chunk + delta | 类型化事件 |

迁移的高频错误（官方指南列出）：function_call_output 回传时缺 `call_id`；以为 `previous_response_id` 会延续 `instructions`（不会，每次都要重发）；丢掉 reasoning Item 再传上下文导致推理模型准确率下降（见 [[3.2 状态管理：store、previous_response_id 与加密上下文]]、[[3.3 内置工具与推理模型]]）。

> [!example] 实践例子
> 「指令与数据分离」在项目里有同构设计：装配器产出的 ModelContext 把稳定区（系统职责、身份、技能指令）与轮转区（历史、证据、状态栏）分开管理，渲染顺序见 [[11.代码级逻辑：一次 LLM 调用如何装配上下文]] 与 [[7.KV Cache 与上下文布局]]。

## 边界问答

**1. Q：** Responses 是 Chat Completions 的版本升级吗，旧代码必须迁吗？
**A：** 不是升级，是并行的两个 endpoint；Chat Completions 未弃用，旧代码可以继续跑。但新能力只进 Responses：内置工具、完整推理支持——GPT-5.4 起 Chat Completions 上非 none 推理力度的工具调用已不可用，新模型（如 GPT-6 Astra 的工具调用）要求 Responses。新项目没有理由再选 Chat Completions。

**2. Q：** output 里的 reasoning Item 要保存吗？
**A：** 要。多轮场景把上轮 output 的 Item（包括 reasoning）拼回下轮 input，是官方推荐的无状态用法；丢弃 reasoning Item 会降低推理模型准确率（官方内部评测 SWE-bench 上差约 3%）。reasoning 的完整处理见 [[3.3 内置工具与推理模型]]。

**3. Q：** instructions 为什么不随 previous_response_id 延续？
**A：** 设计如此：链式引用只带对话数据，instructions 是每轮请求的显式输入。这样应用可以中途改指令而不断链，代价是忘了重发就丢指令——官方指南把它列为常见迁移错误。
