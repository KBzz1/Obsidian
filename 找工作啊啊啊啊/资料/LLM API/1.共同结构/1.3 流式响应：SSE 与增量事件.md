# 流式响应：SSE 与增量事件

## 为什么需要流式

模型逐 token 生成，一段长回答全部算完可能要几十秒。流式让服务端边生成边把增量推给客户端，用户在首 token 延迟（time to first token，从发请求到收到第一个生成片段的耗时）后就能开始阅读。对 Agent 应用，流式还承载过程可见性——工具调用参数、推理摘要都能边生成边展示。三家 API 都用 `stream: true`（Responses 用 `stream` 或 SDK 的 `stream()` 辅助方法）开启。

## SSE：共同的传输层

流式都跑在 SSE（Server-Sent Events）上：HTTP 响应头 `Content-Type: text/event-stream`，连接保持打开，服务端持续写入 `data: <JSON>\n\n` 格式的事件帧，每帧是一个 JSON 对象，直到连接关闭。SSE 是单向的（只有服务端到客户端），这正好匹配生成场景——请求早已发完，回来的只有增量。SSE 本身的 wire format、自动重连与代理缓冲问题见 [[5.SSE：HTTP 上的服务端单向推送]]。

三家的差异在事件语义，不在传输层。

## 三种增量设计

**Chat Completions：chunk + delta**。流被切成 `chat.completion.chunk` 对象，每个 chunk 里 `choices[].delta` 只带增量字段：第一帧 delta 带 `role`，中间帧带 `content` 的几个字符，工具调用帧带 `tool_calls[].function.arguments` 的增量片段，最后一帧带 `finish_reason`。客户端把所有 delta 的 `content` 拼接起来等于非流式的完整回答。设计特点：一种 chunk 结构表达所有内容类型，客户端靠字段是否出现来区分。

```text
data: {"choices":[{"delta":{"content":"今天"}}]}
data: {"choices":[{"delta":{"content":"天气"}}]}
data: {"choices":[{"delta":{},"finish_reason":"stop"}]}
```

消费这段流的代码骨架：遍历 chunk、按字段是否出现分流、拼接增量：

```python
stream = client.chat.completions.create(
    model="gpt-5",
    messages=[{"role": "user", "content": "讲讲今天的恢复建议"}],
    stream=True,
    stream_options={"include_usage": True},   # 让末尾附加一帧 usage
)
parts = []
for chunk in stream:
    if not chunk.choices:                     # usage 附加帧没有 choices
        continue
    delta = chunk.choices[0].delta
    if delta.content:                         # 文本增量：每次几个字符
        parts.append(delta.content)
    # 工具调用帧走 delta.tool_calls，参数是增量字符串片段
text = "".join(parts)                         # 拼完 = 非流式的完整回答
```

**Responses：类型化事件**。每个事件自带 `type` 字段，客户端按类型分支处理：`response.created`（响应对象创建）→ `response.output_text.delta`（文本增量）→ `response.completed`（终态，携带完整响应对象与 usage）。工具调用参数的增量走 `response.function_call_arguments.delta` 与 `.done`。相比 chunk + delta，类型化事件不用猜字段含义，每类信息有明确的起止事件。

**Anthropic：content block 生命周期事件**。流式事件模拟响应结构的组装过程：`message_start`（消息骨架与初始 usage）→ 对每个内容块 `content_block_start` → `content_block_delta`（增量子类型：`text_delta` 文本、`input_json_delta` 工具参数 JSON 片段、`thinking_delta` 思考文本、`signature_delta` 思考签名）→ `content_block_stop` → 全部块完成后 `message_delta`（携带 `stop_reason` 与最终 usage）→ `message_stop`。中间穿插 `ping` 保活事件。设计特点：事件序列与非流式响应的 content blocks 结构一一对应，收流即组装消息。

```python
text_parts = []
with client.messages.stream(              # SDK 的事件流封装
    model="claude-sonnet-4-5",
    max_tokens=1024,                      # 非流式的必填字段照样要传
    messages=[{"role": "user", "content": "讲讲今天的恢复建议"}],
) as stream:
    for event in stream:                  # 事件自带 type，按类型分支
        if event.type == "message_start":
            pass                          # 消息骨架与输入 token 计数
        elif event.type == "content_block_delta":
            if event.delta.type == "text_delta":
                text_parts.append(event.delta.text)   # 文本增量
            # input_json_delta：工具参数 JSON 的增量片段
        elif event.type == "message_delta":
            pass                          # stop_reason 与最终 usage 在这里
text = "".join(text_parts)
```

## 流式下的 usage 与停止原因

流式没有单一响应对象，元数据的交付位置三家不同：Chat Completions 在最后一个 chunk 给 `finish_reason`，usage 要显式传 `stream_options: {"include_usage": true}` 才在末尾附加一帧；Responses 把 usage 放进 `response.completed` 事件的响应对象里；Anthropic 在 `message_start` 给输入 token 计数，`message_delta` 给输出 token 与停止原因的最终值。做计费与观测时，流式代码必须处理到这些终止事件，不能在第一个空 delta 就收工。

## 边界问答

**1. Q：** 为什么用 SSE 而不是 WebSocket？
**A：** 生成场景是单向后推，SSE 够用且更简单：普通 HTTP 连接、自动重连语义、经过代理与网关的兼容性好。WebSocket 的双向能力（客户端中途发消息）在「一次请求一次生成」的模型里用不上；需要中途打断时，OpenAI 与 Anthropic 都提供独立的取消机制，不依赖传输层。WebSocket 的升级握手与全双工机制见 [[6.WebSocket：HTTP 升级出的全双工通道]]。

**2. Q：** 流式会影响生成内容吗？
**A：** 不会。同样的请求，流式与非流式的最终内容一致，差异只在交付方式。会影响内容的是采样参数与模型版本，不是 `stream` 开关。个别平台对流式与非流式的限速策略不同，那属于配额管理，不改变生成语义。

**3. Q：** 工具调用参数的流式增量怎么拼？
**A：** 三家都把工具参数的 JSON 作为增量片段推送：Chat Completions 是 `delta.tool_calls[].function.arguments` 的字符串片段，Anthropic 是 `input_json_delta.partial_json`，Responses 是 `function_call_arguments.delta` 事件的字符串片段。客户端把片段按顺序拼接成一个完整 JSON 字符串再解析，解析前必须等该工具调用的流结束——片段本身不是合法 JSON。
