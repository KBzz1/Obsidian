# 多轮对话：无状态服务与客户端拼接

## 每轮重发全量历史

LLM API 服务端不保存对话（见 [[1.1 LLM API 的共同形态：endpoint、鉴权与请求骨架]]），所以多轮对话的实现是：客户端把「到目前为止的完整对话」作为输入数组重发，服务端基于全量上下文生成下一条消息。第 N 轮请求里的输入数组大致是：

```python
messages = [
    {"role": "system",    "content": "你是一个健康助手"},   # 系统指令，每轮固定重发
    {"role": "user",      "content": "我今天跑了五公里"},   # 第 1 轮用户输入
    {"role": "assistant", "content": "不错，配速如何？"},   # 第 1 轮模型回复
    {"role": "user",      "content": "六分半"},             # 第 2 轮用户输入
]
# 把整个数组重发给 API，模型接着生成第 2 轮回复
```

这个模式叫历史重发，有三层代价：输入 token 数随轮数线性增长且按输入计费；数组总长不能超过模型的上下文窗口（context window，模型一次能处理的 token 上限）；生成质量对历史质量敏感——历史里的错误内容会被模型当作既定事实继续用。

唯一的协议级例外是 OpenAI Responses 的服务端存储：`previous_response_id` 让服务端代管历史，客户端只发新增消息，机制与代价见 [[3.2 状态管理：store、previous_response_id 与加密上下文]]。

## 拼接的结构约束

历史数组不是任意堆放，两家各有约束，违反会直接报 400 错误：

**角色交替**。OpenAI 与 Anthropic 都要求消息按对话顺序排列；Anthropic 更严格——第一条必须是 `user` 消息，且最后一条消息如果是 `assistant`，模型会从它结尾继续写下去而不是新起一条回复。这个行为被 Anthropic 文档化为 prefill（预填充）特性：应用可以主动放半条 assistant 消息，让模型按指定的开头续写，用来强约束回复格式或语气。

```python
messages = [
    {"role": "user",      "content": "用 JSON 总结今天的训练"},
    # prefill：历史末尾放半条 assistant 消息
    {"role": "assistant", "content": '{"summary": "'},
]
# 模型从半条消息的结尾续写而不是新起回复，
# 生成内容直接拼成合法 JSON 的后半段，开头格式被硬约束
```

**连续同角色合并**。Anthropic 允许相邻同角色消息存在（服务端会合并处理），OpenAI 的 messages 数组同样接受连续 user 消息。工具调用的结果回传正是借道这一规则：OpenAI 用独立 `tool` 角色（见 [[2.2 函数调用：tools、tool_calls 与 tool 角色]]），Anthropic 把 tool_result 块放进 `user` 消息（见 [[4.2 工具调用：tool_use、tool_result 与 tool_choice]]）。

**系统指令的位置**。OpenAI 把系统指令写成第一条 `system`（或新模型的 `developer`）消息，混在 messages 数组里；Anthropic 把它提出来做独立的顶层 `system` 字段，不占 messages。差异细节见 [[4.1 请求结构：system 字段与 content blocks]]。

## 历史增长的两个工程后果

**计费随轮数上涨**。每轮都为全部历史付输入 token 费用，长对话的第 50 轮请求比第 1 轮贵一个数量级。缓解手段是 prompt caching（前缀命中缓存的输入按折扣计费）与历史压缩（把旧对话摘要成短文本替换原文）。OpenAI 对满足条件的前缀自动隐式缓存，Anthropic 要求显式在内容块上标 `cache_control` 断点，机制见 [[4.3 thinking 与 prompt caching]]。

**裁剪权在客户端**。正因为历史由客户端拼，应用可以自由裁剪：丢弃旧轮次、摘要压缩、只保留工具调用对。这是无状态设计的回报——服务端存会话的产品（如 OpenAI 早期的 Assistants API，已于 2026-08-26 下线）反而把这层控制权收走了。Agent 工程里「历史整理」由此成为独立的上下文工程问题。

> [!example] 实践例子
> 健康管理项目把这层做成了显式设计：上下文装配器每轮按 ContextPolicy 决定历史里哪些消息入选，历史轨迹的整理与裁剪策略见 [[6.历史轨迹与上下文整理]]，一次真实调用的装配走查见 [[11.代码级逻辑：一次 LLM 调用如何装配上下文]]。

## 边界问答

**1. Q：** 每轮重发全量历史，服务端会不会重复计费？
**A：** 会。重发的部分就是本轮的输入 token，按输入价计费。OpenAI Responses 的 `previous_response_id` 也不例外——官方迁移指南明确说链上先前响应的输入 token 仍按输入计费。缓存的减免是折扣，不是免除。

**2. Q：** 客户端能不能改历史，比如删掉一条模型说错的话？
**A：** 能，这正是客户端拼接的权利。历史数组就是普通数据，发送前怎么改都行，模型只看到最终发过去的版本。工程上常用它做历史修正与摘要压缩；副作用是模型对历史的信任没有校验，改写后模型无法区分原始对话与改写版。

**3. Q：** 上下文窗口快满时，API 会自动截断历史吗？
**A：** 默认不会——超长直接报错。OpenAI Responses 提供显式的 `truncation` 参数（`"auto"` 时服务端截断中间内容），Chat Completions 与 Anthropic Messages 都由应用自己保证不超窗。应用侧的对应设计是历史裁剪策略，见 [[6.历史轨迹与上下文整理]]。
