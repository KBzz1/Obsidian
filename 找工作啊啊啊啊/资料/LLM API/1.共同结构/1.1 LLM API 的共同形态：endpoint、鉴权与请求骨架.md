# LLM API 的共同形态：endpoint、鉴权与请求骨架

## 一次调用是一次 HTTP POST

无论 OpenAI 还是 Anthropic，对话模型 API 的形态都是同一件事：向一个 HTTPS endpoint 发 JSON POST 请求，同步拿回 JSON 响应。模型不是长连接服务，也没有会话——每次请求自带模型看到的全量输入，服务端算完返回，连接即结束（HTTP 请求响应与无状态的协议基础见 [[3.HTTP：请求响应、方法、头部与状态码]]，「长连接」的传输层含义见 [[2.TCP 连接：握手、可靠传输与长连接]]）。三家当前的主端点：

| 服务商 | endpoint | 对象类型 |
|---|---|---|
| OpenAI Chat Completions | `POST /v1/chat/completions` | `chat.completion` |
| OpenAI Responses | `POST /v1/responses` | `response` |
| Anthropic Messages | `POST /v1/messages` | `message` |

请求体的骨架三家一致：选哪个模型（`model`）、给什么输入（OpenAI 是 `messages` 或 `input`，Anthropic 是 `messages`）、加什么生成参数（`temperature`、停止条件、输出上限）。这个骨架来自 OpenAI 2023 年定下的形态，Anthropic 沿用了字段名但重排了内部结构。剥掉 SDK 看原始 HTTP 层，一次调用长这样：

```python
import requests

resp = requests.post(
    "https://api.openai.com/v1/chat/completions",   # 换成上表任一端点即换服务
    headers={"Authorization": "Bearer sk-..."},     # 鉴权放请求头，不进请求体
    json={
        # 输入：对话历史（Responses 的同位字段叫 input）
        "messages": [{"role": "user", "content": "我今天跑了五公里"}],
        "model": "gpt-5",              # 模型标识：决定能力与计费
        "temperature": 0.7,            # 生成参数：采样、停止条件、输出上限
    },
)
# resp.json() 是同步返回的完整 JSON；服务端算完才返回，连接即结束
```

## 鉴权

OpenAI 两类 API 用标准 HTTP Bearer 鉴权：`Authorization: Bearer <API key>`。Anthropic 用自定义头：`x-api-key: <API key>`，且要求同时带 `anthropic-version` 头声明 API 版本（如 `2023-06-01`），版本不对的请求会被拒绝——这是两家在协议习惯上的一个显式差异，Anthropic 把 API 版本做成了显式协商，OpenAI 靠平台整体演进。

```python
# OpenAI：标准 Bearer 头，Chat Completions 与 Responses 同一鉴权方式
headers_openai = {
    "Authorization": "Bearer sk-...",    # key 只出现在请求头，不进请求体
}

# Anthropic：自定义 key 头，且必须同时声明 API 版本
headers_anthropic = {
    "x-api-key": "sk-ant-...",           # 自定义鉴权头，不走 Bearer
    "anthropic-version": "2023-06-01",   # 显式版本协商，不匹配即拒绝
}
```

key 一律只放在请求头，不出现在请求体里，公网传输段的保密性由 HTTPS 的 TLS 层保证（见 [[4.HTTPS 与 TLS：加密握手与证书]]）；key 泄露等于别人可以花你的钱，轮换与撤销都在各家控制台做。

## 响应里的三块共有信息

响应体除了模型生成的内容外，三家都返回三类元数据，它们是上层工程（计费、循环控制、观测）的直接输入。以 Chat Completions 的响应为例，三块在 JSON 里各占的位置：

```python
resp.json() == {
    "id": "chatcmpl-abc123",             # 本次调用的唯一标识，排障时报给官方
    "choices": [{
        "message": {
            "role": "assistant",         # 固定为 assistant
            "content": "干得漂亮，注意拉伸",   # ① 内容本体：模型产出的内容
        },
        "finish_reason": "stop",         # ② 停止原因：这轮为什么停在这里
    }],
    "usage": {                           # ③ 用量：计费与限速的第一手数据
        "prompt_tokens": 52,             #   输入 token 数
        "completion_tokens": 18,         #   输出 token 数
        "total_tokens": 70,              #   两者合计
    },
}
```

**内容本体**。Chat Completions 是 `choices[].message.content`；Responses 是 `output` 数组里的 `output_text` 等类型化 Item；Anthropic 是 `content` 数组里的 text / tool_use 块。形态不同，语义相同：模型产出的结构化内容。

**停止原因**。回答「这轮为什么停在这里」：正常说完（OpenAI `finish_reason: "stop"`，Anthropic `stop_reason: "end_turn"`）、撞了输出长度上限（`"length"` / `"max_tokens"`）、要调工具（`"tool_calls"` / `"tool_use"`）、触发停止序列（`"stop"` / `"stop_sequence"`）、安全拒绝（`"content_filter"` / `"refusal"`）。Agent 循环靠它分支：看到工具调用原因就去执行工具再发下一轮，看到正常停止就收尾。

**用量**。`usage` 字段报告本轮输入与输出的 token 数。三家的公共字段是输入 token 与输出 token（OpenAI 叫 `prompt_tokens` / `completion_tokens`，Responses 与 Anthropic 叫 `input_tokens` / `output_tokens`）；各家再叠自己的扩展，如 OpenAI 的缓存命中 token（`cached_tokens`）与推理 token（`output_tokens_details.reasoning_tokens`）、Anthropic 的缓存写入与读取（`cache_creation_input_tokens` / `cache_read_input_tokens`）。token 是 API 计费与限速的统一单位，usage 是成本核算和预算控制的第一手数据。

> [!example] 实践例子
> 健康管理项目把这三块元数据都接进了治理层：模型网关回来的 usage 交给任务预算（[[4.任务预算与任务准入]]），停止原因驱动 Agent 循环分支，观测数据边界见 [[3.Task、Run 与 Trace 身份关联]]。

## 无状态假设贯穿三家

三家 API 的服务端默认不记得你是谁：上一轮说了什么，服务端不保存（OpenAI Responses 的服务端存储是显式可选项，见 [[3.2 状态管理：store、previous_response_id 与加密上下文]]），因此多轮对话由客户端拼接历史实现，代价与做法见 [[1.2 多轮对话：无状态服务与客户端拼接]]。

## 边界问答

**1. Q：** 为什么 LLM API 设计成无状态，而不是像传统聊天服务那样服务端存会话？
**A：** 无状态让服务端可以任意水平扩展与路由请求，不需要会话粘滞；状态放客户端也让应用方完全掌控模型看到的历史（裁剪、改写、注入都由应用决定）。代价是每轮全量重发输入，token 成本随对话变长线性上涨，这个代价由 prompt caching 缓解（OpenAI 隐式缓存、Anthropic 显式 `cache_control`，见 [[4.3 thinking 与 prompt caching]]）。OpenAI Responses 后来补的服务端状态是产品化的便利层，不是协议层的必需。

**2. Q：** 三家 endpoint 路径里的 `/v1` 意味着什么？
**A：** 是 API 的主版本号，路径级版本控制——破坏性变更只在新主版本发生。Anthropic 额外用 `anthropic-version` 请求头做细粒度版本协商，OpenAI 的平台演进整体在 `/v1` 内部消化（Responses 是同版本下的新 endpoint，不是 `/v2`）。

**3. Q：** 同步 POST 拿完整个响应，和流式是什么关系？
**A：** 同步是完整语义：请求发出去，服务端把整段生成算完再一次性返回。流式（`stream: true`）是同一请求的另一种交付方式，边生成边推增量事件，见 [[1.3 流式响应：SSE 与增量事件]]。两种方式的最终内容一致，差异只在交付节奏与首字延迟。
