# thinking 与 prompt caching

## thinking：显式的思考预算

Claude 的扩展思考（extended thinking）在生成最终回复前先产出思考内容。开关是顶层 `thinking` 参数：

```python
resp = client.messages.create(
    model="claude-sonnet-4-5",
    max_tokens=2000,                       # 上限必须大于 budget，否则报错
    thinking={
        "type": "enabled",                 # enabled / disabled / adaptive（按需自适应）
        "budget_tokens": 2048,             # 思考预算，下限 1024
        "display": "summarized",           # 思考内容的呈现：summarized / omitted
    },
    messages=[...],
)
```

`budget_tokens` 是思考阶段的 token 上限（不含最终回复），下限 1024。响应 content 里思考内容以 `thinking` 块出现，位于 text 块之前；计费上思考 token 计入输出。

回传约束是硬性的：多轮对话把上轮的 thinking 块拼回历史时，必须带上它的 `signature` 字段原样回传——签名被改或缺失，请求直接 400。签名的作用是防篡改：思考内容是模型推理链的一部分，被改写会破坏推理一致性。另一变体 `redacted_thinking` 块是安全过滤后的密文形态，同样必须原样回传。这与 OpenAI Responses 的 encrypted_content（见 [[3.2 状态管理：store、previous_response_id 与加密上下文]]）是同一工程问题的两家解法：推理上下文必须完整传递，但不以明文开放。

## prompt caching：显式断点与缓存计量

Anthropic 的提示缓存要求显式标记：在内容块上标 `cache_control`，声明「从这里往前是可缓存前缀」。命中条件是前缀完全一致——逐 token 相同才复用，差一个字符就全部 miss。

```python
resp = client.messages.create(
    model="claude-sonnet-4-5",
    max_tokens=1024,
    system=[                                        # 长指令用块数组形态
        {"type": "text", "text": LONG_SYSTEM_PROMPT,
         "cache_control": {"type": "ephemeral"}},   # 断点：到此为止的前缀可缓存
    ],
    messages=[...],
)
```

规则与计量（2026-09 文档口径）：`type` 目前只有 `ephemeral`，可选 `ttl`（`"5m"` 默认 / `"1h"`）；一个请求最多 4 个断点（system 一处、messages 两处、tools 一处是典型布局）；顶层快捷参数会在最后一个可缓存块上自动打标。usage 里的计量：`cache_creation_input_tokens`（本轮写入缓存的 token，写入有加价）、`cache_read_input_tokens`（命中缓存的 token，按折扣计费）——缓存读写的价格系数随模型与时间调整，以官方价格页为准，机制本身是稳定口径。

缓存的命中依赖稳定前缀，这把「上下文布局」变成性能问题：system 指令、工具定义这些每轮不变的内容放前面，用户消息这类变化内容放后面。断点打在「变与不变的分界线」上才有价值。

## 两个机制如何配合

thinking 与 caching 不是两个孤立开关，多轮 Agent 场景里它们咬合：思考块回传进历史（保推理一致性），历史前缀稳定（保缓存命中）。布局模板：system（断点）→ tools 定义（断点）→ 历史消息（含 thinking / tool_use / tool_result 块）→ 本轮新增。每轮往数组尾部追加，前缀不动，缓存链持续命中；一旦改写历史中部（裁剪、摘要），从改动点起全部失效重算。

OpenAI 侧对照：OpenAI 的前缀缓存是隐式的（满足长度与前缀条件自动缓存，`cached_tokens` 计量），Anthropic 是显式的（应用声明断点、读写分开计量）。显式版本多一层控制（能精确圈定缓存边界），也多一层心智负担（断点打错就白写）。

## 边界问答

**1. Q：** budget_tokens 设多大合适，思考是不是越多越好？
**A：** 下限 1024 起步，复杂任务（多工具编排、数学、长链推理）给到数千；预算花不完模型会提前结束思考，不会硬凑。思考 token 按输出计费并计入延迟，开放对话类任务开思考通常不划算——按任务分级配置，对照项目 [[4.任务预算与任务准入]]。

**2. Q：** 缓存断点为什么最多 4 个，打在哪最值？
**A：** 断点数量是服务侧资源约束（每段缓存都要存与查）。打点原则是「变化频率的分界线」：system 指令与工具定义几乎不变，断点打在它们之后；历史消息如果整段稳定，可以在历史尾再放一个，让新增消息前的前缀都命中。4 个用不完没关系，打错位置（放在每轮都变的内容后面）才是浪费。

**3. Q：** 前缀差一个字符就 miss，这对提示词工程意味着什么？
**A：** 动态内容（时间戳、随机 id、每轮变化的指令）不许出现在缓存前缀里；system 里要放变量时，把变量挪到前缀之后的用户消息或用模板固定。这与项目「稳定区 / 轮转区」的分区原则完全一致，见 [[7.KV Cache 与上下文布局]]。

**4. Q：** thinking 块和 OpenAI 的 reasoning Item 是不是一回事？
**A：** 概念同构（推理上下文需完整回传），开放度不同：Anthropic 的 thinking 内容在 display 配置下可读（summarized），OpenAI 只开放摘要（summary 字段），原文两家用密文（signature 校验 / encrypted_content）保护。面试口径：两家都把「推理过程」做成一等公民数据，而不是黑盒延迟。
