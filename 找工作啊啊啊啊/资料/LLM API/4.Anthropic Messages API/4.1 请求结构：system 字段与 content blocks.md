# 请求结构：system 字段与 content blocks

## 必填三件套，max_tokens 强制

Messages API（`POST /v1/messages`）的必填字段是 `model`、`max_tokens`、`messages` 三个。输出上限必填是与 OpenAI 的显式差异——Chat Completions 的输出上限可省略（默认放开到模型上限），Anthropic 强制应用显式声明。`max_tokens` 允许设为 0，语义是只处理输入不生成内容，专门用来预热 prompt cache（见 [[4.3 thinking 与 prompt caching]]）。

```python
resp = client.messages.create(
    model="claude-sonnet-4-5",        # 模型标识
    max_tokens=1024,                  # 必填：输出 token 上限
    system="你是健康助手",              # 系统指令：独立顶层字段，不在 messages 里
    messages=[                        # 对话历史：role + content
        {"role": "user", "content": "我今天跑了五公里"},
    ],
)
```

## system 是独立字段，不是消息角色

OpenAI 把系统指令做成 messages 数组里的第一条 system 消息；Anthropic 把它提出来做顶层 `system` 字段，取值可以是字符串，也可以是带 `cache_control` / `citations` 的文本块数组（块数组形态是给长指令做缓存断点用的，见 [[4.3 thinking 与 prompt caching]]）。API 里没有名为 system 的消息角色。

这个差异的工程含义：网关层做两家适配时，指令要在「消息数组第一项」与「独立字段」之间搬运；渲染顺序（指令在前、对话在后）两家一致。

## content blocks：消息内容的基本单位

`messages` 里每条消息是 `role`（`user` / `assistant`，基础对话只有这两种）加 `content`。content 可以是字符串（等价于单个文本块），完整形态是块数组——这是 Anthropic 数据模型的核心：一条消息由多个类型化块组成，文本、图像、工具调用、工具结果、思考过程都是块。

```python
messages = [
    {"role": "user", "content": [
        {"type": "text", "text": "这次跑步的轨迹截图"},       # 文本块
        {"type": "image", "source": {                         # 图像块：多模态输入
            "type": "base64",                                 # 来源形态：base64 / url / file
            "media_type": "image/jpeg",
            "data": "...",
        }},
    ]},
]
```

输入侧的块类型：`text`（文本，可带 `cache_control` 与 `citations`）、`image`（图像）、`document`（PDF 等文档）、`tool_use` / `tool_result`（工具往返，见 [[4.2 工具调用：tool_use、tool_result 与 tool_choice]]）、`thinking` / `redacted_thinking`（思考块回传，见 [[4.3 thinking 与 prompt caching]]），以及服务器端工具的结果块。输出侧的 content 同样是块数组：一次响应里 text 块与 tool_use 块按生成顺序排列。

拼接规则两条：连续同角色消息会被服务端合并处理；历史末尾放 `assistant` 消息时，模型从它的结尾续写（prefill 特性，见 [[1.2 多轮对话：无状态服务与客户端拼接]]）。第一条消息必须是 `user`。

## 响应与停止原因

```python
{
  "id": "msg_abc123",                       # 消息唯一标识
  "role": "assistant",                       # 固定为 assistant
  "content": [
    {"type": "text", "text": "干得漂亮……"},   # 文本块；要调工具时换成/混入 tool_use 块
  ],
  "stop_reason": "end_turn",                 # 停止原因
  "usage": {
    "input_tokens": 52,                      # 输入 token
    "output_tokens": 18,                     # 输出 token
    "cache_creation_input_tokens": 0,        # 本轮写入缓存的 token
    "cache_read_input_tokens": 0             # 本轮命中缓存的 token
  }
}
```

`stop_reason` 枚举：`end_turn`（正常说完）、`max_tokens`（撞输出上限）、`stop_sequence`（命中停止序列）、`tool_use`（请求调工具）、`refusal`（安全拒绝）、`model_stop`（模型自行终止）。usage 里缓存读写单列是 Anthropic 的特色——缓存是显式资源，计量透明。

## 采样参数的弃用现状（2026-09）

新世代 Claude 模型上，传统采样参数已走向弃用：`temperature` 仅接受 1.0，`top_p` 仅接受不低于 0.99，`top_k` 任何取值都被拒绝。可控性的方向从采样旋钮转向两类参数：停止序列 `stop_sequences` 照常工作；输出控制力（推理力度、格式约束）走 `output_config`（`effort` 与 `format: {type: "json_schema"}`——结构化输出在顶层配置，不是 OpenAI 式的 response_format 字段）。写跨家网关时别把 OpenAI 的 temperature 语义照搬给 Claude 新模型。

> [!example] 实践例子
> 「一条消息由类型化块组成」与项目的 ContextManifest 同构：模型看到的每一块内容都有类型与来源标注，清单化交接见 [[4.ContextManifest 与模型可见上下文]]；采样参数收敛进网关统一配置、节点不接触供应商参数的边界见 [[3.生产运行时治理边界]]。

## 边界问答

**1. Q：** max_tokens 必填是防呆设计还是定价设计？
**A：** 更接近防呆加计量：输出 token 是主要成本项，强制声明让每次调用的成本上限在请求里显式可见，配合任务预算直接可算（对照项目 [[4.任务预算与任务准入]]）。设 0 只预热缓存是它的计量极端形态。

**2. Q：** content 字符串和块数组怎么选？
**A：** 单文本用字符串最省事；需要多模态、工具结果、缓存断点、引用标注时用块数组。两种形态语义等价，字符串就是单 text 块的语法糖。

**3. Q：** 为什么 Anthropic 把 system 提出消息数组？
**A：** 结构上把「行为规范」与「对话数据」分开，system 天然是稳定前缀（缓存友好，见 [[4.3 thinking 与 prompt caching]]），也不会被多轮拼接的裁剪逻辑误伤。OpenAI Responses 的 instructions 字段殊途同归——两家新一代设计都把指令从消息流里拆了出来。

**4. Q：** 温度参数弃用后，要降低输出随机性怎么办？
**A：** 新模型的官方路径是靠 prompt 与输出约束而不是采样温度：结构化输出用 `output_config.format`，行为稳定性靠 system 指令与工具 schema 约束。若业务确实依赖低温采样，只能选仍支持它的模型或服务商——这是跨家网关要登记的能力差异项。
