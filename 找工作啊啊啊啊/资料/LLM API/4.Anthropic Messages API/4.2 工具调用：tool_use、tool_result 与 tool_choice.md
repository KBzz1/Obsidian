# 工具调用：tool_use、tool_result 与 tool_choice

## 定义：扁平的三字段

`tools` 数组里每个自定义工具三个核心字段，没有 OpenAI 式的 function 包裹层：

```python
tools = [{
    "name": "record_run",            # 工具名（最长 200 字符）
    "description": "记录一次跑步",    # 模型判断何时使用的依据
    "input_schema": {                # 参数的 JSON Schema（OpenAI 叫 parameters）
        "type": "object",
        "properties": {
            "distance_km": {"type": "number"},
            "duration_min": {"type": "number"},
        },
        "required": ["distance_km"],
    },
}]
```

`tool_choice` 的取值：`{"type": "auto"}`（默认，模型自行决定）、`{"type": "any"}`（必须调工具，等价 OpenAI 的 `required`）、`{"type": "tool", "name": "record_run"}`（强制调指定工具）、`{"type": "none"}`（禁用）。所有取值都可加 `disable_parallel_tool_use: true`，把默认的并行调用改成每轮至多一个——OpenAI 用独立的 `parallel_tool_calls` 布尔表达同一件事。

`any` / `tool` 的强制模式会比 auto 多消耗系统提示 token（官方文档明示的计费细节）。想在 auto 模式下引导调用频率，官方建议用 system 指令（轻则「先查再答」，重则「回答前必须先调工具」），真要硬约束再上 tool_choice。

## 响应：tool_use 块，input 是对象

模型决定调工具时，响应的 `content` 数组里出现 `tool_use` 块，`stop_reason` 为 `"tool_use"`：

```python
resp.content = [
    {"type": "tool_use", "id": "toolu_abc123",   # 调用请求唯一标识（toolu_ 前缀）
     "name": "record_run",
     "input": {"distance_km": 5.0}},             # 参数：已是对象，不是 JSON 字符串
]
resp.stop_reason == "tool_use"
```

与 OpenAI 的两个结构差异值得记：参数直接是对象（`input`），不需要 `json.loads`——流式场景下它同样逐片段推送（`input_json_delta`，见 [[1.3 流式响应：SSE 与增量事件]]），但终态响应里给的是组装好的对象；模型可以一段回复里先写文字再带工具调用（text 块与 tool_use 块混排），比 Chat Completions「content 与 tool_calls 并列在 message 上」的表达更贴生成顺序。

官方文档还记录了一个行为观察：必填参数缺失时，Opus 倾向于识别缺失并向用户追问，Sonnet 更可能自己推断一个合理值——工具 schema 的 required 与执行侧校验不能省，见 [[7.Tool Result 与错误协议]] 的项目对照。

## 回传：tool_result 块放进 user 消息

工具结果不设独立角色，作为 `tool_result` 块放在下一条 `user` 消息的 content 数组里：

```python
messages = [
    {"role": "user", "content": "帮我记录今天跑了五公里，用时28分钟"},
    {"role": "assistant", "content": [resp.content[0]]},      # 上轮响应原样回传（tool_use 块）
    {"role": "user", "content": [                             # 结果借 user 消息回传
        {"type": "tool_result",
         "tool_use_id": "toolu_abc123",    # 对应 tool_use 块的 id
         "content": "已记录，编号 run_88",  # 结果内容，支持字符串或块数组
         "is_error": False},               # 错误标志：True 时模型按失败处理
    ]},
]
```

`tool_use_id` 必须与 tool_use 块的 `id` 配对（校验规则与 OpenAI 的 tool_call_id 相同）。`is_error: true` 是显式的错误通道：执行失败不是抛异常终止循环，而是把错误内容回传给模型，让它决定重试、换参数或告知用户——与函数调用成功的路径统一，错误成为模型可见的普通输入。并行调用时多个 tool_result 块放同一条 user 消息里，按调用顺序排列。

## 服务器端工具：type 版本化的另一族工具

`tools` 里除了自定义工具，还有一族用 `type` 声明的服务器端工具：`web_search_*`（联网搜索）、`web_fetch_*`（取网页）、`code_execution_*`（沙箱执行代码）、`bash_*`、`text_editor_*`、`memory_*`，以及 2026-08 新增的 `browser_toolset_*` 与 `computer_toolset_*`（浏览器与桌面操作）。名称里的日期后缀是版本号（如 `web_search_20260209`），由 Anthropic 基础设施执行，执行过程在响应里以 `server_tool_use` 与对应结果块呈现，应用侧只声明与付费。这与 OpenAI Responses 内置工具（见 [[3.3 内置工具与推理模型]]）是同一层概念的两家实现。

自定义工具同样支持 `"strict": true` 的 schema 强制（strict tool use），语义与 OpenAI 的 strict 同向：约束模型生成的参数严格匹配 input_schema。

## 边界问答

**1. Q：** tool_result 为什么放 user 消息里，而不是像 OpenAI 那样设独立 tool 角色？
**A：** Anthropic 的消息模型只有 user / assistant 两种对话角色，所有非模型侧的输入（用户文本、工具结果、图片）都是 user 方的内容，用块类型区分来源。OpenAI 的 tool 角色与它在语义上等价，网关适配时做块 ↔ 角色消息的双向翻译即可。

**2. Q：** 强制工具调用（any / tool）什么时候用？
**A：** 用在「这一步必须产生结构化动作」的节点：意图分类、字段抽取、必须落库的记录。注意计费差异与副作用——强制模式禁止模型直接回复用户，用户问了个跑题问题时模型也必须挑一个工具调，所以面向开放对话的入口别开强制。

**3. Q：** 服务器端工具和自定义工具混用，结果怎么区分？
**A：** 服务器端工具的执行与结果都在响应 content 里完成（server_tool_use 块及其结果块），不需要应用回传；自定义工具的 tool_use 块必须由应用执行并以 tool_result 回传。循环代码按块类型分流：看到 server_tool_use 相关结果直接跳过，看到 tool_use 才进执行分支。
