# 执行模型与任务边界

## 控制平面职责

控制平面负责管理一次请求或任务如何进入智能体运行时、如何推进，以及在人工中断或执行异常之后如何继续。它维护的是执行状态，而不是业务事实。

业务事实有自己独立的去处：已经确认的训练计划和历史训练记录仍然写入业务数据库；尚未确认的计划由草稿存储（Draft Store）保存；LangGraph 状态和检查点只记录当前执行到了哪里，以及恢复执行需要的运行状态（分层定义见 [[5.Task Runtime、Checkpoint 和业务状态#四层状态分层]]）。

## 执行单元与编排方式

执行单元指控制平面管理的一次执行：一个智能体调用或一个持久任务，被选择、启动、推进，必要时暂停和恢复。系统目前有两个领域智能体——训练智能体与饮食智能体——加一个持久存在的会话主管（见第五章 [[4.Supervisor 架构与委派]]）。

它们之间的差异不在能力，而在两个相互独立的维度：编排方式和生命周期。

### 能力层是共享的

训练智能体、饮食智能体和每日计划运行在同一层能力（工具与记忆）之上，任何一类执行单元都不独占某套工具。训练/饮食不是只能回答简单问题的普通处理器：它们同样能调用工具、读写记忆，完成查询、修改、生成等操作。每日计划能调用的训练计划工具，训练智能体同样能调用；反过来，这些工具也不会因为每日计划是固定流程就被排除在训练/饮食的能力之外。能力的可见范围由第二章的 [[8.能力渐进装载]] 按业务域与技能收敛，记忆归第三章；二者都不以「自由智能体还是固定工作流」为分界。

### 维度一：编排方式

这根轴就是 LangGraph 官方的应用形态分类：Workflow 与 agent（见 [[1.1 LangGraph 是什么]]）。官方的区分标准只有一个——过程决定权归谁：代码路径提前确定的叫 Workflow，由 LLM 自己决定过程和工具用法的叫 agent。

- **自由编排（ReAct，推理-行动循环）**，即官方的 agent 形态：训练智能体和饮食智能体收到 DomainTask 后，由模型自主决定调用哪些工具、读哪些记忆、按什么顺序完成。步骤不是预先写死的；简单请求直接走确定性路径，只有任务复杂到需要显式拆步骤时，才按需触发 Planner（见 [[9.Planner 按需规划]]）。
- **预编排（领域工作流）**，即官方的 Workflow 形态：每日计划是一段提前编排好的固定工作流，步骤预先确定，由 Harness 按状态机推进，模型不负责决定「下一步做什么」。它是训练智能体的领域工作流，作为一项领域能力被调用（见第五章 [[5.Domain Agent 执行模型]]）。

两个维度落到代码上是两种不同的图构建方式。下面按 LangGraph 真实 API 写成设计示意：框架调用是真实接口，业务节点函数尚未实现。

自由编排的训练智能体：

```python
# 自由编排：训练/饮食智能体（ReAct）——步骤由模型现场决定
from langgraph.prebuilt import create_react_agent

workout_agent = create_react_agent(
    model=llm,          # 底层模型：自主决定调哪些工具、按什么顺序
    tools=query_tools,  # 共享能力层的工具与记忆，谁都不独占
)
```

图里没有写死的步骤序列：模型自己循环「推理 → 调工具 → 看结果 → 再推理」，同一张图处理「查昨天深蹲」和「改这周计划」走的是不同的路径。预编排的每日计划则相反：

```python
# 预编排：每日计划（领域工作流）——步骤在设计期写死，由状态机推进
from langgraph.graph import StateGraph, START, END

# 图状态：各节点共享读写的数据结构
builder = StateGraph(DailyPlanState)

# 节点即流程步骤：generate_draft 生成草稿，写入草稿存储；
# prepare_invocation 经工具运行时固化动作，创建调用实例；
# wait_for_human 调用 interrupt() 停下等用户确认；
# execute_invocation 执行已固化的调用实例；complete_task 收尾，草稿与任务进终态
builder.add_node("generate_draft", generate_draft)
builder.add_node("prepare_invocation", prepare_invocation)
builder.add_node("wait_for_human", wait_for_human)
builder.add_node("execute_invocation", execute_invocation)
builder.add_node("complete_task", complete_task)

# 边在设计期固定：「下一步做什么」不经过模型，模型只在节点内部干活
builder.add_edge(START, "generate_draft")
builder.add_edge("generate_draft", "prepare_invocation")
builder.add_edge("prepare_invocation", "wait_for_human")
builder.add_edge("wait_for_human", "execute_invocation")
builder.add_edge("execute_invocation", "complete_task")
builder.add_edge("complete_task", END)
```

`add_node` / `add_edge` 把每一步是哪个节点、按什么顺序全部定死，运行时按这张静态结构推进；`wait_for_human` 内部如何停下来见 [[6.HIL 与恢复#中断协议（Interrupt）]]。

官方同时强调 Workflow 与 agent 两类可以混排同一张图——需要可靠可预测的地方用确定性步骤，需要灵活的才交给模型，这是它反复强调的核心卖点。本系统处处是这种混排：每日计划图的拓扑（生成草稿 → 固化动作 → 等确认）由边和路由函数确定，节点内部生成草稿是模型调用；Supervisor 输出 SupervisorAction 是模型决策，根运行时校验后落状态是确定性步骤；任务入口匹配、状态机、恢复校验也全是确定性代码，task 内部跑什么才交给模型。

### 维度二：生命周期

- **请求级作用域（request-scoped）**：生命周期绑定单次请求，通常在一个 HTTP 请求内完成，请求结束即结束。
- **任务级作用域（task-scoped）**：跨越多个请求。创建当天训练计划时，流程可能先补充参数，再检查已有计划，生成草稿后等待用户确认；用户之后还可能修改草稿、再次确认，最后才正式保存。整个过程跨越多个请求，因此不能和普通智能体调用共用同一种生命周期，需要独立的任务生命周期（见 [[4.Conversation 与 Task 生命周期]]）。

在目前的系统里，这两个维度在每日计划上恰好重合：每日计划既是预编排、也是任务级；训练/饮食的常规 ReAct 调用既是自由编排、也是请求级。把它们拆成两个维度，是为了避免把「没有工具、没有记忆」误当成请求级的含义，也避免把「固定流程」误当成「独立智能体」。官方的 Workflow / agent 分类只回答编排这一根轴，不回答生命周期：一个 agent 形态的执行可以是请求级（常规问答），也可以是任务级（第五章的后台 AsyncAgentTask）。生命周期这根轴是本系统在官方分类之外自建的，两轴组合出系统里的全部形态：

| | 预编排（Workflow 形态） | 自由编排（agent 形态） |
| --- | --- | --- |
| 任务级（task） | 每日计划 T100 | 后台 AsyncAgentTask |
| 请求级 | 领域工作流被请求级调用 | 训练/饮食常规问答 |

### 升级为持久任务的标准

**持久任务指执行状态需要持久保存、能跨请求暂停和恢复的任务**。不是每个智能体调用都需要任务检查点：训练/饮食的常规请求失败以后可以重新执行，所以仍然按请求级作用域处理。只有满足以下任一条件的流程，才升级成持久任务：

- 需要跨请求暂停、等待人工确认
- 需要服务重启以后恢复
- 中间执行成本已经高到不希望从头重跑

持久化机制本身见 [[5.Task Runtime、Checkpoint 和业务状态]]。第五章进一步区分同步执行与后台异步执行：后台任务同样是持久任务，但当前会话不等待它完成（见 [[9.HIL 与异步任务]]）。

这三条标准用在设计期，不在运行时。任务类型（如 `daily_plan`）是设计期注册的，注册一个任务类型时要一并确定它的三样元数据：

```python
# 设计期注册的任务类型元数据（设计示意）：运行时会话主管只按这张表做匹配
TASK_TYPE_REGISTRY = {
    "daily_plan": {
        "state_machine": DAILY_PLAN_STATES,   # 状态机配置：状态集合与转移条件
        "expires_rule": "follow_plan_date",   # 过期：跟随 plan_date，次日零点
        "confirm_points": ["wait_for_human"], # 确认点：在哪一步停下等用户确认
    },
}
```

运行时，会话主管只做匹配：判断这轮消息是否命中某个已注册类型，命中就交给任务控制器创建任务，没命中就走直接回答或普通委派。当前系统只注册了 daily_plan 一种，会话主管的候选集合里也只有它——系统不会在执行中“发现”一种新的长任务。

这个候选集合是设计期可扩展的：以后出现新的长流程业务，做法是注册一个新的任务类型。比如饮食侧将来要提供与每日训练计划同构的饮食计划（一段预编排工作流），就注册 `diet_plan` 类型，沿用同一套任务外壳——状态机、检查点、`agent_task_runtime` 登记表都不变。`task_thread_id` 的结构里本来就有任务类型一段（根线索前缀 + 任务类型 + `task_id`，见 [[4.Conversation 与 Task 生命周期]]），新类型只是让这一段多一个取值。扩展动作发生在设计期的类型注册上，不发生在运行时的执行链里。

所以不存在“请求级执行到中途升级成任务”的通道。看起来“跑着跑着发现要等用户、就地升级”更灵活，但升级缺的不是身份——`task_id` 随时可以生成——缺的是上面那三样业务语义：这个任务的状态机长什么样、过期时间按什么规则算、确认点放在哪。这些是设计决策，无法从一个跑了一半的 ReAct 执行里推导出来。即使真加一个运行时升级入口，它第一步仍然要查一张设计期定义好的类型元数据表，绕一圈回到原点。

普通对话里的反问也不构成升级理由。智能体问“你体重多少”，用户下一条消息回答，靠会话上下文衔接——中间没有需要持久化的执行状态，失败了整轮重跑也没有损失，三条标准一条都不满足。

真正有风险的场景是执行前无法预判长短：请求被当成普通问答委派出去，跑了很久被迫中断，进度丢失。应对不是开升级入口，而是两条更便宜的路。一是保守预估：预计可能长的请求，一开始就按后台任务启动（见 [[9.HIL 与异步任务]]），宁可高估，多付的只是持久化开销。二是中间产物走 Artifact 落盘（见 [[6.通信协议与 Artifact]]），把万一重跑的损失压下来。

## 路由：由会话主管决策

**路由是为每轮请求选择执行目标的过程**：决定这一轮应该直接回答、调用共享能力，还是委派给哪个领域智能体。这个决策由会话主管完成，不再有独立的 Router 组件（理由见第五章 [[4.Supervisor 架构与委派#不设独立 Router]]）。

```text
                          用户请求
                             │
                             ▼
                          根状态图
                             │
                             ▼
                          会话主管
                             │
              ┌──────────────┼──────────────────┐
              ▼              ▼                  ▼
         直接回答        共享能力                委派
                                              │
                                        ┌─────┴─────┐
                                        ▼           ▼
                                  训练智能体    饮食智能体
                                        │
                                        ▼
                                每日计划工作流
```

例如「罗马尼亚硬拉是什么动作」不涉及领域状态，会话主管直接回答。「我昨天深蹲做了多少」需要访问训练数据，会话主管委派给训练智能体。

当请求需要进入每日计划工作流时，会话主管不直接挂在每日计划的执行链上等待用户，而是把请求交给任务控制器（Task Controller），由它创建一个独立任务，再启动对应的每日计划图。任务入口的分流见 [[4.Conversation 与 Task 生命周期#任务入口分流]]。

## 业务归属与运行时

每日计划因此没有被定义成第三个业务领域，也没有被定义成第三个智能体。业务上它仍然属于训练，只是训练智能体的一项预编排工作流，在运行时中拥有单独的任务生命周期：

```text
业务归属

训练
├── 训练智能体（ReAct）
└── 每日计划（领域工作流）


运行时

训练智能体常规调用      请求级作用域
饮食智能体常规调用      请求级作用域
每日计划（含 HIL）      任务级作用域
后台 AsyncAgentTask      持久化 / 异步
```

这样拆分的原因主要是生命周期与编排方式不同，而不是能力不同，也不是为了增加一个新的智能体层级。任务生命周期的具体定义见 [[4.Conversation 与 Task 生命周期]]，后台任务的持久化见 [[9.HIL 与异步任务]]。

## 边界问答

**1. Q：** 训练/饮食和每日计划的能力有区别吗？

**A：** 没有。三者共用同一层工具与记忆，每日计划能调用的训练计划工具，训练智能体同样能调用，训练/饮食也不是只能回答简单问题的处理器。区别在编排方式（固定工作流 vs 自由编排）和生命周期（任务级 vs 请求级），不在能力。

**2. Q：** 为什么训练/饮食请求不升级成持久任务？

**A：** 这类请求通常在一个 HTTP 请求内完成，失败以后可以重新执行，所以按请求级作用域处理。只有需要跨请求暂停、人工确认、服务重启恢复，或者执行成本高到不希望从头重跑的流程，才升级成持久任务。

**3. Q：** 为什么路由不再由独立 Router 组件完成？

**A：** 独立 Router（无论确定性还是 LLM，大语言模型）都会与会话主管重复语义判断。领域选择是会话主管决策的一部分，由会话主管在每一步动态判断直接回答、调用共享能力还是委派领域智能体，理由见 [[4.Supervisor 架构与委派]]。

**4. Q：** 每日计划为什么不定义成第三个业务领域或第三个智能体？

**A：** 业务上它仍然属于训练，只是训练智能体的一项预编排工作流，在运行时拥有单独的任务生命周期。拆分的真正原因是生命周期与编排方式不同，而不是能力不同，也不是为了增加一个新的智能体层级。

**5. Q：** 普通问答执行到中途，能不能升级成持久任务？

**A：** 不能，也不存在这条通道，原因见上文：升级需要的状态机配置、过期规则、确认点位置只能来自设计期注册的类型定义，运行时能生成身份、不能发明业务语义。不可预判长短的请求，用保守预估和 Artifact 落盘应对，不开运行时升级入口。

**6. Q：** workflow 和 task 为什么不统一叫法？

**A：** 两者不等价。workflow 是预编排的执行步骤定义，task 是带身份与生命周期的一次执行实例：同一个 daily_plan 工作流每次用户发起都实例化成新的 task（T100、T101……），各有自己的 `task_id`、状态机与过期时间，关系类似程序与进程。两个维度也能解耦出其他组合：后台 AsyncAgentTask 有 task 但内部是自由 ReAct、没有预编排 workflow（见 [[9.HIL 与异步任务]]）；领域工作流作为一项领域能力被调用时，调用本身也不自动产生任务外壳。统一叫法后这些区分就无法表达。

**7. Q：** LangGraph 官方说的 agent 和本系统的 Agent 是一回事吗？

**A：** 不是同一层概念。官方的 agent 是应用形态——LLM 自己决定过程和工具用法的那种执行形态，与 Workflow（预编排）相对；本系统的训练/饮食智能体、会话主管是组件。一个组件内部可以同时有两种形态：训练智能体的常规调用是 agent 形态（ReAct），每日计划是它的 Workflow 形态能力。被问「你们的多智能体系统是 workflow 还是 agent」时，按官方口径回答是混排：编排与控制平面是确定性步骤，领域执行是 agentic 步骤；task 与生命周期则是官方分类之外自建的另一根轴。
