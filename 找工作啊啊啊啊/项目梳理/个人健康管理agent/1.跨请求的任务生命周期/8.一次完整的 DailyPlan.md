# 一次完整的 DailyPlan

## 发起：路由到任务控制器

用户输入：

```text
“今天只有 40 分钟，帮我安排腿部训练。”
```

会话主管判断它属于训练下的每日计划请求（路由机制见 [[3.执行模型与任务边界#路由：由会话主管决策]]）：

```text
用户消息
    ↓
根会话图
    ↓
会话主管
    ↓
target = daily_plan
    ↓
任务控制器
```

## 创建并进入等待

任务控制器检查当前会话没有活跃任务后创建 T100，并启动每日计划（活跃任务约束见 [[4.Conversation 与 Task 生命周期#活跃任务约束]]）：

```text
T100 = RUNNING
    ↓
每日计划图
    ↓
参数准备
    ↓
冲突检查
    ↓
生成草稿 D200
    ↓
prepare_invocation：经工具运行时固化动作，创建调用实例 I300
    ↓
wait_for_human
    ↓
interrupt（载荷携带 invocation_id = I300）
    ↓
检查点持久化
    ↓
T100 = WAITING_HUMAN
    ↓
返回确认卡片
```

用户批准的不只是草稿 D200 这份方案，而是 I300 所代表的已固化动作「替换为 D200 v3」——调用实例在中断之前创建并冻结参数，确认与执行之间不再有重新解释的空间（创建时机与冻结参数见 [[找工作啊啊啊啊/项目梳理/个人健康管理agent/4.给工具调用一个稳定身份/9.代码级逻辑：从提议到业务副作用]]）。

状态机语义见 [[4.Conversation 与 Task 生命周期#任务状态机]]，中断协议见 [[6.HIL 与恢复#中断协议（Interrupt）]]，检查点见 [[5.Task Runtime、Checkpoint 和业务状态#LangGraph 检查点语义]]。

## 中断期间切换话题

这时用户不处理卡片，而先问：

```text
“我今天蛋白质应该吃多少？”
```

这条消息仍然作为新的会话请求进入会话主管：

```text
会话主管
    ↓
饮食智能体
    ↓
响应
```

T100 不发生变化。

## 恢复并完成

之后用户点击原来的确认按钮：

```text
卡片动作（携带 invocation_id = I300）
    ↓
任务控制器
    ↓
检查 task_id / expires_at
    检查 task_version / draft_version
    检查 I300 归属、审批状态与冻结参数
    ↓
登记新 Run（run_002）
    ↓
Command(resume=...)
    ↓
execute_invocation(I300)
    ↓
工具运行时 → 训练领域服务
    ↓
业务数据库提交（source_invocation_id = I300）
    ↓
D200 = COMMITTED
    ↓
T100 = COMPLETED
```

恢复执行的仍然是 I300——不重新经历「模型 → 工具调用 → 创建新实例」：用户批准的动作与系统执行的动作是同一个对象。校验清单的完整说明见 [[6.HIL 与恢复#恢复流程与校验]]，过期与版本语义分别见 [[4.Conversation 与 Task 生命周期#过期策略]] 和 [[7.版本控制与并发#旧卡片的乐观并发控制（OCC）]]，执行链路与幂等保护见 [[找工作啊啊啊啊/项目梳理/个人健康管理agent/4.给工具调用一个稳定身份/9.代码级逻辑：从提议到业务副作用]]。

## 三个生命周期

这套设计最终维护的是三个不同的生命周期：

```text
会话
    跨多轮消息持续存在

任务
    创建 → 执行 → 等待 → 恢复 → 结束

业务对象
    草稿 → 正式业务数据
```

会话不因为一个每日计划进入 `WAITING_HUMAN` 就停止工作，每日计划也不需要通过重新读取整段聊天记录来推断自己进行到了哪一步。任务执行状态由检查点保存，任务的粗粒度生命周期由运行时注册表管理，尚未确认和已经确认的业务数据分别进入草稿存储和业务数据库。

## 组件职责回顾

在这个边界下：

- 会话主管负责选择执行目标 —— [[3.执行模型与任务边界#路由：由会话主管决策]]
- 任务控制器管理长任务的创建和恢复 —— [[6.HIL 与恢复#恢复流程与校验]]
- 运行时注册表提供任务索引和生命周期状态 —— [[5.Task Runtime、Checkpoint 和业务状态#agent_task_runtime 控制索引]]
- LangGraph 检查点保存可恢复执行位置 —— [[5.Task Runtime、Checkpoint 和业务状态#LangGraph 检查点语义]]
- 数据库约束和版本控制保证状态推进不会因为并发请求而发生覆盖 —— [[7.版本控制与并发]]

业务副作用本身如何保证安全重放，则由后续工具运行时负责（见 [[找工作啊啊啊啊/项目梳理/个人健康管理agent/1.跨请求的任务生命周期/1.总览#章节边界]]）。

## 边界问答

**1. Q：** 中断期间用户切换话题，正在等待的任务会丢吗？

**A：** 不会。T100 保持在 `WAITING_HUMAN`，普通消息作为新的会话请求照常进入会话主管，任务执行状态由检查点保存，和普通对话互不影响。

**2. Q：** 卡片动作请求为什么不重新走自然语言路由？

**A：** 卡片动作已经带有 `task_id` 和明确动作，可以直接交给任务控制器恢复任务，不需要再经过一轮语言理解。
