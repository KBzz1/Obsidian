# Conversation 与 Task 生命周期

## 身份模型

系统里同时存在两种“进行中的一件事”，它们的身份是分开的。

**会话（Conversation）** 是用户与系统之间连续的多轮对话。它对应根图（Root Graph，处理每轮对话请求的顶层执行图）的 `root_thread_id`。

先解释 thread 这个基础概念：LangGraph 把一次连续执行称为一条 thread（执行线索），检查点按 thread 归档。`root_thread_id` 就是根图这条执行线索的标识——会话建立时确定一次，之后的多轮消息都沿用同一个值，系统靠它把整段对话的历次执行串成一条连续记录。这也是会话能维持多轮聊天连续性的原因。

同一个会话可以先后进入训练（Workout）、饮食（Diet）业务，也可以随时发起每日计划。

**任务（Task）** 是每日计划这类跨多个请求的长流程创建出来的执行单元。任务在会话身份之外额外获得两个标识：

```text
task_id          # 任务身份：卡片、任务控制器、运行时注册表都靠它确认操作的是哪个任务
task_thread_id   # 任务专属执行线索：用来定位这个任务自己的 LangGraph 检查点
```

例如：

```text
root_thread_id = user-42-v3                        # 会话（根图）的执行线索，会话建立时确定
task_id        = 8fa2...                           # 任务身份
task_thread_id = user-42-v3:daily_plan:8fa2...     # 任务执行线索 = 根线索前缀 + 任务类型 + 任务身份
```

从示例可以看出，`task_thread_id` 以 `root_thread_id` 为前缀，再接上任务类型和 `task_id`。

两个任务标识的分工：

- `task_id` 是控制平面使用的任务身份。前端卡片、任务控制器（Task Controller）和运行时注册表（Runtime Registry）都通过它确认正在操作哪一个任务。
- `task_thread_id` 是任务自己的执行线索标识，用于定位这个任务专属的 LangGraph 检查点（检查点语义见 [[5.Task Runtime、Checkpoint 和业务状态#LangGraph 检查点语义]]）。

### 任务与 Run

`task_id` 标识一个逻辑任务从创建到终态的完整生命周期。`run_id` 的定义是：一个真正启动任务运行时（Task Runtime）、拥有独立检查点与恢复生命周期的任务，其一次连续执行阶段。同一个任务可能经历多次连续执行：创建后执行到 `WAITING_HUMAN`，用户确认以后再恢复执行，每一段连续执行都有各自的 `run_id`：

```text
T100

├── run_001
│   → 执行
│   → WAITING_HUMAN
│
└── run_002
    → Resume
    → COMPLETED
```

`run_id` 的约束：

- `run_id` 只标识执行阶段，不进入任务状态机，也不是新的业务生命周期；
- 任务创建时生成第一个 `run_id`，每次恢复产生新的 `run_id`，`task_id` 始终不变；
- 恢复仍然沿 `task_thread_id` 读取同一个 LangGraph 检查点，`run_id` 不改变检查点的归档方式；
- 等待人工确认期间不需要维持一条长时间执行链，每次连续 Run 对应一条独立 Trace（Trace 的构建与关联归后续测试与评估章节）；
- `run_id` 由任务运行时创建，随 RuntimeContext 传递给 Agent、Retrieval、Tool 等执行模块（见 [[4.统一 Tool Runtime]]）；
- 同步委派的 DomainTask 即使拥有自己的 `task_id` 与 `parent_task_id`，也只是父任务当前 Run 内的嵌套执行，不创建独立 `run_id`；只有独立等待、独立恢复的后台异步 DomainTask 才拥有自己的 `run_id`（Run 归属见 [[9.HIL 与异步任务]]）。

Run 的登记落点（代码级逻辑补齐）：`run_id` 被 RuntimeContext、执行记录、Trace 多处引用，必须有明确的创建者与登记处，不能是一个只在引用处出现的标识。每段 Run 在轻量登记表 `agent_task_run` 中占一行——`run_id`、`task_id`、`status`、`started_at`、`ended_at`、`resume_from_run_id`（恢复链，如 run_002 ← run_001）。任务控制器启动任务时登记第一行，恢复校验通过后登记新行并把控制索引的 `current_run_id` 指向它。它只登记执行段的起止与链关系，不进入任务状态机，也不复制执行事实。结构与创建时机见 [[10.代码级逻辑：跨请求的任务暂停与恢复]]。

## 任务状态机

任务状态机描述一个任务从创建到结束会经历哪些状态，以及在什么条件下转移。每日计划的任务状态保持得比较简单：

```text
CREATED
   ↓
RUNNING
   ↓
WAITING_HUMAN
   ↓ 恢复
RUNNING
   ├── COMPLETED
   ├── ABANDONED
   ├── EXPIRED
   └── FAILED
```

各状态的含义：

- `CREATED`：任务已创建，尚未开始执行。
- `RUNNING`：执行中。
- `WAITING_HUMAN`（等待人工确认）：图已经执行到一个稳定的人工交互点，恢复需要的状态已经持久化，在等用户操作。
- `COMPLETED`：正常完成。
- `ABANDONED`：被用户主动放弃。
- `EXPIRED`：超过业务有效期，见 [[#过期策略]]。
- `FAILED`：最终失败，且不再保留重试能力。

普通节点失败不会直接把任务标记成 `FAILED`；如果仍然能够从已有检查点重试，就继续保留恢复能力。

> [!note] 与人工介入（HIL）的关系
> `WAITING_HUMAN` 由 [[6.HIL 与恢复#中断协议（Interrupt）]] 中的 `interrupt()` 触发；恢复位置必须持久化到 [[5.Task Runtime、Checkpoint 和业务状态#LangGraph 检查点语义|LangGraph 检查点]]。

## 活跃任务约束

当前业务约束是：**同一个会话同一时间最多有一个活跃任务（Active Task）**。`CREATED`、`RUNNING` 和 `WAITING_HUMAN` 都属于活跃状态；已经完成、放弃、过期或最终失败的任务不再占用这个位置。

这个限制只约束长任务数量，不锁住整个会话——会话里的普通对话照常进行。

例如用户先创建一个每日计划：

```text
T100 = WAITING_HUMAN
```

卡片还没有确认时，又问：

```text
“今天蛋白质应该吃多少？”
```

这条消息仍然经过正常的会话主管路由，进入饮食智能体。T100 保持在原来的 `WAITING_HUMAN` 状态，不会因为用户切换话题而被退出。

并发下“一个会话最多一个活跃任务”的数据库级保证，见 [[7.版本控制与并发#单个活跃任务的数据库约束]]。

## 任务入口分流

用户之后再点击原来的确认卡片，请求不需要重新经过自然语言路由。卡片动作（Card Action）本身已经带有 `task_id` 和明确动作，可以直接交给任务控制器：

```text
普通消息
聊天消息
    ↓
会话主管
    ↓
对应领域智能体


任务操作
卡片动作
    ↓
任务控制器
    ↓
恢复 T100
```

如果 T100 尚未结束，而用户又提出“重新帮我生成一个腿部计划”，系统不会直接创建 T101。新的任务请求会先检查当前活跃任务，并要求用户确认是否放弃旧任务。确认以后，旧任务和它对应的草稿（Draft）先进入 `ABANDONED`，再创建新的任务。

这里不能只覆盖 `active_task_id`。旧草稿如果仍然保留为可编辑状态，后续旧卡片仍有可能继续修改它，所以任务和草稿的废弃需要作为一次完整状态切换处理。切换的原子事务见 [[7.版本控制与并发#状态切换事务]]。

## 过期策略

任务有业务失效时间，但不统一使用固定 TTL。每日计划与具体 `plan_date` 绑定，因此过期时间跟随计划日期，而不是简单设置为“创建 24 小时以后”。

例如用户晚上 23:50 创建当天训练计划。如果机械使用 24 小时 TTL，它第二天晚上仍然可以继续确认，但这时“今日训练”的业务语义已经发生变化。第二天再操作这张卡片时，任务控制器会先检查 `expires_at`，将任务标记为 `EXPIRED`，同时废弃未确认草稿，再要求用户重新创建当天计划。

## 终态保留与清理

任务结束以后不会立即删除运行时记录（Runtime Record）和检查点。`COMPLETED`、`ABANDONED`、`EXPIRED` 和 `FAILED` 先作为终态保留一段时间，再由后台清理。这样即使最终写入已经成功、但结果返回客户端之前连接断开，系统仍然能够确认 T100 已经完成，而不是因为任务一结束就删除所有执行记录。

## 边界问答

**1. Q：** 任务为什么需要 `task_id` 和 `task_thread_id` 两个标识？

**A：** 两者分工不同。`task_id` 是控制平面的任务身份，卡片、任务控制器和运行时注册表都按它确认正在操作哪个任务；`task_thread_id` 是任务自己的执行线索，LangGraph 检查点按它归档。恢复时先按 `task_id` 找到任务，再按 `task_thread_id` 读检查点。

**2. Q：** 普通节点失败为什么不直接把任务标记成 `FAILED`？

**A：** `FAILED` 表示最终失败且不再保留重试能力。只要任务还能从已有检查点重试，就继续保留恢复能力，不提前判死。

**3. Q：** 过期时间为什么不统一使用固定 TTL？

**A：** 每日计划与具体 `plan_date` 绑定，过期时间跟随计划日期。例如 23:50 创建的当天计划如果机械按 24 小时 TTL 算，第二天晚上仍可确认，但“今日训练”的业务语义已经变了。

**4. Q：** 任务结束后为什么不立即删除运行时记录和检查点？

**A：** 终态先保留一段时间再由后台清理。这样即使最终写入已经成功、但结果返回客户端之前连接断开，系统仍能确认任务已经完成，而不是因为记录被删而无法确认。
