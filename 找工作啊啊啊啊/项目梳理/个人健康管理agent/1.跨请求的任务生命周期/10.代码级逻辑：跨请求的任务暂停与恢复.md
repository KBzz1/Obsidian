# 代码级逻辑：跨请求的任务暂停与恢复

本篇回答一个问题：一个暂停中的每日计划任务，跨请求保存了什么、由谁恢复、恢复后为什么还能继续原来已经准备好的动作。场景沿用 Hero Scenario：用户说「帮我重新调整这周的训练计划」，系统生成新的训练方案草稿；由于要修改正式训练计划，任务暂停等待确认；等待期间用户继续问「晚上训练的话，晚饭应该提前多久吃？」；之后用户确认新方案，系统恢复任务并落正式计划。整个过程由六个对象承担：会话 C10、任务 T100、Run R1/R2、草稿 D200、工具调用实例 I300、检查点。

## 六个身份对象

先看六个对象的关系，再逐个说明：

```text
会话 C10（root_thread_id）
    │  可以包含多个请求
    ├── 普通消息 → 会话主管 → 领域智能体（请求级，不创建任务）
    │
    └── 每日计划请求 → 任务 T100（task_id）
            ├── Run R1：创建 → 执行到 wait_for_human → 停在中断点
            ├── Run R2：恢复 → execute_invocation → complete_task
            ├── 草稿 D200（draft_id + draft_version）
            ├── 工具调用实例 I300（invocation_id）
            └── 检查点（按 task_thread_id 定位：图位置 + 中断现场）
```

**会话（C10）** 代表用户与系统之间持续存在的对话入口，对应根图的执行线索 `root_thread_id`（见 [[4.Conversation 与 Task 生命周期#身份模型]]）。它由会话入口在会话建立时创建，生命周期跟随用户与系统的使用关系，远长于任何一个任务；会话中的消息由会话主管路由。会话不等于某一个正在运行的任务：T100 等待期间 C10 照常处理新消息，这条边界是第一章全部设计的出发点。

**任务（T100）** 代表一个明确业务目标——调整本周训练计划——的完整逻辑生命周期，跨多个 HTTP 请求存在。它由任务控制器创建，控制数据持久化在 `agent_task_runtime`（四层状态分层见 [[5.Task Runtime、Checkpoint 和业务状态#四层状态分层]]）；到达终态（`COMPLETED` / `ABANDONED` / `EXPIRED` / `FAILED`）并度过保留期后由后台清理销毁。只有任务控制器与图的收尾节点可以推进它的状态。

```python
class AgentTaskRuntime:
    # —— 身份组：把任务和它的会话、用户、执行线索对上 ——
    task_id: UUID              # 逻辑任务身份：卡片、任务控制器、控制索引都靠它确认操作的是哪个任务
    root_thread_id: str        # 任务来自哪个持续会话；「一个会话最多一个活跃任务」的唯一约束按它生效
    task_thread_id: str        # 任务自己的执行线索 = 根线索前缀 + 任务类型 + task_id，恢复时按它定位检查点
    user_id: UUID              # 任务所属用户；工具运行时注入执行身份的来源之一

    # —— 控制组 ——
    task_type: str             # 任务类型（如 daily_plan），决定启动哪一张图
    status: str                # 任务状态机当前位置（CREATED / RUNNING / WAITING_HUMAN / 终态）
    task_version: int          # 乐观并发版本，状态推进时自增，用于拒绝旧确认卡片
    current_run_id: str        # 指向 agent_task_run 中最新一行：恢复时换新，是向执行模块注入 run_id 的来源

    # —— 草稿关联组 ——
    draft_id: UUID | None      # 当前关联草稿，任务尚未生成草稿时为空
    draft_version: int | None  # 该草稿当前版本，与任务版本一起构成恢复校验链

    # —— 时效组 ——
    expires_at: datetime | None # 过期时间，跟随 plan_date 而非固定 TTL（见 4.Conversation 笔记过期策略）
    created_at: datetime       # 创建时间
    updated_at: datetime       # 最后更新时间
```

Run 的持久化落点是代码级下沉时补齐的：`run_id` 的身份语义已在 [[4.Conversation 与 Task 生命周期#任务与 Run]] 定义，但「`run_id` 由谁创建、登记在哪里」原先没有写明——而 RuntimeContext、执行记录、Trace 都在引用它，不能是一个没人负责持久化的标识。落点选轻量登记表，每段 Run 一行：

```python
class AgentTaskRun:
    run_id: str                   # 一段连续执行的身份，如 R1 / R2
    task_id: str                  # 所属任务，如 T100
    status: str                   # 本段执行状态：RUNNING / INTERRUPTED / COMPLETED / FAILED
    started_at: datetime          # 本段开始时间
    ended_at: datetime | None     # 本段结束时间，进行中为空
    resume_from_run_id: str | None # 因恢复产生时的上一段 Run（如 R2 ← R1）；首段为空
```

创建时机：`TaskController.create_task()` 创建任务时登记 R1；`resume_task()` 校验通过后登记 R2，并把控制索引的 `current_run_id` 指向新行。`run_id` 由此进入 RuntimeContext、执行记录与 Trace（见 [[3.Task、Run 与 Trace 身份关联]]）。登记行只记执行段的起止与恢复链，不进入任务状态机，也不复制执行事实——那是执行记录与 Trace 的职责。

**Run（R1、R2）** 代表任务的一次连续执行阶段。R1 由任务控制器在 `create_task()` 时登记，R2 在 `resume_task()` 校验通过后登记（登记表见下文 `AgentTaskRun`）；每段 Run 从执行开始到停在中断点或任务终态为止。Run 需要单独存在的原因：Task 表示逻辑目标的整个生命周期，Run 表示其中一段不中断的执行。T100 先后在 R1 执行到等待、在 R2 执行到完成——任务没有变，执行段变了。如果只有 Task 一个身份，系统无法表达「同一个目标经历了几段执行」，执行记录与 Trace 的 `run_id` 归属也就没有挂靠点。

**草稿（D200）** 代表尚未成为正式业务事实的训练方案，由 `generate_draft` 节点创建并写入草稿存储。它从生成开始存在，到 `COMMITTED`（随调用实例执行成功转为正式计划）或 `ABANDONED` / `EXPIRED` 结束；图中的草稿节点随用户修改推进 `draft_version`。草稿不等于正式训练计划：草稿可以被修改、拒绝、重新生成、过期，只有用户确认并经工具执行提交之后，业务数据库里才出现新的正式计划。草稿状态机在代码级下沉中补齐为：

```text
EDITING            # 生成中或用户仍在修改，每次修改 draft_version 自增
   ↓ prepare_invocation 固化动作之后
PENDING_APPROVAL   # 等待用户对「D200 v3 + 调用实例 I300」的确认
   ↓ 确认且恢复校验链通过
APPROVED           # 用户已批准，等待执行
   ↓ execute_invocation 成功
COMMITTED          # 已成为正式训练计划，草稿使命结束

等待类状态 → ABANDONED / EXPIRED   # 用户放弃，或超过业务有效期
```

**工具调用实例（I300）** 指一次已经由工具运行时接管、参数已经确定、可以跨暂停和恢复继续引用的工具动作——本场景中就是把 D200 v3 替换为正式训练计划这个动作。它由 `prepare_invocation` 节点请求工具运行时创建，是用户确认的对象、也是恢复后执行的对象；本篇只讲它在任务生命周期里的角色，结构与执行语义见 [[9.代码级逻辑：从提议到业务副作用]]。

**检查点** 以 `task_thread_id`（下文缩写 TH100，实际形如 `user-42-v3:daily_plan:T100`）定位，由 LangGraph 在每个节点执行完成后保存，记录图执行到哪个节点、状态数据与待处理中断。它在任务终态保留期后随任务清理。检查点回答「图从哪里继续」，不回答「任务现在什么状态」（那是控制索引的事），更不回答「业务数据有没有变」（那是业务数据库的事）。

## 第一段执行：从用户消息到等待确认

### 创建任务

用户消息进入会话入口后的完整调用链，标注每一步谁写什么状态：

```text
POST /conversations/C10/messages        # 用户消息进入会话入口
    ↓
ConversationService.handle_message()    # 会话入口服务（示意命名）：记录消息，交给根图
    ↓
会话主管路由                            # 判断：这是一个新的每日计划请求
    ↓
TaskController.create_task()            # 任务控制器：创建任务
    ↓
INSERT agent_task_runtime               # 写入 T100：status=RUNNING、task_version=1、current_run_id=R1
    ↓
DailyPlanGraph.invoke(thread_id=TH100)  # 启动每日计划图，检查点按 TH100 归档
```

会话入口服务的职责边界：它只负责判断当前用户请求是否需要创建一个新的任务，不负责控制任务生命周期——任务的推进、等待与结束归任务控制器与图本身。会话主管在这里完成的是路由决策（见 [[3.执行模型与任务边界#路由：由会话主管决策]]），结论是「交给任务控制器」，而不是替任务执行。

### 每日计划图的节点链

把 [[6.HIL 与恢复#可重放性约束]] 的节点边界落到具体节点名：

```text
generate_draft        # 生成草稿 D200，写入草稿存储
    ↓
prepare_invocation    # 创建调用实例 I300，invocation_id 写入图状态
    ↓
wait_for_human        # 只读取已有 invocation_id，interrupt()，任务停在此处
    ↓  —— 恢复后 ——
execute_invocation    # 执行 I300（链路见第四章代码级逻辑篇）
    ↓
complete_task         # 草稿 COMMITTED、任务 COMPLETED
```

LangGraph 在每个节点执行完成后保存检查点，所以节点边界就是状态持久化的粒度。

`generate_draft` 读任务输入参数与当前正式计划（对业务数据库只读），生成草稿 D200 写入草稿存储。草稿不能直接写正式训练计划：此时方案还没有获得用户确认，直接落正式库等于绕过人工介入边界；「尚未确认」与「已经生效」两类数据必须分属草稿存储与业务数据库两层（分层理由见 [[5.Task Runtime、Checkpoint 和业务状态#四层状态分层]]）。

`prepare_invocation` 在进入人工介入之前，向工具运行时申请创建调用实例：

```text
prepare_invocation
    ↓
ToolRuntime.prepare()
    ↓
get_or_create I300         # 以（task_id, 节点意图, draft_id, draft_version）为键查询：
                           # 已存在则复用，不存在才创建
    ↓
state.invocation_id = I300 # 写入图状态，随本节点结束后的检查点一起持久化
```

I300 中固定 `task_id`、`draft_id`、`draft_version`、`tool_name`、`arguments` 与幂等令牌，即把「将要把 D200 v3 替换为正式计划」这个动作钉死。为什么必须在人工介入之前创建：用户应该确认一个已经确定的动作，而不是确认以后运行时再重新询问模型「你刚刚想做什么」。如果等确认之后再重新生成工具调用，批准与执行之间就又插进一次模型输出，用户批准 A、系统执行 B 的窗口由此打开。固化内容与创建语义见 [[9.代码级逻辑：从提议到业务副作用]]。

`wait_for_human` 只读取图状态里已有的 `invocation_id` 组装载荷，然后 `interrupt()`，不创建任何对象。把创建动作和 interrupt 混在同一节点是危险的写法：interrupt 恢复后包含它的节点可能重新执行，每次重入都可能新建一个调用实例，用户批准的 I300 与实际执行的 I301 从此对不上。中断载荷结构：

```python
class TaskInterruptPayload(BaseModel):
    kind: str                   # 中断类型：这次停下来是为了什么（等待计划确认）
    task_id: UUID               # 任务身份，恢复校验用
    task_version: int           # 任务版本，恢复校验用
    invocation_id: str          # 本次等待确认的动作：代码级补齐字段，把确认对象绑定到调用实例
    draft_id: UUID | None       # 关联草稿，无草稿时为空
    draft_version: int | None   # 草稿版本，无草稿时为空
    ui_card: dict               # 前端渲染卡片的数据（内含 invocation_id，卡片动作原样带回）
    allowed_actions: list[str]  # 允许的操作（approve / reject / request_changes）
```

`invocation_id` 进入中断载荷是第一章与第四章接起来的接口之一：HIL 协议原先只绑定任务与草稿，代码级下沉后把「用户确认的是哪一个动作」也钉进载荷与卡片（字段相对 [[6.HIL 与恢复#中断协议（Interrupt）]] 的版本新增了 `invocation_id`）。

`interrupt()` 之后，LangGraph 先把「图停在 `wait_for_human`、待处理中断为上述载荷」写入检查点；任务控制器随后把控制索引推进为 `WAITING_HUMAN`（`task_version` 自增）。先持久化中断现场、再改任务状态，两件事都落库后这个请求才返回。

### 暂停瞬间的完整数据状态

T100 处于 `WAITING_HUMAN` 时，系统各层保存的内容：

```text
会话 C10         status = ACTIVE                      # 会话照常工作，与任务状态无关

任务 T100        status = WAITING_HUMAN
                 task_version = 4                     # 期间经历两次草稿修改
                 current_run_id = R1

Run R1           status = INTERRUPTED                 # 登记于 agent_task_run：本段停在中断点

草稿 D200        version = 3
                 status = PENDING_APPROVAL            # 用户正在确认哪一个方案

调用实例 I300     approval_state = WAITING_APPROVAL   # 用户确认的是哪一个真实业务动作
                 status = PENDING                     # 尚未执行

检查点 TH100     图位置 = wait_for_human
                 待处理中断 = TaskInterruptPayload    # 图从哪里继续

业务数据库        正式训练计划仍是旧版本                # 什么都没有变
```

六个对象各回答一个问题：检查点回答「图从哪里继续」；任务回答「逻辑目标现在处于什么阶段」；Run 回答「这是第几段连续执行」；草稿回答「用户正在看哪个方案」；调用实例回答「用户确认的是哪个动作」；业务数据库回答「正式事实有没有变化」。此刻前五个对象都动了，最后一个没动——暂停的全部意义就在这里。

## 等待期间：会话为什么可以继续

用户发来「晚上训练的话，晚饭应该提前多久吃？」：

```text
POST /conversations/C10/messages
    ↓
ConversationService.handle_message()
    ↓
会话主管：新的普通健康问题，与 T100 无关
    ↓
委派饮食智能体（请求级，不创建任务）
    ↓
回答返回 C10
```

T100 全程保持 `WAITING_HUMAN`，没有任何对象被改动。系统不会因为 C10 中存在等待中的 T100，就把新消息自动当成 `resume(T100)`：恢复必须携带 `task_id`、版本与动作的确定信息，自然语言消息不具备；把「这句话是不是在确认计划」交给模型判断，等于给控制路径引入一次不可靠推理——所以第一版明确不支持用自然语言恢复任务（见 [[6.HIL 与恢复#恢复流程与校验]]）。会话与任务的分离在这里兑现：等待中的任务不锁会话，继续的会话不打扰任务。

## 恢复：确认请求如何回到任务

确认走独立的结构化入口，不进普通消息入口：

```python
POST /tasks/T100/actions

TaskAction(
    task_id="T100",         # 要操作的任务
    action_id="approve",    # 用户点击的动作
    task_version=4,         # 卡片携带的任务版本，校验是否仍为最新
    invocation_id="I300",   # 卡片携带的调用实例，校验确认的正是这个动作
    draft_id="D200",
    draft_version=3,
)
```

任务控制器 `resume_task()` 的校验链，全部通过以后才触达图：

```python
def resume_task(action: TaskAction):
    task = load_task(action.task_id)                  # ① 任务存在，且 status == WAITING_HUMAN
    check(task.task_version == action.task_version)   # ② 任务版本匹配（拒绝旧卡片）
    draft = load_draft(action.draft_id)               # ③ 草稿存在
    check(draft.version == action.draft_version)      # ④ 草稿版本匹配
    inv = load_invocation(action.invocation_id)       # ⑤ 调用实例存在且属于 T100
    check(inv.approval_state == "WAITING_APPROVAL")   # ⑥ 仍在等待批准，未被处理过
    check(inv.arguments_snapshot["draft_id"] == "D200"    # ⑦ 调用实例冻结的参数仍是 D200 v3，
          and inv.arguments_snapshot["draft_version"] == 3)  #    确认对象与执行对象没有漂移
    check(business_precondition_ok(task))            # ⑧ 等待期间业务前置条件未变（执行前护栏还会复查）

    # —— 校验全部通过：登记新 Run，任务身份不变 ——
    INSERT agent_task_run                            # 新行：R2，resume_from_run_id = R1
    UPDATE agent_task_runtime
    SET status = 'RUNNING', task_version = task_version + 1,
        current_run_id = 'R2'
    WHERE task_id = 'T100'
      AND status = 'WAITING_HUMAN'
      AND task_version = 4;                           # OCC：并发确认只有一个能成功

    DailyPlanGraph.invoke(
        thread_id = TH100,                            # 沿原任务执行线索读检查点
        command = Command(resume={"action_id": "approve",
                                  "invocation_id": "I300"}),
    )
```

为什么不是重新创建任务：用户确认的是 T100 这个逻辑目标里的 D200 方案。新建 T101 会丢掉原有检查点、草稿关联与调用实例，把「继续」变成「重来」。为什么 Run 换成 R2：恢复后的执行是一段新的连续执行，需要自己的执行记录与 Trace 挂靠；R1 已经结束在等待点，不应被拉成一条跨越数小时等待的执行链。`task_id` 稳定、`run_id` 更新，就是「Task 表示逻辑目标生命周期，Run 表示一次连续执行阶段」在代码上的样子。

## 恢复后：执行的还是原来那个动作

```text
T100 不变     TH100 不变     D200 不变     I300 不变

R1 → 已停在 wait_for_human（历史执行段，事实由执行记录与 Trace 保存）
R2 → execute_invocation(I300) → complete_task
```

图从 `wait_for_human` 的检查点继续，`execute_invocation` 读取图状态里的 `invocation_id` 执行 I300，全程不重新经历「模型 → 工具调用 → 创建 I301」：模型没有再次介入，不存在第二次提议，用户批准的动作与系统执行的动作是同一个对象。这一步是第一章与第四章真正接起来的地方——执行链路（护栏复查、领域服务写入、幂等保护、崩溃窗口）见 [[9.代码级逻辑：从提议到业务副作用]]。

## 状态变化总表

| 阶段 | 任务 T100 | 当前 Run | 草稿 D200 | 调用实例 I300 | 业务库训练计划 |
| --- | --- | --- | --- | --- | --- |
| 创建任务 | RUNNING (v1) | R1 RUNNING | 无 | 无 | 旧计划 |
| 草稿生成 | RUNNING | R1 RUNNING | v3 EDITING | 无 | 旧计划 |
| 固化动作后 | RUNNING (v4) | R1 RUNNING | v3 PENDING_APPROVAL | WAITING_APPROVAL / PENDING | 旧计划 |

| 确认校验通过 | RUNNING (v5) | R2 RUNNING（← R1） | v3 APPROVED | APPROVED / PENDING | 旧计划 |

调用实例一列用「审批状态 / 执行状态」两维表达。读法：每跨一行只有被涉及的对象变化；「等待期间会话继续」一行五个对象全部不变；业务库直到「工具执行中」才被触碰，且由领域服务完成，不由运行时代写。

## 异常路径一：旧确认卡片

用户持有 `task_version=4` 的旧卡片提交，而任务已推进到 v5（例如期间草稿又被修改）：

```sql
UPDATE agent_task_runtime
SET status = 'RUNNING', task_version = task_version + 1, current_run_id = 'R2'
WHERE task_id = 'T100'
  AND status = 'WAITING_HUMAN'
  AND task_version = 4;   -- 当前已是 5：0 行被更新
```

校验链在第②步拒绝：不修改任何数据，重新读取最新状态并把新卡片返回给用户，让用户基于当前版本重新决定。版本检查存在的理由：确认卡片可能在客户端停留任意久，期间任务状态可能被其他请求推进；没有版本比对，旧请求会静默覆盖新状态（机制见 [[7.版本控制与并发#旧卡片的乐观并发控制（OCC）]]）。

## 异常路径二：调用实例已创建、检查点未保存

```text
prepare_invocation：I300 已创建并落库
    ↓
进程异常
    ↓
state.invocation_id 尚未随检查点持久化
```

服务恢复后，图从 `prepare_invocation` 之前的检查点重放该节点。如果 prepare 的语义是无条件创建，重放会产生 I301，库里同时存在两个实例，之后 `wait_for_human` 读到哪个取决于重放结果，身份的稳定 reference 从此失去保证。所以 prepare 必须是 get_or_create：以（`task_id`、节点意图、`draft_id`、`draft_version`）为键，I300 已存在就复用并把 `invocation_id` 写回图状态。节点重放是检查点机制下的正常行为，不是异常分支；所有创建身份对象的节点都要按可重放语义编写（约束来源见 [[6.HIL 与恢复#可重放性约束]]）。

## 第一章代码级理解总结

四个对象各自承担什么、为什么不能合并：

- **会话与任务不能合并**。合并意味着「一个等待中的任务锁死整个会话」，或「会话结束任务就得重建」。Hero Scenario 要求两件事同时成立：任务在等、会话在答；T100 的 `WAITING_HUMAN` 与 C10 的 `ACTIVE` 是两个独立状态机的独立取值。
- **任务与 Run 不能合并**。合并后无法区分「目标的生死」与「一段执行的起止」。恢复创建新 Run，让执行记录、Trace、工具执行尝试各有准确的 `run_id` 挂靠；任务身份与检查点线索保持稳定，恢复才能沿原线索继续。
- **任务控制索引与检查点不能合并**。前者是任务生命周期的可快速查询的控制数据（有没有活跃任务、版本多少、是否过期），后者是执行现场（图位置、状态数据、待处理中断）。读写模式与清理时机都不同：只留其一，要么恢复时找不到中断现场，要么每次查询任务状态都要解析检查点。
- **草稿与正式计划不能合并**（业务侧分层，见 [[5.Task Runtime、Checkpoint 和业务状态#四层状态分层]]）：等待期间业务数据库必须保持不变，这件事只有在「未确认数据只存在于草稿存储」时才是数据上可判定的，而不只是状态字段上的声明。

第一章保证「任务能回来」；第四章保证「回来之后动作安全落地」。中间的粘合点是 I300：它在 `prepare_invocation` 创建、被卡片携带确认、在 `execute_invocation` 执行。

## 边界问答

**1. Q：** 确认请求为什么不能走普通消息入口（`POST /conversations/C10/messages`）？

**A：** 普通消息入口的产出是自然语言理解与路由，而恢复需要 `task_id`、版本、动作的确定校验。混在同一入口意味着用模型判断「这句话是不是在确认」，给控制路径引入不可靠推理；独立的结构化入口让整条校验链保持确定。

**2. Q：** Run 为什么用轻量登记表 `agent_task_run`，而不是并进 `agent_task_runtime` 或任务状态机？

**A：** `run_id` 被 RuntimeContext、执行记录、Trace 多处引用，需要明确的创建者与登记处；但 Run 不是新的业务生命周期，登记行只记起止、状态与恢复链（`resume_from_run_id`），不进入任务状态机，也不复制执行事实——那是执行记录与 Trace 的职责。控制索引的 `current_run_id` 只是指向最新登记行的快速指针，不承载 Run 的历史。

**3. Q：** `wait_for_human` 重入为什么危险？

**A：** `interrupt()` 恢复后，包含它的节点可能重新执行。如果创建调用实例与 interrupt 混在同一节点，每次重入都可能新建实例，用户批准的对象与最终执行的对象就会脱钩。所以创建收敛在 `prepare_invocation`（get_or_create），`wait_for_human` 只读取。

**4. Q：** 先改任务状态、后持久化中断现场，行不行？

**A：** 反过来会出现任务已 `WAITING_HUMAN`、检查点里却没有待处理中断的窗口。卡片重发机制按运行时注册表找 `WAITING_HUMAN` 任务、再读检查点里的待处理中断重建卡片（见 [[6.HIL 与恢复#卡片投递与事实来源]]）；先现场后状态，卡片重发才总有据可依。

**5. Q：** 暂停期间业务数据库为什么必然不变？

**A：** 修改正式计划只有一个入口：调用实例 I300 的执行，而 I300 停在 `WAITING_APPROVAL` / `PENDING`；等待期间的草稿修改只写草稿存储。「等待」因此是数据上可判定的状态，不依赖任何组件的自我约束。
