# 版本控制与并发

## 三种标识

任务控制中有三种经常容易混淆的标识：

```text
task_id
    标识操作针对哪个 Task

task_version / draft_version
    判断操作基于的是否还是最新状态

idempotency_key
    判断同一个副作用操作是否已经执行过
```

`task_id` 回答“操作谁”；版本号回答“我看到的还是不是最新版”；幂等键回答“这件事是不是已经做过”。第一章主要处理前两种。幂等键属于第四章（见 [[找工作啊啊啊啊/项目梳理/个人健康管理agent/1.跨请求的任务生命周期/1.总览#章节边界]]）。

## 旧卡片的乐观并发控制（OCC）

乐观并发控制（OCC，Optimistic Concurrency Control）的基本做法是：更新时带上自己读到的版本号，数据库在写入时校验版本没有被别人改过；一旦版本变了，就拒绝这次更新，让调用方重新读取最新状态，而不是用旧数据覆盖新数据。

版本号首先用这个机制解决旧卡片问题。

例如用户最初拿到草稿 v3，之后已经通过一次修改把草稿更新到 v4，但旧页面上仍然保留 v3 的确认按钮。用户此时点击旧按钮，请求仍然携带：

```text
expected_draft_version = 3    # 旧请求携带的版本（来自旧页面）
```

而数据库已经是：

```text
current_draft_version = 4     # 数据库中的当前版本
```

这次操作不能继续执行。系统拒绝旧版本修改，重新读取最新草稿，并把 v4 卡片返回给用户：

```text
旧 v3 Card
    ↓
version mismatch
    ↓
不修改数据
    ↓
load Draft v4
    ↓
返回最新 Card
```

## 任务状态更新的乐观并发控制

任务状态也采用同样的乐观并发控制。例如：

```sql
UPDATE agent_task_runtime
SET
    status = 'ABANDONED',                     -- 推进到放弃终态
    task_version = task_version + 1           -- 版本自增，旧请求携带的版本随即失效
WHERE task_id = :task_id
  AND status = 'WAITING_HUMAN'                -- 只允许从等待人工确认的状态发起放弃
  AND task_version = :expected_task_version;  -- 乐观校验：版本不符就不会更新任何行
```

如果没有更新到任何记录，说明当前任务已经被另一个请求推进，调用方需要重新读取最新状态，而不是继续覆盖。

## 单个活跃任务的数据库约束

并发创建任务的问题不能只靠乐观并发控制。因为“一个会话最多一个活跃任务”属于数据库级不变量（语义见 [[4.Conversation 与 Task 生命周期#活跃任务约束]]）。

假设两个请求同时进入：

```text
Request A                 Request B
   │                         │
 查 Active Task            查 Active Task
   │                         │
 没有                      没有
   │                         │
 创建 T100                 创建 T101
```

如果只在应用层做 `if not active_task`，两个请求都可能通过。

因此 `agent_task_runtime` 对活跃任务建立部分唯一约束：只有状态处于活跃值的行，才要求 `root_thread_id` 唯一。SQL 里的 `WHERE` 就是“部分”的含义——非活跃状态的历史行不受这个约束限制。

```sql
-- 同一会话同一时间最多一个活跃任务，由数据库层直接保证
CREATE UNIQUE INDEX uq_one_active_task_per_thread
ON agent_task_runtime(root_thread_id)
WHERE status IN (           -- WHERE 条件就是“部分”的含义：约束只对活跃状态生效
    'CREATED',
    'RUNNING',
    'WAITING_HUMAN'
);
```

应用层仍然可以先查一次活跃任务，用于大多数正常请求的快速判断。但即使两个 Worker 同时通过查询，数据库最终也只允许一个 INSERT 成功。另一个请求捕获唯一约束冲突后重新读取当前活跃任务，并返回正常业务提示。

## 锁的定位

进程内的 `asyncio.Lock`（异步锁）可以继续保留，但只用于降低同一个 Worker 内重复请求互撞的概率。多个 Worker 各自拥有独立内存，不能靠它保证全局正确性。

当前并发控制组合保持为：

```text
asyncio.Lock
    单进程优化

PostgreSQL unique constraint
    单 Active Task 约束

task_version / draft_version
    状态更新 OCC
```

暂时不引入 Redis 分布式锁。选型理由见 [[5.Task Runtime、Checkpoint 和业务状态#边界问答]]。

## 状态切换事务

需要同时废弃旧任务、废弃草稿并创建新任务时，使用一个短数据库事务完成状态切换。事务中不执行 LLM、Retrieval 或 Tool 调用，也不在等待用户输入期间持有数据库锁。

例如：

```text
BEGIN

校验并锁定 T100
T100 -> ABANDONED
D100 -> ABANDONED
创建 T101

COMMIT

然后启动 DailyPlan T101
```

数据库锁只保护短时间的状态转换，不参与长时间 Agent 执行。

## 边界问答

**1. Q：** 并发创建任务为什么不能只靠乐观并发控制？

**A：** 两个请求可能同时查到“没有活跃任务”，应用层检查都能通过。所以“一个会话最多一个活跃任务”由部分唯一索引在数据库层兜底：即使两个 Worker 同时通过查询，最终也只允许一个 INSERT 成功。

**2. Q：** `asyncio.Lock` 为什么不能保证全局正确性？

**A：** 它是进程内锁，只对同一个 Worker 内的请求有效；多个 Worker 各自拥有独立内存。跨进程的正确性靠数据库唯一约束和版本号。

**3. Q：** 状态切换事务里为什么不执行 LLM、Retrieval 或 Tool 调用？

**A：** 数据库锁只保护短时间的状态转换，不参与长时间 Agent 执行，也不在等待用户输入期间持有锁。

**4. Q：** 为什么不引入 Redis 分布式锁？

**A：** 当前任务状态推进的正确性已经由唯一约束和版本号覆盖，暂时没有必须依赖分布式锁才能解决的点；Redis 的持久化与淘汰成本见 [[5.Task Runtime、Checkpoint 和业务状态#边界问答]]。
