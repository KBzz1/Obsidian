# HIL 与恢复

HIL（Human-in-the-Loop，人工介入）指的是流程执行到需要用户确认或决策的点时暂停下来，把决定权交给用户，而不是全自动跑完。本章的 HIL 机制围绕两个原语展开：`interrupt()` 负责停下来（中断），`resume` 负责继续（恢复）。

## 中断协议（Interrupt）

中断协议指的是围绕 interrupt() 的整套约定：在哪里停、中断现场保存什么、恢复时怎么继续。每日计划到达需要人工确认的位置时调用 interrupt()，将任务停在明确的交互边界。

中断中保存的是恢复这一次交互需要的信息，例如：

```python
class TaskInterruptPayload(BaseModel):
    kind: str                        # 中断类型：这次停下来是为了什么

    task_id: UUID                    # 任务身份，恢复时校验
    task_version: int                # 任务版本，恢复时校验请求是否基于最新状态

    draft_id: UUID | None            # 这次交互关联的草稿，没有草稿时为空
    draft_version: int | None        # 草稿版本，没有草稿时为空

    ui_card: dict                    # 前端渲染卡片需要的数据
    allowed_actions: list[str]       # 这次交互允许用户执行的操作列表
```

各字段的含义：

- `kind`：中断类型，标识这次停下来是为了什么。
- `task_id`、`task_version`：任务身份与版本，恢复时校验用。
- `draft_id`、`draft_version`：这次交互关联的草稿及其版本，可以为空。
- `ui_card`：前端渲染卡片需要的数据。
- `allowed_actions`：这次交互允许用户执行的操作列表。

生成草稿 D200 v3 后，一次中断可以表示为：

```text
每日计划
    ↓
生成草稿 D200 v3
    ↓
wait_for_human
    ↓
interrupt(...)
    ↓
T100 = WAITING_HUMAN
```

`WAITING_HUMAN` 的状态定义见 [[4.Conversation 与 Task 生命周期#任务状态机]]；中断现场由 [[5.Task Runtime、Checkpoint 和业务状态#LangGraph 检查点语义|检查点持久化]]。

## 恢复流程与校验

前端展示这次中断对应的卡片。用户点击按钮以后提交结构化操作：

```python
TaskAction(
    task_id="T100",         # 要操作的任务
    action_id="save_plan",  # 用户点击的动作类型
    task_version=4,         # 客户端看到的任务版本，恢复前校验
    draft_id="D200",        # 这次交互关联的草稿
    draft_version=3,        # 客户端看到的草稿版本，恢复前校验
)
```

任务控制器不直接把这个请求交给图，而是先检查：

1. 任务是否仍然存在、是否已经结束（状态定义见 [[4.Conversation 与 Task 生命周期#任务状态机]]）
2. 是否已经过期（过期策略见 [[4.Conversation 与 Task 生命周期#过期策略]]）
3. 任务和草稿版本是否仍然匹配（乐观并发控制机制见 [[7.版本控制与并发#旧卡片的乐观并发控制（OCC）]]）

全部通过以后才调用：

```python
Command(
    resume={
        "action_id": "save_plan",   # 校验全部通过后，把用户动作交回给图，从检查点继续
    }
)
```

第一版不支持用自然语言恢复任务。比如用户输入“就这样吧”，系统不会尝试用模型判断这句话是不是在确认当前每日计划。卡片动作已经能提供确定的任务身份和操作类型，没有必要为了更自然的交互给控制路径再增加一次模型判断。

## 可重放性约束

可重放性指同一个节点在恢复后再次执行，也不会产生重复或错误的业务写入。HIL 设计还有一个必须遵守的执行约束：包含 interrupt() 的节点恢复时可能重新进入，因此等待人工输入的节点本身不能在中断之前做不可重复的业务写入。

每日计划的节点大致保持这种边界：

```text
生成或修改草稿
        ↓
准备卡片
        ↓
wait_for_human
        ↓
interrupt

------ 恢复 ------

解析卡片动作
        ↓
修改 / 保存 / 放弃
```

检查点只能解决恢复位置，不能保证业务写入只发生一次。

一个典型故障是：

```text
persist_daily_plan
        ↓
业务数据库写入成功
        ↓
进程崩溃
        ↓
新的检查点尚未完成
```

服务恢复以后，运行时仍有可能再次执行保存节点。所以第一章只规定副作用节点必须允许重放，真正的幂等键、事务以及重复调用处理放在第四章工具运行时（Tool Runtime）中设计（见 [[找工作啊啊啊啊/项目梳理/个人健康管理agent/1.跨请求的任务生命周期/1.总览#章节边界]]）。

## 持久检查点的必要性

持久检查点首先解决的是下面这个场景：

```text
生成草稿
    ↓
interrupt
    ↓
T100 = WAITING_HUMAN
    ↓
后端重启
    ↓
用户点击确认
    ↓
根据 task_thread_id 加载检查点
    ↓
Command(resume=...)
    ↓
继续原来的每日计划
```

如果每日计划仍然使用进程内检查点存储，后端重启以后这条执行链就无法恢复，只能重新创建计划。持久化选型见 [[5.Task Runtime、Checkpoint 和业务状态#边界问答]]。

## 卡片投递与事实来源

这里的事实来源指判断“任务正在等待什么”时以哪份状态为准。另一个容易被忽略的问题发生在检查点和界面投递之间：系统可能已经成功保存中断，但 SSE（Server-Sent Events，服务器向浏览器单向推送事件的通道）在卡片发送到客户端之前断开：

```text
interrupt 持久化成功
        ↓
T100 = WAITING_HUMAN
        ↓
发送卡片
        ↓
连接断开
```

这时服务端认为任务正在等待人工确认，客户端却可能根本没看到卡片。

所以卡片不能作为 HIL 的事实来源。用户重新进入会话时，如果运行时注册表中存在 `WAITING_HUMAN` 的活跃任务，系统会读取对应检查点中的待处理中断（pending interrupt），并重新生成或下发当前卡片。

这样即使界面投递丢失，任务仍然可以从服务端持久状态恢复。

## 边界问答

**1. Q：** 检查点已经持久化了，为什么还要可重放性约束？

**A：** 检查点只解决“恢复到哪一步”，不能保证业务写入只发生一次。包含 `interrupt()` 的节点恢复时可能重新进入，所以等待人工输入的节点不能在中断之前做不可重复的业务写入。

**2. Q：** 为什么第一版不支持用自然语言恢复任务？

**A：** 卡片动作已经能提供确定的任务身份和操作类型，没有必要为了更自然的交互给控制路径再增加一次模型判断。

**3. Q：** 为什么卡片不能作为 HIL 的事实来源？

**A：** 检查点保存成功和卡片送达客户端之间可能断线：服务端以为任务在等用户，客户端却可能根本没看到卡片。重新进入会话时，系统按运行时注册表里的 `WAITING_HUMAN` 任务读取检查点中的待处理中断，重新生成或下发卡片。

**4. Q：** 恢复前为什么必须先做一轮校验？

**A：** 任务可能已经结束或过期，任务、草稿的版本也可能已经被更新。直接交给图恢复，旧请求会覆盖新状态；校验全部通过后才调用 `Command(resume=...)`。
