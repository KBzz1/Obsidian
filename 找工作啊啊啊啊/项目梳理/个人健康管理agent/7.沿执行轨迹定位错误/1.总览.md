# 第七章 总览：沿执行轨迹定位错误

## 章节定位

第七章回答一个问题：最终回答错了以后，怎样判断到底是哪一层出了问题。

第一～六章合起来是一套在线 Agent Harness（任务、上下文、证据、工具、协作、治理都在执行路径上）；第七章不在执行路径上，而是这套系统的质量反馈闭环：它不重新实现任何执行能力，而是读取前六章各运行时在执行过程中已经产生的结构化事实，把它们串成统一执行轨迹，还原一次 Agent Task 实际看到了什么、做了什么、产生了什么结果，再沿执行链路分层评估，并与稳定基线做回归比较，回答「智能体是否做对、系统改动是否真正改善结果」。

与普通文本生成应用不同，Agent 应用不能只通过最终回答判断质量。普通 LLM 应用只需要评价「输入 → 输出」：

```text
普通 LLM 应用

User Input
→ Final Output
```

而 Agent Harness 在一次任务里会发生一系列真实动作：

```text
Agent Harness

User Input
→ Context
→ Retrieval
→ Agent Decision
→ Tool / DomainTask
→ Business Effect
→ Final Output
```

一个最终答案可能表面正确，但 Agent 在过程中调用了不必要的 Tool、使用了错误的业务状态，或者绕过了应该发生的 HIL；反过来，一次任务失败也可能不是模型判断错误，而是 Retrieval 没有找到正确资料、Context Assembler 没有把已有 Evidence 放入上下文，或者 Tool 返回了真实业务冲突。因此本章需要回答四类问题：

- 模型当时看到了什么
- Agent 实际做了什么
- 真实系统产生了什么 Effect
- 最终任务有没有正确完成

观测与评估由此连接成一套统一体系：观测负责还原执行事实，评估负责判断这些事实是否符合任务预期。整体关系可以表示为：

```text
Agent Task 执行
    ↓
各 Runtime 产生结构化运行事实
    ↓
Trace 将一次 Run 中的调用关系串联起来
    ↓
还原模型当时看到的 Context、Evidence 与能力
    ↓
还原 Agent 实际执行的 Retrieval、Tool 和 DomainTask
    ↓
构造成可评估的执行轨迹
    ↓
分层 Evaluation
    ↓
Regression Comparison
```

## 章节边界

第七章只负责观测关联、分层评估与回归比较。以下概念**不在本章展开**，各有归属章节：

| 不在本章展开 | 归属章节 |
| --- | --- |
| 任务的创建、推进、中断、检查点（Checkpoint）与恢复，以及 task_id / run_id 的身份定义 | 第一章 · Harness 控制平面与任务状态编排 |
| 单次模型调用装配哪些上下文、ContextManifest 如何生成 | 第二章 · 上下文工程与能力渐进装载 |
| 长期记忆写入、RAG、证据装配、RetrievalRecord | 第三章 · 长期记忆、知识 RAG 与证据装配 |
| 一次工具调用的参数校验、权限、HIL、幂等、重试与执行记录 | 第四章 · 工具运行时与纵深安全控制 |
| 多智能体业务协作、DomainTask 的创建与 Run 归属 | 第五章 · 多智能体协作与异步任务执行 |
| 任务预算、队列、并发、背压、服务级熔断与支撑治理的轻量运行监控 | 第六章 · 生产运行时治理 |

与第六章的分工可以概括为：

```text
第六章
→ 生产 Runtime 治理与轻量运行监控
→ 回答「系统是否稳定运行、治理机制是否生效」

第七章
→ 统一执行轨迹与 Agent 质量评估
→ 回答「智能体是否做对、系统改动是否真正改善结果」
```

> [!note] 观测不建立第二套 Runtime 数据库
> Task State、EvidenceBundle、ToolInvocation、ExecutionRecord、DomainTask 等数据仍然由对应模块保存并维护，第七章只通过统一身份与 Trace 关联、筛选和评价这些事实。

> [!note] 生产 Trace 本身不是 Eval Case
> 生产 Trace 记录当时发生了什么，而 Eval Case 必须定义在固定输入条件下系统应该做什么；二者之间必须经过筛选、脱敏、状态冻结和 Ground Truth 补充。

## 与其他章节的接口

第七章消费前面章节产生的结构化事实，不修改它们的职责：

- 与第一章的接口是任务身份：`task_id`、`run_id` 的语义以第一章为准（见 [[4.Conversation 与 Task 生命周期#任务与 Run]]），每个 Run 对应一条独立 Trace，Trace 不改变检查点归档方式。
- 与第二章的接口是 ContextManifest：装配器在每次正式模型调用前生成清单（见 [[3.上下文装配器与 ContextPolicy#上下文清单（ContextManifest）]]），第七章用它判断模型当时是否获得了正确信息、哪些能力当时可见。
- 与第三章的接口是 RetrievalRecord 与 EvidenceBundle：检索记录保存候选召回与选中关系（见 [[8.证据检索#检索记录（RetrievalRecord）]]），`Evidence.evidence_id` 是跨模块引用证据的唯一身份。
- 与第四章的接口是 ToolInvocation 与 ExecutionRecord：执行记录与执行尝试一一对应，每次尝试记录自己实际发生的 `run_id`（见 [[7.Tool Result 与错误协议#执行记录与工具结果分离]]），第七章据此判断动作选择与真实业务 Effect。
- 与第五章的接口是 DomainTask 的 Run 归属：同步 DomainTask 拥有自己的 `task_id` 但嵌套在父 Run 内，异步 DomainTask 拥有独立的 `task_id` / `run_id` / `trace_id`（见 [[9.HIL 与异步任务#三种执行方式]]），第七章沿 `parent_task_id` 还原多 Agent 轨迹。
- 与第六章的接口是观测边界：支撑生产治理的运行指标归 [[8.轻量运行监控]]，完整 Trace 分析与质量评估在本章。
