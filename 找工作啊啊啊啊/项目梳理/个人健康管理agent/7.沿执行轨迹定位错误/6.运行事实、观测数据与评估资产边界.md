# 运行事实、观测数据与评估资产边界

## 观测不建立第二套 Runtime 数据库

本章的观测体系不建立第二套 Runtime 数据库。Task State、EvidenceBundle、ToolInvocation、ExecutionRecord、DomainTask 等数据仍然由对应模块保存并维护，本章通过统一身份和 Trace 将这些事实关联起来。Trace 负责表达调用关系和执行过程，结构化 Record 保存具有模块语义的事实，Log 用于搜索关键运行事件；支撑生产运行治理的运行指标已经在第六章的轻量运行监控中承担（见 [[8.轻量运行监控]]），本章只在评估需要时补充效率维度（Latency / Calls / Token Usage），不重复建设治理指标。四者承担不同职责，不相互替代。

## 三层数据边界

在此基础上，系统将数据分为三个层级，各自有不同的保存责任和保留策略：

```text
正式运行事实
→ Task Control State / Checkpoint / Business Facts / 重要 ToolInvocation 与 ExecutionRecord
→ 影响恢复、业务状态或安全审计，由对应 Runtime 可靠保存

观测数据
→ Trace / ContextManifest / RetrievalRecord / 结构化运行日志
→ 用于排障、执行分析和发现 Eval Case，可设置保留周期，不要求永久保存

评估资产
→ Eval Case / Fixture / Expected Behavior / Rubric / Regression Result
→ 固定、可重复、不可变
```

三者之间不能直接互通。生产 Trace 不等于 Eval Case：生产 Trace 只是发现问题和还原事实的来源，记录当时发生了什么；而 Eval Case 必须定义在固定输入条件下系统应该做什么。真正进入 Eval Dataset 的 Case 必须经过筛选、脱敏、状态冻结、形成固定 Fixture，并补充 Expected Behavior 或 Rubric（转换过程与三类数据集见 [[7.Evaluation Case 与测试数据集]]）。这样生产数据可以持续反馈到测试体系，同时避免 Eval Dataset 依赖不断变化的线上状态。

## 边界问答

**1. Q：** 为什么观测数据可以设置保留周期，评估资产必须固定、不可变？

**A：** 观测数据用于排障、执行分析和发现 Eval Case，过期后价值随时间降低，不必永久保存；Eval Case 依赖固定 Fixture、Expected Behavior 或 Rubric，一旦变化，同一 Case 在不同版本系统上的运行结果就失去可比性。

**2. Q：** 为什么本章不重复建设治理指标？

**A：** 支撑生产运行治理的指标已经由第六章的轻量运行监控承担；本章只在评估需要时补充效率维度（Latency / Calls / Token Usage），不建第二套指标体系。

**3. Q：** 为什么生产 Trace 不能直接当 Eval Case 用？

**A：** 生产 Trace 记录当时发生了什么，Eval Case 必须定义在固定输入条件下系统应该做什么。二者之间必须经过筛选、脱敏、状态冻结成 Fixture，并补充 Expected Behavior 或 Rubric，生产数据才能进入测试体系。
