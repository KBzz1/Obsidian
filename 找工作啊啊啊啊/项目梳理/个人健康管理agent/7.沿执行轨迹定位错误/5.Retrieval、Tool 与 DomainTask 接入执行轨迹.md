# Retrieval、Tool 与 DomainTask 接入执行轨迹

ContextManifest 回答「模型当时看到了什么」（见 [[4.ContextManifest 与模型可见上下文]]），但模型看到的信息从哪里来、Agent 的动作真正产生了什么 Effect，需要把前面章节的执行记录接入同一条轨迹。这里不重复第三、四、五章的全部机制，只说明它们如何被统一关联。

## 检索链路：从候选到证据

第三章的 EvidenceBundle 表示最终经过验证和装配、可以提供给 Agent 使用的 Evidence。为了评估 Retrieval 和 Evidence Assembly，本章使用第三章的 RetrievalRecord 还原一次检索中真正返回过哪些候选资料（记录的定义与归属见 [[8.证据检索#检索记录（RetrievalRecord）]]）：

```python
class RetrievalRecord:
    retrieval_id: str              # 本次检索记录身份

    task_id: str                   # 所属任务
    run_id: str                    # 所属 Run：任务的一次连续执行阶段，见第一章
    agent_id: str                  # 触发检索的调用者，如 supervisor / workout_agent

    query_ref: str                 # 检索查询引用，敏感原文可脱敏或只存哈希
    source_scope: list[str]        # 检索范围：用户画像 / 用户记忆 / 业务事实 / 领域知识 / 上游产物
    retrieval_config_version: str  # 本次检索使用的配置版本

    retrieved_items: list[dict]    # 候选召回结果
        # source_id               # 来源标识
        # source_version          # 来源版本 / 哈希，复现当时的资料版本
        # rank                    # 候选排名
        # score                   # 候选分数

    selected_evidence_ids: list[str]  # 最终进入证据包的证据身份（Evidence.evidence_id）
    evidence_bundle_id: str           # 关联的证据包身份
```

其中 `selected_evidence_ids` 引用 `Evidence.evidence_id`，`evidence_bundle_id` 引用 `EvidenceBundle.bundle_id`。因此一条完整的数据链是：

```text
Retrieval
    ↓
RetrievalRecord
    ↓
Candidate Sources
    ↓
Evidence Assembly
    ↓
EvidenceBundle
    ↓
Context Assembler
    ↓
ContextManifest
```

通过这条链路，评估时可以区分正确资料根本没有被 Retriever 找到、资料已经召回但证据装配没有选中；是否进入本轮上下文、Agent 是否看到正确信息仍然做错，由 ContextManifest 区分（见 [[4.ContextManifest 与模型可见上下文]]）。

## 工具链路：从提议到真实 Effect

Tool 层不为评估重新建立数据结构。第四章已经定义的 ToolInvocation、ExecutionRecord 和 ToolResult 继续作为 Tool 执行的事实来源：

```text
Agent Proposal
→ ToolInvocation (created_run_id)
→ ExecutionRecord (run_id)
→ ToolResult
```

ToolInvocation 是稳定的逻辑动作，可以跨越不同 Run：Agent 在 `run_001` 中提出修改计划并进入 HIL，用户确认后真正的工具执行发生在 `run_002`。执行记录与执行尝试一一对应：它不是调用实例整个生命周期的聚合记录，同一调用实例每次真实执行尝试各产生一条执行记录，`attempt_count` 表示本次尝试的序号，`run_id` 记录本次尝试实际发生的 Run。因此 ToolInvocation 记录最初产生它的 `created_run_id`，每一次执行尝试在自己的执行记录中记录实际执行发生时的 `run_id`（见 [[7.Tool Result 与错误协议#执行记录与工具结果分离]]）。

```text
ToolInvocation invocation_123
│
├── task_id
├── created_run_id = run_001
│
└── ExecutionRecord
    └── run_id = run_002
```

第七章通过这些记录判断 Agent 选择了哪个 Tool、参数是否符合任务要求、执行是否经过批准、最终业务 Effect 是否真实发生，以及失败以后 Agent 是否采取了正确恢复行为。

## DomainTask 如何出现在轨迹中

同步 DomainTask 通过 Domain Agent Span 出现在父 Trace 中，与父任务处于同一条执行轨迹；异步 DomainTask 拥有独立 Trace，通过 `parent_task_id` 挂回父任务（Run 归属见 [[3.Task、Run 与 Trace 身份关联#多 Agent 的 Run 归属]]）。因此评估系统既可以分析一个 Task 内 Supervisor 与 Domain Agent 的协作轨迹，也可以沿 `parent_task_id` 父子关系检查异步任务是否正确产生 Artifact 并返回主流程，而不需要让多个 Agent 共享完整历史记录。

## 边界问答

**1. Q：** 为什么 ToolInvocation 记录 `created_run_id`，执行记录另外记录 `run_id`？

**A：** ToolInvocation 是可以跨越不同 Run 的稳定逻辑动作——Agent 可能在 `run_001` 提出修改并进入 HIL，用户确认后真正的执行发生在 `run_002`；执行记录与每次真实执行尝试一一对应，记录本次尝试实际发生时的 Run。两个身份分开，评估才能分别判断「动作在哪个阶段被提议」与「动作实际在哪个阶段执行」。

**2. Q：** 为什么 Tool 层不为评估重新建立数据结构？

**A：** 第四章已经定义的 ToolInvocation、ExecutionRecord 和 ToolResult 就是 Tool 执行的事实来源，本章只消费它们做关联与评价；另建一套评估专用记录会带来两份数据的一致性问题。
