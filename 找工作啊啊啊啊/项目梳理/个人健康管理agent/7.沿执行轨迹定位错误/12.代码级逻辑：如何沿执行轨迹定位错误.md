# 代码级逻辑：如何沿执行轨迹定位错误

本篇回答一个问题：最终结果错误以后，怎样沿执行轨迹把错误定位到具体一层，而不是把所有失败都归结为「LLM 回答不好」。评估不是只有一个「最终答案好不好」的问题。最终 Workout Plan 忽略「工作日只能晚练」，可能发生在检索没召回、证据装配丢弃、上下文没装进本轮、模型看到正确事实仍决策错误、工具选错或执行失败、跨 Agent 交接丢失、最终回复没有忠实描述真实 Effect——这七个位置中的任何一个。第七章不重新实现前六章，只消费它们已经产生的结构化事实。

走查沿用已冻结身份：跨领域主例 T200（AgentTask，整个用户目标），配领域任务 DT10 / DT20、训练产物 A100、后台执行记录 AE500；主链 Run 为 R1，对应轨迹 trace_A（身份语义见 [[3.Task、Run 与 Trace 身份关联]]）。领域任务用 `domain_task_id` 标识，不拥有独立的 `task_id` / `run_id`；后台执行记录 AE500 绑定 `domain_task_id`、可拥有独立 `run_id` / `trace_id`（口径见 [[5.Retrieval、Tool 与 DomainTask 接入执行轨迹#DomainTask 如何出现在轨迹中]]）。

## 统一主链

从一次任务执行到一次回归比较，全部动作发生在这条链上，后续各节逐段展开：

```text
T200 / R1 开始
    ↓
任务运行时创建 trace_id              # 一个 Run 一条 Trace
    ↓
TraceContext 随 RuntimeContext 传播   # 身份进入每个工程边界，模块不再自己猜
    ↓
各工程边界创建 Span                   # 只为有意义的边界建区段
    ↓
Span 结束时回填结构化 Record 引用      # Trace 不复制事实内容
    ↓
Run 结束 → Trace 完成
    ↓
EvaluationLoader                     # 评估侧加载器
    ↓ 按 task_id / run_id / trace_id 加载相关 Runtime Facts
TaskExecutionView                    # 评估时临时装配的执行视图
    ↓
分层 Evaluator
    ├─ Retrieval / Evidence
    ├─ Context
    ├─ Tool / Action
    ├─ Trajectory / Multi-Agent
    └─ Final Task
    ↓ 确定性规则优先，必要时构造 JudgeInput
LayerEvaluationResult                # 每层独立结果，不是一个总分
    ↓
FailureAttribution                   # primary_failure + findings，不强行归成唯一根因
    ↓
Regression Comparison                # 与稳定 Baseline 比较
```

## TraceContext：身份随 RuntimeContext 传播

TraceContext 是观测身份的传播载体：一次 Run 的 `task_id`、`run_id`、`trace_id`，加上当前正在执行的 Span 位置。Run 创建时，任务运行时建立 `trace_id`，与 `task_id`、`run_id` 一起打进 RuntimeContext，随后传给 Supervisor、ContextAssembler、LLM Gateway、Retrieval、Tool Runtime、Domain Agent——每个工程边界从 RuntimeContext 读取身份，不让各模块自己重新猜「这次调用属于哪个任务哪段执行」：

```python
class TraceContext:
    task_id: str          # 所属逻辑任务，如 T200
    run_id: str           # 所属执行段，如 R1
    trace_id: str         # 本 Run 的轨迹身份，Run 创建时生成
    span_id: str          # 当前正在执行的 Span
    parent_span_id: str | None  # 当前 Span 的父区段；轨迹根为 None
```

`span_id` / `parent_span_id` 随 Span 创建与结束推进，表达的是「此刻执行到轨迹的哪个位置」；它们随每个边界组件在 RuntimeContext 里下沉，落盘后成为 TraceSpan 的字段。

## TraceSpan：只为工程边界建区段

Span（区段）是轨迹中一段有开始、有结束、有状态的执行区间。只为有工程意义的边界建 Span——Supervisor 编排轮次、Domain Agent 执行、Context Assembly、LLM Call、Retrieval、Tool Invocation、Final Response；普通内部函数不建，否则轨迹膨胀成执行日志，定位错误的信噪比反而下降：

```python
class TraceSpan:
    trace_id: str               # 属于哪条轨迹
    span_id: str                # 本区段身份
    parent_span_id: str | None  # 父区段；表达调用嵌套关系

    task_id: str                # 归属任务，从 TraceContext 读取
    run_id: str                 # 归属执行段，从 TraceContext 读取

    domain_task_id: str | None  # 若本区段在推进某个领域任务，如 DT10；否则为空
    agent_id: str | None        # 执行本区段的智能体，如 workout_agent

    span_type: str              # supervisor / domain_agent / context_assembly /
                                # llm_call / retrieval / tool_invocation / final_response
    status: str                 # running / completed / failed

    started_at: datetime        # 区段开始时刻
    ended_at: datetime | None   # 区段结束时刻，进行中为空

    record_refs: list[str]      # 指向对应模块的结构化 Record，结束时回填
    error_code: str | None      # 区段失败的错误码，如 DependencyUnavailable
```

一个同步领域工作单元在轨迹中的样子：Supervisor 委派 DT10 后，训练智能体的执行落在 `domain_task_id = DT10` 的 Domain Agent Span 内，其内部再嵌套 Context Assembly、LLM Call、Retrieval、Tool Invocation 子区段——整棵 Span 树挂在 T200 / R1 的 trace_A 上。后台执行则是另一棵树：AE500 拥有自己的 `run_id` / `trace_id`，Span 树建在自己的轨迹上，通过 `parent_task_id + domain_task_id` 挂回 T200 / DT10。

## Span 引用 Record，不复制 Runtime Fact

Trace 与 Runtime Record 的分工：Trace 只保存「谁调用谁 + 时间 + 状态 + 引用」，模块真正的事实仍在各章 Record 里。Span 结束时只回填引用身份，不同类型的 Span 引用不同的 Record：

```text
Context Span       → context_id                     # 第二章 ContextManifest
LLM Call Span      → llm_call_id + context_id       # 本篇 LLMCallRecord + 清单
Retrieval Span     → retrieval_id / evidence_bundle_id   # 第三章检索记录与证据包
Tool Span          → invocation_id / execution_record_id # 第四章调用实例与执行记录
Domain Agent Span  → domain_task_id / artifact_refs # 第五章领域任务与产物
Budget / Runtime   → 必要时引用对应记录              # 第六章预算扣减、切片、熔断事件
```

这样定的理由与 [[6.运行事实、观测数据与评估资产边界]] 的三层数据边界一致：复制内容会制造两份需要保持一致的数据，Trace 一旦保存事实正文，事实源就不再唯一。评估需要内容时，沿引用回到对应 Record 读取——观测不建立第二套 Runtime 数据库。

## LLMCallRecord：模型调用的观测身份

ContextManifest 只能回答「Harness 准备给模型看什么」；装配成功不代表调用成功，清单也不知道模型调用最终用了什么版本、返回了什么。这一段观测由 LLMCallRecord 补齐——它是第六章为预算引入的逻辑模型调用（LC）的观测记录，`llm_call_id` 就是 LC 身份，一次逻辑调用一条记录、网络重试不新增：

```python
class LLMCallRecord:
    llm_call_id: str            # 逻辑模型调用身份，即第六章 LC，如 LC300

    task_id: str                # 归属任务
    run_id: str                 # 归属执行段

    context_id: str             # 本轮调用的上下文清单身份，指向 ContextManifest

    agent_id: str               # 发起调用的智能体，如 supervisor / workout_agent
    model_id: str               # 实际使用的模型

    prompt_version: str | None        # 实际生效的提示模板版本
    model_config_version: str | None  # 实际生效的模型配置版本

    status: str                 # success / failed：调用本身是否成功
    output_ref: str | None      # 结构化输出的引用，见下文
    token_usage: dict | None    # 令牌用量，效率指标来源之一
    error_code: str | None      # 调用失败错误码，如 DependencyUnavailable
```

`context_id` 是清单与调用记录之间的挂接点：第二章统一调用入口装配出 ModelContext 与 ContextManifest（同源双产出，见 [[11.代码级逻辑：一次 LLM 调用如何装配上下文#同源双产出：ContextManifest]]），调用发生时 LLMCallRecord 记下这个 `context_id`，「模型被给了什么」与「模型调用结果如何」在评估时按它对上。`output_ref` 引用本次调用产出的结构化对象——SupervisorAction、Tool Proposal、AgentResult 或最终响应——或保存受控摘要 / 哈希；Chain-of-Thought 不保存也不评估，评估只看可观察的输出与动作。

## TaskExecutionView：评估时的临时装配视图

评估器不自己到十张表里乱查。EvaluationLoader 按 `task_id` / `run_id` / `trace_id` 把一次任务相关的 Runtime Facts 加载关联出来，构成 TaskExecutionView——它只是评估时读取和关联出来的视图，不落库、不成为新的事实源：

```python
class TaskExecutionView:
    task_id: str                  # 被评估的任务，如 T200

    runs: list[str]               # 相关执行段：R1，后台执行则含 AE500 的 run_id
    traces: list[str]             # 相关轨迹：trace_A，后台执行另有 trace

    context_manifests: list[str]  # 本任务全部上下文清单（context_id）
    llm_calls: list[str]          # 本任务全部模型调用记录（llm_call_id）

    retrieval_records: list[str]  # 检索记录（retrieval_id）
    evidence_bundles: list[str]   # 证据包（bundle_id）

    tool_invocations: list[str]   # 调用实例（invocation_id）
    execution_records: list[str]  # 执行记录（尝试级）

    domain_tasks: list[str]       # 领域任务（domain_task_id）
    artifacts: list[str]          # 领域产物（artifact_id）

    final_response_ref: str | None  # 最终响应引用
```

视图里存的全是引用身份：Evaluator 拿到视图后，按各层的需要沿引用读取 Record 内容。HIL 暂停产生多个 Run 的任务（如 T100 的 R1 / R2），视图把多个 Run、多条 Trace 收进同一个 `task_id` 下，评估看到的是任务全程。

## 归因：每层独立评估，primary_failure 加 findings

Final Task 层失败后，归因沿执行链的固定顺序逐层独立评估，例如「Diet 调整忽略了工作日只能晚练」，每层按自己的判据判：

```text
1. RetrievalRecord      正确事实有没有被召回？
2. EvidenceBundle       正确事实有没有进入最终 Evidence？
3. ContextManifest      该 Evidence / A100 有没有进入本轮模型上下文？
4. LLMCallRecord        模型是否看到正确 Context 后仍做出错误动作？
5. ToolInvocation / Effect   模型动作是否被正确执行？
6. DomainTask / Artifact     跨 Agent 交接是否丢失正确结果？
7. Final Response       最终回复是否忠实反映真实状态？
```

关键规则是**不强行归因成唯一根因**：一次失败可能同时是多个层的独立问题。模型选错了 Tool（model_decision FAIL），错误 Tool 又执行失败（tool_execution FAIL），最终回复还错误声称成功（final_response FAIL）——这是三个独立可判定的问题，不能最后只留下一个。上游失败也不终止后续层的评估：每层结论记录进 findings，FailureAttribution 从 findings 中取执行链上最早可证实的偏离点作为 primary_failure：

```python
class Finding:                    # 单个层的独立发现
    layer: str                    # 哪一层发现问题，如 model_decision
    status: str                   # FAIL / UNKNOWN；PASS 不进入 findings
    reason_code: str              # 层内原因，如 wrong_action_with_correct_context
    evidence_refs: list[str]      # 支撑判断的 Record 引用

class FailureAttribution:
    primary_failure: str | None   # 执行链上最早可证实的偏离点所在层；无 FAIL 时为空
    reason_code: str | None       # primary 层内的原因类别
    findings: list[Finding]       # 全部层级的独立发现，含 primary 之后的 secondary findings
```

primary_failure 的取法是确定性的：沿 1 → 7 的层序取 findings 中最早一个 FAIL；UNKNOWN 是「无法证实」，不竞争 primary。例如上下文正确、模型决策错误、工具随后执行失败：primary_failure = model_decision，findings 同时含 model_decision 与 tool_execution 两条。修复顺序也由此可推导——先修 primary，再复核后续 findings 是否随之消失。

不允许未经逐层检查就把所有错误归成「LLM 回答不好」：那既不可修复，也不可回归验证。这个「不要求唯一固定轨迹」的思想与 [[8.Agent 分层评估]] 的 Trajectory 评估一致：评估约束的是可判定的偏离，不是把一次执行压成单点结论。

## 确定性 Evaluator 优先

凡是从结构化 Record 能直接判定的问题，不调用 LLM-as-Judge。这一层检查是纯代码：读视图里的引用，比对 EvalCase 声明的期望，输出 PASS / FAIL；判定所需的 Record 缺失时该层记 UNKNOWN（见「观测自身的三个异常边界」），UNKNOWN 不进 FAIL 统计：

| 确定性检查 | 读取的事实 | 判定方式 |
| --- | --- | --- |
| required Evidence 是否存在 | ContextManifest 的 `evidence_refs` 对照 Case 声明 | 引用集合包含检查 |
| Tool 是否允许 | `visible_tool_refs` 与实际 ToolInvocation | 调用的工具是否在暴露清单内 |
| 是否经过 HIL | ToolInvocation 的 `approval_state` | 写操作必须 APPROVED 才有执行记录 |
| Tool 参数是否正确 | `arguments_snapshot` 对照 Case 期望 | 字段级比较 |
| Business Effect 是否成功 | ExecutionRecord 终态与业务 Effect | 状态与效果断言 |
| DomainTask 是否越权 | ExecutionRecord 的域与 DT 声明的领域 | 跨域调用即违规 |
| Artifact 是否来自正确 producer | DomainArtifact 的 `producer_domain_task_id` | 归属校验 |
| CONFLICT 后是否恢复 | CONFLICT 执行记录之后的轨迹动作 | 必须存在重新读取 / 重新规划 / 上报 Supervisor |
| 最终声明是否与 Effect 一致 | 最终响应声明对照 ExecutionRecord | 声称成功必须有效果佐证 |

这些检查与 [[9.Rubric 与 LLM-as-Judge]] 的分工一致：能编码成规则的不交给模型。跨层安全规则（禁止 Tool、HIL Bypass、跨 Domain 越权）也在这里判定，出现即 FAIL，不进语义评分。

## LLM-as-Judge 只处理开放质量

确定性规则覆盖不了的是开放式语义问题：训练计划整体是否合理、多个软约束是否权衡充分、最终建议是否完整。Judge 的输入不使用整个 Trace，统一从 TaskExecutionView 构造：

```python
class JudgeInput:
    user_request              # 用户请求
    relevant_business_facts   # 与本任务相关的业务事实
    evidence                  # 评估依据的证据
    executed_actions          # 实际执行的动作
    tool_effects              # 动作产生的真实业务效果
    final_response            # 最终回复
    rubric                    # 本 Case 使用的评分标准
```

Judge 返回少量离散等级——NOT_MET / PARTIAL / MET——加简短理由，不做百分制细评分。等级与理由随 LayerEvaluationResult 保存，成为可追溯的评估事实。

## EvalCase 与 EvaluationRun：数据集与执行分开

EvalCase 是可重复运行的评估场景（定义见 [[7.Evaluation Case 与测试数据集]]），字段保持已有设计：`case_id` / `user_request` / `fixture_ref` / `capability_config` / `evaluators` / `tags`。Fixture 必须不可变：它在生成 Case 时脱敏冻结，评估执行时用它恢复 Business State、Memory、Knowledge、User State、Current Plan 五类起始状态，使同一 Case 在任何版本系统上从同一起点跑起。

一次评估执行本身也要有身份。EvaluationRun 记录这次跑了哪个数据集、用哪个版本的系统与 Judge 跑的——两个 Eval Score 只有追溯到同一组配置才真正可比较：

```python
class EvaluationRun:
    eval_run_id: str              # 本次评估执行的身份

    dataset_version: str          # 使用的数据集版本
    candidate_version: str        # 被评估的系统版本

    model_version: str            # 被评估系统的模型版本
    prompt_version: str           # 提示模板版本
    workflow_version: str         # Workflow 编排版本
    retrieval_config_version: str # 检索配置版本
    tool_schema_version: str      # 工具 Schema 版本

    judge_version: str | None     # Judge 复合版本引用（模型 + Prompt + Rubric）；无 Judge 时为空

    started_at: datetime          # 开始时刻
    finished_at: datetime | None  # 结束时刻
```

字段全部是版本引用，不复制配置全文——与 ContextManifest 记版本不记 Prompt 正文是同一条边界。概念层面 [[10.Regression 与质量反馈闭环]] 列出的记录维度（app / model / prompt / workflow / retrieval / tool schema / judge 各项），在代码级统一收进这些版本字段。

## LayerEvaluationResult：每层独立出结果

每层 Evaluator 输出统一的分层结果，而不是最后只保存一个总分：

```python
class LayerEvaluationResult:
    case_id: str                 # 属于哪个评估用例
    eval_run_id: str             # 属于哪次评估执行

    layer: str                   # retrieval_evidence / context / tool_action /
                                 # trajectory / final_task

    status: str                  # PASS / FAIL / UNKNOWN / REVIEW
                                 # UNKNOWN：Record 缺失、Trace 不完整、无法证明发生了什么

    metric_values: dict          # 本层指标值，如 recall@k、tool_selection_accuracy
    violations: list[str]        # 违规项，硬门槛违规也记在这里

    runtime_fact_refs: list[str]  # 支撑本层结论的 Record / Span 引用
    reason_code: str | None      # FAIL 或 UNKNOWN 的原因类别，如 INSUFFICIENT_OBSERVATION
```

`runtime_fact_refs` 保证每个结论可回溯：任何一个 FAIL 都能指出是哪些 Record 支持了这个判断，复核时沿引用重放，不靠记忆和截图。UNKNOWN 单列的目的是守住一条边界：**没有观测到 ≠ 证明 Agent 做错**——观测缺失的层不出 FAIL，只如实标记无法评估；这些层以 UNKNOWN 进入 FailureAttribution 的 findings，不竞争 primary_failure。

## Regression：三类判断，不用统一总分

回归比较保持三类判断。硬门槛——Forbidden Tool、HIL Bypass、跨 Domain 越权、关键业务状态错误——出现即 FAIL，不允许其他指标的提升抵消。质量指标——Recall@K、Tool Selection Accuracy、Trajectory Pass Rate、Task Completion——与稳定 Baseline 在相同 Dataset 上比较，波动范围根据已有基线和实际数据逐步设置，不在没有数据的情况下虚构精确阈值。效率指标——Latency / 模型与工具调用次数 / Token Usage——从 Trace 时长与 LLMCallRecord 的 `token_usage` 统计而来，通常不直接决定质量 PASS，用于发现「质量提升但成本失控」的情况。

三类判断汇总成整次回归的最终状态：PASS（无硬门槛失败、关键质量无明显退化）/ FAIL（硬门槛违规或关键质量下降）/ REVIEW（质量与成本此消彼长，需要人工判断 Trade-off）。

## 生产问题如何进入 Regression Dataset

生产 Trace 本身不是 EvalCase。一次生产失败要经过固定链路转换成可重复执行的 Fixture + Request + Evaluator，才能进数据集：

```text
Production Task
    ↓
Trace + Runtime Records          # 还原事实
    ↓
用户反馈 / 异常发现
    ↓
FailureAttribution               # 先定位错误在哪一层
    ↓
脱敏                             # 用户身份、敏感内容
    ↓
固定起始状态为 Fixture            # 冻结 Business State / Memory / Knowledge / User State / Current Plan
    ↓
创建 EvalCase                    # 补 Expected Behavior 或 Rubric
    ↓
加入 Regression Dataset
```

顺序有含义：先 FailureAttribution 再做 Case——归因告诉你这个失败真正考察的是哪一层（检索、装配还是决策），EvalCase 的 evaluators 与断言按它声明；跳过归因直接保存失败现场，得到的只是「又一条失败记录」，不是可回归验证的用例。

## 观测自身的三个异常边界

观测与评估链路自己也会出错，三条边界事先定死：

1. **Trace 写失败，不能导致正式业务事务失败。** Runtime Fact 仍是唯一事实源，Trace 是观测层；写入失败时该 Run 的轨迹标记 `observation_incomplete`，业务照常执行。
2. **某个 Record 引用不存在，Evaluator 返回 `INSUFFICIENT_OBSERVATION`。** 证据链断了就说断：该层 status = UNKNOWN（reason_code = INSUFFICIENT_OBSERVATION），进入 findings 但不竞争 primary_failure；不能让 Judge 猜发生了什么——猜测产出的评估结论不可回归。
3. **Judge 失败，确定性 Evaluation 结果仍保留。** Judge 维度标记 unavailable，本次 Regression 不因 Judge 故障被当成系统执行失败，也不产出含猜测的 Judge 分数。

三条共同的边界逻辑：观测不绑架业务，证据不完整不硬评，单维度故障不否定整次执行。

## 场景走查

### 走查一：Diet 调整错误，归因到 model_decision

用户反馈 T200 的最终 Diet 调整忽略了「工作日只能晚练」。沿七步顺序检查 R1 / trace_A：

```text
T200 / R1 / trace_A
    ↓ DT10 Workout succeeded，产物 A100 正确（归属 DT10、status = ready）
    ↓ DT20 Diet 执行，最终结果错误

① RetrievalRecord（finalized）
    selected_evidence_ids 含「工作日只能晚练」相关事实   → 召回没有丢
② EvidenceBundle
    该 Evidence 在最终证据包内                          → 装配没有丢
③ ContextManifest（Diet 的 LLM 调用，context_id = ctx_52）
    evidence_refs 含该 Evidence；artifact_refs 含 A100   → 上下文没有丢
④ LLMCallRecord（llm_call_id = LC260）
    context_id = ctx_52，status = success，prompt / model 版本正确
    → 模型看到正确输入，仍给出错误动作
⑤⑥⑦ Tool 执行正常、交接无丢失、最终回复如实描述了（错误的）结果
    → 逐层评估通过，不产生 finding；若任一层也失败，继续记入 findings

FailureAttribution(
    primary_failure = "model_decision",     # 执行链上最早可证实的偏离点
    reason_code = "wrong_action_with_correct_context",
    findings = [
        Finding(layer = "model_decision", status = "FAIL",
                reason_code = "wrong_action_with_correct_context",
                evidence_refs = [ctx_52, LC260, DT20 的 ExecutionRecord...]),
    ],
)
```

### 走查二：同样症状，归因到 context_assembly

换一条执行：EvidenceBundle 里有正确事实，但 Diet 的 ContextManifest `evidence_refs` 不含它——可能被上下文预算裁剪掉。第 ③ 层即失败，后续层不短路、继续评估：

```text
③ ContextManifest：required Evidence 不在 evidence_refs
    → context_assembly FAIL
④ LLMCallRecord：模型收到的 ctx_53 不含该 Evidence
    → 后续决策偏差由上游传播导致，不重复记为模型层 finding
⑤⑥⑦ 继续独立评估：本例无其他独立问题

FailureAttribution(
    primary_failure = "context_assembly",
    reason_code = "required_evidence_not_visible",
    findings = [
        Finding(layer = "context_assembly", status = "FAIL",
                reason_code = "required_evidence_not_visible",
                evidence_refs = [bundle_id, ctx_53, ...]),
    ],
)
```

同样的最终症状，两条不同的归因：修复一个要调模型或 Prompt，另一个要调上下文策略与预算裁剪顺序。这就是第七章真正要证明的能力——最终结果错误不再只有一种解释。

### 走查三：工具失败，归因到依赖故障而不是模型

Diet 智能体调用营养查询工具失败。Tool Span 的 `error_code` 与 ExecutionRecord 显示 `DependencyUnavailable`，第六章观测事实中 `model_api` / 营养服务的熔断器当时处于 OPEN：

```text
⑤ ToolInvocation I270：approval 正常、参数正确
   ExecutionRecord：DependencyUnavailable（熔断 OPEN 期间）
    ↓
FailureAttribution(
    primary_failure = "tool_execution",
    reason_code = "dependency_unavailable",
    findings = [
        Finding(layer = "tool_execution", status = "FAIL",
                reason_code = "dependency_unavailable",
                evidence_refs = [I270, ExecutionRecord, 熔断事件...]),
    ],
)
```

归因指向共享依赖健康，不指向模型决策；模型的恢复行为（是否按恢复规则重试或上报）另由 Trajectory 层检查。第六章的治理观测事实在这里被消费，两章各取所需。

## 第七章代码级理解总结

- **Trace 与 Record 分工**：Trace = 谁调用谁 + 时间 + 状态 + 引用；Record = 模块真正的事实。Span 只存引用，事实源不重复，观测不建第二套 Runtime 数据库。
- **身份只产生一次**：Run 创建时定 trace_id，经 TraceContext / RuntimeContext 单向传播；模块不猜身份，评估按 task_id / run_id / trace_id 精确取数。
- **ContextManifest 与 LLMCallRecord 各答一半**：前者答「准备给模型看什么」，后者答「调用是否成功、用了什么版本、输出了什么」，`context_id` 把两半对上。
- **归因不收敛到唯一根因**：七层逐层独立评估，findings 汇总全部层级的发现，primary_failure 取执行链上最早的 FAIL；UNKNOWN 是「无法证实」，不竞争 primary、不等于做错。
- **确定性优先**：能从 Record 判定的不进 Judge；Judge 只收 TaskExecutionView 构造的 JudgeInput，输出三档等级。
- **可比较性靠版本**：EvalCase 冻结起点（Fixture 不可变），EvaluationRun 冻结版本配置，缺一不可比。
- **观测不绑架业务**：Trace 写失败标记 incomplete、引用缺失返回 INSUFFICIENT_OBSERVATION、Judge 故障保留确定性结果。

## 未下沉与不新增

仍未达到代码级逻辑的部分：各确定性检查的具体实现库与断言语法；质量指标波动范围的实际数值（等有基线数据后再定）；Judge 校准 Case 的具体清单；观测数据的保留周期数值；TraceSpan 与 OpenTelemetry 一类标准协议的映射（未来接观测后端时再定，当前只保证字段语义清晰）。

本轮明确不新增：独立的评估数据库、第二套 Runtime 事实存储、完整 Prompt 持久化、Chain-of-Thought 记录、在线全量 Judge、多 Judge 投票、复杂的指标平台。评估消费的每一份事实都来自前六章已有结构，新增的只有 TraceSpan、LLMCallRecord、TaskExecutionView、LayerEvaluationResult、FailureAttribution、EvaluationRun 六个观测与评估侧结构。

明确保留的遗留问题：`observation_incomplete` 的 Trace 在评估时的降级策略（按 INSUFFICIENT_OBSERVATION 处理还是部分评估）暂定为前者，待首轮真实回归后复核；后台 DomainTask 的效率指标归属（记在 AE500 还是摊回 T200）暂按 AE500 自身统计、汇总视图再归并，同样待实现时复核。

## 边界问答

**1. Q：** task_id / run_id / trace_id 分别是什么？

**A：** task_id 是一个逻辑任务完整生命周期的稳定身份（T200）；run_id 是任务一段连续执行的身份，HIL 恢复、后台执行会产生新的 Run；trace_id 是该 Run 对应的观测轨迹身份，Run 创建时生成，一个 Run 一条 Trace。任务跨越多段执行时，多个 run_id / trace_id 挂在同一个 task_id 下。

**2. Q：** 同步 DomainTask 为什么没有独立 task_id / run_id？

**A：** DomainTask 是 T200 内部的工作单元，不是独立任务：同步委派只是父任务当前 Run 内的嵌套执行，没有独立的执行生命周期，给它配 task / Run 等于让一次子调用背上完整任务运行时。它用 `domain_task_id` 标识，出现在 T200 / R1 的 Trace 中；只有进入后台执行时才由执行记录 AE500 拥有独立 run_id / trace_id，并通过 `parent_task_id + domain_task_id` 挂回。

**3. Q：** TraceSpan 为什么只存 Record 引用？

**A：** Tool 参数、Evidence 内容、执行效果这些事实已经由各章 Record 保存；Span 再存一份就出现两份需要保持一致的数据，事实源不再唯一。Trace 只答「谁调用谁、何时、状态如何」，内容沿引用回 Record 取——观测不建第二套 Runtime 数据库。

**4. Q：** ContextManifest 和 LLMCallRecord 分别回答什么？

**A：** ContextManifest 回答「Harness 准备给模型看什么」：哪些证据、事实、产物、工具能力进入本轮上下文。LLMCallRecord 回答「这次模型调用本身怎么样」：是否成功、用了哪个模型与 Prompt 版本、输出了什么结构化结果。两者经 `context_id` 关联，前者由装配链生成，后者由调用链生成，谁也不覆盖谁。

**5. Q：** TaskExecutionView 是数据库吗？

**A：** 不是。它是评估时由 EvaluationLoader 读取并关联出来的临时视图，存的全是引用身份，不落库、不成为事实源；任务执行的事实仍在各章 Runtime 的存储里。

**6. Q：** 如何判断：没召回 / Evidence 丢失 / Context 丢失 / 模型决策错？

**A：** 按固定顺序查结构化事实：RetrievalRecord 的候选与选中里没有正确资料是没召回（retrieval）；候选有、EvidenceBundle 没选它是装配丢（evidence_assembly）；Evidence 在包里、ContextManifest 的 `evidence_refs` 没引用它是上下文丢（context_assembly）；四层都对、LLMCallRecord 确认输入正确仍做错，才是模型决策错（model_decision）。

**7. Q：** 为什么确定性规则优先于 Judge？

**A：** Tool 是否允许、是否经过 HIL、Effect 是否成功这类问题有唯一正确答案，从 Record 直接判定是零成本、可复现、可解释的；交给 Judge 会把确定性问题变成概率评分。Judge 只在开放语义问题（计划是否合理、权衡是否充分）上使用，且输入收敛为 JudgeInput。

**8. Q：** Judge 为什么不读取完整生产 Trace？

**A：** 完整 Trace 含大量与评价无关的执行细节，放大输入成本，还迫使 Judge 自行理解各 Runtime 的内部语义，本可确定性判断的错误也变成概率判断。JudgeInput 只给完成评价需要的事实：请求、相关事实、证据、动作、效果、最终回复与 Rubric。

**9. Q：** 生产 Trace 为什么不能直接当 EvalCase？

**A：** 生产 Trace 记录「当时发生了什么」，EvalCase 必须定义「固定输入条件下系统应该做什么」。Trace 的起始状态、数据、记忆都在变化，直接回放不可重复；必须经归因、脱敏、状态冻结成 Fixture、补充期望或 Rubric，才成为可跨版本重复执行的用例。

**10. Q：** Fixture 为什么必须不可变？

**A：** 同一 Case 要在不同版本系统上比较，起点必须相同。Fixture 在生成时脱敏冻结，恢复出的 Business State / Memory / Knowledge / User State / Current Plan 每次一致；起点一变，结果差异就分不清是系统改动还是数据变化造成的。

**11. Q：** 为什么 EvaluationRun 必须记录版本？

**A：** 两个 Eval Score 只有追溯到同一组数据集、模型、Prompt、Workflow、检索配置、工具 Schema 与 Judge 配置时才可比。缺版本记录的分数无法解释差异来源，Regression Comparison 失去比较基准。

**12. Q：** Regression 为什么不用统一总分？

**A：** 硬门槛违规不能被其他指标提升抵消（出现即 FAIL）；质量指标要相对 Baseline 判断退化；效率指标通常不决定质量 PASS。统一总分无法表达「质量提升但成本明显增加」这类需要人工判断的情况，三类分开才有 PASS / FAIL / REVIEW。

**13. Q：** 如何把一次生产失败变成 Regression Case？

**A：** 沿固定链路：还原 Trace 与 Runtime Records → 用户反馈或异常发现 → FailureAttribution 定位出错层 → 脱敏 → 把起始状态冻结成不可变 Fixture → 创建 EvalCase 并补充 Expected Behavior 或 Rubric → 加入 Regression Dataset。生产 Trace 本身不进数据集，转换后的 Fixture + Request + Evaluator 才是 Case。
