# Evaluation Case 与测试数据集

## Eval Case 与固定 Fixture

一个 Eval Case（Evaluation Case）不是简单的“问题 + 标准答案”，而是一份可重复运行的 Agent 任务场景。它引用一个不可变 Fixture，用于恢复任务开始时的用户状态、业务事实、Memory、Domain Knowledge 和 Current Plan 等必要条件。

```text
EvalCase

case_id            # 本条评估用例的身份
user_request       # 固定的用户请求输入
fixture_ref        # 引用的不可变 Fixture，恢复任务起始状态
capability_config  # 本 Case 运行时的能力配置
evaluators         # 本 Case 声明的评估器，只声明与自身相关的部分
tags               # 分类标签
```

Fixture 中的事实在生成 Eval Case 时被脱敏并冻结，使同一个 Case 在不同版本系统上运行时具有相同起点，而不是依赖当前线上数据库或可能已经发生变化的 Memory。

每个 Case 只声明与自身相关的 Evaluator。例如一个 Retrieval Case 只需要运行 Recall 和 Evidence Coverage；一个 Tool Recovery Case 可以同时检查 Tool Selection、参数、恢复轨迹和最终业务结果；复杂 Workout Planning Case 才需要进一步进入最终 Rubric 和 LLM-as-Judge。

## 三类 Dataset

当前 Dataset 主要由三类 Case 组成。

第一类是核心能力集，由人工构造并长期保持稳定，覆盖 Supervisor 路由、Workout、Diet、Retrieval、Tool、HIL、多 Agent 等系统主要能力。它用于验证系统基础能力没有随着改动发生明显退化。

第二类是边界与故障集，专门覆盖正常路径不容易暴露的 Harness 行为，例如 Evidence 缺失、Tool Conflict、Timeout、Budget 接近耗尽、HIL Resume、禁止 Tool Call、跨 Domain Tool 等场景。

第三类是生产回归集。生产运行中发现具有代表性的失败后，通过 Trace 和结构化 Record 定位根因，再将必要的用户输入和系统状态脱敏、固定为 Fixture，并定义 Expected Behavior 或 Rubric，最终加入 Regression Dataset。生产 Trace 与 Eval Case 的边界以及转换步骤见 [[6.运行事实、观测数据与评估资产边界#三层数据边界]]。

## 边界问答

**1. Q：** 为什么 Eval Case 必须引用不可变 Fixture，而不是直接使用当前线上数据？

**A：** Fixture 在生成 Case 时被脱敏并冻结，使同一个 Case 在不同版本系统上运行时具有相同起点；如果依赖当前线上数据库或可能已经变化的 Memory，同一 Case 两次运行的结果无法比较。

**2. Q：** 为什么每个 Case 只声明与自身相关的 Evaluator？

**A：** 一个 Retrieval Case 只需要运行 Recall 和 Evidence Coverage；一个 Tool Recovery Case 检查 Tool Selection、参数、恢复轨迹和最终业务结果；只有复杂的 Workout Planning Case 才需要进入最终 Rubric 和 LLM-as-Judge。按 Case 声明，简单场景就不会被推向最重的评估方式。

**3. Q：** 为什么需要单独的边界与故障集？

**A：** Evidence 缺失、Tool Conflict、Timeout、Budget 接近耗尽、HIL Resume、跨 Domain Tool 这类场景在正常路径中不容易暴露，专门构造 Case 才能稳定覆盖这些 Harness 行为。
