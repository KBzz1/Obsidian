> 本笔记是「Agent 分层评估」的唯一归属地：沿上下文与 Evidence、Tool / Action、Trajectory、Final Task 四层定位质量。确定性判断与 LLM-as-Judge 的边界见 [[9.Rubric 与 LLM-as-Judge]]。

# Agent 分层评估

评估系统不使用单一总分判断 Agent 是否优秀，而是沿 Agent 执行链路分层定位质量。当前系统将主要评估对象分为四层：上下文与 Evidence、Tool 与动作、Agent 执行轨迹以及最终任务结果。安全、权限和业务约束作为跨层规则贯穿整个评估过程。

```text
上下文与 Evidence
        ↓
Tool / Action
        ↓
Agent Trajectory
        ↓
Final Task

横向约束：
Safety / Policy / Business Constraints

辅助维度：
Latency / Calls / Token Usage
```

## 上下文与 Evidence

这一层评估 Agent 做出决策之前是否获得了正确的信息。评估链覆盖 Retrieval、Evidence Assembly 和 Context Assembly，而不是只看向量检索的 Top-K 结果。

当前主要保留三个指标。`Recall@K` 检查应该被找到的资料是否进入 Top-K Retrieval Candidate；Evidence Coverage 检查完成任务所需的关键事实是否进入最终 EvidenceBundle；Evidence Grounding 检查 Evidence 中的 Claim 是否真正能够由对应 Source 支持。

结合 `RetrievalRecord`、`EvidenceBundle` 和 `ContextManifest`，评估系统能够进一步定位错误发生在哪一步。例如 Retriever 已经召回正确资料，但 Evidence Assembly 丢掉了该资料；或者 Evidence 已经形成，但 Context Assembler 没有把它加入当前 Agent 的模型上下文。这种分层定位比只评价最终回答是否正确更适合 Agent Harness。

## Tool / Action

Tool 层重点评估 Agent 是否选择了正确动作，而不是只检查调用最终是否成功。当前主要检查 Tool Selection、参数正确性、不必要调用和禁止行为。

Tool Selection 检查任务要求和实际选择的 Tool 是否匹配；参数评估检查关键字段是否齐全、对象是否正确以及业务参数是否符合用户意图。能够直接进行 Schema 或字段比较的部分使用确定性检查，复杂语义参数才进入 Rubric。

评估系统还会检查 Agent 是否进行了没有必要的 Tool Call 或重复 Tool Call。例如已有 Current Plan Evidence 时，Agent 不应反复调用相同读取工具。对于越权 Tool、跨 Domain Tool、应该经过 HIL 却直接执行等行为，则作为硬约束处理，而不是通过语义评分判断。

## Agent Trajectory

Agent Trajectory 评估关注从输入到最终结果之间的可观察行为序列。系统不记录也不评估模型内部 Chain-of-Thought，只检查实际发生的 Retrieval、Tool、DomainTask、HIL 和最终响应等动作。

一个 Eval Case 可以声明关键行为约束：

```text
required_actions       # 必须发生的关键动作
forbidden_actions      # 禁止发生的动作
ordering_constraints   # 动作顺序约束，如读取当前版本必须发生在写入之前
recovery_rules         # 失败后的恢复要求，如 CONFLICT 后重新获取状态再重新规划
```

例如修改 Current Workout Plan 时，可以要求读取当前版本必须发生在写入之前；Tool 返回 `CONFLICT` 后，必须重新获取 Current State，再重新规划，而不能使用旧版本参数重复调用。评估不要求 Agent 严格按照唯一 A→B→C 的固定轨迹执行，只约束真正影响正确性的关键动作、前置条件和恢复行为。

## Final Task

最终任务层评估用户请求是否真正完成。对于存在明确业务结果的任务，优先使用确定性检查。例如用户要求保存训练记录，可以直接验证业务数据库中对应记录是否产生；Agent 声称“计划已经更新”时，可以检查 Tool Effect 是否确实表明修改成功。

对于 Workout Plan、Nutrition Plan 等没有唯一正确文本的开放式任务，则使用 Rubric 进行语义质量评估。当前 Rubric 主要从任务完成度、约束遵守、事实与 Evidence 一致性、领域合理性以及最终描述与真实业务动作的一致性几个方向进行判断。

## 边界问答

**1. Q：** 为什么不用一个统一总分评价 Agent？

**A：** 总分回答不了「错误首先出现在哪一层」。沿执行链路分四层评估，结合 ContextManifest、RetrievalRecord、ToolInvocation 等结构化事实，才能把问题分别定位到 Retrieval、Evidence 装配、上下文装配、动作选择或最终结果。

**2. Q：** 为什么越权 Tool、跨 Domain Tool、应经 HIL 却直接执行这类行为不进入语义评分？

**A：** 它们是硬约束，出现即违规，直接从结构化事实判定；交给 Rubric 语义评分会把确定性问题变成概率判断（两类问题的完整分工见 [[9.Rubric 与 LLM-as-Judge]]）。

**3. Q：** 为什么 Trajectory 评估不要求 Agent 按唯一固定轨迹执行？

**A：** 评估只约束真正影响正确性的关键动作、前置条件和恢复行为，不要求严格按照唯一 A→B→C 的固定轨迹执行；Agent 保留合理的自主规划空间，过程本身仍然可以对照 Harness 规则判断。

**4. Q：** 为什么不评估模型内部的 Chain-of-Thought？

**A：** 系统不记录也不评估模型内部推理过程，只检查实际发生的 Retrieval、Tool、DomainTask、HIL 和最终响应等可观察行为。
