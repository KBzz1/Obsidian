# 困难以及应对办法

这次演化只围绕一个问题展开：早期测试只建立了「用户输入 → 最终输出」的评价关系，导致不同类型的问题在最终回答上都表现为同一个「回答错误」。

## 旧设计：测试主要围绕最终回答展开

早期版本的测试方式主要围绕最终回答展开。对于普通问答，这种方法成本低，也比较直观：给定一组用户输入，运行 Agent 后检查最终回答是否满足预期；对于没有唯一标准答案的 Workout Plan 或 Nutrition Plan，则通过简单人工检查或单一 Rubric 判断输出质量。Tool 层和 Retrieval 层虽然各自存在运行日志，但这些信息主要用于单次调试，并没有被统一组织成可以参与评估的执行事实。

## 困难：最终回答无法反映一次 Agent Task 的真实质量

这种方式在任务路径较短时能够工作，但随着系统逐渐加入 Retrieval、Context Assembler、Domain Agent、Tool Runtime、HIL 和状态恢复，最终回答开始无法准确反映一次 Agent Task 的真实质量。同一个错误结果背后可能对应完全不同的问题：Retriever 根本没有找到正确资料，Evidence 已经找到但没有进入本轮 Context，Agent 已经看到了正确 Evidence 却选择了错误 Tool，也可能 Tool 已经正确执行，但 Agent 在最终回复中错误描述了业务结果。只看最终答案时，这些问题最终都会表现为同一个「回答错误」。

这一问题在 Agent Harness 中尤其明显，因为系统输出不再只是文本。Agent 在执行过程中会主动检索信息、调用 Tool、修改业务状态、创建子任务以及请求 HIL。即使最终文本看起来合理，中间过程也可能已经产生错误的真实动作。例如 Agent 可以在使用了过期 Current Plan Version 的情况下反复调用修改工具，最终又生成一段看起来正常的回复；如果评估系统只判断最后一段文本，就无法发现 Tool Conflict 后没有重新获取状态这一真正的问题。

最初尝试继续补充最终结果测试也无法彻底解决这一困难。为每种失败情况增加更多 Final Answer Rubric，只能告诉系统「结果哪里不好」，仍然无法确定错误首先出现在哪一层。与此同时，如果直接把完整 Prompt、Tool Log 和所有执行日志全部交给一个 LLM-as-Judge，又会引入新的问题：输入越来越大，Judge 需要自行理解不同 Runtime 的内部语义，很多本可以确定性判断的错误也变成了概率评分，评估结果难以解释和稳定复现。

## Harness 层根因：缺少执行事实与评估对象的对应关系

问题的根因在于，早期测试只建立了「用户输入 → 最终输出」的评价关系，却没有建立 Agent 执行过程中的可观察事实与评估对象之间的对应关系。对于 Agent Harness，真正需要验证的不只是最后生成了什么，还包括模型当时看到了什么、系统检索到了什么、Agent 选择了什么动作，以及动作最终产生了什么真实 Effect。如果这些中间事实没有结构化保存和关联，最终评估就只能把不同类型的问题混在一起。

## 改造：先补齐统一执行轨迹，再分层评估

因此后续改造首先没有增加更多 Judge，而是补齐统一的执行轨迹。Task Runtime 区分稳定的 `task_id` 和一次连续执行的 `run_id`（Run 的身份语义见 [[4.Conversation 与 Task 生命周期#任务与 Run]]），每个 Run 建立独立 Trace；Context Assembler 生成 ContextManifest（见 [[3.上下文装配器与 ContextPolicy#上下文清单（ContextManifest）]]），记录本轮模型真正看到的 Agent Status、Evidence、Tool Result、Artifact 和可见能力；Retrieval Runtime 通过 RetrievalRecord 保存候选召回结果与最终 EvidenceBundle 的关联（见 [[8.证据检索#检索记录（RetrievalRecord）]]）；Tool 层继续复用第四章已有的 ToolInvocation 和 ExecutionRecord（执行记录是尝试级，见 [[7.Tool Result 与错误协议#执行记录与工具结果分离]]），记录真正执行的动作与业务 Effect。本章不重新保存这些事实，而是通过统一身份把各 Runtime 已经产生的数据串成完整执行轨迹（见 [[3.Task、Run 与 Trace 身份关联]]）；支撑生产治理的轻量运行指标仍然归第六章（见 [[8.轻量运行监控]]），本章的观测数据只服务于排障、执行分析与评估。

在能够还原执行事实后，评估体系从单一最终结果判断改成分层评估。上下文与 Evidence 层判断正确资料是否被召回、装配并真正进入模型上下文；Tool 与 Action 层判断 Agent 是否选择了正确 Tool、参数是否正确以及是否发生禁止动作；Trajectory 层检查关键前置动作、执行顺序和失败恢复行为；最终任务层再判断用户请求是否真正完成，以及开放式结果的领域质量是否达到要求（四层评估见 [[8.Agent 分层评估]]）。能够通过结构化事实确定的问题优先使用确定性检查，只有训练计划整体合理性、多重软约束权衡等无法直接编码的语义问题才进入 Rubric 和 LLM-as-Judge。

评估数据的组织方式也随之发生变化。生产 Trace 不再直接被当成测试用例，而是作为发现问题和还原事实的来源。具有代表性的失败任务经过脱敏后，将任务起始状态冻结成不可变 Fixture，并补充 Expected Evidence、关键行为约束、最终结果要求或 Rubric，形成可以跨版本重复执行的 Eval Case。这样一次生产问题在被修复以后不会只停留在一次调试记录中，而能够进入 Regression Dataset，在后续修改 Prompt、Context Assembler、Retrieval、Tool Schema 或 Workflow 时重新验证。

## 最终形成的评估流程

最终形成的评估流程从：

```text
旧设计

User Input
    ↓
Agent
    ↓
Final Answer
    ↓
人工检查 / 单一 Rubric
```

演化为：

```text
当前设计

Agent Task
    ↓
结构化执行事实
    ↓
统一执行轨迹
    ↓
Eval Case / 固定 Fixture
    ↓
上下文与 Evidence 评估
    ↓
Tool / Action 评估
    ↓
Trajectory 评估
    ↓
Final Task 评估
    ↓
Regression Comparison
```

## 改造代价

这套方法增加了 `run_id`、ContextManifest、RetrievalRecord、Eval Fixture 和分层 Evaluator 等额外结构，评估系统也比早期直接检查最终回答复杂。但新增的数据都对应明确的问题定位需求，并没有为了评估重新复制 Task State、Tool ExecutionRecord 或 Business Facts。完整生产数据也不会全部永久保存或全部交给 Judge，而是由各 Runtime 保存自己的真实事实，本章只负责关联、筛选和评价。

## 边界问答

**1. Q：** 为什么继续补充最终结果测试解决不了问题？

**A：** 为每种失败情况增加更多 Final Answer Rubric，只能告诉系统「结果哪里不好」，仍然无法确定错误首先出现在哪一层。直接把完整 Prompt、Tool Log 和所有执行日志全部交给 LLM-as-Judge 又会引入新问题：Judge 需要自行理解不同 Runtime 的内部语义，很多本可以确定性判断的错误变成概率评分，结果难以解释和稳定复现。

**2. Q：** 为什么生产 Trace 不能直接当成 Eval Case？

**A：** 生产 Trace 记录当时发生了什么，而 Eval Case 必须定义在固定输入条件下系统应该做什么。二者之间必须经过筛选、脱敏、状态冻结和 Ground Truth 补充，生产数据才能进入 Regression Dataset。

**3. Q：** 这次改造的最终目标是不是更准确的 Agent 总分？

**A：** 不是。它让一次评估失败能够进一步回答：问题首先出现在 Retrieval、Context Assembly、Agent Action、Tool Execution 还是最终任务结果。对于包含 Retrieval、Tool、HIL 和多 Agent 协作的 Harness，这种可定位、可复现的分层评估比单纯提高最终回答评分更重要，也是后续 Regression 和生产质量反馈能够成立的基础。
