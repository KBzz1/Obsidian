# Regression 与质量反馈闭环

Regression 不使用一个统一总分作为发布判断，而是将评估结果分成三类。

第一类是硬门槛，例如 Forbidden Tool Call、HIL Bypass、跨 Domain 越权、关键业务状态错误以及 Tool Effect 与最终声明明显不一致。这类行为出现后直接视为 Regression Failure，不允许用其他指标上的提升抵消。

第二类是质量指标，例如 Recall@K、Tool Selection Accuracy、Trajectory Pass Rate、Task Completion 和 Constraint Compliance。Candidate Version 与当前稳定 Baseline 使用相同 Dataset 运行，根据已有基线和实际数据逐步设置允许波动范围，而不是在没有数据的情况下提前制定虚假的精确阈值。

第三类是效率指标，包括任务耗时、模型调用次数、Tool 调用次数和 Token Usage。这些数字来自执行记录与 Trace 的统计，不为此建立独立的指标系统。它们通常不直接决定质量 Pass 或 Fail，而用于判断一次质量提升是否付出了过高运行成本。

因此一次 Regression Result 可以有：

```text
PASS
→ 无硬门槛失败，关键质量指标没有明显退化

FAIL
→ 存在硬门槛违规或关键质量明显下降

REVIEW
→ 质量提升但资源成本明显增加，需要人工判断 Trade-off
```

## Evaluation Run 与版本记录

回归比较依赖可追溯的评估运行记录：不同时间得到的 Eval Score，只有追溯到同一组配置时才有可比性。每次完整评估都会形成独立的 Evaluation Run，并记录当时对应的系统配置：

```text
EvalRun

eval_run_id               # 本次评估运行的唯一身份
dataset_version           # 使用的 Dataset 版本

app_version               # 被评估系统的应用版本
prompt_version            # Prompt 版本
workflow_version          # Workflow 编排版本
retrieval_config_version  # 检索配置版本
tool_schema_version       # 工具 Schema 版本

model_config              # 被评估系统的模型配置

judge_model               # Judge 使用的模型
judge_prompt_version      # Judge Prompt 版本
rubric_version            # Rubric 版本

results                   # 本次评估结果
```

当前系统不要求所有组件都建设复杂的独立版本管理服务，但至少需要保证一次评估结果能够追溯到对应的 Prompt、Workflow、Retrieval 和 Tool Schema 配置，否则不同时间的 Eval Score 无法可靠比较。

## 不同开发阶段的评估策略

开发阶段不需要每次修改都运行完整 Dataset。Prompt、Context Assembler、Tool Schema 或 Retrieval 调整时，可以先运行少量核心 Case 和当前正在修复的失败 Case，以快速确认改动方向。

准备进入稳定版本前，再运行核心能力集、边界故障集和生产回归集，完成 Retrieval、Tool、Trajectory、Final Task 以及必要的 LLM-as-Judge 评估，并与当前 Baseline 进行 Regression Comparison。

生产环境不默认给每一个真实用户 Task 再额外调用一次 LLM-as-Judge。线上主要通过前述运行观测、关键错误和用户反馈发现问题，只有具有代表性的 Case 才经过脱敏和固定化处理进入 Eval Dataset。系统性的 Judge 和 Regression 主要在线下执行，从而避免在线评估增加不必要的延迟和成本。

## 质量反馈闭环

最终，第七章形成的是一个从生产运行回到离线验证的持续反馈过程：

```text
Production Runtime
    ↓
结构化运行事实与 Trace
    ↓
发现异常行为或用户反馈
    ↓
定位 Retrieval / Context / Tool / Trajectory / Final Result
    ↓
脱敏并构造 Eval Case
    ↓
加入 Regression Dataset
    ↓
修改 Prompt / RAG / Tool / Workflow / Agent Policy
    ↓
运行分层 Evaluation
    ↓
与 Baseline 比较
    ↓
Regression Pass
    ↓
进入下一版本
```

这套设计使评估不再只检查最终文本，而是覆盖 Agent 执行过程中真正具有工程意义的决策边界；其中确定性规则负责可以明确判断的行为，LLM-as-Judge 只补充开放式语义评价，在可解释性、成本和评估覆盖度之间保持平衡。

## 边界问答

**1. Q：** 为什么发布判断不用统一总分？

**A：** 硬门槛违规不能被其他指标的提升抵消，出现即 Regression Failure；质量指标与 Baseline 比较，波动范围根据已有基线和实际数据逐步设置；效率指标不直接决定 Pass / Fail。三类结果分开，才能表达「质量提升但运行成本明显增加」这种需要人工 Trade-off 的 REVIEW 情况。

**2. Q：** 为什么生产环境不默认对每个真实任务跑 LLM-as-Judge？

**A：** 在线评估会增加不必要的延迟和成本。线上靠运行观测、关键错误和用户反馈发现问题，系统性的 Judge 和 Regression 在线下执行。

**3. Q：** 为什么每次评估都要记录 Evaluation Run 的版本配置？

**A：** 不同时间得到的 Eval Score，只有追溯到同一组 Prompt、Workflow、Retrieval、Tool Schema 和 Judge 配置时才可比；缺少这些记录，Regression Comparison 就失去了比较基准。
