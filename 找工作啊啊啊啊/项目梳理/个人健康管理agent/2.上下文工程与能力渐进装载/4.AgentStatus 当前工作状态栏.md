# 当前工作状态栏

## 状态栏是什么

当前工作状态栏（AgentStatus）是每次模型调用前，从结构化状态、工具返回结果和任务产物中确定性投影出来的进度视图，告诉模型当前任务进展到哪一步、本轮要完成什么、动作边界在哪里。它在每轮调用前重新生成，置于模型上下文靠后的位置。

## 为什么动态替换而不是追加

早期常见的做法是把状态视图持续追加（append-only）到历史轨迹。实际工程里任务流转的轮次并不多，但单次状态栏的信息密度高，持续追加会让上下文堆积大量冗余且已失效的中间状态快照，所以采用动态替换：每轮重新生成，替换上一份。

代价是状态栏之后的内容每轮都变，这一段的前缀缓存无法复用。对策是把状态栏后置：前部系统提示词、固有能力描述和长期不变轨迹保持稳定，缓存损失只发生在状态栏之后的一小段（缓存机制见 [[7.KV Cache 与上下文布局]]）。

## 示例：状态栏每轮重新生成，而不是不断追加

以「修改训练计划」任务为例，同一份状态栏在三轮调用中分别生成：

第一次调用：

```yaml
当前工作状态:
  phase: plan_revision
  current_step: search_replacement
  plan_version: 2
```

搜索完成后：

```yaml
当前工作状态:
  phase: plan_revision
  current_step: evaluate_replacement
  plan_version: 2
  candidate_count: 2
```

草稿保存后：

```yaml
当前工作状态:
  phase: awaiting_confirmation
  current_step: wait_for_confirmation
  plan_version: 3
  disabled_capabilities:
    - publish_plan：用户尚未确认
```

这三段状态栏不会全部追加进消息历史。每一轮都根据最新状态重新生成、替换上一份；历史状态变化保存在 Checkpoint、Trace 或 Event Store 中，模型上下文只保留当前状态。

## 四个数据区块

状态栏由四个区块构成。

**当前执行议程**：告知模型本轮为什么被触发、当前处在执行流程的哪个位置。执行议程由系统运行时（Harness）基于结构化状态计算派生，不是大模型自己生成的执行计划（Plan）：它决定模型当前处理的目标与退出条件，模型不能通过它反向控制状态图的流转。

```python
execution_agenda = {
    "goal": "完成今日训练计划修改",        # 本轮总目标
    "phase": "plan_revision",              # 当前所处阶段
    "current_action": "替换第二个训练动作",  # 当前正在执行的动作
    "pending_actions": [                   # 剩余待处理事项
        "检查修改后的训练量",
        "生成新草稿",
        "等待用户确认",
    ],
    "completion_condition": "用户确认最终训练计划",  # 本轮退出条件
}
```

**事件侧信道**：透传那些不宜伪装成自然语言对话、但直接影响本轮决策的运行时事件——工具执行完毕信号、人工介入（HIL，见 [[6.HIL 与恢复]]）流程中的拒绝操作、上游验证器的阻断反馈、外部服务的降级状态。侧信道数据只来自系统运行时和工具环境的确定性产出，模型自身的猜测推断不允许写入该通道。

**当前环境状态**：执行当前动作需要的业务语境——所处的业务领域、正在操作的任务产物版本号、任务挂起状态、依赖的时间戳或环境探针数据。这个区块保持极简，只滤入对本轮决策有实质影响的环境信息。

**当前能力状态**：定义当前执行周期内的动作边界。它区别于全局静态的工具列表（Tool Schema）：只声明当前阶段被激活或被限制的能力。例如草稿待确认阶段，修改和重新评估类能力可用，最终方案的发布接口被系统级屏蔽。

## 状态栏整体视图

```text
当前工作状态

当前执行议程
- 当前目标
- 当前阶段
- 当前动作
- 待处理事项
- 完成条件

事件侧信道
- 最近影响当前决策的运行时 / 工具 / HIL 事件

当前环境状态
- 当前业务状态
- 当前任务产物版本
- 必要运行环境

当前能力状态
- 本轮允许的能力
- 暂时不可执行的能力
```

状态栏机制的核心是建立 `状态 → 模型` 的精选工作视图：从全局状态里只挑出经评估切实影响本轮模型决策意图的信息投影进来。执行议程与「业务域计划」「执行计划」的区分见 [[9.Planner 按需规划#三类计划]]。

## 边界问答

**1. Q：** 为什么状态栏由运行时生成，而不是让模型自己总结进度？
**A：** 模型总结是对历史的概率性推测，中断恢复以后可能偏离真实状态；状态栏来自结构化状态的确定性投影，是系统权威坐标。让模型自己总结，等于把任务阶段定位重新交给推测（演化过程见 [[找工作啊啊啊啊/项目梳理/个人健康管理agent/2.上下文工程与能力渐进装载/10.困难以及应对办法]]）。

**2. Q：** 动态替换状态栏会破坏缓存，为什么不改用追加？
**A：** 追加会让失效的中间状态快照在上下文里越积越多。替换只影响状态栏之后的一小段前缀缓存；状态栏后置以后，前部稳定部分的缓存仍然复用。

**3. Q：** 事件侧信道为什么不允许写入模型推断？
**A：** 侧信道只透传系统运行时和工具环境的确定性产出，模型推断不在其列。写入推断会让事件失去确定来源，把猜测伪装成系统事实。
