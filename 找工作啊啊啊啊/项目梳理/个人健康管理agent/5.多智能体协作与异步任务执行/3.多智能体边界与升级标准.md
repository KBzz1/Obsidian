# 多智能体边界与升级标准

## 模块定位

**多智能体模块解决的是：一个任务需要多个专业能力参与时，系统如何确定任务所有者、如何拆分和委派子任务、智能体之间传递什么信息、哪些任务可以并行、哪些存在前后依赖，以及长任务如何从当前会话解耦并重新接回主任务。**

这一层不负责定义完整的任务生命周期和检查点（Checkpoint）恢复机制（第一章）；不负责决定每次模型调用装配哪些记忆（Memory）、检索增强证据（RAG Evidence）和历史消息（第二、三章）；也不把智能体的工具调用直接视为可执行操作，参数验证、权限、幂等、审批和工具安全护栏（Tool Guardrail）仍由第四章工具运行时（Runtime）负责。第五章只定义这些能力在多智能体协作中的接口和调用关系。

## 为什么不默认拆成多个 Agent

系统不因为任务复杂就默认拆成多个智能体。LangChain 当前的多智能体（Multi-Agent）指南同样指出，复杂任务并不天然要求多智能体，单智能体配合合适的提示词（Prompt）和工具很多时候已经能完成任务。多智能体（Multi-Agent）真正有价值的场景集中在四处：**专业上下文隔离**、**独立能力边界**、**并行执行**，以及**单智能体工具面（Tool Surface）过大后选择质量下降**。

因此本系统的总体原则是：

> 默认由一个会话级主管（Supervisor）完成任务；只有当某项能力形成独立的数据所有权、工具集合、业务工作流或大规模专业上下文时，才提升为独立领域智能体（Domain Agent）。

## 按能力所有权划分，不按话题划分

系统不按照「训练是一个话题、饮食是一个话题」划分智能体。话题分类只能说明两个问题语义不同，不能说明它们需要两个独立执行单元。

领域智能体（Domain Agent）的拆分以能力所有权（Capability Ownership）和业务所有权（Business Ownership）为依据。判断一项能力是否值得成为智能体，观察五个维度：

| 判断维度 | 含义 |
| --- | --- |
| 业务事实所有权 | 是否拥有一组明确且相对独立的正式业务状态，并负责对这些状态做决策 |
| 工具面（Tool Surface） | 是否拥有一组其他能力不应长期看到或调用的领域工具 |
| 工作流所有权（Workflow Ownership） | 是否存在独立、复杂且可以沉淀的领域 SOP |
| 上下文边界（Context Boundary） | 是否需要较大的专业提示词（Prompt）、知识、历史结果或工作上下文 |
| 独立执行价值 | 是否存在并行执行、独立失败、独立恢复或独立演化的价值 |

如果一个能力只是拥有几个 CRUD 工具，或者只是在提示词（Prompt）中扮演一个不同角色，而没有形成上述边界，就不单独建立智能体。

## Workout 与 Diet 的边界

基于当前业务，训练与饮食已经形成比较自然的领域边界。

训练智能体（Workout Agent）负责训练领域事实和能力：训练记录、训练会话（Session）、训练计划、训练量、动作表现，以及训练计划相关的工作流。饮食智能体（Diet Agent）负责饮食领域事实和能力：饮食记录（Meal Log）、营养摄入、宏量营养素、营养计划（Nutrition Plan），以及饮食规划工作流。

两者可以存在业务关联，但不共享同一份业务事实的修改权。例如饮食智能体（Diet Agent）可以读取训练负荷作为营养调整依据，却不能直接修改训练计划（Workout Plan）；训练智能体（Workout Agent）可以指出当前训练计划对能量摄入存在要求，却不能直接修改营养计划（Nutrition Plan）。这种边界允许领域之间协作，同时避免多个智能体对同一状态拥有模糊的写权限。

## Habit 为什么不是独立 Agent

习惯（Habit）当前不作为独立领域智能体（Domain Agent）。它目前主要承担创建习惯、每日打卡、查看状态等明确操作，更适合作为一个轻量业务能力（Capability）暴露给会话主管（Supervisor）。只有当产品发展为长期行为干预系统，习惯（Habit）开始拥有行为计划、依从性分析、动态目标调整、长期干预工作流（Intervention Workflow）等独立业务状态和复杂决策过程时，才有必要提升为领域智能体（Domain Agent）。

因此智能体数量不是预先固定的，能力沿着以下抽象层级演化：

```text
普通 Tool
   ↓
Skill / Workflow
   ↓
Domain Agent
```

是否升级取决于业务复杂度和上下文边界，而不是为了维持一个固定的多智能体（Multi-Agent）拓扑。

## 边界问答

**1. Q：** 复杂任务为什么不天然拆成多个智能体？

**A：** 复杂任务很多时候单智能体配合合适的提示词（Prompt）和工具已经能完成。多智能体（Multi-Agent）只在专业上下文隔离、独立能力边界、并行执行、单智能体工具面（Tool Surface）过大导致选择质量下降这几类场景才真正有价值，不为复杂而拆。

**2. Q：** 为什么不按「训练 / 饮食」话题划分智能体？

**A：** 话题只说明两个问题语义不同，不说明它们需要两个独立执行单元。判断标准是能力所有权和业务所有权：是否拥有独立的业务状态、工具面（Tool Surface）、工作流、上下文边界和执行价值。

**3. Q：** 饮食智能体（Diet Agent）能读训练负荷，为什么不直接改训练计划（Workout Plan）？

**A：** 读取训练负荷作为营养调整依据是业务关联；修改训练计划（Workout Plan）是越过领域所有权。两个智能体不共享同一份业务事实的修改权，避免对同一状态产生模糊的写权限。

**4. Q：** 习惯（Habit）现在有工具，为什么还不算智能体？

**A：** 它目前只有创建习惯、打卡、查状态等明确操作，没有形成独立业务状态和复杂决策。只有当它拥有行为计划、依从性分析、长期干预（Intervention）等独立状态和决策过程时，才需要提升为领域智能体（Domain Agent）。

**5. Q：** 智能体数量是预先定好的吗？

**A：** 不是。能力沿工具（Tool）→ 技能/工作流（Skill/Workflow）→ 领域智能体（Domain Agent）演化，是否升级取决于业务复杂度和上下文边界，不为固定拓扑而拆。
