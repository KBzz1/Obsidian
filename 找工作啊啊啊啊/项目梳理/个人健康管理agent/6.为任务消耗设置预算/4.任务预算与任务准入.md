# 任务预算与任务准入

智能体任务（Agent Task）的执行长度具有不确定性。简单任务可能一次模型调用即可结束，复杂任务可能在模型推理、知识检索和工具调用之间循环多轮。如果完全依赖模型自行决定何时停止，一个异常的推理-行动循环（ReAct，见 [[5.Domain Agent 执行模型]]）就可能持续消耗模型调用和外部服务资源。因此每个任务在创建时都绑定一份任务预算（Task Budget），由运行时对任务能够进行的自主执行范围设置硬限制；同时执行轻量任务准入，防止异常创建大量任务，或在系统过载时无限接收工作。

## 三个预算维度

当前任务预算主要控制三个维度：逻辑模型调用次数、逻辑工具调用次数和有效执行时间。这里统计的是智能体层面的逻辑动作，而不是底层网络尝试次数。例如智能体发起一次 `replace_workout_plan`，任务预算中的工具调用额度消耗一次；如果工具运行时因临时网络异常在同一次工具调用内部进行了两次执行尝试，仍然只算一次逻辑工具调用。工具内部的超时和重试上限继续由第四章的工具运行时策略管理（见 [[6.可靠执行]]）。这样保持「任务整体资源预算」和「单次调用可靠性策略」的语义分离。

## 预算结构

任务预算属于任务运行时的控制状态，而不是业务数据，也不是由智能体自己维护的上下文。其结构可以表示为：

```text
TaskRuntimeState                     # Task 运行状态
├── task_id                          # 任务唯一标识
├── lifecycle_status                 # 生命周期状态（推进 / 等待 / 恢复等）
├── checkpoint_ref                   # 检查点引用，中断后据此恢复
└── budget                           # 任务预算，属于运行时控制状态
     ├── limits                      # 预算上限（硬限制）
     │    ├── max_llm_calls          # 逻辑模型调用次数上限
     │    ├── max_tool_invocations   # 逻辑工具调用次数上限
     │    └── max_active_runtime     # 有效执行时间上限
     ├── usage                       # 已使用额度
     │    ├── used_llm_calls         # 已使用模型调用次数
     │    ├── used_tool_invocations  # 已使用工具调用次数
     │    └── active_runtime         # 已使用有效执行时间
     └── status                      # 预算状态
          ├── NORMAL                 # 正常
          ├── LOW                    # 偏低，提示智能体收敛探索
          └── EXHAUSTED              # 耗尽，运行时拒绝对应调用
```

由于任务支持中断和恢复，预算使用量必须和任务的运行状态一起持久化。一个已经使用大部分预算的任务在恢复后继续使用原来的剩余额度，而不能因为重新加载检查点（Checkpoint）就重新获得完整预算。有效执行时间只统计任务实际占用执行资源的时间；排队等待、人工介入（HIL）等待以及其他不占执行资源的暂停时间不直接消耗有效执行时间预算。

## 预算数值由运行时策略决定

具体预算数值由运行时策略（Runtime Policy）决定，而不是由语言模型直接填写。会话主管（Supervisor）或协作调用可以描述任务类型和复杂度，例如普通领域任务、复杂计划任务或后台任务；Harness 根据这些确定性字段映射到预先配置的预算策略。调用子智能体时，会话主管可以提交 `task_type`、`difficulty`、目标和约束，但不会直接传入 `max_llm_calls=20` 之类的执行额度。这样模型可以表达任务复杂度，真正的资源权限仍然掌握在运行时中。

## 预算投影进入智能体上下文

任务预算同时会生成一个面向智能体的简化投影，并通过第二章的智能体状态（Agent Status）进入模型上下文（见 [[4.AgentStatus 当前工作状态栏]]）。例如模型可以看到剩余模型调用次数、剩余工具调用次数以及当前预算状态。当预算已经较低时，智能体可以主动减少新的探索行为，优先利用已经获得的证据和工具结果完成当前任务。不过这个状态只用于指导决策，真正的限制仍然由运行时强制执行；当任一硬预算耗尽后，运行时不再接受对应的自主调用。

## 任务准入

除了限制单个任务，系统在任务创建时还执行轻量的任务准入。当前项目并不面向大规模高并发流量，因此没有单独建设复杂的准入服务（Admission Service）。准入主要检查当前用户是否已经存在过多正在运行的任务，以及系统任务队列是否已经达到容量上限。它的作用是防止单个用户异常创建大量任务，或者在系统已经无法及时消费任务时仍然无限接收新的工作。

## 边界问答

**1. Q：** 为什么统计逻辑调用次数而不是底层网络尝试次数？

**A：** 为了保持「任务整体资源预算」和「单次调用可靠性策略」的语义分离。智能体发起一次工具调用，工具调用额度消耗一次；同一次工具调用内部因临时网络异常进行的多次执行尝试仍算一次逻辑调用，其内部的超时和重试上限由第四章工具运行时策略管理。

**2. Q：** 为什么预算数值不由模型直接填写？

**A：** 模型只描述任务类型（`task_type`）和复杂度（`difficulty`），Harness 再映射到预算策略。这样模型可以表达任务复杂度，但真正的资源权限掌握在运行时中，避免模型自己抬高执行额度。

**3. Q：** 预算使用量为什么要随运行状态持久化？

**A：** 任务支持中断和恢复。已使用大部分预算的任务恢复后应继续用剩余额度，不能因为重新加载检查点就重新获得完整预算。

**4. Q：** 为什么有效执行时间不统计排队和人工介入等待？

**A：** 有效执行时间预算只统计任务实际占用执行资源的时间。排队等待、人工介入等待以及其他不占执行资源的暂停时间不应消耗预算，否则等待本身会被误算成资源消耗。

**5. Q：** 为什么不建设复杂的准入服务？

**A：** 当前项目不面向大规模高并发流量，准入只需防止单个用户异常创建大量任务、以及在系统无法及时消费任务时无限接收新工作，检查「用户运行中任务数」和「队列容量」即可。
