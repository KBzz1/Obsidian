# 代码级逻辑：一个 Task 如何被预算与调度治理

本篇回答一个问题：一个逻辑任务从创建到终态，整个生命周期最多允许消耗多少资源；多个任务同时存在时，谁能运行、谁等待、什么时候被拒绝继续执行。一个任务可能跨越：R1 的多次模型调用、工具调用、训练与饮食两个领域的领域任务、人工介入（HIL）暂停、R2 恢复、后台执行，以及后台里更多的模型与工具调用。因此 HTTP 请求的数量不等于任务的实际资源消耗——治理基本单位是任务，不是请求。

走查沿用两条已冻结的链：跨领域主例用 T200（第五章冻结身份，配 DT10 / DT20 / 后台执行记录 AE500），HIL 与恢复段用 T100（第一章冻结身份，配调用实例 I300 与 R1 / R2）。预算机制不区分任务类型，两者走同一条链；工具调用实例、执行尝试等既有身份的语义不在这里重新定义。

## 统一主链

一个新任务从到达到终态，全部治理动作都发生在这条链上，后续各节逐段展开：

```text
新 Task 请求
    ↓
BudgetPolicyResolver          # 预算策略解析：task_type / difficulty / execution_mode → 预算策略
    ↓
AdmissionController           # 准入检查：用户活跃任务数 / 队列压力 / 背压档位
    ↓ 通过
创建 T200 + TaskBudget + R1   # 任务、预算、首段执行一起登记
    ↓
生成 SchedulingItem → 入队    # 调度项：等待一次执行机会
    ↓
Queue / Scheduler             # 进程内队列 + 调度器，分发执行槽位
    ↓
Task Execution Slot           # 取得任务执行槽位（任务执行信号量放行）
    ↓
ExecutionSlice 开始计时       # 执行切片：任务实际占用执行资源的时段
    ↓
Agent Runtime
    ├─ LLM 逻辑调用（LC）
    │     BudgetManager.consume_once → Circuit.allow → LLM Semaphore → Model API
    └─ ToolInvocation（I）
          BudgetManager.consume_once → Circuit.allow → Tool Semaphore → Tool Runtime
    ↓
ExecutionSlice 结束 → 结算 active_runtime → 累计进 TaskBudget
    ↓（执行到人工介入）
释放 Slot → WAITING_HUMAN     # 等待期间不占槽位、不计时
    ↓（用户确认）
Resume：登记 R2 → 重新 Scheduling → 重新取槽
    ↓
COMPLETED / FAILED（failure_code = BUDGET_EXHAUSTED）
```

## 四个身份：AgentTask、Run、SchedulingItem、Resource Call

治理链上有四个容易被混为一谈的身份，先把它们拆开。**AgentTask** 是逻辑任务（T100 / T200），预算绑定在它身上。**Run**（R1 / R2）是任务的连续执行阶段：R1 执行到中断点，R2 从恢复开始——执行段换了，任务没换，所以预算也不能换。**资源调用（Resource Call）** 是任务执行过程中发生的逻辑模型调用（logical call，下文用 LC 标识）与工具调用实例（I300 一类），是预算的实际消耗者。**调度项（SchedulingItem）** 是新出现身份：它表示「某个已有 Task / Run 当前等待一次执行机会」这个短暂事实，由调度器在任务入队时创建、取得槽位后消费：

```python
class SchedulingItem:
    scheduling_id: str   # 调度项身份，如 SI100；调度器内部引用它
    task_id: str         # 属于哪个任务，如 T100；预算与控制状态都按它归属
    run_id: str          # 等待执行的是哪段 Run，如 R1；同一 Run 同时最多一个调度项
    trigger: str         # 为何进入调度：create / resume / background / recovery
    priority: str        # interactive / background，决定调度器先给谁槽位
    enqueued_at: datetime  # 入队时间，队列等待时间指标从这里起算
```

T100 / R1 对应调度项 SI100；用户确认后 T100 / R2 对应 SI101。调度项不是新的任务：它没有业务目标、没有检查点、没有预算，被拿掉再重建都不影响任务本身——调度器崩溃时丢掉的只有调度项（见后文 Queue 重建）。它的 `run_id` 字段也说明了一件事：调度项挂在 Run 上，不是挂在任务上，一个任务的每段执行各自排队。

## TaskBudget：预算的最终结构

任务预算（TaskBudget）是本章的中心数据结构，属于任务运行时的控制状态，不是业务数据，也不是模型自己维护的计数器。结构与 [[4.任务预算与任务准入]] 中 `TaskRuntimeState.budget` 子树一致，代码级补齐 `task_id`、`policy_id` 与 `version`：

```python
class TaskBudget:
    # —— 归属组 ——
    task_id: str              # 绑定的任务，如 T200；预算只认任务，不认请求或 Run
    policy_id: str            # 由 BudgetPolicyResolver 解析出的策略标识，记录额度来自哪条策略

    # —— 上限组（硬限制）——
    max_llm_calls: int        # 逻辑模型调用次数上限
    max_tool_invocations: int # 逻辑工具调用次数上限
    max_active_runtime: duration  # 有效执行时间上限（口径见 ExecutionSlice 一节）

    # —— 已用组（与任务控制状态一起持久化）——
    used_llm_calls: int       # 已消耗的模型调用次数，跨 Run 累计
    used_tool_invocations: int  # 已消耗的工具调用次数，跨 Run 累计
    used_active_runtime: duration  # 已累计的有效执行时间

    # —— 状态组 ——
    status: str               # NORMAL / LOW / EXHAUSTED；LOW 是提示，EXHAUSTED 是拒绝
    version: int              # 乐观并发版本，原子扣减时做条件更新（同第一章 OCC 思想）
```

三个预算维度与三个 `used_*` 字段一一对应；`status` 由 BudgetManager 在每次扣减后重算。预算使用量随任务控制状态一起持久化：任务中断、恢复、甚至跨进程重启之后，已用额度原样带过来，恢复不等于重新拨款。

## 额度由 BudgetPolicyResolver 决定

预算上限不由模型填写。会话主管（Supervisor）或协作调用可以声明任务类型与复杂度（`task_type`、`difficulty`、`execution_mode`，第五章的委派字段），预算策略解析器（BudgetPolicyResolver）把这些确定性字段映射到预先配置的预算策略：

```python
def resolve_budget_policy(task_type: str, difficulty: str,
                          execution_mode: str) -> BudgetPolicy:
    # task_type：任务类型，如 cross_domain_plan（跨领域计划）/ ordinary_qa（普通问答）
    # difficulty：复杂度描述，同类型内调节额度档位
    # execution_mode：sync / background，影响调度优先级与策略档位
    return POLICY_TABLE.lookup(task_type, difficulty, execution_mode)
    # 策略表是部署配置：ordinary_qa / complex_plan / cross_domain_plan /
    # background_analysis 各有自己的额度档；具体数值不是架构的一部分
```

Supervisor 可以判断「这是一个跨领域计划任务」，但不能直接决定 `max_llm_calls = 100`——具体额度由运行时策略决定，模型表达复杂度，资源权限留在运行时（与第五章「业务决策与状态修改分离」同构）。

## 新 Task 的 Admission 与已有 Task 的 Resume 分开

准入控制器（AdmissionController）是 Harness 内的一个检查步骤，不是独立的准入服务（概念口径见 [[4.任务预算与任务准入]]）。新任务与已有任务的恢复走两条不同的链，这是本章最容易被忽略的边界：

```text
新任务：
TaskCreateRequest
    ↓ BudgetPolicyResolver：解析预算策略
    ↓ AdmissionController：
        ├── 当前用户活跃任务数 < 每用户上限
        ├── 交互队列压力 < 容量
        └── 背压档位允许接收（档位定义见背压一节）
    ↓ 全部通过
创建 T200 + TaskBudget + R1 + SchedulingItem
    ↓ 任一不通过
AdmissionRejected(reason)      # 任务不存在，预算也不存在

已有任务恢复（T100 = WAITING_HUMAN）：
TaskAction                     # 用户确认（第一章结构化入口）
    ↓ 第一章恢复校验链 + 受理事务（OCC 推进、I300 → APPROVED、登记 R2）
    ↓ scheduler.ensure_scheduled(T100, R2)   # 生成 SI101，入队
    ↓ 等待执行槽位 → 取得槽位后继续执行
```

恢复链上没有 AdmissionController：不重新做新任务准入，不重新创建 TaskBudget，不重置 usage。系统再忙，已接受任务的恢复也只是排队等槽（QUEUED），不会被当成新任务拒绝。第一章恢复受理事务的产物（R2 登记行）在本章视角下进入调度；事务成功后的图恢复调用，对应「取得槽位之后的执行段」——第一章描述逻辑恢复流程，本章补上中间的调度一跳。

## 预算扣减由 BudgetManager 强制执行

模型能通过第二章的智能体状态（Agent Status）看到一份预算视图（BudgetView）——剩余模型调用次数、剩余工具调用次数、当前预算状态。这份视图只是决策提示：

```python
class BudgetView:
    # 只读投影，经第二章 AgentStatus 装配链进入模型上下文（见 [[4.AgentStatus 当前工作状态栏]]）
    remaining_llm_calls: int       # 剩余逻辑模型调用次数
    remaining_tool_invocations: int  # 剩余逻辑工具调用次数
    budget_status: str             # NORMAL / LOW / EXHAUSTED
```

真正的执行门槛在预算管理器（BudgetManager）：每一次逻辑调用发生前，运行时调用 `BudgetManager.consume(...)`，失败抛 `BudgetDenied`，真实的 LLM 调用或工具调用不会发生。视图与强制分工明确——模型看到 LOW 可以减少探索、优先收敛，但不能要求运行时增加预算；模型看到的是额度，能改额度的只有运行时。

## consume_once：一次逻辑动作只扣一次

预算扣减必须经得起两类重复：图节点重放（检查点恢复后同一节点可能再执行一次）和调用重试（同一动作的多次执行尝试）。机制是预算扣减记录（BudgetCharge）加幂等键：

```python
class BudgetCharge:
    task_id: str        # 从哪个任务的预算扣的
    resource_type: str  # 资源类型：llm_call / tool_invocation / active_runtime
    operation_id: str   # 逻辑动作的稳定身份：LC300 / I300 / ES10
    amount: int | duration  # 本次扣减量：次数或时长
```

逻辑唯一键是 `task_id + resource_type + operation_id`：同一动作在同一任务上最多产生一条扣减记录，重复扣减请求命中已有记录直接返回。键的稳定性来自前面章节的身份设计：

- **工具侧**：第四章的调用实例就是预算的操作身份。`tool budget operation_id = I300`——同一个 I300 内部的 Attempt 1 / 2 / 3 不重复扣工具预算，重试复用同一条记录。
- **模型侧**：逻辑模型调用 `logical_call_id = LC300` 是本章为 LLM 补上的稳定逻辑身份。底层 API 的网络重试（换连接、按 `Retry-After` 重发）仍属于同一个 LC300，不重复扣。一次逻辑模型决策不等于一次网络尝试。

计费时机的统一口径：**运行时接受一个新的逻辑 LLM 调用或工具调用实例时，就消费一次预算**。I300 在 `prepare_invocation` 被运行时接受的那一刻，工具预算 +1；即使后续执行因依赖故障失败，也不退款。这样定的理由：TaskBudget 限制的是「智能体能自主发起多少逻辑动作」，不只是 API 账单——一次已经发起的动作无论成败，都消耗了任务的自主行动额度。

## 检查与扣减必须原子

剩最后一次模型额度时，两个并行的领域任务（DT10、DT20）同时申请扣减，不能两个都通过——检查「还够不够」和写入「已用 +1」必须是原子操作：

```python
def consume_once(task_id: str, resource_type: str,
                 operation_id: str, amount) -> BudgetCharge:
    if (c := find_charge(task_id, resource_type, operation_id)):
        return c                    # 幂等命中：重放 / 重试不再扣
    atomic:                         # 单事务内完成（示意）：
        budget = load_for_update(task_id)             # ① 锁定预算行（SELECT ... FOR UPDATE 一类）
        check(budget.used + amount <= budget.limit)   # ② 额度检查
        budget.used += amount                         # ③ 扣减
        budget.version += 1                           # ④ 版本自增（条件更新兜底）
        return insert_charge(task_id, resource_type,  # ⑤ 写扣减记录，唯一键防重
                             operation_id, amount)
```

②～⑤ 在同一事务里提交；未来实现用数据库事务加 `version` 条件更新即可，不引入分布式锁——与第三章 SUPERSEDE 条件更新、第五章 `ensure_domain_task` 是同一条约束在不同层的落点。DT10 与 DT20 抢最后一个额度时，事务串行化保证恰好一个成功，另一个得到 `BudgetExceeded`。

## 预算耗尽：谁停止执行

已用次数到达上限后，模型仍然可能发起新的逻辑调用 LC9。此时停止执行的不是模型的自觉，而是运行时：

```text
BudgetManager.consume_once(LC9)
    ↓ 额度检查失败
BudgetExceeded
    ↓ LLM Gateway 不发出真实调用
budget.status = EXHAUSTED
    ↓ 图无法继续推进（必要动作全部被拒）
任务 FAILED，failure_code = BUDGET_EXHAUSTED
    ↓ 已有产物能否作为部分结果返回
沿用第五章 partial_result_policy
```

`LOW` 与 `EXHAUSTED` 的待遇不同：LOW 只是提示——例如 `max_llm_calls = 10`、已用 8 时状态翻为 LOW，视图把剩余额度带给模型，模型可以据此收敛；EXHAUSTED 是拒绝——运行时不再接受对应的自主调用。模型在两种情况下都无法给任务续预算。

## active_runtime 与 ExecutionSlice

有效执行时间（active_runtime）指任务实际占用 Harness 执行资源的累计时间，不包括队列等待、HIL 等待和纯人工等待。计时的载体是执行切片（ExecutionSlice）：

```python
class ExecutionSlice:
    slice_id: str               # 切片身份，如 ES10；结算幂等的操作身份
    task_id: str                # 属于哪个任务
    run_id: str                 # 属于哪段执行；后台切片这里是 AE500 自己的 run_id
    domain_task_id: str | None  # 若本切片在推进某个领域任务，记录它；否则为空
    started_at: datetime        # 取得执行槽位的时刻
    ended_at: datetime | None   # 释放槽位的时刻，进行中为空
```

任务取得执行槽位时开始切片，释放槽位时结束切片，时长结算进 `used_active_runtime`；一个任务在后台领域任务上并行推进时，多个切片各自计时、各自结算，累计值就是真正的资源占用。因此它不是用户体验的墙钟时间——用户离开三小时，任务一分钱预算都没花。

硬限制不能等结算才发现：若只在切片结束后结算，超支总是事后才被告知。因此切片开始时，运行时把剩余时间额度换算成本切片的截止时刻，执行过程中按 Runtime 边界检查：

```text
ExecutionSlice start
    ↓
读取 remaining_active_runtime                    # TaskBudget 中的剩余时间额度
    ↓
slice_deadline = now + remaining_active_runtime  # 本切片允许占用执行资源的截止时刻
    ↓
执行过程中 Runtime 边界检查                       # 下一次逻辑调用发起前等确定性边界
    ↓ 超过 slice_deadline
BudgetExceeded(active_runtime)                   # 不再发起新的逻辑调用，切片终止
```

检查发生在 Runtime 已有的确定性边界（下一次逻辑调用发起前、人工介入中断前），超过截止时刻后第一个边界即拒绝，不为切片引入抢占式计时器。切片仍只在结束时结算一次，结算的是实际用时；截止时刻只作用在执行时间轴上，Queue / HIL 等待不推进它。

切片结算同样要幂等：同一个切片 ES10 不能因崩溃恢复被重复结算。做法与调用扣减一致——`BudgetCharge(resource_type = active_runtime, operation_id = ES10)`，结算前先查记录，每个切片最多结算一次。

## SchedulingItem、Queue 与 Scheduler

队列只回答「哪些任务正在等待」，它不是任务事实源。真实任务状态在持久 Runtime（第一章的控制索引与检查点）；进程内队列只是当前实例的调度索引：

```text
Persistent Task State  = source of truth    # 任务存在与否、执行到哪，看这里
In-memory Queue        = 当前调度索引        # 谁在排队，看这里
```

进程崩溃时队列消失，任务不消失——T100 还在 `WAITING_HUMAN`，已登记的 R2 还是 R2，丢掉的只有 SI101 这个排队事实。进程启动时调度器恢复（Scheduler Recovery）补回排队事实：

```text
进程启动
    ↓
Scheduler Recovery：扫描持久 Runtime 中
    任务未到终态、未停在等待人工介入、
    当前 Run 已受理但尚未执行到终点的 Task / Run
    ↓（已停在 WAITING_HUMAN 的任务不在此列：它们等的是用户，不是槽位）
对每一条执行 ensure_scheduled(task_id, run_id)
    ↓
重新生成 SchedulingItem，队列恢复
```

`ensure_scheduled(task_id, run_id)` 同时负责去重：Resume API 因网络重试被调用两次（`schedule(T100, R2)` 两次），以（`task_id`, `run_id`）为键查询已存在的调度项，存在即复用——不会出现两个并行 SI101。调度侧的排队状态由调度器维护在调度项上，不进入第一章的任务状态机：任务控制索引不因「还在排队」改变状态。

## 两层并发控制：Task Slot 与资源信号量

并发限制分几层，回答不同的问题。第一层任务执行信号量（TaskExecutionSemaphore）限制「同时真正推进多少个 Agent Task / Run」——取得它的任务获得一个执行槽位（Task Slot）。第二层是共享资源的信号量：LLM Semaphore 与 Tool Semaphore 限制任务内部对模型与工具的并发调用——例如模型 API 并发只限制 Harness 同时向外部模型服务发出的请求数，不是模型实例池（口径见 [[5.任务队列、优先级与有限并发]]）；SystemBackgroundSemaphore 单独限制不属于任何 AgentTask 的系统后台 Job（如记忆巩固），它不是任务槽位的另一种叫法。

组合关系：T100 取得任务槽位，不代表它可以无限并发调用 LLM——槽位之内每次调用还要过 LLM / Tool Semaphore。反过来，LLM 信号量有空位也不代表任务可以执行——没有槽位，任务根本没在推进。系统后台 Job 与两者都不同：不占 TaskExecutionSlot、不走 LLM / Tool Semaphore，只在 SystemBackgroundSemaphore 里限并发。

## HIL：等待期间释放槽位

人工介入把槽位还回系统，这是调度与任务生命周期的接缝：

```text
T100 / R1 执行到 wait_for_human
    ↓ 检查点持久化（第一章）
ExecutionSlice ES100 结束 → 结算 active_runtime
    ↓
释放 Task Slot                # 槽位还给调度器
    ↓
T100 → WAITING_HUMAN
```

用户等待的三小时里：不占槽位，`active_runtime` 不增长，队列里其他任务正常拿槽执行。用户确认后走第一章恢复校验与受理事务，登记 R2、`ensure_scheduled` 生成 SI101、重新排队、重新取槽——预算继续累计（R1 的 usage + R2 的 usage），任务还是原来那个任务。

## 后台 DomainTask 与系统后台 Job

第五章的后台执行在本章获得资源形态。AgentTask 之下的后台 DomainTask 与前台任务走同一条调度链，只是排队优先级不同——调度器为它生成后台调度项（`trigger = background`），仍要经过调度器取得任务执行槽位：

```text
DT10 background → AE500 → background SchedulingItem
    ↓
Scheduler → TaskExecutionSlot → ExecutionSlice
    ↓ 切片内的调用
LLM → LLMSemaphore；Tool → ToolSemaphore    # 与前台任务同一套资源信号量
    ↓ 每一次 LC / I
仍消费 parent_task_id = T200 对应的 TaskBudget
```

后台切片的 `task_id` 填 T200、`run_id` 填 AE500 自己的 run_id、`domain_task_id` 填 DT10；消耗从 T200 的预算扣，扣满上限时后台执行同样被拒。后台只是执行方式与排队优先级，不是第二类资源通道。

系统自身的后台工作则是另一类：记忆巩固（Memory Consolidation）这类系统后台 Job 不属于任何用户任务，没有 `task_id`，不占 TaskExecutionSlot，也不涉及 TaskBudget——它使用独立的 SystemBackgroundSemaphore 控制并发。区分标准就一条：有 `task_id` 的 Agent Task Work 走调度链与 TaskBudget；没有 `task_id` 的 System Background Job 走 SystemBackgroundSemaphore。三个对象互不等价：TaskExecutionSlot ≠ LLM / Tool Semaphore ≠ SystemBackgroundSemaphore——槽位管多少任务在推进，LLM / Tool Semaphore 管任务内部调用的并发，SystemBackgroundSemaphore 管无主系统工作的并发。

## 优先级与背压

调度优先级只保留两类：interactive（用户正在等待的交互任务）与 background（后台任务），默认优先 interactive。当前接受一个遗留问题：交互任务长期繁忙时，后台任务可能等待较久——不引入 aging、加权公平队列或多级优先级（理由见文末遗留问题）。

背压（Backpressure）与有限并发分工不同：有限并发限制正在执行的任务数，背压限制新任务继续进入。背压分三档：

| 档位 | 新交互任务 | 新后台任务 | 已有任务 |
| --- | --- | --- | --- |
| NORMAL | 正常接受 | 正常接受 | 正常执行 |
| PRESSURED | 正常接受 | 延后或拒绝新增 | 不受影响 |
| SATURATED | AdmissionRejected(SYSTEM_BUSY) | 拒绝 | 不删除，只等待资源 |

SATURATED 档重申了本章开头那条边界：新任务 T300 在此档位下被准入拒绝，但已处于 `WAITING_HUMAN` 的 T100 在用户确认后照常登记 R2、入队排队等槽（QUEUED），不会被取消或拒绝。拒绝新增负载不等于丢弃已接受任务——准入门槛拦的是还没进门的任务，对已经承诺的任务只有「等待」一种处理。

## Circuit Breaker：共享依赖的健康开关

依赖熔断器（DependencyCircuit）维护每个共享外部依赖的整体健康状态。熔断属于共享 Runtime，不属于某个任务——所有任务访问同一个依赖时共用同一个熔断器：

```python
class DependencyCircuit:
    dependency_key: str          # 依赖标识：model_api / exercise_search_api / nutrition_service
    state: str                   # CLOSED（正常）/ OPEN（熔断）/ HALF_OPEN（试探）
    consecutive_failures: int    # 连续失败计数，成功时清零；达到阈值即熔断（阈值由配置决定）
    opened_at: datetime | None   # 进入 OPEN 的时刻
    next_probe_at: datetime | None  # 冷却结束、允许探测的时刻
```

```text
CLOSED ──连续失败达到阈值──→ OPEN
  ↑                            │ 冷却到 next_probe_at
  │                            ↓
  └─────探测成功────── HALF_OPEN ──探测失败──→ OPEN（重新计时）
```

调用顺序上，熔断检查发生在预算扣减之后、真实调用之前：

```text
准备调用依赖 X
    ↓ Circuit.allow(X)
CLOSED：正常调用
OPEN：直接返回 DependencyUnavailable，不占外部调用槽位
HALF_OPEN：只放行少量探测请求
    ↓ 真实调用内部的重试仍由第四章 Retry Policy 处理
```

由此重试与熔断分层清楚：Retry 回答「这一次调用失败后怎么办」，Circuit Breaker 回答「这个共享依赖现在还值不值得继续调用」。偶发 Timeout 走有限重试；连续多个任务在同一个依赖上失败，后续任务不再分别等待并重复验证相同的故障。

哪些失败计入熔断由错误类别决定：Timeout、429、5xx、连接失败计入（它们说明共享依赖本身异常）；参数校验失败、权限拒绝、业务规则拒绝、HIL 拒绝不计入（这些是个别请求的问题，依赖本身可能完全健康）。

计数的单位是逻辑调用的最终结果，不是 Retry Attempt。LC300 的 Attempt 1 timeout、Attempt 2 timeout、Attempt 3 success——前两次失败在第四章重试策略内部消化，逻辑调用最终成功，熔断计数清零；只有全部尝试失败、逻辑调用以失败收场时，`consecutive_failures` 才加一。按 Attempt 累加会让一次逻辑失败被网络重试放大成多次计数，熔断阈值被重试噪音淹没——逻辑调用与 Retry Attempt 保持两个身份。

熔断不决定业务降级。依赖熔断时本章只返回 `DependencyUnavailable`，业务上怎么处理由既有语义决定：第三章的证据依赖 OPEN 时，optional 证据走 PARTIAL EvidenceBundle、required 证据走 FAILED（见 [[9.证据装配与失败语义]]），第三章或第四章的失败语义不因第六章重新定义。

预算与熔断的交叉按扣减时机裁定：I300 已被运行时接受、工具预算已消费一次，随后才发现熔断 OPEN——I300 以 `DependencyUnavailable` 失败，不退款；对同一个 I300 的重试不重复扣预算。预算计「发起」，熔断计「依赖健康」，两个账本各记各的。

## 一次资源调用的统一顺序

把前面所有机制串起来，第一版保持这条固定顺序：

```text
BudgetManager.consume_once      # ① 预算：这个任务还能不能发起动作
    ↓
Circuit.allow                   # ② 熔断：这个依赖现在值不值得调
    ↓
Resource Gate acquire           # ③ 信号量：LLM / Tool Semaphore 有没有并发空位
    ↓
真实调用                        # ④ Model API / Tool Runtime
    ↓
record dependency outcome       # ⑤ 按逻辑调用的最终结果记录：成功清零、全部尝试失败才 +1
    ↓
release Resource Gate           # ⑥ 归还信号量
```

顺序的含义：熔断已 OPEN 时不占外部调用槽位（②失败直接短路，③⑥不发生），预算已耗尽时连依赖健康都不用查（①失败更早短路）。对跨越人工介入的 I300，这条顺序拆在两个时点执行：预算扣减发生在运行时接受它的时刻（`prepare_invocation`），熔断检查与信号量获取发生在每次真实执行前——顺序不变，只是中间隔了一段等待。

## 场景走查

### 走查一：主链——T200 从准入到跨领域执行

用户在会话 C10 提出「根据新的工作时间重新调整训练计划，饮食同步调整」，Supervisor 判断这是跨领域目标，任务控制器创建 T200：

```text
TaskCreateRequest（task_type = cross_domain_plan）
    ↓ BudgetPolicyResolver → cross_domain_plan 档（具体数字不重要）
    ↓ AdmissionController → PASS
创建 T200 + TaskBudget + R1 + SI200 入队
    ↓ 取得 Task Slot，开始切片 ES200
Supervisor 决策：LC200 → LLM 预算 +1，委派 DT10（workout）
训练智能体：LC201 → +1；工具调用 I210 被运行时接受 → Tool 预算 +1
    ↓ DT10 succeeded
Supervisor 再次决策：LC202 → +1，创建 DT20（diet）
    ↓ DT20 的每一次 LC / I
继续消费同一个 T200 TaskBudget（parent_task_id），而不是新预算
```

预算不随领域切分：无论动作发生在 Supervisor、训练智能体还是饮食智能体，扣的都是 T200 那一份。单领域的 T100 走的也是这条链，只是没有领域任务一层。

### 走查二：HIL 与 Resume——预算跨 Run 累计

T100 的 R1 执行中：`generate_draft` 消耗 LC100（+1），`prepare_invocation` 创建 I300（Tool +1），随后中断等待确认：

```text
wait_for_human → 检查点持久化 → ES100 结算 → 释放槽位 → WAITING_HUMAN
    ↓ 用户离开三小时（不占槽位、active_runtime 不增长）
用户确认（TaskAction，第一章校验链通过）
    ↓ 受理事务：R2 登记、I300 → APPROVED
ensure_scheduled(T100, R2) → SI101 → 排队 → 取得新槽位
    ↓
execute_invocation(I300)：同一操作身份，不再扣 Tool 预算
complete_task：D200 → COMMITTED、T100 → COMPLETED，usage 保留全程累计
```

三小时等待没有花掉任何预算；恢复后的执行与等待前的执行共享同一份 usage——这就是「预算绑定 task_id、不因 R1 → R2 重置」。

### 走查三：过载——PRESSURED 到 SATURATED

```text
后台队列满、交互队列接近上限
    ↓ 背压 → PRESSURED
新后台任务：延后 / 拒绝；交互任务继续接受
    ↓ 交互增长到硬上限
背压 → SATURATED
新任务 T300：AdmissionRejected(SYSTEM_BUSY)——任务与预算都不创建
T100 = WAITING_HUMAN，用户确认：R2 → 正常登记 → QUEUED 等槽（不拒绝、不取消）
```

### 走查四：熔断——model_api 从 OPEN 到恢复

多个任务的模型调用连续 Timeout / 429 / 5xx：

```text
model_api 熔断器：consecutive_failures 达到阈值 → OPEN
    ↓ 之后任何任务的新 LC
Circuit.allow → DependencyUnavailable（预算已扣，不退款）
    ↓ 冷却到 next_probe_at
HALF_OPEN：放行一个探测 LC
    ├── 成功 → consecutive_failures 清零 → CLOSED
    └── 失败 → 回到 OPEN，重新计时
```

熔断期间只有依赖 `model_api` 的执行路径受影响：本地工具、数据库、其他依赖照常工作。

## 第六章代码级理解总结

五组对象各自承担什么、为什么不能合并：

- **预算不能绑 Request 或 Run**。预算限制的是逻辑目标整个生命周期的自主行动总量；Request 只是入口计数，Run 只是执行段。绑 Run，R1 → R2 就变成重新拨款；绑 Request，一次暂停恢复就逃出治理。
- **SchedulingItem 不能并入 Task 或 Run**。调度项表达「正在等待一次执行机会」这个可重建的短暂事实；Task / Run 是持久身份。队列崩溃时允许丢掉的只有调度项。
- **Task Slot 与资源信号量不能合并**。一个回答「多少任务在推进」，一个回答「每类共享资源允许多少并发」。合并后要么大量任务空转抢不到资源，要么少数任务打爆外部依赖。
- **BudgetView 与 BudgetManager 不能合并**。提示与强制分开：模型看得到额度、改不了额度；改额度的代码路径只有运行时的扣减与策略。
- **Retry 与 Circuit 不能合并**。一次调用的再试判断与一个依赖的整体健康判断发生在不同层级；混同会把偶发失败放大成全局停摆，或把持续故障当成可以重试的偶发抖动。

## 未下沉与不新增

仍未达到代码级逻辑的部分：各预算策略（ordinary_qa / complex_plan / cross_domain_plan / background_analysis）的具体额度数值；准入的每用户上限、队列容量与硬上限数值；熔断阈值与冷却时间的具体数值；第五章遗留的「委派深度与 DomainTask 数量」配额字段（属预算策略配置，本篇只下沉了三个主维度）。

本轮明确不新增：Kafka、Redis Queue、Celery、Kubernetes、分布式 Scheduler、分布式锁、复杂 Fair Queue、多级 Priority、Autoscaling、动态预算学习、复杂成本计费、Service Mesh。当前组合——单实例 + 进程内 Queue + 持久 Task State + Semaphore + 简单 Circuit Breaker——已经覆盖当前规模。

明确保留的遗留问题：队列非持久（进程内，重建靠恢复扫描）；优先级只有两级（接受后台任务可能长期饥饿）；熔断是单实例状态（多实例间不共享依赖健康）；active_runtime 是治理口径不是财务级计费。未来只有出现多实例部署、任务需要跨实例执行、后台长期饥饿、需要跨实例统一依赖健康这几种情况，才值得升级对应机制。

## 边界问答

**1. Q：** 为什么 Budget 绑定 Task，而不是 Request 或 Run？

**A：** HTTP 请求的数量不等于任务的实际消耗（一个请求背后可能是几十次模型调用），Run 只是任务的一段执行。预算要约束的是「这个逻辑目标全程最多自主发起多少动作」，只有 task_id 覆盖整个生命周期。

**2. Q：** R1 → R2 为什么不重置预算？

**A：** Run 是执行段，不是新的授权。恢复只是继续原目标，若 R2 重新获得完整预算，任务可以通过「暂停—恢复」循环无限续额度；usage 跨 Run 累计，恢复不等于重新拨款。

**3. Q：** 谁决定预算上限？

**A：** 运行时策略。BudgetPolicyResolver 把 `task_type` / `difficulty` / `execution_mode` 映射到预配置策略；Supervisor 只声明任务类型与复杂度，不能直接填写 `max_llm_calls` 之类的数字。

**4. Q：** 模型为什么只能看到 Budget，不能修改？

**A：** BudgetView 是只读投影，用于指导模型收敛决策；真正的限制由 BudgetManager 在调用前强制检查。允许模型改预算等于让被治理者写治理规则。

**5. Q：** LLM / Tool 到底什么时候扣 Budget？

**A：** 运行时接受一个新的逻辑 LLM 调用（LC）或工具调用实例（I）时扣一次。I300 在 `prepare_invocation` 被接受即扣，即使后续依赖失败也不退款——预算限制的是自主发起动作的总量，不只是 API 账单。

**6. Q：** Retry 和节点重放为什么不会重复扣？

**A：** 每次扣减写一条 BudgetCharge，唯一键 `task_id + resource_type + operation_id`；操作身份是稳定的（工具用 I300、模型用 LC300、时间用切片 ES10）。同一动作的重试与重放命中已有记录，直接复用，不再扣。

**7. Q：** 并行 DomainTask 抢最后一个额度怎么办？

**A：** 检查与扣减在同一个原子事务里完成（加 `version` 条件更新兜底）。剩余 1 次额度时 DT10、DT20 同时 consume，恰好一个成功，另一个得到 `BudgetExceeded`。不需要分布式锁。

**8. Q：** active_runtime 怎么算？

**A：** 以 ExecutionSlice 为单位累计：取得执行槽位时开始、释放时结束，时长结算进 `used_active_runtime`；并行切片各自累计。硬限制不靠事后结算发现——切片开始时把剩余额度换算成 `slice_deadline`，Runtime 在边界检查，超过即 `BudgetExceeded(active_runtime)`。它是任务实际占用执行资源的累计时间，不是墙钟时间。

**9. Q：** 为什么 Queue / HIL 等待不算？

**A：** 等待期间任务不占用执行资源。把排队和人工等待计进预算，等于惩罚「等待慢」而不是限制「消耗多」；用户离开三小时再确认，任务不应该为此花掉预算。

**10. Q：** SchedulingItem 是什么？

**A：** 「某个已有 Task / Run 当前等待一次执行机会」的调度项，由调度器在入队时创建、取得槽位后消费。它不是新任务：没有目标、没有检查点、没有预算，可丢可重建，挂靠在 `run_id` 上。

**11. Q：** Queue 为什么不是事实源？

**A：** 队列是进程内的调度索引，只回答「谁在排队」；任务是否存在、执行到哪，事实在持久 Runtime（控制索引 + 检查点）。队列可以消失重建，任务状态不能依赖它。

**12. Q：** 进程重启如何恢复队列？

**A：** Scheduler Recovery 扫描持久 Runtime 中「任务未到终态、不在等待人工介入、当前 Run 已受理但未执行到终点」的条目，逐条 `ensure_scheduled(task_id, run_id)` 重新生成调度项。不需要 Redis Queue / Kafka / Celery。

**13. Q：** 为什么 Task Slot 和 LLM / Tool Semaphore 要分层？

**A：** 两层限制的对象不同：Slot 限制同时推进的任务数（防止单实例被任务占满），Semaphore 限制每类共享资源的并发调用数（防止外部依赖被打爆）。T100 有槽位仍要过 LLM Semaphore，两层各自独立配置。系统后台 Job 是第三个对象：不占槽位、不走 LLM / Tool Semaphore，只在 SystemBackgroundSemaphore 里限并发。

**14. Q：** 新 Task Admission 和 Resume 有什么区别？

**A：** Admission 检查用户活跃任务数、队列压力与背压档位，通过才创建任务与预算；Resume 不走 Admission——不重新准入、不重建预算、不重置 usage，系统忙时只是排队等槽。

**15. Q：** 后台 DomainTask 消耗谁的 Budget？

**A：** 父任务的。AE500 后台切片内发生的每一次 LC / I 都记在 `parent_task_id` 指向的 TaskBudget 上（切片的 `domain_task_id` 记录 DT10）；后台是执行方式，不是第二个预算主体，不能绕过预算。

**16. Q：** Backpressure 与有限并发有什么区别？

**A：** 有限并发限制正在执行的任务数量；背压在处理能力饱和时从源头限制新任务进入队列，防止等待队列无限增长。前者管执行侧，后者管进入侧。

**17. Q：** 为什么 SATURATED 时新交互 Task 也可能被拒绝？

**A：** 硬上限是系统自我保护的最后防线：连交互队列都满了，继续接受只会让所有任务一起长时间等待。拒绝并返回 `SYSTEM_BUSY` 比无限排队更诚实；已有任务不受影响。

**18. Q：** 为什么已有 Task Resume 不能被当成新任务拒绝？

**A：** 任务已被系统接受并消耗了预算，用户确认的是既有的 I300 / R2，不是新增负载。拒绝恢复等于丢弃已承诺的工作；正确处理是排队等槽（QUEUED）。拒绝新增负载 ≠ 丢弃已接受任务。

**19. Q：** Retry 与 Circuit Breaker 有什么区别？

**A：** Retry（第四章）回答「这一次调用失败后怎么办」，在单次调用内部；Circuit（本章）回答「这个共享依赖现在还值不值得继续调用」，在依赖层面。顺序上熔断检查在前、真实调用内部的重试在后。

**20. Q：** Circuit 属于 Task 吗？

**A：** 不属于。DependencyCircuit 是共享 Runtime 状态，所有任务访问同一个依赖时共用——如果每个任务各自维护，等于每个任务都要亲自验证一遍相同的故障，熔断就失去了止损意义。

**21. Q：** 哪些错误影响 Circuit？

**A：** 计入：Timeout、429、5xx、连接失败——它们说明共享依赖本身异常。不计入：参数校验失败、权限拒绝、业务规则拒绝、HIL 拒绝——这些是个别请求的问题，依赖可能完全健康。计数单位是逻辑调用的最终结果：全部尝试失败才 +1，尝试内部的 Retry 不累加。

**22. Q：** Budget Exhausted 后谁停止执行？

**A：** 运行时。`consume_once` 抛 `BudgetExceeded` 后 LLM Gateway / Tool Runtime 不发出真实调用，`budget.status = EXHAUSTED`，任务无法继续时 FAILED（`failure_code = BUDGET_EXHAUSTED`）；已有产物按第五章 `partial_result_policy` 处理。停止执行靠运行时拒绝，不靠模型自觉。

**23. Q：** 本章如何与第一、二、四、五章衔接？

**A：** 第一章提供 Task / Run / Checkpoint / Resume，本章决定 Run 什么时候获得执行资源、预算如何跨 Run 累计；第二章把 BudgetView 装进 AgentStatus 但硬限制仍在 BudgetManager；第四章的 I300 是工具预算的操作身份、Attempt 不重复扣；第五章的 `task_type` / `execution_mode` 是策略输入、后台 DomainTask 消耗父任务预算。完整接口见「与前五章的接口」表。
