# Task Runtime、Checkpoint 和业务状态

## 四层状态分层

每日计划涉及的状态不会全部放进同一个存储。原因在于这些状态的用途和生命周期不一样：控制面要快速查询的任务元数据、图恢复需要的执行状态、还没确认的草稿、以及已经确认的正式业务数据，读写模式和可靠性要求都不同。

四层从上到下依次是：

```text
LangGraph 检查点
        │
        │ 执行状态
        ▼
agent_task_runtime
        │
        │ 任务控制索引
        ▼
草稿存储
        │
        │ 用户确认
        ▼
业务数据库
```

- **LangGraph 检查点**：执行状态。图当前执行到哪个节点、状态数据、待处理的中断现场都保存在这里。
- **agent_task_runtime**：任务控制索引。当前有哪些任务、各自什么状态、版本多少、什么时候过期。
- **草稿存储（Draft Store）**：尚未确认的计划。生成出来等用户确认或修改，确认后才进入下一层。
- **业务数据库（Business Database）**：正式业务事实，比如已经确认生效的训练计划。

这几层之间不存在替代关系。

例如，检查点记录每日计划已经运行到最终保存节点，不代表训练计划已经成为正式业务事实。只有业务服务成功提交数据库以后，任务才能进入 `COMPLETED`（状态定义见 [[4.Conversation 与 Task 生命周期#任务状态机]]）。

反过来，如果业务计划已经保存成功，即使后面清理了对应检查点，也不能影响正式业务数据。图回退到旧检查点同样不能被理解成业务数据库也发生了回滚。

第五章进一步引入 Artifact Store：它保存跨智能体协作的中间/交付产物（如 TrainingLoadAssessment、WorkoutPlanDraft），介于运行时状态与业务状态之间，不自动成为正式业务事实（见 [[6.通信协议与 Artifact]]）。

## agent_task_runtime 控制索引

控制平面增加一张轻量的 `agent_task_runtime` 表：

```python
class AgentTaskRuntime:
    task_id: UUID                  # 任务身份
    root_thread_id: str            # 所属会话（根图）的执行线索
    task_thread_id: str            # 任务自己的执行线索，用来定位它的检查点
    user_id: UUID                  # 任务所属用户

    task_type: str                 # 任务类型，如 daily_plan
    status: str                    # 当前任务状态
    task_version: int              # 乐观并发版本，状态更新时自增

    draft_id: UUID | None          # 当前关联草稿，可为空
    draft_version: int | None      # 草稿版本，可为空

    expires_at: datetime | None    # 过期时间，可为空
    created_at: datetime           # 创建时间
    updated_at: datetime           # 更新时间
```

这张表主要用于快速回答两个问题：某个会话当前是否存在活跃任务；`task_id` 对应哪个 `task_thread_id`。

字段可以分成几组：

- 身份：`task_id`、`root_thread_id`、`task_thread_id`、`user_id`，把一个任务和它的会话、用户、执行线索对上。
- 控制：`task_type`、`status`、`task_version`，记录任务类型、当前状态和乐观并发版本。
- 草稿关联：`draft_id`、`draft_version`，指向当前草稿及其版本。
- 时效：`expires_at`、`created_at`、`updated_at`。

它同时保存任务状态、版本和过期时间，方便任务控制器在恢复图之前完成控制层校验。版本与过期字段的语义分别见 [[7.版本控制与并发]] 与 [[4.Conversation 与 Task 生命周期#过期策略]]。

运行时注册表（Runtime Registry）负责登记当前活跃任务、跟踪任务生命周期状态；任务状态、版本和过期时间的字段持久化在这张表里。

完整的图状态（Graph State）不复制到这里。Messages、每日计划中间状态、候选动作和中断现场仍然由 LangGraph 检查点管理。

## LangGraph 检查点语义

检查点（Checkpoint）是 LangGraph 在节点执行过程中保存的运行快照：包含图当前执行到哪个节点、状态数据，以及待处理的中断（pending interrupt）。恢复时按它确定“从哪一步继续”。

`agent_task_runtime` 和检查点的关系可以理解为：

```text
agent_task_runtime
    task_id
    status
    expires_at
    task_thread_id
          │
          ▼
LangGraph 检查点
    图当前位置
    图状态
    待处理中断
```

检查点只解决“恢复到哪一步”，不保证业务写入只发生一次；可重放性约束见 [[6.HIL 与恢复#可重放性约束]]。

> [!note] 什么时候才升级成持久任务
> “哪些流程需要任务检查点”属于执行模型决策，见 [[3.执行模型与任务边界#执行单元与编排方式]]。

## 边界问答

**1. Q：** 检查点已经记录了执行位置，为什么还不能代替业务数据库？

**A：** 两层含义不同。检查点记录“执行到哪一步”，不代表业务事实成立：只有业务服务成功提交数据库以后任务才能进入 `COMPLETED`；反过来，业务数据保存成功后即使清理对应检查点，也不影响正式业务数据。

**2. Q：** `agent_task_runtime` 为什么不把完整的图状态也存进来？

**A：** 它只是轻量控制索引，用于快速回答“当前有没有活跃任务、`task_id` 对应哪个 `task_thread_id`”。Messages、每日计划中间状态、候选动作和中断现场仍然由检查点管理，控制索引不复制。

**3. Q：** 为什么使用 PostgreSQL 作为检查点存储？

**A：** 凡是需要跨服务或跨重启恢复状态的图，均使用 PostgreSQL 进行持久化。会话和任务可以共享同一套 PostgreSQL 实例与连接池，通过划分不同的 `thread_id` 命名空间进行数据隔离，能够满足可靠性要求。

**4. Q：** 系统为什么不引入 Redis？

**A：** 基于最小依赖原则，当前系统已依赖 PostgreSQL，且当前阶段的任务持久化数量与并发规模尚未达到关系型数据库的瓶颈。额外引入 Redis 会带来持久化策略、数据淘汰机制、连接管理等多重开发维护成本，并增加新的故障边界，目前系统暂未出现必须依赖 Redis 才能解决的性能痛点。

**5. Q：** 进程内缓存（In-process Cache）的定位是什么？

**A：** 进程内缓存仅能作为纯粹的性能优化手段，例如缓存非核心的查询结果。它严禁用于存储关键的业务节点（如 `WAITING_HUMAN` 的中断恢复位置）。只要系统要求“后端重启后用户仍能继续之前的交互”，该状态数据就必须进入持久化存储，不能依赖易失性的内存缓存。
