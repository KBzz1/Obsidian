# 任务队列、优先级与有限并发

任务通过准入后，并不意味着立即获得执行资源。智能体任务（Agent Task）的耗时和资源消耗差异较大，如果所有任务一进入系统就同时调用模型 API、工具和数据库，即使应用本身可以创建大量异步协程，也可能迅速把外部 API 配额、数据库连接或本地执行资源占满。因此系统通过任务队列（Queue）保存暂时无法执行的任务，再由有限的执行槽位控制实际并发量。

## 任务队列

队列解决的是「哪些任务正在等待」。任务通过准入后先进入队列，等待调度器（Scheduler）分配执行资源，而不是立即并发执行。这样不同耗时和资源消耗的任务不会在进入系统的瞬间同时冲击模型 API、工具和数据库。

## 两类执行优先级

当前系统只区分两类执行优先级。交互任务是用户正在等待结果的会话任务，例如一次训练智能体（Workout Agent）的计划调整；后台任务包括记忆巩固（Memory Consolidation）、后台分析和不要求立即返回的异步任务（见 [[9.HIL 与异步任务]]）。调度器优先让交互任务获得执行资源，后台任务在资源允许时运行。这里不需要引入复杂的多级优先级调度器，当前业务只需要保证用户正在等待的请求不会因为后台任务占满资源而长时间无法运行。

## 有限并发

有限并发解决的是「同一时间到底允许多少调用真正执行」。系统分别对主要资源设置并发上限，例如模型 API 调用并发、外部工具调用并发以及后台任务并发。这里的模型 API 并发并不是模型实例池，因为模型实际由第三方供应商提供；它只是限制 Harness 同时向外部模型服务发出的请求数量。对于当前单实例规模，进程内任务队列配合 Semaphore 即可实现这套机制，不需要引入 Kafka 或复杂的分布式工作线程（Worker）系统。

## 人工介入等待不占用槽位

人工介入（HIL）等待状态不会持续占用执行槽位。当一个任务执行到需要用户确认的步骤时，第一章负责保存检查点（Checkpoint）并把任务进入等待状态（见 [[5.Task Runtime、Checkpoint 和业务状态]] 与 [[6.HIL 与恢复]]），第六章则释放当前执行资源。用户完成确认并恢复任务后，任务重新进入调度过程，再次取得执行槽位后继续运行。这样长时间等待用户输入的任务不会占用有限的并发资源。

当前队列和并发控制的目标是管理单实例内部的运行秩序，而不是包装成完整的分布式任务系统。任务状态本身仍然按照第一章的持久化机制保存，但进程内队列只承担当前实例中的调度职责。

## 边界问答

**1. Q：** 为什么任务要通过队列而不是直接并发执行？

**A：** 任务的耗时和资源消耗差异较大，全并发会迅速占满外部 API 配额、数据库连接或本地执行资源。队列保存暂时无法执行的任务，有限槽位控制实际并发量。

**2. Q：** 为什么只区分两类优先级？

**A：** 当前业务只需要保证用户正在等待的交互任务不被后台任务占满资源而长时间无法运行，不需要复杂的多级优先级调度器。

**3. Q：** 人工介入等待为什么不占用执行槽位？

**A：** 长时间等待用户输入的任务不应占用有限并发资源。任务进入等待状态时释放槽位，用户确认恢复后重新进入调度，再次取得槽位继续运行。

**4. Q：** 为什么不引入 Kafka 或分布式工作线程系统？

**A：** 当前是单实例规模，进程内任务队列配合 Semaphore 即可满足；任务状态本身仍按第一章持久化机制保存，进程内队列只承担当前实例内的调度职责。
