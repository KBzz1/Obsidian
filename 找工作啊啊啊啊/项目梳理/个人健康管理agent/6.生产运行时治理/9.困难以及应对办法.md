# 困难以及应对办法

这次演化只围绕一个问题展开：早期系统的并发控制停留在请求层和单次调用层，随着智能体任务变长、人工介入和后台任务加入，单个请求与一个智能体任务的真实执行成本开始脱离，系统缺少以逻辑智能体任务为单位的资源治理边界。

## 旧设计：资源控制停留在请求层和单次调用层

早期版本的系统并没有专门针对智能体任务（Agent Task）做资源治理。一次用户请求进入服务后，根运行时直接启动对应的智能体执行流程；需要调用模型、工具或后台任务时，则继续通过异步调用向下执行。并发控制主要停留在普通接口层和单次外部调用层，例如限制 HTTP 请求数量、为单次工具调用设置超时和重试。对于最初较短的智能体任务，这种方式能够正常工作，因为一次请求通常只包含少量模型调用和工具调用，请求本身与实际资源消耗基本接近。

## 困难：请求成本与任务成本开始脱离

随着训练智能体（Workout Agent）、饮食智能体（Diet Agent）、人工介入（HIL）和后台任务逐渐加入，单个请求与一个智能体任务的真实执行成本开始明显脱离。两个同时进入系统的请求看起来占用了相同的接口并发，但其中一个可能只进行一次模型调用，另一个却可能在推理-行动循环（ReAct，见第五章 [[5.Domain Agent 执行模型]]）中连续执行多轮模型调用、知识检索和工具调用。任务还可能中途等待人工确认，恢复后再次进入执行。此时仅从 HTTP 请求或单次协程数量控制并发，已经无法表达一个逻辑智能体任务到底消耗了多少资源。

这一问题最容易在长任务中表现出来。假设一个训练智能体因为当前状态判断不稳定，在模型调用和工具查询之间持续循环。旧实现并没有为整个任务设置统一执行边界，只要每一次模型调用和工具调用本身没有报错，任务就可以继续推进。与此同时，记忆巩固（Memory Consolidation）等后台任务与用户交互任务共享相同的执行资源。当多个复杂任务同时进入后，系统可能创建越来越多正在等待外部模型或工具的异步调用。即使单个调用都符合第四章的超时和重试规则（见 [[6.可靠执行]]），整个系统仍然会出现用户交互任务等待时间增加、后台任务争抢资源以及外部 API 被集中请求等现象。

## Harness 层根因：缺少任务级治理边界

问题的根因不在某个工具的重试配置得不合理，也不只是协程数量太多，而是旧设计缺少以逻辑智能体任务为单位的资源治理边界。一次工具调用可以知道自己最多重试几次，却不知道整个任务已经调用了多少次工具；一个 HTTP Handler 可以限制自己是否正在执行，却不知道它内部还会继续产生多少轮模型调用。请求层、智能体层和工具层分别存在局部限制，但没有统一回答「这个任务最多允许执行到什么程度」以及「多个任务竞争资源时谁应该先获得执行机会」。

## 改造：引入统一的任务级治理

因此后续改造没有继续在每个智能体或工具上分别增加更多局部限制，而是在生产运行时层引入统一的任务治理。每个任务创建时由运行时策略（Runtime Policy）分配任务预算（Task Budget，见 [[4.任务预算与任务准入]]），限制逻辑模型调用、逻辑工具调用和有效执行时间；预算使用量作为任务的控制状态持久化，使任务在检查点（Checkpoint）恢复以后继续使用原来的剩余额度。智能体可以通过智能体状态（Agent Status）看到剩余预算并主动收敛，但真正的执行上限始终由运行时强制控制。

在多个任务同时运行时，任务不再进入系统后立即无限创建新的执行协程，而是先经过轻量准入并进入有界任务队列（见 [[5.任务队列、优先级与有限并发]]）。交互任务优先于后台任务获得执行资源，模型 API、外部工具和后台任务分别通过有限执行槽位控制实际并发。人工介入中断后的任务保存状态并释放执行槽位，恢复时重新进入调度过程，而不是在等待用户期间持续占用运行资源。当队列已经接近处理上限时，系统通过背压（Backpressure，见 [[6.背压]]）延后后台任务并限制继续积压新的低优先级任务。

外部依赖保护也由单次调用提升到跨任务的治理层级（见 [[7.外部依赖保护与服务级熔断]]）。第四章仍然负责一次工具调用是否可以重试，而第六章根据多个任务对同一外部依赖的失败情况判断依赖是否整体异常。当连续超时、429 或 5xx 达到设定条件后，服务级熔断暂时阻止新的调用，冷却后再通过少量请求探测恢复状态。这样已经明显异常的依赖不会继续让后续每个任务分别等待、重试并消耗自身预算。

## 最终形成的运行方式

```text
旧设计

用户请求
    ↓
智能体运行时
    ↓
不断产生模型 / 工具 / 异步调用
    ↓
各调用只管理自己的超时 / 重试


当前设计

任务创建
    ↓
运行时策略分配任务预算
    ↓
任务准入
    ↓
有界队列 + 优先级
    ↓
获得有限执行资源
    ↓
智能体 / 工具运行时
    ↓
外部依赖
    ↓
背压 / 服务级熔断
```

## 改造代价

这次改造增加了任务预算状态、任务队列、并发控制和依赖健康状态等额外运行信息，执行链比早期直接启动智能体更复杂。同时，任务不再能够无限占用资源，后台工作也可能因为用户交互任务而被延迟。但这些成本对应的是 Agent Harness 中真实存在的不确定执行长度问题。当前项目仍然采用进程内队列、Semaphore 和轻量策略配置，没有进一步引入分布式消息系统或复杂调度平台，因此治理能力与系统当前规模保持一致。

## 遗留问题与未来改进

当前生产运行时治理主要面向单实例和有限数量的并发智能体任务。进程内队列和 Semaphore 可以控制当前实例内部的等待顺序与并发量，但队列本身不是持久化任务系统。如果进程在任务仍然排队时崩溃，任务的正式运行状态可以依靠第一章的持久化机制恢复，但尚未进入执行的内存队列顺序不会被完整保留。当前规模下可以接受这一边界；如果未来开始运行大量长时间后台任务，或者要求排队任务在服务重启后仍然按照原有调度继续执行，再考虑将调度层演化为基于 Redis 的队列或独立任务系统。

当前优先级只区分用户正在等待的交互任务和后台任务，调度规则保持简单。持续存在大量交互请求时，低优先级后台任务可能等待较久。现阶段没有必要引入复杂公平调度算法；如果后续发现记忆巩固、异步领域任务（DomainTask）等后台工作长期无法获得执行资源，可以增加等待时间提升优先级或预留少量后台执行槽位。

任务预算目前依据任务类型和复杂度使用预设策略分配，预算本身不会由模型任意扩大。随着真实运行数据积累，可以进一步根据不同任务类型的实际模型调用次数、工具调用次数和有效执行时间调整默认额度。只有在「合法任务经常在接近完成时耗尽预算」成为稳定现象后，才值得考虑受控的预算扩展（Budget Extension）；当前版本直接采用硬上限，避免过早引入动态预算审批逻辑。

服务级熔断目前采用单实例内的依赖健康状态。如果未来系统扩展为多个应用实例，各实例分别判断依赖状态可能导致同一外部服务在不同实例中出现不一致的熔断结果。只有在多实例部署成为真实需求时，才需要考虑共享依赖健康状态或集中式限流与熔断控制。当前没有必要为尚不存在的多实例运行环境引入分布式协调。

本章只保留支撑运行时治理的轻量运行指标（见 [[8.轻量运行监控]]）。完整执行轨迹分析、评测数据构建、RAG 召回质量、工具调用正确性、Rubric、LLM-as-Judge 和回归测试不在本章展开，统一进入后续测试与评估章节。这样第六章保持在「系统如何稳定运行」的职责范围内，第七章再解决「智能体是否做对以及系统改动是否真正改善结果」的问题。

## 边界问答

**1. Q：** 最早的「请求层 + 单次调用层」并发控制为什么一开始是合理的？

**A：** 早期智能体任务较短，一次请求通常只包含少量模型调用和工具调用，请求本身与实际资源消耗基本接近，请求层和单次调用层的限制足够表达真实成本。问题在训练智能体、饮食智能体、人工介入和后台任务加入、任务执行成本与请求成本脱离以后才出现。

**2. Q：** 为什么继续在请求层和单次调用层增加限制解决不了问题？

**A：** 请求层、智能体层和工具层分别只有局部限制：一次工具调用知道自己最多重试几次，却不知道整个任务已经调用了多少次工具；一个 HTTP Handler 知道自己是否正在执行，却不知道内部还会继续产生多少轮模型调用。它们无法统一回答「这个任务最多允许执行到什么程度」和「多个任务竞争资源时谁应该先获得执行机会」。

**3. Q：** 这次改造的代价是什么，为什么仍然值得做？

**A：** 增加了任务预算状态、任务队列、并发控制和依赖健康状态等额外运行信息，执行链更复杂，任务不能再无限占用资源，后台工作可能被交互任务延迟。但这些成本对应 Agent Harness 中真实存在的不确定执行长度问题；当前仍用进程内队列、Semaphore 和轻量策略配置，治理能力与系统当前规模保持一致。

**4. Q：** 进程内队列不持久化，为什么当前可以接受？

**A：** 队列本身不是持久化任务系统。进程崩溃时，任务的正式运行状态可以依靠第一章的持久化机制恢复，但尚未进入执行的内存队列顺序不会完整保留。当前单实例规模下可以接受；未来运行大量长时间后台任务、或要求排队任务在重启后仍按原有调度执行时，再考虑基于 Redis 的队列或独立任务系统。

**5. Q：** 为什么不提前做多实例的分布式熔断协调？

**A：** 当前是单实例部署，各实例分别判断依赖状态导致结果不一致的问题只在多实例运行环境中出现。没有必要为尚不存在的多实例环境引入分布式协调，等多实例部署成为真实需求时再考虑共享依赖健康状态或集中式限流与熔断控制。

**6. Q：** 为什么预算采用硬上限而不是动态扩展？

**A：** 预算由运行时策略按任务类型和复杂度预设，模型不能任意扩大。只有在「合法任务经常在接近完成时耗尽预算」成为稳定现象后才考虑受控的预算扩展（Budget Extension）；当前直接采用硬上限，避免过早引入动态预算审批逻辑。
