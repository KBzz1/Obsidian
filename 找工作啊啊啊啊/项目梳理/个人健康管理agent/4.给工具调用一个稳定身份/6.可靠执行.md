# 可靠执行

护栏决定当前动作是否允许执行，可靠执行负责动作通过护栏以后，如何在超时、失败、重试和任务恢复情况下保持业务副作用可控。当前系统重点建设超时、幂等、重试、调用预算和执行结果核验，不引入复杂分布式事务机制。

## 超时

所有同步工具调用实例都设置明确的执行超时，避免某个工具长时间阻塞当前智能体循环。

读取型工具通常采用较短的超时，普通业务写工具根据领域服务（承载具体业务逻辑的服务）特性配置独立超时。

如果某项能力天然需要数分钟甚至更长时间，不通过不断拉长工具超时解决，而是转化为异步任务：

```text
工具
→ 创建异步任务
→ 返回 task_id
```

后续任务生命周期、事件状态和完成后的重新接入属于第五章异步任务机制（见 [[9.HIL 与异步任务|第五章异步任务]]）。

## 幂等

所有可能产生持久化业务副作用、并且可能因为重试或任务恢复被重复执行的工具，都必须声明幂等策略。幂等指同一个业务动作重复提交多次，也只产生一次业务副作用。

智能体系统比普通同步接口更容易产生重复执行，因为同一个业务动作可能同时经历：

```text
网络失败后的运行时重试

ReAct 智能体看到失败后的再次调用

任务中断恢复后重新经过执行节点
```

因此副作用工具在第一次真实执行之前就会创建稳定的幂等令牌（用于标识一次逻辑业务动作的唯一身份），而不是发生错误以后再临时补救：

```text
工具调用实例 I1
      ↓
idempotency_key = K1
      ↓
执行尝试 1
      ↓
失败
      ↓
执行尝试 2
      ↓
仍然使用 K1
```

如果领域服务或业务数据库由本系统控制，可以通过唯一约束、调用实例标识符或执行账本（记录已发生副作用的技术）保证同一个幂等键不产生第二次业务副作用。

例如：

```text
WorkoutSession
source_invocation_id UNIQUE
```

任务恢复或网络重试再次提交同一个调用实例时，领域服务能够识别这是同一个业务动作，而不是新的训练记录。

## 重试

重试不是「失败以后固定重试 N 次」，而是根据工具策略、错误类型以及幂等能力决定。

```text
参数错误
→ 不重试

权限错误
→ 不重试

业务规则不满足
→ 不重试

状态冲突
→ 不重试，由智能体 / 工作流重新获取状态并决策

网络瞬时故障
→ 可以重试

临时依赖服务错误
→ 可以重试

副作用工具
→ 只有具备安全幂等语义时才允许自动重试
```

运行时内部允许自动恢复的失败会优先在工具运行时内完成重试。只有重试策略已经结束以后，最终错误才返回智能体，避免把每一次瞬时网络异常都交给大模型自己判断是否重试。

## 调用预算与调用级止损

除了运行时自身的重试，还需要防止 ReAct 智能体不断重新提出相同的工具调用：

```text
工具调用失败
    ↓
智能体再次调用
    ↓
相同错误
    ↓
智能体再次尝试
```

系统因此对同一任务中相同工具的连续失败维护有限调用预算。达到阈值以后，运行时会停止继续自动执行，并向智能体返回明确的重试耗尽状态，让智能体重新规划、询问用户或停止任务。

这一机制只处理当前调用实例或当前任务范围内的重复失败。跨用户、跨任务共享的服务级熔断、背压和全局降级仍然属于第六章生产运行时治理。

## 执行结果核验

工具适配器返回成功不一定意味着预期业务效果已经真实发生。对于重要副作用工具，如果可以低成本进行确定性验证，运行时会进一步核验实际业务状态：

```text
请求：
替换当前计划 → plan_18

领域服务：
成功

核验：
current_plan_id == plan_18
new_version == expected_version
```

如果领域服务自身已经在事务内返回可信的影响实体、新版本和已提交效果，则不需要机械地对每个写操作再次读取数据库。

因此执行结果核验遵循：

```text
可低成本、确定性验证
→ 验证

额外验证成本高且领域服务已提供可靠事务结果
→ 使用领域服务的已提交结果
```

这一机制的目的不是增加一次固定数据库查询，而是避免系统仅根据接口返回成功或函数正常返回，就错误地认为业务动作已经完成。

## 边界问答

**1. Q：** 为什么长耗时能力不通过不断扩大工具超时来解决？

**A：** 需要数分钟甚至更长的能力会长时间阻塞当前智能体循环。应把它转化为异步任务并返回 `task_id`，后续任务生命周期、事件状态和完成后的重新接入属于第五章异步任务机制，而不是靠加长同步超时硬扛。

**2. Q：** 为什么副作用工具要在第一次真实执行之前就建幂等令牌？

**A：** 智能体场景比普通同步接口更容易重复执行：网络失败后的运行时重试、ReAct 智能体看到失败后的再次调用、任务中断恢复后重新经过执行节点，都可能在业务上指向同一个动作。提前建立稳定的幂等令牌才能在重试时复用同一身份，避免重复业务写入；等出错后再补救，往往已经产生了副作用。

**3. Q：** 什么情况下可以自动重试？

**A：** 根据工具策略、错误类型和幂等能力决定。参数错误、权限错误、业务规则不满足、状态冲突不重试；网络瞬时故障、临时依赖服务错误可重试；副作用工具只有具备安全幂等语义时才允许自动重试。可自动恢复的失败优先在工具运行时内完成，真正处理不了才返回给智能体。

**4. Q：** 调用预算和执行结果核验分别解决什么问题？

**A：** 调用预算阻止同一任务内相同工具的连续失败循环——智能体反复重新调用同一工具导致重复消耗与可能的重复副作用，达到阈值后返回重试耗尽状态让智能体重新规划。执行结果核验避免把接口返回成功误当成业务动作已完成，对可低成本确定性验证的重要副作用做核验，验证成本高且领域服务已给出可靠事务结果时则信任其结果。
