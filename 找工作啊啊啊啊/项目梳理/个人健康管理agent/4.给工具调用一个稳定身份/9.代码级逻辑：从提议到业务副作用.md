# 代码级逻辑：从提议到业务副作用

本篇回答两个问题：模型提出的一个动作如何获得稳定身份；这个动作最终如何安全地产生真实业务副作用。场景与第一章代码级逻辑篇同一段 Hero Scenario 的后半段：任务 T100 已在 `prepare_invocation` 创建调用实例 I300 并停在 `WAITING_HUMAN`；用户确认后，R2 从检查点恢复，到达 `execute_invocation` 节点执行 I300，正式训练计划被替换。

## 四个身份对象

一个动作从模型输出到业务事实，先后经过四类对象：

```text
工具调用（Tool Call）        模型或工作流的输出：「想做什么」——没有身份，不能被恢复引用
    ↓ 运行时接受并类型化
工具请求（Tool Request）     类型化的动作提议：tool_name + 业务参数
    ↓ 副作用动作需要人工确认
工具调用实例（I300）          运行时接管：参数固化、身份稳定、可跨暂停与恢复引用
    ↓ 每次真实执行
执行记录（ExecutionRecord）  一次执行尝试的事实（Attempt 1、Attempt 2…）
    ↓ 尝试成功
业务效果（Business Effect）  业务数据库中的正式变化，source_invocation_id 绑定
```

**工具调用（Tool Call）** 是大模型输出的一段函数调用意图，代表模型想做什么，生命周期到运行时接受为止。Tool Call 不等于工具调用实例：前者只是提议，没有身份；后者是运行时已经接管、参数已经确定的动作。两者混同时，一次函数调用就同时承担提议、授权与执行事实三个角色，系统无法区分「这是新请求，还是上一个动作的继续」——这正是 [[8.困难以及应对办法]] 演化出调用实例的起点。

**工具请求** 是类型化后的提议，只含业务参数（`draft_id`、`draft_version` 这类）；`user_id`、`task_id`、`run_id` 等执行身份由运行时上下文注入，模型不可伪造（分离设计见 [[4.统一 Tool Runtime#工具请求与运行时上下文分离]]）。

**工具调用实例（I300）** 是一次由运行时接管的逻辑业务动作。由 `ToolRuntime.prepare()` 创建，从创建存活到 `SUCCEEDED` / `FAILED` / `REJECTED`，可以跨越人工介入、重试与任务恢复——这是它区别于 Tool Call 的地方。DailyPlan 场景下的具体化结构（字段沿用 [[7.Tool Result 与错误协议#执行记录与工具结果分离]]）：

```python
class ToolInvocation:
    invocation_id: str        # I300：稳定身份，卡片、恢复校验链、执行、业务幂等都引用它
    task_id: str              # T100：属于哪个任务
    created_run_id: str       # R1：最初创建它的 Run；实例跨 Run 稳定，此字段不再变化
    caller: str               # daily_plan_workflow：谁提出的动作
    tool_name: str            # replace_workout_plan：要执行的工具
    status: str               # PENDING / EXECUTING / SUCCEEDED / FAILED：执行状态
    arguments_snapshot: dict  # 冻结的执行参数 {"draft_id": "D200", "draft_version": 3}：
                              # 恢复后执行靠它还原动作，digest 只能证明参数未变、不能还原参数
    request_digest: str       # 关键参数摘要：绑定「批准的就是这个动作」，用于完整性校验
    idempotency_key: str      # 幂等令牌：第一次真实执行前生成，重试与重放复用
    approval_state: str       # WAITING_APPROVAL / APPROVED / REJECTED：人工审批状态
    attempt_count: int        # 已发生的真实执行尝试次数
    effect: dict | None       # 真实造成的业务变化，成功后写入
    error: dict | None        # 结构化错误，最终失败时写入
```

`status` 与 `approval_state` 是两个维度：前者描述执行到哪一步，后者描述人工审批到哪一步。「已批准但未执行」「等待批准」「执行中」都靠两者的组合表达，单用一个字段无法区分「用户没确认」和「确认了但还没跑」。

**执行记录（ExecutionRecord）** 是一次真实执行尝试的记录，由工具运行时在每次尝试开始时创建；一条记录对应恰好一次尝试，失败重试产生第二条记录而不是修改第一条。调用实例不等于执行尝试（Invocation ≠ Attempt）：调用实例是逻辑动作，只有一个；执行尝试是物理执行，可以有多次。两者混同要么丢失「同一动作试了几次」的事实，要么把重试当成新动作——每次重试换一个幂等令牌，业务重复写入由此产生。执行记录内含本次尝试实际发生的 `run_id`（Attempt 级归属，见 [[7.Tool Result 与错误协议#执行记录与工具结果分离]]）。

**业务效果** 是领域服务提交进业务数据库的正式变化，通过 `source_invocation_id = I300` 与调用实例绑定。四类对象里只有它是「对外真实」的：前三个都是 Harness 内部状态，删掉重建不影响用户已生效的计划；业务效果一旦产生，就是用户可见的正式事实。

## prepare：动作在确认之前固定

`prepare_invocation` 节点把工具请求交给 `ToolRuntime.prepare()`：

```python
def prepare(req: ToolRequest, ctx: RuntimeContext) -> ToolInvocation:
    key = (ctx.task_id, req.node_intent,         # 节点意图：每日计划的保存动作
           req.arguments["draft_id"],
           req.arguments["draft_version"])
    if (inv := find_invocation(key)):            # 已存在：节点重放场景，直接复用
        return inv
    return create_invocation(                    # 首次创建：
        invocation_id=new_id(),                  #   I300
        task_id=ctx.task_id,                     #   T100
        created_run_id=ctx.run_id,               #   R1
        tool_name=req.tool_name,                 #   replace_workout_plan
        arguments_snapshot=freeze(req.arguments),#   {"draft_id": "D200", "draft_version": 3} 冻结参数
        request_digest=digest(req.arguments),    #   参数摘要
        idempotency_key=new_key(),               #   幂等令牌在第一次真实执行前生成
        approval_state="WAITING_APPROVAL",       #   副作用动作：等待人工确认
        status="PENDING",
    )
```

get_or_create 的键设计针对节点重放（I300 已创建、检查点未保存的异常场景，推导见 [[10.代码级逻辑：跨请求的任务暂停与恢复]]），保证重放不产生 I301。

冻结参数保存两份表达：`arguments_snapshot` 与 `request_digest` 分工不同。digest 是摘要，只能证明参数没有变，不能从它还原参数；任务等待确认可能跨越数小时甚至一次服务重启，第二天恢复执行时，运行时必须能从调用实例本身还原「replace 哪个计划、哪个版本」——这靠 snapshot，不靠摘要。

为什么必须在人工介入之前创建，而不是等用户确认以后再重新生成工具调用：用户应该确认一个已经确定的动作。确认之后再生成，意味着批准与执行之间还存在一次模型输出——用户批准的是「替换为 D200 v3」，重新生成后执行的可能是参数已经漂移的动作；[[5.护栏#执行护栏]] 中「避免用户批准 A 后智能体又重新生成 B」约束的就是这个窗口。prepare 之后，动作参数、幂等令牌、审批对象全部固定，确认与执行之间不再有任何重新解释的空间。

## 与第一章 HIL 的接口

调用实例与任务生命周期在三个点交接：

1. **prepare 产生审批状态**：工具描述符声明 `approval_policy = EXPLICIT_CONFIRMATION`（替换训练计划这类直接修改正式业务数据的写操作），运行时据此决定走人工介入，而不是由智能体自己判断「这个操作看起来危险」（见 [[5.护栏#执行护栏]]）。
2. **中断载荷与卡片携带 `invocation_id`**：第一章的中断载荷与确认卡片把它原样带给用户，用户点击后原样带回。
3. **恢复校验链校验调用实例**：任务控制器在第⑤～⑧步确认 I300 属于 T100、仍在等待批准、冻结参数仍指向 D200 v3、等待期间业务前置条件未变（校验链全文见 [[10.代码级逻辑：跨请求的任务暂停与恢复]]）。通过后，`I300.approval_state → APPROVED` 与任务 OCC 推进、R2 登记写在同一次恢复受理事务中——批准状态的落点在第一章的受理事务，不在本篇执行链里。

另有一条时间带来的约束：确认可能间隔很久，批准后执行前运行时要复查业务前置条件——审批时正式计划还是版本 12，执行前已被其他任务更新到 13，此时返回 `CONFLICT` 而不是执行过时写入（见 [[5.护栏#执行护栏]]）。

## execute：一次执行尝试的完整链路

R2 从检查点恢复后到达 `execute_invocation`，整条链路按步骤标注谁执行、谁写什么：

```text
execute_invocation(state.invocation_id = I300)
    ↓
ToolRuntime.execute(I300)
    ├── ① 执行护栏复查：调用者 / 用户范围 / 领域权限；参数结构校验
    ├── ② 业务前置条件复查：正式计划版本仍匹配、D200 仍待提交
    │       不匹配 → ToolResult(CONFLICT)，不执行
    ├── ③ 创建执行记录 Attempt 1（run_id = R2）
    ├── ④ WorkoutService.replace_plan(           # 领域服务（示意命名）执行业务写入
    │       args = I300.arguments_snapshot,      # 按冻结参数执行，不重新生成
    │       source_invocation_id = I300,          # 业务幂等绑定
    │       idempotency_key = K1)                 # 与调用实例相同的幂等令牌
    ├── ⑤ 业务数据库事务提交：正式计划替换为新版本（12 → 13）
    ├── ⑥ 核验：当前计划内容 == D200 v3，且 source_invocation_id = I300 已登记
    ├── ⑦ 执行记录补全：execution_status = SUCCEEDED，effect 写入
    └── ⑧ 返回 ToolResult(status = SUCCEEDED, effect = {...})
    ↓
complete_task：D200 → COMMITTED（草稿存储）；T100 → COMPLETED（控制索引，OCC 更新）
```

各步骤的写入归属：④⑤ 是领域服务与业务数据库的事，运行时不代写；⑥⑦ 是运行时写执行记录；`complete_task` 由图收尾节点写控制层两处状态。顺序约束：T100 只能在业务提交成功之后进入 `COMPLETED`——检查点记录「图执行到保存节点」永远不等于业务事实成立（分层语义见 [[5.Task Runtime、Checkpoint 和业务状态#四层状态分层]]）。

失败分叉按位置不同：④ 之前失败，业务无变化，I300 保持待执行，按结构化错误类型决定重试或返回（错误分类见 [[7.Tool Result 与错误协议#结构化错误]]）；⑤ 事务失败回滚，业务无变化，可用同一 I300 与同一幂等令牌发起 Attempt 2；⑥⑦⑧ 之间进程崩溃，业务已变化但运行时没有记上——这是最关键的窗口，下一节展开。

## 副作用只发生一次：失败窗口与三者分工

窗口场景：

```text
I300 → replace_plan()
    ↓
⑤ 业务数据库 COMMIT 成功（计划已替换，source_invocation_id = I300 已写入业务库）
    ↓
进程在 ⑦/⑧（执行记录补全、返回结果）之前崩溃
    ↓
运行时视角：I300 无成功记录 → 认为本次执行没有正常完成
    ↓
任务恢复，图重放 execute_invocation
```

此时如果简单地再次执行 `replace_plan`，正式业务数据可能被再改一次。防线在业务侧幂等——用唯一约束表达「一个调用实例最多产生一个正式业务效果」：

```sql
-- 业务库示意：把调用实例身份登记到被它修改的业务行上
ALTER TABLE workout_plan
    ADD COLUMN source_invocation_id UUID;          -- 本次替换动作的来源调用实例

CREATE UNIQUE INDEX uq_one_effect_per_invocation
    ON workout_plan(source_invocation_id);         -- 同一调用实例最多产生一个正式效果
```

重放路径：

```text
Runtime 再次执行 I300（同一 idempotency_key = K1）
    ↓
WorkoutService 识别 I300 已生效（唯一约束命中 / 效果账本已有记录）
    ↓
返回已有效果（版本 13、当前计划内容）
    ↓
运行时补写执行记录：Attempt 2 = SUCCEEDED（复用已有效果）
    ↓
I300 → SUCCEEDED，不发生第二次业务写入
```

三个机制在这里缺一不可：

- **只有检查点**：能回到 `execute_invocation`，但重放会再次执行写入。检查点只保证「从哪里继续」，它对业务数据库里已经发生了什么一无所知。
- **只有调用实例**：知道动作身份与尝试次数，但业务库若不认识 `source_invocation_id`，重试仍会落成第二次真实写入——身份在 Harness 内部，副作用在业务库里，两边必须用同一个标识接上。
- **只有业务幂等**：能识别重复提交，但没有检查点就无法回到正确的执行位置，没有调用实例就没有跨等待期稳定传递的 `source_invocation_id` 可供业务侧识别。

所以第一章与第四章在这句话上会合：检查点负责图从哪里继续，调用实例负责动作身份与尝试事实，业务侧幂等负责最终只有一个正式效果。三者各管一段，谁也不能替谁兜底。

## 状态推进联动

调用实例、执行尝试与业务效果在各时点的推进：

| 时点 | 调用实例 I300 | 执行记录 | 业务效果 |
| --- | --- | --- | --- |
| prepare 之后 | WAITING_APPROVAL / PENDING | 无 | 无 |
| 恢复校验通过 | APPROVED / PENDING | 无 | 无 |
| 尝试执行中 | APPROVED / EXECUTING | Attempt 1 EXECUTING | 无 |
| 提交成功、记录前崩溃 | 仍 EXECUTING | 缺失（进程未及写入） | 已产生（版本 13） |
| 重放识别已生效 | SUCCEEDED | Attempt 2 SUCCEEDED（复用已有效果） | 不再新增 |

任务、Run、草稿同一时间线的完整状态表见 [[10.代码级逻辑：跨请求的任务暂停与恢复#状态变化总表]]。

## 第四章代码级理解总结

提议、调用实例、执行尝试、业务效果四层各自承担什么、为什么不能合并：

- **提议与调用实例不能合并**。合并后无法区分「模型想做什么」与「系统承诺执行什么」，人工介入没有可绑定的确认对象——用户确认的必须是一个参数已固化的动作，而不是一段模型输出。
- **调用实例与执行尝试不能合并**。合并后要么丢失重试事实（尝试次数、每次的错误），要么把每次重试当成新动作换幂等令牌，业务重复写入由此产生。一个动作一个身份，多次尝试多条记录。
- **执行尝试与业务效果不能合并**。把「执行成功」直接当「业务已变化」在崩溃窗口里正好相反：业务已变化、执行未记成功。业务效果必须由业务侧自己登记（`source_invocation_id`），运行时的记录只描述尝试，不定义事实。
- 四层的职责一句话：提议表达意图，调用实例承载身份与审批，执行尝试记录物理执行，业务效果是对外的正式事实。

与第一章的分工：第一章保证任务跨请求存续（暂停、恢复、校验），第四章保证动作落地安全（受理、护栏、幂等、核验）。`prepare_invocation` 创建 I300、卡片携带 I300 确认、`execute_invocation` 执行 I300，这三步是两章共用的骨架。

## 边界问答

**1. Q：** 为什么同时要 `arguments_snapshot` 和 `request_digest`，只留一个行不行？

**A：** digest 是完整性凭据，恢复后无法从摘要还原要执行什么；snapshot 是恢复后执行的参数来源，但摘要比对能发现「批准时的参数与执行时的参数不一致」这类漂移。一个负责还原动作，一个负责校验一致，职责互补。

**2. Q：** 幂等令牌为什么在第一次真实执行之前生成，而不是失败后补？

**A：** 失败可能发生在任何时点，包括「已写入、未回报」的窗口；事后补令牌时副作用可能已经发生。第一次执行前随调用实例生成，重试与重放天然复用同一身份（见 [[6.可靠执行#幂等]]）。

**3. Q：** 执行护栏在 prepare 阶段查过一次，执行前为什么还要复查？

**A：** 人工确认可能间隔很久，业务状态在此期间可能变化：计划版本被推进、草稿被废弃。复查发现不匹配返回 `CONFLICT`，让上层重新决策，而不是执行一个批准时有效、执行时已过时的动作（见 [[5.护栏#执行护栏]]）。

**4. Q：** 业务写入成功但执行记录没写上，为什么不算「调用实例失败」？

**A：** 调用实例的成败以业务效果为准。执行记录缺失只说明运行时没来得及记账；重放时通过业务侧幂等识别已有效果并补记。这正是执行尝试与业务效果必须分开记录的原因。

**5. Q：** `execute_invocation` 为什么不让模型重新发起一次工具调用？

**A：** 这一段是确定性工作流节点，动作已在 prepare 阶段固定。让模型再次提议，等于在批准与执行之间重新引入一次模型输出，确认对象与执行对象可能脱钩——恢复的语义是继续原动作，不是重新决策。
