# 工具能力设计与工具面

## 五类工具

系统按能力用途把工具划分为五类：感知工具、执行工具、协作工具、用户沟通工具和事件触发工具。这一分类主要服务于工具面的设计，不要求五类能力在当前项目中具有相同的工程复杂度。

- **感知工具**：负责让智能体获取当前业务系统或领域知识中的事实，例如读取当前训练计划、查询历史训练记录、读取饮食日志、检索动作知识。它们不会主动改变业务状态，是训练智能体（Workout Agent）和饮食智能体（Diet Agent）当前最常使用的一类工具。感知工具的返回结果需要保留结构化数据和来源信息，从而能继续被第三章的证据装配（Evidence Assembly，把四类数据统一成下游可用的证据，见 [[9.证据装配与失败语义]]）使用，而不是退化成一段无法追溯来源的自然语言。
- **执行工具**：负责改变真实业务状态，例如记录一次训练、修改当前训练计划、更新饮食日志、保存新的营养计划。由于这类工具会产生持久化副作用，它们是工具运行时中安全与可靠性要求最高的一类能力，需要进一步处理权限、业务规则、人工确认、幂等、重试和结果核验。
- **协作工具**：用于向其他领域智能体提交结构化任务或获取结构化产物。例如会话主管（Supervisor）可以通过协作能力发起训练或饮食领域的领域任务（DomainTask），但协作工具本身不会重新定义第五章已经确定的智能体协作协议。真正的跨智能体数据边界仍然是领域任务和类型化产物（Typed Artifact，见 [[6.通信协议与 Artifact]]），而不是让智能体通过自由文本消息共享内部上下文。
- **用户沟通工具**：只用于具有明确运行时语义的交互，例如请求用户确认一个高风险动作。普通对话回复不需要被包装成工具。
- **事件触发工具**：当前只保留轻量能力边界。未来当训练提醒、设备同步、后台任务完成等事件驱动需求增加以后，再扩展为更完整的事件触发机制。

上述划分与教材把感知、执行、协作、用户沟通和事件触发作为不同工具能力形态一致；本项目只实现当前业务真正需要的部分。

## 工具面按领域隔离

工具注册表（保存系统里所有工具元数据的地方）中可以存在完整工具集合，但模型每次能够看到的工具面由当前智能体和当前任务决定。工具面就是「当前模型这一次能调用的工具集合」。

```text
会话主管
→ 共享 / 编排能力

训练智能体
→ 训练专用工具

饮食智能体
→ 饮食专用工具
```

这种隔离首先降低模型错误选工具和跨领域误操作的概率，同时减少模型上下文中的工具描述数量。但「模型看不到某个工具」只能算能力披露层面的约束，不能作为真正的权限控制。即使模型错误地产生了一个未暴露工具的调用请求，工具运行时仍然必须再次检查调用者身份和权限。

## 工具采用业务能力接口

智能体面向的是业务动作，不直接获得数据库、HTTP 接口、命令行等通用基础设施能力。例如系统提供：

```text
get_current_workout_plan(...)
replace_workout_plan(...)
log_workout_session(...)
```

而不会向训练智能体暴露：

```text
execute_sql(...)
call_http(...)
update_table(...)
```

工具适配器（负责把结构化工具请求翻译成对具体服务的调用）内部可以继续调用训练服务、饮食服务、对象关系映射（ORM）或外部接口（API），但这些基础设施细节不进入智能体的动作空间。

这种设计能显著缩小模型可控制的参数空间，使权限、业务规则和审计都能够围绕明确业务动作建立。SQL 注入等风险首先通过「不向模型开放任意 SQL」来降低，而不是主要依赖危险字符串黑名单。

## 工具参数保持语义保真

工具对智能体暴露的参数语义必须和真实执行语义保持一致。运行时可以进行必要的协议级规范化，例如将国际标准（ISO）日期字符串转换为内部 `datetime`，或者在单位已经明确的前提下把分钟转换为下游接口所需的秒数，但不得在模型不可见的情况下改变业务含义。

例如下面的转换不允许发生：

```text
智能体请求：
每周 5 天训练计划

运行时：
判断 4 天更合理
→ 静默修改成 4 天
```

如果目标对象不存在，也不能自动选择一个「最接近」的业务对象继续执行。运行时应返回结构化错误，让智能体根据真实系统状态重新决策。

因此工具请求、真实执行动作和最终工具结果三者必须保持业务语义一致。模型看到的动作空间不能和工具实际作用的世界存在系统性偏差，否则智能体的理解与真实系统状态会脱节。

## 工具描述符同时服务模型与运行时

工具注册表中保存的不只是函数名和 JSON Schema（参数结构定义），而是完整的工具描述符。描述符可以同时派生模型可见定义和运行时内部策略。

```python
class ToolDescriptor:
    name: str                     # 工具唯一名称，模型与运行时共同引用
    version: str                  # 工具版本，用于变更追踪与适配

    owner_domain: str             # 归属领域，如 workout / diet
    allowed_callers: set[str]     # 允许调用该工具的调用者集合（权限依据）

    input_schema: type            # 输入参数的结构定义，用于结构校验
    output_schema: type           # 输出结果的结构定义，用于输出校验

    operation_type: str           # 操作类型，区分感知 / 执行等

    permission_policy: str        # 权限策略，执行护栏使用的调用资格规则
    approval_policy: str          # 是否以及何时需要人工确认（NONE / EXPLICIT_CONFIRMATION）
    idempotency_policy: str       # 幂等策略，决定能否安全重试
    timeout_policy: str           # 该工具允许的执行超时
    retry_policy: str             # 失败后的重试规则

    adapter: ToolAdapter          # 工具适配器，负责真正调用领域服务
```

模型侧只需要看到：

```text
name
description
input schema
必要的调用说明
```

而：

```text
owner_domain
allowed_callers
approval_policy
idempotency_policy
timeout_policy
retry_policy
adapter
```

属于运行时内部策略，不依赖提示词向模型解释，也不能由模型覆盖。这样策略在运行时侧集中定义，模型拿到的只是一份「如何调用」的裁剪视图。

## 边界问答

**1. Q：** 为什么「模型看不到某个工具」不能算权限控制？

**A：** 它只是能力披露层面的约束。模型仍可能错误地产生一个未暴露工具的调用请求，所以工具运行时仍必须再次检查调用者身份和权限。「看不到」降低的是误选概率，不是授权判断。

**2. Q：** 为什么不把 SQL、HTTP、命令行直接暴露给智能体？

**A：** 智能体面向业务动作而非基础设施能力。业务能力接口显著缩小模型可控制的参数空间，让权限、业务规则、审计都能围绕明确业务动作建立；SQL 注入等风险先通过「不向模型开放任意 SQL」来降低，而不是主要依赖危险字符串黑名单。

**3. Q：** 为什么只能做协议级规范化，不能改业务含义？

**A：** 参数语义必须和真实执行语义一致。若运行时在模型不可见的情况下改变业务含义（例如把每周 5 天静默改成 4 天），模型看到的动作空间就和工具实际作用的世界产生系统性偏差，智能体会基于错误前提继续决策。结构合理、语义一致的转换可以，悄悄篡改不行。

**4. Q：** 工具描述符为什么要由一套数据同时派生出模型视图和运行时策略？

**A：** 模型只需要「如何调用」；调用的资格、审批、幂等、超时、重试和适配属于运行时内部策略，不应依赖提示词讲解也不应被模型覆盖。用一份描述符同时派生两侧，能让模型的可见定义与运行时的强制策略保持同一来源，避免两边不一致。
