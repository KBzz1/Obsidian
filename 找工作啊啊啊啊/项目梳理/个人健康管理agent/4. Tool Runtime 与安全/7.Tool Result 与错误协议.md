# 工具结果与错误协议

工具运行时执行结束以后，不直接把适配器的原始响应交给智能体，而是在内部执行记录和智能体可见结果之间建立清晰边界：

```text
真实工具执行
        ↓
执行记录
        ↓
结果规范化
        ↓
输出护栏
        ↓
工具结果
        ↓
当前智能体 / 工作流
```

## 执行记录与工具结果分离

执行记录是 Harness 内部对一次真实执行的记录，用于可靠执行、任务恢复、审计和后续可观测性；工具结果是经过标准化和输出护栏以后，智能体当前任务真正需要看到的结果。两者不能直接等同。

执行记录可能包含：

```text
invocation_id
tool_name
tool_version

task_id
run_id
caller
user_scope

request_digest
idempotency_key

approval_state

started_at
finished_at
attempt_count

execution_status

raw_result
internal_error

effect
trace_id
```

执行记录与执行尝试一一对应：它不是调用实例整个生命周期的聚合记录，同一调用实例每次真实执行尝试各产生一条执行记录。`attempt_count` 表示本次尝试的序号；`run_id` 记录本次尝试实际发生的 Run——一次尝试恰好落在一个 Run 内，而调用实例可以跨 Run 存在，`created_run_id` 保持不变（见 [[4.统一 Tool Runtime#工具调用只是提议]]）。

其中内部错误栈、系统服务名称、令牌、调试字段等不应直接进入大模型上下文。

普通感知工具不需要为每次调用都建立强持久化执行表，可以依靠结构化日志 / 追踪（保存调用信息而不必单独建表）保存调用信息。真正需要可持久化调用实例的是具有副作用的工具，因为它们需要跨越人工介入、幂等、重试和任务恢复维持稳定的逻辑执行身份。

一个轻量的副作用调用实例可以保存：

```python
class ToolInvocation:
    invocation_id: str       # 调用实例唯一身份，稳定跨越重试与恢复
    task_id: str             # 所属任务
    created_run_id: str      # 最初创建该实例的 Run，实例跨 Run 稳定，此字段不再变化
    caller: str              # 提出调用的智能体，如 workout_agent / supervisor
    tool_name: str           # 工具名称

    status: str              # 当前执行状态，如 pending / executing / succeeded / failed

    request_digest: str      # 关键业务参数的摘要，用于绑定批准/执行的实际动作
    idempotency_key: str     # 幂等令牌，重复提交时复用

    approval_state: str | None  # 人工审批状态
    attempt_count: int       # 真实执行尝试次数

    effect: dict | None      # 真实造成的业务变化
    error: dict | None       # 结构化错误信息
```

其中 `request_digest` 用于绑定需要执行或已经批准的关键业务参数，防止人工介入前后的实际执行动作发生不可见变化。

调用实例可以跨越多次连续执行（Run）存在：`created_run_id` 记录实例最初被创建的 Run，之后不再变化；每一次执行尝试在执行记录中记录自己实际发生的 `run_id`（Run 的身份语义见 [[4.Conversation 与 Task 生命周期#任务与 Run]]）。

## 标准工具结果

工具结果保持相对简单：

```text
ToolResult

status
data
effect
source
error
```

`data` 主要描述感知工具读取到的业务事实，例如当前的训练计划、训练历史或知识检索结果。

`effect` 主要描述执行工具真实造成的业务变化，例如：

```text
operation = replace
entity_type = workout_plan
entity_id = wp_18
previous_version = 12
new_version = 13
```

执行工具不能只返回：

```text
success = true
```

因为智能体需要知道真实系统最终发生了什么，而不能把自己的原始工具调用当成已发生事实。

`source` 保留结果的基本来源：

```text
source_type
entity_type
entity_id
version
observed_at
```

这样第三章可以继续把业务工具结果转换为证据包（见 [[9.证据装配与失败语义]]），同时保留来源、时效和来源追溯信息。

## 结构化错误

工具错误同样不直接以异常字符串的方式进入智能体，而是统一成有限的结构化错误类型。

当前项目使用：

```text
VALIDATION_ERROR

PERMISSION_DENIED

BUSINESS_RULE_VIOLATION

CONFLICT

TIMEOUT

DEPENDENCY_ERROR

INTERNAL_ERROR
```

`VALIDATION_ERROR` 表示工具请求本身不符合结构或参数规则；`PERMISSION_DENIED` 表示当前调用者、用户范围或领域不允许执行；`BUSINESS_RULE_VIOLATION` 表示参数合法但当前业务状态不允许该动作；`CONFLICT` 表示智能体使用的状态已经过期，例如预期计划版本为 12，但真实当前版本已经变成 13。

运行时可以为结构化错误附带有限的恢复提示：

```text
FIX_REQUEST
REPLAN
ASK_USER
STOP
```

该字段只描述系统语义上的恢复方向，不允许智能体绕过运行时已经做出的权限或业务规则判断。

运行时内部能够安全重试的异常会在工具结果返回之前处理完成，因此智能体得到的是一次逻辑工具调用实例的最终状态，而不是每一次内部执行尝试的原始错误。

## 工具结果的可见性

工具结果默认只属于：

```text
当前工具调用实例
→ 当前任务
→ 当前智能体
```

训练智能体（Workout Agent）查询到的原始工具结果不自动广播给会话主管（Supervisor）或饮食智能体（Diet Agent）。

如果结果需要进入跨智能体协作，需要先由当前领域智能体形成第五章定义的类型化产物：

```text
工具结果
    ↓
当前领域智能体
    ↓
类型化产物
    ↓
会话主管 / 其他领域智能体
```

工具运行时因此不会成为新的共享上下文通道。

## 边界问答

**1. Q：** 为什么执行记录和工具结果要分开？

**A：** 执行记录是 Harness 内部对一次真实执行的记录，用于可靠执行、任务恢复、审计和可观测性，可能包含内部错误栈、系统服务名、令牌、调试字段；工具结果是经过标准化和输出护栏后的智能体可见结果。两者用途不同，内部细节不应进入大模型上下文，所以不能等同。

**2. Q：** 为什么工具结果的 `effect` 比一个 `success = true` 更重要？

**A：** 智能体需要知道真实系统最终发生了什么，而不能把自己的原始工具调用当成已发生事实。`effect` 携带 `operation`、`entity_type`、`entity_id`、`previous_version`、`new_version`，让后续推理建立在真实执行结果上，而不是建立在自己的原始调用意图上。

**3. Q：** 为什么错误要统一成结构化类型，而不是直接抛异常字符串？

**A：** 结构化错误让智能体得到可判断、可处理的有限状态（参数错、权限拒绝、业务规则不满足、冲突、超时等），并能附带有限的恢复方向；同时避免原始堆栈、服务名或敏感信息进入上下文，也防止智能体绕过运行时已经做出的权限或业务规则判断。

**4. Q：** 为什么工具结果默认不广播给其他智能体？

**A：** 工具结果默认属于当前调用实例、当前任务、当前智能体。若需跨智能体协作，须先由当前领域智能体把它收敛成第五章的类型化产物再移交。因此工具运行时不会成为新的共享上下文通道，避免绕过既有的跨域数据边界。
