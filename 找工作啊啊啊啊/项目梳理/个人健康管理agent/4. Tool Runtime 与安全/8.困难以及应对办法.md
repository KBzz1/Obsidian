# 困难以及应对办法

这次演化只围绕一个问题展开：早期系统把大模型生成的工具调用同时当成「智能体的动作提议」和「可以直接执行的业务命令」，随着任务开始涉及真实业务写入、人工确认和失败恢复，这两种语义逐渐无法继续混在一起。

## 旧设计：函数调用直接连接业务函数

项目早期的工具调用比较直接。训练智能体（Workout Agent）或饮食智能体（Diet Agent）根据当前上下文产生函数调用，框架完成参数解析以后直接进入对应的 Python 工具，再由工具调用领域服务：

```text
大模型
 ↓
函数调用
 ↓
Python 工具
 ↓
训练 / 饮食服务
 ↓
业务数据库
```

例如训练智能体需要替换当前训练计划时，可以产生：

```text
replace_workout_plan(
    plan_id="plan_18",
    effective_date="..."
)
```

Python 工具内部完成基础参数校验，再调用训练服务修改数据库。

这种设计在第一版是合理的。当工具主要承担查询和少量简单写入时，一次函数调用基本可以同时表示：

```text
智能体决定调用某项能力
+
系统立即执行这个动作
```

因此没有必要为一次工具调用额外建立独立生命周期。

问题是在任务逐渐变长、真实业务写入增加以后，这个假设不再成立。

## 困难：一次工具调用开始拥有多个不同状态

以「替换当前训练计划」为例。随着系统增加真实业务约束，一次调用不再总是：

```text
模型生成
→ 立即执行
→ 返回结果
```

它可能经历：

```text
智能体提出替换计划
       ↓
需要人工确认
       ↓
任务暂停
       ↓
用户稍后确认
       ↓
任务恢复
       ↓
执行工具
```

执行过程中又可能出现网络超时：

```text
工具执行
   ↓
超时
   ↓
运行时重试
```

而 ReAct 智能体（推理-行动循环，见第五章 [[5.Domain Agent 执行模型]]）本身在看到失败结果以后，也可能重新提出一次相同或相近的工具调用。

这时原来的：

```text
replace_workout_plan(...)
```

开始同时承担几种完全不同的语义：

```text
模型建议执行这个动作

用户是否已经批准这个动作

运行时是否已经接受这个动作

这个动作是否已经尝试执行

真实业务系统是否已经发生变化
```

如果仍然只把函数调用当成系统中的唯一动作对象，Harness 很难准确回答：

> 当前看到的这次工具调用，到底是一个新的业务动作，还是上一次动作恢复后的继续执行？

这也是后续人工介入（Human-in-the-Loop，见 [[5.护栏#执行护栏]]）、幂等和任务恢复开始互相缠绕的地方。

## Harness 层根因：提议与执行没有分离

最开始比较容易采取的办法，是继续在 Python 工具周围增加逻辑：

```text
函数调用
   ↓
参数检查
   ↓
权限检查
   ↓
必要时询问用户
   ↓
重试
   ↓
Python 函数
```

但这些补丁没有解决最根本的问题。因为系统仍然把：

```text
大模型工具调用
```

当成了唯一的动作身份。

模型输出本身是不稳定的。一次任务暂停再恢复以后，智能体可以重新生成工具调用；一次执行失败以后，ReAct 也可以再次调用同一个工具。即使两个工具调用看起来参数相同，它们在业务上可能是同一个动作的重试，也可能是用户后来要求执行的第二个新动作。仅凭函数调用本身无法稳定区分。

同样，人工确认如果只是存在会话历史里的：

```text
“是否确认修改？”
“确认。”
```

运行时也无法严格证明用户批准的是哪一组最终参数。

因此问题并不是 Python 工具少了几个校验函数，而是 Harness 缺少一个位于模型决策和真实业务副作用之间的稳定执行对象。

## 改造：把工具调用降级为动作提议

新的设计首先改变工具调用的语义。大模型或工作流产生的调用统一被视为工具提议，表示「上游希望系统执行某项能力」。提议随后转换成结构化工具请求（机制见 [[4.统一 Tool Runtime#工具调用只是提议]]）：

```text
智能体 / 工作流
       ↓
工具提议
       ↓
类型化工具请求
       ↓
工具运行时
```

工具请求中只包含智能体有权决定的业务参数，例如：

```text
tool_name:
replace_workout_plan

arguments:
plan_id
effective_date
```

而 `user_id`、`caller_agent`、`task_id`、`domain`、`permission` 由 Harness 根据当前可信运行状态注入 `RuntimeContext`。

因此智能体只能表达「我希望做什么」，不能通过工具参数决定「我是谁、我代表谁、我有什么权限」。

## 副作用操作引入稳定的工具调用实例

对于真正产生业务副作用的工具，工具运行时在接受请求以后创建一个稳定的工具调用实例：

```text
工具请求
   ↓
工具运行时
   ↓
工具调用实例
```

这里的调用实例表示「运行时正在管理的一个逻辑业务动作」。例如一次替换训练计划的调用实例可以保存：

```text
invocation_id
task_id
tool_name

request_digest
idempotency_key

approval_state
attempt_count

effect
error
```

这样人工确认、重试和任务恢复不再围绕一条大模型消息工作，而是围绕同一个调用实例工作。

## 人工介入从「确认一句话」变成「确认一个具体动作」

旧方法里，人工确认很容易写成：

```text
智能体：
是否确认替换当前计划？

用户：
确认。

智能体：
再次生成 replace_workout_plan(...)
```

这个过程中，用户确认的对象和真正执行的第二次工具调用并没有强绑定关系。

新设计中，运行时先固化实际待执行动作：

```text
工具调用实例
    ↓
工具
目标对象
规范化参数
request_digest
```

然后对这个调用实例发起审批请求：

```text
工具调用实例
      ↓
人工介入
      ↓
用户批准
      ↓
继续原调用实例
```

用户批准以后不会让智能体再重新生成一次动作，而是继续原来的调用实例。

如果等待确认期间业务状态已经变化，例如：

```text
审批时：
当前计划版本 = 12

真正恢复时：
当前计划版本 = 13
```

运行时会重新检查关键业务前置条件并返回冲突，而不是使用旧状态强行执行。这样人工介入才真正成为执行授权，而不只是会话中的一次问答。

## 幂等和重试也开始拥有明确归属

引入调用实例后，运行时可以区分一个逻辑业务动作和这个动作的多次执行尝试：

```text
调用实例 I1
   ↓
幂等键 K1
   ↓
执行尝试 1
   ↓
超时
   ↓
执行尝试 2
```

执行尝试 2 仍然属于 I1，因此继续使用相同的幂等键，而不是因为重新调用函数就产生新的业务写入。

这解决了智能体场景中比较特殊的重复来源：

```text
运行时自动重试

智能体自己再次调用

任务恢复后重新进入执行节点
```

运行时可以根据调用实例身份判断这是同一个逻辑动作的继续执行，还是一个新的业务请求。幂等与重试的完整机制见 [[6.可靠执行]]。

## 执行事实和智能体认知进一步分离

旧设计里 Python 工具返回 `success = true` 以后，智能体很容易把自己刚才提出的工具调用直接当成「真实世界已经发生的事实」。新的工具运行时在执行结束以后先记录真实执行记录，再生成标准化工具结果（见 [[7.Tool Result 与错误协议#执行记录与工具结果分离]]）：

```text
工具请求
→ 智能体想做什么

工具调用实例
→ 运行时正在管理什么动作

执行记录
→ 真实系统发生了什么

工具结果
→ 智能体应该知道什么
```

执行工具返回的不只是 `success`，而是明确的效果，例如：

```text
entity_type = workout_plan
entity_id = plan_18

previous_version = 12
new_version = 13
```

这样智能体后续推理建立在真实执行结果上，而不是建立在自己的原始调用意图上。

## 最终形成当前的工具运行时

经过这次调整以后，工具执行链从：

```text
大模型函数调用
      ↓
Python 工具
      ↓
业务系统
```

演化为：

```text
智能体 / 工作流
        ↓
工具提议
        ↓
类型化工具请求
        ↓
工具运行时
        ↓
护栏 / 人工介入
        ↓
工具调用实例
        ↓
可靠执行
        ↓
工具适配器
        ↓
领域服务
        ↓
执行记录
        ↓
输出护栏
        ↓
工具结果
```

这次改造并没有取消函数调用。模型仍然可以使用函数调用表达工具意图，但函数调用不再直接拥有真实业务系统的执行权。

这一变化使权限、人工确认、幂等、重试和实际效果都能够围绕稳定的运行时对象建立，而不是继续挂在一次不稳定的模型输出上。

代价是系统增加了工具注册表、运行时策略、工具调用实例和标准结果协议，副作用工具也需要维护额外的持久化执行状态。对于只有查询和简单无状态工具的智能体，这套结构没有必要；但在当前系统已经包含长期任务、业务数据库、多个领域智能体、人工介入和真实业务写入之后，这些额外状态提供了明确的执行边界，也使工具调用能够在任务中断和故障恢复以后保持一致的业务语义。

## 边界问答

**1. Q：** 最早的「函数调用直接执行」设计为什么一开始是合理的？

**A：** 当工具主要承担查询和少量简单写入时，一次函数调用基本可以同时表示「智能体决定调用某项能力」和「系统立即执行这个动作」，两种语义没有冲突，因此没必要为一次工具调用额外建立独立生命周期。问题在任务变长、真实业务写入增加以后才出现。

**2. Q：** 为什么继续在 Python 工具周围增加校验函数解决不了问题？

**A：** 这些补丁仍然把大模型工具调用当成唯一动作身份。模型输出本身不稳定：暂停恢复后可以重新生成工具调用，执行失败后 ReAct 也可以再次调用同一工具。即使两个工具调用参数相同，业务上可能是同一个动作的重试，也可能是用户后来要求执行的第二个新动作，仅凭函数调用无法稳定区分。

**3. Q：** 为什么要把工具调用降级为工具提议？

**A：** 把大模型或工作流产生的调用统一视为「上游希望系统执行某项能力」的提议，再转换成结构化工具请求。工具请求只包含智能体有权决定的业务参数，执行身份（user_id、caller、domain、permission）由 Harness 注入运行时上下文。这样智能体只能表达「我希望做什么」，不能决定「我是谁、我代表谁、我有什么权限」，权限模型建立在 Harness 可信状态上。

**4. Q：** 工具调用实例解决了什么根本问题？

**A：** 它给一次逻辑业务动作提供了稳定身份。人工确认、重试和任务恢复不再围绕一条大模型消息工作，而是围绕同一个调用实例；运行时可以据此区分「同一逻辑动作的继续执行」和「新的业务请求」，并把人工介入、幂等、重试、实际效果都挂到稳定对象上，而不是挂在不稳定的模型输出上。
