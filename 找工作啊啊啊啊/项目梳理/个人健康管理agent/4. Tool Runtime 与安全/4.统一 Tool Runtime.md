# 统一工具运行时

## 所有真实调用都经过同一运行时

系统中所有需要进入真实业务系统的工具调用都通过统一工具运行时执行。无论调用来自 ReAct 智能体（推理-行动循环，模型交替进行「推理、行动、观察」的执行方式，见第五章 [[5.Domain Agent 执行模型]]）还是确定性工作流节点（按固定步骤顺序执行的节点），执行层使用相同的运行时：

```text
ReAct 智能体 ───────┐
                   │
                   ▼
             工具运行时
                   │
                   ▼
              工具适配器
                   │
                   ▼
             领域服务
                   ▲
                   │
工作流节点 ────────┘
```

因此工具运行时不依赖「大模型函数调用」这一种调用方式。大模型只是工具请求的一种生产者，工作流也可以在稳定标准作业流程（SOP）中确定性地产生工具请求。

## 工具请求与运行时上下文分离

智能体只能提供业务动作参数，而执行身份由 Harness 注入。

例如训练智能体可以提出：

```text
tool_name = replace_workout_plan

arguments:
- plan_id
- effective_date
```

但不能自行提供或修改：

```text
user_id
agent_id
task_id
domain
permission
```

这些信息来自受信任的运行时上下文。

```python
class RuntimeContext:
    user_id: str          # 当前动作所属用户
    task_id: str          # 当前任务标识
    thread_id: str        # 所属线程执行线索

    caller: str           # 调用者身份，如 workout_agent / supervisor
    domain: str           # 归属领域，如 workout / diet

    invocation_source: str  # 动作来源，如 react_agent / workflow_node
```

因此系统形成明确边界：

```text
智能体
→ 决定「想做什么」

Harness
→ 决定「谁在做」
→ 「代表哪个用户做」
→ 「属于哪个领域」
```

这可以防止模型通过工具参数伪造 user_id、调用者身份或领域，从而把权限模型建立在 Harness 的可信状态上，而不是建立在大模型输出上。

## 工具调用只是提议

大模型生成工具调用后，运行时首先构造一个结构化工具请求，而不是立即执行：

```text
大模型 / 工作流
      ↓
工具调用提议
      ↓
类型化工具请求
      ↓
工具运行时
```

工具请求表示「上游希望执行什么」，它本身不代表已经授权，更不代表真实系统已经发生变化。真正的执行语义从运行时接受该请求以后才开始。

对于产生副作用的工具，运行时会进一步创建一个稳定的工具调用实例。调用实例代表一次逻辑业务动作，可以跨越人工介入（Human-in-the-Loop）、重试和任务恢复继续存在。

```text
工具请求
→ 动作提议

工具调用实例
→ 运行时接受并管理的一次逻辑业务动作

执行尝试
→ 调用实例的一次真实执行尝试
```

这种分离避免把模型一次函数调用同时当成「提议、授权和执行事实」。模型输出一个工具调用只是上游的一个愿望；是否被接受、是否被授权、是否真的发生，分别由后续的工具请求、护栏与工具调用实例 / 执行尝试承担。

## 边界问答

**1. Q：** 为什么 ReAct 智能体和工作流节点都要走同一个工具运行时？

**A：** 执行层不依赖「大模型函数调用」这一种调用方式。大模型只是工具请求的一种生产者，工作流也能在稳定标准作业流程中确定性地产生工具请求。统一执行层保证两者经过相同的校验、授权与可靠执行，避免「模型调用」和「流程调用」落到两套不同的执行逻辑。

**2. Q：** 为什么智能体不能自己决定 user_id、domain、permission？

**A：** 这些来自受信任的运行时上下文，由 Harness 根据当前可信运行状态注入，不属于智能体可控制的业务参数。若允许模型通过工具参数伪造 user_id、调用者身份或领域，权限模型就建立在可预测的 Harness 状态之外，变成依赖一堆可能被污染的大模型输出。

**3. Q：** 工具请求和工具调用实例有什么区别？

**A：** 工具请求是一次动作提议，表示「上游希望执行什么」，不代表已授权，更不代表真实系统已经变化。工具调用实例是运行时接受并管理的一次逻辑业务动作，可以跨越人工介入、重试和任务恢复继续存在，是可靠执行、幂等与恢复围绕的稳定对象。

**4. Q：** 为什么要把「提议、授权、执行事实」拆开？

**A：** 一次模型函数调用如果同时承担提议、授权和执行事实，系统就无法稳定区分「这是上一个动作的继续，还是一个新的业务请求」。拆开后每个阶段有明确归属对象，人工介入、幂等、重试和任务恢复才能围绕正确的对象工作。
