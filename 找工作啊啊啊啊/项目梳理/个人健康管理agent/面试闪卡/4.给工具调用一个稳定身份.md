# 面试闪卡 · 第四章：给工具调用一个稳定身份

> [!info] 用法
> 一问一答背诵卡。答案保留冻结术语与 ID；事实以 [[9.代码级逻辑：从提议到业务副作用]] 为准。

## 主问题与边界

> 题源：[[找工作啊啊啊啊/项目梳理/个人健康管理agent/4.给工具调用一个稳定身份/1.总览|1.总览]]、[[9.代码级逻辑：从提议到业务副作用]]

**1. Q：**第四章回答的唯一主问题是什么？主边界怎么表述？

**A：**LLM 说「我要执行这个动作」后，为什么系统不能马上真的执行。主边界：模型提议 ≠ Runtime 接管的动作 ≠ 执行尝试 ≠ 真实业务修改。口号：Agent 只有提议权，Runtime 才有执行权。

**2. Q：**从模型输出到业务事实，四个身份对象是什么？

**A：**
```text
工具调用（Tool Call）        模型输出：「想做什么」——没有身份，不能被恢复引用
    ↓ 运行时接受并类型化
工具请求（Tool Request）     类型化提议：tool_name + 业务参数
    ↓ 副作用动作需要人工确认
工具调用实例（I300）          参数固化、身份稳定、可跨暂停与恢复引用
    ↓ 每次真实执行
执行记录（ExecutionRecord）  一次执行尝试的事实（Attempt 1、2…）
    ↓ 尝试成功
业务效果（Business Effect）  业务库正式变化，source_invocation_id 绑定
```
工具请求只含业务参数（draft_id、draft_version 这类）；user_id / task_id / run_id 等执行身份由运行时上下文注入，模型不可伪造。四类对象里只有业务效果是对外真实的：前三个是 Harness 内部状态，删掉重建不影响用户已生效的计划。

**3. Q：**ToolInvocation 为什么用两维状态？

**A：**status（PENDING / EXECUTING / SUCCEEDED / FAILED）描述执行到哪一步，approval_state（WAITING_APPROVAL / APPROVED / REJECTED）描述人工审批到哪一步。「已批准但未执行」「等待批准」「执行中」都靠两者的组合表达，单用一个字段无法区分「用户没确认」和「确认了但还没跑」。

## 机制与流程

**4. Q：**prepare 的 get_or_create 键是什么？针对什么场景？

**A：**键 =（task_id、节点意图、draft_id、draft_version）。针对节点重放：I300 已创建、检查点未保存的异常场景下，图重放 prepare_invocation 时 I300 已存在就复用，不产生 I301，身份的稳定 reference 保持保证。

**5. Q：**为什么 arguments_snapshot 和 request_digest 要保存两份表达？

**A：**分工互补：digest 是摘要，只能证明「批准时的参数与执行时的参数一致」，不能从它还原参数；snapshot 是冻结的执行参数（{"draft_id": "D200", "draft_version": 3}），任务等待确认可能跨数小时甚至一次服务重启，第二天恢复执行时运行时必须能从调用实例本身还原「replace 哪个计划、哪个版本」——这靠 snapshot，不靠摘要。一个负责校验一致，一个负责还原动作。

**6. Q：**幂等令牌为什么在第一次真实执行之前生成？

**A：**失败可能发生在任何时点，包括「已写入、未回报」的窗口；失败后补令牌时副作用可能已经发生。第一次执行前随调用实例生成，重试与重放天然复用同一身份。

**7. Q：**execute 的八步链是什么？各步骤写入归属？

**A：**
```text
ToolRuntime.execute(I300)
① 执行护栏复查：调用者 / 用户范围 / 领域权限、参数结构校验
② 业务前置条件复查：正式计划版本仍匹配、D200 仍待提交；不匹配 → CONFLICT 不执行
③ 创建执行记录 Attempt 1（run_id = R2）
④ WorkoutService.replace_plan(args=I300.arguments_snapshot,      # 按冻结参数执行
                              source_invocation_id=I300,           # 业务幂等绑定
                              idempotency_key=K1)
⑤ 业务数据库事务提交：正式计划替换为新版本（12 → 13）
⑥ 核验：当前计划内容 == D200 v3，且 source_invocation_id=I300 已登记
⑦ 执行记录补全：SUCCEEDED、effect 写入
⑧ 返回 ToolResult(SUCCEEDED, effect)
    ↓ complete_task：D200 → COMMITTED（草稿存储）；T100 → COMPLETED（控制索引，OCC）
```
④⑤ 是领域服务与业务数据库的事，运行时不代写；⑥⑦ 运行时写执行记录。顺序约束：T100 只能在业务提交成功之后进入 COMPLETED——检查点记录「图执行到保存节点」永远不等于业务事实成立。

**8. Q：**最关键的失败窗口是什么？防线在哪？

**A：**⑤ 业务库 COMMIT 成功后、⑦⑧（补记录、返回结果）之前进程崩溃：业务已变化（版本 13、source_invocation_id 已写入业务库），运行时没有成功记录，任务恢复后图重放 execute_invocation。如果简单地再次执行 replace_plan，业务数据被再改一次。防线是业务侧幂等——SQL 唯一约束：`workout_plan.source_invocation_id` 加唯一索引 `uq_one_effect_per_invocation`，表达「一个调用实例最多产生一个正式业务效果」。重放路径：再次执行 I300（同一幂等令牌 K1）→ 领域服务识别 I300 已生效 → 返回已有效果 → 运行时补写 Attempt 2 = SUCCEEDED（复用已有效果）→ 不发生第二次业务写入。

**9. Q：**检查点、调用实例、业务幂等三者为什么缺一不可？

**A：**只有检查点：能回到 execute_invocation，但重放会再次执行写入——检查点只保证「从哪里继续」，对业务库里已发生什么一无所知。只有调用实例：知道动作身份与尝试次数，但业务库若不认识 source_invocation_id，重试仍落成第二次真实写入——身份在 Harness 内部，副作用在业务库，两边必须用同一个标识接上。只有业务幂等：能识别重复提交，但没有检查点回不到正确执行位置，没有实例就没有跨等待期稳定传递的标识。三者各管一段：检查点管「图从哪里继续」，调用实例管「动作身份与尝试事实」，业务幂等管「最终只有一个正式效果」。

## 身份与状态辨析

**10. Q：**调用实例和执行尝试为什么不能合并（Invocation ≠ Attempt）？

**A：**调用实例是逻辑动作，只有一个；执行尝试是物理执行，可以有多次（一条记录对应恰好一次尝试，失败重试产生第二条而不是修改第一条）。混同的后果：要么丢掉「同一动作试了几次」的事实（尝试次数、每次的错误），要么把重试当成新动作——每次重试换一个幂等令牌，业务重复写入由此产生。一句话：一个动作一个身份，多次尝试多条记录；执行记录内含本次尝试实际发生的 run_id（Attempt 级归属）。

**11. Q：**执行前为什么要复查业务前置条件？

**A：**人工确认可能间隔很久：审批时正式计划还是版本 12，执行前已被其他任务更新到 13，此时返回 CONFLICT 而不是执行过时写入，让上层重新决策。同理，走人工介入的判定来自工具描述符声明 `approval_policy = EXPLICIT_CONFIRMATION`（替换训练计划这类直接修改正式业务数据的写操作），不是智能体自己判断「这个操作看起来危险」。只有副作用工具才进入 HIL / 幂等 / 重试 / 核验链路，查询型工具可以直接执行（早期雏形形态）。

**12. Q：**和第一章的分工与粘合点是什么？

**A：**第一章保证任务跨请求存续（暂停、恢复、校验），第四章保证动作落地安全（受理、护栏、幂等、核验）。粘合点是 I300 的三步：prepare_invocation 创建 → 中断载荷与确认卡片携带 invocation_id → execute_invocation 执行；恢复校验链第⑤～⑧步校验的就是它。恢复后执行的仍是原来那个动作：图从检查点继续，execute_invocation 读图状态里的 invocation_id，全程不重新经历「模型 → 工具调用 → 创建 I301」——模型没有再次介入，不存在第二次提议。

## 困难与演化

> 题源：[[找工作啊啊啊啊/项目梳理/个人健康管理agent/4.给工具调用一个稳定身份/8.困难以及应对办法|8.困难以及应对办法]]

**13. Q：**第四章的演化起点是什么？一次工具调用怎么开始拥有多个状态的？

**A：**旧设计（雏形）：函数调用直接连接业务函数——大模型产生函数调用，框架解析参数后直接进 Python 工具，再调领域服务改数据库。工具只承担查询和少量简单写入时合理：一次函数调用同时表示「智能体决定调用某项能力」+「系统立即执行」，两种语义不冲突。任务变长、真实业务写入增加后，一次调用开始经历：提议 → 需要人工确认 → 任务暂停 → 用户稍后确认 → 任务恢复 → 执行工具；执行中又可能网络超时重试、ReAct 智能体看到失败后再提出相同或相近调用——同一个 replace_workout_plan(...) 同时承担「模型建议执行 / 用户是否批准 / 运行时是否接受 / 是否已尝试执行 / 业务是否已变化」几种完全不同的语义，系统无法回答「这是新动作，还是上一次动作的继续执行」。

**14. Q：**在 Python 工具周围加校验逻辑为什么解决不了？根因是什么？

**A：**参数检查 → 权限检查 → 必要时询问用户 → 重试，这些补丁仍然把大模型工具调用当成唯一的动作身份。模型输出本身不稳定：任务暂停恢复后可以重新生成工具调用，执行失败后 ReAct 可以再次调用同一工具——即使两次调用参数相同，业务上可能是同一动作的重试，也可能是用户后来要求的第二个新动作，仅凭函数调用无法稳定区分。人工确认若只是会话历史里的「是否确认修改？」「确认。」，运行时也无法严格证明用户批准的是哪一组最终参数。根因：Harness 缺少一个位于模型决策和真实业务副作用之间的稳定执行对象。

**15. Q：**改造后语义怎么分化的？代价是什么？

**A：**① 工具调用降级为动作提议：只含业务参数，user_id / caller / task_id / domain / permission 由 Harness 注入运行时上下文——智能体只能表达「我希望做什么」，不能决定「我是谁、我代表谁、我有什么权限」。② 副作用动作创建工具调用实例：人工确认、重试、任务恢复围绕同一个实例工作，不再围绕一条模型消息。③ HIL 从「确认一句话」变成「确认一个具体动作」：批准后继续原实例、不重新生成；等待期业务状态变化（审批时版本 12、执行前已是 13）返回 CONFLICT，人工介入才真正成为执行授权。④ 幂等与重试有归属：同实例同幂等键，运行时能区分运行时自动重试、智能体再次调用、任务恢复重入三种重复来源。⑤ 执行事实与智能体认知分离：执行记录 + 明确效果（如 previous_version 12 → new_version 13），推理建立在真实执行结果上而非自己的调用意图上。代价：工具注册表、运行时策略、调用实例、标准结果协议等额外结构——只有查询和无状态工具的系统没必要上这套。
