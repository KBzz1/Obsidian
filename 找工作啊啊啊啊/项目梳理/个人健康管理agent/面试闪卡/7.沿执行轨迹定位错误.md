# 面试闪卡 · 第七章：沿执行轨迹定位错误

> [!info] 用法
> 一问一答背诵卡。答案保留冻结术语与 ID；事实以 [[12.代码级逻辑：如何沿执行轨迹定位错误]] 为准。第七章只消费前六章已产生的结构化事实，不重新实现它们。

## 主问题与主链

> 题源：[[找工作啊啊啊啊/项目梳理/个人健康管理agent/7.沿执行轨迹定位错误/1.总览|1.总览]]、[[12.代码级逻辑：如何沿执行轨迹定位错误]]

**1. Q：**第七章回答的唯一主问题是什么？

**A：**最终回答错了以后，怎样判断到底是哪一层出了问题。第一～六章是在线 Harness，第七章是质量反馈闭环。最终 Workout Plan 忽略「工作日只能晚练」，可能发生在检索没召回、证据装配丢弃、上下文没装进本轮、模型看到正确事实仍决策错误、工具选错或执行失败、跨智能体交接丢失、最终回复没有忠实描述真实效果——七个位置中的任何一个；只看最终答案无法定位。

**2. Q：**第七章的统一主链是什么？

**A：**
```text
T200 / R1 开始
    ↓ 任务运行时创建 trace_id（一个 Run 一条 Trace）
    ↓ TraceContext 随 RuntimeContext 传播（模块不再自己猜身份）
    ↓ 各工程边界创建 Span（只为有意义的边界建区段）
    ↓ Span 结束时回填结构化 Record 引用（Trace 不复制事实内容）
    ↓ Run 结束 → Trace 完成
    ↓ EvaluationLoader 按 task_id / run_id / trace_id 加载 Runtime Facts
    ↓ TaskExecutionView（评估时临时装配的执行视图）
    ↓ 分层 Evaluator（确定性规则优先，必要时构造 JudgeInput）
    ↓ LayerEvaluationResult（每层独立结果，不是一个总分）
    ↓ FailureAttribution（primary_failure + findings，不强行归成唯一根因）
    ↓ Regression Comparison（与稳定 Baseline 比较）
```

**3. Q：**task_id / run_id / trace_id 三者什么关系？

**A：**task_id 是逻辑任务完整生命周期的稳定身份（T200）；run_id 是一段连续执行的身份，HIL 恢复、后台执行会产生新的 Run；trace_id 是该 Run 对应的观测轨迹身份，Run 创建时生成，一个 Run 一条 Trace。任务跨多段执行时，多个 run_id / trace_id 挂在同一个 task_id 下。同步 DomainTask 没有独立 task / run——它是 T200 内部工作单元，用 domain_task_id 标识、出现在父任务 Trace 中（领域智能体 Span 内嵌套子区段）；后台执行记录 AE500 拥有独立 run_id / trace_id，Span 树建在自己的轨迹上，经 parent_task_id + domain_task_id 挂回 T200 / DT10。

## 观测结构

**4. Q：**TraceSpan 只在哪七类工程边界建？为什么？

**A：**supervisor（编排轮次）、domain_agent（领域智能体执行）、context_assembly（上下文装配）、llm_call（模型调用）、retrieval（检索）、tool_invocation（工具调用）、final_response（最终回复）。普通内部函数不建——否则轨迹膨胀成执行日志，定位错误的信噪比反而下降。

**5. Q：**Span 为什么只存 Record 引用、不复制事实内容？

**A：**Trace 只保存「谁调用谁 + 时间 + 状态 + 引用」，模块真正的事实仍在各章 Record 里；Span 结束时只回填引用身份：Context Span → context_id（第二章清单）；LLM Call Span → llm_call_id + context_id；Retrieval Span → retrieval_id / evidence_bundle_id；Tool Span → invocation_id / execution_record_id；Domain Agent Span → domain_task_id / artifact_refs；必要时引用第六章预算扣减、切片、熔断事件。复制内容会制造两份需要保持一致的数据，事实源不再唯一；评估需要内容时沿引用回 Record 读取——观测不建立第二套 Runtime 数据库。

**6. Q：**LLMCallRecord 和 ContextManifest 各回答什么？怎么挂接？

**A：**ContextManifest 回答「Harness 准备给模型看什么」（哪些证据、事实、产物、工具能力进入本轮）；LLMCallRecord 回答「这次模型调用本身怎么样」：是否成功、实际用的 model_id、prompt_version 与 model_config_version、结构化输出引用、token_usage、error_code。两者经 context_id 关联——第二章统一入口装配出 ModelContext 与清单（同源双产出），调用发生时 LLMCallRecord 记下这个 context_id，「模型被给了什么」与「调用结果如何」在评估时对上。llm_call_id 就是第六章逻辑调用 LC 的身份，一次逻辑调用一条记录、网络重试不新增；output_ref 引用结构化输出（SupervisorAction、Tool Proposal、AgentResult、最终响应），Chain-of-Thought 不保存也不评估。

**7. Q：**TaskExecutionView 是数据库吗？

**A：**不是。它是评估时由 EvaluationLoader 按 task_id / run_id / trace_id 读取并关联出来的临时视图，不落库、不成为新的事实源；里面全是引用身份（runs、traces、context_manifests、llm_calls、retrieval_records、evidence_bundles、tool_invocations、execution_records、domain_tasks、artifacts、final_response_ref）。HIL 暂停产生多个 Run 的任务（T100 的 R1 / R2）被收进同一个 task_id 下，评估看到的是任务全程。

## 归因机制

**8. Q：**七层归因的顺序是什么？为什么不收敛到唯一根因？

**A：**① RetrievalRecord：正确事实有没有被召回；② EvidenceBundle：有没有进入最终证据；③ ContextManifest：该证据 / A100 有没有进入本轮上下文；④ LLMCallRecord：模型是否看到正确上下文后仍做出错误动作；⑤ ToolInvocation / Effect：动作是否被正确执行；⑥ DomainTask / Artifact：跨智能体交接是否丢失正确结果；⑦ Final Response：最终回复是否忠实反映真实状态。关键规则：逐层独立评估、不短路——一次失败可能同时是多个层的独立问题（模型选错工具 + 错误工具又执行失败 + 最终回复谎称成功，是三个独立可判定的问题）；每层结论记进 findings，FailureAttribution 的 primary_failure = 执行链上最早可证实的偏离点（沿 1→7 取最早的 FAIL），UNKNOWN 不竞争 primary。修复顺序由此可推导：先修 primary，再复核后续 findings 是否随之消失。不允许未经逐层检查就把错误归成「LLM 回答不好」——那既不可修复，也不可回归验证。

**9. Q：**「同样的最终症状」怎么归因出不同层？举个例子。

**A：**三条走查：① 检索记录 selected_evidence_ids 含正确事实 → 证据包里有 → 但 Diet 的 ContextManifest.evidence_refs 不含它（可能被上下文预算裁掉）→ 第③层 FAIL，primary_failure = context_assembly（required_evidence_not_visible），后续决策偏差是上游传播、不重复记模型层 finding——修复要调上下文策略与裁剪顺序。② 四层都对、LLMCallRecord 确认输入正确仍做错 → primary_failure = model_decision（wrong_action_with_correct_context）——修复要调模型或 Prompt。③ 工具失败、ExecutionRecord 显示 DependencyUnavailable 且熔断器当时 OPEN → primary_failure = tool_execution（dependency_unavailable）——归因指向共享依赖健康，不指向模型决策。同样的症状，不同的修复对象——这就是第七章要证明的能力。

**10. Q：**UNKNOWN 状态守的是什么边界？

**A：**LayerEvaluationResult 的 status 含 UNKNOWN：Record 缺失、Trace 不完整、无法证明发生了什么时，reason_code = INSUFFICIENT_OBSERVATION。守住的是：没有观测到 ≠ 证明 Agent 做错——观测缺失的层不出 FAIL，只如实标记无法评估；这些层以 UNKNOWN 进 findings、不竞争 primary_failure；不能让 Judge 猜发生了什么，猜测产出的评估结论不可回归。

## 评估资产

**11. Q：**为什么确定性规则优先于 LLM-as-Judge？清单有哪些？

**A：**Tool 是否允许、是否经过 HIL、Effect 是否成功这类问题有唯一正确答案，从 Record 直接判定是零成本、可复现、可解释的；交给 Judge 会把确定性问题变成概率评分。九项确定性检查：required Evidence 是否存在（清单 evidence_refs 对照 Case 声明）、Tool 是否允许（visible_tool_refs 与实际调用比对）、是否经过 HIL（写操作必须 APPROVED 才有执行记录）、Tool 参数是否正确（arguments_snapshot 字段级比对）、Business Effect 是否成功、DomainTask 是否越权（跨域调用即违规）、Artifact 是否来自正确 producer（producer_domain_task_id）、CONFLICT 后是否恢复（必须存在重新读取 / 重新规划 / 上报）、最终声明是否与 Effect 一致。跨层安全规则（禁止 Tool、HIL Bypass、跨域越权）出现即 FAIL，不进语义评分。

**12. Q：**LLM-as-Judge 怎么用？为什么不读完整 Trace？

**A：**只处理确定性规则覆盖不了的开放式语义问题（训练计划整体是否合理、软约束权衡是否充分、建议是否完整）。输入是从 TaskExecutionView 构造的 JudgeInput：user_request、relevant_business_facts、evidence、executed_actions、tool_effects、final_response、rubric——完整 Trace 含大量与评价无关的执行细节，放大输入成本，还迫使 Judge 自行理解各 Runtime 内部语义，把本可确定性判断的错误也变成概率判断。输出少量离散等级 NOT_MET / PARTIAL / MET 加简短理由，不做百分制细评分；等级与理由随 LayerEvaluationResult 保存，成为可追溯的评估事实。

**13. Q：**EvalCase 和 EvaluationRun 分别冻结什么？为什么？

**A：**EvalCase 是可重复运行的评估场景（case_id / user_request / fixture_ref / capability_config / evaluators / tags）；Fixture 必须不可变——生成 Case 时脱敏冻结，评估执行时恢复 Business State、Memory、Knowledge、User State、Current Plan 五类起始状态；起点一变，结果差异就分不清是系统改动还是数据变化造成的。EvaluationRun 记录这次评估本身的身份与全套版本引用：dataset_version、candidate_version、model_version、prompt_version、workflow_version、retrieval_config_version、tool_schema_version、judge_version——两个 Eval Score 只有追溯到同一组配置才真正可比，缺版本记录的分数无法解释差异来源。字段全是版本引用不复制配置全文，与 ContextManifest 记版本不记 Prompt 正文是同一条边界。

**14. Q：**生产 Trace 为什么不能直接当 EvalCase？转换链路是什么？

**A：**生产 Trace 记录「当时发生了什么」，EvalCase 必须定义「固定输入条件下系统应该做什么」——Trace 的起始状态、数据、记忆都在变化，直接回放不可重复。链路：Production Task → Trace + Runtime Records 还原事实 → 用户反馈 / 异常发现 → FailureAttribution（先定位错误在哪一层）→ 脱敏 → 固定起始状态为不可变 Fixture → 创建 EvalCase（补 Expected Behavior 或 Rubric）→ 加入 Regression Dataset。顺序有含义：先归因再做 Case——归因告诉你这个失败真正考察的是哪一层（检索、装配还是决策），EvalCase 的 evaluators 与断言按它声明；跳过归因直接保存失败现场，得到的只是「又一条失败记录」，不是可回归验证的用例。

**15. Q：**Regression 为什么不用统一总分？三类判断是什么？

**A：**硬门槛——Forbidden Tool、HIL Bypass、跨 Domain 越权、关键业务状态错误——出现即 FAIL，不允许其他指标提升抵消。质量指标——Recall@K、Tool Selection Accuracy、Trajectory Pass Rate、Task Completion——与稳定 Baseline 在相同 Dataset 上比较，波动范围根据基线和实际数据逐步设置，不在没有数据的情况下虚构精确阈值。效率指标——Latency / 模型与工具调用次数 / Token Usage——从 Trace 时长与 LLMCallRecord 的 token_usage 统计，通常不直接决定质量 PASS，用于发现「质量提升但成本失控」。汇总三种终态：PASS（无硬门槛失败、关键质量无明显退化）/ FAIL（硬门槛违规或关键质量下降）/ REVIEW（质量与成本此消彼长，需人工判断 Trade-off）。统一总分无法表达「质量提升但成本明显增加」这类情况。

**16. Q：**观测与评估链路自己的三条异常边界是什么？

**A：**① Trace 写失败，不能导致正式业务事务失败——Runtime Fact 仍是唯一事实源，Trace 是观测层，写入失败时该 Run 标记 observation_incomplete，业务照常执行。② Record 引用不存在，Evaluator 返回 INSUFFICIENT_OBSERVATION——证据链断了就说断，该层 UNKNOWN，不能让 Judge 猜。③ Judge 失败，确定性评估结果仍保留——Judge 维度标记 unavailable，本次 Regression 不因 Judge 故障被当成系统执行失败，也不产出含猜测的分数。共同逻辑：观测不绑架业务，证据不完整不硬评，单维度故障不否定整次执行。

## 困难与演化

> 题源：[[找工作啊啊啊啊/项目梳理/个人健康管理agent/7.沿执行轨迹定位错误/11.困难以及应对办法|11.困难以及应对办法]]

**17. Q：**第七章的起点方案是什么？为什么不够？（构造场景，非线上事故）

**A：**第一版评估只围绕最终回答展开：给定一组用户输入，运行后检查最终回答是否满足预期；没有唯一标准答案的输出用人工检查或单一 Rubric 判断。任务路径短时能工作。Retrieval、上下文装配、领域智能体、工具运行时、HIL、状态恢复加入后失效：同一个错误结果背后可能对应完全不同的问题——检索没找到正确资料 / 证据找到但没进入本轮上下文 / 模型看到正确证据却选错工具 / 工具正确执行但最终回复错误描述了结果——只看最终答案，这些问题全表现为同一个「回答错误」。且 Agent 系统的输出不只是文本：中间过程可能已产生错误的真实动作（在使用过期计划版本的情况下反复调用修改工具、CONFLICT 后没有重新获取状态，最终却生成一段看起来正常的回复），只评最终文本发现不了。

**18. Q：**补更多 Final Answer Rubric、或把全部日志交给 LLM-as-Judge 为什么都不行？

**A：**为每种失败情况增加更多最终结果 Rubric，只能告诉系统「结果哪里不好」，仍然无法确定错误首先出现在哪一层。反过来把完整 Prompt、Tool Log 和所有执行日志全部交给一个 LLM-as-Judge：输入越来越大，Judge 需要自行理解不同 Runtime 的内部语义，很多本可以确定性判断的错误也变成概率评分，评估结果难以解释和稳定复现。根因：第一版评估只建立了「用户输入 → 最终输出」的评价关系，却没有建立执行过程中的可观察事实与评估对象之间的对应关系——需要验证的不只是最后生成了什么，还包括模型当时看到了什么、检索到了什么、选了什么动作、动作产生了什么真实效果。

**19. Q：**改造的顺序是什么？最终目标是不是更准的总分？

**A：**改造第一步不是增加更多 Judge，而是补齐统一执行轨迹：每个 Run 建独立 Trace，ContextManifest 记录模型真正看到什么，RetrievalRecord 保存候选与最终证据包的关联，工具层复用 ToolInvocation 与 ExecutionRecord——不重新保存事实，用统一身份把各 Runtime 已有数据串成完整执行轨迹。在此基础上评估从单一结果判断改为分层评估：能通过结构化事实确定的问题优先确定性检查，只有无法直接编码的开放语义才进 Rubric 和 LLM-as-Judge。最终目标不是更准确的 Agent 总分，而是让一次评估失败能进一步回答「问题首先出现在检索、上下文装配、智能体动作、工具执行还是最终结果」——可定位、可复现的分层评估是 Regression 和生产质量反馈能够成立的基础。
