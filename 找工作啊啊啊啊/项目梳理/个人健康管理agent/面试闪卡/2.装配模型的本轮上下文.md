# 面试闪卡 · 第二章：装配模型的本轮上下文

> [!info] 用法
> 一问一答背诵卡。答案保留冻结术语与 ID；事实以 [[11.代码级逻辑：一次 LLM 调用如何装配上下文]] 为准。

## 主问题与边界

> 题源：[[找工作啊啊啊啊/项目梳理/个人健康管理agent/2.装配模型的本轮上下文/1.总览|1.总览]]、[[11.代码级逻辑：一次 LLM 调用如何装配上下文]]

**1. Q：**第二章回答的唯一主问题是什么？主边界是什么？

**A：**系统保存了很多运行信息后，模型这一轮到底应该看到什么。主边界：完整 Runtime State ≠ 模型本轮上下文——任务长期存在会持续积累聊天历史、工具结果、中间状态、恢复信息和执行轨迹，这些为恢复和排障需要完整保存，但模型每轮只需要完成当前判断所需的信息。

**2. Q：**三层上下文是什么？

**A：**完整持久化轨迹（恢复与审计的事实，从不删除）→ 历史候选（HistoryCandidateBuilder 在每次装配时生成的临时派生视图，用完即弃）→ 本轮模型上下文（ContextPolicy 裁决后的最终结果）。三个层次必须区分：完整轨迹不是历史候选，历史候选也不是最终上下文；上下文整理只影响「以后哪些历史还有资格进入模型」，不删库。

## 机制与流程

**3. Q：**一次装配的完整调用链（主轴）是什么？

**A：**
```text
执行节点准备调用 LLM
    ↓ call_model（统一模型调用入口）
构建 ContextAssemblyRequest
    ↓ ContextAssembler.assemble(request)
读取 ContextPolicy / Runtime State（控制索引）
    ├── AgentStatusBuilder 生成状态栏
    ├── HistoryCandidateBuilder 生成历史候选
    ├── 读取业务事实 / 任务产物（plan_88@v2 / D200）
    ├── EvidenceReader 读取证据包 EB500
    └── CapabilityRegistry 加载可见 Skill / Tool
    ↓ 统一转换成 ContextBlock
    ↓ 执行令牌预算（必需块先入，可选块按优先级）
    ↓ 按固定布局渲染
ModelContext + ContextManifest（同源双产出）
    ↓ 模型网关调用 LLM
```

**4. Q：**为什么要有统一的模型调用入口 call_model？

**A：**执行节点不直接调用模型网关，而是调用 call_model 完成构建装配请求 → 装配 → 调用三步。由此确立：任何正式智能体模型调用都不允许节点自己手工拼 Prompt；节点只负责三件事——我是谁、在哪一步、要调用模型，「模型本轮具体看到什么」全部收敛在装配器。少了这条收敛，同一个底层状态在不同节点眼里含义漂移，统一上下文治理无从谈起。

**5. Q：**ContextAssemblyRequest 有哪些字段？validate_request 校验什么？

**A：**task_id / run_id / agent_id / stage / node_id、latest_event_id（装配截止的事件游标，如 evt_9001：只读这条及之前的输入事件，等待期间新到达的事件留给下一轮）、context_policy_id、evidence_bundle_id（EB500；本轮不需要证据为 None）。校验六项：任务存在、run_id 是当前 Run、agent_id / stage / node_id 与运行状态逐项一致、策略确实绑定当前节点。口径：装配请求是调用参数，不是权限凭据——节点只能报告自己在哪，不能申报自己想被当成谁，否则能力渐进装载的作用域收敛会被绕过。

**6. Q：**为什么说 Runtime State 是读取锚点，不是数据仓库？

**A：**系统存在任务控制索引、业务数据库、草稿存储、证据包、完整持久化轨迹、能力注册表多个来源；装配器按控制索引给的稳定引用到各自归属的存储读取当前版本，统一的是读取与组装过程，不是事实的拥有者。把物理数据全部复制进一份 AgentState 等于建第二套事实源，违反唯一事实来源原则。

**7. Q：**装配器的只读边界是什么？

**A：**只允许「读 → 派生 → 筛选 → 裁剪 → 渲染 → 记录上下文清单」这条流水线；不允许修改任务状态、推进状态图、修改草稿、写业务数据库、创建工具调用实例、决定下一节点、执行 RAG、执行工具。清单的生成与记录分离：装配器只生成 ContextAssemblyResult，统一调用入口在调模型网关之前把 manifest 交给观测记录层（context_observer.record）；观测系统内部实现属第七章。

**8. Q：**一套可执行的 ContextPolicy 必须回答哪四件事？

**A：**什么必须进入（required_sections，缺失即本轮装配失败）、什么允许进入（optional_sections，按预算与优先级裁剪）、各类内容最多占多少（history_budget / evidence_budget）、当前允许暴露哪些能力（capability_scope）＋用哪个提示模板（prompt_template_version）。策略绑定在节点配置上，装配器只读取执行，模型无权选择。绑定节点而非智能体的意义：同一训练智能体在 search_replacement 阶段必需的是正式计划 plan_88@v2，草稿生成后下一阶段才把 D200 列入必需——策略声明的是当前阶段需要什么，不是智能体永远需要什么。

**9. Q：**ContextBlock 为什么是统一中间形态？有哪些关键字段？

**A：**历史、状态栏、产物、证据、技能、工具是不同类型的内容，直接对每种类型写 if 分支拼 Prompt，令牌预算就没有统一操作对象。统一成块后：block_type（system_instruction / agent_status / latest_user_input / history / evidence / business_fact / task_artifact / skill_instruction / tool_schema 九类）、source_refs（来源引用，清单的各类 refs 按它登记）、required、priority、estimated_tokens、atomic_group_id（同组块要么全进要么全不进，如执行中的工具调用与结果对）。预算在块上执行、清单从 source_refs 生成、布局按类型排序——三个下游共享同一操作对象。

**10. Q：**business_fact 块和 task_artifact 块为什么要分两类身份？

**A：**plan_88@v2 来自业务数据库，是已确认生效的正式计划（ACTIVE）；任务草稿 D200 与候选动作随任务执行演进。两类身份不混用，同一轮上下文里模型能分清「现在生效的计划是什么」和「正在提议的修改是什么」。正式计划只有经第四章调用实例提交才会变更，业务库才出现 plan_88@v3。

**11. Q：**AgentStatus 状态栏有哪四个区块？为什么不是新的事实源？

**A：**① 当前执行议程（goal / phase / current_action / pending_actions / completion_condition）；② 事件侧信道（最近影响决策的确定性运行时事件，只来自系统与工具产出）；③ 当前环境状态（current_object_refs，如 plan_88@v2、target_item_id）；④ 当前能力状态（disabled_capabilities 及原因，如 publish_plan: draft_not_confirmed）。每轮模型调用前由 AgentStatusBuilder 从控制索引、草稿存储、检查点 / 事件存储、能力注册表确定性投影生成；不落库、上轮状态栏不参与任何系统控制，下游要控制语义应读控制索引本身；清单只存 agent_status_hash（摘要），不建状态栏存储。

**12. Q：**令牌预算的公式、执行时机和失败语义是什么？

**A：**上下文预算 = 模型最大上下文 − 预留输出空间 − 安全余量；20 万令牌只是当前部署示例值，是配置不是架构规则。预算在块生成之后、渲染之前执行，对象是块不是拼好的字符串：先核对必需块总量（超出直接抛 required_context_overflow 显式失败），可选块按优先级整组放入不拆半。必需上下文自身超预算时不能中间随机截断、也不能触发全部摘要，由 Harness 决定换模型、减输入、进压缩流程或中止（降级治理属第六章）——装配器不能静默破坏必需上下文。裁剪顺序由节点策略声明，默认模板：失效历史 → 已被产物替代的工具结果 → 低优先级历史候选 → 补充型证据块。

**13. Q：**固定布局的顺序是什么？和 KV Cache 什么关系？

**A：**稳定系统提示词、固定职责 / 安全规则 / 技能指令 / 工具模式在前 → 较稳定区：本轮选入的历史与证据 → 尾部动态区：当前任务产物、事件侧信道、状态栏、最新用户输入。状态栏每轮都变所以压尾部，缓存失效只波及其后一小段；稳定系统指令放最前让前缀缓存尽可能长复用；不每轮随机改 Prompt 结构，因为前部任何变动都会让后续全部缓存作废。正确性优先于缓存友好。

**14. Q：**ModelContext 和 ContextManifest 为什么必须同源同时生成？

**A：**两者来自同一套 ContextBlock：一边按布局渲染成 ModelContext（context_id、稳定区 system_messages、较稳定 history_messages、task_context、evidence_context、agent_status、current_user_input、tool_schemas），一边从块的 source_refs 生成 ContextManifest（business_fact_refs / evidence_refs / artifact_refs / visible_tool_refs / visible_skill_refs / prompt_template_version / context_policy_version / context_hash / agent_status_hash / estimated_tokens）。先生成 Prompt 再事后补记，只能猜测模型当时看到了什么，清单对评估失去价值。完整 Prompt 不作为默认长期日志保存；清单主要作为第二章向第七章的观测接口存在。

**15. Q：**装配失败的三条路径是什么？

**A：**① 控制索引与业务版本不一致（索引记 active_plan_version=2，业务库已到 v3）→ 返回 version_conflict，装配器不许自行决定「那我用 v3 吧」——用哪个版本是业务并发语义，读取层不越权；② 证据包不存在或已过期 → 策略声明为 optional 时记录缺失继续装配，required 时本轮装配失败——不能把「没有证据」伪装成「证据支持」；③ 必需块自身超预算 → required_context_overflow 显式失败。

**16. Q：**模型能看到某个工具，等于可以执行吗？

**A：**不。上下文中没有的工具，模型无法主动提出这个调用；上下文中存在工具，也只代表当前节点允许模型提议该动作，不代表工具运行时必须执行——提案之后的权限、参数与业务规则重新校验和真实执行全属第四章。能力渐进装载的收敛示例：会话主管只看三个业务域的轻量描述 → 训练智能体看到技能完整指令 → search_replacement 步骤看到 search_exercise / evaluate_training_load / update_plan_draft → awaiting_confirmation 时 update 类工具退场，publish_plan 因 draft_not_confirmed 不向模型暴露。
