# 面试闪卡 · 第一章：跨请求的任务生命周期

> [!info] 用法
> 一问一答背诵卡。答案保留冻结术语与 ID；背不住时沿各节题源回查原文，事实以 [[10.代码级逻辑：跨请求的任务暂停与恢复]] 为准。

## 主问题与边界

> 题源：[[找工作啊啊啊啊/项目梳理/个人健康管理agent/1.跨请求的任务生命周期/1.总览|1.总览]]、[[10.代码级逻辑：跨请求的任务暂停与恢复]]

**1. Q：**第一章回答的唯一主问题是什么？主边界是什么？

**A：**一个 Agent Task 现在究竟执行到哪里。主边界：Conversation ≠ Task，运行状态 ≠ 正式业务事实。Harness 控制平面负责任务的创建、推进、中断、恢复和结束，维护的是执行状态而不是业务事实。

**2. Q：**Hero Scenario 在第一章怎么用？

**A：**系统生成新训练方案草稿后需要用户确认，任务暂停但不结束；等待期间用户继续问「晚上训练的话，晚饭应该提前多久吃？」，这条消息不能被当成恢复旧任务的输入。会话与任务的分离在这里兑现：等待中的任务不锁会话（T100 保持 WAITING_HUMAN，C10 照常处理新消息），继续的会话不打扰任务（没有任何对象被改动）。

## 机制与流程

**3. Q：**第一章的六个身份对象是什么？各自回答什么问题？

**A：**会话 C10（对话入口，对应根图 root_thread_id）、任务 T100（一个明确业务目标的完整逻辑生命周期，控制数据在 agent_task_runtime）、Run R1 / R2（任务的一段连续执行，登记在 agent_task_run）、草稿 D200（尚未成为正式业务事实的训练方案，草稿存储）、工具调用实例 I300（参数已确定、可跨暂停恢复引用的工具动作）、检查点（按 task_thread_id 定位：图位置 + 中断现场）。一句话：检查点回答「图从哪里继续」，任务回答「目标处于什么阶段」，Run 回答「这是第几段连续执行」，草稿回答「用户正在看哪个方案」，调用实例回答「用户确认的是哪个动作」，业务数据库回答「正式事实有没有变化」。

**4. Q：**任务创建的完整调用链是什么？

**A：**
```text
POST /conversations/C10/messages        # 用户消息进入会话入口
    ↓ ConversationService.handle_message()
会话主管路由                            # 判断：新的每日计划请求
    ↓ TaskController.create_task()
INSERT agent_task_runtime               # T100：status=RUNNING、task_version=1、current_run_id=R1
    ↓ DailyPlanGraph.invoke(thread_id=TH100)   # 检查点按 TH100 归档
```
会话入口只判断是否需要创建任务，不控制任务生命周期；会话主管在这里只完成路由决策。

**5. Q：**每日计划图的节点链是什么？为什么节点边界重要？

**A：**generate_draft（生成草稿 D200，对业务库只读）→ prepare_invocation（创建调用实例 I300，invocation_id 写入图状态）→ wait_for_human（只读取已有 invocation_id，interrupt()）→ 恢复后 execute_invocation（执行 I300）→ complete_task（D200 COMMITTED、T100 COMPLETED）。LangGraph 在每个节点执行完成后保存检查点，节点边界就是状态持久化的粒度。

**6. Q：**为什么调用实例必须在人工介入之前创建？

**A：**用户应该确认一个已经确定的动作，而不是确认以后运行时再重新问模型「你刚刚想做什么」。确认之后再生成工具调用，等于在批准与执行之间又插进一次模型输出——用户批准 A、系统执行 B 的窗口由此打开。prepare 之后，动作参数、幂等令牌、审批对象全部固定，确认与执行之间不再有任何重新解释的空间。

**7. Q：**agent_task_runtime 的关键字段有哪些？

**A：**身份组：task_id、root_thread_id（「一个会话最多一个活跃任务」的唯一约束按它生效）、task_thread_id（= 根线索前缀 + 任务类型 + task_id，形如 `user-42-v3:daily_plan:T100`，恢复时按它定位检查点）、user_id。控制组：task_type、status（CREATED / RUNNING / WAITING_HUMAN / 终态）、task_version（乐观并发版本，自增用于拒绝旧确认卡片）、current_run_id（指向 agent_task_run 最新一行的指针）。草稿关联组：draft_id + draft_version。时效组：expires_at（跟随 plan_date 而非固定 TTL）。

**8. Q：**Run 为什么用轻量登记表 agent_task_run？登记哪些字段？

**A：**run_id 被 RuntimeContext、执行记录、Trace 多处引用，需要明确的创建者与登记处；但 Run 不是新的业务生命周期。每段 Run 一行：run_id、task_id、status（RUNNING / INTERRUPTED / COMPLETED / FAILED）、started_at、ended_at、resume_from_run_id（因恢复产生时的上一段 Run，如 R2 ← R1）。登记行只记起止与恢复链，不进任务状态机，不复制执行事实；current_run_id 只是指向最新登记行的快速指针。

**9. Q：**resume_task 的恢复校验链有哪八步？

**A：**① 任务存在且 status == WAITING_HUMAN；② task_version 与卡片携带版本匹配（拒绝旧卡片）；③ 草稿存在；④ draft_version 匹配；⑤ 调用实例存在且属于 T100；⑥ approval_state 仍是 WAITING_APPROVAL（未被处理过）；⑦ arguments_snapshot 冻结的参数仍指向 D200 v3（确认对象与执行对象没有漂移）；⑧ 等待期间业务前置条件未变（执行前护栏还会复查）。确认走 POST /tasks/T100/actions 结构化入口，不进普通消息入口。

**10. Q：**恢复受理事务包含哪四步？为什么必须同一事务？

**A：**① OCC 推进任务（UPDATE … SET status='RUNNING', task_version+1, current_run_id='R2' WHERE status='WAITING_HUMAN' AND task_version=4，0 行即整体回滚）；② I300.approval_state → APPROVED；③ D200.status → APPROVED；④ INSERT agent_task_run 登记 R2。分开提交的后果：并发确认各自插入 R2、R3 而 OCC 只允许一个成功，失败一侧留下没有任何执行含义的孤儿 Run；审批同理会出现半批准状态（任务已 RUNNING、实例仍 WAITING_APPROVAL），后续校验链失去判定依据。事务内不执行图恢复、LLM 或工具调用。

**11. Q：**为什么恢复是登记新 Run R2，而不是重建任务？

**A：**用户确认的是 T100 这个逻辑目标里的 D200 方案；新建 T101 会丢掉原有检查点、草稿关联与调用实例，把「继续」变成「重来」。恢复后的执行是一段新的连续执行，需要自己的执行记录与 Trace 挂靠，R1 不应被拉成一条跨越数小时等待的执行链。task_id 稳定、run_id 更新，就是「Task 表示逻辑目标生命周期，Run 表示一次连续执行阶段」在代码上的样子。

**12. Q：**T100 处于 WAITING_HUMAN 的暂停瞬间，各层保存什么？

**A：**C10 status=ACTIVE（会话照常）；T100 status=WAITING_HUMAN、task_version=4、current_run_id=R1；R1 status=INTERRUPTED；D200 version=3、PENDING_APPROVAL；I300 approval_state=WAITING_APPROVAL / status=PENDING；检查点图位置停在 wait_for_human、待处理中断为 TaskInterruptPayload；业务数据库正式计划仍是旧版本。前五个对象都动了、业务库没动——暂停的全部意义：修改正式计划只有一个入口（I300 的执行），「等待」因此是数据上可判定的状态，不依赖组件自我约束。

## 身份与状态辨析

**13. Q：**第一章的四个「不能合并」分别为什么？

**A：**① 会话与任务不能合并：合并等于等待中的任务锁死会话、或会话结束任务就得重建，Hero 要求「任务在等、会话在答」同时成立。② 任务与 Run 不能合并：合并后无法区分目标的生死与一段执行的起止，执行记录、Trace、执行尝试的 run_id 挂靠消失。③ 控制索引与检查点不能合并：前者是可快速查询的控制数据，后者是执行现场（图位置、状态数据、待处理中断），读写模式与清理时机都不同。④ 草稿与正式计划不能合并：「未确认数据只存在于草稿存储」让等待期业务库必然不变成为数据上可判定的事实。

**14. Q：**草稿 D200 的状态机是什么？

**A：**EDITING（生成中或用户仍在修改，每次修改 draft_version 自增）→ prepare_invocation 固化动作后 PENDING_APPROVAL（等待用户对「D200 v3 + I300」的确认）→ 确认且恢复校验链通过后 APPROVED（已批准待执行）→ execute_invocation 成功后 COMMITTED（成为正式训练计划）；等待类状态可转 ABANDONED（用户放弃）/ EXPIRED（超过业务有效期）。

## 异常路径

**15. Q：**用户拿着旧确认卡片提交会怎样？

**A：**卡片携带 task_version=4 而任务已推进到 v5：受理事务里 OCC 更新的 WHERE 条件匹配 0 行，整个事务回滚，校验链在第②步拒绝；不修改任何数据，重新读取最新状态并把新卡片返回，让用户基于当前版本重新决定。版本检查存在的理由：确认卡片可能在客户端停留任意久，没有版本比对，旧请求会静默覆盖新状态。

**16. Q：**I300 已创建、检查点还没保存时进程崩溃怎么办？

**A：**prepare_invocation 落库了 I300，但 state.invocation_id 尚未随检查点持久化；服务恢复后图从该节点之前的检查点重放 prepare_invocation。所以 prepare 必须是 get_or_create：以（task_id、节点意图、draft_id、draft_version）为键，I300 已存在就复用并写回图状态，不产生 I301——否则库里同时存在两个实例，wait_for_human 读到哪个取决于重放结果，身份的稳定 reference 失去保证。节点重放是检查点机制下的正常行为，所有创建身份对象的节点都要按可重放语义编写。

**17. Q：**为什么不能用自然语言消息恢复任务？

**A：**恢复需要 task_id、版本、动作的确定校验信息，自然语言不具备；把「这句话是不是在确认计划」交给模型判断，等于给控制路径引入一次不可靠推理。所以确认走独立的结构化入口（TaskAction），普通消息入口的产出只是自然语言理解与路由。
