# 面试闪卡 · 第三章：把记忆与知识汇成证据

> [!info] 用法
> 一问一答背诵卡。答案保留冻结术语与 ID；事实以 [[11.代码级逻辑：从用户事实到 EvidenceBundle]] 为准。

## 主问题与边界

> 题源：[[找工作啊啊啊啊/项目梳理/个人健康管理agent/3.把记忆与知识汇成证据/1.总览|1.总览]]、[[11.代码级逻辑：从用户事实到 EvidenceBundle]]

**1. Q：**第三章回答的唯一主问题是什么？主边界是什么？

**A：**当前 Task 之外，还有哪些长期事实、正式业务事实和外部知识要取回来。主边界：Task State ≠ 长期用户事实 ≠ 正式业务事实 ≠ 外部领域知识——四类信息的生命周期与权威来源各不相同。本章两条主链：Memory Write Path（用户事实如何沉淀）与 Evidence Read Path（任务如何取用）。

**2. Q：**五种身份是什么？为什么不能混？

**A：**Current User Input ≠ Episode Memory ≠ Semantic Memory ≠ User Profile ≠ Evidence。最新用户输入是本轮刚说的话，当前任务立即使用；情节记忆（E21）是某个时间背景下真实发生过的一次陈述，历史层只追加；语义记忆（S31，`training.availability.workday_training_time = evening`，status=current）是根据情节当前能支持的长期判断，认知层版本化；用户画像（`training_availability.workday_time = evening`）是读取层的当前快速视图，可变；证据（ev_712）是为某个具体任务整理出来、交给下游模型使用的有来源主张——是当前任务对长期事实的一次读取结果，不是新的长期记忆。

**3. Q：**三个数据层是什么？和「情节 / 语义 / 程序性」分类什么关系？

**A：**数据层是设计依据：历史层只追加（Episode，只置 invalid / deleted 不改写）、认知层版本化（Semantic，SUPERSEDE 切换）、读取层可变（画像投影）。认知分类（情节 / 语义 / 程序性）只作解释旁证，不作为结构名——两套词汇曾混用，重构后显式分为两个维度。

**4. Q：**MemoryEvent 里 occurred_at 和 recorded_at 为什么分开？

**A：**occurred_at 是事实发生时间（事实属于什么时候），recorded_at 是系统记录时间（什么时候拿到这条事实）。用户今天说「去年一直晨练」，两个时间差一年；混用一个时间戳，后续语义巩固就无法判断「偏好晨练」是过去状态还是当前状态。

**5. Q：**为什么当前任务不用等记忆管道？「写入延迟」边界是什么？

**A：**用户这句话进来时，当前任务立即把它作为 latest user input 用于本轮规划（第二章装配链的必需块）；与此同时记忆事件记录器旁路写入缓冲（MemoryEventRecorder.record），抽取、巩固、投影全部后台异步。约束：Memory 写入延迟，不能导致当前 Task 忽略最新用户输入——「当前任务用了这句话」与「长期记忆已形成」是两件事。

## 写入链机制

**6. Q：**Memory Write Path 的完整链路是什么？

**A：**
```text
Conversation Event
    ↓ MemoryEventRecorder → 持久记忆事件缓冲
    ↓ MemoryExtractor（后台批次：事件量 / 用户空闲 / 任务正常结束触发）
    ↓ EpisodeCandidate（五项校验）
    ↓ Episode Memory（历史层，只追加，如 E21 / E22）
    ↓ state_key dirty
    ↓ SemanticConsolidator（后台，只处理 dirty 的键）
    ↓ Semantic Version（认知层，版本化，如 S31）
    ↓ Profile Projection（读取层，可变）
```

**7. Q：**EpisodeCandidate 写入正式情节前过哪五项校验？

**A：**① 结构校验（字段完整、时间合法）；② 用户归属校验（user_id 正确）；③ 主体归属校验（「我朋友对花生过敏」的主体不是 self，不能写进用户本人画像）；④ state_key 校验（必须在注册表中）；⑤ 幂等检查（键 = source_event_id + extraction_batch_id + candidate_index，同一批抽取重试不生成两条相同情节）。向量相似度不参与覆盖决策——相似只说明可能相关，不说明同一事实。

**8. Q：**state_key 为什么靠注册表维护、不让模型自由创造？

**A：**抽取器从 MemorySchemaRegistry 的已定义键中选择，映射不了的标 unknown 走人工可解释的扩展流程。不约束的话，模型会为同一维度生成 training_time、workout_time、preferred_workout_hour、exercise_time_preference 四个同义键，围绕 state_key 的巩固、dirty 标记、画像映射全部失效。「偏好晨练」（`training.preference.training_time`，用户真正偏好）与「工作日只能晚练」（`training.availability.workday_training_time`，现实约束下的可用时间）必须落在两个键——SUPERSEDE 只发生在同一 state_key 的版本之间，混成一个键，「晚练」就会覆盖「偏好晨练」，偏好与约束两个信息同时丢失。

**9. Q：**语义巩固的四种输出状态是什么？SUPERSEDE 为什么是原子的？

**A：**NO_CHANGE（新情节只是再次支持现有认知，不建新语义，情节标记为已消费）；NEW_SEMANTIC（该键首次形成稳定认知，S31 current）；SUPERSEDE（同一 state_key 的当前认知真正变化）；UNCERTAIN（证据冲突或不足，不修改语义与画像，情节保留，悬着等更多证据——「系统永远有当前值」不是本层的正确性标准）。SUPERSEDE 是一次原子事务：条件更新旧版本（仅当仍为 current，0 行即冲突）→ 旧版本转 historical → INSERT 新版本 current → INSERT supersedes 关系 → 画像投影，一次提交。不变量：同一 user_id + state_key 最多一个 current 语义；两个巩固器并发时，只有一个条件更新能改到行，另一个落 0 行后重读重试——数据库事务加版本检查即可，不引入分布式锁。

**10. Q：**画像投影怎么做？热路径的适用边界是什么？

**A：**语义成功变化后，ProfileProjector 按 state_key → 画像字段的固定映射做确定性投影（程序而非模型重写），字段保留溯源：value、source_type（semantic_projection / user_stated）、source_memory_id、updated_at——否则「用户说的」和「系统推导的」无法区分。三类事实允许走窄热路径（立即抽取 + 立即写情节 + 立即投影，语义巩固仍后台补完）：安全事实（严重过敏）、用户明确要求记住的信息、预定义且当前请求之后立即需要生效的关键画像约束。边界：热路径的意义是「几小时后的另一个任务能尽快读到」，不是当前任务正确执行的前提——当前任务靠 latest user input；把热路径设计成当前任务的依赖，等于把异步管线偷偷塞回同步关键路径。

## 读取链机制

**11. Q：**EvidenceRequest 的结构是什么？user_id 为什么不由智能体填？

**A：**task_id / run_id / agent_id / stage 加三类需要：memory_needs（MemoryNeed 优先 state_keys 而非自然语言查询，query_text 兜底；required 标记必需性）、business_needs（如 active_workout_plan）、knowledge_needs；include_episode_history 默认 false，只有解释历史类问题才下钻情节。进入协调器前先做一致性校验（与第二章同思想，不允许伪造 stage）。user_id 由检索协调器从任务运行时派生并绑定所有查询——这不是第四章的权限系统，是第三章最基本的数据归属边界：否则一个智能体填上别人的 user_id 就能读另一个用户的记忆。

**12. Q：**四路检索怎么分工？

**A：**ProfileReader 画像：预定义高价值字段直接读，最快路径。MemoryRetriever 记忆：结构化过滤 + 向量 + 词法三路（Postgres + pgvector，不引入新检索服务），三级下钻——普通请求画像 + 当前语义，需要解释变化才下钻情节。BusinessFactReader 业务事实：直接调业务服务并带稳定版本（WorkoutService.get_active_plan() → plan_88@v2），不去向量库搜「我的当前计划是什么」。KnowledgeRetriever 领域知识：结构化条件优先（动作模式、目标肌群、排除标签），自由文本增长后再叠向量混合检索。每路只返回 RetrievedCandidate 候选，没有哪一路直接拼 Prompt。

**13. Q：**RetrievedCandidate 和 Evidence 什么区别？冲突怎么处理？

**A：**候选是「检索器找到了什么」，证据是「装配器标准化并选中、可交给下游的主张」。Evidence 增加结构化主张身份：claim 给模型和人读，claim_key + value 给运行时做去重与冲突识别。去重按 claim_key：画像与语义两路召回同一事实（availability=evening）时保留来源更完整的一条（S31，带版本与 provenance）。冲突不靠后返回覆盖前面的：同 claim_key、都 current、value 不同 → EvidenceConflict(unresolved)，不静默让 EV2 覆盖 EV1；程序能判定的只有 current 优先 historical。另有一条硬约束：一条证据的 claim 必须由它自己的 source 与 provenance 真正支持——「偏好晨练但现实只能晚练」这种组合结论必须显式做成派生证据（provenance 同时指向 S10 与 S31），不伪装成单来源事实。

**14. Q：**EvidenceBundle 是什么？三态完整性怎么用？

**A：**按任务与 Run 生成的检索结果快照：bundle_id（EB500）、user_id / task_id / run_id、retrieval_id、created_at、status、四类证据列表、conflicts、missing_sources。三态：COMPLETE（必需全存在）、PARTIAL（必需齐全可选有缺）、FAILED（至少一个必需缺失）。第二章的对应消费：COMPLETE 与可接受的 PARTIAL 可加载进装配链，FAILED 不进入正常模型调用——「必需证据缺失则本轮装配失败」的既有语义闭环。跨 Run 默认重新检索生成新包（EB501），第一版不建跨 Run 证据缓存；快照语义让第二章的存在 / 归属 / 有效三项校验有据可查。

**15. Q：**RetrievalRecord 为什么是两阶段？和 ContextManifest 什么区别？

**A：**旧结构要求同时记 retrieved_items 和 selected_evidence_ids，但 evidence_id 在装配器处理之后才存在，一次性写入时间上不成立。两阶段：协调器完成四路检索后立即创建记录写 retrieved_items（status=retrieved）；装配器生成证据与证据包后回填 selected_evidence_ids 与 bundle_id（status=finalized）。与 ContextManifest 的分工：检索记录回答「检索器找到什么、装配器选中什么」（第三章检索侧），上下文清单回答「模型本轮实际准备看到什么」（第二章装配侧）。完整数据链：候选 → RetrievalRecord → 装配选中 → 第二章再筛 → ContextManifest.evidence_refs；第七章沿这条链分别定位「没召回」「召回了没选」「进了证据包但没装进上下文」。

**16. Q：**Artifact 为什么不是第三章的第五类证据来源？

**A：**证据来源保持四类：画像、记忆、业务事实、领域知识。上游智能体产物（第五章的 Workout Artifact → Diet）是任务 / 智能体之间的结构化产物移交，归第五章协议；第二章已有独立的产物读取路径（Artifact → ContextBlock）。证据包不把产物复制成长期证据；产物能帮助生成检索条件时，作为 EvidenceRequest 的输入引用参与，仅此而已。

**17. Q：**第三章的三条异常路径怎么处理？

**A：**① 记忆抽取失败：原始 MemoryEvent 已持久化，事件保持 pending / retryable 后续批次重试，不产生假情节，当前用户请求不因后台抽取失败而回滚——写入链在主路径之外，失败不反向传导。② 两个巩固器并发更新同一 state_key：只有一个条件更新能提交，另一个落 0 行后重读重试，任何时刻同一键不会出现两个 current。③ 必需证据缺失：证据包 status=FAILED、missing_sources 列出缺口，不能空着当前计划让模型自己猜；下游由第二章既有语义接管。

## 困难与演化

> 题源：[[找工作啊啊啊啊/项目梳理/个人健康管理agent/3.把记忆与知识汇成证据/10.困难以及应对办法|10.困难以及应对办法]]

**18. Q：**第三章的起点方案是什么？在哪里失败？（构造场景，非线上事故）

**A：**「原子事实 + 相似度覆盖」：会话结束后抽取原子事实、生成向量嵌入写入 UserMemory；新事实写入前先搜相似旧记忆，相似度高就 UPDATE 旧记录，或用 superseded_by 标记替代。静态属性（身高、不吃牛肉）能工作；用户状态随时间变化后失败：早期「喜欢早上训练」、几个月后「只能晚上训练」，两条记忆高度围绕「用户 + 训练时间 + 偏好」，向量相似度极高，被当成同一事实直接 UPDATE——数据库得到了更当前的值，但「用户过去喜欢晨练」这个事实消失，系统再也无法解释变化何时发生、为什么发生。

**19. Q：**调相似度阈值、加替代标记为什么都解决不了？

**A：**调阈值只影响「是否误合并」，回答不了「什么时候应该更新」——「我以前喜欢晨练」和「我现在改成晚练」语义相似度非常高，但它们是同一个用户状态在不同时间的两个有效阶段，不是重复事实；这是数据语义问题，不是相似度阈值问题。superseded_by 保留旧记录，但检索默认过滤被替代记忆，问题从「历史被删除」变成「历史在库里但智能体看不见」；且写入阶段被迫回答「新记忆是在纠正旧事实，还是描述一个新的历史状态」——抽取只看到当前一小段会话，让它同时理解完整历史与时间关系，职责过重。

**20. Q：**问题的最终定性和三层改造是什么？代价与收益怎么权衡？

**A：**定性：旧系统把三种不同含义的数据（发生过什么 / 目前根据历史形成什么认知 / 智能体现在应该快速读取什么状态）混在同一个 UserMemory 抽象里——一次用户状态变化同时触发三种互相冲突的需求（旧事实必须保留、当前判断应该变化、最好直接得到最新值），单个可变记录不可能同时满足。改造：历史层只追加（情节 E1、E2 都长期存在，分别带时间与来源）、认知层版本化（语义 S1 historical → S2 current，derived_from 指回情节）、读取层可变（画像投影）；抽取职责收窄为「有没有值得跨会话保存的新事件」，是否形成稳定认知交语义巩固；向量相似度从「相似 → 可能更新」改为「相似 → 可能相关 → 交给时间 / 语义判断」。代价：维护 state_key、derived_from、有效时间和后台巩固；换来历史可追溯、当前状态快速读取、认知可解释证据来源。不引入事件溯源、时序知识图谱或复杂记忆图谱——当前用户状态集中在有限的健身 / 饮食 / 交互偏好主题，三层已够。
