# 面试闪卡 · 第五章：把编排责任交还 Supervisor

> [!info] 用法
> 一问一答背诵卡。答案保留冻结术语与 ID；事实以 [[12.代码级逻辑：Supervisor 如何持续推进跨领域任务]] 为准。Supervisor 是全库唯一保留英文的角色名。

## 主问题与边界

> 题源：[[找工作啊啊啊啊/项目梳理/个人健康管理agent/5.把编排责任交还 Supervisor/1.总览|1.总览]]、[[12.代码级逻辑：Supervisor 如何持续推进跨领域任务]]

**1. Q：**第五章回答的唯一主问题是什么？根因是什么？

**A：**一个用户目标同时涉及训练和饮食时，谁负责持续推进整个目标。根因：整体任务编排责任放错了层级——旧版顶层只完成一次性领域选择，没有一个持续存在的角色知道这个目标完成到了哪里（旧版结构细节见本章困难节）。

**2. Q：**第五章最容易混淆的三层任务身份是什么？

**A：**AgentTask T200：第一章的逻辑任务，代表用户的整个跨领域目标，跨请求、跨人工确认持续存在，拥有 Run / Checkpoint 生命周期。DomainTask DT10 / DT20：T200 内部的领域工作单元，协作层的稳定身份，由 Supervisor 委派、根运行时登记与推进。后台执行记录 AE500：DT10 以 execution_mode = background 进入异步运行时产生的持久执行记录，绑定 domain_task_id、拥有独立 run_id / trace_id。关系是包含不是平级：统一命名 `domain_task_id` + `parent_task_id`，不让裸 task_id 同时指父任务和子任务；AE500 的关系是「AE500 succeeded → DT10 succeeded」，不是第二个业务任务。根运行时指第一章根状态图与任务控制器所在的确定性执行层：不调模型、不做业务判断，只校验编排动作、推进状态机、保存控制状态。

**3. Q：**同步 DomainTask 为什么没有独立的 task / Run？ChildTask 去哪了？

**A：**同步委派只是父任务当前 Run 内的嵌套执行，没有独立执行生命周期；给它配 task / Run 等于让一次子调用背上完整任务运行时——它用 `domain_task_id` 标识，通过领域智能体 Span（Domain Agent Span）在父任务 Trace 中定位；只有真正跨请求后台运行的工作才交给异步运行时建持久执行记录。ChildTask 模型吸收进 DomainTask：两者描述同一对象（子任务身份、被指派智能体、依赖、输入输出产物、状态），维护两套必然漂移。统一后的结论：DomainTask 本身就是任务依赖图（Task DAG）中的节点，depends_on 与状态直接是它的字段，根运行时不保存第二份子任务状态；领域到智能体的映射由注册表配置（workout → workout_agent）。

**4. Q：**DomainTask 只保存哪两类信息？为什么不复制用户事实？

**A：**只存委派出的约束（constraints，Supervisor 对本领域的要求）与信息需求声明（evidence_requirements，完成本任务需要知道什么，如 state_key 列表）。原结构的 `relevant_user_facts: dict` 被删除：复制用户长期事实快照会让委派对象变成第二份事实源，与第二、三章的读取层冲突。口径：DomainTask 表达「你需要知道什么」，不表达「这里复制一份我认为是真的的东西」——领域智能体执行到需要信息的节点时，走第三章 EvidenceRequest → EvidenceBundle、第二章装配链，拿到的是当时的真实状态而不是委派那一刻的快照。

**5. Q：**输入引用为什么分三个字段？

**A：**input_artifact_refs 只放上游 DomainArtifact（含版本，如 A100@v1）；input_constraint_refs 放跨领域约束（如 XC10）——约束是带身份的结构化对象，但不是产物；input_conflict_refs 放冲突报告（如 CR20）——修订分支据此知道要解决什么。约束和冲突不伪装成 Artifact 混进产物引用。

## 编排机制

**6. Q：**SupervisorAction 有哪六类？为什么模型输出动作、根运行时落状态？

**A：**direct_answer（直接回答）、create_domain_task（创建领域任务，ensure 语义）、wait_for_tasks（等待在途任务）、request_user_input（把问题交给主会话）、create_revision_task（冲突裁决后建修订任务）、complete_parent_task（声明父目标业务上可以结束）。Supervisor 是大语言模型智能体，适合决定业务编排（要不要委派、先谁后谁、冲突后修哪个），但不能直接修改 DT10.status 或父任务完成状态——「我觉得 DT10 已经完成了」不能成为合法状态。链路：Supervisor 输出 SupervisorAction → 根运行时校验器逐项确认（DT10 存在、属于 T200、A100 ready、领域在允许范围内、任务数量与委派深度在预算内）→ 通过才确定性修改状态，不过则拒绝并把原因返回重新决策。与第二章「请求是调用参数不是权限凭据」同构。

**7. Q：**DomainTask 的状态机是什么？conflict 和 failed 为什么是两个状态？

**A：**pending → running → succeeded / waiting_input / conflict / failed / cancelled，全部由根运行时推进。failed 是执行层面出错；conflict 是业务层面「无法满足约束」——工作本身没有错，需要的是编排裁决而不是重试。depends_on 的推进规则只有一条：所有前置状态为 succeeded 本任务才 runnable——conflict 不算 succeeded，冲突分支不能伪装成正常依赖，所以修订任务 DT30 不把 DT20 写进 depends_on（新分支，不建通用循环图）。并行：depends_on = [] 的 DT10 / DT20 在父 Run 内同步并发（asyncio.gather 一类原语），只是并发优化，不是后台任务系统。

**8. Q：**AgentResult 有哪四种终止结果？succeeded 由谁判定、校验哪四项？

**A：**succeeded（完成，产出待校验产物）、needs_input（缺必要输入，携带 InputRequest）、conflict（无法满足跨领域约束，携带 ConflictReport）、failed（失败，携带错误码）；结果绑定 domain_task_id。succeeded 不是智能体说了算：根运行时收到后校验——① 产物逐一存在；② producer_domain_task_id 归属本任务；③ status == ready；④ 至少有一个产物满足 required_output_type（单数 = 主要交付类型；artifact_refs 里的辅助产物不参与必需类型判定，但仍逐一校验归属与状态）。全过才写 succeeded；任何一项不满足按 failed 收尾、产物原状保留。没有可校验的产物就没有完成。

**9. Q：**OrchestrationState 是什么？Supervisor 每轮看到什么？

**A：**根运行时保存的最小编排状态（作为第一章 Runtime State 中第五章负责的字段，不建新存储）：parent_task_id、goal、domain_task_refs、artifact_refs、pending_input_request_ids、final_status。不保存领域智能体内部的推理循环、工具结果、产物正文或记忆——那些属执行轨迹、产物存储与第三章；不存在「大 Supervisor Memory」。模式是每次领域任务终止，Supervisor 被再次调用：第一次看到空状态 → create DT10；DT10 succeeded 后第二次 → create DT20；全部终止产物齐备第三次 → complete_parent_task。它每轮看到的不是几十轮聊天历史，而是第二章装配链投给它的结构化状态——自己的模型调用同样走 call_model → ContextAssemblyRequest → 装配器，状态栏的执行议程区块由 OrchestrationState 投影生成。

**10. Q：**训练产物 A100 怎么进入饮食智能体的上下文？为什么 Diet 看不到 Workout 的完整历史？

**A：**DT20 携带 input_artifact_refs = [A100@v1]，饮食智能体调用模型时由第二章装配器经 ArtifactReader 按引用与版本读取，以 task_artifact 块进入上下文，清单 artifact_refs 登记；Supervisor 不把 A100 正文手工拼进 Diet 的提示词。Diet 看到的是结构化结果（训练日、时间、负荷、营养含义），看不到训练智能体的完整对话、工具执行轨迹与推理过程——完整历史里混着与当前任务无关的过程，交接的是结构化结果。版本钉死：DT20 固定引用 A100@v1，若 v1 已被 DT30 产出的 v2 取代（v1 → superseded）且不再允许消费，装配读取显式失败、DT20 标记 stale，由 Supervisor 决定创建引用 v2 的新任务——版本钉死加显式失败，替代自动升级。

## 缺输入与冲突

**11. Q：**InputRequest（IR50）的链路是什么？为什么要稳定身份？

**A：**训练智能体缺必要输入 → AgentResult(DT10, needs_input, input_request=IR50)（字段：input_request_id / domain_task_id / parent_task_id / field / question / status）→ 根运行时：DT10 → waiting_input，T200.pending_input_request_ids += IR50 → Supervisor 被再次调用 → SupervisorAction(request_user_input) → 主会话向用户提出 IR50 的问题。匿名 {field, question} 字典做不到可恢复：无法登记到等待清单、无法匹配回答、无法取消。子智能体不持有主会话控制权，问题统一经 Supervisor 从主会话提出；IR50、IR51 可以合并成一次用户提问展示，但底层映射不能丢——合并的是展示，不是身份。

**12. Q：**用户回答后怎么恢复？普通会话消息为什么不行？

**A：**用户回答携带 input_request_id 的结构化提交 → Input Resolution：IR50 = answered（答案写入请求记录）→ 根运行时明确知道 IR50 属于 DT10 → DT10 → runnable，T200 恢复（复用第一章中断与恢复机制，新 Run 段，任务与领域任务都不重建）。Supervisor 不重新读聊天历史猜「这句话应该是回答训练智能体的吧」；等待期间用户问「香蕉训练前吃可以吗？」是普通新消息，由 Supervisor 直接回答或按需委派，不解除等待。边界：会话输入 ≠ 领域任务恢复输入，与第一章「会话继续不打扰任务」是同一条。

**13. Q：**跨领域约束 XC10 和冲突报告 CR20 是什么？冲突的裁决路径有哪些？

**A：**CrossDomainConstraint 是训练结果影响饮食任务的载体，必须带来源身份：constraint_id、parent_task_id、source_domain_task_id（DT10）、source_artifact_ref（A100@v1）、source_domain / target_domain、type（如 nutrition_requirement）、payload（如额外碳水需求）——Diet 收到的不能是一段无来源文本。Diet 无法满足时返回 ConflictReport（conflict_id、domain_task_id、constraint_refs、reason_code、summary、affected_artifact_refs）后终止，不能直接把训练计划改轻一点——修改训练计划越过了领域所有权，两个智能体不共享同一业务事实的修改权。控制权随 CR20 回到 Supervisor，三类裁决：A 创建训练修订任务 DT30（input_conflict_refs = [CR20]）；B 询问用户是否修改目标；C 任务策略允许时返回明确标注无法同时满足的部分结果。无论选哪条，实际创建任务仍经根运行时校验——Supervisor 决定业务方向，运行时决定状态条件。

## 异步与收尾

**14. Q：**后台任务完成后为什么不能直接完成父任务？T200 最终谁决定 COMPLETED？

**A：**后台完成只表示 DT10 succeeded，父目标可能还有未执行的领域任务；异步回调直接把父任务判完成会跳过编排判断——「这个领域做完了」和「用户的整个目标达成了」是两个判断。完成链路：异步完成事件 → 根运行时更新 DT10（先确认产物已持久化并通过 succeeded 校验）→ 父任务重新可评估 → Supervisor 被再次调用决定下一步。T200 的完成 = Supervisor 声明 complete_parent_task（业务上可以结束）+ 根运行时按 ParentTaskPolicy 校验（状态条件允许结束）：所有必需领域任务已终止、必需产物类型齐备、没有未解决冲突、没有等待中的输入请求、partial_result_policy 满足。部分结果是创建参数不是临时发挥：allowed 时一成一败可返回训练部分结果并明确说明饮食失败；not_allowed 时不能把部分信息包装成完整成功。

**15. Q：**Supervisor 决策节点重放怎么办？ensure_domain_task 的键是什么？

**A：**第一次已创建 DT20 但返回前进程异常，重放后再次请求「创建饮食任务」；创建语义若是无条件的，库里会出现 DT20、DT21 两个相同逻辑工作单元。所以领域任务创建必须是 ensure_domain_task 语义，键 =（parent_task_id、target_domain、objective_key 委派目标的稳定业务键、输入产物的版本组合）get_or_create。这是与第一章 prepare_invocation 的 get_or_create、第三章写入路径幂等键同一条约束在三个层的落点：决策节点允许重放，结构化委派必须幂等。不需要分布式锁。

**16. Q：**DT10 succeeded 之后，正式训练计划改了吗？

**A：**没有。训练产物 A110（WorkoutPlanDraft）status = ready 只表示它已作为协作结果确认完成；产物协议层没有 committed 一类状态，正式训练计划的变更要等用户确认后经第四章调用实例提交，业务库才出现新版本。DT10 succeeded 不自动意味着业务数据库已被修改——「协作完成」不能被误读成「业务数据库已修改」。

## 困难与演化

> 题源：[[找工作啊啊啊啊/项目梳理/个人健康管理agent/5.把编排责任交还 Supervisor/11.困难以及应对办法|11.困难以及应对办法]]

**17. Q：**旧版分层（真实代码）为什么回答不了「谁持续推进跨领域目标」？

**A：**旧版结构 Root Router → Domain Team → Planner → Orchestrator → Worker，隐含假设「一次用户任务只需要选择一个主要领域，进入领域后该领域自己能完成剩余任务」。代码事实：顶层路由是一次性的——模型完成工具调用后代码只读 tool_calls[0] 生成唯一 next_node，只回答「这次请求先去哪个节点」，不回答「这个任务需要哪些领域参与、第一个领域完成后下一步做什么」；领域内部流程状态全存 TeamState（plan、current_step_index、next_worker、worker_output、task_results、scratchpad），Orchestrator 按计划串行推进、可并行步骤用 asyncio.gather() 收集结果；Worker 是 create_react_agent() 创建的「无状态工具人」，只拿 manager_instruction、不注入 recalled_memories；后来加 fast-path 在能直接确定工具时跳过 ReAct 循环。跨领域目标下，谁创建下一个领域任务、哪份结果能作为下游正式输入、冲突后谁调度、确认后从谁恢复、何时算完成——全都没有归属；与此同时领域内部编排反而过重，编排器-工人层级对多数简单操作只是重复描述已知状态机。

**18. Q：**给顶层路由加组合规则为什么不够？根因怎么表述？

**A：**为「训练 + 饮食」这类固定组合写专门节点，少数组合下可用；协作方式一多，根图就要承担大量业务组合逻辑（能否并行、是否必须先完成、冲突后是否再次调用、谁最终合成、确认后从谁恢复）。即便让路由一次返回多个工具调用，也只能表达「A 和 B 都需要执行」，无法表达「A 产出结构化结果、B 消费它」的依赖，也没有跨智能体结果的所有权和交付格式。不断加条件，最终会把单步分类器写成一个隐式的会话主管——功能上接近了，但身份、职责和恢复语义都不是显式设计出来的。根因：问题不在某个组件写错，而在整体任务编排责任放错了层级——顶层只有一次性路由，领域内部却对简单操作默认采用重编排层级。

**19. Q：**重构怎么重新划分控制范围？五个组成部分是什么？新增了哪些成本？

**A：**三个控制范围：Root StateGraph 运行时控制（任务状态推进与恢复）／ Supervisor 会话级编排（谁负责持续推进整个任务）／ Domain Agent 领域级执行（ReAct / 领域工作流）。五个组成部分：① 不默认使用多智能体——单智能体配合提示词和工具多数时候够用，只有形成独立的数据所有权、工具集合、业务工作流或大规模专业上下文时才提升为领域智能体（判断标准是能力所有权，不是话题分类）；② 领域内部不设固定层级、独立路由并入会话主管——路由与会话主管是重复的语义判断；③ 智能体之间传结构化任务与产物（DomainTask / AgentResult / 版本化 Artifact），不共享完整对话历史；④ 缺输入与跨领域冲突都交还会话主管（子智能体不持有会话控制权、不越权改对方领域）；⑤ 后台异步是任务的一种执行方式（持久执行记录 + 确定性状态恢复，不是把函数写成 async def）。共同点：没有会话主管时，这五件事都需要某个智能体从聊天历史里猜。成本：一次委派比直接回答多一轮模型调用；DomainTask / AgentResult / Artifact 协议要维护；任务依赖图当前只覆盖单跳和少量多跳，没有通用图执行引擎；委派深度与任务数量靠配置化预算硬上限。
