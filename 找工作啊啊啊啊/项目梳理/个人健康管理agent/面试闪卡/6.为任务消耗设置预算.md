# 面试闪卡 · 第六章：为任务消耗设置预算

> [!info] 用法
> 一问一答背诵卡。答案保留冻结术语与 ID；事实以 [[10.代码级逻辑：一个 Task 如何被预算与调度治理]] 为准。

## 主问题与边界

> 题源：[[找工作啊啊啊啊/项目梳理/个人健康管理agent/6.为任务消耗设置预算/1.总览|1.总览]]、[[10.代码级逻辑：一个 Task 如何被预算与调度治理]]

**1. Q：**第六章回答的唯一主问题是什么？从什么推导出来？

**A：**一个长期运行的 Task 最多允许消耗多少系统资源。从前五章因果推导：一个任务可能跨 R1 的多次模型调用、工具调用、双领域领域任务、HIL 暂停、R2 恢复、后台执行——Task 生命周期超过 Request 生命周期，HTTP 请求数量不等于任务的实际资源消耗，治理基本单位必须从请求提升到任务。不虚构用户规模与线上事故。

**2. Q：**治理链上的四个身份是什么？

**A：**AgentTask（T100 / T200，逻辑任务，预算绑定在它身上）；Run（R1 / R2，连续执行阶段——执行段换了任务没换，预算也不能换）；资源调用 Resource Call（逻辑模型调用 LC300 与工具调用实例 I300，预算的实际消耗者）；调度项 SchedulingItem（SI100，「某个已有 Task / Run 当前等待一次执行机会」的短暂事实，由调度器在入队时创建、取得槽位后消费）。调度项不是新任务：没有业务目标、没有检查点、没有预算，挂靠在 run_id 上（一个任务的每段执行各自排队），可丢可重建。

## 预算机制

**3. Q：**TaskBudget 的结构是什么？为什么跨 Run 累计？

**A：**三维上限 max_llm_calls / max_tool_invocations / max_active_runtime，与三个 used_* 字段一一对应；status（NORMAL / LOW / EXHAUSTED，LOW 是提示、EXHAUSTED 是拒绝）；version（乐观并发）；task_id + policy_id。使用量随任务控制状态一起持久化，跨 Run 累计。绑 Run 的话 R1 → R2 变成重新拨款，任务可以通过「暂停—恢复」循环无限续额度；绑 Request 的话一次暂停恢复就逃出治理——预算要约束的是逻辑目标全程的自主行动总量。

**4. Q：**预算上限谁决定？模型能改自己的预算吗？

**A：**BudgetPolicyResolver 把 task_type / difficulty / execution_mode（第五章的委派字段）映射到预配置的策略表（ordinary_qa / complex_plan / cross_domain_plan / background_analysis 各有额度档，具体数值是部署配置不是架构的一部分）。Supervisor 可以判断「这是跨领域计划任务」，但不能直接填 max_llm_calls——模型表达复杂度，资源权限留在运行时（与第五章业务决策与状态修改分离同构）。模型通过第二章 AgentStatus 看到一份只读的 BudgetView（剩余次数 + 状态），看到 LOW 可以减少探索优先收敛，但改不了额度；真正的执行门槛在 BudgetManager.consume，失败抛 BudgetDenied，真实调用不发生——被治理者不能写治理规则。

**5. Q：**consume_once 的幂等键是什么？怎么保证原子？

**A：**每次扣减写一条 BudgetCharge，逻辑唯一键 = task_id + resource_type + operation_id。操作身份的稳定性来自前章设计：工具侧 operation_id = I300（同一实例的 Attempt 1 / 2 / 3 不重复扣，重试复用同一条记录）；模型侧 logical_call_id = LC300（底层 API 网络重试换连接、按 Retry-After 重发仍属同一个 LC——一次逻辑模型决策不等于一次网络尝试）；时间侧 = 切片 ES10（每个切片最多结算一次）。检查与扣减在同一事务：锁定预算行（SELECT … FOR UPDATE）→ 额度检查 → 扣减 → version 自增 → 写扣减记录（唯一键防重）。剩余 1 次额度时 DT10、DT20 并发申请，事务串行化保证恰好一个成功、另一个 BudgetExceeded——不需要分布式锁，与第三章 SUPERSEDE 条件更新、第五章 ensure_domain_task 是同一条约束在不同层的落点。

**6. Q：**预算什么时候扣？失败退款吗？

**A：**统一口径：运行时接受一个新的逻辑 LLM 调用或工具调用实例时，就消费一次预算。I300 在 prepare_invocation 被运行时接受的那一刻工具预算 +1，即使后续执行因依赖故障失败也不退款——TaskBudget 限制的是「智能体能自主发起多少逻辑动作」，不只是 API 账单，一次已发起的动作无论成败都消耗了任务的自主行动额度。预算计「发起」，熔断计「依赖健康」，两个账本各记各的。

**7. Q：**active_runtime 怎么算？硬限制怎么不超支？

**A：**以执行切片（ExecutionSlice）为计时载体：取得执行槽位时开始、释放时结束，时长结算进 used_active_runtime；并行切片各自计时各自结算。它不是墙钟时间：队列等待、HIL 等待、纯人工等待都不算——用户离开三小时再确认，任务一分钱预算都没花（把排队和人工等待计进预算，等于惩罚「等待慢」而不是限制「消耗多」）。硬限制不靠事后结算发现：切片开始时把剩余时间额度换算成 slice_deadline = now + remaining，执行过程中 Runtime 在已有确定性边界（下一次逻辑调用发起前、人工介入中断前）检查，超过后第一个边界即 BudgetExceeded(active_runtime)，不为切片引入抢占式计时器。

## 调度与并发

**8. Q：**Admission 和 Resume 为什么分开？

**A：**新任务过准入控制器（AdmissionController，Harness 内的检查步骤不是独立服务）：当前用户活跃任务数 < 每用户上限、交互队列压力 < 容量、背压档位允许接收——任一不过 AdmissionRejected，任务与预算都不创建。已有任务的恢复不走 Admission：第一章恢复校验链 + 受理事务通过后 ensure_scheduled(T100, R2) 生成 SI101 入队等槽。不重新准入、不重建预算、不重置 usage——任务已被系统接受并消耗了预算，用户确认的是既有动作不是新增负载；拒绝恢复等于丢弃已承诺的工作。口径：拒绝新增负载 ≠ 丢弃已接受任务。

**9. Q：**背压三档分别怎么表现？

**A：**NORMAL：新交互 / 新后台任务正常接受，已有任务正常执行。PRESSURED：交互正常接受，新后台任务延后或拒绝新增。SATURATED：新交互任务也 AdmissionRejected(SYSTEM_BUSY)（硬上限是系统自我保护的最后防线，拒绝比让所有任务一起长时间等待更诚实），新后台任务拒绝，已有任务不删除只等待资源——已处于 WAITING_HUMAN 的 T100 在用户确认后照常登记 R2、QUEUED 等槽。分工：有限并发限制正在执行的任务数（执行侧），背压在饱和时从源头限制新任务进入（进入侧），防止等待队列无限增长。

**10. Q：**HIL 期间槽位和预算怎么处理？

**A：**T100 / R1 执行到 wait_for_human → 检查点持久化 → ExecutionSlice ES100 结算 active_runtime → 释放任务执行槽位 → WAITING_HUMAN。用户等待的三小时里不占槽位、active_runtime 不增长、队列里其他任务正常拿槽执行。确认后走第一章恢复校验与受理事务（登记 R2、I300 → APPROVED），ensure_scheduled 生成 SI101、重新排队、重新取槽——预算继续累计（R1 usage + R2 usage），任务还是原来那个任务。

**11. Q：**三种并发控制对象为什么互不等价？

**A：**任务执行信号量（TaskExecutionSemaphore）限制「同时真正推进多少个 Agent Task / Run」，取得它获得执行槽位；LLM Semaphore 与 Tool Semaphore 限制任务内部对模型与工具的并发调用（模型 API 并发是 Harness 同时向外部模型服务发出的请求数，不是模型实例池）；SystemBackgroundSemaphore 单独限制不属于任何 AgentTask 的系统后台 Job（如记忆巩固）——不占任务槽位、不走 LLM / Tool 信号量、不涉及 TaskBudget。组合关系：T100 取得槽位不代表可以无限并发调用 LLM（槽位内每次调用还要过信号量）；信号量有空位也不代表任务可以执行（没槽位任务根本没在推进）。区分标准一条：有 task_id 的走调度链与 TaskBudget，没有 task_id 的走 SystemBackgroundSemaphore。后台 DomainTask 走同一条调度链（trigger = background、优先级低），切片的 task_id 填 T200、run_id 填 AE500 自己的 run_id，消耗从父任务 T200 的预算扣——后台是执行方式，不是第二类资源通道。

**12. Q：**为什么队列不是事实源？进程重启怎么恢复？

**A：**真实任务状态在持久 Runtime（第一章控制索引 + 检查点），进程内队列只是当前实例的调度索引，只回答「谁在排队」。进程崩溃时队列消失、任务不消失——T100 还在 WAITING_HUMAN，已登记的 R2 还是 R2，丢掉的只有调度项。进程启动时调度器恢复（Scheduler Recovery）扫描持久 Runtime 中「任务未到终态、未停在等待人工介入、当前 Run 已受理但未执行到终点」的条目（已停在 WAITING_HUMAN 的不在此列：它们等的是用户，不是槽位），逐条 ensure_scheduled(task_id, run_id) 重新生成调度项。ensure_scheduled 以（task_id, run_id）为键去重，Resume 网络重试两次调用不会出现两个并行 SI101。调度侧的排队状态不进入任务状态机。

## 熔断与统一顺序

**13. Q：**熔断器的状态机是什么？哪些失败计入？

**A：**DependencyCircuit 按共享外部依赖（model_api / exercise_search_api / nutrition_service）维护：CLOSED（正常）→ 连续失败达到阈值 → OPEN（熔断，后续调用直接返回 DependencyUnavailable，不占外部调用槽位）→ 冷却到 next_probe_at → HALF_OPEN（只放行少量探测请求：成功则计数清零回 CLOSED，失败则回 OPEN 重新计时）。熔断属于共享 Runtime 不属于某个任务——每个任务各自维护等于各自验证一遍相同故障，失去止损意义。计入的错误：Timeout、429、5xx、连接失败（说明共享依赖本身异常）；不计入：参数校验失败、权限拒绝、业务规则拒绝、HIL 拒绝（个别请求的问题，依赖可能完全健康）。计数单位是逻辑调用的最终结果，不是 Retry Attempt：LC300 前两次 timeout 第三次 success，逻辑调用最终成功、计数清零；只有全部尝试失败才 +1——按 Attempt 累加会让一次逻辑失败被网络重试放大成多次计数，阈值被重试噪音淹没。熔断不决定业务降级：返回 DependencyUnavailable 后，第三章 optional 证据走 PARTIAL、required 走 FAILED 的既有语义接管。

**14. Q：**Retry 和 Circuit Breaker 的区别？一次资源调用的统一顺序是什么？

**A：**Retry（第四章）回答「这一次调用失败后怎么办」，在单次调用内部；Circuit（第六章）回答「这个共享依赖现在还值不值得继续调用」，在依赖层面。统一顺序：
```text
① BudgetManager.consume_once   # 预算：这个任务还能不能发起动作
② Circuit.allow                # 熔断：这个依赖现在值不值得调
③ Resource Gate acquire        # 信号量：有没有并发空位
④ 真实调用                     # Model API / Tool Runtime
⑤ record dependency outcome    # 按逻辑调用最终结果记账
⑥ release Resource Gate
```
顺序的含义：熔断 OPEN 时不占外部调用槽位（②失败短路），预算耗尽时连依赖健康都不用查（①失败更早短路）。跨人工介入的 I300 拆在两个时点：预算扣减发生在运行时接受它的时刻（prepare_invocation），熔断检查与信号量获取发生在每次真实执行前——顺序不变，中间隔了一段等待。

**15. Q：**预算耗尽后谁来停止执行？

**A：**运行时，不靠模型自觉。模型仍可能发起新的逻辑调用 LC9：consume_once 额度检查失败 → BudgetExceeded → LLM Gateway 不发出真实调用 → budget.status = EXHAUSTED → 图无法继续推进 → 任务 FAILED（failure_code = BUDGET_EXHAUSTED），已有产物按第五章 partial_result_policy 处理。LOW 与 EXHAUSTED 待遇不同：LOW 只是提示，视图把剩余额度带给模型供收敛；EXHAUSTED 是拒绝，运行时不再接受对应的自主调用。两种情况下模型都无法给任务续预算。

**16. Q：**被追问「单人使用的系统为什么要这套治理」怎么答？

**A：**诚实口径：治理单位从「Task 生命周期超过 Request 生命周期」推导，不是从用户规模推导，没有虚构用户量与线上事故；按当前单人使用规模属于「值得设计、暂不必部署」。当前组合——单实例 + 进程内 Queue + 持久 Task State + Semaphore + 简单 Circuit Breaker——已覆盖当前规模，不新增 Kafka / Redis Queue / Celery / 分布式调度器 / 分布式锁。主动交代的遗留边界：队列非持久（重建靠恢复扫描）、优先级只有两级（后台任务可能长期饥饿）、熔断是单实例状态（多实例间不共享依赖健康）；只有出现多实例部署、任务跨实例执行、后台长期饥饿这几种情况才值得升级。

## 困难与演化

> 题源：[[找工作啊啊啊啊/项目梳理/个人健康管理agent/6.为任务消耗设置预算/9.困难以及应对办法|9.困难以及应对办法]]

**17. Q：**第六章的演化起点是什么？困难在哪里表现最明显？

**A：**旧设计（雏形）：资源控制停留在请求层和单次调用层——限制 HTTP 请求数量、给单次工具调用设超时和重试，没有针对智能体任务的专门治理。早期短任务下合理：一次请求只含少量模型与工具调用，请求本身与真实资源消耗基本接近。双领域智能体、人工介入、后台任务加入后，请求成本与任务成本脱离：两个占相同接口并发的请求，一个只做一次模型调用，另一个在 ReAct 循环里连续多轮模型调用、知识检索和工具调用，还可能中途等人工确认、恢复后再次执行。最明显的表现是长任务：状态判断不稳定时模型调用与工具查询持续循环，旧实现没有任务级统一执行边界，只要每次调用本身不报错任务就能无限推进；记忆巩固等后台任务还与交互任务共享执行资源。

**18. Q：**继续在请求层 / 单次调用层加限制为什么解决不了？根因是什么？

**A：**请求层、智能体层、工具层分别只有局部限制：一次工具调用知道自己最多重试几次，却不知道整个任务已经调用了多少次工具；一个 HTTP Handler 知道自己是否正在执行，却不知道它内部还会继续产生多少轮模型调用。它们无法统一回答两个问题：「这个任务最多允许执行到什么程度」「多个任务竞争资源时谁应该先获得执行机会」。根因：不是某个工具的重试配置不合理，而是缺少以逻辑智能体任务为单位的资源治理边界。

**19. Q：**改造引入了什么？为什么克制在当前规模？

**A：**改造：任务创建时由运行时策略分配任务预算（三维上限，使用量随控制状态持久化、恢复后继续用剩余额度）；多任务先过轻量准入进有界队列，交互优先于后台，模型 / 工具 / 后台各经有限槽位控并发；HIL 中断释放槽位、恢复重新调度；队列接近上限时背压延后后台任务、限制新任务积压；外部依赖保护从单次调用提升到跨任务层级——按多个任务对同一依赖的失败判断整体健康，熔断阻止后续任务分别等待重试。克制：仍用进程内队列、Semaphore、轻量策略配置，不引入分布式消息系统或调度平台——治理能力与系统当前规模保持一致。遗留升级触发条件：大量长后台任务或要求重启后保留排队顺序才上 Redis 队列；后台长期饥饿才加 aging 或预留槽位；「合法任务经常在接近完成时耗尽预算」成为稳定现象才考虑受控预算扩展；多实例部署成为真实需求才共享依赖健康状态。
