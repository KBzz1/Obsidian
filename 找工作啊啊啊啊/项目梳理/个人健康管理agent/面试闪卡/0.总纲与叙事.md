# 面试闪卡 · 总纲与叙事

> [!info] 用法
> 一问一答背诵卡，覆盖项目主线、Hero Scenario、七次边界、三条设计原则、实现真实性口径与薄弱点风险题；七章细节见本目录各章闪卡。事实与冻结口径一致，冲突时以 [[项目总览]]、[[实现真实性地图]] 与各章代码级逻辑笔记为准。

## 项目定位与主线

> 题源：[[项目总览]]

**1. Q：**面试官让你介绍这个项目，主线怎么讲？

**A：**个人健康管理 agent 是健身 / 饮食健康管理系统，训练与饮食两个领域分别由训练智能体与饮食智能体负责，每日计划是训练智能体内部的领域工作流。项目讲的主线是：系统从「一次请求对应一次智能体执行、一轮模型调用加少量工具调用」的「会聊天、会查数据的智能体」起步——用户请求、聊天历史、工具调用三者互相可推断；业务复杂度上升后，这些靠一次请求和聊天历史隐式表达的系统语义逐一失效，必须逐步提升成明确的 Harness（智能体运行框架，负责承载和约束智能体执行）机制。

**2. Q：**最初的简单形态为什么当时合理？后来哪里不对了？

**A：**当时请求短、任务生命周期等于请求生命周期、工具调用即执行、信息都在聊天里，隐含假设成立。失效的是这组假设：任务要暂停等待用户确认（生命周期超过请求）；历史持续积累而模型每轮只需要当前判断所需的信息；「以后只能晚上训练」这类跨任务事实与正式业务事实混不进聊天历史；模型提议不等于真实业务修改；跨领域目标没有持续负责人；请求成本不再代表任务消耗；最终回答错了无法定位哪一层出错。

## Hero Scenario 与七次边界

**3. Q：**Hero Scenario 是什么？为什么选它？

**A：**用户过去习惯早晨训练，因工作安排变化说「以后工作日只能晚上训练了。最近训练量也有点大，帮我重新调整一下这周的训练计划，饮食也跟着调整一下」。这句话表面上是一句话，从「生成新计划」走到「最终建议」会依次出现七个矛盾，每个都是原来靠聊天历史和一次请求隐式表达、现在必须变成明确机制的问题，出现顺序与七章一一对应。它是为统一解释七章架构选择的复杂案例，不是每个请求都走全链路——系统渐进升级，只在请求确实需要的层上付出成本。

**4. Q：**七次边界变化（七个不等式）分别是什么？

**A：**
```text
Conversation ≠ Task                                    （第一章：任务执行到哪里）
完整 Runtime State ≠ 模型本轮上下文                     （第二章：模型本轮看到什么）
Task State ≠ 长期用户事实 ≠ 正式业务事实 ≠ 外部领域知识 （第三章：跨任务的信息从哪来）
LLM Tool Call ≠ 工具运行时接管的动作 ≠ 真实业务修改     （第四章：动作如何安全执行）
跨领域整体编排 ≠ 单领域内部执行                         （第五章：谁持续推进整个目标）
Request ≠ Task 资源成本                                 （第六章：任务允许消耗多少资源）
最终回答质量 ≠ 整个执行链路正确性                       （第七章：错在哪一层）
```

**5. Q：**Hero Scenario 的七个矛盾分别怎么对应七章？

**A：**① 新方案等用户确认、会话还在继续——任务暂停但不锁会话；② 完整保存的运行历史与按需供给的本轮上下文分开；③「以后只能晚上训练」是长期用户事实、当前生效计划是正式业务事实、还有长期偏好与外部训练 / 饮食知识，四类信息生命周期与权威来源各不相同；④ 用户确认后系统真正修改业务数据，模型输出「应该替换计划」只是提议；⑤ 训练的结构化结果（时间、日期、负荷）是饮食调整的输入，跨领域要有持续负责人——旧版顶层 Root Router 只做一次性领域选择，没有这个角色；⑥ 一个任务跨多次请求、多轮模型、多个工具、人工确认、双领域，请求数不再代表资源消耗；⑦ 最终建议错了，错误可能来自记忆没取到、检索没命中、上下文没装载、判断错、工具执行错、跨领域传递丢、最终描述错七层中任何一层。

## 设计原则与章节展开

**6. Q：**七章背后的三条统一设计原则是什么？

**A：**① 不同生命周期、不同权威来源的数据必须分开——不是「架构上就应该分层」，而是任务运行状态、正式业务事实、模型本轮看到的内容、跨任务长期事实在维护者、生命周期、可否恢复、是否代表现实、是否该进上下文这些维度上确实不同，混在一起必然互相干扰。② LLM 处理模糊语义，确定性程序维护明确系统状态——判断标准：一个问题在系统中应该存在唯一确定答案时，就不要让模型猜。③ 跨重要边界传递信息优先用稳定结构而不是聊天历史——AgentStatus、Evidence、DomainTask、Artifact、ToolInvocation、ExecutionRecord、Trace 各解决一个「靠聊天历史说不清」的问题（模型猜阶段、证据无法引用、任务目标含糊、交付靠猜、动作无身份、执行无法定位、错误无法归因）。

**7. Q：**七章是七个并列专题吗？章节顺序怎么理解？

**A：**不是并列，是按业务复杂度和系统依赖逐层展开的一条主线：上一章先明确一种边界，边界清楚之后系统承担更复杂业务时，下一类原本混在当前边界里的问题才作为独立问题显形。但这不是单线程因果——长期记忆的需求不是有了上下文装配器才产生，工具安全与多智能体协作也各有独立动因；只是边界没明确之前，下一类问题与它混在一起、归属不清。例子：装配器明确了当前任务内已有信息怎么进入模型，这条边界清楚后，「任务结束以后还要继续存在的信息」才能与任务状态清楚分开，长期记忆由此成为独立机制边界。

**8. Q：**简单请求和复杂请求在系统里怎么分级？

**A：**
```text
普通问答                  → 简单回答（会话主管直接答）
需要当前业务数据           → 单领域智能体 / 查询工具
需要长期个人事实           → 记忆检索
需要外部专业知识           → RAG
需要修改真实业务数据       → 工具运行时
达到风险条件               → 人工介入（HIL）
真正跨领域                 → 会话主管 + 领域智能体
长生命周期或成本较高       → Task 级运行时治理
```
例子：「高 GI 食物是什么」不触发任何后续模块；「我昨天深蹲做了多少」委派训练智能体查数据；「根据最近四周训练量调整计划」走记忆 + 证据 + 领域工作流。这也是各章「不默认 X」式克制的原因：系统只在需要的层付出成本。

**9. Q：**整个项目最终回答的一个问题是什么？

**A：**一个健康管理 Agent 从短对话演化成能长期运行、跨会话记忆、调用真实工具、等待用户确认、跨领域协作并产生真实业务修改的系统以后，原来可以靠一次请求、聊天历史和简单 Tool Call 隐式表达的系统语义，必须逐步提升成明确的 Harness 机制。七章就是七次「语义显式化」：任务生命周期、模型上下文、跨任务信息、动作执行、跨领域编排、资源治理、质量反馈。最终系统不再靠模型从历史里猜「现在执行到哪、该做什么、做没做成」，由 Harness 用确定性机制维护这些答案，模型只负责它擅长的语义判断。

## 实现真实性口径

> 题源：[[实现真实性地图]]

**10. Q：**项目实现到什么程度？面试口径怎么说？

**A：**七章统一口径「代码级逻辑已补齐，尚未实现」：架构细化到数据结构、调用链、状态写入时机与异常路径，可以自然翻译成代码，但真实代码仍然没有；补齐内容以各章代码级逻辑笔记为准。真实代码只覆盖旧版形态。两条纪律：不把设计说成已实现，不把构造的演化场景说成真实线上事故。

**11. Q：**仓库里真实存在的旧代码有哪些？

**A：**第五章旧分层 Root Router → Domain Team → Planner → Orchestrator → Worker：`tool_calls[0]` 一次性路由、`TeamState` 存全部流程状态、`create_react_agent()` 创建 Worker、`asyncio.gather()` 并行、fast-path 旁路；第二章直连式消息历史（模型回溯历史自判状态）；第六章请求层 + 单次调用层资源控制雏形（没有任务级执行边界）。这些都作为演化起点讲。

**12. Q：**哪些场景是构造的，不能说成线上事故？

**A：**第三章「原子事实 + 相似度覆盖」旧记忆方案（演示事实覆盖问题）、第六章请求层资源失控场景、第七章「输入 → 最终回答 → Judge」早期评估思路——都是为理解与面试训练构造的演化场景，不是真实线上事故，实现真实性地图里已标注。

## 薄弱点与风险题

> 题源：叙事重构报告 §8 / §9（工作区 docs/agent_review，未入库）

**13. Q：**被追问「上下文整理后 KV Cache 前缀失效实际损失多少命中率」怎么答？

**A：**诚实口径：当前没有量化或示例支撑，是已知薄弱点。已有的结论是布局原则——稳定系统提示词与固定职责在前、每轮都变的状态栏与最新输入压尾部，缓存失效只波及其后一小段；正确性优先于缓存友好。缺的是「整理触发后前缀缓存失效的代价计算」，属深挖清单第四项，量化示例需要用假设数字标注后再补。

**14. Q：**被追问「两份 Evidence 冲突时谁赢、要不要提示用户」怎么答？

**A：**诚实口径：当前只有边界声明，没有裁决流程。已冻结的边界：冲突不静默覆盖——同 claim_key、都标 current、value 不同时生成 `EvidenceConflict(unresolved)`；程序能判定的只有 current 优先于 historical；两个真正冲突的 current 不按最后更新时间或向量分数裁决真相，标记后交给下游。缺的是「两份冲突证据如何装配、如何向模型呈现」的具体流程（深挖清单第二项）。

**15. Q：**被追问「这套评估第一轮怎么跑起来」怎么答？

**A：**诚实口径：EvalCase、分层评估、Judge、Regression 机制完整，但没有任何已运行的评估实例或数据集规模数字。冷启动是深挖清单第三项：第一版测试数据集从 Hero Scenario 手工构造多少条、Judge 的 Rubric 怎么定第一版——尚未做，不虚构数字。

**16. Q：**次一级薄弱点有哪些？

**A：**第五章任务依赖图只覆盖单跳 / 少量多跳场景；第六章治理机制与单人使用规模的必要性张力。第六章的回答口径：治理单位从「Task 生命周期超过 Request」推导，不虚构用户规模与线上事故；按当前单人规模属于「值得设计、暂不必部署」，文档已诚实标注，遗留边界（进程内队列不持久化、优先级只有两级、单实例熔断）主动交代。

**17. Q：**项目下一步是什么？

**A：**七章跨模块总验收：检查 T100 从创建 → Context → Evidence → Tool → Multi-Agent → Runtime Governance → Evaluation 能否用同一套 ID、状态、Artifact 从头走到尾。当前各章走查身份是三套（第一章 T100、第二 / 三章 task_7001、第五章 T200），尚未统一，这正是总验收要暴露的问题；之后进入整体架构图与面试故事整理。
