# 通信协议与 Artifact

## Agent 之间传什么

不同智能体不直接共享完整会话历史（conversation history），也不通过自由形式的「智能体 A 给智能体 B 发一段话」协作。智能体之间交换的是结构化的任务、结果和产物。

会话主管（Supervisor）委派任务时生成一个明确的领域任务（DomainTask）。它不是第一章的 AgentTask，而是父任务内部的一项领域工作单元，因此身份字段统一命名为 `domain_task_id`，并用 `parent_task_id` 挂回父任务——同一个「task_id」不再同时指父任务和领域任务：

```python
class DomainTask:
    domain_task_id: str              # 领域任务身份，协作、产物溯源、状态推进都引用它
    parent_task_id: str              # 父 AgentTask 身份，把工作单元挂回用户目标

    target_domain: Literal["workout", "diet"]   # 目标领域；领域到智能体的映射由注册表配置

    objective: str                   # 本任务必须完成什么，不是简单复制用户原始消息
    constraints: list[str]           # Supervisor 明确委派出的任务约束

    evidence_requirements: list[str] # 完成本任务需要哪些信息的声明（如 state_key 或事实类型），
                                     # 真实事实由第三章检索、第二章装配按需获取，不随委派复制
    input_artifact_refs: list[str]   # 上游 Artifact 引用（含版本），用于跨 Agent 协作

    required_output_type: str        # 要求产出的 Artifact 类型，succeeded 判定用它校验

    depends_on: list[str]            # 前置领域任务，全部成功后本任务才可执行（runnable）
    execution_mode: Literal[          # 执行方式：sync 在父 Run 内执行；background 进入异步运行时
        "sync",
        "background"
    ]

    status: str                      # pending / running / waiting_input / succeeded /
                                     # conflict / failed / cancelled，由根运行时推进
    output_artifact_refs: list[str]  # succeeded 判定通过后由根运行时写入
```

`evidence_requirements` 表达「完成本任务需要知道什么」，不表达「这里复制一份我认为是真的东西」：用户长期事实、正式业务状态仍由第三章证据检索与第二章上下文装配在执行时获取，DomainTask 不保存第二份事实源。任务依赖图（Task DAG）不再有独立的 ChildTask 结构——DomainTask 本身就是 DAG 中的节点，`depends_on` 与状态直接是它的字段。

领域智能体（Domain Agent）完成后返回任务结果（AgentResult）：

```python
class AgentResult:
    domain_task_id: str              # 结果绑定的领域任务身份

    status: Literal[                 # 终止状态：成功 / 缺输入 / 冲突 / 失败
        "succeeded",
        "needs_input",
        "conflict",
        "failed"
    ]

    artifact_refs: list[str]         # 本任务产出的 Artifact 引用

    input_request: InputRequest | None   # status=needs_input 时，带稳定身份的输入请求（见 [[9.HIL 与异步任务]]）
    conflict: ConflictReport | None      # status=conflict 时，结构化冲突报告（见 [[8.跨领域协作与冲突]]）
    error_code: str | None               # status=failed 时，错误码
```

真正需要被其他智能体使用的结果保存为类型化产物（typed Artifact）：

```python
class DomainArtifact:
    artifact_id: str                 # Artifact 身份
    parent_task_id: str              # 属于哪个父 AgentTask
    producer_domain_task_id: str     # 由哪个领域任务产出——溯源、succeeded 校验、冲突排查都靠它

    artifact_type: str               # Artifact 类型，如 TrainingLoadAssessment
    producer_agent: str              # 生产者智能体，如 workout_agent / diet_agent

    version: int                     # 版本号
    status: Literal[                 # 生命周期：草稿 / 就绪 / 被取代
        "draft",
        "ready",
        "superseded"
    ]

    payload: dict                    # 结构化载荷
    created_at: datetime             # 创建时间
```

产物生命周期只有 `draft → ready → superseded`，没有「已提交」一类的状态。`ready` 表示产物已作为协作结果确认完成、可供下游消费；它仍然不等于业务状态生效——正式业务变更必须经第四章工具运行时的调用实例提交到领域服务。例如计划草稿 A110 `status = ready` 后，用户确认的动作是「经调用实例 → 领域服务 → 正式计划新版本」这条链，而不是「A110 状态翻转所以自动变成业务事实」。这条边界与第一章「草稿确认后才提交」是同一条（见 [[9.代码级逻辑：从提议到业务副作用]]）。

例如训练智能体（Workout Agent）可以产生 `TrainingLoadAssessment:v2`。饮食智能体（Diet Agent）接收到的是这个结构化结果，而不是训练智能体的完整大语言模型（LLM）对话和工具链路追踪（Tool Trace）。

## Artifact Store 与业务数据库的边界

产物存储（Artifact Store）并不替代业务数据库。

业务数据库保存用户已经成立的正式事实：Workout Session、Meal Log、Habit Check-in、当前正式 Workout Plan、当前正式 Nutrition Plan。产物（Artifact）保存一次智能体任务（Agent Task）在协作过程中产生的中间或交付产物：TrainingLoadAssessment、NutritionRecommendation、WorkoutPlanDraft、DietPlanDraft、AnalysisReport。

一个计划草稿首先可以作为 `WorkoutPlanDraft:v3` 存在于产物存储（Artifact Store）中。如果业务需要用户确认，确认后再通过对应的领域服务（Domain Service）/ 工具运行时（Runtime）将其提交为正式训练计划（Workout Plan）；提交成功后才成为正式业务事实。这避免了「大语言模型（LLM）生成了一段内容 = 业务数据库已经发生修改」的混淆，也避免把跨智能体协作需要的大量中间结果直接塞进根状态（Root State）。

状态因此分为三个作用域：

| 状态层级 | 保存内容 | 主要所有者 |
| --- | --- | --- |
| Runtime State | 当前任务、领域任务（DomainTask）状态、依赖、中断（interrupt）、产物引用（artifact ref） | Root StateGraph |
| Agent Working State | 当前智能体消息（Agent messages）、工具结果、局部执行状态 | 对应领域智能体 |
| Business State | 用户真实训练、饮食、习惯等正式数据 | Domain Service / DB |

产物（Artifact）位于运行时（Runtime）与业务状态（Business State）之间，承担跨智能体交付协议，但不会自动成为正式业务事实。四层持久化状态的划分见 [[5.Task Runtime、Checkpoint 和业务状态#四层状态分层]]。

## 边界问答

**1. Q：** 为什么智能体之间不直接共享完整会话历史（conversation history）？

**A：** 完整历史（history）里混杂着与当前任务无关的其他智能体过程。智能体之间交换的是领域任务（DomainTask）、任务结果（AgentResult）和领域产物（DomainArtifact），接收方拿到结构化结果而不是对方的内部对话和工具链路追踪（Tool Trace）。

**2. Q：** 产物存储（Artifact Store）为什么不替代业务数据库？

**A：** 两者保存的对象不同：业务数据库保存已经成立的正式事实，产物（Artifact）保存协作过程中的中间或交付产物。草稿确认后经领域服务（Domain Service）提交才成为正式事实，避免「大语言模型（LLM）生成内容 = 数据库已修改」的混淆。

**3. Q：** 为什么中间结果不直接塞进根状态（Root State）？

**A：** 跨智能体协作的中间结果量大且生命周期短，塞进根状态（Root State）会让控制状态膨胀。产物（Artifact）作为跨智能体交付协议独立存放，位于运行时状态（Runtime State）与业务状态（Business State）之间，既不污染控制状态也不污染业务数据。

**4. Q：** `objective` 为什么不是简单复制用户原始消息？

**A：** 领域任务（DomainTask）的 objective 表述的是「这个智能体当前必须完成什么」，由会话主管从用户请求中提炼。复制原始消息会把理解用户意图的负担转嫁给领域智能体（Domain Agent），也丢失了会话主管（Supervisor）拆分任务时的约束信息。
