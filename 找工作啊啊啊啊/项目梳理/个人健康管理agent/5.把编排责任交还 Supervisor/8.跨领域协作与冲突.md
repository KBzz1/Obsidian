# 跨领域协作与冲突

## 单领域任务

单领域任务只有一个明确所有者：

```text
User
 ↓
Supervisor
 ↓
Workout Agent
 ↓
Workout Artifact
 ↓
Supervisor
 ↓
User
```

会话主管（Supervisor）不介入训练智能体（Workout Agent）的具体领域推理，只负责定义目标、等待结果以及将结果整合进主会话。

## 跨领域任务与依赖判断

跨领域任务由会话主管判断依赖关系。

如果两个任务互不依赖，例如「分别分析我本周训练情况和饮食情况」，可以在同一次请求内并行执行：

```text
                 ┌─ Workout Agent ── WorkoutAnalysis
Supervisor ──────┤
                 └─ Diet Agent ───── DietAnalysis
                          ↓
                    Supervisor
                          ↓
                       summary
```

如果后一个任务依赖前一个结果，例如「根据我最近的训练负荷调整饮食」，则顺序执行：

```text
Supervisor
    ↓
Workout Task
    ↓
TrainingLoadArtifact
    ↓
Diet Task
    ↓
NutritionArtifact
    ↓
Supervisor
```

会话主管在这里承担持续的编排，而不是一次性路由。

## Task DAG

跨领域依赖以任务依赖图（Task DAG，有向无环的任务依赖图）表达。图中没有独立的 ChildTask 结构：**DomainTask 本身就是 DAG 中的节点**，依赖与状态直接是它的字段（完整结构见 [[6.通信协议与 Artifact]]）：

```text
DomainTask 字段中承担 DAG 职责的部分：

depends_on: list[str]            # 前置领域任务
status:                          # pending / running / waiting_input /
                                 # succeeded / conflict / failed / cancelled
input_artifact_refs: list[str]   # 输入 Artifact 引用（含版本）
output_artifact_refs: list[str]  # succeeded 判定通过后由根运行时写入
```

只有 `depends_on` 中的前置任务状态为 succeeded，后续任务才能进入可执行（runnable）状态；冲突（conflict）与失败（failed）不算成功，不能伪装成正常依赖。状态转换由根运行时确定性完成，领域智能体返回 AgentResult 后由运行时校验落状态，不采信模型自述（判定链见 [[12.代码级逻辑：Supervisor 如何持续推进跨领域任务]]）。

智能体不直接互相调用（训练智能体 ↔ 饮食智能体），而始终是训练智能体→ 会话主管（Supervisor）→ 饮食智能体（Diet Agent）。这样任务所有权（Task Ownership）、终止条件和跨域冲突都集中在会话主管层管理。

## 跨领域冲突处理

跨领域协作允许智能体提出影响其他领域的约束，但不能越过业务所有权直接修改其他领域状态。

例如训练智能体（Workout Agent）得出「high training load → additional carbohydrate availability required」，它可以生成带来源身份的跨领域约束：

```python
class CrossDomainConstraint:
    constraint_id: str               # 约束身份，如 XC10
    parent_task_id: str              # 属于哪个父任务
    source_domain_task_id: str       # 由哪个领域任务产出，如 DT10
    source_artifact_ref: str         # 依据哪份产物，如 A100@v1
    source_domain: str               # 约束来源领域
    target_domain: str               # 约束作用的目标领域
    type: str                        # 约束类型，如 nutrition_requirement
    payload: dict                    # 约束的结构化载荷
```

来源字段让下游拿到的不是一段无来源文本：看到约束就能回答它由哪个任务、依据哪份产物提出。会话主管（Supervisor）将该产物（Artifact）或约束（Constraint）作为下一次饮食任务（Diet Task）的输入。如果饮食智能体判断当前饮食限制无法满足该要求，则返回 `status = "conflict"` 与结构化的冲突报告，而不是自行修改训练计划（Workout Plan）：

```python
class ConflictReport:
    conflict_id: str                 # 冲突身份，如 CR20
    domain_task_id: str              # 报告冲突的领域任务
    constraint_refs: list[str]       # 冲突涉及的约束，如 [XC10]
    reason_code: str                 # 冲突原因码
    summary: str                     # 冲突内容摘要
    affected_artifact_refs: list[str]  # 受影响的产物
```

冲突的控制权回到会话主管，它在三类动作里裁决：创建新的训练修订任务、询问用户是否愿意修改目标、任务策略允许时返回明确标注无法同时满足的部分结果。例如选择修订训练时，Supervisor 根据冲突报告显式创建新任务：

```text
Workout
   ↓
constraint（XC10）
   ↓
Diet
   ↓
conflict（CR20）
   ↓
Supervisor 裁决
   ↓
Workout revision task（新任务，input_artifact_refs 指向原产物、
                      input_conflict_refs 指向 CR20，
                      不把冲突任务写进 depends_on——依赖只认 succeeded）
```

这种协作允许形成多跳，但不会让智能体无限制互相讨论。每个领域任务（DomainTask）都必须具有明确的 `required_output_type` 和终止状态，会话主管（Supervisor）对委派深度和任务数量设置配置化执行预算。完整的资源预算（Budget）和背压（Backpressure）在第六章定义。

## 失败与部分结果

所有子智能体（Subagent）调用必须返回明确的终止状态（terminal status），不能只返回一段自然语言让会话主管猜测执行是否成功。

如果一个跨领域任务需要训练（Workout）与饮食（Diet）两个结果才能成立，而训练任务（Workout Task）失败，则依赖训练产物（Workout Artifact）的饮食任务（Diet Task）不会启动，会话主管（Supervisor）也不能将现有部分信息包装成「完整结果」。

如果两个任务互不依赖，可以允许 `Workout = succeeded, Diet = failed`，然后根据任务策略决定返回部分结果还是整体失败。是否允许部分结果（partial result）由父任务创建时声明的策略字段（`partial_result_policy = allowed / not_allowed`）决定，而不是由会话主管临时发挥；父任务收尾时，根运行还要校验所有必需领域任务已终止、必需产物齐备、无未解决冲突、无等待中的输入（完成条件见 [[12.代码级逻辑：Supervisor 如何持续推进跨领域任务]]）。

领域智能体（Domain Agent）内部的工具重试（retry）、超时（timeout）、幂等和补偿不在这一章处理。智能体只消费工具运行时（Runtime）返回的确定执行结果。

## 边界问答

**1. Q：** 为什么智能体不直接互相调用，而要经过会话主管（Supervisor）？

**A：** 直接互相调用会把任务所有权（Task Ownership）、终止条件和跨域冲突分散到各智能体。始终走训练智能体→ 会话主管→ 饮食智能体（Diet Agent），让这些职责集中在会话主管（Supervisor）层管理。

**2. Q：** 跨领域依赖为什么用任务依赖图（Task DAG）而不是让模型读聊天推断？

**A：** 只有 `depends_on` 中的必要前置任务成功后，后续任务才可执行（runnable）。依赖关系由结构化状态确定，父任务恢复靠确定性的任务（Task）状态，而不是让模型重新读整段聊天猜测执行到哪。

**3. Q：** 饮食智能体满足不了训练负荷约束，为什么不自己改训练计划（Workout Plan）？

**A：** 改训练计划（Workout Plan）是越过业务所有权。饮食智能体（Diet Agent）返回 `status = "conflict"`，把冲突交给会话主管决定是否创建新的训练修订任务，形成多跳但不越权。

**4. Q：** 为什么部分结果（partial result）要由父任务（父 Task）声明，而不是会话主管（Supervisor）临时决定？

**A：** 是否允许部分结果取决于任务本身的语义（两个结果是否缺一不可），属于父任务（父 Task）的创建参数。让会话主管每次临时发挥，会把策略判断散布到运行时，也无法在创建时就明确下游依赖能否启动。

**5. Q：** 一个跨领域任务缺一个结果，为什么不能把现有部分信息包装成完整结果？

**A：** 依赖产物（Artifact）的任务（Task）在依赖失败时不会启动，现有信息不足以支撑结论。把部分结果包装成完整结果会掩盖失败，会话主管（Supervisor）只能如实返回失败或按声明的部分结果（partial result）策略处理。
