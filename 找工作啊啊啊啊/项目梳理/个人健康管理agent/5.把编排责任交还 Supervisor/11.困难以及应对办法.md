> 本笔记是第五章的取舍复盘。全章只有一个主问题：一个用户目标同时涉及训练与饮食两个领域时，谁负责持续推进整个目标。下面各节都围绕这个问题展开：旧版结构为什么回答不了它、为什么打补丁不够、当前方案怎样重新划分编排责任，以及这套方案带来的新成本。概念定义一律以链接指向归属笔记，不在此复述。

# 困难以及应对办法

## 演化起点：旧版结构为何不够

这一节以仓库里仍然存在的旧版实现作为事实起点。旧版并不是「写错了」，而是一套在单领域任务下成立的先选领域、再在领域内做规划-执行的分层；它隐含了一个后来不再成立的假设——一次用户任务只需要选择一个主要领域，进入领域后该领域自己就能完成剩余任务。下面的故障情形不是真实线上事故，而是根据这些真实机制反推出来的工程演化场景，用来解释为什么最终收敛到本笔记其余几节描述的决策。

旧版完整结构（顶层只做一次性领域选择，还不存在会话主管这个角色）：

```text
Root Router
    ↓
Domain Team
    ↓
Planner
    ↓
Orchestrator
    ↓
Worker ReAct Agent
    ↓
Tool
```

这一分层在代码里能对应上几处事实：

- 顶层路由是一次性的。模型完成工具调用（Tool Calling）后，代码只读取 `tool_calls[0]`，据此生成唯一的 `next_node`。它只回答「这次请求先去哪个节点」，不回答「这个任务需要哪些领域参与、它们之间有什么依赖、第一个领域完成后下一步做什么」。
- 领域内部的流程状态全部存在 `TeamState`：`plan`、`plan_history`、`current_step_index`、`manager_instruction`、`next_worker`、`worker_output`、`task_results`、`scratchpad`。Orchestrator（编排器）用它推进串行计划（`current_step_index` 加一），可并行步骤用 `asyncio.gather()` 并行执行、结果收集进 `task_results`。Worker 是用 `create_react_agent()` 创建的 ReAct（推理-行动循环）智能体，只拿到 `manager_instruction`，在自己的工具集合里跑循环，结果回写 `worker_output`、`task_results` 和 `scratchpad`；代码把它描述成「无状态工具人」，且不注入 `recalled_memories`。
- 后来加了 fast-path：当 Orchestrator 能直接确定工具时，跳过 Worker 的 ReAct 循环，直接把该步标记完成。

单看每个环节都合理。用 Hero Scenario 的跨领域请求检验这套结构就能看出问题：「以后工作日只能晚上训练，帮我调整这周的训练计划，饮食也跟着调整」需要先生成新的训练方案、再把新的训练日期、时间、负荷交给饮食领域继续调整。旧版最上层只有一个一次性路由，没有一个持续存在的角色知道这个目标现在完成到了哪里：谁创建下一个领域任务、训练的哪份结果能作为饮食的正式输入、两领域冲突后谁重新调度、用户确认后从哪个智能体恢复、整个目标什么时候算完成，这些问题在旧版结构里都没有归属。

与此同时，领域内部的编排反而很重：Orchestrator 的 plan 是 `{worker, instruction}`，`next_worker` 只从本领域计划中选 Worker，能回答「训练领域内下一步执行什么」，回答不了「训练完成后为什么启动饮食」。很多 Worker 的差异只是 Prompt 和工具白名单，却都拥有完整的 ReAct 循环；fast-path 的出现说明系统已经开始为简单任务绕开通用的规划-执行链路。

## 为什么继续打补丁不够

一个自然的补救是继续给顶层路由加组合规则：为「训练 + 饮食」这类固定组合写专门的节点。这在少数固定组合下可用，但协作方式一增加，根图就要承担大量业务组合逻辑（能否并行、是否必须先完成、冲突后是否再次调用、谁最终合成、用户确认后从哪个智能体恢复）。即便让路由一次返回多个工具调用，也只能表达「A 和 B 都需要执行」，无法表达「A 产出结构化结果、B 消费它」的依赖，也没有跨智能体结果的所有权和交付格式。不断加条件，最终会把这个单步分类器写成一个隐式的会话主管——功能上接近了，但身份、职责和恢复语义都不是显式设计出来的。

这指向同一个根因：问题不在某个组件写错，而在整体任务编排责任放错了层级。顶层只有一次性路由，没有跨领域的任务编排者；领域内部却对大量简单操作默认采用较重的编排器-工人层级。

## 当前设计：三个控制范围的重新划分

重构因此不是换一个多智能体框架的 API，而是重新划分三个控制范围：

```text
Root StateGraph          → 运行时控制（任务状态推进与恢复）
Conversation Supervisor  → 会话级编排（谁负责持续推进整个任务）
Domain Agent             → 领域级执行（ReAct / 领域工作流）
```

会话主管（Supervisor，持续持有主会话上下文的完整智能体）负责决定是否自己回答、是否调用智能体、调哪些智能体、智能体之间是什么依赖、如何依据前一个结果继续、什么时候整个任务才算完成。训练智能体、饮食智能体只负责领域内部的执行。任务的暂停、恢复、检查点仍由第一章的运行时控制承担。

下面的组成部分都服务于这一个主问题：没有会话主管时，每一项都需要由某个智能体从聊天历史里猜。

## 组成部分一：不默认使用多智能体

多智能体不是系统的默认执行方式。复杂任务并不天然要求拆成多个智能体，单智能体配合合适的提示词（Prompt）和工具很多时候已经能完成任务；默认拆分会让每次请求多一层调用成本，智能体之间的协调本身也带来新的复杂度。默认由会话主管完成任务，只有当某项能力形成独立的数据所有权、工具集合、业务工作流或大规模专业上下文时，才提升为独立的领域智能体（Domain Agent）——判断标准是能力所有权，不是话题分类。训练与饮食按这个标准成了自然领域边界；习惯只有创建、打卡、查状态等明确操作，仍作为轻量能力暴露给会话主管（升级标准见 [[3.多智能体边界与升级标准]]）。

委派的成本用减少无意义委派来控制：简单请求、常识问题、不依赖领域状态的问题留在会话主管层直接回答，只有真正需要领域独有能力时才委派（见 [[4.Supervisor 架构与委派#直接回答与委派的边界]]）。

## 组成部分二：领域内部不设固定层级，路由并入会话主管

训练、饮食智能体内部不再默认保留规划器 → 管理器 → 工人智能体 → 工具的固定层级——多数场景那只是在重复描述已知的状态机。开放式领域任务用 ReAct 循环处理：模型每轮决定调用哪个工具、拿到结果后继续，直到得到领域结果；已经稳定沉淀的流程作为领域工作流（Domain Workflow）整体调用，不再要求智能体每次重新规划（见 [[5.Domain Agent 执行模型]]）。

独立路由（Router）组件也被去掉。路由与会话主管会重复两次几乎相同的语义判断；既然会话主管在每一步都能动态决定直接回答、调用共享能力还是委派领域智能体，领域选择就应该是它决策的一部分，保留独立路由只会多一层没有增量信息的判断（见 [[4.Supervisor 架构与委派#不设独立 Router]]）。

## 组成部分三：智能体之间传结构化任务与产物

智能体之间不共享完整对话历史，也不以「A 给 B 发一段话」协作——接收方会拿到与当前任务无关的过程，而且无法确认对方执行到了哪一步。会话主管给领域智能体一个领域任务（DomainTask，目标、约束、需要的用户事实、上游产物引用）；领域智能体返回任务结果（AgentResult，终止状态、产物引用、缺失输入或冲突）；真正要被其他智能体使用的结果做成版本化的类型化产物（typed Artifact），由产物存储（Artifact Store）保存，不自动成为正式业务事实（协议见 [[6.通信协议与 Artifact]]）。在 Hero Scenario 里，「新训练方案的日期、时间、负荷」就是这样一份从训练流向饮食的产物，而不是饮食智能体自己去聊天历史里猜。

## 组成部分四：缺输入与跨领域冲突都交还会话主管

子智能体默认不持有与用户的会话控制权。发现缺输入时不自己发消息，而是返回 `needs_input`，由会话主管统一收集多个领域的请求后向用户发问，再按对应的子任务恢复执行。

跨领域协作允许智能体提出影响其他领域的约束，但不能越过业务所有权直接改对方的状态。饮食智能体可以读训练负荷作为营养调整依据，却不能直接改训练计划；当它无法满足训练负荷带来的营养要求时，返回 `status = "conflict"`，由会话主管判断是否创建新的训练修订任务——形成多跳，但不越权。会话主管对委派深度和任务数量设置配置化执行预算，避免智能体无限制互相讨论（见 [[8.跨领域协作与冲突#跨领域冲突处理]]）。

## 组成部分五：后台异步是任务的一种执行方式

后台任务不能靠单纯把函数写成 `async def` 就算异步。真正的异步是主智能体启动一个后台任务后继续运行，当前会话不等待任务完成；后台任务建立持久化的异步任务记录（AsyncAgentTask），完成后先持久化产物、再产生完成事件，父任务按确定性的任务状态恢复，而不是靠模型读聊天猜测进度（见 [[9.HIL 与异步任务]]）。这延续了第一章的边界：任务的推进状态由运行时维护，模型不猜。

## 为什么这些机制回答的是同一个问题

把上面五个组成部分放回主问题就能看到它们的共同点：没有会话主管时，每一项都需要某个智能体从聊天历史里猜——该不该拆智能体、下一步找谁、对方拿到什么、缺输入问谁、冲突谁裁决、后台任务做完怎么接回。会话主管加上结构化的任务与产物，把这些猜测变成了显式的决策与可校验的数据。这就是整体任务编排责任回到会话层级以后的形态。

## 新增的复杂度与未解决的边界

新方案的成本同样明确：一次委派（会话主管 → 领域智能体 → 会话主管）一定比直接回答多一轮模型调用；DomainTask、AgentResult、Artifact 一套协议需要维护；任务依赖图（Task DAG）的复杂度随协作组合增长，当前只覆盖训练 → 饮食这类单跳和少量多跳场景，没有做通用的图执行引擎；委派深度与任务数量靠配置化预算约束，是硬上限而不是动态调度。这些边界在 [[8.跨领域协作与冲突]] 与 [[10.职责所有权与执行模型]] 中有展开。

这个变化也自然引出第六章的问题：现在一个任务可以跨请求、跨多个智能体、跨人工确认、以后台方式长期运行，一次 HTTP Request 的数量已经不能代表这个任务实际消耗的资源，资源治理必须有任务级的单位。

## 边界问答

**1. Q：** 复杂任务为什么不默认拆成多个智能体？
**A：** 多智能体会带来额外的调用成本与协调复杂度，而单智能体配合合适的提示词和工具很多时候已经能完成任务。默认由会话主管完成、只在形成独立能力边界时才提升为领域智能体，是不为复杂而拆。

**2. Q：** 为什么不给领域智能体内部保留规划器 → 管理器 → 工人层级？
**A：** 固定层级多数场景只是在重复描述已知状态机，规划器和管理器没有额外信息量。开放式任务用 ReAct 循环，稳定流程用领域工作流整体调用。

**3. Q：** 独立路由为什么被去掉？
**A：** 路由与会话主管会重复两次语义判断。领域选择本身就是会话主管决策的一部分，保留独立路由只会多一层没有增量信息的判断。

**4. Q：** 为什么子智能体不直接和用户说话？
**A：** 让子智能体直接交互会把会话控制权分散到各个子智能体。它返回 `needs_input`，由会话主管统一收集后再向用户发问，会话控制权始终在会话主管。
