# 代码级逻辑：Supervisor 如何持续推进跨领域任务

本篇回答一个问题：一个跨训练与饮食的用户目标，由谁持续持有，又怎样通过结构化的任务、结果与产物推进到完成。场景是 Hero Scenario 的跨领域版本：用户在会话 C10 中说「帮我根据新的工作时间重新调整训练计划，饮食也跟着新的训练安排一起调整」，任务控制器为此创建父任务 T200。第一章走查的 T100 是单领域每日计划任务，本篇的跨领域请求是同一身份体系下的新任务实例，不共用对象。训练一侧的世界沿用前几章冻结的现场：正式训练计划仍是 plan_88@v2，工作日晚间训练约束来自第三章证据链（E22 → S31）。Supervisor 如何决策委派、每次模型调用看到什么、长期事实怎么检索、工具动作怎么安全执行，分别属于本章概念笔记与第二、三、四章；本篇只讲它们之间的协作骨架。

## 三层身份：AgentTask、DomainTask、后台执行记录

第五章最容易出错的地方，是三个不同层次的东西都叫 `task_id`。代码级逻辑的第一件事是把它们拆开：

```text
AgentTask T200            第一章的逻辑任务：用户的整个跨领域目标，
                          跨请求、跨人工确认持续存在，拥有 Run / Checkpoint 生命周期

DomainTask DT10 / DT20    T200 内部的领域工作单元：协作层的稳定身份，
                          由 Supervisor 委派、根运行时登记与推进

后台执行记录 AE500        DT10 进入后台时的持久执行方式记录，
                          不是第二类业务任务，只回答「这次后台执行运行到哪了」
```

文中的根运行时（Root Runtime）指第一章根状态图与任务控制器所在的确定性执行层：它不调用模型、不做业务判断，只负责校验编排动作、推进状态机与保存控制状态。T200 与 DT10 的关系是包含而不是平级：T200 的目标成立需要训练与饮食两个领域的结果，DT10、DT20 是它在两个领域里的工作单元。由此，领域委派里的身份字段统一命名为 `domain_task_id`，父任务身份用 `parent_task_id` 挂回——不再让一个裸 `task_id` 同时指父任务和子任务，第一、二章的校验链（`current_run_id`、`current_agent_id` 等）引用的都是父任务 T200 的控制索引，不受影响。

原来并存的 ChildTask 模型吸收进 DomainTask。ChildTask 描述的子任务身份、`assigned_agent`、`depends_on`、输入输出产物、状态，与 DomainTask 是同一对象的两个视角，维护两套必然漂移。统一后的结论是：**DomainTask 本身就是任务依赖图（Task DAG）中的节点**，`depends_on` 与状态直接是它的字段，根运行时不再额外保存第二份子任务状态。被指派的智能体也不作为委派时的自由字段：领域到智能体的映射由注册表配置（workout → workout_agent），只有后台执行记录里显式记录 `assigned_agent`。

AsyncAgentTask 的定位同步收窄：它不是与 DomainTask 平级的第二种任务定义——否则「DT10 进入后台以后为什么突然变成另一个任务」无法回答。统一解释为：**DomainTask 是协作层稳定身份，后台运行记录只是它的一种执行方式**。DT10 以 `execution_mode = background` 进入异步运行时时产生一条执行记录 AE500，AE500 绑定 `domain_task_id`，完成后的结论写回 DT10；两者的关系是「AE500 succeeded → DT10 succeeded」，不存在互相冲突的业务目标。

同步领域工作不需要独立生命周期。Supervisor 委派训练智能体、立即等待结果的这类调用里，DT10 只是父任务当前 Run 内的一次结构化工作单元：没有自己的 task / Run / Checkpoint，通过 `domain_task_id` 加领域智能体 Span（Domain Agent Span，执行轨迹中标记「这段执行属于哪个领域智能体」的区段）定位。只有真正跨请求、后台运行的工作才交给异步运行时建立持久执行记录。这样一次普通的子智能体调用不会背上完整的任务运行时。

## DomainTask：最终结构与两类信息

统一后的 DomainTask 结构（概念定义见 [[6.通信协议与 Artifact]]，已按本篇同步）：

```python
class DomainTask:
    domain_task_id: str        # 领域任务身份，如 DT10；协作、产物溯源、状态推进都引用它
    parent_task_id: str        # 父 AgentTask，如 T200；把工作单元挂回用户目标
    target_domain: Literal[    # 目标领域；领域到智能体的映射由注册表配置
        "workout", "diet"]

    objective: str             # 本领域任务必须完成什么，由 Supervisor 从用户目标提炼
    constraints: list[str]     # Supervisor 明确委派出的任务约束，如「完成后必须提供训练日和负荷摘要」
    evidence_requirements: list[str]   # 完成本任务需要哪些信息的声明，如 state_key 或事实类型

    input_artifact_refs: list[str]     # 上游产物引用（含版本），跨领域交接的唯一入口
    required_output_type: str          # 要求产出的产物类型，succeeded 判定用它校验

    depends_on: list[str]      # 前置 DomainTask；全部 succeeded 才 runnable
    execution_mode: Literal[   # sync：父 Run 内执行；background：进入异步运行时
        "sync", "background"]

    status: str                # pending / running / waiting_input / succeeded /
                               # conflict / failed / cancelled，由根运行时推进
    output_artifact_refs: list[str]    # succeeded 判定通过后由根运行时写入
```

原结构里的 `relevant_user_facts: dict` 被删除。它会让 DomainTask 变成第二份事实源：用户长期事实的快照、记忆内容、正式业务事实的副本都会随委派复制进来，与第二、三章的读取层失去单一事实来源。DomainTask 只保存两类信息——**委派出的约束**（constraints，Supervisor 对本领域的要求）与**信息需求声明**（evidence_requirements，完成本任务需要知道什么）。真正的用户当前训练时间约束、当前正式计划、记忆与知识，仍由第三章证据检索与第二章上下文装配获取：

```text
DomainTask 表达「你需要知道什么」，
不表达「这里复制一份我认为是真的东西」。
```

DT10 的声明是 `evidence_requirements = ["training.availability", "active_workout_plan", "training_goal"]`。领域智能体执行到需要这些信息的节点时，走第三章的 EvidenceRequest → EvidenceBundle、第二章的装配链，拿到的是当时的真实状态而不是委派那一刻的快照。

## 编排状态：OrchestrationState

Supervisor 不靠聊天历史记住「Workout 做完了吗、Diet 是不是该开始了」。根运行时保存最小编排状态（作为第一章 Runtime State 中第五章负责的字段，不建新的存储）：

```python
class OrchestrationState:
    parent_task_id: str              # 父任务，如 T200
    goal: str                        # 用户目标原文摘要：调整训练并同步调整饮食
    domain_task_refs: list[str]      # 领域任务引用：DT10、DT20；状态细节在 DomainTask 行上
    artifact_refs: list[str]         # 已交付产物引用：A100@v1、A200@v1
    pending_input_request_ids: list[str]   # 等待用户回答的输入请求：IR50
    final_status: str                # 编排层结论：目标达成 / 部分达成 / 无法达成，供父任务收尾校验
```

它只保存控制状态和引用，不保存 Workout 内部的推理与行动循环历史、Diet 的工具结果、完整产物正文或任何记忆——那些分别属于各领域智能体的执行轨迹、产物存储与第三章。也不存在「大 Supervisor Memory」：Supervisor 每轮可见的是这份状态的投影，不是它私有的记忆库。

## Supervisor 输出 SupervisorAction，根运行时落状态

这是本章最重要的 Harness 边界。Supervisor 是大语言模型智能体，适合决定业务编排：要不要委派、先 Workout 还是先 Diet、两个领域是否依赖、收到冲突后下一步修哪个领域。但它不能直接修改 `DT10.status`、`DT20.depends_on` 或父任务的完成状态——模型输出的是一次结构化的编排动作，状态的确定性修改由根运行时完成：

```python
class SupervisorAction:
    action_type: Literal[            # 本轮决策的类型
        "direct_answer",             # 直接回答，不委派
        "create_domain_task",        # 创建领域任务（ensure 语义，见异常一）
        "wait_for_tasks",            # 等待在途领域任务终止
        "request_user_input",        # 把 InputRequest 的问题交给主会话问用户
        "create_revision_task",      # 冲突裁决后创建修订任务
        "complete_parent_task",      # 声明父目标业务上可以结束
    ]
    payload: dict                    # 动作参数，如目标领域、objective、input_artifact_refs
```

SupervisorAction 不是新的长期数据库对象，只是 Supervisor 一轮决策的结构化输出。之后的链路：

```text
Supervisor（LLM 决策）
    ↓ SupervisorAction
根运行时校验器（确定性）
    ↓ 校验通过：确定性修改 OrchestrationState / DomainTask
    ↓ 校验不过：拒绝动作，把原因返回给 Supervisor 重新决策
```

以「创建 DT20」为例，校验器逐项确认：DT10 是否存在、是否属于 T200、A100 是否 ready、`target_domain` 是否在允许领域内、任务数量与委派深度是否还在预算内。任何一项不满足，动作被拒绝——Supervisor 不能靠自行填写参数越过这些条件。这与第二章请求校验的思想同构：请求是调用参数，不是权限凭据。

## 状态机与推进规则归根运行时

DomainTask 的状态转换全部由根运行时完成：

```text
pending ──→ running ──→ succeeded
              │  │
              │  ├──→ waiting_input ──（用户结构化回答）──→ 回到 runnable
              │  ├──→ conflict（业务上无法满足，等 Supervisor 裁决）
              │  └──→ failed（执行出错）
              └──→ cancelled
```

`conflict` 与 `failed` 是两个终止状态：failed 是执行层面的出错，conflict 是业务层面「无法满足约束」，工作本身没有错，需要的是编排裁决而不是重试。`depends_on` 的推进规则只有一条：所有前置 DomainTask 状态为 succeeded，本任务才 runnable——conflict 不算 succeeded，所以冲突分支不能伪装成正常依赖（见走查三）。

领域智能体返回的是结构化的 AgentResult（概念定义见 [[6.通信协议与 Artifact]]，已按本篇同步）：

```python
class AgentResult:
    domain_task_id: str              # 结果绑定领域任务，不再用模糊的 task_id
    status: Literal[                 # 四种终止结果
        "succeeded",                 # 完成，产出待校验产物
        "needs_input",               # 缺必要输入，携带输入请求
        "conflict",                  # 无法满足跨领域约束，携带冲突报告
        "failed"]                    # 失败，携带错误码
    artifact_refs: list[str]         # 本任务产出的产物引用
    input_request: InputRequest | None    # status=needs_input 时非空
    conflict: ConflictReport | None       # status=conflict 时非空
    error_code: str | None                # status=failed 时非空
```

succeeded 不是智能体说了算。收到 `AgentResult(status=succeeded, artifact_refs=[A100])` 后，根运行时校验四项：A100 是否存在、`A100.producer_domain_task_id == DT10`、`A100.status == ready`、`A100.artifact_type` 是否满足 DT10 声明的 `required_output_type`。全部通过才写 `DT10 → succeeded`、`output_artifact_refs = [A100]`；任何一项不满足，结果不成立，按 failed 收尾并保留产物原状，由 Supervisor 决定是否重新委派。领域智能体只说一句「Workout 做完了」没有意义——没有可校验的产物，就没有完成。

## DT20 消费 A100：引用经第二章装配进入上下文

DomainTask 只携带 `input_artifact_refs`，产物正文不随委派复制。Diet 智能体真正调用模型时，走的是第二章的统一装配链：

```text
DT20（input_artifact_refs = ["A100@v1"]）
    ↓ 饮食智能体的执行节点发起模型调用
ContextAssemblyRequest（T200 / R1 / diet_agent / 当前阶段）
    ↓ 上下文装配器
ArtifactReader.load("A100@v1")     # 按引用与版本读取产物正文
    ↓
ContextBlock（task_artifact 块）
    ↓
Diet Agent 的本轮模型上下文
```

Supervisor 不把 A100 的正文手动拼进 Diet 的提示词。所有正式模型调用统一由上下文装配器管理模型可见信息（第二章冻结的边界），跨领域交接在装配层的样子就是：引用进 DomainTask，正文经 ArtifactReader 进 ContextBlock。第二章走查里以 task_artifact 块进入上下文、在上下文清单 artifact_refs 中登记的任务产物（如 D200@v1），与本篇的 A100 是同一层的对象——第五章的视角下，它们都是带 `producer_domain_task_id` 的 DomainArtifact。

由此 Diet 智能体看到的是 A100 的结构化结果（训练日、训练时间、负荷、营养含义），看不到训练智能体的完整对话、工具执行轨迹与推理过程——隔离的理由见 [[7.上下文隔离]]。

## needs_input：InputRequest 的稳定身份与控制权回主会话

缺输入必须拥有可恢复的稳定身份，一个匿名字典做不到。结构化的输入请求（概念定义见 [[9.HIL 与异步任务]]，已按本篇同步）：

```python
class InputRequest:
    input_request_id: str        # 输入请求身份，如 IR50；回答匹配、状态流转、恢复都引用它
    domain_task_id: str          # 属于哪个领域任务，如 DT10
    parent_task_id: str          # 挂回父任务，供 T200 的 pending_input_request_ids 登记
    field: str                   # 缺少的输入字段，如 available_training_days
    question: str                # 向用户提出的问题，如「每周最多可以安排几天训练？」
    status: Literal[             # 请求状态：等待 / 已回答 / 已取消
        "pending", "answered", "cancelled"]
```

链路是：

```text
训练智能体缺必要输入
    ↓ AgentResult(status=needs_input, input_request=IR50)
根运行时
    ↓ DT10 → waiting_input；T200.pending_input_request_ids += IR50
Supervisor（被再次调用，看到 pending input）
    ↓ SupervisorAction(request_user_input)
主会话向用户提出 IR50 的问题
```

子智能体不持有主会话控制权：它不直接向用户发消息，问题统一经 Supervisor 从主会话提出。如果 DT10、DT20 同时缺输入，Supervisor 可以把 IR50、IR51 合并成一次用户提问展示，但底层 `IR50 → DT10`、`IR51 → DT20` 的映射不能丢——合并的是展示，不是身份。

## 用户回答的结构化恢复

用户回答走结构化入口，与第一章 HIL 同构。回答提交后由输入解析（Input Resolution）处理：

```text
用户回答（携带 input_request_id 的结构化提交）
    ↓ Input Resolution
IR50 = answered（答案写入请求记录）
    ↓ 根运行时明确知道 IR50 belongs_to DT10
DT10 → runnable（T200 恢复执行，复用第一章中断与恢复机制）
    ↓
原协作链继续：T200 没有被重建，DT10 也没有被重建
```

Supervisor 不重新阅读聊天历史然后猜「这句话应该是回答训练智能体的吧」。普通新消息（见异常三）不会解除等待；只有明确匹配 InputRequest 的结构化回复才把 `waiting_input` 拉回 runnable。会话输入与领域任务恢复输入是两种输入，这条边界和第一章「会话继续不打扰任务」是同一条。

## 跨领域约束与冲突：XC10 与 CR20

跨领域约束（CrossDomainConstraint）是训练结果影响饮食任务的载体，必须带来源身份——Diet 智能体收到的不能是一段无来源文本：

```python
class CrossDomainConstraint:
    constraint_id: str               # 约束身份，如 XC10
    parent_task_id: str             # 属于哪个父任务，如 T200
    source_domain_task_id: str      # 由哪个领域任务产出，如 DT10
    source_artifact_ref: str        # 依据哪份产物，如 A100@v1
    source_domain: str              # 来源领域：workout
    target_domain: str              # 作用领域：diet
    type: str                       # 约束类型，如 nutrition_requirement
    payload: dict                   # 约束的结构化内容，如额外碳水需求
```

DT10 的产物 A100 里，训练负荷较高这一结论伴随 XC10（「高训练负荷要求饮食提供额外碳水可用性」）。Supervisor 创建 DT20 时把 A100 与 XC10 一起作为输入，饮食智能体据此调整饮食；如果用户当前饮食限制无法满足，它返回结构化的冲突报告：

```python
class ConflictReport:
    conflict_id: str                # 冲突身份，如 CR20
    domain_task_id: str             # 报告冲突的领域任务，如 DT20
    constraint_refs: list[str]      # 冲突涉及的约束，如 [XC10]
    reason_code: str                # 冲突原因码，如 diet_restriction_unsatisfiable
    summary: str                    # 冲突内容摘要
    affected_artifact_refs: list[str]   # 受影响的产物
```

领域智能体不能自行解决跨领域冲突。Diet 智能体发现训练量太高时直接「把训练计划改轻一点」是被禁止的——修改训练计划越过了领域所有权。它的职责边界是：报告 Diet 无法满足，附上 CR20，终止。控制权随 CR20 回到 Supervisor，由它做业务裁决，可选路径只有三类：

```text
A. 创建训练修订任务 DT30（重新调整训练负荷）
B. 询问用户是否愿意修改目标
C. 任务策略允许时，返回明确标注无法同时满足的部分结果
```

无论选哪条，实际创建 DT30 仍经过根运行时校验——Supervisor 决定业务方向，运行时决定状态条件。DT30 是 Supervisor 根据 CR20 显式创建的新分支，`input_artifact_refs = [A100@v1, CR20]`；它不把 DT20 写进 `depends_on`，因为 depends_on 只认 succeeded，冲突分支不是正常依赖，不建通用循环图。

## Supervisor 的持续责任与可见状态

T200 的目标成立需要两个领域的结果，Supervisor 对它的责任是持续的，不是一次性的。模式是**每次领域任务终止，Supervisor 被再次调用**：

```text
第一次：看到空编排状态 → 决定先 Workout → create DT10
DT10 succeeded → Supervisor 被再次调用
第二次：看到 DT10 succeeded / A100 ready / DT20 不存在 → create DT20
DT20 succeeded → Supervisor 被再次调用
第三次：看到全部领域任务终止、产物齐备 → complete_parent_task
```

它每轮看到的不是几十轮聊天历史，而是第二章装配链投给它的结构化状态。Supervisor 自己的模型调用同样走 `call_model → ContextAssemblyRequest → 装配器`，它的 AgentStatus 状态栏（第二章四区块）里，执行议程区块由 OrchestrationState 投影生成：

```text
Parent Goal:
  按新的工作时间调整训练，并同步调整饮食
Domain Tasks:
  DT10 workout  succeeded
  DT20 diet     pending
Ready Artifacts:
  A100@v1
Pending Input:
  none
Conflicts:
  none
```

根运行时保存真实状态，第二章负责把状态投影成 Supervisor 本轮可见上下文；Supervisor 不从聊天历史推断任务依赖图，也不靠记忆回忆「Workout 好像已经做完了」。

## Task DAG 最小实现与并行

依赖表达只需要 `DomainTask + depends_on`：

```text
DT10 workout   depends_on = []
DT20 diet      depends_on = [DT10]
```

运行时规则：所有 `depends_on` 状态为 succeeded → runnable。这就足够覆盖当前「训练 → 饮食」单跳与少量多跳场景，不引入通用工作流引擎、BPMN、Temporal 或复杂 DAG 调度器。

并行任务用同一个模型。「分别分析本周训练和饮食」时创建 DT10、DT20，两者 `depends_on = []`，均 runnable，在父任务当前 Run 内同步并发执行（`asyncio.gather` 一类并发原语，当前请求仍等待全部必要结果返回）。这只是并发优化，不是后台任务系统，不把 gather 包装成异步运行时。

## 后台执行：AE500 只改执行方式

DT10 很耗时时，`execution_mode = background`，执行交给异步运行时，产生持久执行记录（结构见 [[9.HIL 与异步任务]]，已按本篇同步）：AE500 绑定 `domain_task_id = DT10`、拥有独立的 `run_id`、记录 `assigned_agent` 与排队 / 运行 / 终止时间。DT10 仍是 Supervisor 编排的那个工作单元，AE500 只是它的后台运行记录，协作协议没有任何变化。

后台完成只表示 DT10 succeeded，不表示父目标完成：

```text
异步完成事件
    ↓ 根运行时更新 DT10（先确认产物已持久化、通过 succeeded 校验）
    ↓ 父任务 T200 重新可评估
    ↓ Supervisor 被再次调用，决定下一步
```

如果 DT20 还没执行，T200 不能进入 COMPLETED。异步回调直接把父任务判完成是被禁止的——「这个领域做完了」和「用户的整个目标达成了」是两个判断，后者只有 Supervisor 加根运行时收尾校验能下（见下节）。

## 父任务完成条件与部分结果

T200 不能由 Supervisor 自由地说「差不多了，结束吧」。父任务创建时声明最小完成条件：

```python
class ParentTaskPolicy:
    parent_task_id: str                 # 所属父任务
    required_output_types: list[str]    # 必须齐备的产物类型，如 WorkoutAdjustmentSummary + DietAdjustment
    partial_result_policy: Literal[     # 是否允许部分结果
        "allowed", "not_allowed"]
```

根运行时收到 `complete_parent_task` 动作时校验：所有必需领域任务已终止、必需产物都存在、没有未解决的冲突、没有等待中的输入请求、部分结果策略满足。全部通过才写 `T200 → COMPLETED`。分工是：**Supervisor 决定业务上可以结束，根运行时决定状态条件是否允许结束**。

部分结果同样由创建时声明约束。`partial_result_policy = allowed` 时，两个互不依赖任务一成一败（Workout succeeded、Diet failed），Supervisor 可以返回训练部分结果并明确说明饮食失败；`not_allowed` 时不能把部分信息包装成完整成功。部分结果不是 Supervisor 的临时发挥——是否缺一不可取决于任务语义，是父任务的创建参数。

## 走查一：主链，T200 从创建到完成

用户消息进入会话入口，Supervisor 判断这是需要两个领域协作的目标，任务控制器创建 T200（创建链与第一章相同：写控制索引、登记 R1）。此后每一步只标谁决定、谁落状态：

```text
用户（C10）：根据新的工作时间重新调整训练计划，饮食也跟着调整
    ↓ Supervisor 第一次决策（其模型调用经第二章装配，状态栏见上节）
SupervisorAction(create_domain_task, workout, depends_on=[])
    ↓ 根运行时校验通过，创建 DT10（pending → running）
    ↓ 训练智能体执行（ReAct / 领域工作流；证据经第三章、装配经第二章）
    ↓ 训练智能体产出：A100（WorkoutAdjustmentSummary，draft → ready）、A110（WorkoutPlanDraft）
    ↓ AgentResult(DT10, succeeded, artifact_refs=[A100, A110])
    ↓ 根运行时四项校验通过：DT10 → succeeded
    ↓ Supervisor 第二次被调用，看到 DT10 succeeded / A100 ready
SupervisorAction(create_domain_task, diet,
                 input_artifact_refs=[A100@v1], depends_on=[DT10])
    ↓ 根运行时校验通过，创建 DT20（依赖已满足 → runnable → running）
    ↓ 饮食智能体执行，ArtifactReader.load(A100@v1) 经装配进入其上下文
    ↓ 产出 A200（DietAdjustment，draft → ready）
    ↓ AgentResult(DT20, succeeded, artifact_refs=[A200])
    ↓ 根运行时校验通过：DT20 → succeeded
    ↓ Supervisor 第三次被调用，看到全部终止、产物齐备
SupervisorAction(complete_parent_task)
    ↓ 根运行时按 ParentTaskPolicy 校验通过
T200 → COMPLETED
```

状态变化总表：

| 阶段 | T200 | DT10 | DT20 | 产物 |
| --- | --- | --- | --- | --- |
| 创建任务 | RUNNING (R1) | 无 | 无 | 无 |
| 第一次决策后 | RUNNING | pending → running | 无 | 无 |
| DT10 完成 | RUNNING | succeeded | 无 | A100 ready、A110 ready |
| 第二次决策后 | RUNNING | succeeded | pending → running | A100 ready |
| DT20 完成 | RUNNING | succeeded | succeeded | A200 ready |
| 收尾校验通过 | COMPLETED | 终止 | 终止 | A100 / A110 / A200 留存 |

训练计划本身此时仍是草稿：A110 status = ready 只表示它已作为协作结果确认完成，正式训练计划的变更要等用户确认后经第四章调用实例提交（第一章走查的 I300 承担的角色、第二章冻结的提交边界），业务库才出现新版本正式计划。DT10 succeeded 不自动意味着业务数据库已被修改。

## 走查二：needs_input（IR50）

在 DT10 执行中途，训练智能体发现不知道用户每周最多能安排几天训练：

```text
DT10 running
    ↓ AgentResult(DT10, needs_input, input_request=IR50)
    ↓ field=available_training_days，question=「每周最多可以安排几天训练？」
根运行时
    ↓ DT10 → waiting_input；T200.pending_input_request_ids += IR50
    ↓ T200 暂停（复用第一章中断机制，Run 留在中断点）
Supervisor 被再次调用
    ↓ SupervisorAction(request_user_input)
主会话问用户：每周最多可以安排几天训练？
    ↓ 用户回答「四天」（携带 input_request_id=IR50 的结构化提交）
Input Resolution：IR50 = answered
    ↓ DT10 → runnable，T200 恢复（新 Run 段，任务与领域任务都不重建）
    ↓ 训练智能体带着 IR50 的答案继续执行
```

关键事实：T200 没有被重新创建，DT10 也没有被重新创建，恢复的是原协作链。等待期间会话 C10 照常处理其他消息（见异常三），两者互不干扰。

## 走查三：conflict（XC10 → CR20 → DT30）

主链的变体：DT20 执行中发现用户饮食限制无法满足训练负荷要求。

```text
DT10 succeeded，A100 含「训练负荷较高」+ XC10（额外碳水需求）
    ↓ Supervisor 创建 DT20，input_artifact_refs=[A100@v1]、约束含 XC10
饮食智能体执行
    ↓ 用户当前饮食限制无法满足 XC10
    ↓ AgentResult(DT20, conflict, conflict=CR20)
根运行时
    ↓ DT20 → conflict（终止）；冲突登记进编排状态，Supervisor 可见
Supervisor 被再次调用，裁决
    ↓ 选择 A：降低训练负荷
SupervisorAction(create_revision_task, workout,
                 input_artifact_refs=[A100@v1, CR20])
    ↓ 根运行时校验通过，创建 DT30（workout 修订，depends_on=[]——新分支，不依赖冲突任务）
    ↓ DT30 产出 A100 v2（修订后的训练调整摘要；v1 → superseded）→ succeeded
    ↓ Supervisor 再次被调用，基于 A100@v2 创建新的饮食任务……
```

多跳由 Supervisor 显式创建新任务形成，每个任务都有明确的 `required_output_type` 和终止状态；委派深度与任务数量受配置化预算约束（完整资源治理属第六章），智能体之间不会无限制互相讨论。

## 异常路径一：Supervisor 决策节点重放

Supervisor 的某次决策步骤重试：第一次已经创建 DT20，但返回前进程异常；重放后再次请求「创建饮食任务」。如果创建语义是无条件的，库里会出现 DT20、DT21 两个相同逻辑工作单元。因此领域任务的创建必须是 `ensure_domain_task` 语义——按稳定业务键识别同一委派：

```python
def ensure_domain_task(parent, target_domain, objective_key, input_refs):
    key = (parent.task_id,        # 属于哪个父任务
           target_domain,         # 哪个领域
           objective_key,         # 委派目标的稳定业务键（同一目标的规范标识）
           version_refs(input_refs))   # 输入产物的版本组合
    return get_or_create(key)     # 已存在同一委派则复用，不新建
```

不需要分布式锁。明确的设计事实是：Supervisor 决策节点允许重放，结构化委派必须幂等——这与第一章 `prepare_invocation` 的 get_or_create、第三章写入路径的幂等键是同一条约束在三个层的落点。

## 异常路径二：输入产物已被新版本取代

```text
DT10 先产出 A100 v1
    ↓ 之后训练修订任务 DT30 产出 A100 v2（v1 → superseded）
    ↓ 但 DT20 的 input_artifact_refs 固定引用 A100@v1
```

DT20 执行前，根运行时与 ArtifactReader 必须确认它固定引用的是哪一个版本：读取严格按 `A100@v1` 进行，不静默替换成 v2——饮食智能体自己偷偷换输入是被禁止的。如果 v1 已 superseded、不再允许消费，装配读取显式失败，DT20 被标记为过期（stale），由 Supervisor 决定创建引用 v2 的新任务或更新后续计划。版本钉死加显式失败，替代自动升级。

## 异常路径三：needs_input 期间的普通会话消息

```text
DT10 waiting_input，IR50 pending
    ↓ 用户在主会话问：「香蕉训练前吃可以吗？」
```

这是普通新消息，由 Supervisor 直接回答或按需委派，与第一章等待期间会话继续完全一致。它不能自动把 IR50 置为 answered——只有明确匹配 InputRequest 的结构化回复才解除等待。这条异常证明的边界是：**会话输入（Conversation Input）≠ 领域任务恢复输入（DomainTask Resume Input）**，自然语言消息不具备恢复控制路径所需的确定信息。

## 与前四章及第六章的接口

| 相邻章节 | 第五章提供 | 相邻章节负责 |
| --- | --- | --- |
| 第一章 | DomainTask 引用、OrchestrationState（作为 Runtime State 字段） | 父 AgentTask 的 Task / Run / Checkpoint / HIL / Resume |
| 第二章 | DomainTask refs、Artifact refs、OrchestrationState 投影 | Supervisor / Workout / Diet 每次调用 LLM 时具体看到什么 |

## 未下沉与不新增

仍未达到代码级逻辑的部分：委派深度与任务数量预算的具体配额与准入队列（属第六章）；异步运行时的队列、工作线程池与取消语义细节（属第六章）；产物存储的物理落点、版本保留与清理策略；多跳冲突的轮次上限策略数值；Supervisor 决策提示词与决策质量（模型层问题，不是结构问题）。

本轮明确不新增：通用工作流引擎、BPMN、Temporal、复杂 DAG 调度器、第二套后台协作协议、分布式锁、消息队列，以及把 `asyncio.gather` 包装成的后台异步系统。

## 边界问答

**1. Q：** T200 和 DT10 有什么区别？

**A：** T200 是第一章身份体系里的逻辑任务，代表用户的整个跨领域目标，拥有 Run、检查点与完整的暂停恢复生命周期；DT10 是 T200 内部的领域工作单元，是协作层的稳定身份，由 Supervisor 委派、根运行时推进。前者是目标的生死，后者是目标在一领域内的工作单元。

**2. Q：** 为什么 DomainTask 不应该继续用普通的 `task_id`？

**A：** 裸 `task_id` 会让父任务与领域任务共用一个命名层，第一、二章的校验链引用父任务控制索引，协委派引用领域工作单元，两者混用后「这个 task_id 是谁」要靠上下文猜。统一 `domain_task_id` + `parent_task_id`，包含关系在字段上可判定。

**3. Q：** DomainTask 和 ChildTask 为什么不能维护两套？

**A：** 两者描述的是同一对象：子任务身份、被指派智能体、依赖、输入输出产物、状态。两套并存必然漂移。统一后 DomainTask 本身就是 Task DAG 的节点，`depends_on` 与状态直接是它的字段，根运行时不保存第二份子任务状态。

**4. Q：** AsyncAgentTask 和 DomainTask 是什么关系？

**A：** DomainTask 是协作层稳定身份，AsyncAgentTask 是它进入后台运行时后的持久执行记录，绑定 `domain_task_id`、拥有独立 run_id。关系是「AE500 succeeded → DT10 succeeded」，不是第二个业务任务。

**5. Q：** Supervisor 创建的究竟是什么？

**A：** 一轮 SupervisorAction——结构化的编排动作（创建领域任务、等待、请求输入、创建修订、声明收尾），不是直接的状态写入，也不是新的长期数据库对象。动作经根运行时校验后才确定性落状态。

**6. Q：** Supervisor 能不能直接修改 `DT10.status`？

**A：** 不能。Supervisor 是大语言模型智能体，输出的是决策动作；状态机转换由根运行时完成。让模型直接写状态，「我觉得 DT10 已经完成了」就会成为合法状态。

**7. Q：** 谁真正保存 Task DAG？

**A：** 根运行时，以 DomainTask 行上的 `depends_on` 字段加 OrchestrationState 的引用清单保存。不是 LLM，也不是聊天历史——Supervisor 每轮看到的是这份状态的第二章投影。

**8. Q：** DomainTask 为什么不复制用户事实？训练智能体怎么获得长期事实？

**A：** 复制 `relevant_user_facts` 会让委派对象变成第二份事实源，与第二、三章的读取层冲突。DomainTask 只声明 constraints（委派约束）与 evidence_requirements（需要知道什么）；执行到需要信息的节点时，走第三章 EvidenceRequest → EvidenceBundle、第二章装配链读取当时真实状态。

**9. Q：** DT10 succeeded 是谁判定的？

**A：** 根运行时。收到 succeeded 结果后校验产物存在、`producer_domain_task_id` 归属、status == ready、类型满足 `required_output_type`，四项全过才写 succeeded。智能体的自述不构成完成。

**10. Q：** Artifact 为什么必须带 `producer_domain_task_id`？ready 为什么不等于业务生效？

**A：** 溯源字段让任何产物都能回答「它是哪个领域任务产的」，succeeded 校验、冲突裁决、执行轨迹排查都依赖它。ready 只表示产物已作为协作结果确认完成；正式业务变更必须经第四章调用实例提交到领域服务——产物协议层没有 committed 一类的状态，就是为了不让「协作完成」被误读成「业务数据库已修改」。

**11. Q：** Workout 的产物怎样进入 Diet 智能体的上下文？为什么 Diet 看不到 Workout 的完整历史？

**A：** DT20 携带 `input_artifact_refs = [A100@v1]`，饮食智能体调用模型时由第二章装配器经 ArtifactReader 按版本读取，以 task_artifact 块进入上下文。Supervisor 不手工拼正文进提示词。完整历史里混着与当前任务无关的过程，交接的是结构化结果，不是对方的内部对话与工具轨迹。

**12. Q：** 为什么需要 `input_request_id`？用户回答后谁知道恢复 DT10？

**A：** 匿名的 `{field, question}` 字典没有可恢复的身份：无法登记到父任务的等待清单、无法匹配结构化回答、无法取消。IR50 把缺输入变成有身份的对象，用户回答经 Input Resolution 匹配 IR50，根运行时明确知道它属于 DT10，把 `waiting_input` 拉回 runnable——不靠 Supervisor 重读聊天猜归属。

**13. Q：** 饮食智能体遇到跨领域冲突，为什么不能直接把训练计划改轻？冲突最终回到谁？

**A：** 修改训练计划越过了领域所有权，两个智能体不共享同一业务事实的修改权。它返回 `status = conflict` 加 CR20 后终止，控制权回到 Supervisor，由它在「创建修订任务 / 问用户 / 按策略返回部分结果」里裁决，实际创建任务仍经根运行时校验。

**14. Q：** 后台任务完成后，为什么不能直接完成父任务？T200 最终谁决定可以 COMPLETED？

**A：** 后台完成只说明 DT10 succeeded，父目标可能还有未执行的领域任务；异步回调直接判完成会跳过编排判断。T200 的完成由 Supervisor 声明（业务上可以结束）加根运行时按 ParentTaskPolicy 校验（状态条件允许结束）共同决定，缺一不可。

**15. Q：** 如果创建领域任务的 Supervisor 决策节点重放怎么办？

**A：** 领域任务创建是 `ensure_domain_task` 语义：以父任务、领域、委派目标业务键、输入产物版本组合为键 get_or_create，重放复用已存在的 DT20，不产生 DT21。与第一章调用实例、第三章写入路径的幂等设计同构：决策节点允许重放，结构化委派必须幂等。
