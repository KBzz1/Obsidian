# 第五章 总览：把编排责任交还 Supervisor

> [!warning] 实现状态
> 本章描述的是当前定稿的设计与代码级逻辑（数据结构、调用链、状态表），尚未在本仓库完成真实代码落地。逐机制状态见 [[实现真实性地图]]。

## 章节定位

第五章回答一个问题：一个用户目标同时涉及训练与饮食两个领域时，谁负责持续推进整个目标。

用 Hero Scenario 检验：训练方案调整完成后，新的训练日期、时间、负荷要成为饮食调整的输入。旧版结构里顶层只有一次性路由，路由完成后没有任何角色持续知道整个目标完成到了哪里；真正重的编排逻辑反而沉在单个领域内部。问题的根因不是智能体太多，而是整体任务编排责任放错了层级。本章的演化就是把编排责任收回会话层级：会话主管（Supervisor，持续持有主会话上下文的完整智能体）负责整体推进，领域智能体（Domain Agent）只负责领域内部执行。

本章的核心判断是：多智能体不是系统的默认执行方式，而是 Harness 在需要专业能力隔离和跨领域协作时使用的一种执行机制。默认由会话主管完成任务；只有当某项能力形成独立的数据所有权、工具集合、业务工作流或大规模专业上下文时，才提升为独立领域智能体。

## 与其他章节的接口

第五章确定的多智能体架构会反向要求前面几个模块做少量接口调整。这些调整的机制本身仍在各自章节展开：

- 第一章根状态（Root State）需要保存第五章负责的编排字段（领域任务引用 `domain_task_id` 列表、`depends_on`、产物引用与等待中的输入请求，即最小编排状态 OrchestrationState），以支持会话主管派生任务及后续恢复；父任务（AgentTask）的检查点和恢复机制仍在第一章描述。
- 第二章上下文装配器（Context Assembler）需要区分会话主管上下文与领域上下文：会话主管（Supervisor）保存完整工作会话，训练智能体（Workout Agent）/饮食智能体（Diet Agent）从 TaskSpec、相关业务事实、记忆（Memory）/检索增强证据（RAG Evidence）和产物（Artifact）中构建任务局部上下文（task-local context）。令牌预算（Token Budget）、压缩和渐进披露（Progressive Disclosure）仍在第二章。
- 第三章记忆与 RAG（检索增强生成）检索不能默认把所有长期记忆传给所有智能体，而要根据 `DomainTask` 和领域范围（scope）返回相关证据。
- 第四章工具运行时（Runtime）接收来自会话主管或领域智能体（Domain Agent）的工具调用（Tool Call），但智能体身份本身不代表操作已经被授权；模式校验（Schema validation）、所有权检查、业务规则、人机介入（HIL）、幂等、重试（retry）和安全护栏（Guardrail）在第四章统一处理。
- 第六章在异步运行时（Async Runtime）和并行任务的接口基础上，进一步处理多用户并发、任务队列、资源池、背压与速率限制（Rate Limit）；完整 Trace 串联与统一执行轨迹归后续测试与评估章节。
