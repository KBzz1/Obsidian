# Supervisor 架构与委派

## 总体运行架构

第五章采用中心化的会话主管 + 领域子智能体（Domain Subagents）架构：

```text
                         用户
                          │
                          ▼
                 根状态图（Root StateGraph）
                 / 智能体运行时（Agent Runtime）
                          │
                          ▼
                会话主管（Conversation Supervisor）
                 / 通用智能体（Generalist Agent）
                          │
          ┌───────────────┼────────────────┐
          │               │                │
          ▼               ▼                ▼
       直接回答        共享能力          委派
                          │                │
                    习惯工具          ┌────┴────┐
                                      │         │
                                      ▼         ▼
                                训练智能体   饮食智能体
                                      │         │
                               ReAct /  ReAct /
                               工作流    工作流
                                      │         │
                                      └────┬────┘
                                           │
                                      领域产物（Domain Artifact）
                                           │
                                      产物存储（Artifact Store）
```

根状态图（Root StateGraph）不是另一个智能体，也不会为了「进入 Harness」额外执行一次模型调用。它属于智能体运行时（Agent Runtime），负责当前任务状态、检查点（Checkpoint）、中断（Interrupt）、任务恢复以及确定性控制节点。会话主管（Supervisor）才是用户会话中的主要大语言模型（LLM）智能体。

会话主管是整个会话唯一的控制者，同时承担通用助手与任务编排两个职责：它既可以自己完成任务，也可以调用专业子智能体（Subagent）。官方子智能体（Subagents）模式同样采用中心主智能体（main agent）调用子智能体即工具（subagent-as-tool）的形式，并把主会话状态留在主智能体（main agent）中。它与一次性路由（Router）的区别在于，会话主管（Supervisor）本身是持续存在的完整智能体，可以跨多个步骤和多个领域动态决定下一步调用谁。

## 不设独立 Router

系统不再额外增加一层独立的大语言模型（LLM）路由（Router）：

```text
路由（Router）
    ↓
会话主管
```

这会重复两次语义判断。领域选择本身就是会话主管（Supervisor）决策的一部分。路由的机制定义在第一章（见 [[3.执行模型与任务边界]]），但路由的决策者从独立的路由（Router）收回到会话主管：由会话主管（Supervisor）在每一步动态判断直接回答、调用共享能力还是委派给领域智能体。

## 直接回答与委派的边界

会话主管不是所有请求的中转站。简单请求停留在会话主管（Supervisor）层完成，这是控制多智能体（Multi-Agent）成本和复杂度的关键机制。

```text
“高 GI 食物是什么？”
“蛋白质有什么作用？”
“罗马尼亚硬拉是什么动作？”
“RPE 是什么意思？”
```

这些问题虽然在语义上属于训练或饮食领域，但不依赖用户私有业务状态、不需要领域工具、不需要复杂领域工作流，也不需要大量专业上下文，所以直接由会话主管回答。

相反，需要访问领域状态或领域能力的请求才委派：

```text
“我昨天深蹲做了多少？”
```

需要访问用户训练数据，因此委派训练智能体（Workout Agent）。

```text
“根据最近四周训练量调整一下训练计划。”
```

涉及训练历史、训练规则和计划生成，也委派训练智能体。

```text
“我今天已经摄入多少蛋白质？”
```

需要读取饮食记录（Meal Log）和营养计算，由饮食智能体（Diet Agent）执行。

所以系统判断的不是「这个问题属于哪个领域」，而是「完成当前任务是否需要某个领域独有的能力」。这使智能体的边界建立在实际执行能力上，而不是关键词分类上。

## Supervisor 决策的结构化输出：SupervisorAction

会话主管（Supervisor）是持续存在的完整智能体，但它对协作状态的修改不是直接的。Supervisor 适合决定业务编排——要不要委派、先 Workout 还是 Diet、两个领域是否依赖、收到冲突后下一步修哪个；它不能直接改领域任务状态、依赖关系或父任务的完成状态。它每轮输出的是一个结构化的编排动作（SupervisorAction，一轮决策的结构化输出，不是新的长期数据库对象）：

```python
class SupervisorAction:
    action_type: Literal[          # 本轮决策的类型
        "direct_answer",           # 直接回答，不委派
        "create_domain_task",      # 创建领域任务（幂等 ensure 语义）
        "wait_for_tasks",          # 等待在途领域任务终止
        "request_user_input",      # 把输入请求的问题交给主会话问用户
        "create_revision_task",    # 冲突裁决后创建修订任务
        "complete_parent_task",    # 声明父目标业务上可以结束
    ]
    payload: dict                  # 动作参数：目标领域、objective、输入产物引用等
```

之后的链路是「Supervisor 输出动作 → 根运行时校验器逐项验证 → 确定性修改编排状态」。例如创建饮食任务前，校验器确认前置任务存在且属于本父任务、输入产物已就绪（ready）、目标领域在允许范围内、任务数量与委派深度仍在预算内；任何一项不满足，动作被拒绝并把原因返回给 Supervisor 重新决策——智能体不能靠自行填写参数越过这些条件。分工由此清晰：**Supervisor 决定业务上做什么，根运行时决定状态条件是否允许、并落状态**；Supervisor 每轮看到的是编排状态经第二章装配链投给它的投影，而不是从聊天历史里回忆任务进展（完整调用链与校验清单见 [[12.代码级逻辑：Supervisor 如何持续推进跨领域任务]]）。

## 共享能力与前端结构化操作

会话主管（Supervisor）还可以拥有少量真正通用、低复杂度的能力（Capability）。例如习惯（Habit）打卡，或者产品未来增加的通用实时信息工具，可以直接暴露给会话主管，不需要为每个工具创建一个智能体。

对于前端已经具有明确语义的结构化操作，例如用户点击习惯（Habit）页面上的「完成今日肌酸打卡」，甚至不要求请求经过大语言模型（LLM）：前端可以通过普通业务 API 完成操作。智能体运行时（Agent Runtime）主要处理自然语言驱动、需要理解和决策的交互，而不是强迫 App 的每一个按钮都经过智能体。

## 边界问答

**1. Q：** 为什么不再设一层独立的大语言模型（LLM）路由（Router）？

**A：** 路由（Router）→ 会话主管（Supervisor）会重复两次语义判断。领域选择本身就是会话主管决策的一部分，会话主管（Supervisor）是持续存在的完整智能体，可以在每一步动态决定直接回答、调用共享能力还是委派领域智能体。

**2. Q：** 「高 GI 食物是什么」属于饮食话题，为什么不由饮食智能体回答？

**A：** 它不依赖用户私有业务状态、不需要领域工具、不需要复杂工作流，也不需要大量专业上下文，会话主管直接回答即可。委派判断的依据是「是否需要领域独有的能力」，而不是「属于哪个领域」。

**3. Q：** 为什么不让 App 的每个按钮都经过智能体？

**A：** 前端已经有明确语义的结构化操作（如点击「完成今日肌酸打卡」）可以直接通过普通业务 API 完成。智能体运行时（Agent Runtime）处理的是自然语言驱动、需要理解和决策的交互，强迫每个按钮经过大语言模型（LLM）是多余的一层。

**4. Q：** 会话主管（Supervisor）既是通用助手（generalist）又是编排者（orchestrator），会不会职责过重？

**A：** 这正是设计取舍：与其加一层路由（Router）重复语义判断，不如让会话主管这一个完整智能体承担两个职责。简单请求留在会话主管（Supervisor）层完成、只有真正需要领域能力的请求才委派，成本靠减少无意义委派来控制。
