# HIL 与异步任务

## Subagent 不持有会话控制权

子智能体（Subagent）默认不拥有与用户的会话控制权。如果训练智能体（Workout Agent）在任务过程中发现缺少必要输入，不直接向用户发送独立消息，而是返回带稳定身份的输入请求（InputRequest）——匿名的 `{field, question}` 字典无法登记、匹配与取消，缺输入必须成为有身份的对象：

```python
class InputRequest:
    input_request_id: str        # 输入请求身份，如 IR50；回答匹配、状态流转、取消都引用它
    domain_task_id: str          # 属于哪个领域任务，如 DT10——用户回答后恢复谁的依据
    parent_task_id: str          # 挂回父任务，供其等待清单（pending_input_request_ids）登记引用
    field: str                   # 缺少的输入字段，如 available_training_days
    question: str                # 向用户提出的问题，如「每周最多可以安排几天训练？」
    status: Literal[             # 请求状态：等待 / 已回答 / 已取消
        "pending", "answered", "cancelled"]
```

InputRequest 由根运行时创建并持久登记：父任务的等待清单持有它的引用，`pending → answered / cancelled` 的流转发生在它自己的 `status` 字段上，回答匹配与取消都以 `input_request_id` 为键。训练智能体缺输入时在任务结果里携带它返回：

```python
AgentResult(
    status="needs_input",              # 终止状态：缺必要输入
    input_request=InputRequest(...)    # 携带完整输入请求（IR50，pending）
)
```

会话主管（Supervisor）将多个领域请求统一处理，再由主会话向用户发问：

```text
训练智能体
      ↓
需要输入（needs_input）+ IR50
      ↓
会话主管
      ↓
用户
```

如果训练与饮食智能体同时缺输入，会话主管可以把两个请求合并成一次用户提问展示，但底层 `IR50 → 训练任务`、`IR51 → 饮食任务` 的映射不能丢——合并的是展示，不是身份。

用户补充信息后，输入解析（Input Resolution）按 `input_request_id` 结构化匹配：IR50 置为 answered，根状态图（Root StateGraph）据此把对应的领域任务（DomainTask）从 `waiting_input` 拉回可执行——不靠会话主管重读聊天历史猜测「这句话是回答谁的」。普通新消息不解除等待，这条边界与第一章「会话继续不打扰任务」一致。

如果某个领域工作流（Domain Workflow）内部存在高风险确认点，也可以触发中断（interrupt），但最终的会话控制权仍在会话主管。官方子智能体（Subagent）文档同样默认子智能体（Subagent）将结果返回主智能体（main agent），而不是直接持有用户交互。检查点（Checkpoint）、中断（Interrupt）后从哪个节点继续、用户回答如何重新映射到任务（Task），属于第一章控制平面的详细设计（见 [[6.HIL 与恢复]]）。

## 三种执行方式

系统明确区分三种执行方式：

```text
同步执行
同请求并行执行
后台异步执行
```

同步执行用于会话主管（Supervisor）下一步立即依赖子智能体（Subagent）结果的场景。

同请求并行是：

```python
await gather(workout_task, diet_task)
```

两项任务并行，但当前请求仍然等待全部必要结果返回。这只是并发优化，不是后台任务系统。

真正的异步执行意味着当前会话不等待任务完成。官方当前子智能体（Subagents）文档也特别区分了后台异步（background async）与 Python `async/await`：真正的 async 是主智能体启动一个后台任务（job）后继续运行，而不是单纯把函数写成 `async def`。

三种执行方式与 Run 的归属：

```text
同步执行 / 同请求并行
→ DomainTask 是父任务当前 Run 内的结构化工作单元：
  domain_task_id 定位，不拥有独立的 task / Run / Checkpoint 生命周期
→ 通过 Domain Agent Span 区分执行主体

后台异步执行
→ 同一个 DomainTask（协作层身份不变），执行交给异步运行时
→ 持久执行记录（AsyncAgentTask）绑定 domain_task_id，拥有独立 run_id
→ 完成后经任务状态把结果接回父任务
```

Run 的身份语义见 [[4.Conversation 与 Task 生命周期#任务与 Run]]。

## 进入后台异步运行时的条件

只有满足以下特征的任务才进入后台异步运行时（Async Runtime）：任务明显耗时较长；当前用户响应不依赖结果立即完成；或者任务需要多个智能体 / 外部系统长期执行。

后台任务建立持久化的执行记录。AsyncAgentTask 不是与领域任务（DomainTask）平级的第二种业务任务定义——否则「DT10 进入后台以后为什么突然变成另一个任务」无法回答。统一语义是：**DomainTask 是协作层稳定身份，AsyncAgentTask 是它进入后台运行时后的持久执行记录**，绑定 `domain_task_id`，完成后的结论写回对应的 DomainTask：

```python
class AsyncAgentTask:
    async_agent_task_id: str        # 后台执行记录身份，如 AE500
    domain_task_id: str             # 属于哪个领域任务：协作层身份不变，执行记录只回答「这次后台执行运行到哪了」
    parent_task_id: str             # 挂回父任务

    run_id: str                     # 本段后台执行独立拥有的 Run
    assigned_agent: str             # 实际执行的领域智能体

    status: Literal[                # 执行记录状态
        "queued",                   # 已入队
        "running",                  # 执行中
        "waiting_input",            # 等待用户输入
        "succeeded",                # 成功
        "failed",                   # 失败
        "cancelled"                 # 已取消
    ]

    created_at: datetime             # 创建时间
    started_at: datetime | None      # 开始执行时间，可为空
    finished_at: datetime | None     # 结束时间，可为空

    error_code: str | None           # 失败错误码，可为空
```

稳定关系是「AE500 succeeded → DT10 succeeded」：执行记录与领域任务不拥有互相冲突的业务目标；产物引用也不在执行记录上重复维护，仍由 DomainTask 的输入输出引用承载。

会话主管通过统一接口提交和操作后台任务：

```python
handle = async_runtime.submit(task)      # 提交后台任务，拿到句柄
async_runtime.get_status(handle)         # 查询任务状态
async_runtime.cancel(handle)             # 取消任务
```

## 完成如何接回父任务

任务完成后首先持久化产物（Artifact），再产生完成事件：

```text
异步任务
    ↓
领域智能体
    ↓
产物已持久化
    ↓
领域任务 = 成功（succeeded）
    ↓
任务完成事件
    ↓
父任务重新可评估
    ↓
会话主管被再次调用，决定下一步
```

后台完成只表示对应的领域任务 succeeded，不表示父任务目标完成——如果其他领域任务还没执行，父任务不能进入完成态，异步回调直接判定父任务完成是被禁止的。父任务恢复依赖确定性的任务（Task）状态，而不是让模型重新读取整段聊天并猜测「之前执行到哪里」。

具体的队列（Queue）、工作线程池（Worker Pool）、优先级（Priority）、背压（Backpressure）等生产调度实现属于第六章。第五章只要求异步运行时（Async Runtime）具备持久的任务身份（durable task identity）、状态（status）、结果引用（result reference）和取消/恢复（cancel/resume）接口，不提前引入 Kafka 或复杂分布式任务基础设施。

## 边界问答

**1. Q：** 子智能体（Subagent）缺输入时为什么不直接问用户？

**A：** 子智能体（Subagent）默认不持有会话控制权。它返回 `needs_input`，由会话主管（Supervisor）统一收集多个领域的请求后再由主会话发问，保持会话控制权在会话主管。

**2. Q：** 同请求并行和真正异步有什么区别？

**A：** 同请求并行是 `await gather` 的并发优化，当前请求仍等全部结果返回；真正异步是主智能体启动后台任务（job）后继续运行，当前会话不等待任务完成。官方特意区分后台异步（background async）和 Python `async/await`。

**3. Q：** 什么任务才进入后台异步运行时（Async Runtime）？

**A：** 任务明显耗时较长、当前用户响应不依赖结果立即完成、或者需要多个智能体 / 外部系统长期执行。同步请求和同请求并行覆盖不了这类场景，才走后台。

**4. Q：** 后台任务完成后，父任务怎么知道可以继续？

**A：** 完成链路是「先持久化产物（Artifact）→ 领域任务置为成功（succeeded）→ 发任务完成事件 → 父任务重新可评估 → 会话主管决定下一步」。后台完成只覆盖一个领域任务，父任务是否完成由会话主管声明、根运行时按完成条件校验；父任务恢复依赖确定性的任务（Task）状态，不靠模型读聊天猜测进度。
