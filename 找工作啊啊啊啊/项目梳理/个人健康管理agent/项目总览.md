# 个人健康管理agent · 项目总览

> [!important] 故事骨架已冻结（2026-09-04）
> 本篇确定的项目主线、Hero Scenario 与七章映射、七次边界、三条设计原则、各章唯一主问题与章节顺序即最终骨架，不再因措辞与表达偏好继续重构。只有三种情况允许重新打开骨架：代码实现证明当前设计技术上无法成立；不同章节出现真实技术矛盾（职责真的冲突，而非文字重复）；面试准备中发现主故事存在事实错误。下一阶段为代码证据与纵向链路落地。

## 项目最初解决什么问题

个人健康管理 agent 是一个健身 / 饮食健康管理系统，业务上分为训练与饮食两个领域，分别由训练智能体与饮食智能体负责；每日计划是训练智能体内部的领域工作流。它最初的目标很简单：用户用自然语言提问，系统给出回答；用户要求安排训练、记录饮食时，系统调用业务数据完成操作。这个阶段的系统是一个「会聊天、会查数据的智能体」——一次请求对应一次智能体执行，一次执行对应一轮模型调用和少量工具调用。用户请求、聊天历史、工具调用三者可以互相推断，系统语义不需要额外的运行机制来维护。

这种简单形态在当时是合理的：请求短、任务生命周期等于请求生命周期、工具调用即执行、信息都在聊天里。它隐含了一系列假设，这些假设在业务复杂度上升以后逐一失效。整个项目要讲的故事，就是这些假设如何被新的业务场景打破，以及 Harness（智能体运行框架，负责承载和约束智能体的执行）如何被一步步补强。

## 业务复杂度如何逐渐提高：Hero Scenario

用一个贯穿全部章节的场景说明这种复杂度变化。用户过去习惯早晨训练；因为工作安排变化，用户告诉系统：

> 以后工作日只能晚上训练了。最近训练量也有点大，帮我重新调整一下这周的训练计划，饮食也跟着调整一下。

这个请求表面上是一句话。沿着它从「生成新计划」走到「最终建议」，会依次出现七个矛盾，每一个都是原来可以靠聊天历史和一次请求隐式表达、现在必须变成明确机制的问题。它们正是七章的来源，出现顺序与章节一一对应：

1. **计划等待确认，会话还在继续（第一章）**。系统生成新的训练方案后需要用户确认；用户可能暂时不确认，但仍然可以继续问别的健康问题，比如「晚上训练的话，晚饭应该提前多久吃？」。暂停中的计划任务和当前会话不再拥有相同生命周期——这把 Conversation 与 Task 分开。
2. **完整保存的运行历史与按需供给的本轮上下文（第二章）**。任务可以暂停、恢复、长期存在以后，会持续积累聊天历史、工具结果、中间状态、恢复信息和执行轨迹。这些内容为了恢复和排障需要完整保存；模型每一轮却只需要完成当前判断所需的信息——这把完整 Runtime State 与模型本轮上下文分开。
3. **任务状态、长期用户事实、正式业务事实与外部知识（第三章）**。「以后工作日只能晚上训练」这条事实，以后其他任务仍然要用；与此同时，当前建议还可能依赖当前正式训练计划、用户长期偏好和外部训练 / 饮食知识。这四类信息的生命周期与权威来源各不相同，不能都算作当前任务状态——这把 Task State 与长期用户事实、正式业务事实、外部领域知识分开。
4. **模型提议不等于真实业务修改（第四章）**。用户确认新的训练计划以后，系统需要真正修改业务数据。模型输出「应该替换训练计划」只是一次提议，距离真实业务修改还隔着工具运行时的受理、权限校验与可靠执行——这把 LLM Tool Call、工具运行时接管的动作与真实业务修改分开。
5. **跨领域目标需要持续负责人（第五章）**。训练调整完成以后，新的训练时间、日期、负荷要成为饮食调整的输入：训练产生结构化结果，饮食基于结构化结果继续处理。这需要有人在整个跨领域目标期间持续负责推进，而不是只做一次性路由——旧版顶层只完成一次性领域选择的 Root Router 恰恰没有这个角色，这正是第五章把编排责任交还会话主管（Supervisor）的原因。
6. **请求成本不等于任务消耗（第六章）**。到这里，一个任务已经可能跨越多次 HTTP 请求、多轮模型调用、多个工具、人工确认、多个领域智能体和暂停恢复。一次请求的代价不再代表这个任务的真实资源消耗——治理与计量的单位必须从请求提升到任务。
7. **最终回答错误不等于只有最终生成出错（第七章）**。当最终建议出现问题时，错误可能来自记忆没取到、检索没命中、上下文没装载、智能体判断错、工具执行错，也可能是最终回答描述错。只看最终答案无法定位错误在哪一层，需要沿执行轨迹分层检查。

必须说明：Hero Scenario 是为了统一解释七章架构而选择的复杂案例，不是说每个用户请求都经过全部七章。系统是渐进升级的：

```text
普通问答                  → 简单回答
需要当前业务数据           → 单领域智能体 / 查询工具
需要长期个人事实           → 记忆检索
需要外部专业知识           → RAG
需要修改真实业务数据       → 工具运行时
达到风险条件               → 人工介入（HIL）
真正跨领域                 → 会话主管 + 领域智能体
长生命周期或成本较高       → Task 级运行时治理
```

## 七次主要边界变化

把上面的矛盾归纳起来，整个项目一共发生了七次边界重构，每一次对应一章：

```text
Conversation ≠ Task                                    （第一章：任务执行到哪里）
完整 Runtime State ≠ 模型本轮上下文                     （第二章：模型本轮看到什么）
Task State ≠ 长期用户事实 ≠ 正式业务事实 ≠ 外部领域知识 （第三章：跨任务的信息从哪来）
LLM Tool Call ≠ 工具运行时接管的动作 ≠ 真实业务修改     （第四章：动作如何安全执行）
跨领域整体编排 ≠ 单领域内部执行                         （第五章：谁持续推进整个目标）
Request ≠ Task 资源成本                                 （第六章：任务允许消耗多少资源）
最终回答质量 ≠ 整个执行链路正确性                       （第七章：错在哪一层）
```

## 三条统一设计原则

七章背后只有三条设计原则，所有机制都是这三条原则的具体化。

**原则一：不同生命周期、不同权威来源的数据必须分开。** 任务运行状态、正式业务事实、模型本轮看到的内容、跨任务长期用户事实，它们的维护者不同、生命周期不同、是否允许恢复不同、是否代表现实世界不同、是否应该进入模型上下文也不同。分开不是因为「架构上就应该分层」，而是因为它们在这些维度上确实不同，混在一起必然互相干扰。

**原则二：LLM 处理模糊语义，确定性程序维护明确系统状态。** 用户意图、领域分析、计划生成这类没有唯一答案的问题交给模型；当前任务编号、当前执行阶段、当前计划版本、用户批准的是哪一次调用、工具是否已经执行、是否超出预算这类系统里存在唯一确定答案的问题，由程序直接维护，不让模型从自然语言历史里猜。判断标准是：一个问题在系统中应该存在唯一确定答案时，就不要让模型猜。

**原则三：跨重要边界传递信息时，优先使用稳定结构，而不是聊天历史。** 当前执行阶段（AgentStatus）、证据（Evidence）、领域任务（DomainTask）、领域产物（Artifact）、工具调用实例（ToolInvocation）、执行记录（ExecutionRecord）、执行轨迹（Trace），这些结构各自解决一个「靠聊天历史说不清」的问题：模型自己猜阶段、证据无法引用、任务目标含糊、跨领域交付靠猜、动作没有稳定身份、执行过程无法定位、错误无法归因。结构把模糊的语义交流变成程序可以校验的确定信息；每个结构的具体定义放在它所属的章节。

## 七章如何逐层展开

七章不是七个并列专题，而是按照业务复杂度和系统依赖关系逐层展开的一条主线。上一章先明确一种 Harness 边界；在这个边界已经清楚之后，系统继续承担更复杂业务时，又会出现下一类不能继续混在当前边界里的问题。这不是说每一章的问题都由上一章的方案造成——长期记忆的需求并不是有了上下文装配器才产生，工具安全与多智能体协作也各有独立动因——而是说，上一层边界没有明确之前，下一类问题与它混在一起、归属不清；边界明确以后，下一类问题才作为独立问题显形。

```text
Task 可以正确暂停和恢复（第一章）
        ↓ 边界明确后，完整 Task State 不能等于模型本轮上下文
上下文工程（第二章）
        ↓ 当前 Task 上下文可控了，跨 Task 长期事实和外部知识不属于当前 State
记忆 / RAG / 证据装配（第三章）
        ↓ 智能体得到可靠信息了，模型提出 Tool Call 不能直接修改真实数据
工具运行时（第四章）
        ↓ 单领域动作安全了，训练 → 饮食的任务没有持续存在的整体负责人
多智能体协作（第五章）
        ↓ Task 能跨请求跨智能体长期运行了，HTTP Request 不再代表真实资源成本
运行时治理（第六章）
        ↓ 系统能稳定执行复杂任务了，但执行完成不代表整个行为正确
测试与评估（第七章）
```

以第二章到第三章的过渡为例：上下文装配器明确了当前任务内已有信息怎样进入模型，这条边界清楚之后，「以后只能晚上训练」这类需要在任务结束以后继续存在的信息，就不能继续混在当前 Task State 里，长期记忆由此成为独立的机制边界——不是说这个需求此时才产生，而是说它此时才能与任务状态清楚分开。每一章过渡都遵循同样的推理方式，不再逐章展开。

## 简单请求与复杂请求的渐进式路径

这套架构不是为了复杂而复杂。系统对请求按需分级：

```text
「高 GI 食物是什么？」
→ 会话主管直接回答，不触发任何后续模块

「我昨天深蹲做了多少？」
→ 需要访问训练数据，委派训练智能体，调用查询工具

「根据最近四周训练量调整一下训练计划。」
→ 需要长期记忆、业务事实、领域知识，走记忆检索 + 证据装配 + 领域工作流

「以后只能晚上训练，帮我调整这周计划和饮食。」
→ Hero Scenario 全链路：记忆写入 + 任务创建 + 计划生成 + 人工确认 + 工具执行 + 跨领域协作
```

系统只在请求确实需要的层上付出成本。这也是第三章「普通常识问题不触发记忆检索」、第五章「不默认使用多智能体」、第六章「治理对象是逻辑任务而不是请求」这些设计克制的原因。

## 整个项目最终回答的一个问题

把七章重新收回来：一个健康管理 Agent 从短对话演化成能长期运行、跨会话记忆、调用真实工具、等待用户确认、跨领域协作并产生真实业务修改的系统以后，原来可以靠一次请求、聊天历史和简单工具调用隐式表达的系统语义，必须逐步提升成明确的 Harness 机制。七章就是七次「语义显式化」：任务生命周期显式化、模型上下文显式化、跨任务信息显式化、动作执行显式化、跨领域编排显式化、资源治理显式化、质量反馈显式化。最终，系统不再靠模型从历史里猜「现在执行到哪、该做什么、做没做成」，而是由 Harness 用确定性机制维护这些答案，模型只负责它真正擅长的语义判断。

各机制的实现程度（已实现 / 雏形 / 已确定设计未实现 / 未来改进）见 [[实现真实性地图]]，防止把设计当成已实现能力。
