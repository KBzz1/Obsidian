# 个人健康管理agent · 项目总览

## 项目最初解决什么问题

个人健康管理 agent 是一个健身 / 饮食健康管理系统，业务上分为训练与饮食两个领域：会话主管统一协调训练智能体与饮食智能体两个领域智能体，每日计划是训练智能体内部的领域工作流。它最初的目标很简单：用户用自然语言提问，系统给出回答；用户要求安排训练、记录饮食时，系统调用业务数据完成操作。这个阶段的系统是一个「会聊天、会查数据的智能体」——一次请求对应一次智能体执行，一次执行对应一轮模型调用和少量工具调用。用户请求、聊天历史、工具调用三者可以互相推断，系统语义不需要额外的运行机制来维护。

这种简单形态在当时是合理的：请求短、任务生命周期等于请求生命周期、工具调用即执行、信息都在聊天里。它隐含了一系列假设，这些假设在业务复杂度上升以后逐一失效。整个项目要讲的故事，就是这些假设如何被新的业务场景打破，以及 Harness（智能体运行框架，负责承载和约束智能体的执行）如何被一步步补强。

## 业务复杂度如何逐渐提高：Hero Scenario

用一个贯穿全部章节的场景说明这种复杂度变化。用户过去习惯早晨训练；因为工作安排变化，用户告诉系统：

> 以后工作日只能晚上训练了。最近训练量也有点大，帮我重新调整一下这周的训练计划，饮食也跟着调整一下。

这个请求表面上是一句话，实际上同时触发了七种不同的系统需求：

1. **长期事实变化**：「习惯早晨训练」变成「工作日只能晚上训练」。这条新事实以后其他任务仍然要用，不能只存在当前对话里。
2. **当前业务事实**：系统不能靠聊天历史猜测用户当前使用哪版训练计划，真正生效的计划来自正式业务数据。
3. **长生命周期任务**：系统生成新训练方案后需要用户确认；用户可能暂时不确认，任务应该暂停但没有结束。
4. **Conversation 与 Task 不同步**：等待确认期间用户继续问「晚上训练的话，晚饭应该提前多久吃？」，这条消息不应该自动变成「恢复旧任务」。
5. **真实工具副作用**：用户确认以后，系统要真正修改训练计划。模型认为「应该替换训练计划」不等于「系统拥有修改数据库的权限」。
6. **跨领域协作**：训练计划修改完成后，新的训练日期、时间、负荷成为饮食智能体调整饮食计划的输入，需要「训练产生结构化结果、饮食基于结构化结果继续」，而不是两个智能体各自读聊天历史猜测。
7. **更长的执行链**：一个任务最终可能包含多次模型调用、记忆与检索、两个领域智能体、多次工具调用、人工确认、暂停恢复。这进一步产生资源治理和评估问题。

必须说明：Hero Scenario 是为了统一解释七章架构而选择的复杂案例，不是说每个用户请求都经过全部七章。系统是渐进升级的：

```text
普通问答                  → 简单回答
需要当前业务数据           → 单领域智能体 / 查询工具
需要长期个人事实           → 记忆检索
需要外部专业知识           → RAG
需要修改真实业务数据       → 工具运行时
达到风险条件               → 人工介入（HIL）
真正跨领域                 → 会话主管 + 领域智能体
长生命周期或成本较高       → Task 级运行时治理
```

## Hero Scenario 逐步暴露哪些边界问题

上面的七种需求不是同时出现的，而是随着系统一步步加能力逐步暴露的。每一项都对应一个「原来可以靠聊天历史和一次请求隐式表达、现在必须变成明确机制」的矛盾：

- 「以后只能晚上训练」这条信息如果在任务结束就消失，用户下次训练计划又会按早晨生成。它必须跨越任务、跨越会话继续存在——这就把任务内部状态和长期用户事实分开。
- 系统不能靠聊天历史猜当前用哪版计划，因为聊天里可能出现过多个草稿；正式生效的版本在业务数据库里。这就把运行状态和正式业务事实分开。
- 生成新方案后用户不马上确认，任务要暂停但不能结束；等待期间用户继续问饮食问题，不能把这条消息当成恢复旧任务。这就把会话和任务分开。
- 模型说「替换训练计划」和系统真的修改数据库之间隔着权限、确认和真实执行。这就把模型提议和真实动作分开。
- 训练计划修改完成后饮食要接着调整，两个领域之间需要结构化交付而不是互相猜。这就把单领域执行和跨领域编排分开。
- 一个任务跨请求、跨领域、跨人工确认长期存在后，一次请求的代价已经不能代表这个任务的资源消耗。这就把请求和任务资源成本分开。
- 最终回答错了，可能是记忆没取到、取到了没进上下文、上下文对但判断错、动作对但工具执行错。只看最终答案无法定位。这就把最终回答质量和整个执行链路正确性分开。

## 七次主要边界变化

把上面的矛盾归纳起来，整个项目一共发生了七次边界重构，每一次对应一章：

```text
Conversation ≠ Task                    （第一章：任务执行到哪里）
完整 Runtime State ≠ 模型本轮上下文     （第二章：模型本轮看到什么）
Task State ≠ 长期用户事实 / 外部知识    （第三章：跨任务的信息从哪来）
LLM Tool Call ≠ 真实业务动作            （第四章：动作如何安全执行）
单领域执行 ≠ 跨领域整体编排             （第五章：谁持续推进整个目标）
Request ≠ Task 资源成本                 （第六章：任务允许消耗多少资源）
最终回答质量 ≠ 整个执行链路正确性       （第七章：错在哪一层）
```

## 三条统一设计原则

七章背后只有三条设计原则，所有机制都是这三条原则的具体化。

**原则一：不同生命周期、不同权威来源的数据必须分开。** 任务运行状态、正式业务事实、模型本轮看到的内容、跨任务长期用户事实，它们的维护者不同、生命周期不同、是否允许恢复不同、是否代表现实世界不同、是否应该进入模型上下文也不同。分开不是因为「架构上就应该分层」，而是因为它们在这些维度上确实不同，混在一起必然互相干扰。

**原则二：LLM 处理模糊语义，确定性程序维护明确系统状态。** 用户意图、领域分析、计划生成这类没有唯一答案的问题交给模型；当前任务编号、当前执行阶段、当前计划版本、用户批准的是哪一次调用、工具是否已经执行、是否超出预算这类系统里存在唯一确定答案的问题，由程序直接维护，不让模型从自然语言历史里猜。判断标准是：一个问题在系统中应该存在唯一确定答案时，就不要让模型猜。

**原则三：跨重要边界传递信息时，优先使用稳定结构，而不是聊天历史。** 当前执行阶段（AgentStatus）、证据（Evidence）、领域任务（DomainTask）、领域产物（Artifact）、工具调用实例（ToolInvocation）、执行记录（ExecutionRecord）、执行轨迹（Trace），这些结构各自解决一个「靠聊天历史说不清」的问题：模型自己猜阶段、证据无法引用、任务目标含糊、跨领域交付靠猜、动作没有稳定身份、执行过程无法定位、错误无法归因。结构把模糊的语义交流变成程序可以校验的确定信息；每个结构的具体定义放在它所属的章节。

## 七章因果关系

七章不是七个并列专题，而是一条因果链：每一章解决的问题，都是上一章的方案在更大场景下暴露出来的新问题。

```text
Task 可以正确暂停和恢复（第一章）
        ↓ 但完整 Task State 不能等于模型本轮上下文
上下文工程（第二章）
        ↓ 当前 Task 上下文可控了，但跨 Task 长期事实和外部知识不属于当前 State
记忆 / RAG / 证据装配（第三章）
        ↓ 智能体得到可靠信息了，但模型提出 Tool Call 不能直接修改真实数据
工具运行时（第四章）
        ↓ 单领域动作安全了，但训练 → 饮食的任务没有持续存在的整体负责人
多智能体协作（第五章）
        ↓ Task 能跨请求跨智能体长期运行了，HTTP Request 不再代表真实资源成本
运行时治理（第六章）
        ↓ 系统能稳定执行复杂任务了，但执行完成不代表整个行为正确
测试与评估（第七章）
```

以第二章到第三章的过渡为例：上下文装配器已经解决了当前任务内已有信息怎样进入模型，但「以后只能晚上训练」这种信息需要在任务结束以后继续存在，因此不能继续放在当前 Task State 里，这才需要长期记忆。每一章过渡都遵循同样的推理方式，不再逐章展开。

## 简单请求与复杂请求的渐进式路径

这套架构不是为了复杂而复杂。系统对请求按需分级：

```text
「高 GI 食物是什么？」
→ 会话主管直接回答，不触发任何后续模块

「我昨天深蹲做了多少？」
→ 需要访问训练数据，委派训练智能体，调用查询工具

「根据最近四周训练量调整一下训练计划。」
→ 需要长期记忆、业务事实、领域知识，走记忆检索 + 证据装配 + 领域工作流

「以后只能晚上训练，帮我调整这周计划和饮食。」
→ Hero Scenario 全链路：记忆写入 + 任务创建 + 计划生成 + 人工确认 + 工具执行 + 跨领域协作
```

系统只在请求确实需要的层上付出成本。这也是第三章「普通常识问题不触发记忆检索」、第五章「不默认使用多智能体」、第六章「治理对象是逻辑任务而不是请求」这些设计克制的原因。

## 整个项目最终回答的一个问题

把七章重新收回来：一个健康管理 Agent 从短对话演化成能长期运行、跨会话记忆、调用真实工具、等待用户确认、跨领域协作并产生真实业务修改的系统以后，原来可以靠一次请求、聊天历史和简单工具调用隐式表达的系统语义，必须逐步提升成明确的 Harness 机制。七章就是七次「语义显式化」：任务生命周期显式化、模型上下文显式化、跨任务信息显式化、动作执行显式化、跨领域编排显式化、资源治理显式化、质量反馈显式化。最终，系统不再靠模型从历史里猜「现在执行到哪、该做什么、做没做成」，而是由 Harness 用确定性机制维护这些答案，模型只负责它真正擅长的语义判断。

各机制的实现程度（已实现 / 雏形 / 已确定设计未实现 / 未来改进）见 [[实现真实性地图]]，防止把设计当成已实现能力。
