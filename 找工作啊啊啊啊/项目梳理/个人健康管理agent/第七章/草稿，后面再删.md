# 第七章 测试、评估与质量反馈

本章负责验证 Agent 系统在真实任务中的行为是否正确，并为后续版本迭代提供可重复的质量基线。前面的章节已经分别定义了任务状态、上下文装配、Memory 与 Evidence、Tool Runtime、多 Agent 协作以及生产运行治理，本章不重新实现这些能力，而是利用各模块在执行过程中产生的结构化事实，还原一次 Agent Task 实际看到了什么、做了什么以及产生了什么结果，再基于这些事实进行分层评估。

与普通文本生成应用不同，Agent 应用不能只通过最终回答判断质量。一个最终答案可能表面正确，但 Agent 在过程中调用了不必要的 Tool、使用了错误的业务状态，或者绕过了应该发生的 HIL；反过来，一次任务失败也可能不是模型判断错误，而是 Retrieval 没有找到正确资料、Context Assembler 没有把已有 Evidence 放入上下文，或者 Tool 返回了真实业务冲突。因此，本章将观测与评估连接成一套统一体系：观测负责还原执行事实，评估负责判断这些事实是否符合任务预期。

整体关系可以表示为：

```text
Agent Task 执行
    ↓
各 Runtime 产生结构化运行事实
    ↓
Trace 将一次 Run 中的调用关系串联起来
    ↓
还原模型当时看到的 Context、Evidence 与能力
    ↓
还原 Agent 实际执行的 Retrieval、Tool 和 DomainTask
    ↓
构造成可评估的执行轨迹
    ↓
分层 Evaluation
    ↓
Regression Comparison
```

## 7.1 统一观测与执行轨迹

本章的观测体系不建立第二套 Runtime 数据库。Task State、EvidenceBundle、ToolInvocation、ExecutionRecord、DomainTask 等数据仍然由对应模块保存并维护，本章通过统一身份和 Trace 将这些事实关联起来。Trace 负责表达调用关系和执行过程，结构化 Record 保存具有模块语义的事实，Log 用于搜索关键运行事件，Metric 用于观察整体趋势。四者承担不同职责，不相互替代。

### 7.1.1 Task、Run 与 Trace 的身份关系

系统以 `task_id` 表示一个逻辑 Agent Task 的稳定身份。一个 Task 可能因为 HIL、异步等待或故障恢复经历多次连续执行，因此进一步使用 `run_id` 标识某一次实际执行阶段，并为每个 Run 建立独立的 `trace_id`。

```text
task_id
→ 一个逻辑任务的完整生命周期

run_id
→ Task 的一次连续执行阶段

trace_id
→ 该 Run 对应的观测链路
```

例如一个任务第一次运行到 HIL 后暂停，用户完成确认后再次恢复：

```text
task_123

├── run_001
│   └── trace_A
│       → Agent 执行
│       → HIL Requested
│
└── run_002
    └── trace_B
        → Resume
        → Tool Execution
        → Completed
```

这样 Task 可以保持稳定的业务执行身份，而 Trace 不需要跨越长时间等待持续存在。`run_id` 由 Task Runtime 创建并通过 RuntimeContext 向 Agent Runtime、Retrieval Runtime 和 Tool Runtime 传递，使不同模块产生的运行记录能够重新关联到同一次执行阶段。

### 7.1.2 Trace 负责串联执行过程

一次 Run 的 Trace 只覆盖具有实际工程边界的执行阶段，而不是为所有内部函数创建 Span。典型 Trace 可以包括 Supervisor、Domain Agent、模型调用、Retrieval、Tool Runtime、DomainTask 和最终响应等阶段。

```text
Trace: run_002

Root Task Runtime
│
├── Conversation Supervisor
│   └── LLM Call
│
├── Workout Agent
│   ├── Context Assembly
│   ├── LLM Call
│   ├── Retrieval
│   └── Tool Invocation
│       └── Tool Runtime
│
└── Final Response
```

Trace 中保存调用开始和结束时间、状态、错误类型以及相关 Record 的引用。例如 Tool Span 可以保存 `invocation_id`，Retrieval Span 保存 `retrieval_id`，模型调用 Span 保存 `context_id`。真正的 Tool 参数、执行效果和 Evidence 内容仍然从对应的结构化 Record 中获取，而不是复制到 Trace 中。

### 7.1.3 Context Manifest 记录模型实际可见上下文

第二章的 Context Assembler 在每次正式模型调用之前生成 `ContextManifest`，记录本轮模型实际看到了哪些上下文组成以及哪些能力被暴露。它不默认持久化完整 Prompt，而保存必要的引用、版本和摘要信息。

```text
ContextManifest

context_id
task_id
run_id
agent_id
stage

agent_status_ref / version

memory_refs
evidence_refs
tool_result_refs
artifact_refs

visible_tool_refs
visible_skill_refs

prompt_template_version
context_hash
estimated_tokens
```

这一结构主要用于区分不同类型的失败。例如 Agent 没有选择一个正确 Tool 时，系统可以进一步判断该 Tool 当时是否已经进入模型的可见 Tool Surface；Agent 忽略用户伤病限制时，可以检查相关 Evidence 是否进入了 `ContextManifest`。因此评估系统能够分别定位 Context Assembly 和 Agent Decision 的问题，而不是把所有错误归因到模型本身。

完整 Prompt 不作为默认长期观测数据。只有在特定调试或 Evaluation Case 需要时，才在符合隐私要求的情况下生成脱敏 Snapshot。

### 7.1.4 Retrieval Record 连接检索与 Evidence

第三章的 `EvidenceBundle` 表示最终经过验证和装配、可以提供给 Agent 使用的 Evidence。为了评估 Retrieval 和 Evidence Assembly，本章使用第三章补充的 `RetrievalRecord` 还原一次检索中真正返回过哪些候选资料。

```text
RetrievalRecord

retrieval_id
task_id
run_id
agent_id

query_ref / query_hash
source_scope
retrieval_config_version

retrieved_items:
    source_id
    source_version
    rank
    score

selected_evidence_ids
evidence_bundle_id
```

因此一条完整的数据链是：

```text
Retrieval
    ↓
RetrievalRecord
    ↓
Candidate Sources
    ↓
Evidence Assembly
    ↓
EvidenceBundle
    ↓
Context Assembler
    ↓
ContextManifest
```

通过这条链路，评估时可以区分正确资料根本没有被 Retriever 找到、资料已经召回但未进入 EvidenceBundle、EvidenceBundle 已经包含正确内容但没有进入本轮 Context，以及 Agent 已经看到正确 Evidence 但仍然做出错误决策等不同问题。

### 7.1.5 Tool 执行沿用 Tool Runtime 的真实记录

Tool 层不为评估重新建立数据结构。第四章已经定义的 `ToolInvocation`、`ExecutionRecord` 和 `ToolResult` 继续作为 Tool 执行的事实来源。

一个稳定的 ToolInvocation 可能跨越不同 Run。例如 Agent 在 `run_001` 中提出修改计划并进入 HIL，用户确认后真正的工具执行发生在 `run_002`。因此 ToolInvocation 记录最初产生它的 `created_run_id`，具体 Execution Attempt 记录实际执行发生时的 `run_id`。

```text
ToolInvocation invocation_123
│
├── task_id
├── created_run_id = run_001
│
└── ExecutionRecord
    └── run_id = run_002
```

第七章通过这些记录判断 Agent 选择了哪个 Tool、参数是否符合任务要求、执行是否经过批准、最终业务 Effect 是否真实发生，以及失败以后 Agent 是否采取了正确恢复行为。

### 7.1.6 多 Agent 轨迹保持任务边界

同步调用的 Domain Agent 仍然属于父 Task 当前的 Run，通过不同 Agent Span 区分执行主体；拥有独立生命周期、能够独立等待和恢复的异步 DomainTask 则创建自己的 `child_task_id`，并通过 `parent_task_id` 关联父任务。

因此评估系统既可以分析一个 Task 内 Supervisor 与 Domain Agent 的协作轨迹，也可以沿父子任务关系检查异步任务是否正确产生 Artifact 并返回主流程，而不需要让多个 Agent 共享完整历史记录。

### 7.1.7 运行事实、观测数据与评估数据分离

系统将数据分为三个层级。第一类是正式运行事实，包括 Task Control State、Checkpoint、Business Facts、重要 ToolInvocation 和 ExecutionRecord 等，这些数据直接影响恢复、业务状态或安全审计，由对应 Runtime 可靠保存。

第二类是观测数据，包括 Trace、ContextManifest、RetrievalRecord 和结构化运行日志。这些数据主要用于排障、执行分析和发现 Evaluation Case，可以设置合理的保留周期，不要求永久保存。

第三类是固定评估资产。生产运行中发现具有代表性的任务后，不直接把原始 Trace 当作测试用例，而是经过筛选、脱敏和状态冻结，形成不可变的 Evaluation Fixture 和 Eval Case。这样生产数据可以持续反馈到测试体系，同时避免 Eval Dataset 依赖不断变化的线上状态。

## 7.2 Agent 测试与评估体系

评估系统不使用单一总分判断 Agent 是否优秀，而是沿 Agent 执行链路分层定位质量。当前系统将主要评估对象分为四层：上下文与 Evidence、Tool 与动作、Agent 执行轨迹以及最终任务结果。安全、权限和业务约束作为跨层规则贯穿整个评估过程。

```text
上下文与 Evidence
        ↓
Tool / Action
        ↓
Agent Trajectory
        ↓
Final Task

横向约束：
Safety / Policy / Business Constraints

辅助维度：
Latency / Calls / Token Usage
```

### 7.2.1 Evaluation Case 与固定 Fixture

一个 Eval Case 不是简单的“问题 + 标准答案”，而是一份可重复运行的 Agent 任务场景。它引用一个不可变 Fixture，用于恢复任务开始时的用户状态、业务事实、Memory、Domain Knowledge 和 Current Plan 等必要条件。

```text
EvalCase

case_id
user_request
fixture_ref
capability_config
evaluators
tags
```

Fixture 中的事实在生成 Eval Case 时被脱敏并冻结，使同一个 Case 在不同版本系统上运行时具有相同起点，而不是依赖当前线上数据库或可能已经发生变化的 Memory。

每个 Case 只声明与自身相关的 Evaluator。例如一个 Retrieval Case 只需要运行 Recall 和 Evidence Coverage；一个 Tool Recovery Case 可以同时检查 Tool Selection、参数、恢复轨迹和最终业务结果；复杂 Workout Planning Case 才需要进一步进入最终 Rubric 和 LLM-as-Judge。

### 7.2.2 上下文与 Evidence 评估

这一层评估 Agent 做出决策之前是否获得了正确的信息。评估链覆盖 Retrieval、Evidence Assembly 和 Context Assembly，而不是只看向量检索的 Top-K 结果。

当前主要保留三个指标。`Recall@K` 检查应该被找到的资料是否进入 Top-K Retrieval Candidate；Evidence Coverage 检查完成任务所需的关键事实是否进入最终 EvidenceBundle；Evidence Grounding 检查 Evidence 中的 Claim 是否真正能够由对应 Source 支持。

结合 `RetrievalRecord`、`EvidenceBundle` 和 `ContextManifest`，评估系统能够进一步定位错误发生在哪一步。例如 Retriever 已经召回正确资料，但 Evidence Assembly 丢掉了该资料；或者 Evidence 已经形成，但 Context Assembler 没有把它加入当前 Agent 的模型上下文。这种分层定位比只评价最终回答是否正确更适合 Agent Harness。

### 7.2.3 Tool 与动作评估

Tool 层重点评估 Agent 是否选择了正确动作，而不是只检查调用最终是否成功。当前主要检查 Tool Selection、参数正确性、不必要调用和禁止行为。

Tool Selection 检查任务要求和实际选择的 Tool 是否匹配；参数评估检查关键字段是否齐全、对象是否正确以及业务参数是否符合用户意图。能够直接进行 Schema 或字段比较的部分使用确定性检查，复杂语义参数才进入 Rubric。

评估系统还会检查 Agent 是否进行了没有必要的 Tool Call 或重复 Tool Call。例如已有 Current Plan Evidence 时，Agent 不应反复调用相同读取工具。对于越权 Tool、跨 Domain Tool、应该经过 HIL 却直接执行等行为，则作为硬约束处理，而不是通过语义评分判断。

### 7.2.4 Agent Trajectory 评估

Agent Trajectory 评估关注从输入到最终结果之间的可观察行为序列。系统不记录也不评估模型内部 Chain-of-Thought，只检查实际发生的 Retrieval、Tool、DomainTask、HIL 和最终响应等动作。

一个 Eval Case 可以声明关键行为约束：

```text
required_actions
forbidden_actions
ordering_constraints
recovery_rules
```

例如修改 Current Workout Plan 时，可以要求读取当前版本必须发生在写入之前；Tool 返回 `CONFLICT` 后，必须重新获取 Current State，再重新规划，而不能使用旧版本参数重复调用。评估不要求 Agent 严格按照唯一 A→B→C 的固定轨迹执行，只约束真正影响正确性的关键动作、前置条件和恢复行为。

这种设计允许 Agent 保留合理的自主规划空间，同时能够判断过程本身是否违反 Harness 规则。

### 7.2.5 Final Task 评估

最终任务层评估用户请求是否真正完成。对于存在明确业务结果的任务，优先使用确定性检查。例如用户要求保存训练记录，可以直接验证业务数据库中对应记录是否产生；Agent 声称“计划已经更新”时，可以检查 Tool Effect 是否确实表明修改成功。

对于 Workout Plan、Nutrition Plan 等没有唯一正确文本的开放式任务，则使用 Rubric 进行语义质量评估。当前 Rubric 主要从任务完成度、约束遵守、事实与 Evidence 一致性、领域合理性以及最终描述与真实业务动作的一致性几个方向进行判断。

Rubric 使用少量离散等级，例如“未满足、部分满足、满足”，而不是依赖过度精细的百分制评分。这样 Judge 更容易保持一致，也更便于解释具体质量问题。

### 7.2.6 确定性检查优先于 LLM-as-Judge

整个 Evaluation 系统遵循一个明确原则：能够从结构化运行事实中确定性判断的问题，不交给 LLM-as-Judge。

例如是否调用正确 Tool、参数字段是否正确、Evidence Source 是否存在、CONFLICT 后是否重新读取状态、是否经过 HIL、最终 Tool Effect 是否成功，这些都直接从 Runtime Record 判断。

LLM-as-Judge 只用于无法完全编码成确定性规则的开放式质量问题，例如一个训练计划是否整体合理、复杂约束是否被充分权衡、最终建议是否完整并符合领域要求。

Judge 接收的也不是完整生产 Trace，而是一份经过整理的评估输入：

```text
JudgeInput

user_request
relevant_business_facts
evidence
executed_actions
tool_effects
final_response
rubric
```

这样 Judge 只看到完成评价所需要的事实，而不是大量无关执行日志。Judge 返回结构化的维度评分、违规项和简短评价说明，不依赖长篇内部推理过程。

为了保证结果可比较，每次 Evaluation Run 会记录 Judge 使用的模型、Judge Prompt Version 和 Rubric Version。系统同时维护一小组人工确认的校准 Case，用于检查 Judge 的评分方向是否与人工判断基本一致。当前系统不引入多 Judge 投票或复杂 Judge Agent，仅在少量重要且波动明显的 Case 上进行重复评估。

### 7.2.7 Evaluation Dataset

当前 Dataset 主要由三类 Case 组成。

第一类是核心能力集，由人工构造并长期保持稳定，覆盖 Supervisor 路由、Workout、Diet、Retrieval、Tool、HIL、多 Agent 等系统主要能力。它用于验证系统基础能力没有随着改动发生明显退化。

第二类是边界与故障集，专门覆盖正常路径不容易暴露的 Harness 行为，例如 Evidence 缺失、Tool Conflict、Timeout、Budget 接近耗尽、HIL Resume、禁止 Tool Call、跨 Domain Tool 等场景。

第三类是生产回归集。生产运行中发现具有代表性的失败后，通过 Trace 和结构化 Record 定位根因，再将必要的用户输入和系统状态脱敏、固定为 Fixture，并定义 Expected Behavior 或 Rubric，最终加入 Regression Dataset。

生产 Trace 本身不是 Eval Case。生产 Trace 记录当时发生了什么，而 Eval Case 必须定义在固定输入条件下系统应该做什么。二者之间必须经过筛选、脱敏、状态冻结和 Ground Truth 补充。

### 7.2.8 Evaluation Run 与版本记录

每次完整评估都会形成独立的 Evaluation Run，并记录当时对应的系统配置，使不同版本之间的结果具有可比性。

```text
EvalRun

eval_run_id
dataset_version

app_version
prompt_version
workflow_version
retrieval_config_version
tool_schema_version

model_config

judge_model
judge_prompt_version
rubric_version

results
```

当前系统不要求所有组件都建设复杂的独立版本管理服务，但至少需要保证一次评估结果能够追溯到对应的 Prompt、Workflow、Retrieval 和 Tool Schema 配置，否则不同时间的 Eval Score 无法可靠比较。

### 7.2.9 Regression 规则

Regression 不使用一个统一总分作为发布判断，而是将评估结果分成三类。

第一类是硬门槛，例如 Forbidden Tool Call、HIL Bypass、跨 Domain 越权、关键业务状态错误以及 Tool Effect 与最终声明明显不一致。这类行为出现后直接视为 Regression Failure，不允许用其他指标上的提升抵消。

第二类是质量指标，例如 Recall@K、Tool Selection Accuracy、Trajectory Pass Rate、Task Completion 和 Constraint Compliance。Candidate Version 与当前稳定 Baseline 使用相同 Dataset 运行，根据已有基线和实际数据逐步设置允许波动范围，而不是在没有数据的情况下提前制定虚假的精确阈值。

第三类是效率指标，包括任务耗时、模型调用次数、Tool 调用次数和 Token Usage。它们通常不直接决定质量 Pass 或 Fail，而用于判断一次质量提升是否付出了过高运行成本。

因此一次 Regression Result 可以有：

```text
PASS
→ 无硬门槛失败，关键质量指标没有明显退化

FAIL
→ 存在硬门槛违规或关键质量明显下降

REVIEW
→ 质量提升但资源成本明显增加，需要人工判断 Trade-off
```

### 7.2.10 不同开发阶段的评估策略

开发阶段不需要每次修改都运行完整 Dataset。Prompt、Context Assembler、Tool Schema 或 Retrieval 调整时，可以先运行少量核心 Case 和当前正在修复的失败 Case，以快速确认改动方向。

准备进入稳定版本前，再运行核心能力集、边界故障集和生产回归集，完成 Retrieval、Tool、Trajectory、Final Task 以及必要的 LLM-as-Judge 评估，并与当前 Baseline 进行 Regression Comparison。

生产环境不默认给每一个真实用户 Task 再额外调用一次 LLM-as-Judge。线上主要通过前述运行观测、关键错误和用户反馈发现问题，只有具有代表性的 Case 才经过脱敏和固定化处理进入 Evaluation Dataset。系统性的 Judge 和 Regression 主要在线下执行，从而避免在线评估增加不必要的延迟和成本。

### 7.2.11 质量反馈闭环

最终，第七章形成的是一个从生产运行回到离线验证的持续反馈过程：

```text
Production Runtime
    ↓
结构化运行事实与 Trace
    ↓
发现异常行为或用户反馈
    ↓
定位 Retrieval / Context / Tool / Trajectory / Final Result
    ↓
脱敏并构造 Eval Case
    ↓
加入 Regression Dataset
    ↓
修改 Prompt / RAG / Tool / Workflow / Agent Policy
    ↓
运行分层 Evaluation
    ↓
与 Baseline 比较
    ↓
Regression Pass
    ↓
进入下一版本
```

这套设计使评估不再只检查最终文本，而是覆盖 Agent 在执行过程中真正具有工程意义的决策边界。ContextManifest 和 RetrievalRecord 使系统能够判断模型当时是否获得了正确信息；ToolInvocation 和 ExecutionRecord 提供真实动作与业务 Effect；Trajectory Evaluation 检查 Agent 是否按照正确前置条件和恢复规则执行；Final Task Rubric 再评价开放式任务的最终质量。确定性规则负责可以明确判断的行为，LLM-as-Judge 只补充开放式语义评价，从而在可解释性、成本和评估覆盖度之间保持平衡。
