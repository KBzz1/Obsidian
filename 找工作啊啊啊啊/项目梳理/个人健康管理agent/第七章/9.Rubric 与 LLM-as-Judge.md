# Rubric 与 LLM-as-Judge

这一节回答：什么问题应该交给 Judge，什么不应该。整个 Evaluation 系统遵循一个明确原则：能够从结构化运行事实中确定性判断的问题，不交给 LLM-as-Judge。

例如是否调用正确 Tool、参数字段是否正确、Evidence Source 是否存在、CONFLICT 后是否重新读取状态、是否经过 HIL、最终 Tool Effect 是否成功，这些都直接从 Runtime Record 判断。

LLM-as-Judge 只用于无法完全编码成确定性规则的开放式质量问题，例如一个训练计划是否整体合理、复杂约束是否被充分权衡、最终建议是否完整并符合领域要求。

Rubric 使用少量离散等级，例如“未满足、部分满足、满足”，而不是依赖过度精细的百分制评分。这样 Judge 更容易保持一致，也更便于解释具体质量问题。

Judge 接收的也不是完整生产 Trace，而是一份经过整理的评估输入：

```text
JudgeInput

user_request
relevant_business_facts
evidence
executed_actions
tool_effects
final_response
rubric
```

这样 Judge 只看到完成评价所需要的事实，而不是大量无关执行日志，也不要求保存模型内部 Chain-of-Thought。Judge 返回结构化的维度评分、违规项和简短评价说明，不依赖长篇内部推理过程。

为了保证结果可比较，每次 Evaluation Run 会记录 Judge 使用的模型、Judge Prompt Version 和 Rubric Version。系统同时维护一小组人工确认的校准 Case，用于检查 Judge 的评分方向是否与人工判断基本一致。当前系统不引入多 Judge 投票或复杂 Judge Agent，仅在少量重要且波动明显的 Case 上进行重复评估。
