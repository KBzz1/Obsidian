# 证据检索

## 用户记忆检索：按需而不是固定召回

长期记忆不在每次请求开始时固定召回前若干条。会话主管或领域智能体根据当前任务判断是否需要用户长期信息，例如：

```text
“深蹲主要训练哪些肌群？”
→ 不需要用户记忆

“根据我的情况帮我安排下周训练计划。”
→ 需要目标 / 伤病 / 可用时间 / 偏好

“为什么我最近的训练安排和以前不一样？”
→ 需要当前语义 + 历史情节
```

记忆检索使用当前已有的 Postgres + pgvector 体系继续演化，不额外引入独立搜索服务。

检索综合三类信号：

```text
结构化过滤
+
语义向量检索
+
词法检索
```

结构化过滤用于限定：

```text
user_id            # 归属用户
memory_type        # episodic / semantic
state_key          # 状态键
subject            # 主体
当前 / 历史        # 是否当前有效
时间范围           # 时间范围
安全等级           # 安全等级
```

语义向量检索主要针对增强备注，用于发现自然语言语义相关的长期记忆。词法检索补足用户名词、器械、动作名称这类向量可能不稳定的精确关键词。

多路结果可以使用倒排融合（RRF）一类简单融合方式合并，再基于时间状态、当前语义、安全优先级和任务相关性做轻量重排序。

普通个性化任务优先读取：

```text
用户画像
      ↓
当前语义记忆
```

只有在需要解释来源、处理冲突、了解变化过程或语义证据不足时，才进一步下钻情节记忆。因此低层情节不需要每次都进入大模型上下文。

## 相似不再等于同一事实

一个贯穿检索与写入的原则：向量相似度只表示「可能相关」，不代表「同一事实」，更不代表「该覆盖」。

```text
旧版：相似 → 可能更新

新版：相似 → 可能相关 → 交给时间 / 语义判断
```

这个转变是第三章改造的根源，见 [[找工作啊啊啊啊/项目梳理/个人健康管理agent/3.把记忆与知识汇成证据/10.困难以及应对办法]]。

## 领域知识检索：结构化优先

领域知识与用户记忆完全分开。项目中的健身动作知识库属于领域知识，它描述的是动作名称、肌群、动作模式、器械、适用场景、限制条件和注意事项等公共领域知识，不描述某个用户。

当前健身动作知识已经具有较强的结构化属性，因此第一阶段优先使用元数据结构化检索，而不是为了引入检索增强生成强行把所有内容切成文本块后做向量召回。

例如训练智能体在选择动作时可以调用：

```python
search_exercise_knowledge(
    target_muscles,     # 目标肌群，如 quads / hamstrings / glutes
    movement_pattern,   # 动作模式，如 squat / hinge / push
    equipment,          # 器械条件，如 barbell / dumbbell / bodyweight
    must_tags,          # 必须满足的标签
    exclude_tags,       # 排除的标签
    user_constraints,   # 用户约束，如伤病限制
)
```

先通过结构化条件缩小候选集合，再返回动作描述和必要知识。

当未来出现越来越多难以通过固定字段表达的自由文本知识，例如更复杂的动作解释、训练理论文章或康复注意事项，再给向量增强后的文本增加向量检索，形成：

```text
结构化过滤
+
向量检索
```

的混合知识检索。

复杂多跳知识问题如果未来确实出现，可以让领域智能体多次调用检索能力，例如第一次搜索后发现证据不足，再修改查询重试。当前简单任务仍采用一次按需检索，不把所有知识请求包装成复杂的智能体式检索增强。

## 业务事实归业务库

正式业务事实始终由业务数据库 / 业务服务管理。例如：

```text
训练记录
饮食记录
习惯打卡
当前训练计划
当前饮食计划
训练历史
```

这些数据不会为了统一记忆而复制一份到向量库。如果智能体需要今天的训练计划，直接查询训练服务；如果需要当前饮食计划，直接查询饮食服务。

业务数据库中的数据只有在形成长期个性化意义时，才可以转换成记忆证据。例如连续多周的训练记录显示用户晚间完成训练更稳定，可以形成一个结构化领域信号：

```text
最近四周的训练主要发生在晚间。
```

这个信号可以作为情节或语义巩固的依据，但仍保留对原始训练记录的引用，而不是复制所有训练明细。

结构化领域信号不需要重新经过自然语言大模型抽取。如果业务程序已经明确知道事件含义，可以确定性映射成对应高级 JSON 卡片（见 [[5.记忆卡片与持久化模型]]）。

## 检索记录（RetrievalRecord）

检索链路目前只留下最终证据包，无法还原一次检索最初返回过哪些候选、各自排名如何、最终选中了哪些。为了后续能够区分「Retriever 没找到」和「证据装配没选」，检索运行时在每次检索结束时保留一份轻量检索记录（RetrievalRecord）：

```python
class RetrievalRecord:
    retrieval_id: str              # 本次检索记录身份

    task_id: str                   # 所属任务
    run_id: str                    # 所属 Run：任务的一次连续执行阶段，见第一章
    agent_id: str                  # 触发检索的调用者，如 supervisor / workout_agent

    query_ref: str                 # 检索查询引用，敏感原文可脱敏或只存哈希
    source_scope: list[str]        # 检索范围：用户画像 / 用户记忆 / 业务事实 / 领域知识
    retrieval_config_version: str  # 本次检索使用的配置版本

    retrieved_items: list[dict]    # 候选召回结果（第一阶段写入）
        # source_id               # 来源标识
        # source_version          # 来源版本 / 哈希，复现当时的资料版本
        # rank                    # 候选排名
        # score                   # 候选分数

    selected_evidence_ids: list[str]  # 最终进入证据包的证据身份（第二阶段回填）
    evidence_bundle_id: str           # 关联的证据包身份（第二阶段回填）

    status: str                       # retrieved（候选已记）→ finalized（装配完成）
```

记录分两个阶段补齐生命周期：协调器完成四路检索后立即创建记录并写入 retrieved_items；证据装配器生成证据与证据包之后，回填 selected_evidence_ids 与 evidence_bundle_id——`evidence_id` 在装配之后才存在，一次性写入在时间上不成立。仍是同一条记录，不建第二套日志（代码级时序见 [[11.代码级逻辑：从用户事实到 EvidenceBundle#读取链 ④：证据包快照与两阶段检索记录]]）。

检索记录属于检索运行时，只保存候选、排序、选中关系和引用，不复制证据正文；Query 原文不强制永久保存，可以保存脱敏内容或哈希。它补全了下面的链路：

```text
检索
    ↓
检索记录（候选召回）
    ↓
证据装配
    ↓
证据包（见 [[9.证据装配与失败语义]]）
    ↓
上下文装配器（见 [[3.上下文装配器与 ContextPolicy]]）
```

这样后续评估可以分别定位：资料没有被 Retriever 找到、已经召回但证据装配没有选中、已经进入证据包但上下文装配器没有放入本轮上下文，以及 Agent 已经看到证据但仍然决策错误。
## 边界问答

**1. Q：** 为什么不引入独立的向量搜索服务？

**A：** 当前使用 Postgres + pgvector 已经能满足检索需求，额外引入独立搜索服务会带来部署与同步成本。记忆检索在现有体系上继续演化，而不是新建一套。

**2. Q：** 为什么已经有语义向量检索还要词法检索？

**A：** 用户名词、器械、动作名称这类精确关键词，向量可能不稳定，词法检索负责补足精确匹配，保证这类词不会因为向量语义偏差而漏掉。

**3. Q：** 为什么领域知识优先做结构化检索，而不是先切块做向量召回？

**A：** 健身动作知识已有较强结构化属性（肌群、动作模式、器械、标签），先用结构化条件缩小候选集合更准确、成本更低。只有当自由文本知识变多、固定字段表达不了时，才叠加向量检索形成混合检索。

**4. Q：** 为什么业务数据不复制一份到向量库？

**A：** 业务事实由业务数据库 / 业务服务管理，需要最新值直接查询服务即可。复制一份会引入两份数据的一致性问题。只有业务数据在形成长期个性化意义时才转成记忆证据，且保留对原始记录的引用。

**5. Q：** 为什么普通任务读取路径是画像 → 语义记忆，而不是先查情节？

**A：** 大多数个性化任务只需要当前高价值状态（画像）和当前认知（语义记忆）。只有需要解释来源、处理冲突或语义证据不足时才下钻情节，所以低层情节不必每次都进大模型上下文。
