# 代码级逻辑：从用户事实到 EvidenceBundle

本篇回答一个总问题：用户说出的同一句话，如何既支撑当前任务立即执行，又沉淀为跨任务长期可用的事实。场景沿用 Hero Scenario：用户过去习惯早晨训练，换工作后说「我还是喜欢早上，但是新工作以后工作日只能晚上练」。这句话进来以后，系统同时做两件不同的事——当前任务立刻把它作为最新用户输入用于本轮规划；记忆管道在后台把它保存成跨任务事实。几天后开启新的修改训练计划任务（第二章的 task_7001），系统仍然通过证据包知道工作日晚间才是可训练时间。写入链管前者的沉淀，读取链管后者的取用。

当前任务使用最新用户输入，不等于长期记忆已经形成：记忆抽取、语义巩固、画像投影都是后台异步过程，当前任务绝不依赖它们完成。第三章解决「这条信息以后如何跨 Task 保存和读取」；第二章（已冻结）解决「当前这轮模型究竟看到哪些已经存在的信息」。本篇把两条链各自写到可以直接翻译成代码的程度。

## 五种身份：从一句话到一条证据

写入链与读取链经过五种身份，任何两种都不能混：

```text
Current User Input ≠ Episode Memory ≠ Semantic Memory ≠ User Profile ≠ Evidence
```

**最新用户输入**是用户当前这轮刚说的话（「工作日以后只能晚上训练」），当前任务立即使用，不等待记忆管道。**情节记忆**是某个时间和背景下真实发生过的一次经历或陈述（E21：2026-09-04，用户因新工作安排明确表示工作日只能晚上训练），属于历史层，只追加。**语义记忆**是根据一个或多个情节当前能够支持的长期判断（S31：`training.availability.workday_training_time = evening`，status=current），属于认知层，版本化。**用户画像**是当前最常被读取的高价值用户状态视图（`training_availability.workday_time = evening`），可更新，不是历史事实库。**证据**是为某个具体任务整理出来、交给下游模型使用的有来源主张（EV712：claim「用户当前工作日只能安排晚间训练」，source = semantic S31），不是新的长期记忆，是当前任务对长期事实的一次读取结果。

三层数据语义（只追加 / 版本化 / 可变）的定义见 [[4.长期记忆语义模型]] 与 [[7.语义巩固与用户画像#三种更新语义]]。

## 写入链 ①：会话事件进入记忆事件缓冲

用户消息照常进入会话与任务（第一章的 ConversationService），与此同时记忆事件记录器把事件写入长期记忆管道自己的输入缓冲：

```text
ConversationService.handle_message()
    ├── 用户消息正常进入 Task / Conversation        # 主路径不受任何影响
    └── MemoryEventRecorder.record(event)            # 旁路：写入持久记忆事件缓冲
```

记忆事件缓冲是记忆管道自己的输入记录，只存事件本身，不复制整个 LangGraph 状态——图状态属于会话线程的控制状态（见 [[3.模块定位与职责边界]]）。事件结构：

```python
class MemoryEvent:
    event_id: str                    # 事件唯一标识
    user_id: str                     # 归属用户：记忆的主作用域
    conversation_id: str | None      # 来源会话线程
    task_id: str | None              # 所属任务（闲聊消息可为空）
    run_id: str | None               # 所属 Run（任务内事件）

    source_agent: str                # 来源智能体，如 workout / supervisor
    source_message_id: str           # 来源消息，追溯用

    content: str                     # 事件文本

    occurred_at: datetime            # 事件发生时间：事实属于什么时候
    recorded_at: datetime            # 系统记录时间：什么时候拿到这条事实
    status: str                      # pending / flushed / invalid
```

`occurred_at` 与 `recorded_at` 必须分开。用户今天说「去年一直晨练」，`recorded_at` 是今天，事实时间属于去年；混用一个时间戳，后续语义巩固就无法判断「偏好晨练」是过去状态还是当前状态（卡片层的同一分工见 [[5.记忆卡片与持久化模型#高级 JSON 卡片：统一的应用层表示]]）。

当前任务与记忆缓冲完全解耦。Hero 这句话进入系统时，训练任务立即把它作为 latest user input 用于本轮规划；与此同时缓冲里记下原始事件 E_RAW_21。即使此刻抽取器、巩固器、画像投影全部还没运行，当前任务依然正确理解工作日只能晚上训练。写成约束：

```text
Memory 写入延迟，不能导致当前 Task 忽略最新用户输入
```

这是第三章与第二章的重要边界——第二章的装配链里，最新输入是必需块，从不等待记忆管道。

## 写入链 ②：批次抽取与情节候选

普通记忆形成走后台批次：事件缓冲达到刷新条件（事件量、用户空闲、任务正常结束）后，抽取器以批次为输入生成情节候选。抽取器只回答一个问题：这段事件中有没有值得跨任务保存的长期经历？它不同时更新画像、覆盖旧语义、删除历史、判断最终当前状态或生成证据包——那些分别是巩固器、投影器和读取链的职责。

候选结构：

```python
class EpisodeCandidate:
    candidate_id: str                # 候选身份
    user_id: str                     # 归属用户

    subject_id: str                  # 事实主体：这条信息说的是谁
    relationship_to_user: str        # 主体与用户的关系，self 才能进入用户画像

    state_key: str                   # 目标状态键：从注册表中选择，不允许自由创造
    value: object                    # 事实值，如 morning / evening / reported

    event_start: datetime | None     # 事实发生起点（对应 occurred_at 语义）
    event_end: datetime | None       # 事实结束点，可为空

    confidence: str                  # 置信度：low / medium / high
    source_event_ids: list[str]      # 支撑本候选的原始事件

    simple_note: str                 # 简洁备注：最短可读描述
    enhanced_note: str               # 增强备注：携带背景，服务检索与阅读
```

候选只是候选，写入正式情节前过五项校验：结构校验（字段完整、时间合法）、用户归属校验（user_id 正确）、主体归属校验（「我朋友对花生过敏」不能写进用户本人的画像，主体必须是 self 或明确关联）、state_key 校验（必须在注册表中）、幂等检查（见下一节）。

`state_key` 的稳定性靠一张简单的注册表维护，不建 Schema 框架：

```text
MemorySchemaRegistry（配置，非新组件）
training.preference.training_time            用户真正偏好什么时候训练
training.availability.workday_training_time  当前工作日实际什么时候可以训练
fitness.condition.knee_discomfort
fitness.goal.primary
diet.restriction.allergy
interaction.preference.response_style
```

抽取器从已定义的键中选择当前事件属于哪个；无法映射的输出 unknown / unsupported，进入人工可解释的扩展流程或暂不形成当前语义。注册表要挡住的问题很具体：不约束的话，模型会为同一个维度生成 `training_time`、`workout_time`、`preferred_workout_hour`、`exercise_time_preference` 四个实际同义的键，后续围绕 state_key 的巩固、dirty 标记、画像映射全部失效。

Hero 的两个事实必须落在两个键上：偏好晨练是 `training.preference.training_time`，工作日只能晚练是 `training.availability.workday_training_time`。「我更喜欢早上」与「因为上班只能晚上」语义再相关，也不写进同一个 state_key；`SUPERSEDE` 只允许发生在同一 state_key 的状态版本之间，绝不因为两句话相似就互相覆盖（这层区分的语义依据见 [[7.语义巩固与用户画像#语义巩固]]）。

## 写入链 ③：append-first 写入情节

校验通过后写入历史层：

```text
EpisodeCandidate
    ↓ EpisodeRepository.append()
E21（正式情节，只追加）
```

情节只追加。2026-03 的 E10 描述「用户过去习惯早晨训练」，2026-09 的 E21 描述「新工作后工作日只能晚上练」，两条都保留——E10 不因 E21 出现被修改，旧情节即使不再代表当前状态也有历史价值（见 [[4.长期记忆语义模型#历史层：记录发生过什么]]）。只有抽取错误、用户删除请求或数据治理要求才把情节置为 invalid / deleted。

批次重试的幂等键沿用既有设计：`source_event_id + extraction_batch_id + candidate_index`，目标只有一个——同一批抽取重试不会生成两条完全相同的情节。向量相似度不参与覆盖决策：相似只说明可能相关，不说明同一事实，更不说明该覆盖（见 [[8.证据检索#相似不再等于同一事实]]）。

## 写入链 ④：dirty 标记与语义巩固

情节写入后只把对应 state_key 标记为 dirty，不重扫用户全部记忆：

```text
E21 写入
    ↓ state_key = training.availability.workday_training_time
    ↓ mark_dirty()
后台 Consolidator 只处理 dirty 的键
```

一次巩固的输入：

```python
class SemanticConsolidationRequest:
    user_id: str                             # 目标用户
    state_key: str                           # 本次巩固的键
    current_semantic_id: str | None          # 当前版本：该键还没有稳定认知时为空
    pending_episode_ids: list[str]           # 尚未被巩固消费的新情节
    supporting_business_fact_refs: list[str] # 必要时的业务事实佐证（如训练记录趋势）
```

巩固器读取当前语义 + 未处理新情节 + 少量必要历史情节 + 必要时的业务事实，不读取全部用户历史。输出仍然只有四种状态，各自的代码级处理：

```text
NO_CHANGE       新情节只是再次支持现有认知
                → 不创建新语义；把本批情节标记为已被本轮巩固消费

NEW_SEMANTIC    该 state_key 过去没有稳定认知
                → 创建新语义（S31），status = current

SUPERSEDE       同一 state_key 的当前认知真正变化
                → 旧版本 → historical，新版本 → current（原子切换见下文）

UNCERTAIN       证据冲突或不足
                → 不修改当前语义，不修改画像，情节保留，
                  未来出现更多证据时重新巩固
```

UNCERTAIN 不强迫系统给出答案——「系统永远有当前值」不是本层的正确性标准，证据不足就让它悬着。

SUPERSEDE 是一次原子状态变化：

```text
读取当前 S30（availability = morning，current）
    ↓ Consolidator 判定 SUPERSEDE
    ↓ 事务开始
    ↓ 条件更新：仅当 S30 仍为 current（版本未变，0 行即冲突）
    ↓ S30 → historical，valid_to = 新版本 valid_from
    ↓ INSERT S31（current，valid_from）
    ↓ INSERT supersedes 关系（S31 → S30，记忆关系表）
    ↓ Profile Projection（S31 → 画像字段）
    ↓ 事务提交
```

由此有一个不变量：同一 `user_id + state_key`，正常情况下最多存在一个 current 语义。两个 Consolidator 同时基于 S30 巩固同一键时，只有一个能提交成功；另一个的条件更新落在 0 行上，发现当前版本已变，重新读取后再处理——不会出现同一键两个 current。当前规模只需要数据库事务加版本 / 当前状态检查，不引入分布式锁、消息队列或事件溯源。

## 写入链 ⑤：画像投影与窄热路径

语义成功变化后，画像投影器做确定性映射：

```text
S31（availability = evening）
    ↓ ProfileProjector（按 state_key → 画像字段的固定映射，程序而非模型重写）
profile.training_availability.workday_time = evening
```

画像字段保留溯源，不产生无来源的值：

```python
{
    "value": "evening",                    # 当前值
    "source_type": "semantic_projection",  # 来源：semantic_projection / user_stated
    "source_memory_id": "S31",             # 来源语义版本
    "updated_at": "2026-09-04",            # 更新时间
}
```

投影程序化、字段带来源的约束见 [[7.语义巩固与用户画像#画像投影：尽量确定性]]。

记忆形成默认后台批次，但三类事实允许走窄热路径：安全事实（「我对花生严重过敏」）、用户明确要求系统记住的信息、预定义且当前请求之后立即需要生效的关键画像约束。热路径 = 立即抽取 + 立即写情节 + 立即投影画像（source_type = user_stated），语义巩固仍后台补完。它不构成第二条记忆管线——走的还是同一条写入链，只是跳过等待。

热路径的适用边界要写死：**Hero 的「工作日只能晚上训练」即使被识别为高价值约束，当前任务首先仍然通过 latest user input 知道它**。热路径的意义是——当前任务结束几小时后用户开启另一个独立任务，新任务能尽快通过长期状态读到该约束，而不是当前任务正确执行的前提。把热路径设计成当前任务的依赖，等于把异步管线偷偷塞回同步关键路径。

## 写入链走查：偏好与约束分开落库

```text
2026-03
E10：用户最近习惯早晨训练
    ↓ 后台巩固
S10：training.preference.training_time = morning（current）
    ↓ 投影
profile.training_preference.time = morning

2026-09-04
用户：「我还是喜欢早上，但是新工作以后工作日只能晚练。」
    ├── 当前任务：latest user input 立即可用（第二章装配链，必需块）
    └── 记忆管道：
        MemoryEvent E_RAW_21
            ↓ 批次抽取（同批两个候选，五项校验）
        E21：training.preference.training_time = morning
        E22：training.availability.workday_training_time = evening
            ↓ mark_dirty × 2
        巩固 preference：新情节再次支持 morning → NO_CHANGE（S10 保持 current）
        巩固 availability：首次形成稳定认知 → NEW_SEMANTIC → S31（current）
            ↓ 投影
        profile.training_preference.time = morning          # 不变
        profile.training_availability.workday_time = evening # 新增
```

最终画像是两个字段：偏好晨练、工作日晚间可用。不能形成 `training_preference = evening`——那一行会同时丢掉「用户真实偏好」和「为什么当前只能晚练」两个信息，正是旧版「相似即覆盖」的错误（见 [[找工作啊啊啊啊/项目梳理/个人健康管理agent/3.把记忆与知识汇成证据/10.困难以及应对办法]]）。

## 读取链 ①：EvidenceRequest

第二章已冻结，它只认识 `EvidenceReader.load(EB500)`；本篇解释 EB500 怎么产生。读取的入口是结构化请求：

```python
class EvidenceRequest:
    task_id: str                        # 哪个任务需要证据
    run_id: str                         # 哪一段执行
    agent_id: str                       # 谁在要：workout_agent / supervisor
    stage: str                          # 当前阶段：决定检索范围与必需性

    memory_needs: list[MemoryNeed]          # 记忆需要：优先结构化状态键
    business_needs: list[BusinessNeed]      # 业务事实需要：如 active_workout_plan
    knowledge_needs: list[KnowledgeNeed]    # 领域知识需要：结构化条件

    include_episode_history: bool = False   # 是否下钻历史情节（解释变化类问题才开）
```

`MemoryNeed` 优先表达为 state_keys 而不是自然语言查询：

```python
class MemoryNeed:
    state_keys: list[str]       # 优先：training.availability.workday_training_time 等
    query_text: str | None      # 兜底：自然语言查询，解释历史类问题使用
    required: bool              # 缺失时本轮任务不能假装继续
```

当前智能体必须明确告诉检索协调器这一次决策需要哪类证据，不默认检索用户全部记忆。训练智能体重建计划时需要的是「当前训练时间约束、当前目标、膝盖限制」，直接写成三个 state_keys 精确查询；只有用户问「为什么我现在的训练习惯和以前不一样」这类需要解释历史的问题，才打开 `include_episode_history` 走向量 / 词法补召回。

必需与可选在请求里声明：重建计划时当前正式计划、用户时间约束是 required，补充训练历史解释、额外领域文章是 optional。这让系统知道哪些证据没找到时，本轮任务不能假装继续（失败语义见读取链 ④）。

请求进入协调器前先做与第二章同思想的一致性校验：task_id 存在、run_id 属于当前任务且仍为当前 Run、agent_id 是当前合法调用者、stage 与运行状态一致。校验不通过不检索——不允许调用者伪造 stage 拿到本阶段本不该访问的信息。

`user_id` 不由智能体自己填。EvidenceRequest 只携带 task_id / run_id / agent_id，检索协调器从任务运行时派生「当前任务属于哪个用户」，随后所有画像、记忆、业务事实查询都绑定这个 user_id。这不是第四章的权限系统，是第三章最基本的数据归属边界——没有它，一个智能体填上别人的 user_id 就能读到另一个用户的记忆。

## 读取链 ②：四路检索与候选

```text
EvidenceRequest
    ↓ 一致性校验 + user_id 派生
RetrievalCoordinator
    ├── ProfileReader         画像：预定义高价值字段，最快路径
    ├── MemoryRetriever       记忆：结构化过滤 + 向量 + 词法三路（Postgres + pgvector，不引入新检索服务）
    ├── BusinessFactReader    业务事实：直接调业务服务
    └── KnowledgeRetriever    领域知识：结构化条件优先
    ↓
RetrievedCandidate[]
```

每一路只返回自己的数据候选，没有哪一路直接拼 Prompt。四路的分工：

**画像**最快：预定义字段直接读。**记忆**按三级下钻：普通个性化请求优先画像 + 当前语义；只有需要解释变化原因、当前语义不够、存在冲突或用户明确问过去时，才下钻情节记忆（见 [[8.证据检索#用户记忆检索：按需而不是固定召回]]）。**业务事实**直接读业务服务——当前正式训练计划必须由 `WorkoutService.get_active_plan()` 返回带版本引用的 plan_88@v2，而不是去向量库搜「我的当前训练计划是什么」；业务事实的读取结果必须带稳定版本，证据才能标明当时依据的是哪个正式版本（业务事实归业务库见 [[8.证据检索#业务事实归业务库]]）。**领域知识**结构化优先：动作模式、目标肌群、器械、排除标签、用户限制先过滤，自由文本知识真正增长后再叠加向量形成混合检索；当前不引入 GraphRAG、Agentic RAG、多跳框架或新向量数据库，Postgres + pgvector 边界不变。

候选的统一中间形态：

```python
class RetrievedCandidate:
    source_type: str             # 来源类型：profile / semantic_memory / business_db / knowledge
    source_id: str               # 来源标识，如 S31 / plan_88@v2
    source_version: str | None   # 来源版本

    claim_key: str | None        # 能映射到 state_key 时填充，服务后续去重与冲突识别
    value: object | None         # 结构化值

    text: str                    # 自然语言正文（备注 / 摘要）
    temporal_status: str | None  # 当前 / 历史 / 未知
    confidence: str | None       # 置信度

    provenance: list[str]        # 溯源引用（情节 / 记录）
    retrieval_score: float | None  # 检索得分，仅排序参考
```

候选不是证据，它只是「检索器找到了什么」。区分候选与最终证据，后面才能分开回答「没找到」和「找到了但装配没选」。

## 读取链 ③：证据装配

证据装配器（EvidenceAssembler）的职责是有限的：

```text
RetrievedCandidate[]
    ↓ 统一 Evidence 格式（claim_key + value + claim 文本）
    ↓ 按 claim_key 去除明显重复
    ↓ 保留 source / version / provenance
    ↓ 标记 temporal_status
    ↓ 识别明显冲突 → EvidenceConflict
    ↓
EvidenceBundle
```

它不重新做记忆检索、不做 RAG、不决定 Prompt、不推进任务、不修改记忆、不修改业务数据库。

证据增加结构化主张身份——只有自然语言 claim 时，去重与冲突识别都不稳定：

```python
class Evidence:
    evidence_id: str            # 证据身份，下游按它引用
    claim_key: str | None       # 主张键：能映射 state_key 时填充
    value: object | None        # 主张值：evening / morning / plan_88@v2

    source_type: str            # 来源类型
    source_id: str              # 来源标识
    source_version: str | None  # 来源版本

    claim: str                  # 主张文本：给模型和人阅读
    temporal_status: str | None # 当前 / 历史 / 未知
    confidence: str | None      # 置信度
    provenance: list[str]       # 溯源
```

`claim` 给模型和人读，`claim_key + value` 给运行时做去重与冲突识别，两者分工。另有一条硬约束：**一条证据的 claim 必须由它自己的 source 与 provenance 真正支持**——「用户仍然偏好晨练」由 S10 支持，「工作日只能安排晚间训练」由 S31 支持，两者合起来才能推出的「偏好晨练但现实只能晚练」不能只挂在 S10 名下。确实需要组合结论时，把它显式做成派生证据，provenance 同时指向 S10 与 S31，而不是把多来源结论伪装成单来源事实。

去重按 claim_key：同一稳定事实已从画像与语义两路召回（profile 投影与 S31 是同一事实的两种视图）时，装配保留来源更完整的一条或合并来源，不重复塞两条正文。

冲突不靠「后返回的覆盖前面的」：

```text
EV1：claim_key = training.availability.workday_training_time，value = morning
EV2：claim_key = training.availability.workday_training_time，value = evening
两条款都是 current
    ↓
EvidenceConflict(claim_key=…, evidence_ids=[EV1, EV2], status="unresolved")
```

装配器发现同一 claim_key、当前状态、不同 value 时生成未解决冲突，不静默让 EV2 覆盖 EV1。程序能判定的来源优先级保留：current 与 historical 同时出现时明确优先 current；但两个真正互相冲突的 current，不按最后更新时间或向量分数裁决真相——标记冲突，需要进一步判断时把冲突一起交给下游。

有一处跨章修正同时落在这里：证据来源最终保持四类——画像、记忆、业务事实、领域知识。上游智能体产物（Artifact）不再是第五类证据来源：第五章的 Workout Artifact → Diet 属于任务 / 智能体之间的结构化产物移交，第二章已有独立的产物读取路径（Artifact → ContextBlock），证据包不把它复制成长期证据来源。如果某个产物能帮助生成检索条件，它作为 EvidenceRequest 的输入引用参与，仅此而已。[[9.证据装配与失败语义]] 的结构已同步修正。

## 读取链 ④：证据包快照与两阶段检索记录

证据包是按任务与 Run 生成的快照，结构上必须让第二章的三项读取校验（存在、归属、有效）有据可查：

```python
class EvidenceBundle:
    bundle_id: str                  # 证据包身份，如 EB500
    user_id: str                    # 归属用户：第二章校验「属于当前用户」的依据
    task_id: str                    # 归属任务
    run_id: str                     # 归属 Run
    retrieval_id: str               # 由哪次检索产生（指向 RetrievalRecord）

    created_at: datetime            # 快照时间：过旧即无效的判断依据
    status: str                     # COMPLETE / PARTIAL / FAILED（完整性，见下文）

    profile: list[ProfileEvidence]     # 画像证据
    memories: list[MemoryEvidence]     # 记忆证据
    business_facts: list[BusinessEvidence]  # 业务事实证据
    knowledge: list[KnowledgeEvidence]      # 领域知识证据

    conflicts: list[EvidenceConflict]   # 未解决冲突
    missing_sources: list[str]          # 缺失的来源（含 required 缺失明细）
```

完整性三态：COMPLETE 表示所有必需证据都存在；PARTIAL 表示必需齐全、可选有缺失；FAILED 表示至少一个必需证据缺失。第二章的对应消费：COMPLETE 与可接受的 PARTIAL 可以加载进装配链，FAILED 不进入正常模型调用——与第二章「声明为必需的证据缺失则本轮装配失败」的既有失败语义闭环（具体任务的降级治理归第六章）。

失败语义的总口径修正为：记忆形成（后台抽取、语义巩固、普通画像更新）不属于普通用户请求必须同步完成的关键路径；但证据检索是否是当前任务的必要前置，由当前任务的必需性声明决定。可选记忆证据失败 → 返回 PARTIAL 包继续；必需业务事实失败 → 证据装配失败；必需知识证据失败 → 明确返回缺失，不让模型把无法确认的内容伪装成检索结果。什么检索失败都让模型接着猜，是被禁止的。

EB500 是一次检索结果快照，绑定 task_7001 / R1。任务经过人工介入从 R1 恢复为 R2、而新决策可能依赖已经变化的业务事实时，默认重新检索生成新的证据包（EB501），第一版不建跨 Run 的证据缓存；稳定的记忆 / 知识检索底座未来可以加缓存，证据包本身保持具体一次 Task / Run 的快照语义——第二章的有效性检查因此最容易解释。

检索记录补成两阶段。旧结构同时要求记录 retrieved_items 和 selected_evidence_ids，但 evidence_id 在装配器处理之后才存在，一次性写入在时间上不成立：

```python
class RetrievalRecord:
    retrieval_id: str                  # 本次检索记录身份

    task_id: str                       # 所属任务
    run_id: str                        # 所属 Run
    agent_id: str                      # 触发检索的调用者

    query_ref: str                     # 检索查询引用（state_keys 或脱敏 query）
    source_scope: list[str]            # 检索范围：画像 / 记忆 / 业务事实 / 领域知识
    retrieval_config_version: str      # 配置版本

    retrieved_items: list[dict]        # 第一阶段：四路候选（source_id / version / rank / score）

    selected_evidence_ids: list[str]   # 第二阶段回填：进入证据包的 evidence_id
    evidence_bundle_id: str | None     # 第二阶段回填

    status: str                        # retrieved → finalized
```

第一阶段：协调器完成四路检索后立即创建记录、写入 retrieved_items（status = retrieved）。第二阶段：装配器生成证据与证据包后回填 selected_evidence_ids 与 bundle_id（status = finalized）。不建第二套日志，同一条记录补齐生命周期。

检索记录与第二章的上下文清单职责不同，不能合并：

```text
RetrievalRecord   检索器找到了什么、排名如何、装配器选中了哪些
ContextManifest  证据包交给第二章后，模型本轮最终实际准备看到哪些证据
```

完整数据链：检索器返回候选 → RetrievalRecord 记录 → 装配器选中 → selected_evidence_ids → 第二章再筛 → ContextManifest.evidence_refs。第七章沿这条链可以分别定位「没召回」「召回了没选」「进了证据包但没装进上下文」（消费方式见 [[5.Retrieval、Tool 与 DomainTask 接入执行轨迹]]）。

## 读取链走查：task_7001 的 EB500

写入链走查几天后，用户说「第二个动作换掉，顺便按我现在的时间情况调整一下」（第二章的 task_7001，修改正式计划 plan_88@v2）。训练智能体在进入修改流程前发出证据请求：

```text
EvidenceRequest
    task_id = task_7001，run_id = R1，agent_id = workout_agent，stage = revise_plan
    memory_needs:
        required  training.availability.workday_training_time
        required  fitness.goal.primary
        optional  训练历史解释（include_episode_history = false，本轮不需要）
    business_needs:
        required  active_workout_plan
    knowledge_needs:
        optional  满足当前限制的动作与负荷原则
    ↓
一致性校验通过；user_id 从任务运行时派生（智能体没有填写权）
    ↓
ProfileReader      → training_availability.workday_time = evening（候选：画像投影）
MemoryRetriever    → S10（偏好晨练，current）、S31（工作日晚间，current）
BusinessFactReader → WorkoutService.get_active_plan() → plan_88@v2（带版本）
KnowledgeRetriever → K21（晚间训练安排原则）、K25（肩部受限动作选择）
    ↓
RetrievedCandidate[]（六条）+ RetrievalRecord RR 第一阶段（六条候选全部入 retrieved_items）
    ↓

    画像候选与 S31 候选同 claim_key + 同 value（availability = evening）
        ↓ 去重：保留来源更完整的 S31（带版本与 provenance），不重复保留画像正文
    其余候选标准化、无冲突、标记当前性
    ↓
EB500（status = COMPLETE，绑定 task_7001 / R1）+ RR 第二阶段回填
```

EB500 内容：

```text
profile:        （空——画像候选与 ev_712 是同一主张，去重后并入语义一条）
memories:       ev_711  claim_key = training.preference.training_time，value = morning
                        claim「用户仍然偏好晨练」（source: S10）
                ev_712  claim_key = training.availability.workday_training_time，value = evening
                        claim「用户当前工作日只能安排晚间训练」（source: S31，provenance: E22）

```

每条证据的 claim 都不超出自己来源的证明范围：ev_711 只主张偏好（S10 只含偏好），ev_712 只主张当前可训练时间（S31 及其情节 E22）；「偏好晨练但现实只能晚练」这类组合结论如果需要，必须显式作为派生证据并让 provenance 同时指向 S10 与 S31。

这次走查同时是两阶段检索记录价值的现场：RR 的 retrieved_items 里，画像与语义两路都召回了 availability = evening（同一事实的两种视图）；装配去重后 selected_evidence_ids 只包含 ev_712。第七章未来据此能区分「两路都找到了」与「装配器合并成一条」——没有候选与最终证据的分层，这个取舍就会消失在最终结果里。

随后交接第二章（已冻结，此处只列衔接）：`evidence_bundle_id = EB500` 进入装配请求 → EvidenceReader 三项读取校验（存在 / 归属 task_7001 / 仍有效）→ 装配器按当前策略选取进入本轮的证据子集（第二章走查中进入本轮的正是 ev_712）→ ContextManifest.evidence_refs 登记。第三章到这里结束，不拼 Prompt。

## 三条异常路径

**异常一：记忆抽取失败。**原始 MemoryEvent 已持久化，抽取器失败。结果：事件保持 pending / retryable，后续批次重试；不产生假情节；当前用户请求不因后台抽取失败而回滚或报错——写入链在主路径之外，失败不反向传导。

**异常二：两个巩固器同时更新同一 state_key。**两个后台工作进程都基于 S30（current）判定 SUPERSEDE。只有一个的条件更新能改到行并提交事务；另一个落在 0 行上，发现当前语义版本已变，重新读取后重新巩固。任何时刻同一 `user_id + state_key` 不会出现两个 current。

**异常三：必需证据缺失。**当前正式训练计划声明为 required，WorkoutService 查询失败。第三章返回 `EvidenceBundle.status = FAILED`，missing_sources 列出 active_workout_plan；不能空着当前计划继续让模型自己猜。下游行为由第二章既有语义接管：声明为必需的证据缺失，本轮上下文装配不允许静默继续。

## 未下沉的部分

领域知识的向量混合检索（自由文本知识增长后才需要）、情节时间补全的推断逻辑、巩固器内部对证据强度的具体权衡（当前只有排序原则）、多用户隔离与记忆治理（导出 / 删除）的运营流程，本轮停留在概念级。Postgres + pgvector、结构化过滤 + 词法 + 必要时向量的技术边界不变，不引入 GraphRAG、知识图谱、Agentic RAG、全局记忆服务、消息队列、独立向量数据库、自动遗忘评分、时间衰减算法或复杂重排器。

## 边界问答

**1. Q：** 用户一句话进入系统以后，当前任务为什么不用等记忆管道？

**A：** 当前任务把这句话作为 latest user input 立即使用，它是第二章装配链的必需块；记忆抽取、巩固、投影全部是后台异步过程。写入延迟不能导致当前任务忽略最新输入——「当前任务用了这句话」与「长期记忆已形成」是两件事。

**2. Q：** 偏好晨练和工作日只能晚练为什么不是一个 state_key？

**A：** 一个是 `training.preference.training_time`（用户真正偏好），一个是 `training.availability.workday_training_time`（现实约束下的可用时间）。SUPERSEDE 只发生在同一 state_key 的版本之间；混成一个键，「晚练」就会覆盖「偏好晨练」，偏好与约束两个信息同时丢失。

**3. Q：** state_key 谁生成，为什么不能让模型自由创造？

**A：** 抽取器从 MemorySchemaRegistry 的已定义键中选择，映射不了的标 unknown 走扩展流程。键不稳定，围绕它的 dirty 标记、巩固、画像映射全部失效——同一个维度被写成四个同义键就是反例。

**4. Q：** 为什么一个 state_key 只能有一个 current 语义？

**A：** SUPERSEDE 是条件更新的原子事务：旧版本转 historical、新版本 current、supersedes 关系、画像投影一次提交。并发的第二个巩固器条件更新落空后重读重试。出现两个 current，「当前值」就不再可判定。

**5. Q：** 用户画像为什么不等于语义记忆？

**A：** 画像是读取层：预定义高价值字段的当前快速视图，可变、带来源；语义记忆是认知层：版本化的派生判断。画像只是语义的投影消费端，还要保留 source_type 与 source_memory_id，否则「用户说的」和「系统推导的」无法区分。

**6. Q：** user_id 为什么不能由智能体自己传？

**A：** EvidenceRequest 只带 task_id / run_id / agent_id，协调器从任务运行时派生 user_id 并绑定所有查询。这不是权限系统，是数据归属边界——否则一个智能体填上别人的 ID 就能读另一个用户的记忆。

**7. Q：** 业务事实为什么不进向量记忆库？

**A：** 业务事实归业务库，需要最新值直接查服务并带稳定版本（plan_88@v2）；复制进向量库会引入两份数据的一致性问题，「当前计划是什么」这种问题也不该用语义相似度回答。

**8. Q：** RetrievedCandidate 和 Evidence 有什么区别？

**A：** 候选是「检索器找到了什么」，证据是「装配器标准化并选中、可交给下游的主张」。区分两者加两阶段检索记录，评估才能分开「没召回」与「召回了没选」。

**9. Q：** 为什么 Artifact 不是第三章第五类证据来源？

**A：** Artifact 是任务 / 智能体间的结构化产物移交，归第五章协议；第二章已有独立的产物读取路径。证据包只管四类长期信息来源；产物可以帮助生成检索条件，但不复制成长期证据。

**10. Q：** EvidenceBundle 为什么属于具体 Task / Run？

**A：** 它是一次检索的结果快照，带 user_id / task_id / run_id / created_at / status，第二章的存在、归属、有效三项校验全部有据可查。跨 Run 默认重新检索生成新包，不做跨 Run 证据缓存。

**11. Q：** 必需证据缺失怎么办？

**A：** 证据包 status = FAILED，missing_sources 列出缺口；第二章既有语义接管——声明为必需的证据缺失，本轮上下文装配不允许静默继续。可选证据缺失只降级为 PARTIAL。

**12. Q：** RetrievalRecord 和 ContextManifest 有什么区别？

**A：** 检索记录回答「检索器找到什么、装配器选中什么」；上下文清单回答「证据包交给第二章后，模型本轮实际准备看到什么」。一个在第三章检索侧，一个在第二章装配侧，各自记录不同环节的取舍，合并了就无法定位检索、装配、上下文三个环节各自的责任。
