# 记忆卡片与持久化模型

## 高级 JSON 卡片：统一的应用层表示

情节记忆和语义记忆统一使用高级 JSON 卡片作为应用层的统一表示。

它以普通 JSON 卡片的：

```text
类别
→ 子类
→ 键 / 值
```

为基础，再增加背景、主体身份、主体与用户的关系、时间、原始来源以及记忆之间的派生关系。这些信息的主要作用是消除长期记忆脱离原对话以后产生的歧义。

例如一句简单的「最近膝盖有点不舒服」，如果只作为备注保存，未来无法确定它描述的是用户本人还是用户在讨论朋友，也无法确定这是当前状态还是过去的经历。高级 JSON 卡片会显式记录下面这样的结构（以带注释的 Python 结构表示，实际以 JSON 持久化）：

```python
{
    "memory_type": "episodic",            # 记忆类型：episodic 或 semantic
    "classification": {
        "category": "fitness",            # 领域类别，如 fitness / diet / interaction
        "subcategory": "physical_condition",  # 子类，如伤病、过敏、偏好
        "key": "knee_discomfort",         # 事实键，标识这是一个什么事实
        "value": "reported",              # 事实值，如 reported / morning / evening
    },
    "subject": {
        "entity_id": "user_123",          # 主体唯一标识
        "entity_type": "person",          # 主体类型，如 person
        "relationship_to_user": "self",   # 主体与当前用户的关系，self 表示是用户本人
    },
    "backstory": "用户在讨论近期深蹲训练后的恢复情况时提到右膝出现不适。",  # 背景，消除脱离对话后的歧义
    "temporal": {
        "event_start": "2026-08-20",      # 事件发生时间
        "recorded_at": "2026-08-25T20:30:00+08:00",  # 系统记录时间
        "precision": "approximate",       # 时间精度：approximate / exact / unknown
    },
    "provenance": {
        "source_type": "conversation",    # 来源类型，如 conversation / domain_signal
        "source_refs": ["message_881"],   # 来源引用，指向原始消息或事件
    },
}
```

其中 `event_start` 与 `recorded_at` 必须分离。用户今天说「去年一直晨练」，系统是在今天获得这条信息，但事件描述的是去年。只有区分事件时间与系统记录时间，后续语义巩固才能正确判断事实的时间关系。

## 两种文本表示

高级 JSON 卡片中同时保存简洁备注（simple_note）和增强备注（enhanced_note）两种文本表示，但它们不形成独立记忆库。

简洁备注是最短的人类可读描述，例如：

```text
用户当前主要在晚上训练。
```

它适合调试、界面展示或非常紧凑的证据输出。

增强备注会补充必要背景和语义，例如：

```text
用户当前主要选择晚间训练；这一变化发生在工作时间调整以后，并得到近期实际训练行为支持。
```

增强备注主要服务于向量嵌入、语义检索和最终大模型阅读。相比只对 `value = evening` 做向量嵌入，它携带主体和背景，检索歧义更小。

因此最终不是维护下面的四套记忆：

```text
简洁备注库
增强备注库
JSON 卡片库
高级 JSON 卡片库
```

而是维护一套高级 JSON 卡片，把结构化字段、简洁备注、增强备注作为它的三个组成部分：

```text
高级 JSON 卡片
    ├── 结构化字段
    ├── 简洁备注
    └── 增强备注
```

## 数据库列与扩展字段

画像则使用更轻量的类型化 JSON 卡片，因为它表达的是当前状态，不需要复制完整背景和历史证据。

数据库层也不会把完整高级 JSON 卡片无约束地塞进一个 JSONB（JSON 二进制列）。高频检索和状态判断字段作为普通 SQL 列存储：

```text
id                  # 记忆主键
user_id             # 归属用户，检索主作用域
memory_type         # episodic / semantic

category            # 领域类别
subcategory         # 子类
fact_key            # 事实键
state_key           # 状态键，语义模型见 [[7.语义巩固与用户画像#state_key：把演化状态锚定成键]]

subject_id          # 主体唯一标识
relationship_to_user  # 主体与用户的关系

event_start         # 事件发生时间
event_end           # 事件结束时间（可为空）
recorded_at         # 系统记录时间
valid_from          # 语义版本生效起点
valid_to            # 语义版本生效终点

status              # current / historical / invalid / deleted
safety_level        # normal / critical
confidence          # 置信度，如 low / medium / high

simple_note         # 简洁备注，最短可读描述
enhanced_note       # 增强备注，携带背景的语义文本

payload JSONB       # 类型特有或未来可能演化的字段
embedding           # 向量表示，用于语义检索
schema_version      # 卡片结构版本号
```

类型特有或未来可能演化的字段进入 `payload JSONB`。

## 记忆关系独立存储

记忆之间的关系单独使用记忆关系表保存，而不是全部藏在 JSON 中：

```text
memory_relations

from_memory_id    # 起点记忆
to_memory_id      # 指向记忆
relation_type     # 关系类型：derived_from / supersedes
```

第一版只需要支持：

```text
derived_from
supersedes
```

因此系统保留证据关系，但不建设完整知识图谱。`derived_from` 用于语义记忆追溯证据，`supersedes` 用于语义新版本替代旧版本（见 [[7.语义巩固与用户画像#语义巩固]]）。

## 边界问答

**1. Q：** 为什么要区分简洁备注和增强备注，而不是只存结构化字段？

**A：** 结构化字段适合精确过滤，但大模型阅读和向量检索需要自然语言文本。简洁备注服务调试和紧凑输出；增强备注携带主体与背景，语义检索歧义更小。两者是同一张卡片的两个组成部分，不是两套独立记忆库。

**2. Q：** 为什么不把完整高级 JSON 卡片直接塞进一个 JSONB 列？

**A：** 高频检索和状态判断字段需要走普通 SQL 列才能高效过滤（如 `user_id`、`state_key`、`valid_from`、`safety_level`）。类型特有或未来演化的字段才进 `payload JSONB`，这样既不丢失灵活性，也不牺牲检索性能。

**3. Q：** 为什么记忆关系单独建表，而不是藏在 JSON 里？

**A：** 关系（`derived_from`、`supersedes`）需要作为一等数据参与查询和状态判断，藏在 JSON 里难以索引和遍历。单独用记忆关系表保存，也能明确「只保留证据关系、不建设完整知识图谱」的边界。
