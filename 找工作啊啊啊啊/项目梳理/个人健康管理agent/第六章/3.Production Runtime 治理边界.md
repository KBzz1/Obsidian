# Production Runtime 治理边界

生产运行时治理（Production Runtime Governance）位于 Task Runtime、Agent Runtime、Tool Runtime 和后台任务执行机制之外，负责这些 Runtime 同时运行时对有限资源的约束与运行秩序。前面的章节已经分别定义了任务如何推进和恢复、Agent 如何执行、Tool 如何安全可靠调用，以及多 Agent 和异步任务如何协作；本章不重新设计这些 Runtime 的内部逻辑，只在它们之上增加统一治理。

各 Runtime 的分工保持原样。第一章定义的 Task Runtime 仍负责 Task 的创建、推进、中断、Checkpoint 和恢复（见 [[5.Task Runtime、Checkpoint 和业务状态]]）；第四章定义的 Tool Runtime 仍负责一次 Tool Invocation 的参数校验、权限检查、HIL、幂等、Retry 和 Tool Result（见 [[4.统一 Tool Runtime]] 与 [[6.可靠执行]]）；第五章定义的多 Agent 与异步任务机制仍负责 DomainTask 的业务协作（见 [[3.多智能体边界与升级标准]]）。第六章只关心这些任务在同一运行环境中竞争有限资源时应该如何被约束。

因此本章的治理对象是逻辑 Task，而不是单纯的 HTTP Request。一个用户请求可能只产生一次模型调用，也可能进入 Workout Agent 或 Diet Agent，连续执行多轮模型调用、知识检索和 Tool Invocation，还可能因为 HIL 暂停后再次恢复。仅限制 HTTP 请求并发无法准确描述这种资源消耗，因此系统以 Agent Task 作为生产运行治理的基本单位，并在 Task 之上实施预算、排队、优先级和并发限制。

## 边界问答

**1. Q：** 生产运行时治理和第一章的 Task Runtime 是什么关系？

**A：** 两者是不同层级。Task Runtime 负责单个 Task 的创建、推进、中断、Checkpoint 和恢复，是执行正确性；生产运行时治理在这些 Runtime 同时运行时之上，约束任务竞争有限资源时的预算、排队、优先级和并发，是运行秩序。第六章不重新设计 Task Runtime 的内部逻辑。

**2. Q：** 为什么治理对象是逻辑 Task 而不是 HTTP Request？

**A：** 一个用户请求可能只产生一次模型调用，也可能进入领域智能体连续执行多轮模型调用、知识检索和工具调用，还可能因 HIL 暂停后恢复。仅限制 HTTP 请求并发无法描述这种资源消耗，因此以 Agent Task 作为治理基本单位，在其上实施预算、排队、优先级和并发限制。
