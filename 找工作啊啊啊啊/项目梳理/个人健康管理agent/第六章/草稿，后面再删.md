# 第六章 生产 Runtime 治理

本章负责系统从单个 Agent 能够完成任务，走向多个用户任务、后台任务和外部依赖可以同时稳定运行的阶段。前面的章节已经分别定义了任务如何推进和恢复、Agent 如何执行、Tool 如何安全可靠地调用，以及多 Agent 和异步任务如何协作。本章不重新设计这些 Runtime 的内部逻辑，而是在它们之上增加统一的运行治理，控制任务能够消耗多少资源、多个任务按照什么顺序获得执行机会、系统允许多少任务同时访问外部服务，以及外部依赖持续异常时如何及时停止无效调用。

整体执行关系可以概括为：

```text
Task 到达
   ↓
任务准入与预算分配
   ↓
进入任务队列
   ↓
按照优先级获得执行资源
   ↓
Agent / Tool Runtime 执行
   ↓
访问模型 API、外部 Tool、数据库等依赖
   ↓
限流、失败统计与服务级熔断

整个过程中持续记录必要的运行指标
```

## 6.1 Production Runtime 的治理边界

Production Runtime Governance 位于 Task Runtime、Agent Runtime、Tool Runtime 和后台任务执行机制之外，负责这些 Runtime 同时运行时的资源与运行秩序。第一章定义的 Task Runtime 仍然负责 Task 的创建、推进、中断、Checkpoint 和恢复；第四章定义的 Tool Runtime 仍然负责一次 Tool Invocation 的参数校验、权限检查、HIL、幂等、Retry 和 Tool Result；第五章定义的多 Agent 与异步任务机制仍然负责 DomainTask 的业务协作。第六章只关心这些任务在同一运行环境中竞争有限资源时应该如何被约束。

因此，本章的治理对象是逻辑 Task，而不是单纯的 HTTP Request。一个用户请求可能只产生一次模型调用，也可能进入 Workout Agent 或 Diet Agent，连续执行多轮模型调用、知识检索和 Tool Invocation，还可能因为 HIL 暂停后再次恢复。仅限制 HTTP 请求并发无法准确描述这种资源消耗，因此系统以 Agent Task 作为生产运行治理的基本单位，并在 Task 之上实施预算、排队、优先级和并发限制。

## 6.2 Task Budget 与任务准入

Agent Task 的执行长度具有不确定性。简单任务可能一次模型调用即可结束，而复杂任务可能在模型推理、知识检索和工具调用之间循环多轮。如果完全依赖模型自行决定何时停止，一个异常的 ReAct 循环就可能持续消耗模型调用和外部服务资源。因此，每个 Task 在创建时都绑定一份任务预算（Task Budget），由 Runtime 对任务能够进行的自主执行范围设置硬限制。

当前 Task Budget 主要控制三个维度：逻辑模型调用次数、逻辑 Tool Invocation 次数和有效执行时间。这里统计的是 Agent 层面的逻辑动作，而不是底层网络尝试次数。例如 Agent 发起一次 `replace_workout_plan`，Task 的 Tool Budget 消耗一次；如果 Tool Runtime 因临时网络异常在同一个 Invocation 内部进行了两次执行尝试，仍然只算一次逻辑 Tool Invocation。Tool 内部的超时和 Retry 上限继续由第四章的 Tool Runtime Policy 管理。这样可以保持“任务整体资源预算”和“单次调用可靠性策略”的语义分离。

任务预算属于 Task Runtime 的控制状态，而不是业务数据，也不是由 Agent 自己维护的上下文。其结构可以表示为：

```text
TaskRuntimeState
├── task_id
├── lifecycle_status
├── checkpoint_ref
└── budget
     ├── limits
     │    ├── max_llm_calls
     │    ├── max_tool_invocations
     │    └── max_active_runtime
     ├── usage
     │    ├── used_llm_calls
     │    ├── used_tool_invocations
     │    └── active_runtime
     └── status
          ├── NORMAL
          ├── LOW
          └── EXHAUSTED
```

由于 Task 支持中断和恢复，Budget Usage 必须和 Task 的运行状态一起持久化。一个已经使用大部分预算的 Task 在恢复后继续使用原来的剩余额度，而不能因为重新加载 Checkpoint 就重新获得完整预算。有效执行时间只统计 Task 实际占用执行资源的时间；排队等待、HIL 等待以及其他不占执行资源的暂停时间不直接消耗 Active Runtime Budget。

具体预算数值由 Runtime Policy 决定，而不是由语言模型直接填写。Supervisor 或协作调用可以描述任务类型和复杂度，例如普通领域任务、复杂计划任务或后台任务；Harness 根据这些确定性字段映射到预先配置的预算策略。调用子 Agent 时，Supervisor 可以提交 `task_type`、`difficulty`、目标和约束，但不会直接传入 `max_llm_calls=20` 之类的执行额度。这样模型可以表达任务复杂度，真正的资源权限仍然掌握在 Runtime 中。

Task Budget 同时会生成一个面向 Agent 的简化投影，并通过第二章的 Agent Status 进入模型上下文。例如模型可以看到剩余模型调用次数、剩余 Tool 调用次数以及当前预算状态。当预算已经较低时，Agent 可以主动减少新的探索行为，优先利用已经获得的 Evidence 和 Tool Result 完成当前任务。不过这个状态只用于指导决策，真正的限制仍然由 Runtime 强制执行；当任一硬预算耗尽后，Runtime 不再接受对应的自主调用。

除了限制单个 Task，系统在 Task 创建时还执行轻量的任务准入。当前项目并不面向大规模高并发流量，因此没有单独建设复杂的 Admission Service。准入主要检查当前用户是否已经存在过多正在运行的任务，以及系统任务队列是否已经达到容量上限。它的作用是防止单个用户异常创建大量 Task，或者在系统已经无法及时消费任务时仍然无限接收新的工作。

## 6.3 任务队列、优先级与有限并发

Task 通过准入后，并不意味着立即获得执行资源。Agent Task 的耗时和资源消耗差异较大，如果所有 Task 一进入系统就同时调用模型 API、Tool 和数据库，即使应用本身可以创建大量异步协程，也可能迅速把外部 API 配额、数据库连接或本地执行资源占满。因此系统通过任务队列保存暂时无法执行的 Task，再由有限的执行槽位控制实际并发量。

当前系统只区分两类执行优先级。交互任务是用户正在等待结果的会话 Task，例如一次 Workout Agent 计划调整；后台任务包括 Memory Consolidation、后台分析和不要求立即返回的异步任务。Scheduler 优先让交互任务获得执行资源，后台任务在资源允许时运行。这里不需要引入复杂的多级优先级调度器，当前业务只需要保证用户正在等待的请求不会因为后台任务占满资源而长时间无法运行。

队列解决的是“哪些任务正在等待”，而有限并发解决的是“同一时间到底允许多少调用真正执行”。系统分别对主要资源设置并发上限，例如模型 API 调用并发、外部 Tool 调用并发以及后台任务并发。这里的模型 API 并发并不是模型实例池，因为模型实际由第三方供应商提供；它只是限制 Harness 同时向外部模型服务发出的请求数量。对于当前单实例规模，进程内任务队列配合 Semaphore 即可实现这套机制，不需要引入 Kafka 或复杂的分布式 Worker 系统。

HIL 等待状态不会持续占用执行槽位。当一个 Task 执行到需要用户确认的步骤时，第一章负责保存 Checkpoint 并把任务进入等待状态，第六章则释放当前执行资源。用户完成确认并恢复 Task 后，任务重新进入调度过程，再次取得执行槽位后继续运行。这样长时间等待用户输入的任务不会占用有限的并发资源。

当前队列和并发控制的目标是管理单实例内部的运行秩序，而不是包装成完整的分布式任务系统。任务状态本身仍然按照第一章的持久化机制保存，但进程内 Queue 只承担当前实例中的调度职责。

## 6.4 Backpressure、外部依赖保护与服务级熔断

有限并发只能限制真正正在执行的任务数量。如果系统处理能力已经饱和，而新 Task 仍然无限进入 Queue，最终仍然会形成越来越长的等待队列，增加内存占用和任务等待时间。因此在 Queue 之外还需要背压（Backpressure）机制。当下游已经没有足够处理能力时，上游不再无限接收工作，而是主动降低进入系统的任务数量。

当前背压策略保持简单。当 Queue 处于正常范围时任务正常进入；当资源压力升高时，后台任务优先被延后；当 Queue 达到容量上限后，新的低优先级任务不再继续无限堆积。这样系统在过载时优先保护正在等待结果的交互任务，而不是让所有任务一起进入长时间等待。

任务真正开始执行以后，还会访问第三方模型 API、外部 Tool 服务、数据库和存储等依赖。Runtime 会关注这些依赖的基本运行信号，包括调用延迟、Timeout、429 限流以及 5xx 或其他依赖错误。单次临时失败仍然按照对应调用的 Retry Policy 处理，例如遵守 `Retry-After` 或采用有限退避；但如果某个依赖已经在多个 Task 之间持续失败，仅靠每个 Task 自己 Retry 会重复浪费执行时间和 Task Budget。

因此系统在生产 Runtime 层维护服务级熔断机制。熔断针对的是某一个共享外部依赖的整体健康状态，而不是某一次 Tool Invocation。当依赖正常时，请求照常执行；如果一定时间窗口内的连续失败达到设定阈值，Runtime 将该依赖标记为熔断状态，并暂时停止向它发送新的请求。经过冷却时间后，只允许少量探测请求访问该依赖。如果探测恢复正常，则重新开放；如果仍然失败，则继续保持熔断状态。

```text
依赖正常
   ↓
持续失败达到阈值
   ↓
进入熔断
   ↓
暂停新的调用
   ↓
经过冷却时间
   ↓
少量探测
   ├── 成功 → 恢复正常
   └── 失败 → 继续熔断
```

Retry 和熔断解决的是不同层级的问题。第四章的 Retry 判断“这一次调用是否值得再次尝试”，第六章的熔断判断“这个依赖整体目前是否还值得继续访问”。例如一次偶发 Timeout 可以进行有限 Retry；如果连续多个 Task 都在同一个依赖上 Timeout，则 Runtime 不再让后续 Task 分别等待并重复验证相同的故障，而是直接返回明确的依赖不可用状态。

熔断同样不会停止整个 Agent 系统。只有真正依赖该外部服务的执行路径受到影响，不相关的 Task、Tool 或本地业务能力仍然可以继续运行。这样外部服务的局部故障不会自然扩散成整个 Harness 的资源耗尽。

## 6.5 轻量运行监控

本章只保留支撑生产运行治理所必需的运行监控，不在这里展开完整的 Trace 分析和 Agent 质量评估。第六章需要能够确认前面引入的预算、队列、并发限制和熔断机制是否真正发挥作用。

Task 层主要观察正在运行的 Task 数量、Task Failure 和 Budget Exhausted；队列层观察交互任务与后台任务的 Queue Length 和 Queue Wait Time；外部依赖层观察调用延迟、Timeout、429 和 Error Rate；熔断层记录当前依赖状态、熔断触发次数以及恢复情况。Tool Runtime 已有的失败和 Retry 信息也可以汇总为生产运行指标，用于判断某个工具或依赖是否开始出现系统性异常。

这些指标的目的不是评价 Agent 回答得是否正确，而是回答生产运行中的几个基本问题：当前系统是否已经过载，任务是否开始大量排队，某类 Task 是否经常耗尽预算，某个外部依赖是否持续异常，以及熔断机制是否频繁被触发。更完整的执行链分析、RAG 和 Tool Calling 质量评估、Rubric、LLM-as-Judge 以及回归测试统一放到后续测试与评估章节中处理。

通过以上设计，第六章形成了一套与当前系统规模匹配的生产运行治理方式。Task Budget 控制单个 Agent Task 的执行边界；任务准入避免系统在已经过载时继续无限接收工作；Queue、优先级和有限并发控制多个 Task 之间的资源竞争；Backpressure 在系统处理能力不足时限制继续积压；服务级熔断阻止持续故障的外部依赖反复消耗所有 Task 的执行资源。各机制分别解决不同层级的问题，并通过 Task Runtime、Agent Runtime 和 Tool Runtime 已有的接口协同，而不重新侵入这些模块内部的业务语义。
