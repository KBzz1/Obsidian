# 外部依赖保护与服务级熔断

任务开始执行后会访问第三方模型 API、外部 Tool 服务、数据库和存储等依赖。服务级熔断针对的是某一个共享外部依赖的整体健康状态，在依赖持续失败时暂时停止向它发送新请求，避免每个任务重复验证相同的故障。它不会停止整个 Agent 系统，只有真正依赖该外部服务的执行路径受到影响。

## 依赖健康信号

Runtime 会关注这些依赖的基本运行信号，包括调用延迟、Timeout、429 限流以及 5xx 或其他依赖错误。单次临时失败仍然按照对应调用的 Retry Policy 处理，例如遵守 `Retry-After` 或采用有限退避；但如果某个依赖已经在多个 Task 之间持续失败，仅靠每个 Task 自己 Retry 会重复浪费执行时间和 Task Budget。

## 服务级熔断

因此系统在生产 Runtime 层维护服务级熔断机制。熔断针对的是某一个共享外部依赖的整体健康状态，而不是某一次 Tool Invocation。当依赖正常时，请求照常执行；如果一定时间窗口内的连续失败达到设定阈值，Runtime 将该依赖标记为熔断状态，并暂时停止向它发送新的请求。经过冷却时间后，只允许少量探测请求访问该依赖。如果探测恢复正常，则重新开放；如果仍然失败，则继续保持熔断状态。

```text
依赖正常
   ↓
持续失败达到阈值
   ↓
进入熔断
   ↓
暂停新的调用
   ↓
经过冷却时间
   ↓
少量探测
   ├── 成功 → 恢复正常
   └── 失败 → 继续熔断
```

## Retry 与熔断的分层

Retry 和熔断解决的是不同层级的问题。第四章的 Retry 判断「这一次调用是否值得再次尝试」，第六章的熔断判断「这个依赖整体目前是否还值得继续访问」。例如一次偶发 Timeout 可以进行有限 Retry；如果连续多个 Task 都在同一个依赖上 Timeout，则 Runtime 不再让后续 Task 分别等待并重复验证相同的故障，而是直接返回明确的依赖不可用状态。

熔断同样不会停止整个 Agent 系统。只有真正依赖该外部服务的执行路径受到影响，不相关的 Task、Tool 或本地业务能力仍然可以继续运行。这样外部服务的局部故障不会自然扩散成整个 Harness 的资源耗尽。

## 边界问答

**1. Q：** 为什么不能只靠每个 Task 自己 Retry 处理依赖故障？

**A：** 依赖在多个 Task 之间持续失败时，每个 Task 自己 Retry 会重复浪费执行时间和 Task Budget。熔断在依赖层面统一判断是否还值得继续访问，后续 Task 直接得到明确的不可用状态。

**2. Q：** Retry 和熔断解决什么问题，有什么区别？

**A：** Retry 判断「这一次调用是否值得再次尝试」，熔断判断「这个依赖整体目前是否还值得继续访问」。偶发失败可以有限 Retry，连续多个 Task 在同一依赖上失败则进入熔断。

**3. Q：** 熔断会不会停掉整个 Agent 系统？

**A：** 不会。只有真正依赖该外部服务的执行路径受影响，不相关的 Task、Tool 或本地业务能力继续运行，局部故障不会扩散成整个 Harness 的资源耗尽。
