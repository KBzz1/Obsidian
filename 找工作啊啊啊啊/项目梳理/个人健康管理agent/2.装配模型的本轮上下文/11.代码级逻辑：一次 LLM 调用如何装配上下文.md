# 代码级逻辑：一次 LLM 调用如何装配上下文

本篇回答一个问题：训练智能体的某个执行节点准备调用 LLM 时，上下文装配器到底从哪里读取哪些信息、经过什么规则、最终把什么交给模型。场景沿用第二章配套示例「修改训练计划」：任务 task_7001 处于 R1 段执行，训练智能体即将在 search_replacement 步骤调用模型，业务数据库中的正式训练计划为 plan_88@v2（状态 ACTIVE），本次修改的候选与草稿进入任务草稿 D200，用户确认前业务库保持 v2 不变，用户约束「第二个动作换掉，今天肩膀不太舒服」，第三章已完成一次证据装配、产出证据包 EB500。记忆怎么检索、工具怎么执行、Supervisor 怎么委派分别属于第三、四、五章，本篇不重新展开。

## 主轴：一次装配的完整调用链

```text
执行节点准备调用 LLM
        ↓
构建 ContextAssemblyRequest（装配请求）
        ↓
ContextAssembler.assemble(request)
        │
        ├── 读取 ContextPolicy（当前节点绑定的上下文策略）
        ├── 读取 Runtime State（控制索引：当前是谁、在哪一步、该读什么）
        ├── AgentStatusBuilder 生成当前工作状态栏
        ├── HistoryCandidateBuilder 从完整轨迹生成历史候选
        ├── 读取业务事实 / 任务产物（plan_88@v2 / D200）
        ├── EvidenceReader 读取证据包 EB500
        └── CapabilityRegistry 加载当前可见 Skill / Tool
        ↓
统一转换成 ContextBlock（上下文块）
        ↓
执行令牌预算（必需块先入，可选块按优先级）
        ↓
按固定布局渲染
        ↓
ModelContext（模型上下文） + ContextManifest（上下文清单）
        ↓
模型网关调用 LLM
```

后续各节按这条链展开：谁发起、带什么参数、读哪些源、变成什么块、预算怎么裁、渲染成什么、留下什么记录、哪里会失败。

## 唯一的模型调用入口

概念层只写了「装配器生成模型输入」，没有写这次装配由谁发起。代码级补一个统一入口：执行节点不直接调用模型网关，而是调用智能体运行时的 `call_model`，由它完成「构建装配请求 → 装配 → 调用」三步。模型网关（LLM Gateway）是对模型 API 的统一封装层，示意命名：

```python
def call_model(node_ctx):
    # 智能体运行时的统一模型调用入口：节点只报身份与位置，不拼 Prompt
    request = build_context_request(node_ctx)

    assembled = context_assembler.assemble(request)   # 返回 ContextAssemblyResult

    context_observer.record(assembled.manifest)       # 清单交给观测记录层，发生在模型调用之前；
                                                      # 观测系统内部实现属于第七章
    return llm_gateway.call(assembled.model_context)
    # 模型网关负责把 ModelContext 转成具体模型 API 的 messages / tools 请求体
```

由此确立一条原则：**任何正式智能体模型调用都不允许节点自己手工拼 Prompt。**节点只负责三件事——我现在是谁、我在哪一步、我要调用模型；「这个模型本轮具体看到什么」全部收敛在装配器。少了这条收敛，同一个底层状态在不同节点眼里又会含义漂移，统一上下文治理就无从谈起（问题来源见 [[找工作啊啊啊啊/项目梳理/个人健康管理agent/2.装配模型的本轮上下文/10.困难以及应对办法]]）。

## 装配请求：ContextAssemblyRequest

`ContextAssemblyRequest` 是一次 LLM 调用准备阶段传给装配器的调用参数。它不是新的业务数据库模型，不持久化，装配完成即弃：

```python
class ContextAssemblyRequest:
    task_id: str                # 本次模型调用属于哪个逻辑任务，如 task_7001
    run_id: str                 # 属于任务的哪一段连续执行（R1），从控制索引 current_run_id 读出

    agent_id: str               # 谁在调用模型：supervisor / workout_agent
    stage: str                  # 当前流程阶段，如 plan_revision
    node_id: str                # 当前图节点 / 步骤，如 search_replacement

    latest_event_id: str | None # 装配截止的事件游标（如 evt_9001）：只读这条及之前的输入事件，
                                # 等待期间新到达的事件留给下一轮，不会被悄悄混入本轮

    context_policy_id: str      # 当前节点绑定哪套 ContextPolicy；策略由节点配置决定，模型无权选择

    evidence_bundle_id: str | None  # 第三章产出的证据包身份（EB500）；本轮不需要证据时为 None
```

`task_id` / `run_id` 直接复用第一章的身份模型（[[10.代码级逻辑：跨请求的任务暂停与恢复]]），`evidence_bundle_id` 是第三章与第二章之间的接口。装配请求本身只有引用，没有任何正文——正文由装配器按引用去各数据源读取。

请求进入装配器后，先做一轮确定性一致性校验，全部通过才开始读取：

```python
def validate_request(request):
    task = load_task(request.task_id)                     # ① 任务存在
    check(request.run_id == task.current_run_id)          # ② Run 属于该任务，且仍是当前 Run
    check(request.agent_id == task.current_agent_id)      # ③ 调用者与当前执行身份一致（workout_agent）
    check(request.stage == task.current_stage)            # ④ 阶段与运行状态一致（plan_revision）
    check(request.node_id == task.current_node)           # ⑤ 步骤与当前执行节点一致（search_replacement）
    check(policy_registry.binds(request.context_policy_id,
                                request.node_id))         # ⑥ 策略确实绑定当前节点
```

校验链里的三个位置字段各自独立：当前是谁（`current_agent_id`）、处于哪个阶段（`current_stage`）、执行哪个节点（`current_node`）是三件事，运行状态分别掌握，调用者不能拿其中一项冒充另一项。任何一项不匹配即返回 `ContextAssemblyError("request_mismatch")`，本轮不装配。这层校验存在的原因：装配请求是调用参数，不是权限凭据。没有它，一个节点自行填写别的 stage 或 context_policy_id，就能拿到其他阶段的上下文和工具暴露，能力渐进装载的作用域收敛会被绕过——节点只能报告自己在哪，不能申报自己想被当成谁。

## Runtime State：读取锚点，不是数据仓库

此前概念笔记把装配示意写成 `assemble_context(state, policy)`，并把 `state` 注释为「装配的唯一数据来源」。这层表述必须修正：系统实际存在任务控制索引、业务数据库、草稿存储、证据包、完整持久化轨迹、能力注册表等多个来源，不能为了装配器把它们全部复制进一份 AgentState——那等于建第二套事实源。正确的理解是：**Runtime State 是上下文装配的执行锚点和读取索引，而不是所有信息的物理存储位置。**

控制索引给装配器的是一组稳定引用：

```text
task_id = task_7001
run_id = R1
current_agent_id = workout_agent
current_stage = plan_revision
current_node = search_replacement
active_plan_id = plan_88
active_plan_version = 2
draft_id = None            # search_replacement 阶段草稿尚未创建，修改结果随后进入 D200
```

装配器根据这些引用，到各自归属的存储读取当前版本：

```text
任务控制索引        告诉装配器「当前是谁、在哪一步、应该读取什么」
业务服务            提供正式业务事实（plan_88@v2 正文，业务数据库，状态 ACTIVE）
草稿存储            提供当前任务产物（任务草稿 D200、候选动作）
证据包 EB500        提供第三章整理好的证据
完整持久化轨迹      提供历史候选所依据的全部消息与工具记录
能力注册表          提供当前可见 Skill / Tool 定义
```

装配器统一的是这些信息的**读取与组装过程**，它不是这些事实的拥有者。与此配套的是严格只读约束：装配器不允许修改任务状态、推进状态图、修改草稿、写业务数据库、创建工具调用实例、决定下一节点、执行 RAG、执行工具；它只允许「读 → 派生 → 筛选 → 裁剪 → 渲染 → 记录上下文清单」这条流水线。ContextManifest 是装配结果的观测记录，不算修改业务状态。

## ContextPolicy：从声明到可执行

概念层的策略是几个布尔声明（include_recent_messages、include_work_status 等，见 [[3.上下文装配器与 ContextPolicy]]），能回答「哪些类型允许出现」，回答不了「令牌不够时先删什么」。代码级做最小增强，不引入策略 DSL：

```python
class ContextPolicy:
    policy_id: str                    # 策略身份
    version: str                      # 策略版本；ContextManifest 记录的 context_policy_version 就是它

    required_sections: list[str]      # 必须进入的区块类型：缺失即本轮装配失败
    optional_sections: list[str]      # 允许进入的区块类型：按预算与优先级裁剪

    history_budget: int | None        # 历史候选在本轮最多占用的令牌数，None 表示不限
    evidence_budget: int | None       # 证据在本轮最多占用的令牌数

    capability_scope: str             # 本节点可见的能力作用域（业务域 / 技能）
    prompt_template_version: str      # 本节点使用的提示模板版本
```

两个层面的字段是同一套策略的两面：布尔声明决定候选资格，分区与预算决定装入顺序。一套可执行的策略必须能回答四件事：什么必须进入（required_sections）、什么允许进入（optional_sections）、各类内容最多占多少预算（两个 budget）、当前允许暴露哪些能力（capability_scope）。策略绑定在节点配置上，装配器只读取执行，模型无权选择策略。

## ContextBlock：装配的统一中间形态

历史、状态栏、产物、证据、技能、工具是不同类型的内容。如果装配器直接对每种类型写一段 if 分支拼 Prompt，令牌预算就没有统一的操作对象。因此在装配阶段把它们统一转换成上下文块（ContextBlock）：

```python
class ContextBlock:
    block_id: str                # 块身份，如 B1 / B2
    block_type: str              # 块类型：system_instruction / agent_status / latest_user_input /
                                 # history / evidence / business_fact / task_artifact /
                                 # skill_instruction / tool_schema

    source_refs: list[str]       # 来源引用：evt_9001 / plan_88@v2 / ev_712，
                                 # ContextManifest 的各类 refs 按它登记

    content: str                 # 渲染后的正文

    required: bool               # 必需块：预算溢出时不可裁剪，缺失即装配失败
    priority: int                # 可选块的装入优先级，数值越高越先尝试放入

    estimated_tokens: int        # 本块预估令牌数
    atomic_group_id: str | None  # 原子组：同组块要么全进要么全不进（执行中的工具调用与结果对）
```

一轮装配的块序列示例：

```text
B1  system_instruction    required=true   系统职责：你是训练智能体……
B2  skill_instruction     required=true   revise_workout_plan 技能指令（五条规则）
B3  latest_user_input     required=true   「第二个动作换掉，我今天肩膀不太舒服。」
B4  agent_status          required=true   当前工作状态栏（本轮生成）
B5  business_fact         required=true   plan_88@v2 正式计划正文（业务数据库，ACTIVE）
B6  evidence              required=false  EB500 中允许进入本步骤的证据子集
B7  history               required=false  候选历史中按预算选入的片段
B8  tool_schema           required=true   search_exercise / evaluate_training_load 定义
```

业务事实与任务产物是两类块身份：B5 的 plan_88@v2 来自业务数据库，是已经确认生效的正式计划；任务草稿 D200 与候选动作创建后以 task_artifact 块进入——前者只有经第四章调用实例提交才会变更，后者随任务执行演进。两类身份不混用，同一轮上下文里模型能分清「现在生效的计划是什么」和「正在提议的修改是什么」。

意义在于：装配器最后处理的是一组带来源、优先级和预算信息的块，而不是一整段已经拼好的 Prompt。预算在块上执行，清单从块的 source_refs 生成，布局按块的类型排序——三个下游环节共享同一个操作对象。

## 状态栏：AgentStatusBuilder 读什么、生成什么

状态栏的定位已冻结：每轮模型调用前从结构化状态确定性投影（[[4.AgentStatus 当前工作状态栏]]）。代码级补一个逻辑组件 AgentStatusBuilder，明确读取与产出：

```text
读取：
任务控制索引      当前任务 / Run / phase / step / 版本引用
草稿存储          当前草稿与任务产物版本引用
检查点 / 事件存储 最近工具执行结果、等待中的运行时事件
能力注册表        当前能力边界（enabled / disabled 及原因）

产出：
AgentStatus（本轮状态栏，四个区块）
```

```python
class AgentStatus:
    # —— 当前执行议程 ——
    goal: str                         # 本轮总目标：完成 exercise_2 的替换
    phase: str                        # 当前阶段：plan_revision
    current_action: str               # 当前动作：搜索候选替换动作
    pending_actions: list[str]        # 待处理事项：评估训练量、保存草稿、等待确认
    completion_condition: str         # 退出条件：用户确认最终训练计划

    # —— 事件侧信道 ——
    recent_events: list[str]          # 最近影响决策的确定性运行时事件（只来自系统与工具产出）

    # —— 当前环境状态 ——
    current_object_refs: dict         # 当前对象引用：plan_88@v2、target_item_id=exercise_2

    # —— 当前能力状态 ——
    disabled_capabilities: list[dict] # 暂不可用能力及原因：publish_plan：draft_not_confirmed
```

字段对齐概念笔记的四个区块，不另起一套。生成原则：系统能够确定「现在在哪一步、当前版本是什么、什么已完成、什么未完成、什么动作当前不允许」的内容，直接由程序生成，不让模型从历史推断。

AgentStatus 不是新的事实源。它是 Runtime State 的本轮模型视图：控制索引里 `current_step = evaluate_replacement`、`draft_version = 2`（任务草稿 D200 被修改过一次）变了，下一轮状态栏就重新生成；上一轮的状态栏不参与任何后续系统控制，也不落库。据此，上下文清单中原先悬空的 `agent_status_ref` 字段改为：

```python
agent_status_hash: str | None    # 本轮状态栏正文的摘要哈希：状态栏每轮重新生成、没有长期身份，
                                 # 清单按既有原则只存摘要，不建 AgentStatus 存储
```

两个候选方案（存哈希、或引用一份轻量快照）里选哈希，因为它与清单「只存引用、版本与摘要、不复制正文」的既有定位完全一致，是更小的那个改动；[[3.上下文装配器与 ContextPolicy]] 的字段已同步更新。

## 历史候选：HistoryCandidateBuilder

三层历史（完整持久化轨迹 → 历史候选 → 本轮模型上下文）的语义已冻结，代码级补生成逻辑。HistoryCandidateBuilder 在每次装配时执行：

```text
读取完整持久化轨迹
    ↓ 删除已失效的历史状态栏（状态栏每轮重新生成，轨迹里的旧状态栏全部过期）
    ↓ 删除旧路由结果（已被当前节点取代）
    ↓ 删除已被任务产物取代的大型工具结果
    ↓ 保留仍影响当前决策的历史块（用户约束、未收敛的对话）
    ↓ 保持执行中工具调用与结果的原子关系（同一 atomic_group_id）
    ↓
历史候选（本次装配的临时派生视图）
```

随后由 ContextPolicy 决定哪些候选最终进入本轮上下文（可选块、按优先级、受 history_budget 约束）。三个层次必须保持区分：完整轨迹不是历史候选，历史候选也不是最终上下文。上下文整理只影响「以后哪些历史还有资格进入模型」，数据库里的完整轨迹从不被删除；候选视图用完即弃，本轮不引入长期候选存储，未来若为性能缓存候选，属于优化项。

## 证据：第三章接口与去重

第三章负责把记忆、业务事实与知识检索装配成证据包，第二章只消费：

```text
第三章：Memory + 业务事实 + 知识 RAG
        ↓ 检索协调器 + 证据装配
证据包 EB500（每条证据带 evidence_id / claim / source_id / source_version）
        ↓
第二章：装配请求携带 evidence_bundle_id = EB500
        ↓
EvidenceReader.load(EB500) → 证据块（ContextBlock，source_refs = evidence_id）
        ↓
ContextPolicy 裁决：哪些证据在当前 agent / stage 允许进入本轮
```

分工一句话：第三章决定「找回来什么可信信息」，第二章决定「这些信息本轮模型看到多少」。装配器不做向量检索、RAG、记忆检索或重排——重新检索会把一次确定性读取变成概率性调用，还会让清单失去「本轮到底基于哪些证据」的判定依据。本轮不需要证据时 `evidence_bundle_id = None` 即可。

装配器对证据包只负责读取边界内的三项检查：

```text
① 证据包是否存在（bundle_id 能否读到）
② 是否属于当前用户 / 任务（归属校验，防止读到别的任务的证据）
③ 是否仍有效（读取包上的有效性标记；标记如何生成与维护属于第三章）
```

三项任一不通过按缺失处理：策略声明证据为可选则记录缺失继续装配，声明为必需则本轮装配失败（见「装配失败的三条路径」）。证据如何生成、版本如何维护、何时判定过期，属于第三章（[[9.证据装配与失败语义]]），第二章到此为止。

同一事实可能从多个来源出现：plan_88@v2 是当前业务事实直接读取；「用户只能晚上训练」「肩部负荷相关领域知识」来自证据包；早期对话历史里可能还有这两件事的过期文本。装配器在块生成后按 source_refs 与语义键做简单去重：同一稳定事实已经以结构化业务事实或任务产物进入本轮后，历史与证据中对应的过期大段文本不再保留。只做引用级比对，不建语义去重系统。

## 能力：渐进装载接入调用链

能力渐进装载的设计已冻结（[[8.能力渐进装载]]），代码级接入点在装配链的能力读取一步：

```text
ContextPolicy.capability_scope
    ↓
能力注册表
    ├── 当前作用域的 Skill（如 revise_workout_plan 的完整指令与规则）

skill_instruction 块 + tool_schema 块（ContextBlock）
    ↓

```

同一任务不同位置看到的能力逐级收敛：会话主管只看到 workout / diet / habit 三个业务域的轻量描述；进入训练智能体后看到 revise_workout_plan 技能的完整指令；search_replacement 步骤看到 search_exercise、evaluate_training_load、update_plan_draft；到 awaiting_confirmation，update 类工具退场，publish_plan 因 `draft_not_confirmed` 不向模型暴露。

第二章与第四章的边界在这里：**上下文中没有的工具，模型无法主动提出这个调用；上下文中存在工具，也只代表当前节点允许模型提议该动作，不代表工具运行时必须执行。**提案之后的权限、参数与业务规则重新校验和真实执行全部属于第四章（[[9.代码级逻辑：从提议到业务副作用]]）。

## 预算：令牌预算的执行顺序

预算公式维持既有设计（[[6.历史轨迹与上下文整理]]）：

```text
上下文预算 = 模型最大上下文 − 预留输出空间 − 安全余量
```

它是部署配置，不是架构规则；20 万令牌只是当前部署示例值。代码级的改变在于执行时机：预算在块生成之后、渲染之前执行，对象是块不是字符串：

```python
def apply_budget(blocks, context_budget):
    required = [b for b in blocks if b.required]
    if sum(b.estimated_tokens for b in required) > context_budget:
        raise ContextAssemblyError("required_context_overflow")   # 必需内容自身超预算：显式失败

    kept = list(required)
    for group in optional_groups_by_priority(blocks):             # 可选块按优先级从高到低
        if total_tokens(kept) + group.tokens <= context_budget:
            kept.extend(group.blocks)                              # 原子组整组放入，不拆半
    return kept
```

必需块是缺失后模型连任务都无法正确执行的内容：系统指令、当前智能体身份、当前任务目标、最新用户输入、状态栏、当前业务事实、当前节点必须的技能指令。可选块是可以按策略裁剪的：较早历史、补充证据、非关键工具结果、额外背景产物。

预算不足时的裁剪顺序由 ContextPolicy 声明，不建立所有智能体永远相同的全局顺序。当前策略的默认顺序模板：

```text
1. 删除失效历史（候选生成已删一轮，预算压力下扩大删除范围）
2. 删除已被任务产物替代的工具结果
3. 减少较低优先级的历史候选块
4. 减少补充型证据块
5. 保留当前产物、状态栏、最新输入（它们是必需块，本就不在裁剪之列）
```

## 产出：ModelContext 与固定布局

渲染前，装配结果以结构化形态持有：

```python
class ModelContext:
    context_id: str             # 本轮模型上下文身份，与上下文清单的 context_id 一致

    system_messages: list       # 稳定区：系统职责、智能体身份、技能指令
    history_messages: list      # 较稳定区：本轮选入的历史消息（含原子工具调用对）

    task_context: str           # 当前业务事实与任务产物（plan_88@v2）
    evidence_context: str       # 本轮进入的证据子集（来自 EB500）
    agent_status: str           # 本轮状态栏渲染结果

    current_user_input: str     # 最新用户输入 / 当前事件
    tool_schemas: list          # 本轮可见的工具定义
```

渲染后才变成具体模型 API 需要的 messages / tools，这步转换发生在模型网关，装配器不与任何一家模型供应商的请求格式绑定。布局顺序以 [[7.KV Cache 与上下文布局]] 已确定的设计为准：

```text
稳定系统提示词
固定智能体职责 / 安全规则 / 技能指令 / 工具模式
────────────────────
较稳定：本轮选入的历史轨迹与证据
────────────────────
当前任务产物（plan_88@v2）
事件侧信道
当前工作状态栏
最新用户输入
```

状态栏每轮都变，所以压在尾部动态区，缓存失效只波及其后一小段；稳定系统指令放在最前，是为了让前缀缓存尽可能长地复用；不每轮随机改变 Prompt 结构，是因为前部任何变动都会让后续全部缓存作废。正确性优先于缓存友好，这是布局的既有原则。

## 同源双产出：ContextManifest

一次装配返回两个结果，来自同一套块：

```python
class ContextAssemblyResult:
    model_context: ModelContext    # 送往模型网关的输入
    manifest: ContextManifest      # 同一套块的观测记录
```

同一套 ContextBlock，一边按布局渲染成 ModelContext，一边从块的 source_refs 生成 ContextManifest。不能先生成 Prompt、事后再去猜模型当时可能看到了什么——那样清单就只剩推测价值。清单字段定义见 [[3.上下文装配器与 ContextPolicy]]，它能回答的问题：这是谁的一次调用（task_id / run_id / agent_id / stage）、用了什么策略（context_policy_version）、哪个提示模板（prompt_template_version）、依据哪些正式业务事实（business_fact_refs）、哪些证据与产物（evidence_refs / artifact_refs）、看到了哪些工具与技能（visible_tool_refs / visible_skill_refs）、大概多少令牌（estimated_tokens）、内容是否一致（context_hash、agent_status_hash）。完整 Prompt 不作为默认长期日志保存；受控短期采样留待未来讨论，本轮不展开。清单的消费场景在第七章（[[4.ContextManifest 与模型可见上下文]]）。

生成与持久化是两个职责，分属两个组件：装配器对清单的职责到生成为止——它返回 ContextAssemblyResult，不写任何观测存储，也不修改业务状态；清单的记录由统一模型调用入口在调用模型网关之前交给观测记录层（`context_observer.record`，见「唯一的模型调用入口」），观测系统内部如何组织与存储属于第七章。生成者与记录者分离，装配器的只读边界才保持完整。

## 装配失败的三条路径

**异常一：控制索引与业务版本不一致。**控制索引记录 `active_plan_version = 2`，业务库里 plan_88 已被推进到 version 3。装配器不允许自己决定「那我用 v3 吧」——用哪个版本是业务并发语义，不归读取层管。正确行为是读取失败或版本校验不匹配时返回 `ContextAssemblyError("version_conflict")`，交给 Harness 处理；装配器不能偷偷修改控制索引去迁就业务库。

**异常二：证据包不存在或已过期。**按策略声明的性质分流：Policy 声明证据为 optional 时，记录缺失并继续装配；当前节点声明证据为 required 时，本轮装配直接失败。不能让模型在缺少必要证据时悄悄继续，把「没有证据」伪装成「证据支持」。

**异常三：必需块自身超预算。**系统指令、最新输入、当前业务事实与当前阶段必需的任务产物、必需证据、技能指令加起来已经超出上下文预算——有些阶段还没有草稿，必需的就是正式业务事实本身。此时不能从中间随机截断，也不能触发「全部摘要」：抛出 `ContextAssemblyError("required_context_overflow")`，由 Harness 决定切换模型、减少任务输入、进入特定压缩流程或中止本次调用（降级治理属于第六章，这里只定义边界）。这三条路径共同说明一件事：上下文预算不只是令牌计数器，而是带语义优先级的输入治理——装配器不能静默破坏必需上下文。

## 未下沉的部分：规划器与键值缓存

规划器在本篇只占一个接入点：当前 stage 声明需要规划器时，能力装载加载对应的规划器 Skill / Prompt；固定流程（本场景的六步状态机）不加载。规划器内部机制维持 [[9.Planner 按需规划]] 的概念级设计，本轮不写新的规划框架。键值缓存同理：布局与渲染顺序已定，渲染器保持稳定部分顺序稳定、动态状态栏与当前输入放后部即可；供应商缓存的内部实现、命中算法、前缀树、分布式缓存不在本轮范围。

## 第二章代码级理解总结

- **Runtime State 与 ModelContext 不能合并。**前者是系统事实与读取锚点，后者是单次调用的临时视图。合并等于把完整事实直接暴露给模型，退回直连式历史的老问题。
- **AgentStatus 与 Runtime State 不能合并。**状态栏是派生视图不是事实源：每轮重新生成、旧值不参与控制、清单只留哈希。并进去会让一个本轮视图获得系统控制语义。
- **历史候选与持久化轨迹不能合并。**候选是装配时的临时派生视图，轨迹是恢复与审计的完整事实；整理只改「进入资格」，从不删库。
- **ModelContext 与 ContextManifest 不能合并。**一个送进模型，一个留给观测评估；同源同时生成，生命周期完全不同。

ContextAssemblyRequest 是第二章对外的总接口：task_id / run_id 接第一章身份模型，evidence_bundle_id 接第三章证据包，visible tools 的提议经第四章工具运行时落地执行；任务草稿 D200 的正式提交同样经第四章调用实例完成，业务数据库的新版本 plan_88@v3 只在那时产生。第二章保证「模型看到什么可治理、可观测」；第四章保证「提议之后动作安全落地」。

## 边界问答

**1. Q：** 装配请求为什么不能只有 AgentState 一个参数？

**A：** AgentState（Runtime State）只是读取锚点和索引，业务事实、任务产物、证据、能力定义都在各自归属的存储里。把物理数据全部复制进一份 AgentState 等于建第二套事实源，违反唯一事实来源原则；装配器按引用到各源读取当前版本，才是正确方向。

**2. Q：** 上下文装配器会不会自己做 RAG 或记忆检索？

**A：** 不会。检索在第三章完成并产出证据包，装配器只按 `evidence_bundle_id` 消费现成结果。装配中重新检索会把一次确定性读取变成概率性调用，清单也失去「本轮基于哪些证据」的判定依据。

**3. Q：** 历史候选是数据库吗？

**A：** 不是。它是一次装配中的临时派生视图，用完即弃；完整持久化轨迹继续完整保存。缓存候选可以作为未来优化，本轮不引入长期候选存储。

**4. Q：** AgentStatus 为什么不能当新的事实源？

**A：** 它是 Runtime State 的本轮模型视图，每轮重新生成，上一轮的值不参与任何系统控制。下游若消费状态栏做控制，等于让过期视图获得系统控制权；需要控制语义时应读控制索引本身。

**5. Q：** 模型能看到某个工具，是否意味着一定可以执行？

**A：** 不。上下文中没有的工具，模型无法主动提出调用；存在只代表当前节点允许模型提议该动作。执行前工具运行时会重新校验权限、参数与业务规则，执行权在第四章。

**6. Q：** 令牌预算在什么时机计算？

**A：** 块生成之后、渲染之前，对象是上下文块不是拼好的字符串：先核对必需块总量（超出直接失败），再按优先级逐组放入可选块。渲染完再回头数令牌，裁剪就只能作用于文本了。

**7. Q：** 必需上下文自身超预算怎么办？

**A：** 抛 `required_context_overflow`，由 Harness 决定换模型、减输入、进压缩流程或中止；装配器不做中间截断，也不触发「全部摘要」。装配器不能静默破坏必需上下文，这是它与简单令牌截断器的区别。

**8. Q：** ContextManifest 为什么必须和 ModelContext 同时生成？

**A：** 两者来自同一套上下文块：一边渲染成模型输入，一边登记来源引用。先生成 Prompt 再事后补记，只能猜测模型当时看到了什么，清单对评估就失去价值。

**9. Q：** 模型返回结果以后，是谁修改 Runtime State？

**A：** 不是装配器，它严格只读。模型输出结构化请求或工具调用，Harness 校验后交工具运行时执行，执行成功后由 Harness 写回状态；下一轮装配再从新状态读取。读写分离让「本轮看到了什么」与「本轮改变了什么」各有清晰的归属。

**10. Q：** 版本不一致时，装配器为什么连「改用新版本」都不能自己决定？

**A：** 用哪个版本是业务并发语义。装配器自行选边等于在读取路径上偷偷改写锚点，并发冲突会被静默吞掉；返回装配错误、交 Harness 处理，才不越权。

**11. Q：** 修改结果为什么进任务草稿 D200，而不是直接把正式计划推到 v3？

**A：** 业务数据库只保存已确认生效的正式计划。未确认的修改进草稿存储，用户确认后经第四章工具调用实例提交，业务库才出现 plan_88@v3——「尚未确认」与「已经生效」在数据上分层可判定，等待期间业务库必然不变，正式业务事实与任务产物（Business Fact ≠ Draft / Task Artifact）不混用。

**12. Q：** ContextManifest 由谁记录、存在哪里？

**A：** 装配器只生成不记录：返回 ContextAssemblyResult 后它的职责结束；统一模型调用入口在调用模型网关前把清单交给观测记录层（context_observer.record）。观测系统内部实现属于第七章，装配器不修改业务状态，也不拥有观测数据存储。
