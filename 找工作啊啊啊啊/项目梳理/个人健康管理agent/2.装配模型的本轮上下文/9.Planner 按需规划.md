# Planner 按需规划

## 从默认入口到按需能力

执行规划从「全部任务流强制前置规划器组件」的默认调度入口，降级为按需激活（按需规划）的特定能力：常规请求直接走确定性状态图和垂直领域智能体，只有复杂任务才触发规划器。

## 三类计划

工程上必须严格区分三类不同的「计划」：

| 名称 | 是什么 | 由谁生成 |
| --- | --- | --- |
| 业务域计划（训练 / 饮食计划） | 正式任务产物，业务流程的产出 | 业务流程 |
| 当前工作状态栏（执行议程） | 运行时供给模型的执行进度视图 | Harness 确定性投影 |
| 执行计划（Plan） | 复杂任务下的逻辑步骤列表 | LLM 规划器节点 |

业务域的训练或饮食计划属于正式的任务产物，不是执行计划；执行议程的定义见 [[4.AgentStatus 当前工作状态栏]]。

## 触发条件

常规的修改动作、状态查询或局部数据写入请求，交给确定性的状态图和垂直领域智能体直接处理，无需前置规划。

只有任务存在多环节的深度依赖、步骤间有不可预见的流转逻辑、且上一步结果强力干预下一步动作时，系统才按需触发规划器。

## 示例：固定流程不需要规划器

以「修改训练计划」任务为例，「替换一个训练动作」是固定流程：

```text
load_plan
  ↓
identify_target_item
  ↓
search_replacement
  ↓
evaluate_replacement
  ↓
save_new_draft
  ↓
wait_for_confirmation
```

Harness 直接保存当前步骤游标：

```json
{
  "workflow_type": "fixed",
  "current_step": "evaluate_replacement",
  "completed_steps": [
    "load_plan",
    "identify_target_item",
    "search_replacement"
  ]
}
```

固定流程下规划器只是重复描述 Harness 已经知道的状态机，没有必要额外调用模型。

「综合最近一个月的训练、饮食和恢复情况，重新调整下周方案」这类任务流程并不确定，才由规划器生成执行计划：

```json
{
  "workflow_type": "dynamic",
  "plan": [
    "load_workout_history",
    "load_diet_history",
    "load_recovery_data",
    "analyze_training_recovery",
    "generate_next_week_plan"
  ],
  "current_step": "load_workout_history"
}
```

规划器只负责生成执行计划；当前执行到哪一步、哪些步骤已完成，仍由 Harness 保存。

## 计划回写状态

规划器生成的执行计划写入持久化的结构化状态，由系统运行时全权接管步骤游标的管理与跟进。下游模型读取的仍然是由系统状态投影出的当前执行议程，模型依赖自己阅读原始计划文本跟踪状态的链路被切断（演化原因见 [[找工作啊啊啊啊/项目梳理/个人健康管理agent/2.装配模型的本轮上下文/10.困难以及应对办法]]）。

## 边界问答

**1. Q：** 为什么规划器生成的计划不直接交给下游模型读？
**A：** 计划文本是静态的，无法确证执行中的实时坐标；工具宕机、外部阻断或系统恢复都会让真实状态偏离初始计划。所以计划必须回写结构化状态，由运行时接管游标，下游模型读的是状态投影出的执行议程。

**2. Q：** 常规请求为什么不需要前置规划？
**A：** 常规修改、状态查询和局部写入由确定性状态图和垂直领域智能体直接处理；只有深度多环节依赖、步骤间存在不可预见流转且上一步结果强力干预下一步动作的任务，才触发规划器。

**3. Q：** 固定流程下规划器为什么没有价值？
**A：** 固定流程是 Harness 已知的状态机，规划器只是重复描述这些步骤，没有额外信息量；当前步骤游标由 Harness 直接保存推进即可。只有步骤间存在不可预见的流转逻辑时，规划器的计划才提供增量。
