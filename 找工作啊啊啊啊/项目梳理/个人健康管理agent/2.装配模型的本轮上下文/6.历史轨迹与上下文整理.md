# 历史轨迹与上下文整理

## 默认不提前压缩

常规任务流转中，系统保留原始的自然语言对话和工具执行轨迹，不提前介入上下文压缩。当模型输入规模逼近当前配置的上下文预算时，运行时才主动拉起一次上下文整理流程。

## 上下文预算怎么定

上下文预算不是架构规则，而是每次部署的配置参数，由三个输入推出：

```text
上下文预算 = 模型最大上下文 − 预留输出空间 − 安全余量
```

预留输出空间留给本轮可能产生的大体积工具结果和密集型任务产物，安全余量避免触碰到模型窗口物理上限时被迫做暴力截断。当前部署配置为 20 万令牌只是一个示例值：换更大窗口的模型、或输出更重的任务，调整参数即可，架构不变。

## 整理策略

上下文整理默认用确定性的程序化规则裁剪与重组，不引入额外的 LLM 摘要调用。

清理的对象是已失效或被结构化结果替代的数据层：过期的历史状态栏、废弃的路由探针结果、重复的系统级指导信息，以及执行已完成、状态已收敛进正式任务产物的冗余工具调用过程。

对于仍有业务效用的运行状态，系统不靠旧历史记录维持：整理结束后，用最新结构化数据重新生成工作状态栏和派生视图（见 [[4.AgentStatus 当前工作状态栏]]、[[5.程序化派生上下文]]）。

整理严格保证执行中语义单元的完整性：进行中的工具调用指令、返回结果及其衍生的后续动作作为原子块保留，不强制分割。

## 示例：上下文整理只保留当前有效事实

一个长期任务运行数百轮后，上下文规模可能逼近预算：

```json
{
  "messages": 420,
  "tool_results": 86,
  "draft_versions": 12,
  "estimated_context_tokens": 203500
}
```

Harness 在调用模型前检查预算：

```python
# 上下文预算是部署配置：模型最大上下文 - 预留输出空间 - 安全余量
context_budget = model_max_context - output_reserve - safety_margin  # 当前部署示例值：200000

if estimated_tokens > context_budget:
    run_context_compaction()  # 触发确定性上下文整理
```

整理器执行确定性裁剪：

```text
删除：
- 旧状态栏
- 已完成节点的临时说明
- 旧路由决策输出
- 已被新版本替代的草稿
- 已经转化为结构化产物的大型工具结果

保留：
- 当前草稿
- 当前任务状态
- 当前用户约束
- 当前工作流步骤
- 仍会影响后续决策的工具结果
```

例如原始训练历史查询结果有 3 万令牌：

```json
{
  "tool_name": "query_training_history",
  "token_count": 30000,
  "result": "过去 90 天的完整训练记录"
}
```

业务服务已经生成结构化结果：

```yaml
训练历史分析结果:
  average_frequency_per_week: 4
  recent_volume_trend: increasing
  chest_training_frequency: 2
  last_deload_date: 2025-02-10
```

整理后模型只保留结构化结果，原始工具结果仍完整保存在持久化轨迹中（轨迹、候选、本轮上下文三层见 [[3.上下文装配器与 ContextPolicy]]）。上下文整理优先依赖结构化事实和程序化裁剪，而不是让另一个模型自由摘要：自由摘要可能丢失「60 分钟上限」「避免过顶推举」等明确约束。

## 整理后的新基线

```text
长任务上下文
      │
      │ 达到上下文预算
      ▼
确定性上下文整理
      │
      ├── 当前有效任务状态
      ├── 当前任务产物
      ├── 程序化派生信息
      ├── 尚未解决的用户要求
      └── 必要近期原始消息
      │
      ▼
新的工作上下文基线
```

这个设计里有一个明确的取舍：系统主动承担整理带来的单次前缀缓存失效成本，拒绝为了维持高键值缓存命中率而无限期囤积低价值历史数据（缓存布局见 [[7.KV Cache 与上下文布局]]）。

## 边界问答

**1. Q：** 整理为什么默认不用 LLM 摘要？

**A：** 整理优先采用确定性的程序化规则裁剪与重组，默认不引入额外的 LLM 摘要调用；过期状态栏和派生视图由最新结构化数据重新生成，不需要模型来总结。

**2. Q：** 为什么进行中的工具调用必须作为原子块保留？

**A：** 进行中的工具调用指令、返回结果和衍生后续动作是尚未收敛的语义单元，整理时作为原子块保留，不予强制分割。

**3. Q：** 上下文预算为什么不直接等于模型的窗口上限？

**A：** 预算 = 模型最大上下文 − 预留输出空间 − 安全余量：要给大体积工具结果和任务产物输出留空间，也要留余量避免碰到物理上限时被迫暴力截断。预算由配置推出，20 万令牌只是当前部署的示例值，不是架构原则。

**4. Q：** 为什么不用另一个模型做自由摘要来整理上下文？

**A：** 自由摘要是概率性产出，可能丢失「60 分钟上限」「避免过顶推举」这类明确约束。结构化事实和程序化裁剪保留全部约束与当前有效状态，只在必要时保留仍影响后续决策的原始结果。
