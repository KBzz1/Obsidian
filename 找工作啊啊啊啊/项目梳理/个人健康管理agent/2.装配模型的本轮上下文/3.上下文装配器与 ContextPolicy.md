# 上下文装配器与 ContextPolicy

## 为什么需要装配器

早期各执行节点自行从历史消息里截取片段、拼装模型输入，同一个底层状态在不同节点眼里含义不同。上下文装配器（Context Assembler）是为解决这个歧义引入的统一数据转换层：它不参与状态图的路由决策，也不修改任何任务状态，唯一职责是读取前序确定的系统运行状态，按当前节点绑定的上下文策略（Context Policy）生成最终的模型输入。

上下文策略是绑定在执行节点上的上下文声明，规定这个节点一次模型调用可以从运行状态中看到哪几类数据。装配器读状态、按策略取子集、组装成模型输入。状态本身仍是第一章定义的状态图运行状态与检查点（见 [[5.Task Runtime、Checkpoint 和业务状态]]），装配器只是它的读取端。

## 三层上下文：保存什么、可选什么、看到什么

系统对「历史」有三个层次的处理，不能混为一谈：

```text
完整持久化轨迹
  任务的全部对话消息与工具执行记录，供恢复与审计使用
        ↓ 按整理规则筛选
可供装配器选择的历史候选
  轨迹中仍未失效、有资格进入本轮的片段
        ↓ 按当前节点的上下文策略选取
本轮模型上下文
  当前节点真正看到的模型输入
```

保留原始轨迹、默认不提前摘要，不等于所有历史永远全部进入 Prompt。装配器每轮从候选中按上下文策略选取子集；过期的状态栏、已被结构化产物替代的工具结果在整理后不再进入候选（整理规则见 [[6.历史轨迹与上下文整理]]）。第二章的所有机制都建立在这三层区分上：第一层由运行时持久化，第二层由整理规则维护，第三层由装配器生成。

## 示例：三类数据如何进入一次任务

本章配套示例统一使用「修改训练计划」场景。用户正在修改正式训练计划 plan_88：业务数据库中当前正式版本为 v2、状态 ACTIVE；本次修改产生的候选与草稿进入任务草稿 D200，用户确认前业务数据库保持 v2 不变（草稿与正式计划的分层见 [[5.Task Runtime、Checkpoint 和业务状态]]，提交路径见 [[9.代码级逻辑：从提议到业务副作用]]）：

```json
{
  "plan_id": "plan_88",
  "version": 2,
  "status": "active",
  "duration_limit_min": 60,
  "exercises": [
    {
      "item_id": "exercise_1",
      "name": "杠铃卧推",
      "sets": 4,
      "reps": 8
    },
    {
      "item_id": "exercise_2",
      "name": "杠铃推举",
      "sets": 3,
      "reps": 10
    },
    {
      "item_id": "exercise_3",
      "name": "上斜哑铃卧推",
      "sets": 3,
      "reps": 10
    }
  ]
}
```

用户发送「第二个动作换掉，我今天肩膀不太舒服。」。API Gateway 把这条输入写成事件：

```json
{
  "event_id": "evt_9001",
  "type": "user_message",
  "task_id": "task_7001",
  "payload": {
    "text": "第二个动作换掉，我今天肩膀不太舒服。"
  }
}
```

任务控制索引（第一章的 `agent_task_runtime` 表）据此登记任务 task_7001：

```json
{
  "task_id": "task_7001",
  "domain": "workout",
  "task_type": "revise_plan",
  "current_node": "supervisor",
  "active_plan_id": "plan_88",
  "active_plan_version": 2,
  "status": "running"
}
```

任务建立后，系统里同时存在三类数据：

```text
业务数据：
训练计划、动作、版本

任务数据：
当前节点、任务阶段、目标动作、草稿版本

输入事件：
用户本次发送的内容
```

这三类数据不会直接拼成一段完整 Prompt。它们由不同组件按需读取，再转换成当前节点需要的上下文——这是装配器存在的直接原因。

## 示例：运行时状态保存事实，不保存完整 Prompt

Harness 把用户请求解析成结构化任务状态（Runtime State），而不是把原始对话原样放进模型上下文：

```json
{
  "task_id": "task_7001",
  "current_node": "workout_agent",
  "route": {
    "domain": "workout",
    "intent": "revise_existing_plan"
  },
  "task_context": {
    "plan_id": "plan_88",
    "plan_version": 2,
    "target_item_id": "exercise_2",
    "requested_operation": "replace",
    "temporary_constraints": {
      "shoulder_discomfort_today": true
    }
  },
  "execution": {
    "phase": "plan_revision",
    "current_step": "search_replacement",
    "completed_steps": [
      "load_plan",
      "identify_target_item"
    ],
    "pending_steps": [
      "search_replacement",
      "evaluate_replacement",
      "save_new_draft",
      "wait_for_confirmation"
    ]
  },
  "capabilities": {
    "enabled": [
      "search_exercise",
      "evaluate_training_load",
      "update_plan_draft"
    ],
    "disabled": [
      {
        "name": "publish_plan",
        "reason": "draft_not_confirmed"
      }
    ]
  }
}
```

运行时状态是 Harness 的执行依据。模型不能直接修改它：模型只能通过结构化输出或工具调用请求 Harness 执行操作，工具执行成功后由 Harness 写回状态。由此形成的数据流：

```text
用户事件
  ↓
Harness 更新运行时状态
  ↓
上下文装配器读取状态和业务数据
  ↓
模型生成工具调用
  ↓
工具运行时执行
  ↓
Harness 写回状态
  ↓
重新装配下一轮上下文
```

## 装配接口

```python
class ContextPolicy:
    # 上下文策略：声明一个执行节点每次模型调用可见的数据类型
    include_recent_messages: bool   # 是否携带近期对话与执行轨迹
    include_work_status: bool       # 是否携带当前工作状态栏
    include_task_artifacts: bool    # 是否携带当前任务产物（如草稿）
    include_derived_context: bool   # 是否携带程序化派生信息
    capability_scope: str           # 本节点可见的能力作用域（领域 / 技能）

def assemble_context(
    state: AgentState,      # 结构化运行状态：装配的读取锚点与索引，不是全部信息的物理存储位置
    policy: ContextPolicy,  # 当前节点绑定的上下文策略
) -> ModelContext:          # 输出：单次 LLM 调用的模型上下文
    ...
```

运行状态提供的是稳定引用——当前任务、Run、节点、活跃计划与证据包的标识；业务事实、任务产物、证据与能力定义仍从各自归属的存储按引用读取当前版本，装配器统一的是这些信息的读取与组装过程，不拥有这些事实。装配请求的逐字段定义、各数据源的读取关系与完整调用链见 [[11.代码级逻辑：一次 LLM 调用如何装配上下文]]。

### 上下文清单（ContextManifest）

装配器除了生成模型上下文，还生成一份轻量上下文清单（ContextManifest），记录本轮模型调用实际看到了哪些上下文组成、暴露了哪些能力。清单与模型上下文由装配器从同一份状态按同一策略生成，保存的是引用、版本与摘要，不复制 Evidence、工具结果和 Artifact 的正文，默认也不持久化完整 Prompt：

```python
class ContextManifest:
    context_id: str                # 本轮上下文清单身份

    task_id: str                   # 所属任务
    run_id: str                    # 所属 Run：任务的一次连续执行阶段，见第一章
    agent_id: str                  # 本轮调用者，如 supervisor / workout_agent
    stage: str                     # 当前执行节点 / 阶段

    agent_status_hash: str | None  # 本轮状态栏正文的摘要哈希（状态栏每轮重新生成、没有长期身份，见 [[4.AgentStatus 当前工作状态栏]]）

    memory_refs: list[str]         # 进入本轮的长期记忆引用
    evidence_refs: list[str]       # 进入本轮的证据引用，只存 Evidence.evidence_id
    tool_result_refs: list[str]    # 进入本轮的工具结果引用（如 invocation_id）
    artifact_refs: list[str]       # 进入本轮的产物引用

    visible_tool_refs: list[str]   # 本轮实际暴露给模型的工具（名称 + 版本）
    visible_skill_refs: list[str]  # 本轮实际暴露给模型的技能

    prompt_template_version: str   # 本轮使用的提示模板版本
    context_policy_version: str    # 本轮绑定的上下文策略版本，只存版本引用，不复制策略全文
    context_hash: str              # 本轮上下文的摘要哈希
    estimated_tokens: int          # 本轮上下文预估令牌数
```

清单不改变装配器的只读职责：它只是每次正式模型调用前多保留的一份「模型实际看到了什么」的记录，不修改任何任务状态，也不替代各 Runtime 已保存的事实；完整 Prompt 默认不作为长期观测数据保存。

清单主要服务于后续的判断：某条 Evidence 已经进入证据包但没有进入本轮上下文；某个 Tool 已经注册但本轮没有暴露给模型；本轮状态栏处于哪个版本。`evidence_refs` 只保存 `Evidence.evidence_id` 一种身份，证据包归属由 `EvidenceBundle.bundle_id` 与检索记录维护，清单不混用两种 ID。同一份 Evidence 在版本 A 进入本轮、版本 B 没有进入时，可以结合 `prompt_template_version` 与 `context_policy_version` 判断变化来自提示模板还是上下文策略。这些判断属于后续测试与评估章节的消费场景，第二章只负责在每次正式模型调用前生成并保留这份清单。

## 统一的是构建流程，不是内容

装配器的统一不意味着所有智能体共享同一套上下文。会话主管、训练计划流程、饮食节点和具体技能执行器（Skill Worker）分别绑定差异化策略：会话主管的路由决策只需要当前用户输入、少量会话边界信息和轻量能力描述；训练计划流程高度依赖当前草稿数据、任务执行状态和关联的工具结果；通用对话节点更侧重近期的自然语言交互。

所以装配器统一的是「上下文的构建流程与管理标准」，各执行节点的信息可见性仍然相互隔离。路由决策本身见 [[4.Supervisor 架构与委派]]，能力作用域如何随策略收敛见 [[8.能力渐进装载]]。

## 示例：Supervisor 在路由决策时只读取所需信息

Supervisor 在路由决策这一步只判断业务域和任务类型，它看到的上下文可以很小（Supervisor 的完整职责见 [[4.Supervisor 架构与委派]]）：

```text
系统职责（路由决策阶段）：
识别用户请求所属业务域和任务类型。
只能输出结构化路由结果，不执行具体业务操作。

当前活跃任务：
domain=workout
task_type=revise_plan
status=running

可用业务域：
workout：训练计划、训练记录、动作调整
diet：饮食记录、营养分析、饮食计划
habit：习惯创建、打卡和提醒

用户最新输入：
第二个动作换掉，我今天肩膀不太舒服。
```

会话主管输出结构化路由结果：

```json
{
  "domain": "workout",
  "intent": "revise_existing_plan",
  "target": "active_plan",
  "confidence": 0.98
}
```

会话主管在路由决策时不需要读取完整训练计划，也不需要看到训练工具的详细结果；这一步只负责路由，因此不应暴露无关业务数据。会话主管的路由输出是运行时状态的更新，不是最终用户回复。Harness 根据结果切换节点：

```json
{
  "current_node": "workout_agent",
  "route": {
    "domain": "workout",
    "intent": "revise_existing_plan"
  }
}
```

## 示例：Workout Agent 只获得当前执行所需的上下文

Workout Agent 被调度后，上下文装配器读取业务数据和运行时状态，为当前节点生成工作视图：

```text
当前任务：
修改 plan_88 的 exercise_2

当前计划：
plan_88@v2
时长上限：60 分钟

当前动作：
exercise_2：杠铃推举，3 组 × 10 次

用户约束：
今天肩部不适

当前阶段：
plan_revision

当前步骤：
search_replacement

当前技能：
revise_workout_plan

技能规则：
1. 只修改用户指定的动作。
2. 保留其他动作和参数。
3. 替换后重新评估训练量。
4. 生成新版本草稿。
5. 用户确认前不得发布计划。

当前可用工具：
- search_exercise
- evaluate_training_load
- update_plan_draft
```

模型不需要看到完整运行时状态，也不需要看到会话主管的全部输入。上下文装配器把原始数据转换成当前节点真正需要的工作视图。模型随后生成工具调用：

```json
{
  "tool_name": "search_exercise",
  "arguments": {
    "plan_id": "plan_88",
    "plan_version": 2,
    "replace_item_id": "exercise_2",
    "target_muscle": "chest",
    "avoid_body_parts": [
      "shoulder"
    ],
    "limit": 5
  }
}
```

## 装配链路

系统每次调用 LLM 的上下文生成链路：

```text
LangGraph 状态 / Checkpoint
工具结果 / 任务产物
          │
          ▼
    确定性状态投影
          │
          ├── 当前工作状态栏
          ├── 程序化派生信息
          └── 必要任务数据
          │
          ▼
     上下文装配器
          │
          ├── 当前节点上下文策略
          └── 当前能力配置
          │
          ▼
     模型上下文
```

底层保存全量事实，上层模型拿到过滤后的视图：底层运行状态负责业务流转与故障恢复，装配层负责让模型只看到本轮决策需要的信息，模型不再从冗长历史里反推任务阶段。

## 示例：工具调用必须经过 Harness 校验

模型提出的工具调用不能直接执行。Harness 先校验参数与当前状态的一致性：

```json
{
  "validation": {
    "plan_id_matches_active_plan": true,
    "plan_version_matches_runtime": true,
    "replace_item_exists": true,
    "tool_enabled_for_current_phase": true
  }
}
```

校验通过后，工具运行时调用真实服务：

```json
{
  "tool_name": "search_exercise",
  "status": "success",
  "result": {
    "items": [
      {
        "exercise_id": "machine_chest_press",
        "name": "器械胸推",
        "shoulder_load": "low"
      },
      {
        "exercise_id": "cable_chest_press",
        "name": "绳索夹胸",
        "shoulder_load": "low"
      }
    ]
  }
}
```

Harness 把结果写回状态，同时推进执行步骤：

```json
{
  "artifacts": {
    "candidate_exercises": [
      {
        "exercise_id": "machine_chest_press",
        "name": "器械胸推",
        "shoulder_load": "low"
      },
      {
        "exercise_id": "cable_chest_press",
        "name": "绳索夹胸",
        "shoulder_load": "low"
      }
    ]
  },
  "execution": {
    "current_step": "evaluate_replacement"
  }
}
```

职责边界：模型负责提出动作，Harness 负责校验权限、版本和参数，工具运行时负责执行真实业务操作。正式数据不能由模型直接写入。

## 示例：修改结果进入任务草稿，不推正式版本

模型请求更新草稿：

```json
{
  "tool_name": "update_plan_draft",
  "arguments": {
    "plan_id": "plan_88",
    "base_version": 2,
    "changes": [
      {
        "item_id": "exercise_2",
        "operation": "replace",
        "new_exercise_id": "machine_chest_press",
        "sets": 3,
        "reps": 10
      }
    ]
  }
}
```

草稿服务先校验 base_version 与业务数据库当前正式版本一致——基于过期正式计划的修改不被接受（乐观并发控制见 [[7.版本控制与并发]]）——然后把修改结果写入任务草稿 D200，业务数据库不动：

```text
草稿存储（drafts）
task_id   = task_7001
draft_id  = D200
draft_version = 1
status    = EDITING
base      = plan_88@v2
changes   = exercise_2 替换为 machine_chest_press（3 组 × 10 次）
```

运行时状态随之更新，引用草稿而不推进正式版本：

```json
{
  "draft_id": "D200",
  "draft_version": 1,
  "execution": {
    "phase": "awaiting_confirmation",
    "current_step": "wait_for_confirmation"
  },
  "capabilities": {
    "enabled": [
      "confirm_plan",
      "request_revision"
    ],
    "disabled": [
      {
        "name": "publish_plan",
        "reason": "draft_not_confirmed"
      }
    ]
  }
}
```

模型只提出修改请求，任务草稿由草稿存储管理，业务数据库的正式计划保持 plan_88@v2。前端读取任务草稿 D200，而不是读取模型生成的文本；用户确认后，修改经第四章工具运行时以工具调用实例提交（prepare 固化动作、执行产生业务效果，见 [[9.代码级逻辑：从提议到业务副作用]]），业务数据库才生成新的正式版本 plan_88@v3。正式业务事实与任务草稿是两层身份：前者只保存已确认生效的计划，后者承载进行中的修改。

## 示例：一次完整请求的最小闭环

把上面各环节串起来，就是一次完整请求。用户输入「第二个动作换掉，我今天肩膀不太舒服。」后，系统依次执行：

```text
1. API Gateway 写入 user_message 事件
2. 运行时恢复 task_7001
3. Supervisor 判断 domain=workout、intent=revise_plan
4. Harness 写入 target_item_id=exercise_2
5. 上下文装配器加载正式计划 plan_88@v2
6. Workout Agent 只获得计划修改技能和当前允许工具
7. 智能体调用 search_exercise
8. Harness 校验工具调用
9. 工具运行时返回候选动作
10. Harness 更新 candidate_exercises 和 current_step
11. 上下文装配器重新生成当前工作状态
12. 智能体调用 evaluate_training_load
13. 智能体调用 update_plan_draft
14. 草稿存储写入任务草稿 D200（基于 plan_88@v2）
15. 运行时进入 awaiting_confirmation
16. 前端读取任务草稿 D200（用户确认后经工具运行时提交，业务库产生 plan_88@v3）
```

各组件职责边界：

```text
业务数据库：保存正式训练计划和版本
草稿存储：保存任务草稿 D200（尚未确认的修改）
任务控制索引（agent_task_runtime）：保存当前任务执行状态
事件存储：API 层的输入事件通道，保存用户事件和工具事件
工具运行时：执行真实业务操作
上下文装配器：把当前节点需要的数据转换成模型上下文
模型：根据当前上下文选择下一步动作或调用工具
Harness：校验模型输出、推进状态、写入 Checkpoint
```

这条闭环浓缩了本章的核心结论：完整运行时状态不等于模型上下文。模型上下文是当前节点的工作视图，由业务数据、运行时状态、事件和能力配置按需装配而成；能由程序确定的状态交给程序维护，需要模型判断的部分才交给模型；能力按业务域和技能渐进装载，固定流程由 Harness 推进，动态流程才按需调用规划器。

## 边界问答

**1. Q：** 为什么装配器只读状态，不参与路由、不修改状态？

**A：** 装配器被定义成数据转换层：读取前序确定的系统运行状态，按当前节点的上下文策略生成模型输入。路由决策属于状态图，状态写入也属于状态图；装配器一旦承担这两项职责，模型输入就不再是从确定状态派生出来的纯转换结果。

**2. Q：** 为什么各节点不共享同一份上下文？

**A：** Supervisor 的路由决策只需要用户输入、会话边界和轻量能力描述，训练计划流程才需要草稿和工具结果。全量共享会把无关数据带进每轮决策，业务边界也会被抹平；不同节点绑定不同上下文策略，由装配器按策略过滤。

**3. Q：** 三类数据为什么不能直接拼成一段 Prompt？

**A：** 三类数据的用途和生命周期不同：业务数据要长期保存，任务数据随执行推进，输入事件是单次请求的瞬时输入。直接拼接会把无关数据带进每轮决策，所以由不同组件按需读取，再转换成当前节点需要的上下文。

**4. Q：** 模型为什么不能直接修改运行时状态？

**A：** 运行时状态是 Harness 的执行依据。模型只能通过结构化输出或工具调用请求 Harness 执行操作，工具执行成功后由 Harness 写回状态；让模型直接改状态，等于把任务阶段定位重新交给概率性推测。
