# KV Cache 与上下文布局

## 键值缓存与布局的关系

键值缓存是推理引擎为已处理的前缀保存的键值缓存：前缀不变就能复用，省掉这部分重复计算。模型输入上下文按数据变化频率分层排列，目的就是让稳定的前缀尽可能长、尽可能可复用。

## 分层布局

静态程度最高的内容统一部署在上下文前端，并保持物理顺序与内容绝对稳定：系统提示词（System Prompt）、智能体基础职责约束、全局业务规则定义、长期固定的工具描述。其后衔接自然语言交互的任务轨迹。动态更新频率最高的当前工作状态栏和本轮用户输入，被约束在上下文尾部。

```text
稳定系统提示词
固定智能体职责
固定业务规则
固定工具 / 模式
────────────────────
当前任务历史轨迹
────────────────────
当前工作状态栏
当前用户输入
```

## 示例：稳定前缀与动态后缀

以 Workout Agent 为例。稳定内容包括：

```text
系统提示词
智能体固定职责
安全规则
技能指令
固定工具模式
```

动态内容包括：

```text
当前计划版本
当前步骤
最新工具结果
当前工作状态
最新用户输入
```

上下文装配器固定排列顺序：

```text
[稳定前缀]
系统提示词
智能体职责
安全规则
技能指令
工具模式

[动态后缀]
当前计划
当前步骤
事件侧信道
当前工作状态
最新用户输入
```

稳定内容放在前面，动态内容放在后面，有利于复用稳定前缀对应的键值缓存。状态栏不应放在系统提示词前面：状态栏每轮变化，放在前面会破坏后续所有前缀的稳定性。

## 状态栏后置的缓存理由

状态栏每一轮都被重置替换，是上下文里变化最频繁的部分。放在尾部，缓存失效只波及状态栏之后的一小段；前端的静态指令区和历史基线仍然可以复用推理引擎侧的前缀缓存。状态栏本身的设计见 [[4.AgentStatus 当前工作状态栏]]。

## 正确性优先于缓存友好

这个布局有一条明确的原则：如果缓存友好设计与当前状态的精确表达发生工程冲突，无条件优先保障上下文事实的正确性。

## 边界问答

**1. Q：** 为什么前端稳定层连物理顺序都要固定？
**A：** 前缀缓存按前缀内容逐段匹配复用，稳定层任何内容和顺序的变化都会让整段前缀失效。所以系统提示词、职责约束、业务规则和工具描述统一部署在前端，并保持顺序与内容绝对稳定。

**2. Q：** 状态栏每轮替换损失缓存，为什么可以接受？
**A：** 替换只影响状态栏之后的一小段前缀缓存，前部稳定层不受影响。追加虽然缓存友好，但会让失效的中间状态快照在上下文里越积越多。取舍是承担尾部一小段缓存失效，换状态视图的准确。
