# 记忆写入与生命周期

## 事件缓冲：先落地再批量抽取

长期记忆不在每条用户消息结束后立即调用一次大模型抽取。普通会话事件先进入 `user_id` 范围内的持久化事件缓冲，再以批次方式做记忆抽取。

主要流程：

```text
会话事件
        ↓
记忆事件缓冲
        ↓
达到刷新条件
        ↓
批次记忆抽取
        ↓
情节候选
        ↓
结构校验
+ 归属校验
+ 幂等检查
        ↓
情节记忆
```

缓冲采用 Postgres 持久化，而不是放在 LangGraph 状态里。原因是缓冲的生命周期是跨线程、面向用户长期记忆的，而 LangGraph 状态属于某个会话线程的控制和运行状态（见 [[5.Task Runtime、Checkpoint 和业务状态]]）。

缓冲中的事件仍然保留来源信息：

```text
event_id            # 事件唯一标识
user_id             # 归属用户
thread_id           # 来源会话线程
task_id             # 所属任务（可为空）
source_agent        # 来源智能体，如 workout / diet / supervisor
source_message_id   # 来源消息
content             # 事件文本
created_at          # 事件产生时间
status              # pending / flushed / invalid
```

## 抽取的批次视野与职责

默认刷新条件包括事件或令牌达到一定阈值、用户进入空闲状态以及当前任务正常结束。记忆抽取以批次为输入，可以看到一段完整局部上下文，从而减少把一次临时安排错误抽取成长期偏好的概率。

例如：

```text
用户：今天晚上训练吧。
```

单独看这一句话很容易错误形成：

```text
用户偏好晚间训练。
```

如果和完整任务上下文一起处理，系统可以识别它只是今天的安排，不需要形成长期记忆。

记忆抽取只负责生成情节候选，不负责更新语义、修改画像或判断旧记忆是否应该被替换。它的职责尽量收窄为：

```text
这段用户事件中，有没有值得跨会话保存的长期经历？
```

长期保存的主要候选包括明确长期偏好、目标或状态变化、重要训练或饮食经历、长期约束，以及用户明确要求系统记住的信息。普通寒暄、临时任务选择、智能体自己生成的内容、完整工具结果以及已经存在于业务数据库的业务记录不自动转换成记忆。语义是否成立、当前是否有效，交给后续围绕同一 `state_key` 的 [[7.语义巩固与用户画像#语义巩固]] 判断。

## 幂等：只追加但禁止重复写入

只追加也不等于允许同一个抽取批次重复写入相同事件。工作线程会通过 `source_event_id + extraction_batch_id + candidate_index` 形成幂等键，避免任务重试产生两条完全相同的情节。

但系统不会使用向量相似度判断「这条新记忆是否应该覆盖旧记忆」。相似度只用于寻找相关证据，不用于决定是否覆盖，这个原则见 [[8.证据检索#相似不再等于同一事实]]。

## 关键事实热路径

记忆形成默认采用后台批次，但安全相关信息、明确要求长期记住的信息，以及关键画像状态变化允许走窄热路径。

例如用户说：

```text
我对花生严重过敏。
```

不能等到若干分钟后的缓冲刷新和后台巩固才对智能体生效。

这类事件走：

```text
关键用户陈述
        ↓
立即抽取
        ↓
归属校验 / 结构校验
        ↓
情节记忆
        ↓
立即画像投影
```

语义巩固仍然可以后台完成。因此热路径提供的是「立即持久化和立即进入当前状态」的保证，而不是同步执行整条记忆处理链路。

热路径不允许绕过归属校验。例如「我朋友对花生过敏」不能因为命中了「过敏」关键词就直接写入当前用户的过敏画像。归属校验要判断这条信息的主体是不是用户本人。

## 重要性信号与生命周期

记忆不维护一个不断被后台任务修改的统一 `importance_score`。不同类型的重要性信号被拆开处理：

```text
salience
→ low / normal / high

safety_level
→ normal / critical

时间状态
→ 当前 / 历史 / 未来 / 未知
```

安全信息不会因为长期没有访问而自动降低重要性。近期性、当前有效性以及历史状态更多作为检索阶段的动态排序信号，而不是反过来修改记忆本身。

当前版本也不主动因为记忆较旧就删除情节历史。旧情节可以降低普通检索优先级，但仍然保留用于时间追溯、冲突分析和语义证据补充。只有系统错误、用户删除请求或数据治理要求才触发显式失效 / 删除。

## 边界问答

**1. Q：** 为什么事件缓冲用 Postgres 而不用 LangGraph 状态？

**A：** 缓冲的生命周期是跨线程、面向用户长期记忆的；LangGraph 状态属于某个会话线程的控制和运行状态，生命周期与任务执行绑定。缓冲放在 Postgres 才能跨会话、跨任务、跨重启持久保存。

**2. Q：** 为什么不每条消息都立即抽取，而要等批次？

**A：** 单条消息缺乏上下文，容易把临时安排（“今天晚上训练吧”）误抽成长期偏好。批次抽取能看到一段完整局部上下文，区分今天的一次安排和长期状态。

**3. Q：** 为什么安全事实要走热路径，而普通记忆走后台批次？

**A：** 安全信息需要立即持久化并立即进入当前状态，不能等若干分钟后的缓冲刷新和后台巩固才生效。热路径只保证「立即落库、立即投影到画像」，语义巩固仍可后台完成，不同步跑完整条记忆处理链路。

**4. Q：** 热路径为什么不允许跳过归属校验？

**A：** 命中了「过敏」关键词不代表信息属于用户本人。归属校验判断主体是否为当前用户，避免把「我朋友对花生过敏」错误写入用户的过敏画像。

**5. Q：** 为什么不维护一个统一的重要性分数？

**A：** 不同类型的重要性信号（`salience`、`safety_level`、时间状态）含义和用途不同，混成一个会掩盖语义。安全信息不应因为长期没被访问就降低重要性；近期性和当前有效性只作为检索阶段的动态排序信号，不反过来改写记忆本身。
