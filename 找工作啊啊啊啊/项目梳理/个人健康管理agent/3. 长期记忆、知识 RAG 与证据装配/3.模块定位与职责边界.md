# 模块定位与职责边界

## 模块解决什么问题

长期记忆模块负责管理跨线程、跨任务持续存在的用户信息，并在当前任务需要时，从长期记忆、用户画像、业务数据库和领域知识库中检索相关证据。

它解决的并不是「如何把历史聊天重新放进 Prompt」，而是两个更底层的问题：哪些信息值得长期保存，以及当前任务真正需要哪些长期事实和外部知识。

系统中的 LangGraph 检查点保存器（保存图执行位置的持久化机制，见第一章 [[5.Task Runtime、Checkpoint 和业务状态#LangGraph 检查点语义]]）只负责线程范围内的运行状态与对话恢复，例如当前图执行到哪个节点、任务中断后从哪里恢复。这类状态属于控制状态，不等同于长期记忆。长期记忆以 `user_id` 为主要作用域，即使用户开启新的会话线程，仍然能够读取已经形成的长期认知。

## 与上下文装配的接口

第三章不负责最终 Prompt 拼装。记忆、画像、业务数据库和领域知识经过检索与证据处理后统一输出证据包（EvidenceBundle），由第二章的上下文装配器（见 [[3.上下文装配器与 ContextPolicy]]）决定哪些证据进入当前大模型上下文、采用什么顺序以及占用多少令牌。

两个模块之间的分工：

```text
第三章：
长期信息如何保存
→ 当前任务需要检索什么
→ 哪些事实当前有效
→ 证据来自哪里
→ 输出证据包
    │
    └── 交给第二章
第二章：
证据包中哪些内容进入本轮上下文
→ 如何裁剪
→ 如何组织
→ 如何与任务状态、会话上下文一起装配
```

## 与多智能体的权限边界

第五章的会话主管（Supervisor）和领域智能体（Domain Agent）也不会默认共享所有用户记忆。会话主管或领域智能体根据当前领域任务判断是否需要长期用户信息或领域知识，再显式调用对应检索能力。

普通常识问题不触发记忆检索，需要领域个性化信息时才读取相关证据，从而避免长期记忆重新演化成一份所有智能体每轮都加载的全局上下文。会话主管的委派协议见 [[4.Supervisor 架构与委派]]，领域智能体的执行模型见 [[5.Domain Agent 执行模型]]。

## 四类数据来源

整个长期信息体系的数据来源最终分为四类：

```text
用户画像
→ 当前高价值用户状态

用户记忆
→ 跨会话保存的用户历史与长期认知

业务数据库
→ 正式业务事实

领域知识
→ 健身 / 饮食领域公共知识
```

这些数据可以共同支持一次智能体任务，但不会因为统一进入证据装配就混成同一种存储。每一类的读写语义和存放位置各不相同，见 [[4.长期记忆语义模型]] 与 [[8.证据检索#业务事实归业务库]]。

## 边界问答

**1. Q：** 长期记忆和 LangGraph 检查点保存器有什么区别？

**A：** 检查点保存器只负责线程范围内的运行状态与对话恢复，属于控制状态；长期记忆以 `user_id` 为主要作用域，面向跨会话、跨任务的用户信息。前者回答「这个任务执行到哪、中断后从哪恢复」，后者回答「关于这个用户，系统应长期保存什么、当前任务需要什么」。

**2. Q：** 为什么第三章不直接拼装 Prompt？

**A：** 第三章只负责把四类数据统一转成证据包并保留来源、标记有效性、识别冲突；哪些内容进入本轮模型上下文、顺序与令牌预算，由第二章上下文装配器决定。

**3. Q：** 为什么不把所有记忆默认共享给每个智能体？

**A：** 会话主管或领域智能体根据当前领域任务显式判断是否需要长期用户信息，再调用对应检索。普通常识问题不触发记忆检索，这样避免长期记忆变成每个智能体每轮都加载的全局上下文，也避免无关信息污染模型上下文。
